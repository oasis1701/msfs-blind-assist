# First Officer rules

Loaded when Claude reads matching code. Background: docs/first-officer.md. Full text of each rule: docs/invariants/first-officer.md. Per-family rules: first-officer-boeing.md, first-officer-airbus.md; the automation beside the flows (auto-flaps, auto-AP, 10k lights, altimeters): first-officer-automation.md.

- [FO-1] One First Officer form for every aircraft via `IFoProfile<TExec,TState>`: the profile injects executor, evaluator and data. Full: docs/invariants/first-officer.md#fo-1
- [FO-2] No FMC programming, ever (owner decision): keep checklist text, V-speed reads and SimBrief load-only; never reintroduce CDU-keystroke automation. Full: docs/invariants/first-officer.md#fo-2
- [FO-3] `*_CL` read-back groups are action-free (no item has a non-null `CheckAction`); state/action groups fire the switch on tick and auto-detect from live state. Full: docs/invariants/first-officer.md#fo-3
- [FO-4] `FlowManager`'s "<flow> flow complete" is NON-INTERRUPTING (`Announce`), never `AnnounceImmediate`, which cuts off the flow's last step (a skipped wait's "Timed out… / Skipping…" heard as silence, then success); pinned by `FlowManager_FlowComplete_IsNonInterrupting`. Full: docs/invariants/first-officer.md#fo-4
- [FO-5] `FlowManager`'s 2 s inter-step pause (`InterStepPauseMs`, "Already set" skips included) is deliberate realism pacing for a screen-reader pilot: never remove or shrink it as an optimization; it layers on top of executor write spacing. Full: docs/invariants/first-officer.md#fo-5
- [FO-6] `FlowManager` marks, and on a SKIP excludes from the latch, EVERY id in `FlowStep.LinkedChecklistItemIds`, never only `CompletesChecklistItemId`; a WRITE step links the line it sets. A flow latches `FlowDefinition.CompletionGroupIds`, never `RelatedChecklistGroupIds` alone (more: see full). Full: docs/invariants/first-officer.md#fo-6
- [FO-7] A checklist item with no flow step behind it is still TICKED AND LATCHED when its flow finishes (`MarkGroupComplete` excludes only steps the run SKIPPED: failed, left alone, dependency or FO-20 no-value): every actionable item in a state group needs a delivering step; add one, never rely on the exclusion set. Full: docs/invariants/first-officer.md#fo-7
- [FO-8] A group completed with participation (manual tick or flow MarkComplete) is completion-LATCHED; never latch on auto-ticks alone, never item-level StayComplete or an unconditional 100% latch. An undelivered item is freed per item by `ChecklistItem.ExemptFromCompletionLatch`, whose clear is UNCONDITIONAL (more: see full). Full: docs/invariants/first-officer.md#fo-8
- [FO-9] A hand-tick that fires a linked `CheckAction` sets `AwaitingActionConfirmation`; if `RevertToState` un-ticks it because the switch never moved, `ChecklistManager` raises `ItemActionFailed` ("Unable to complete: {label}"), never for an ordinary revert, and from inside a latched group too when the item is exempted. Full: docs/invariants/first-officer.md#fo-9
- [FO-10] Checklist revert grace is action-aware: `ChecklistManager.RunCheckActionWithGraceAsync` holds the revert until the tick's action completes AND the executor's dispatch gate drains (`IFoActionExecutor.WaitForDispatchDrainAsync`), covering multi-second selector walks and anything queued behind them. Full: docs/invariants/first-officer.md#fo-10
- [FO-11] A checklist item whose state field is a SLOW condition needs its `CheckAction` to hold open until it is true; the 10 s `ManualTickGrace` will not cover it (the Fenix, A32NX and A330 `StartApuAsync` poll AVAIL). Read the Fenix lamp only via `ApuAvailField`; never infer a Fenix legend (more: see full). Full: docs/invariants/first-officer.md#fo-11
- [FO-12] A hand-tick never re-does work the pilot already did: `ChecklistManager.ToggleItem` skips the `CheckAction` (and the `AwaitingActionConfirmation` mark) when the item's own state reads DEFINITELY true; NaN still runs it, and it is gated on `IsAutoDetectable`, so self-tests with no state field fire every tick. Full: docs/invariants/first-officer.md#fo-12
- [FO-13] Each FO gear checklist line ("Landing gear: UP"/"DOWN") is backed by a READ-ONLY wait, the LAST step of the flow that latches it (20 s, Skip, never writes), reading lights or legs per aircraft (`GearLightRules`, `*GearConfirmation`); NaN when any input is unknown. Never add a gear WRITE to a check (more: see full). Full: docs/invariants/first-officer.md#fo-13
- [FO-14] The landing autobrake is a CAPTAIN item on every aircraft: never automate it in a descent/approach flow or checklist action; the reminder names the panel location, with no suggested setting (RTO arm before takeoff and autobrake OFF after takeoff/landing stay automated). Full: docs/invariants/first-officer.md#fo-14
- [FO-20] `FlowManager` treats a `FlowStep.TargetValueProvider` returning null as a SILENT SKIP: nothing is sent or spoken (the paired Captain reminder speaks), its linked lines are not marked and stay out of the latch, and its id counts as skipped for `RequiresStepId`. Never a quiet success (more: see full). Full: docs/invariants/first-officer.md#fo-20
- [FO-22] A First Officer window that first sees the aircraft flying without a takeoff it watched (`InFlightStartDetector`) marks every departure group through After Takeoff complete and latched (`FoDepartureGroups.MarkComplete`), one queued announcement; never an arrival group; every profile group sits in exactly one set. Full: docs/invariants/first-officer.md#fo-22
- [FO-24] Only `FirstOfficerWindows` (exact aircraft code) says which aircraft has a First Officer window; never a per-aircraft field, Show method, menu item or type test in MainForm. Full: docs/invariants/first-officer.md#fo-24
