> **Read this when:** working on the Gemini AI features (display reading, scene/route description, model selection, retry/backoff).

## Gemini AI (display reading + scene/route description)

**AI provider abstraction (`Services/IAiProvider.cs`).** The three AI features (on-demand cockpit-display reading, scene description, the Shift+E route briefing) run behind `IAiProvider` — `AnalyzeDisplayAsync` / `AnalyzeSceneAsync` / `DescribeRouteAsync` / `ListAvailableModelsAsync`. Two implementations: **`GeminiService`** (Google) and **`ClaudeService`** (Anthropic). The user picks one in the unified Settings dialog's **AI panel** (`Forms/Settings/AiSettingsPanel.cs`, a provider combo Gemini/Claude + each backend's fields; model lists populate LAZILY — only the visible provider's list is fetched on dialog open, the other on first switch, so opening Settings never fires two network calls), persisted as `UserSettings.AiProvider`; **`Services/AiProviderFactory.Create()`** returns the chosen backend. The three call sites — `MainForm.DescribeSceneAsync`, `BaseAircraftDefinition.ReadDisplay`, `ElectronicFlightBagForm` route — build via the factory and never branch on provider. **`ReadDisplay` takes an optional `Services.InstrumentViewRequest`** (the SimConnectManager as `ICameraViewIo` + a 0-based instrument-view index): the sim camera is moved to that view before the capture and put back afterwards — written, verified by read-back, a failure spoken once, and done BEFORE the AI call so the pilot's own view is gone for well under a second (the restore was removed 2026-09-09 and reinstated 2026-09-18 when the iFly round-tripped both a custom pilot view and a cabin quickview; docs/md11.md "The restore") — (`Services/InstrumentViewPlan` pure + `InstrumentViewSwitcher`, camera IO in `SimConnectManager.Camera.cs`). The reads are tables of `Aircraft/AiDisplayRead.cs`, dispatched once by `BaseAircraftDefinition.HandleHotkeyAction` from each definition's `DisplayReads` override — an aircraft gains display reads by supplying a table and nothing else. **Five aircraft move the camera**: the MD-11 (`Aircraft/MD11/Md11DisplayReads.cs`), the iFly 737 MAX8 (`Aircraft/IFly737DisplayReads.cs`), the PMDG 737-800 (`Aircraft/Pmdg737DisplayReads.cs`), the Fenix A320 (`Aircraft/FenixA320DisplayReads.cs`) and the PMDG 777 (`Aircraft/Pmdg777DisplayReads.cs`). Only the HorizonSim 787 (`HS787DisplayReads`) still carries a NULL view index on every row, which captures whatever is on screen — exactly what its hand-written switch arms did; measuring its views on the live aircraft turns each null into a number and nothing else changes. **Capture is `PrintWindow` first, BitBlt screen copy when the frame is blank** (`ScreenshotFrame.LooksBlank`), so an MSFSBA window over the sim no longer lands in the picture — scene description included. **Hard switch: when Claude is selected ALL three features go through Claude; no silent cross-provider fallback.** Shared bits: `AiModelInfo` (the dropdown item, `ToString()` is what NVDA speaks) and the three provider-neutral prompt builders (`GeminiService.Get*Prompt`, now `internal static`, reused by `ClaudeService` so wording stays in sync). `DisplayType` stays nested on `GeminiService` (the aircraft defs reference `GeminiService.DisplayType` — don't churn them). The MD-11 prompts are `DisplayType.PFDMd11` / `NDMd11` / `EADMd11` / `SDMd11` / `ISFDMd11`, pinned by `DisplayPromptTests`.

**Claude (`Services/ClaudeService.cs`).** Raw `HttpClient` + Newtonsoft (mirrors the Gemini transport, NO Anthropic SDK dependency). `POST /v1/messages` with `x-api-key` + `anthropic-version: 2023-06-01` headers set PER-REQUEST (the HttpClient is static/shared); vision = base64 `image` content block before the text block; route briefing adds the `web_search_20260209` server tool when `UserSettings.ClaudeWebSearch` is on (the NOTAM-grounding equivalent of Gemini search grounding — extra cost; this is the current dynamic-filtering variant, supported on the default Opus 4.8 + Sonnet 4.6. If the selected model rejects it — e.g. Haiku 4.5 — `DescribeRouteAsync` catches the web_search-named 400, retries ungrounded, and PREFIXES the briefing with a spoken "not grounded with current NOTAM or weather data" note — the degrade must stay AUDIBLE, never silent, per the no-silent-fallback rule), **capped at `max_uses=5`** (an uncapped multi-airport NOTAM briefing runs 10+ searches → slow + $10/1000 searches). **Web-search "process narration" stripping:** the route call also sends a `system` prompt telling the model to output only the briefing, AND `ParseResponse` keeps only the text AFTER the last tool block (`server_tool_use`/`web_search_tool_result`) — together these drop the "Let me search for NOTAMs… now I'll compose the briefing." narration that otherwise leaked ahead of the briefing (a plain vision/text response has no tool blocks, so all text is kept). **`ParseResponse` also surfaces `stop_reason`:** on `max_tokens`/`pause_turn` it appends "(Response may be incomplete — Claude stopped before finishing.)" — or a clear stopped-early message when no answer text survived — because a blind user cannot visually notice a briefing that just stops. **`max_tokens` is REQUIRED by the Messages API** (cannot be omitted); it is 16000 — effectively uncapped for these outputs (a briefing is ~700 tokens) and the documented ceiling for non-streaming requests (larger values need SSE streaming). **Vision screenshots are downscaled client-side to ≤2576 px long edge** (`ComputeScaledSize` + a System.Drawing re-encode; failures fall back to the original bytes): Anthropic caps each image at 5 MB (a 4K PNG screenshot can exceed it) and current models accept at most 2576 px on the long edge before downscaling server-side anyway, so nothing is lost — 1080p/1440p pass through untouched. The pure logic (narration strip, stop_reason, retry delays, scaled sizing) is pinned by `tests/MSFSBlindAssist.Tests/ClaudeServiceTests.cs`. Models from `GET /v1/models` (newest-first, filtered to `claude-*`). Same retry (429/5xx/timeout/connection) + fail-fast (400/401/403/404) shape as Gemini. **No thinking param** (omitted → no extended thinking on Opus 4.7/4.8; keeps display reads fast + cheap). **User-supplied key only** (`UserSettings.ClaudeApiKey`); MSFSBA never pays centrally. Default model `claude-opus-4-8` (Anthropic has no `*-latest` alias — the dropdown lets the user pick Sonnet/Haiku for lower cost). Cost rule of thumb: ~1.5¢/display read on Opus 4.8, so ~$5/month covers a typical hobby flyer; Haiku 4.5 is ~5× cheaper.

**Live-verified (2026-06, real Anthropic API):** Opus 4.8 text + vision work end-to-end — it read a real 1920×1080 MSFS cockpit screenshot exactly (PFD ALT/QNH/heading/THS, ND mode/waypoint/TCAS). **Fable 5 (`claude-fable-5`) is LISTED by `GET /v1/models` but 404s on use** for non-enrolled accounts ("Claude Fable 5 is not available. Please use Opus 4.8" — Fable/Mythos are access-gated programs). So it appears in the AI tab's model dropdown but, if selected, the 404 fail-fast handler shows "model 'claude-fable-5' is unavailable — choose a different model" (graceful, no crash). Don't special-case it; the list endpoint reports models you can *see* but may not be entitled to *use*. **web_search caveats (live Anthropic docs):** dynamic filtering (more accurate, fewer tokens) **requires also declaring the `code_execution` tool** — MSFSBA declares only `web_search`, so it currently gets BASIC search; NOTAM coverage via web search is inherently weak (NOTAMs live in FAA/ICAO systems, not well web-indexed — a dedicated NOTAM API is the real fix, not tool tuning). If web-grounded briefings ever exceed the 120s `HttpClient` timeout, **streaming** is the proper fix (SSE keeps the connection alive through the search pause); `max_uses=5` is the current lighter mitigation. **⚠️ Never paste an API key into chat/logs/code — user keys live only in `UserSettings.ClaudeApiKey` (entered in the Settings dialog's AI tab).**

`Services/GeminiService.cs` powers the Gemini backend (on-demand cockpit-display reading, scene description, and the Shift+E route briefing). Key points:
- **Model is USER-SELECTABLE, not a fallback chain.** The model used for every AI call is `UserSettings.GeminiModel` (default `gemini-flash-latest`, a rolling alias). The AI settings panel (`Forms/Settings/AiSettingsPanel.cs`, Gemini section) populates a `DropDownList` from a LIVE fetch — `GeminiService.ListAvailableModelsAsync()` (`GET …/v1beta/models`, filtered to `generateContent`-capable text/vision models, newest-first) — with a curated fallback list (`gemini-flash-latest`, `gemini-3.5-flash`, `gemini-2.5-flash`) when offline / no key / fetch fails. Do NOT reinstate a silent multi-model fallback: it hid which model produced a response, which the user rejected.
- **Do NOT send `thinkingConfig`/`thinkingBudget`.** `thinkingBudget` is the Gemini 2.5 parameter; Gemini 3.x models use `thinking_level` and treat `thinkingBudget` as deprecated (and error if both are set). The default models (`gemini-3.5-flash`, `gemini-2.5-flash`) already enable dynamic thinking by default, so omitting `thinkingConfig` keeps thinking on for accuracy across every selectable model without sending a wrong/redundant parameter.
- **Reliability = per-request retry/backoff.** `SendRequestAsync` retries transient failures (429, 500/502/503/504, HTTP timeout, connection-level `HttpRequestException`) with backoff and fails fast on client errors (400/401/403/404, where 404 means "model unavailable — pick another"); on exhaustion it throws a clear "Gemini is busy or unavailable — please try again" message. The timeout catch must NOT gate on `ex.CancellationToken.IsCancellationRequested` (false on a modern .NET HttpClient timeout) — catch `TaskCanceledException` as the timeout (the `SimBriefService` pattern).

## Taxi routes in the route briefing (2026-09-25)

The EFB's Describe Route briefing ends with a **TAXI OUT AND TAXI IN** section. The app computes the expected taxi-out (stand → departure runway) and taxi-in (landing exit → stand) routes from the pilot's own scenery data and appends a plain-text `TAXI ROUTES` block to the SimBrief flight data for that AI call only (`ElectronicFlightBagForm.BuildTaxiRoutesBlockAsync`; the stored `ExtractedFlightData` stays pure SimBrief). The prompt's section 7 makes the AI tell that route as ONE short paragraph per leg, in the voice of real-world operations, answering the owner's question ("Provide the step-by-step taxi route at [ICAO Code] from [Runway] to [Terminal/Gate] in a [Aircraft Type]. Please include the expected taxiways, hold short points, and any specific restrictions.") from the block: the route's names, order, turns, sides and distances come from the block only; each leg says it is the expected route on the pilot's scenery and that SayIntentions or ATC gives the actual clearance (the route is the shortest one, and controllers do not always route that way — KATL's V goes around the west end of 08R/26L); and the AI's own additions (restrictions such as an A380's wingspan limits, current operational information such as a NOTAM closure, usual practice, and at most one sentence per leg that controllers usually route differently) may name only taxiways in that leg's lines, including its "Taxiway names at" list — every edge name on the graph the leg was planned on (`TaxiLegBriefing.AirportTaxiways`). The taxi out runs stand → runway and the taxi in runway → exit → stand (the owner's question names only the second direction, so the prompt says so). Every runway the route crosses is always given — including one where no hold short point could be placed, which the block's hold line then reports as "none could be placed; see the notes" rather than "no runway crossings" (`TaxiLegBriefing.UnheldRunways`) — and any other note only when it changes what the pilot does or hears. An OpenStreetMap leg is called the expected route on OpenStreetMap's map. An unavailable leg still gives what the block has for it (exit, side, stand), gets no route when the aircraft is already at the runway, and otherwise may be answered from general knowledge, said to be so, with a total distance only where the block gives one. History: until 2026-09-26 the section had two parts (the computed route, then a "Real-world practice" answer), which the owner found too long; a real-world-only version the same day invented taxiway names (KMEM "V1", KATL "V3"/"V4") and was reverted.

Everything lives in `Navigation/Briefing/`:

- **Tiers per airport** (`TaxiBriefingGraphSource`): navdata (the graph built exactly as `LandingExitForm` builds it — including its bounded wait, up to 8 s and never past the budget, for the online taxiway-name fetch before the build: that cache is memory-only, and without the wait the first briefing of every session briefed LSZH, whose navdata names none of its taxiways, as "(unnamed)" with no exit while a second press named the route), then `OsmPlanningGraph` — a throw-away graph from the cached OpenStreetMap/apt.dat data, built by `TaxiBriefingGraphSource.BuildAsync` (called from the planner's `PlanAsync`) when the database has NO taxiways for that airport; a local value inside that call, never stored anywhere guidance can reach, carrying its own `OsmPlanningGraph.Note` ("stand types unknown (OpenStreetMap)") as one of the leg's notes — said once: when the stand picker's own "stand types unknown at this airport; the stand may not be a …" is on the leg, that replaces it — the TIER LABEL a pilot actually hears ("OpenStreetMap, planning only — taxi guidance cannot use this") is a separate constant, `TaxiBriefingRenderer.OsmLabel`, applied only when the leg is rendered. `TaxiDataMerger`'s never-steer-on-online-geometry rule is untouched — then nothing, with one of four exact reasons appended to "the navigation database has no taxiways for" the ICAO: "and OpenStreetMap data is not available" (the provider isn't the augmenting one at all), "and online taxi data is disabled in settings", "and OpenStreetMap data is not available right now" (nothing arrived within the budget — offline, still fetching, or genuinely nothing there, three causes this one reason cannot tell apart, so it never promises a retry), or "and OpenStreetMap has no named taxiways for it" (fetched, but empty) — in which case the AI's real-world route is the leg's answer.
- **Units**: EVERY distance, length and width in the block — taxi distances, exit distances from the threshold, the missed-exit separation, wingspans, taxiway widths and the stand picker's notes — is in ONE unit, the pilot's ground distance setting (`GroundDistanceUnit`, read once through `DistanceFormatter.UnitProvider` in `BuildTaxiRoutesBlockAsync` and carried on `TaxiBriefingRequest.Unit`), and the block's second line names it ("Distance unit: feet (the pilot's setting); every distance below is in feet"); the prompt tells the AI to use that unit for the whole taxi section. Feet: whole feet with separators ("7,218 ft"). Metres: taxi distances in metres under a kilometre and kilometres above, runway distances in whole metres ("1,890 m"), sizes to 0.1 m (`TaxiBriefingRenderer.FormatDistance`/`FormatAlongRunway`/`FormatSize`). Never write a distance into the block or a note in a hard-coded unit: live KMEM→KATL (2026-09-26) the block gave taxi distances in km beside exit distances in feet, and the briefing read "2.2 kilometers" and "6,025 feet" in one section.
- **Aircraft** (`AircraftSizeClass`): SimBrief type/name/`max_passengers` ONLY (owner's choice): a wingspan table → Annex 14 code letter → typical touchdown speed; freighter when `max_passengers` is 0, the code is a known freighter code, or the name carries one of `AircraftSizeClass`'s exact freighter-regex suffixes — F/BCF/BDSF/SF/PF/PCF/ERF/LRF, immediately after a digit, dash or space — or the bare word Freighter/Cargo anywhere. Unknown type → no fit filter, no width notes, said so in the block.
- **Taxi-out start**: from the aircraft's own position when SimConnect reports it on the ground within 5 km of the departure airport's reference point and a taxiway-network node lies within 150 m of it (`TaxiBriefingPlanner.OwnPositionMaxAirportDistanceMetres`/`OwnPositionMaxNodeDistanceMetres`) — the block names a stand only when that node actually is one, otherwise "current position"; when the aircraft is already sitting on the runway's own lineup-entry node, the leg says so ("the aircraft is already at the runway NN entrance") rather than describing a zero-length route. Off the ground, elsewhere, or with no SimConnect connection, it falls back to the same representative-stand pick as the arrival leg (below) — with no SayIntentions gate, since SayIntentions never assigns a departure gate.
- **Exit** (`BriefingExitPicker`): among the vacating exits ≤ 90° comfortably reachable at the touchdown speed (`RolloutExitGate.ComfortableExitLeadFeet`, the touchdown re-plan's rule) and within 1,500 ft (`PreferenceWindowFeet`) of the first of them, high-speed exits before the rest, each in runway order — and, when the stand is known, the first of those whose route to it does not cross the runway just landed on, either end (owner decision, 2026-09-26: prefer the exit on the gate side; OMDB 12L now briefs M7A on the right instead of N5A on the left with a re-crossing of 30R). If every one crosses, the usual choice stands. Nothing reachable → the last exit, flagged; when the only comfortable exits were set aside for leading off the other side (below), the block says that instead of calling the runway short. "Next exit if missed" is the next candidate on the SAME side at least 500 ft further along (`NextExitMinSeparationFeet`) — never a turn-off across the runway at the same junction (KPIT 32 had one 1 ft on) — and "none" is worded as no later USABLE exit on that side, since the exits list can still show a later one there that turns more than 90° or was set aside; the set-aside names in the unreachable sentence are capped like the exits list. Measured over 438 runway ends at 60 hubs (B738, fs2024): re-crossings of the landing runway 107 → 57, "next exit" within 500 ft 81 → 0. Only exits whose route begins on the side they turn toward are offered (`TaxiBriefingPlanner.BriefableExitRouteStarts`): `LandingExitDestination.Resolve` — shared with the rollout and deliberately unchanged here — can hand an exit another exit's clear-of-runway node across the runway (KLAX 25L briefed "A7, LEFT side" with the route starting on H6 north of it; 33 of 428 measured hub arrivals), and the prompt makes the AI repeat sides exactly. An exit that names no side takes the side its route leaves by. When the route leaves the runway on a named taxiway other than the exit's own — judged by the segment that takes it off the pavement (`TaxiwayLeavingTheRunway`), never by the route's first taxiway, which usually begins where the exit meets a parallel — the block adds "the mapped route leaves the runway on taxiway X" (EGLL 27L: exit S5W, route on N5E).
- **Stand** (`BriefingStandPicker`) draws from different pools — name them distinctly. The EXCLUDED kinds are navdata types 8/16/17 (Military Combat/Fuel/Vehicles) and de-ice pads (`IsExcludedKind`). A representative stand, chosen only when nothing was assigned or found, comes from the representative pool (`IsRepresentativeCandidate`): no excluded kind and no type 1 — navdata's "unknown" bucket that real jetway gates land in too, e.g. LEBB 101–106 — so a None-type stand is NEVER the representative pick, even when it is the only stand that connects (`A_representative_stand_is_never_of_the_None_type` pins the null result there, not a fallback to it). **The SayIntentions match tries its evidence in the order Taxi Assist's own SayIntentions import does** (`TaxiAssistForm.TryResolveExternalDestination`: `MatchDestinationLabel` → `MatchGateByAlias` → `MatchGateByPosition`; owner decision 2026-09-26, reversing the earlier "the pin wins" rule, since that is how SayIntentions works): the NAME first, the scenery's online ALIASES only when no name matches, and SayIntentions' published position — the pin — only when no name or alias matched at all. The name and alias steps match stands of EVERY kind, type 1 included (ranked after every known type), as the import matches whatever its list carries (fuel and vehicle stands only when that list comes from navdata — GSX's gate list never carries them, though it can carry a military combat ramp — and de-ice pads are a destination type of their own there) — but an ordinary stand always beats an excluded one: the excluded kinds are searched, by name and then by alias, only when no ordinary stand answers either way (owner decision 2026-09-26, "follow the import"). An excluded stand found that way — or at the pin, below — is briefed with the note `"this scenery marks that stand as a fuel stand"` (or `military combat ramp`, `vehicle stand`, `de-icing pad`). A name or alias match counts wherever the stand is; among several, exact name beats alias and the one nearest the pin wins, or with no pin a gate before any other type, then list order. That ranking exists because `NormalizeParkingName` strips the stand-type word, so navdata's "Spot 8" and "Gate 8" normalise to the same name — on the real fs2024 database list order alone would have briefed a same-numbered GA ramp as the assigned gate at roughly 20 airports. When the pin lies outside the chosen stand's own reach (`min(150 m, 2 × radius)`, `SayIntentionsGatePositionMatcher`'s own constants; 60 m for a stand of unknown size, e.g. every OpenStreetMap stand), the block adds `"SayIntentions' position is 1.2 km from this stand"` (the distance by `TaxiBriefingRenderer.FormatDistance`, in the pilot's unit), after the kind note when there is one: the stand is still the one the name found, and the pilot hears that SayIntentions put its gate somewhere else. No pin, no such note. The position step takes the nearest stand whose own reach covers the pin — of an ordinary kind when any is in reach, else of an excluded kind, briefed with the same kind note (the owner's "follow the import" applied to the pin, 2026-09-26: with only a fuel stand at the pin, "no stand at SayIntentions' position was found" was untrue); with nothing in reach at all a representative stand is used and the note says no stand at SayIntentions' position was found in this scenery — a claim about the position, the last evidence tried; "not found at this airport" is kept for a gate with no published position that no name or alias matched. Whichever step found it, the stand must connect to the taxiway network. By name, an unconnected first-ranked namesake gives way only to one at least as plausible (`AtLeastAsPlausible`): where the pin is within the reach of either, one within its own reach; where it is within the reach of neither, one ranking the same or better by the no-position rule (a gate after a ramp the pin was merely nearer) that is also no farther from the pin than the first plus the first's own reach — so a pin far from a gate and a same-numbered GA ramp never lets the ramp stand in for the unconnected gate (the rule for no pin forbids that as well), and a same-kind namesake kilometres farther from the pin than the first never stands in for it. Otherwise the match is reported, naming its kind when it is an excluded one (`"… was found as a fuel stand but does not connect to the taxiway network; using a representative stand instead"`), and a representative stand is used — never one of the stands just refused, so "representative stand Gate 5" can never follow "Gate 5 was found but does not connect". At the pin, the nearest stand in reach that connects is used; when that is not the nearest, ONE sentence names both with their distances, in place of the "lists as" note (`"SayIntentions assigned Gate 99; the stand at its position, B 6 (20 m away), does not connect to the taxiway network, so B 7 (30 m away) is used"`) — the distances tell apart stands this scenery calls the same, and no second note calls the stand used SayIntentions' gate. **Where the briefing still differs from the import, deliberately:** among several namesakes the import takes the first entry its own list offers, while the briefing puts an ordinary stand before an excluded one and then takes the one nearest the pin; an ordinary stand's ALIAS beats an excluded stand's NAME in the briefing, where the import's name step takes the name first, whatever kind of stand its list carries it on; among stands in reach of the pin an ordinary one is preferred, where the import takes the nearest of any kind its list carries; the briefing requires the stand to connect to the taxiway network, the import's resolution does not; and the briefing's position step and far note give a stand of unknown size 60 m, where the import's position match skips a stand with no radius. A substitution — by alias or by position rather than by the stand's own name — is briefed as `"SayIntentions assigned X, which this scenery lists as Y"`, always when SayIntentions' label names no stand at all ("Gate"), even beside a stand whose own label names none either. A label that already says what it is ("Gate 5", "Spot 12", "Parking") is never prefixed with "gate" again ("SayIntentions assigned gate Gate 5"). The representative pick itself, among representative-pool stands that connect: category (freighter → cargo; code A → ramp, gate, cargo; everyone else → gate, ramp, cargo), wingspan fit (`ParkingSpot.FitsAircraft`; unknown size kept), the SimBrief airline's stands, then the stand nearest the group's centroid. Every fallback is a note in the block.
- **Hold-shorts**: `RouteRunwayCrossings.InsertRunwayHoldShorts` with a null aircraft; the departure runway's own entry is always added as the "before entering" hold. Every crossing of the runway just landed on IS briefed, never discarded — the taxi-in route always starts at an exit the vacate screen (`LandingExitVacateScreen`) marked as clear of the runway, so a hold naming the landing runway can only describe a re-crossing of it. A hold on no named taxiway renders `runway NN (crossing)` with no taxiway named, rather than "on taxiway" followed by a blank.
- **Taxiway widths are advisory only**: navdata `taxi_path.width` is mostly a scenery default, so it never changes a route. The commonest value is 82 ft = 24.99 m, on 62.1 % of fs2024 taxiway rows (`T` and `PT`) and 64.6 % of fs2020's; 98 ft (about 30 m) is on only 6.4 % / 2.9 %, though it is on nearly every fs2024 KMEM taxiway (measured 2026-09-26). A taxiway below the code letter's Annex 14 minimum is named in a "Taxiway width note", judged at the block's own 0.1 m precision (`TaxiBriefingPlanner.NarrowTaxiways`): 82 ft prints as 25.0 m and is not below code F's 25 m — compared raw, it put almost every taxiway of an A380's route "below" the minimum.
- **Runways** (`BriefingRunwayChoice`): each leg is planned to the flight plan's runway (SimBrief's `plan_rwy`, or the pilot's own pick on the EFB's Departure/Arrival tab) unless SayIntentions is flying THIS flight (`SayIntentionsArrivalGate.IsThisFlight`: its flight file exists and its origin and destination are the flight plan's) and has assigned one (`current_flight.flight_plan_departing_runway` / `flight_plan_arriving_runway`, SAPI's "assigned departure / arrival runway"). Then SayIntentions' runway wins — its controllers will clear the pilot to it — and the leg's first note says where the runway came from: "runway 36L is the runway SayIntentions assigned; the flight plan names 18R", or "SayIntentions has assigned this runway too" when they agree (`RunwayIdsMatch`, so 8L = 08L). The prompt has the AI name a difference in its departure or arrival narrative as well. Live KMEM→KATL (2026-09-26): SayIntentions assigned 36L while SimBrief planned 18R, a runway SayIntentions was not using, and the briefing had routed the taxi-out to 18R. It is a snapshot: SayIntentions can change runways after the briefing is made.
- **SayIntentions' gate source**: the EFB reads SayIntentions through `SayIntentionsService.GetAssignedStatusAsync` — the call MSFS Blind Assist's SayIntentions window makes — so the gate is the flight file's `assigned_gate` with the file's position or, when the file has none yet, the SAPI parking service's answer (`getParking`) with ITS OWN position (`SayIntentionsGateSource.ParkingService`); a name is never paired with the other source's position. Live KMEM→KATL: the file's `assigned_gate` was empty while SayIntentions showed a concourse B arrival gate, and the briefing, which read only the file, used a representative stand. SAPI does not say whether `getParking` means the arrival gate or the current parking (and KMEM has a concourse B too), so a parking-service gate whose position is more than `TaxiBriefingPlanner.ParkingServiceMaxAirportDistanceMetres` (5 km) from the arrival airport's reference point is not briefed — the leg says "SayIntentions' parking service named …, but its position is not at …; using a representative stand instead". A parking-service gate with no position is looked up by NAME in the arrival airport's scenery, as a flight-file gate is, and the leg notes "SayIntentions' parking service gave no position for …, so it was matched by name in this scenery"; a representative stand stands in only when no stand there carries the name (owner, 2026-09-26, reversing that morning's refusal: live KMEM→KATL, `getParking` answered "B3" with no position and the flight file said "Gate B3" nine seconds later, the aircraft at KMEM Gate 17 — the service meant the arrival gate). A flight-file gate is never subject to the distance check. A SayIntentions failure costs the briefing SayIntentions' data only; the taxi legs still come.
- **Turn directions** (`BriefingTurns`): each taxiway after the first carries the turn onto it ("N, left onto M, right onto A, slight right onto B"), and the taxi-in ends with the turn into the stand ("then right into the stand") — only when the unnamed approach to the stand is lead-in length (`BriefingTurns.MaxUnnamedStretchMetres`, 100 m, the stand lead-in length); beyond that its first bend is apron taxilane, not the stand (live KATL C 22: 541 m of unnamed ramp beyond taxiway F), and no stand turn is given. A turn is the sum of the bearing changes over a stretch reaching up to 60 m (`StretchMetres`) into each taxiway but never past its middle, through an unnamed connector of up to 100 m (`BriefingTurns.MaxUnnamedStretchMetres`) — across a longer unnamed stretch no direction is given, a missing direction rather than a wrong one, and the prompt tells the AI to leave it missing (fs2024, 60 hubs: without that limit 615 of 11,579 taxi-outs briefed a turn of 60° or more as straight ahead or the wrong way) — never one junction's angle, because navdata splits real turns into small bends, and never past the middle, so two close turns do not blend. Words: under 20° "straight ahead", under 60° "slight", under 120° plain, then "sharp"; the 20° and 60° lines are `TaxiRouter.GetTurnDirection`'s, the same lines live guidance's callouts use (live guidance judges one junction from the aircraft's heading, and adds "sharp" and the angle from 60° up). No direction is given for joining the first taxiway (the heading after pushback is unknown; on the taxi-in the exit's side is already given) or onto the departure runway (live guidance leaves that hop to the lineup tone).
- **The real-world question is asked, never shown**: `GeminiService.RealWorldTaxiQuestion` is an instruction to the AI. The prompt tells it to write only its answer and never the question — the old wording, "Substitute the airport, runway, stand or terminal and aircraft type from the data", read as "write the filled-in question out", and a live KMEM→KATL Gemini briefing did, under both headings — and both providers run `RouteBriefingText.RemoveEchoedTaxiQuestion` on the reply. It removes the question or either of its sentences (quoted, labelled, after the heading, or split over two lines) and deletes a line it empties; every other line comes back byte-identical.

- Limits: the block adds ~1–2 KB (exits capped at 12), plus each airport's taxiway name list (about 0.5 KB for KATL's 95 names); Claude's `max_tokens` is 16000 and Gemini now reports `finishReason == MAX_TOKENS` with the same "may be incomplete" note; the word target is 600–900 (kept 2026-09-26: the one-part real-world briefing the owner found the right length ran under it). The planner is bounded at 20 s total (`TaxiBriefingPlanner.DefaultBudget`) — taxi-out and taxi-in are computed CONCURRENTLY under that one shared budget, so a slow departure airport cannot starve the arrival leg of its share of it; a cancellation the caller requested is reported as a cancellation, never folded into the "timed out" wording a genuine budget overrun gets. When the online data a leg needs cannot be had in time, that leg says "OpenStreetMap data is not available right now" rather than naming a route.

Diagnostics: `debug.log`, category `taxi_briefing` — one Info-level summary line per leg regardless of outcome (an ordinary "no exit"/"no stand" leg, and a caller cancellation, log at Info too, exactly like a fully computed route), carrying `turns=[…]` and `standTurn="…"` beside `taxiways=[…]`, plus a trailing `notes="…"` (pipe-joined) whenever the leg carries any — the runway note and a parking-service refusal live only in Notes, and without this field the line named the runway used but never said SayIntentions assigned it, or that a gate was refused and why; Warn is reserved for a genuine timeout, an unexpected exception during computation, or a failed SayIntentions read (the briefing then goes on without SayIntentions). What SayIntentions' parking service returned is in `sayintentions.log` (`getParking: name='…' lat=… lon=… heading=…`).
