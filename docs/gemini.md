## Gemini AI (display reading + scene/route description)

**AI provider abstraction (`Services/IAiProvider.cs`).** The three AI features (on-demand cockpit-display reading, scene description, the Shift+E route briefing) run behind `IAiProvider` — `AnalyzeDisplayAsync` / `AnalyzeSceneAsync` / `DescribeRouteAsync` / `ListAvailableModelsAsync`. Two implementations: **`GeminiService`** (Google) and **`ClaudeService`** (Anthropic). The user picks one in the unified Settings dialog's **AI panel** (`Forms/Settings/AiSettingsPanel.cs`, a provider combo Gemini/Claude + each backend's fields; model lists populate LAZILY — only the visible provider's list is fetched on dialog open, the other on first switch, so opening Settings never fires two network calls), persisted as `UserSettings.AiProvider`; **`Services/AiProviderFactory.Create()`** returns the chosen backend. The three call sites — `MainForm.DescribeSceneAsync`, `BaseAircraftDefinition.ReadDisplay`, `ElectronicFlightBagForm` route — build via the factory and never branch on provider. **`ReadDisplay` takes an optional `Services.InstrumentViewRequest`** (the SimConnectManager as `ICameraViewIo` + a 0-based instrument-view index): the sim camera is moved to that view before the capture and put back afterwards — written, verified by read-back, a failure spoken once, and done BEFORE the AI call so the pilot's own view is gone for well under a second (the restore was removed 2026-09-09 and reinstated 2026-09-18 when the iFly round-tripped both a custom pilot view and a cabin quickview; docs/md11.md "The restore") — (`Services/InstrumentViewPlan` pure + `InstrumentViewSwitcher`, camera IO in `SimConnectManager.Camera.cs`). The reads are tables of `Aircraft/AiDisplayRead.cs`, dispatched once by `BaseAircraftDefinition.HandleHotkeyAction` from each definition's `DisplayReads` override — an aircraft gains display reads by supplying a table and nothing else. **Five aircraft move the camera**: the MD-11 (`Aircraft/MD11/Md11DisplayReads.cs`), the iFly 737 MAX8 (`Aircraft/IFly737DisplayReads.cs`), the PMDG 737-800 (`Aircraft/Pmdg737DisplayReads.cs`), the Fenix A320 (`Aircraft/FenixA320DisplayReads.cs`) and the PMDG 777 (`Aircraft/Pmdg777DisplayReads.cs`). Only the HorizonSim 787 (`HS787DisplayReads`) still carries a NULL view index on every row, which captures whatever is on screen — exactly what its hand-written switch arms did; measuring its views on the live aircraft turns each null into a number and nothing else changes. **Capture is `PrintWindow` first, BitBlt screen copy when the frame is blank** (`ScreenshotFrame.LooksBlank`), so an MSFSBA window over the sim no longer lands in the picture — scene description included. **Hard switch: when Claude is selected ALL three features go through Claude; no silent cross-provider fallback.** Shared bits: `AiModelInfo` (the dropdown item, `ToString()` is what NVDA speaks) and the three provider-neutral prompt builders (`GeminiService.Get*Prompt`, now `internal static`, reused by `ClaudeService` so wording stays in sync). `DisplayType` stays nested on `GeminiService` (the aircraft defs reference `GeminiService.DisplayType` — don't churn them). The MD-11 prompts are `DisplayType.PFDMd11` / `NDMd11` / `EADMd11` / `SDMd11` / `ISFDMd11`, pinned by `DisplayPromptTests`.

**Claude (`Services/ClaudeService.cs`).** Raw `HttpClient` + Newtonsoft (mirrors the Gemini transport, NO Anthropic SDK dependency). `POST /v1/messages` with `x-api-key` + `anthropic-version: 2023-06-01` headers set PER-REQUEST (the HttpClient is static/shared); vision = base64 `image` content block before the text block; route briefing adds the `web_search_20260209` server tool when `UserSettings.ClaudeWebSearch` is on (the NOTAM-grounding equivalent of Gemini search grounding — extra cost; this is the current dynamic-filtering variant, supported on the default Opus 4.8 + Sonnet 4.6. If the selected model rejects it — e.g. Haiku 4.5 — `DescribeRouteAsync` catches the web_search-named 400, retries ungrounded, and PREFIXES the briefing with a spoken "not grounded with current NOTAM or weather data" note — the degrade must stay AUDIBLE, never silent, per the no-silent-fallback rule), **capped at `max_uses=8`** (an uncapped multi-airport NOTAM briefing runs 10+ searches → slow + $10/1000 searches). **Web-search "process narration" stripping:** the route call also sends a `system` prompt telling the model to output only the briefing, AND `ParseResponse` keeps only the text AFTER the last tool block (`server_tool_use`/`web_search_tool_result`) — together these drop the "Let me search for NOTAMs… now I'll compose the briefing." narration that otherwise leaked ahead of the briefing (a plain vision/text response has no tool blocks, so all text is kept). **`ParseResponse` also surfaces `stop_reason`:** on `max_tokens`/`pause_turn` it appends "(Response may be incomplete — Claude stopped before finishing.)" — or a clear stopped-early message when no answer text survived — because a blind user cannot visually notice a briefing that just stops. **`max_tokens` is REQUIRED by the Messages API** (cannot be omitted); it is 16000 — effectively uncapped for these outputs (a briefing is ~700 tokens) and the documented ceiling for non-streaming requests (larger values need SSE streaming). **Vision screenshots are downscaled client-side to ≤2576 px long edge** (`ComputeScaledSize` + a System.Drawing re-encode; failures fall back to the original bytes): Anthropic caps each image at 5 MB (a 4K PNG screenshot can exceed it) and current models accept at most 2576 px on the long edge before downscaling server-side anyway, so nothing is lost — 1080p/1440p pass through untouched. The pure logic (narration strip, stop_reason, retry delays, scaled sizing) is pinned by `tests/MSFSBlindAssist.Tests/ClaudeServiceTests.cs`. Models from `GET /v1/models` (newest-first, filtered to `claude-*`). Same retry (429/5xx/timeout/connection) + fail-fast (400/401/403/404) shape as Gemini. **No thinking param** (omitted → no extended thinking on Opus 4.7/4.8; keeps display reads fast + cheap). **User-supplied key only** (`UserSettings.ClaudeApiKey`); MSFSBA never pays centrally. Default model `claude-opus-4-8` (Anthropic has no `*-latest` alias — the dropdown lets the user pick Sonnet/Haiku for lower cost). Cost rule of thumb: ~1.5¢/display read on Opus 4.8, so ~$5/month covers a typical hobby flyer; Haiku 4.5 is ~5× cheaper.

**Live-verified (2026-06, real Anthropic API):** Opus 4.8 text + vision work end-to-end — it read a real 1920×1080 MSFS cockpit screenshot exactly (PFD ALT/QNH/heading/THS, ND mode/waypoint/TCAS). **Fable 5 (`claude-fable-5`) is LISTED by `GET /v1/models` but 404s on use** for non-enrolled accounts ("Claude Fable 5 is not available. Please use Opus 4.8" — Fable/Mythos are access-gated programs). So it appears in the AI tab's model dropdown but, if selected, the 404 fail-fast handler shows "model 'claude-fable-5' is unavailable — choose a different model" (graceful, no crash). Don't special-case it; the list endpoint reports models you can *see* but may not be entitled to *use*. **web_search caveats (live Anthropic docs):** dynamic filtering (more accurate, fewer tokens) **requires also declaring the `code_execution` tool** — MSFSBA declares only `web_search`, so it currently gets BASIC search; NOTAM coverage via web search is inherently weak (NOTAMs live in FAA/ICAO systems, not well web-indexed — a dedicated NOTAM API is the real fix, not tool tuning). If web-grounded briefings ever exceed the 120s `HttpClient` timeout, **streaming** is the proper fix (SSE keeps the connection alive through the search pause); `max_uses=8` is the current lighter mitigation. **⚠️ Never paste an API key into chat/logs/code — user keys live only in `UserSettings.ClaudeApiKey` (entered in the Settings dialog's AI tab).**

`Services/GeminiService.cs` powers the Gemini backend (on-demand cockpit-display reading, scene description, and the Shift+E route briefing). Key points:
- **Model is USER-SELECTABLE, not a fallback chain.** The model used for every AI call is `UserSettings.GeminiModel` (default `gemini-flash-latest`, a rolling alias). The AI settings panel (`Forms/Settings/AiSettingsPanel.cs`, Gemini section) populates a `DropDownList` from a LIVE fetch — `GeminiService.ListAvailableModelsAsync()` (`GET …/v1beta/models`, filtered to `generateContent`-capable text/vision models, newest-first) — with a curated fallback list (`gemini-flash-latest`, `gemini-3.5-flash`, `gemini-2.5-flash`) when offline / no key / fetch fails. Do NOT reinstate a silent multi-model fallback: it hid which model produced a response, which the user rejected.
- **Do NOT send `thinkingConfig`/`thinkingBudget`.** `thinkingBudget` is the Gemini 2.5 parameter; Gemini 3.x models use `thinking_level` and treat `thinkingBudget` as deprecated (and error if both are set). The default models (`gemini-3.5-flash`, `gemini-2.5-flash`) already enable dynamic thinking by default, so omitting `thinkingConfig` keeps thinking on for accuracy across every selectable model without sending a wrong/redundant parameter.
- **Reliability = per-request retry/backoff.** `SendRequestAsync` retries transient failures (429, 500/502/503/504, HTTP timeout, connection-level `HttpRequestException`) with backoff and fails fast on client errors (400/401/403/404, where 404 means "model unavailable — pick another"); on exhaustion it throws a clear "Gemini is busy or unavailable — please try again" message. The timeout catch must NOT gate on `ex.CancellationToken.IsCancellationRequested` (false on a modern .NET HttpClient timeout) — catch `TaskCanceledException` as the timeout (the `SimBriefService` pattern).

## Taxi routes in the route briefing (2026-09-25)

The EFB's Describe Route briefing ends with a **TAXI OUT AND TAXI IN** section. The app computes the expected taxi-out (stand → departure runway) and taxi-in (landing exit → stand) routes from the pilot's own scenery data and appends a plain-text `TAXI ROUTES` block to the SimBrief flight data for that AI call only (`ElectronicFlightBagForm.BuildTaxiRoutesBlockAsync`; the stored `ExtractedFlightData` stays pure SimBrief). The prompt's section 7 gives each leg up to three parts, in order and each on its own line (owner, 2026-09-27). (1) The **route paragraph** answers the owner's question ("Provide the step-by-step taxi route at [ICAO Code] from [Runway] to [Terminal/Gate] in a [Aircraft Type]. Please include the expected taxiways, hold short points, and any specific restrictions.") from the block alone, in the voice of real-world operations. The names, order, turns, sides and distances come only from the block, and nothing comes from the AI's own knowledge except an unavailable leg's general-knowledge route. It ends with the preview phrase: this is the expected route on the pilot's scenery, and SayIntentions or ATC gives the actual clearance. That matters because the route is the shortest one, and controllers do not always route that way (KATL's V goes around the west end of 08R/26L). A general-knowledge route never gets that scenery phrase — it says only that SayIntentions or ATC will give the actual taxi clearance — and a leg with no route at all gets no scenery phrase (final review, 2026-09-27). (2) One **check line** checks the leg's route, exit and stand against the real airport. It begins `GeminiService.RouteCheckFromMemory` ("Real-world check, from memory rather than live charts:"), or `RouteCheckAgainstCharts` ("Real-world check, against current charts:") only when a web search in that briefing found and read the airport's current diagram or chart notes. It says the two agree, names what differs, or says the AI does not know the airport well enough, and never claims an agreement OR a difference it cannot support. When it leaves a point out because the scenery gives no name for it, it does not call that leg an agreement — it says only that not everything could be checked, without naming what. It is left out only for a leg the block gives no route, exit or stand for. (3) An optional **suggestions paragraph** begins `RouteSuggestionsOpening` ("Real-world suggestions, not from your scenery:") and has at most three short sentences, only when the AI has something to add that the scenery cannot provide. It may give a preferred exit from the charts (with its side and distance from the block's exits list), restrictions for the aircraft's size from the block's Aircraft line (a wide-body kept off a taxiway, a wingspan limit, a full-length departure requirement), current operational information such as a NOTAM closing a taxiway on the route, and at most one sentence that controllers usually route differently. It never gives a full alternative route. A suggested exit gets no side or distance when the exits list gives none; when the block gives no size class for the aircraft, a size restriction says which aircraft it applies to; and the suggestions come after the route paragraph, rather than the check line, when a leg has no check line to follow. The check line and the suggestions may name only taxiways, exits and stands in that leg's lines, including its "Taxiway names at" list: every edge name on the graph the leg was planned on (`TaxiLegBriefing.AirportTaxiways`). A same-airport taxi-in whose list equals the taxi-out's prints it as "as listed for the taxi out" (`TaxiBriefingRenderer.SameListAsTaxiOut`), and the prompt says that line gives the leg the taxi-out's list as its own. A point that could only be made with another name is left out. That was the owner's choice: a scenery out of date against the real airport is then not called out by name, but no invented name gets through. `GetRouteDescriptionPrompt(flightData, webSearch)` is told whether the request carrying it has web search (`GeminiSearchGrounding` / `ClaudeWebSearch`, both off by default). The flag swaps exactly one sentence of section 7 (`RouteSearchOffSentence` / `RouteSearchOnSentence`), so a check line can never claim live charts the AI could not have looked at. The search-on sentence tells the AI to do any lookups before it writes any part of the briefing: Claude's `ParseResponse` keeps only the text after the last tool block, so a chart lookup made partway through writing would silently drop every section written before it. It also asks for both airports' current NOTAMs FIRST and the airport diagram and chart notes only after them: within Claude's `max_uses` budget (8) a search budget that still runs out then drops chart lookups, never the NOTAMs — at 5 the chart lookups crowded the NOTAM searches out and the briefing said no notable NOTAMs were found. "Current charts" needs the search to have found the material AND read it — finding it is not enough. When a Claude model rejects the web_search tool, the retry rebuilds the prompt with `webSearch: false`. The taxi out runs stand → runway and the taxi in runway → exit → stand; the owner's question names only the second direction, so the prompt says so. Every runway the route crosses is always given. That includes one where no hold short point could be placed, which the block's hold line reports as "none could be placed; see the notes" rather than "No runway crossings" (`TaxiLegBriefing.UnheldRunways`). Any other note is given only when it changes what the pilot does or hears. An OpenStreetMap or X-Plane leg is called the expected route on that map. An unavailable leg still gives what the block has for it (exit, side, stand), and gets no route when the aircraft is already at the runway. Otherwise it may be answered from general knowledge, said to be so, with a total distance only where the block gives one. That is the one place a name outside the scenery can appear (owner confirmed, 2026-09-27). History: until 2026-09-26 the section had two parts (the computed route, then a "Real-world practice" answer), which the owner found too long. A real-world-only version the same day invented taxiway names (KMEM "V1", KATL "V3"/"V4") and was reverted. Round 5 (2026-09-26) told the route in one paragraph per leg with the AI's own additions mixed in. Round 6 (2026-09-27) moved those additions into the labelled suggestions paragraph and added the check line; the final review the same day added the no-scenery-phrase rule for general-knowledge routes, the no-unsupported-difference rule, the omission rule and the look-up-before-writing rule (owner approved).

Everything lives in `Navigation/Briefing/`:

- **Tiers per airport** (`TaxiBriefingGraphSource`): navdata (the graph built exactly as `LandingExitForm` builds it — including its bounded wait, up to 8 s and never past the budget, for the online taxiway-name fetch before the build: that cache is memory-only, and without the wait the first briefing of every session briefed LSZH, whose navdata names none of its taxiways, as "(unnamed)" with no exit while a second press named the route), then `OsmPlanningGraph` — a throw-away graph from the cached OpenStreetMap/apt.dat data, built by `TaxiBriefingGraphSource.BuildAsync` (called from the planner's `PlanAsync`) when the database has NO taxiways for that airport — stand lead-ins ("P" rows) alone do not count (`TaxiBriefingGraphSource.HasTaxiways`; 66 fs2024 airports, EDDA among them, have nothing else); a local value inside that call, never stored anywhere guidance can reach, carrying its own `OsmPlanningGraph.Note` ("stand types unknown (OpenStreetMap)") as one of the leg's notes — said once: when the stand picker's own "stand types unknown at this airport; the stand may not be a …" is on the leg, that replaces it — the TIER LABEL a pilot actually hears ("OpenStreetMap, planning only — taxi guidance cannot use this") is a separate constant, `TaxiBriefingRenderer.OsmLabel`, applied only when the leg is rendered. When the source it picks (the one with the most named segments, OpenStreetMap on a tie) is X-Plane's apt.dat, the leg is `BriefingTier.XPlane` instead, with `OsmPlanningGraph.XPlaneNote` ("stand types unknown (X-Plane airport data)") and `TaxiBriefingRenderer.XPlaneLabel` ("X-Plane airport data, planning only — taxi guidance cannot use this"), and the prompt's section 7 names both sources ("When a leg's route comes from OpenStreetMap or from X-Plane's airport data, say so in a few words, and call it the expected route on that map rather than on the pilot's scenery; taxi guidance cannot use it."). The online fetch reaches 5 km from the reference point, so the graph keeps only segments, holds and stands inside the navdata airport box grown `CurrentAirportResolver.BoxMarginMetres` (300 m) — else a small field beside a hub was planned on the hub's stands and taxiways (4NY2 beside KLGA, 2N7 beside KTEB, BNH beside KBOS) — and cuts each named segment into pieces of at most `OsmPlanningGraph.DensifyMetres` (25 m), so a stand beside the middle of a long straight way still has a node within reach. Its stands are NEVER passed to `TaxiGraph.Build` (whose parking pass would retype the nearest hold-short vertex or exit junction as a stand); they stay in the bundle for the stand picker. A stand name with two numbers ("Apron 2 Stand 5") keeps its own words rather than becoming stand 25. `TaxiDataMerger`'s never-steer-on-online-geometry rule is untouched — then nothing, with one of four exact reasons appended to "the navigation database has no taxiways for" the ICAO: "and OpenStreetMap data is not available" (the provider isn't the augmenting one at all), "and online taxi data is disabled in settings", "and OpenStreetMap data is not available right now" (nothing arrived within the budget — offline, still fetching, or genuinely nothing there, three causes this one reason cannot tell apart, so it never promises a retry), or "and OpenStreetMap has no named taxiways for it" (fetched, but empty) — in which case the AI's real-world route is the leg's answer.
- **Units**: EVERY distance, length and width in the block — taxi distances, exit distances from the threshold, the missed-exit separation, wingspans, taxiway widths and the stand picker's notes — is in ONE unit, the pilot's ground distance setting (`GroundDistanceUnit`, read once through `DistanceFormatter.UnitProvider` in `BuildTaxiRoutesBlockAsync` and carried on `TaxiBriefingRequest.Unit`), and the block's second line names it ("Distance unit: feet (the pilot's setting); every distance below is in feet"); the prompt tells the AI to use that unit for the whole taxi section. Feet: whole feet with separators ("7,218 ft"). Metres: taxi distances in metres under a kilometre and kilometres above, runway distances in whole metres ("1,890 m"), sizes to 0.1 m (`TaxiBriefingRenderer.FormatDistance`/`FormatAlongRunway`/`FormatSize`). Never write a distance into the block or a note in a hard-coded unit: live KMEM→KATL (2026-09-26) the block gave taxi distances in km beside exit distances in feet, and the briefing read "2.2 kilometers" and "6,025 feet" in one section.
- **Aircraft** (`AircraftSizeClass`): SimBrief type/name/`max_passengers` ONLY (owner's choice): a wingspan table → Annex 14 code letter → typical touchdown speed; freighter when `max_passengers` is 0, the code is a known freighter code, or the name carries one of `AircraftSizeClass`'s exact freighter-regex suffixes — F/BCF/BDSF/SF/PF/PCF/ERF/LRF, immediately after a digit, dash or space — or the bare word Freighter/Cargo anywhere. Unknown type → no fit filter, no width notes, said so in the block.
- **Taxi-out start**: from the aircraft's own position when SimConnect reports it on the ground at the departure airport (`TaxiBriefingPlanner.AtAirport` — `CurrentAirport.Resolve` via `GraphBundle.IsAtAirport`, else within `OwnPositionMaxAirportDistanceMetres` (5 km) of the reference point when the database cannot answer) and a node of the leg's taxi network lies within 150 m of it (`OwnPositionMaxNodeDistanceMetres`) — the block names a stand only when that node actually is one AND the aircraft is within 40 m of it (`TaxiBriefingPlanner.OwnPositionStandMaxMetres`, the same reach `TaxiGraph.DescribeLocation` names a stand within), otherwise "current position"; when the aircraft is already sitting on the runway's own lineup-entry node, the leg says so ("the aircraft is already at the runway NN entrance") rather than describing a zero-length route; a representative stand whose own node is that entrance is a route with no taxiways ("Taxiways: none (the stand leads straight onto the runway)", with only the hold before entering), as the taxi-in treats an exit leading straight onto its stand — never "no taxi route connects". **Reaching the runway**: the taxi-out ends on the runway entrance `RunwayLineupTarget` resolves, but with no entrance at or behind the lineup point that is the plain nearest node, kept for guidance's reach warning (LTAC 21L: 931 m off the centreline). When it lies more than `TaxiGuidanceManager.RUNWAY_REACH_MAX_CROSS_M` (120 m) off the centreline the briefing asks Taxi Assist's own backtrack search (`TaxiGraph.FindBacktrackEntryNode`, anchored on the route's start node, whose piece of the taxi network it keeps to) for the entrance instead — and also when the plain nearest node lies on another piece of the network than the start's: then the start's own piece is first searched for an entrance at or behind the lineup point (`TaxiGraph.FindRunwayLineupEntryNode` with no plain-node shortcut, anchored on the start) — within 120 m the lineup search returns the plain node without searching, and the backtrack search skips an entrance under 40 m along, so a piece whose own full-length entrance is a few metres from another piece's was told to backtrack from far down the runway — then the backtrack search, keeping the plain node when both find nothing so the leg says no taxi route connects; with none the leg says "no taxiway reaches runway X in this scenery", and never "already at the entrance" for a pilot parked at that nearest node. An entrance more than `TaxiBriefingPlanner.BacktrackNoteMinMetres` (150 m) down the runway from the lineup point adds a note naming the taxiway and the distance, in the pilot's unit, and saying a full-length departure means backtracking — a stand whose own node is that entrance (the route with no taxiways) included. **Which runway record**: `FindRunway` matches through `RouteRunwayCrossings.NormalizeDesignator` after stripping a leading "Runway", "RWY" or "RW", spaced or glued ("RW09L", "rwy27"), so "9" is "09" but any suffix is identity ("16W", a water lane, is not "16"; "22A" is not "22" — `CleanRunway` read only L/C/R and made both the land runway), prefers an open record to a closed one of the same name, and a leg whose runway is marked closed says "runway X is marked closed in this scenery" instead of planning it (fs2020: 1,506 closed ends at 834 airports). Off the ground, elsewhere, or with no SimConnect connection, it falls back to the same representative-stand pick as the arrival leg (below) — with no SayIntentions gate, since SayIntentions never assigns a departure gate.
- **Exit** (`BriefingExitPicker`): among the vacating exits ≤ 90° comfortably reachable at the touchdown speed (`RolloutExitGate.ComfortableExitLeadFeet`, the touchdown re-plan's rule) and within 1,500 ft (`PreferenceWindowFeet`) of the first of them, high-speed exits before the rest, each in runway order — and, when the stand is known, the first of those whose route to it does not cross the runway just landed on, either end (owner decision, 2026-09-26: prefer the exit on the gate side; OMDB 12L now briefs M7A on the right instead of N5A on the left with a re-crossing of 30R). If every one crosses, the usual choice stands. When comfortably reachable exits exist but none has a mapped route to the stand (a stand on a piece of the taxi network whose only exit comes early), the last candidate that does is briefed and flagged (`ExitChoice.ReachableExitsHaveNoRoute`) — "No exit comfortably reachable at N kt has a mapped route to the stand: expect to backtrack on the runway to the briefed exit, the last one with a mapped route." — never a reachable exit with no route ("no taxi route connects exit C to …") and never "no exit is comfortably reachable". Nothing reachable → the last exit with a mapped route to the stand (the furthest of all when no stand is known), flagged — every unreachable sentence calls it "the briefed exit" and says it is the last one with a mapped route, never "the last exit is briefed", which was false wherever a later exit had no route; when the only comfortable exits were set aside for leading off the other side (below), the block says that instead of calling the runway short ("so the briefed exit is the last one whose mapped route leaves on that side"). Before saying no exit is comfortable, or that none follows the briefed one, the planner asks the graph for the exits `GetLandingExits` left out (`TaxiGraph.FindDownfieldExits`, merged by `RolloutExitGate.MergeRescueExits`, as the rollout does before "Missed last exit" — KCOS, CYYZ 23) — and when the briefed exit was comfortable and only the one after it was missing, the rescued exits supply that next exit and nothing else, never replacing the briefed one (a rescued high-speed exit inside the preference window once did); with still nothing comfortable, the runway is called short only when the aircraft cannot stop on it comfortably (`TaxiBriefingPlanner.RunwayLongEnoughToStop`: the aim point plus the comfortable lead to a 90° exit's turn-off speed), a longer one is briefed as a backtrack to the briefed exit — the last one with a mapped route to the stand, not necessarily the runway's last exit (CYYQ 15) — and one of unknown length gets neither claim (`ExitChoice.RunwayLength`). "Short" is never said to an unrecognised type (its 130 kt is an assumption) nor to a code A or B aircraft: the verdict is the jet touchdown re-plan's rule (2 s, then 2.0 m/s² down to the turn-off speed, about 1,700 ft for a Cessna 172 at 70 kt), so both get the neutral "No exit is comfortably reachable at N kt; the briefed exit is the last one with a mapped route." (a C172 on a 1,500 ft strip was once told "This runway is short for this aircraft"). "Next exit if missed" is the next candidate on the SAME side at least 500 ft further along (`NextExitMinSeparationFeet`) — never a turn-off across the runway at the same junction (KPIT 32 had one 1 ft on) — and "none" is worded as no later USABLE exit on that side, since the exits list can still show a later one there that turns more than 90° or was set aside; the set-aside names in the unreachable sentence are capped like the exits list. Measured over 438 runway ends at 60 hubs (B738, fs2024): re-crossings of the landing runway 107 → 57, "next exit" within 500 ft 81 → 0. Only exits whose route begins on the side they turn toward are offered (`TaxiBriefingPlanner.BriefableExitRouteStarts`): `LandingExitDestination.Resolve` — shared with the rollout and deliberately unchanged here — can hand an exit another exit's clear-of-runway node across the runway (KLAX 25L briefed "A7, LEFT side" with the route starting on H6 north of it; 33 of 428 measured hub arrivals), and the prompt makes the AI repeat sides exactly. An exit that names no side takes the side its route leaves by. When the route leaves the runway on a named taxiway other than the exit's own — judged by the segment that takes it off the pavement (`TaxiwayLeavingTheRunway`), never by the route's first taxiway, which usually begins where the exit meets a parallel — the block adds "the mapped route leaves the runway on taxiway X" (EGLL 27L: exit S5W, route on N5E).
- **Stand** (`BriefingStandPicker`) draws from different pools — name them distinctly. The EXCLUDED kinds are ParkingTypes' own families — military (7/8), dock (12), fuel (16) and vehicle (17) — and de-ice pads (`IsExcludedKind`); the picker never hand-types the navdata numbers itself (`ExcludedTypeWords`). Cargo (7 RAMP_MIL_CARGO counted as cargo briefed freighters onto 48 fs2024 airports' military ramps) and dock (12, once folded into "ramp": a C172 at KBNA was briefed to "Northeast 12 (Dock GA)") are the two families this replaced. A representative stand, chosen only when nothing was assigned or found, comes from the representative pool (`IsRepresentativeCandidate`): no excluded kind and no type 1 — navdata's "unknown" bucket that real jetway gates land in too, e.g. LEBB 101–106 — so a None-type stand is NEVER the representative pick, even when it is the only stand that connects (`A_representative_stand_is_never_of_the_None_type` pins the null result there, not a fallback to it). **The SayIntentions match tries its evidence in the order Taxi Assist's own SayIntentions import does** (`TaxiAssistForm.TryResolveExternalDestination`: `MatchDestinationLabel` → `MatchGateByAlias` → `MatchGateByPosition`; owner decision 2026-09-26, reversing the earlier "the pin wins" rule, since that is how SayIntentions works): the NAME first, the scenery's online ALIASES only when no name matches, and SayIntentions' published position — the pin — only when no name or alias matched at all. The name and alias steps match stands of EVERY kind, type 1 included (ranked after every known type), as the import matches whatever its list carries (fuel and vehicle stands only when that list comes from navdata — GSX's gate list never carries them, though it can carry a military ramp — and de-ice pads are a destination type of their own there) — but an ordinary stand always beats an excluded one: the excluded kinds are searched, by name and then by alias, only when no ordinary stand answers either way (owner decision 2026-09-26, "follow the import"). An excluded stand found that way — or at the pin, below — is briefed with the note `"this scenery marks that stand as a fuel stand"` (or `military ramp`, `seaplane dock`, `vehicle stand`, `de-icing pad`). A name or alias match counts wherever the stand is; among several, exact name beats alias and the one nearest the pin wins, or with no pin a gate before any other type, then list order. That ranking exists because `NormalizeParkingName` strips the stand-type word, so navdata's "Spot 8" and "Gate 8" normalise to the same name — on the real fs2024 database list order alone would have briefed a same-numbered GA ramp as the assigned gate at roughly 20 airports. When the pin lies outside the chosen stand's own reach (`min(150 m, 2 × radius)`, `SayIntentionsGatePositionMatcher`'s own constants; 60 m for a stand of unknown size, e.g. every OpenStreetMap stand), the block adds `"SayIntentions' position is 1.2 km from this stand"` (the distance by `TaxiBriefingRenderer.FormatDistance`, in the pilot's unit), after the kind note when there is one: the stand is still the one the name found, and the pilot hears that SayIntentions put its gate somewhere else. No pin, no such note. The position step takes the nearest stand whose own reach covers the pin — of an ordinary kind when any is in reach, else of an excluded kind, briefed with the same kind note (the owner's "follow the import" applied to the pin, 2026-09-26: with only a fuel stand at the pin, "no stand at SayIntentions' position was found" was untrue); with nothing in reach at all a representative stand is used and the note says no stand at SayIntentions' position was found in this scenery — a claim about the position, the last evidence tried; "not found at this airport" is kept for a gate with no published position that no name or alias matched. Whichever step found it, the stand must connect to the taxiway network. **Which piece of the taxi network** (`TaxiBriefingPlanner.LegEndNode`, for a stand and for the aircraft's own position alike): the graph has no runway edges, so taxiway pieces that meet only across a runway are separate components (LFBP, VIJU, ENAT, UKHH, KPRC). A leg's end is the nearest node within reach when its piece also holds the leg's OTHER end — on the taxi-out the runway entrance resolved from that node lies on it AND on the runway pavement (`EntersTheRunway`: within half the width plus the 5 m both entrance searches allow, from where a departure begins to the far end — the lineup search's plain node can be anywhere within 120 m of the centreline, and a run-up pad or an unconnected lead-in beside the runway is no entrance), on the taxi-in a briefable exit's route begins on it — provided no node of the largest component is within reach, or the nearer node is a stand's own or on a stand lead-in: an aircraft on the main network beside a narrow runway, between two nodes, can be nearer a node of the piece across the runway, and snapped to it was briefed from the other side, while a stand is where the aircraft is parked, so its piece stays the answer — and otherwise the nearest node of the graph's largest component within reach; a piece that reaches neither (KTUL G 19's island) is never a leg's end. Measured on the real fs2024 database (2026-09-28): 1,677 airports have two or more pieces that each hold stands and reach a runway entrance, and 7,987 stands at 1,857 airports sit on such a piece off the largest one, 6,967 of them with no node of the largest within 100 m — each once briefed as not connecting, or replaced by a representative stand. Route starts still exclude bridge-only stand stubs. By name, an unconnected first-ranked namesake gives way only to one at least as plausible (`AtLeastAsPlausible`): where the pin is within the reach of either, one within its own reach; where it is within the reach of neither, one ranking the same or better by the no-position rule (a gate after a ramp the pin was merely nearer) that is also no farther from the pin than the first plus the first's own reach — so a pin far from a gate and a same-numbered GA ramp never lets the ramp stand in for the unconnected gate (the rule for no pin forbids that as well), and a same-kind namesake kilometres farther from the pin than the first never stands in for it. Otherwise the match is reported, naming its kind when it is an excluded one (`"… was found as a fuel stand but does not connect to the taxiway network; using a representative stand instead"`), and a representative stand is used — never one of the stands just refused, so "representative stand Gate 5" can never follow "Gate 5 was found but does not connect". At the pin, the nearest stand in reach that connects is used; when that is not the nearest, ONE sentence names both with their distances, in place of the "lists as" note (`"SayIntentions assigned Gate 99; the stand at its position, B 6 (20 m away), does not connect to the taxiway network, so B 7 (30 m away) is used"`) — the distances tell apart stands this scenery calls the same, and no second note calls the stand used SayIntentions' gate. **Where the briefing still differs from the import, deliberately:** among several namesakes the import takes the first entry its own list offers, while the briefing puts an ordinary stand before an excluded one and then takes the one nearest the pin; an ordinary stand's ALIAS beats an excluded stand's NAME in the briefing, where the import's name step takes the name first, whatever kind of stand its list carries it on; among stands in reach of the pin an ordinary one is preferred, where the import takes the nearest of any kind its list carries; the briefing requires the stand to connect to the taxiway network, the import's resolution does not; and the briefing's position step and far note give a stand of unknown size 60 m, where the import's position match skips a stand with no radius. A substitution by ALIAS — the name did not match, but an online alias did — is briefed as `"SayIntentions assigned X, which this scenery lists as Y"`, which says the scenery calls the stand by another name; a substitution by POSITION ALONE — no name or alias answered anywhere, so the stand is merely the nearest to the pin — is briefed in the import's own words instead: `"SayIntentions assigned X, which this scenery does not have; the stand nearest SayIntentions' position is Y"`, or, when X itself names no stand at all ("Gate"), `"SayIntentions assigned X, which names no stand; the stand nearest SayIntentions' position is Y"` — never `lists as`, which would claim this scenery calls the stand by SayIntentions' name when it does not have that stand at all. A label that already says what it is ("Gate 5", "Spot 12", "Parking", "Terminal 3 Gate J1") is never prefixed with "gate" again ("SayIntentions assigned gate Gate 5") — the kind word is looked for anywhere in the label, not only at its start, since SayIntentions' own labels carry it mid-string. The representative pick itself, among representative-pool stands that connect: category (freighter → cargo; code A → ramp, gate, cargo; everyone else → gate, ramp, cargo), wingspan fit (`ParkingSpot.FitsAircraft`; unknown size kept), the SimBrief airline's stands, then the stand nearest the group's centroid. Every fallback is a note in the block.
- **Hold-shorts**: `RouteRunwayCrossings.InsertRunwayHoldShorts` runs with the aircraft's own sensed position (`RouteRunwayCrossings.AircraftPosition`, `MayStartHeld` left at its default `true` — the same as a fresh Taxi Assist Calculate) when the taxi-out leg starts from that sensed position; a taxi-out leg that instead starts from a stand, and the taxi-in leg always (it plans from a landing exit the aircraft has not reached yet), still pass no aircraft at all. The departure runway's own entry is always added as the "before entering" hold. Every crossing of the runway just landed on IS briefed, never discarded — the taxi-in route always starts at an exit the vacate screen (`LandingExitVacateScreen`) marked as clear of the runway, so a hold naming the landing runway can only describe a re-crossing of it. A hold on no named taxiway renders `runway NN (crossing)` with no taxiway named, rather than "on taxiway" followed by a blank. A note that no hold short point could be placed is given ONCE per runway PAVEMENT — a reciprocal designator (10L and 28R) is one runway (`TaxiBriefingPlanner.SameRunway`), so the pilot never hears the same crossing reported twice under its two ends.
- **Taxiway widths are advisory only**: navdata `taxi_path.width` is mostly a scenery default, so it never changes a route. The commonest value is 82 ft = 24.99 m, on 62.1 % of fs2024 taxiway rows (`T` and `PT`) and 64.6 % of fs2020's; 98 ft (about 30 m) is on only 6.4 % / 2.9 %, though it is on nearly every fs2024 KMEM taxiway (measured 2026-09-26). A taxiway below the code letter's Annex 14 minimum is named in a "Taxiway width note", judged in whole feet, the unit navdata stores widths in (`TaxiBriefingPlanner.NarrowTaxiways`): the minimum's own whole-foot value (49 ft for code C's 15 m, 75 ft for 23 m, 82 ft for code F's 25 m) IS the minimum, never below it. Compared raw, 82 ft put almost every taxiway of an A380's route "below" the minimum; judged at the metres display's 0.1 m, a feet-mode block told a 737 "49 ft in the navdata, below the 49 ft code C minimum" (49 ft is the third commonest fs2024 width, 96,384 rows at 700+ airports).
- **Runways** (`BriefingRunwayChoice`): each leg is planned to the flight plan's runway (SimBrief's `plan_rwy`, or the pilot's own pick on the EFB's Departure/Arrival tab) unless SayIntentions is flying THIS flight (`SayIntentionsArrivalGate.IsThisFlight`: its flight file exists and its origin and destination are the flight plan's) and has assigned one (`current_flight.flight_plan_departing_runway` / `flight_plan_arriving_runway`, SAPI's "assigned departure / arrival runway"). Then SayIntentions' runway wins — its controllers will clear the pilot to it — and the leg's first note says where the runway came from: "runway 36L is the runway SayIntentions assigned; the flight plan names 18R", or "SayIntentions has assigned this runway too" when they agree (`RunwayIdsMatch`, so 8L = 08L). The prompt has the AI name a difference in its departure or arrival narrative as well. Live KMEM→KATL (2026-09-26): SayIntentions assigned 36L while SimBrief planned 18R, a runway SayIntentions was not using, and the briefing had routed the taxi-out to 18R. It is a snapshot: SayIntentions can change runways after the briefing is made.
- **SayIntentions' gate source**: the EFB reads SayIntentions through `SayIntentionsService.GetAssignedStatusAsync` — the call MSFS Blind Assist's SayIntentions window makes — so the gate is the flight file's `assigned_gate` with the file's position or, when the file has none yet, the SAPI parking service's answer (`getParking`) with ITS OWN position (`SayIntentionsGateSource.ParkingService`); a name is never paired with the other source's position. Live KMEM→KATL: the file's `assigned_gate` was empty while SayIntentions showed a concourse B arrival gate, and the briefing, which read only the file, used a representative stand. SAPI does not say whether `getParking` means the arrival gate or the current parking (and KMEM has a concourse B too), so a parking-service gate whose position is not at the arrival airport (`CurrentAirport.Resolve`, `GraphBundle.IsAtAirport`; within `TaxiBriefingPlanner.OwnPositionMaxAirportDistanceMetres` (5 km) of the reference point only when the database cannot answer) is not briefed — the leg says "SayIntentions' parking service named …, but its position is not at …", with "; using a representative stand instead" appended only when the representative pick actually finds a stand to brief — `TaxiBriefingPlanner`'s own check is `stand != null`, because 205 fs2024 airports have taxi paths and no parking at all, so there is sometimes no representative stand to fall back to and the leg then carries just the plain refusal with no stand at all. A parking-service gate with no position is looked up by NAME in the arrival airport's scenery, as a flight-file gate is, and the leg notes "SayIntentions' parking service gave no position for …, so it was matched by name in this scenery"; a representative stand stands in only when no stand there carries the name (owner, 2026-09-26, reversing that morning's refusal: live KMEM→KATL, `getParking` answered "B3" with no position and the flight file said "Gate B3" nine seconds later, the aircraft at KMEM Gate 17 — the service meant the arrival gate). A flight-file gate is never subject to the distance check. A SayIntentions failure costs the briefing SayIntentions' data only; the taxi legs still come.
- **Turn directions** (`BriefingTurns`): each taxiway after the first carries the turn onto it ("N, left onto M, right onto A, slight right onto B"), and the taxi-in ends with the turn into the stand ("then right into the stand") — only when the unnamed approach to the stand is lead-in length (`BriefingTurns.MaxUnnamedStretchMetres`, 100 m, the stand lead-in length); beyond that its first bend is apron taxilane, not the stand (live KATL C 22: 541 m of unnamed ramp beyond taxiway F), and no stand turn is given. A turn is the sum of the bearing changes over a stretch reaching up to 60 m (`StretchMetres`) into each taxiway but never past its middle, through an unnamed connector of up to 100 m (`BriefingTurns.MaxUnnamedStretchMetres`) — across a longer unnamed stretch no direction is given, a missing direction rather than a wrong one, and the prompt tells the AI to leave it missing (fs2024, 60 hubs: without that limit 615 of 11,579 taxi-outs briefed a turn of 60° or more as straight ahead or the wrong way) — never one junction's angle, because navdata splits real turns into small bends, and never past the middle, so two close turns do not blend. Words: under 20° "straight ahead", under 60° "slight", under 120° plain, then "sharp"; the 20° and 60° lines are `TaxiRouter.GetTurnDirection`'s, the same lines live guidance's callouts use (live guidance judges one junction from the aircraft's heading, and adds "sharp" and the angle from 60° up). No direction is given for joining the first taxiway (the heading after pushback is unknown; on the taxi-in the exit's side is already given) or onto the departure runway (live guidance leaves that hop to the lineup tone).
- **The real-world question is asked, never shown**: `GeminiService.RealWorldTaxiQuestion` is an instruction to the AI. The prompt tells it to write only its answer and never the question — the old wording, "Substitute the airport, runway, stand or terminal and aircraft type from the data", read as "write the filled-in question out", and a live KMEM→KATL Gemini briefing did, under both headings — and both providers run `RouteBriefingText.RemoveEchoedTaxiQuestion` on the reply. It removes the question or either of its sentences (quoted, labelled, after the heading, or split over two lines) and deletes a line it empties — and only where the echo STARTS its line, after indentation, a list marker or a heading ending in a colon or dash: unanchored, it deleted the AI's own sentences that used the question's words ("Ground will provide the step-by-step taxi route after you vacate…" became "Ground will "); every other line comes back byte-identical.

- Limits: the block adds ~1–2 KB (exits capped at 12), plus each airport's taxiway name list (about 0.5 KB for KATL's 95 names); Claude's `max_tokens` is 16000 and Gemini now reports `finishReason == MAX_TOKENS` with the same "may be incomplete" note; the word target is 600–900 (kept 2026-09-26: the one-part real-world briefing the owner found the right length ran under it). The planner is bounded at 20 s total (`TaxiBriefingPlanner.DefaultBudget`) — taxi-out and taxi-in are computed CONCURRENTLY under that one shared budget, so a slow departure airport cannot starve the arrival leg of its share of it; a cancellation the caller requested is reported as a cancellation, never folded into the "timed out" wording a genuine budget overrun gets. When the online data a leg needs cannot be had in time, that leg says "OpenStreetMap data is not available right now" rather than naming a route.

Diagnostics: `debug.log`, category `taxi_briefing` — one Info-level summary line per leg regardless of outcome (an ordinary "no exit"/"no stand" leg, and a caller cancellation, log at Info too, exactly like a fully computed route), carrying `turns=[…]` and `standTurn="…"` beside `taxiways=[…]`, plus a trailing `notes="…"` (pipe-joined) whenever the leg carries any — the runway note and a parking-service refusal live only in Notes, and without this field the line named the runway used but never said SayIntentions assigned it, or that a gate was refused and why; Warn is reserved for a genuine timeout, an unexpected exception during computation, or a failed SayIntentions read (the briefing then goes on without SayIntentions). What SayIntentions' parking service returned is in `sayintentions.log` (`getParking: name='…' lat=… lon=… heading=…`).
