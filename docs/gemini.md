# Gemini AI

> **Read this when:** working on the Gemini AI features (display reading, scene/route description, model selection, retry/backoff).

## Gemini AI (display reading + scene/route description)

**AI provider abstraction (`Services/IAiProvider.cs`).** The three AI features (on-demand cockpit-display reading, scene description, the Shift+E route briefing) run behind `IAiProvider` — `AnalyzeDisplayAsync` / `AnalyzeSceneAsync` / `DescribeRouteAsync` / `ListAvailableModelsAsync`. Two implementations: **`GeminiService`** (Google) and **`ClaudeService`** (Anthropic). The user picks one in the unified Settings dialog's **AI panel** (`Forms/Settings/AiSettingsPanel.cs`, a provider combo Gemini/Claude + each backend's fields; model lists populate LAZILY — only the visible provider's list is fetched on dialog open, the other on first switch, so opening Settings never fires two network calls), persisted as `UserSettings.AiProvider`; **`Services/AiProviderFactory.Create()`** returns the chosen backend. The three call sites — `MainForm.DescribeSceneAsync`, `BaseAircraftDefinition.ReadDisplay`, `ElectronicFlightBagForm` route — build via the factory and never branch on provider. **`ReadDisplay` takes an optional `Services.InstrumentViewRequest`** (the SimConnectManager as `ICameraViewIo` + a 0-based instrument-view index): the sim camera is moved to that view before the capture and put back afterwards — written, verified by read-back, a failure spoken once, and done BEFORE the AI call so the pilot's own view is gone for well under a second (the restore was removed 2026-09-09 and reinstated 2026-09-18 when the iFly round-tripped both a custom pilot view and a cabin quickview; docs/md11.md "The restore") — (`Services/InstrumentViewPlan` pure + `InstrumentViewSwitcher`, camera IO in `SimConnectManager.Camera.cs`). The reads are tables of `Aircraft/AiDisplayRead.cs`, dispatched once by `BaseAircraftDefinition.HandleHotkeyAction` from each definition's `DisplayReads` override — an aircraft gains display reads by supplying a table and nothing else. **Five aircraft move the camera**: the MD-11 (`Aircraft/MD11/Md11DisplayReads.cs`), the iFly 737 MAX8 (`Aircraft/IFly737DisplayReads.cs`), the PMDG 737-800 (`Aircraft/Pmdg737DisplayReads.cs`), the Fenix A320 (`Aircraft/FenixA320DisplayReads.cs`) and the PMDG 777 (`Aircraft/Pmdg777DisplayReads.cs`). Only the HorizonSim 787 (`HS787DisplayReads`) still carries a NULL view index on every row, which captures whatever is on screen — exactly what its hand-written switch arms did; measuring its views on the live aircraft turns each null into a number and nothing else changes. **Capture is `PrintWindow` first, BitBlt screen copy when the frame is blank** (`ScreenshotFrame.LooksBlank`), so an MSFSBA window over the sim no longer lands in the picture — scene description included. **Hard switch: when Claude is selected ALL three features go through Claude; no silent cross-provider fallback.** Shared bits: `AiModelInfo` (the dropdown item, `ToString()` is what NVDA speaks) and the three provider-neutral prompt builders (`GeminiService.Get*Prompt`, now `internal static`, reused by `ClaudeService` so wording stays in sync). `DisplayType` stays nested on `GeminiService` (the aircraft defs reference `GeminiService.DisplayType` — don't churn them). The MD-11 prompts are `DisplayType.PFDMd11` / `NDMd11` / `EADMd11` / `SDMd11` / `ISFDMd11`, pinned by `DisplayPromptTests`.

**Claude (`Services/ClaudeService.cs`).** Raw `HttpClient` + Newtonsoft (mirrors the Gemini transport, NO Anthropic SDK dependency). `POST /v1/messages` with `x-api-key` + `anthropic-version: 2023-06-01` headers set PER-REQUEST (the HttpClient is static/shared); vision = base64 `image` content block before the text block; route briefing adds the `web_search_20260209` server tool when `UserSettings.ClaudeWebSearch` is on (the NOTAM-grounding equivalent of Gemini search grounding — extra cost; this is the current dynamic-filtering variant, supported on the default Opus 4.8 + Sonnet 4.6. If the selected model rejects it — e.g. Haiku 4.5 — `DescribeRouteAsync` catches the web_search-named 400, retries ungrounded, and PREFIXES the briefing with a spoken "not grounded with current NOTAM or weather data" note — the degrade must stay AUDIBLE, never silent, per the no-silent-fallback rule), **capped at `max_uses=5`** (an uncapped multi-airport NOTAM briefing runs 10+ searches → slow + $10/1000 searches). **Web-search "process narration" stripping:** the route call also sends a `system` prompt telling the model to output only the briefing, AND `ParseResponse` keeps only the text AFTER the last tool block (`server_tool_use`/`web_search_tool_result`) — together these drop the "Let me search for NOTAMs… now I'll compose the briefing." narration that otherwise leaked ahead of the briefing (a plain vision/text response has no tool blocks, so all text is kept). **`ParseResponse` also surfaces `stop_reason`:** on `max_tokens`/`pause_turn` it appends "(Response may be incomplete — Claude stopped before finishing.)" — or a clear stopped-early message when no answer text survived — because a blind user cannot visually notice a briefing that just stops. **`max_tokens` is REQUIRED by the Messages API** (cannot be omitted); it is 16000 — effectively uncapped for these outputs (a briefing is ~700 tokens) and the documented ceiling for non-streaming requests (larger values need SSE streaming). **Vision screenshots are downscaled client-side to ≤2576 px long edge** (`ComputeScaledSize` + a System.Drawing re-encode; failures fall back to the original bytes): Anthropic caps each image at 5 MB (a 4K PNG screenshot can exceed it) and current models accept at most 2576 px on the long edge before downscaling server-side anyway, so nothing is lost — 1080p/1440p pass through untouched. The pure logic (narration strip, stop_reason, retry delays, scaled sizing) is pinned by `tests/MSFSBlindAssist.Tests/ClaudeServiceTests.cs`. Models from `GET /v1/models` (newest-first, filtered to `claude-*`). Same retry (429/5xx/timeout/connection) + fail-fast (400/401/403/404) shape as Gemini. **No thinking param** (omitted → no extended thinking on Opus 4.7/4.8; keeps display reads fast + cheap). **User-supplied key only** (`UserSettings.ClaudeApiKey`); MSFSBA never pays centrally. Default model `claude-opus-4-8` (Anthropic has no `*-latest` alias — the dropdown lets the user pick Sonnet/Haiku for lower cost). Cost rule of thumb: ~1.5¢/display read on Opus 4.8, so ~$5/month covers a typical hobby flyer; Haiku 4.5 is ~5× cheaper.

**Live-verified (2026-06, real Anthropic API):** Opus 4.8 text + vision work end-to-end — it read a real 1920×1080 MSFS cockpit screenshot exactly (PFD ALT/QNH/heading/THS, ND mode/waypoint/TCAS). **Fable 5 (`claude-fable-5`) is LISTED by `GET /v1/models` but 404s on use** for non-enrolled accounts ("Claude Fable 5 is not available. Please use Opus 4.8" — Fable/Mythos are access-gated programs). So it appears in the AI tab's model dropdown but, if selected, the 404 fail-fast handler shows "model 'claude-fable-5' is unavailable — choose a different model" (graceful, no crash). Don't special-case it; the list endpoint reports models you can *see* but may not be entitled to *use*. **web_search caveats (live Anthropic docs):** dynamic filtering (more accurate, fewer tokens) **requires also declaring the `code_execution` tool** — MSFSBA declares only `web_search`, so it currently gets BASIC search; NOTAM coverage via web search is inherently weak (NOTAMs live in FAA/ICAO systems, not well web-indexed — a dedicated NOTAM API is the real fix, not tool tuning). If web-grounded briefings ever exceed the 120s `HttpClient` timeout, **streaming** is the proper fix (SSE keeps the connection alive through the search pause); `max_uses=5` is the current lighter mitigation. **⚠️ Never paste an API key into chat/logs/code — user keys live only in `UserSettings.ClaudeApiKey` (entered in the Settings dialog's AI tab).**

`Services/GeminiService.cs` powers the Gemini backend (on-demand cockpit-display reading, scene description, and the Shift+E route briefing). Key points:
- **Model is USER-SELECTABLE, not a fallback chain.** The model used for every AI call is `UserSettings.GeminiModel` (default `gemini-flash-latest`, a rolling alias). The AI settings panel (`Forms/Settings/AiSettingsPanel.cs`, Gemini section) populates a `DropDownList` from a LIVE fetch — `GeminiService.ListAvailableModelsAsync()` (`GET …/v1beta/models`, filtered to `generateContent`-capable text/vision models, newest-first) — with a curated fallback list (`gemini-flash-latest`, `gemini-3.5-flash`, `gemini-2.5-flash`) when offline / no key / fetch fails. Do NOT reinstate a silent multi-model fallback: it hid which model produced a response, which the user rejected.
- **Do NOT send `thinkingConfig`/`thinkingBudget`.** `thinkingBudget` is the Gemini 2.5 parameter; Gemini 3.x models use `thinking_level` and treat `thinkingBudget` as deprecated (and error if both are set). The default models (`gemini-3.5-flash`, `gemini-2.5-flash`) already enable dynamic thinking by default, so omitting `thinkingConfig` keeps thinking on for accuracy across every selectable model without sending a wrong/redundant parameter.
- **Reliability = per-request retry/backoff.** `SendRequestAsync` retries transient failures (429, 500/502/503/504, HTTP timeout, connection-level `HttpRequestException`) with backoff and fails fast on client errors (400/401/403/404, where 404 means "model unavailable — pick another"); on exhaustion it throws a clear "Gemini is busy or unavailable — please try again" message. The timeout catch must NOT gate on `ex.CancellationToken.IsCancellationRequested` (false on a modern .NET HttpClient timeout) — catch `TaskCanceledException` as the timeout (the `SimBriefService` pattern).

## Taxi section of the route briefing (2026-09-26)

The EFB's Describe Route briefing ends with a **TAXI OUT AND TAXI IN** section giving the TYPICAL REAL-WORLD taxi flow at each airport, from the AI's own knowledge. Nothing is computed from the simulator scenery any more (owner, 2026-09-26: the scenery/SayIntentions-computed route was dropped, which also took the graph builds, the stand and exit pickers and the up-to-8 s online taxiway-name wait out of the briefing's time). For each leg the prompt asks the owner's question, `GeminiService.RealWorldTaxiQuestion`, word for word: "Provide the step-by-step taxi route at [ICAO Code] from [Runway] to [Terminal/Gate] in a [Aircraft Type]. Please include the expected taxiways, hold short points, and any specific restrictions." That question is the heart of the section and must never be dropped; the prompt fills its brackets from the block below.

`ElectronicFlightBagForm.BuildTaxiPlanningBlockAsync` appends a short plain-text `TAXI PLANNING` block (`Navigation/Briefing/TaxiPlanningBlock`) to the SimBrief flight data for that AI call only (the stored `ExtractedFlightData` stays pure SimBrief). It carries only the facts the question needs:

- **Units**: the block's second line names the pilot's ground distance setting ("Distance unit: feet (the pilot's setting); give every taxi distance in feet"), and the prompt tells the AI to use it for the whole section — live KMEM→KATL (2026-09-26) once read "2.2 kilometers" beside "6,025 feet".
- **Aircraft** (`AircraftSizeClass`): SimBrief type/name/`max_passengers` ONLY (owner's choice): a wingspan table → Annex 14 code letter; freighter when `max_passengers` is 0, the code is a known freighter code, or the name carries one of `AircraftSizeClass`'s exact freighter-regex suffixes — F/BCF/BDSF/SF/PF/PCF/ERF/LRF, immediately after a digit, dash or space — or the bare word Freighter/Cargo anywhere. The SimBrief airline code follows on its own line, so the AI can pick the airline's usual terminal.
- **Runways** (`BriefingRunwayChoice`): each leg names the flight plan's runway (SimBrief's `plan_rwy`, or the pilot's own pick on the EFB's Departure/Arrival tab) unless SayIntentions is flying THIS flight (`SayIntentionsArrivalGate.IsThisFlight`: its flight file exists and its origin and destination are the flight plan's) and has assigned one (`current_flight.flight_plan_departing_runway` / `flight_plan_arriving_runway`). Then SayIntentions' runway wins and the leg's note says where it came from: "runway 36L is the runway SayIntentions assigned; the flight plan names 18R", or "SayIntentions has assigned this runway too" when they agree (8L = 08L; compass-point ends match too). The prompt has the AI name a difference in its departure or arrival narrative as well. Live KMEM→KATL (2026-09-26): SayIntentions assigned 36L while SimBrief planned 18R. It is a snapshot: SayIntentions can change runways after the briefing is made.
- **Taxi-out start** (`TaxiPlanningBlock.ResolveDepartureStand`): the stand the aircraft is parked at — on the ground within 5 km of the departure airport's reference point, the nearest stand (`ParkingSpotSource.GetNamedSpots`, so a stand has the one name it has everywhere else) within 100 m, named by its identity ("Gate 17", "B 25"). The stand list is read only then. Otherwise "no stand known", and the prompt has the AI use the terminal or apron the airline and aircraft would typically use, saying it is typical, not assigned.
- **Arrival gate** (`SayIntentionsArrivalGate` → `TaxiPlanningBlock.ResolveArrivalGate`): the EFB reads SayIntentions through `SayIntentionsService.GetAssignedStatusAsync`, the SayIntentions window's own call — the flight file's `assigned_gate`, or, when the file has none yet, the SAPI parking service's answer (`getParking`), each with its OWN position (a name is never paired with the other source's position). SAPI does not say whether `getParking` means the arrival gate or the current parking, so a parking-service gate whose position is more than 5 km from the arrival airport is not used and the block says so; one with NO position is used by name (live KMEM→KATL: `getParking` answered "B3" with no position and the flight file said "Gate B3" nine seconds later — it was the arrival gate). No gate → "none assigned", and the AI gives the typical one, saying so. A SayIntentions or database failure costs only that fact; the briefing still comes.
- **The question is asked, never shown**: the prompt tells the AI to write only its answer — the old wording, "Substitute the airport, runway, stand or terminal and aircraft type from the data", read as "write the filled-in question out", and a live KMEM→KATL Gemini briefing did — and both providers run `RouteBriefingText.RemoveEchoedTaxiQuestion` on the reply. It removes the question or either of its sentences (quoted, labelled, after a heading, or split over two lines) and deletes a line it empties; every other line comes back byte-identical.

Diagnostics: `debug.log`, category `taxi_briefing` — one Info line per briefing naming both airports, runways, the stand, the gate and any gate note; a failed position, SayIntentions or database read logs a Warn and the briefing goes on without it.
