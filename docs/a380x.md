### FlyByWire A380X Specific Patterns

`FlyByWireA380Definition` (code `FBW_A380`), branch `fly-by-wire-A380-integration`.

**MSFS-2024-native modular rebuild (FBW #10758, 2026-06) — MSFSBA-impact audit.** The A380X was repackaged as a native MSFS 2024 modular aircraft (new SimObject layout, lighting/perf work, a cabinless "No Cabin" variant). **It is NOT a systems/variable overhaul — verified MSFSBA-safe:** (1) **detection unchanged** — both variants keep `icao_type_designator A388` / `atc_model A380` (the def is menu-selected, not title-detected, so the new marketing Title "FlyByWire A380X (A380-842)" is irrelevant; GSX/docking `A388` resolution intact); (2) **the whole Coherent stack still resolves** — every view title-needle exists unchanged (`A380X_MFD`/`EWD`/`SDv2`/`ND`/`PFD`/`FCU`/`RMP`/`SYSTEMSHOST`, `- EFB`); (3) **no renamed/removed L:vars** — the systems-variable docs (`a380-simvars.md`/`a380x-input-events.md`/`a380x-private-local-vars.md`) were last touched 2026-05-19 by the fuel-system #10641, NOT the rebuild. **New FWS abnormal non-sensed checklists (#10253: RELIGHT IN FLIGHT, TAILPIPE FIRE, VOLCANIC ASH ENCOUNTER, BOMB ON BOARD, SEVERE TURBULENCE)** render through the same FwsCore/`.EclLine` path, so the existing EWD/ECL scrape reads them automatically (no code). **Behaviour XML PATH MOVED:** `FlyByWire_A380_842\model\behaviour\` → `FlyByWire_A380X\attachments\flybywire\Part_Interior_Cockpit\model\behaviour\` (tool-doc references updated). **The only genuinely-new pilot vars** were 12 cockpit-furniture bool toggles in the new `interactive-parts.xml` that MSFSBA lacked — added to the Cockpit panel as `Sel` combos (meal tables, keyboard trays, CAS L/R + OIT + physical cockpit-door-open panels, and the 4 armrest STOW toggles); same `(L:VAR) ! (>L:VAR)` family as the existing table/footrest toggles, routed through the prefix-less calc-path allowlist in `HandleUIVariableSet`. Branch `feat/a380-native-2024-cockpit` (off main). **Stow polarity (0/1) on the armrest STOW combos is not visually confirmed — flip the value dict if a control reads inverted in-sim.**

**No-injection MCDU/flyPad transport.** The A380X MFD/MCDU and flyPad EFB are read AND driven live through the MSFS Coherent GT remote debugger (`http://127.0.0.1:19999`, WebKit inspector, `Runtime.evaluate`) — NOT via a Community-folder mod or HTTP bridge. `SimConnect/CoherentDebuggerClient.cs` (MFD, resolves the view by title needle `A380X_MFD`) and `SimConnect/CoherentEFBClient.cs` (flyPad, title needle `- EFB`) both implement `IMcduBridge`, so `FBWA380MCDUForm`/`FBWA380EFBForm` are transport-agnostic. The in-page agents are `Resources/coherent-a380-agent.js` and `coherent-flypad-agent.js` — **ES5 only** (Coherent GT = Chromium 49: `var`, no arrow funcs, no `String.includes`, top-level try/catch). MFD page-ids shift each session → always resolve by TITLE. **No Community-folder injection, no HTML patching, no sim restart** — the debugger is the sole A380 transport (all injection code was removed; PMDG uses its own Coherent debugger client — the HTTP `EFBBridgeServer` was deleted 2026-07). **Developer Mode is NOT required** — verified empirically on MSFS 2024 (cold boot, Dev Mode off): port 19999 is opened by the sim itself and `/pagelist.json` + the WebSocket `Runtime.evaluate` inspector protocol both work, so the debugger transport runs with no Dev Mode and no dev toolbar.

**flyPad = WebView2 "browser mode".** `FBWA380EFBForm` renders the scraped flyPad elements as a real semantic HTML document inside an embedded **WebView2** (already a dep; PMDG EFB precedent), so the screen reader gets native browse mode (H headings, K links, arrow-by-line, real `<input>`s, `aria-live` page-change). NO http server — `NavigateToString(PageHtml)` once, then `ExecuteScriptAsync("window.__render(<json>)")` per update; the page posts click/set/refresh back via `chrome.webview.postMessage` → `WebMessageReceived` → `EnqueueCommand`. The native flat-list is a SILENT auto-fallback only if WebView2 init fails (no user toggle). **Click index gotcha:** the agent's `clickElement`/`setValue` look up the STAMPED `data-fbwa380-efb-idx`, which diverges from the list position (the list is sorted+deduped after stamping) — so `CoherentEFBClient` carries it as `items.N.aidx` and the form sends THAT, not the loop index. **flyPad div-buttons:** many action buttons (e.g. modal Cancel/Confirm) are styled `<div>`s with no `button`/`btn` token or role — the agent classifies a `hover:`-styled leaf with its own short text as a button (interactive flyPad elements carry Tailwind `hover:` classes; static text never does). Value inputs (PAX/KGS) have no label metadata → `labelFor` reads the field's parent unit text before falling back to the section heading.

**ND OANS / BTV (Ctrl+Shift+B) — DATA-ONLY, ZERO-RENDER (2026-06, latest; supersedes all earlier scrape/TabControl OANS notes).** `Forms/FBWA380/FBWA380OansForm.cs` is a native WinForms `TabControl` (**Map and BTV / Airport / Status**) driven by `SimConnect/CoherentNDClient.cs` + `Resources/coherent-oans-agent.js` — but the agent is now **data-only**: it READS OANS/BTV state from the ND JS instance objects (`document.querySelector('a380x-nd').fsInstrument.oansRef.instance` → `btvUtils` / `labelManager.labels` / `fmsDataStore` / `dataAirportIcao` / `dataAirportName`) plus OANS L:vars, and WRITES via `btvUtils` methods + the msfs-sdk EventBus (`bus.pub`). **It NEVER writes `A32NX_EFIS_L_ND_RANGE`, forces panel `.style.visibility`, or scrapes the control-panel DOM.** ⚠️ The earlier `ensureAirportZoom`+DOM-scrape design forced a continuous full-airport map render on every poll and exhausted host commit memory (paging-file-too-small errors that froze the whole machine) — **do NOT reintroduce any forced render/zoom/visibility or DOM `scrape`/`enumerate`.** Agent API: `ping()`, `snapshot()` → `{ok,available,failed,airport,fms,btv,manual,airac}`, `armRunway(name)`, `armExit(name)`, `clearBtv()`, `displayAirport(icao)` (one-shot AMDB load — USER ACTION ONLY, never on a poll), `setManualStopDistance(m)`. The client polls `snapshot()` read-only (1 s), raises a dedup'd **`oans_state`** push (+ **`oans_connected`**), and exposes commands `get_snapshot` / `oans_arm_runway` / `oans_arm_exit` / `oans_clear` / `oans_display_airport` / `oans_set_manual_stop`. **Two tiers:** with Navigraph maps loaded (`A32NX_OANS_AVAILABLE=1`) the runway/exit pick-lists + arming + predicted dry/wet/live stop, ROT, turnaround and the runway-ahead QFU all work; without Navigraph the form shows a **Manual BTV** section — runway length (ARINC `A32NX_OANS_RWY_LENGTH`), type a stop distance → `oansManualStoppingDistance` bus pub, then "select the landing runway in the FMS". The top banner states which tier is active. **Visual-only OANS controls are intentionally REMOVED** (the RWY/TWY/STAND/OTHER entity picker, ADD CROSS/FLAG, CENTER MAP, the permanently-disabled LDG SHIFT) — they have no audio meaning for a blind pilot (STAND = parking stands, OTHER = de-icing areas — both map-locate-only). The runway-ahead advisory naming (`btvUtils.rwyAheadQfu`) shows in the window readout; an **always-on** named advisory (window closed) is deferred (it would need a persistent ND read socket — the generic SimVar `A32NX_OANS_WORD_1` bit-11 advisory in the def stays the always-on path). **Navigraph is user-side:** the AMDB airport maps are fetched from the online `https://amdb.api.navigraph.com` API using the user's Navigraph login in the flyPad EFB (Shift+T) — there is NO local file to fetch and MSFSBA must never try to; the aircraft loads the maps and MSFSBA reads what's loaded. **Exit pick-list is FILTERED to valid exits for the armed runway** — `snapshot().btv.exits` returns `agent.validExitsForArmed()`, a READ-ONLY (pure airport-local-metre math, NO canvas draw, NO mutation) verbatim port of FBW `OansBrakeToVacateSelection.selectExitFromOans`'s accept/reject test (400 m touchdown-zone, 50 m centerline, 120° gates; falls back to the full list only if the armed-runway threshold refs aren't set). Without it the combo listed all airport exits alphabetically and the first (e.g. OMDB K-series for rwy 12L) were silently rejected. **Multiple exit-line features can share ONE name (live-verified KSFO 28R / exit "Q", 2026-06): a taxiway often exposes a far-off-runway segment AND a valid on-runway one under the same text.** `validExitsForArmed` whitelists a NAME when ANY of its features passes (and sets the `seen` dedup only on ACCEPT, so an invalid first feature can't block a valid later one), so the list correctly shows "Q". But `armExit` used to pick the FIRST feature by name (`findLabel`) — at KSFO that was the off-runway "Q" (230 m off the 28R centerline) → `selectExitFromOans` rejected it → "Exit Q not valid … (wrong side or too close to threshold)" even though Q *was* valid. **FIX:** `armExit(name)` now iterates EVERY same-named exit-line feature and arms the first one `selectExitFromOans` accepts (mirroring a sighted pilot clicking the correct map label). **The per-feature `selectExitFromOans` call is wrapped in its OWN `try/continue` (not one try/catch around the whole loop)** — a throw on an early/malformed same-named feature must fall through to the next candidate, not abort the loop and reject a valid later feature; the last error is reported only if NO feature armed. Likewise `armRunway`'s threshold-search loop guards `feats[k] && feats[k].properties` (it runs outside the method's try, so an unguarded `.properties` deref on a partial AMDB feature would throw uncaught out of `armRunway`). This is SAFE re the memory rule below: it loops only over the 1–2 features sharing the SELECTED name (not all ~290 exits), and a REJECTED feature returns from `selectExitFromOans` BEFORE `drawBtvLayer` — so at most ONE canvas redraw (the accepted feature) occurs, same as before. **Exit list is sorted closest-first with distance:** `validExitsForArmed` returns `[{name, dist}]` sorted ascending by `dist` = the BTV exit distance in metres (raw threshold→exit minus the 400 m touchdown zone == `btvExitDistance`, so the pick-list and the armed-exit readout report the SAME number); the snapshot carries a parallel `btv.exitDists` array, and the form's exit combo items read "Q, 2,289 m / 7,510 ft" (unit per the metric toggle) so the screen reader announces how far down the runway each exit is while arrowing the dropdown. **Rejection feedback:** `EnqueueCommand` captures the arm result and raises `oans_action`; the form announces non-success results (e.g. "Exit K1 not valid for this runway …") so a rejected exit is never silent. ⚠️ NEVER loop `armExit`/`armRunway` over the FULL exit list (~290 calls) — each ACCEPTED arm triggers a BTV canvas redraw and a tight full-sweep exhausts host memory; the validity FILTER above is the read-only way to enumerate valid exits (arming only the 1–2 same-named features, as the fix does, is fine). **Loading an airport: call `oansRef.instance.loadAirportMap(icao)` DIRECTLY, NOT the `oans_display_airport` bus event.** When the OANS is in performance-hide mode (FBW perf mode on + the ND not rendering the OANS — the normal case for us since we never render), the `oans_display_airport` handler (Oanc.tsx) only sets `dataAirportIcao` and SKIPS the load, leaving the ICAO showing with `data===undefined` / 0 labels / `btvReady` false (symptom: "(KLAX)" with no runway list). `agent.displayAirport()` therefore calls `loadAirportMap(icao)` directly (bus pub is the fallback), which loads the AMDB + builds labels regardless of perf-hide (live-verified KLAX → 4789 features / 828 labels, persists; `getAirportData` itself was never the problem). Same gate disables the cockpit auto-load under perf-hide, so the user must press "Display airport" (or Origin/Dest/Alternate) to load — the banner says "maps available — load an airport" until they do.

**Accessible BTV exit arming — native combos + buttons + auto-announce (2026-06, live-verified at VCBI).** On the real A380 you SELECT the BTV landing runway + exit by **clicking the runway-end + exit LABELS on the moving map** (`Oanc.tsx` → `btvUtils.selectRunwayFromOans` / `selectExitFromOans`). Those are SVG on the map canvas with no control-panel widget, so a blind pilot cannot reach them — and selecting RWY/TWY in the control panel only filters the *map*, it does not arm BTV (the user's "if i select rway nothing is shown" / "can't select taxiways after the landing runway is selected" — that dropdown is a map-filter, not an arming control). **`coherent-oans-agent.js` calls the same `btvUtils` methods directly** via the ND instrument instance (`document.querySelector('a380x-nd').fsInstrument.oansRef.instance` → `btvUtils`):
- `oanc()` / `btvReady()`; `btvRunwayList()` / `btvExitList()` (from `labelManager.labels` filtered by `associatedFeature.feattype`: RunwayThreshold=2, runway-centerline=4, RunwayExitLine=19);
- `armRunway(name)` (finds the centerline label + the `data.features` threshold with `idthr===name`, calls `selectRunwayFromOans(icao+name, centerline.associatedFeature, threshold)`); `armExit(name)` (requires a runway armed first; `selectExitFromOans(name, exitLabel.associatedFeature)` — returns "wrong side / too close to threshold" if FBW rejects it); `clearBtv()`;
- `snapshot().btv → `{ready, runways:[], exits:[], runway, exit, lda, exitDist, dry, wet, stop, computing}` — the pick-lists, the armed runway/exit (these are **NOT L:vars**, only OANS observables `btvRunway`/`btvExit`/`btvRunwayLda`/`btvExitDistance`), and the predicted **DRY / WET / live STOP-bar** distances read from the plain-metre L:vars `A32NX_OANS_BTV_{DRY,WET,STOP_BAR}_DISTANCE_ESTIMATED` (0 until the FMS computes the landing on approach; stop-bar only surfaced once dry/wet compute, since it carries a ~40 m ground offset).
`snapshot()` returns the BTV block (data-only — see the zero-render note above). `CoherentNDClient` parses it (`Snapshot.btv`), folds it into the dedup hash, pushes `btv.*` keys, and exposes commands **`oans_arm_runway`** / **`oans_arm_exit`** (value=name) / **`oans_clear`** (plus `oans_display_airport` / `oans_set_manual_stop`). `FBWA380OansForm` builds a **BTV runway combo + "Arm runway"**, an **exit combo + "Arm exit"** (enabled once a runway is armed), and **"Clear BTV"** from the snapshot; the readout shows the armed runway (+ LDA), exit (+ distance), and dry/wet/stop predictions; and it **auto-announces on change** ("BTV armed, runway 22, exit E, 2835 metres" / "BTV cleared"). **Live-verified end-to-end at VCBI** (driving the agent directly): `snapshot().btv returns runways `["04","22"]`, after `armRunway("22")`+`armExit("E")` → `runway:"VCBI22", exit:"E", lda:3351, exitDist:2835`, exits `["A".."E"]`; `clearBtv()` resets to `runway:null`. (Source: `fbw-common/.../OANC/OansBrakeToVacateSelection.ts` + `Oanc.tsx`; selected idents live only on the event bus / observables, so the snapshot reads them from the ND JS instance, not SimVars.)

**OANS refinements (2026-06): units, ROT/turnaround, tab header, tab-aware search.**
- **Distance UNITS follow the metric toggle.** The OANS/BTV distances (LDA, exit distance, dry/wet/live-stop-bar) are stored in METRES but the real ND shows them in **M or FT per the metric setting** (FBW: `CONFIG_USING_METRIC_UNIT` → `UnitType.METER/FOOT`, factor 3.280839895). `snapshot().btv` reads **`A32NX_EFB_USING_METRIC_UNIT`** (the var MSFSBA already follows for weights, which tracks the EFB "US Units" toggle) as `metric`; the form's `Dist()` shows metres or feet accordingly. So OANS distances honour the same unit toggle as the rest of MSFSBA — verified `metric:true` live.
- **BTV ROT + TURNAROUND times (ARINC429-decoded).** `A32NX_BTV_ROT` (runway occupancy time, **seconds**) and `A32NX_BTV_TURNAROUND_{MAX,IDLE}_REVERSE` (brake-cooling time to next departure, **minutes**, idle = hotter brakes = longer) are **ARINC429** words. `coherent-oans-agent.js` `A._arinc(raw)` decodes them (low 32 bits = IEEE-754 float32 via `DataView`, SSM = bits 32-33; valid when SSM 3/2). Surfaced in the readout, **gated on an EXIT being armed** (matching the real OANS, which only shows them then). Live-verified the decode: `rot:30, turnMax:171, turnIdle:197` with an exit armed. Phrasing: "Runway occupancy time 30 seconds" / "Turnaround: 171 minutes max reverse, 197 minutes idle reverse".
- **Current-tab header + tab-aware search.** The readout drops the three tab lines (kept in the controls list to switch) and shows one **"Current tab: MAP DATA"** header derived from the `(active tab)` marker (live-verified clicking a tab moves the active marker). The **search box is tab-dependent** — the "Runway or exit" InputField on MAP DATA is the *airport-code* field on ARPT SEL (with ICAO/IATA/CITY radios) — so the form labels the search box from the live input's own label (`_searchField`, the text before the colon) and disables it when no input is present. `setValue` on the field is live-verified ("ok"); the taxiway search drives the FBW InputField (its accessible payoff is map-centering, so the future airport-diagram reader is the real "tell me about taxiway B" win).

**MFD navigation is via the always-present HEADER, NOT an "INIT hub" — KEEP the page picker (#105).** Investigated the theory that "every MFD page is reachable from INIT" (true-ish on the A320/A330 MCDU via the physical page keys): it is **FALSE for the A380**. Source (`FmsHeader.tsx`) shows every FMS page carries a persistent header of 4 dropdown tabs — **ACTIVE** (F-PLN/PERF/FUEL&LOAD/WIND/INIT), **POSITION** (MONITOR/REPORT/NAVAIDS/IRS/GNSS/TIME), **SEC INDEX** (SEC 1/2/3), **DATA** (STATUS/WAYPOINT/NAVAID/ROUTE/AIRPORT/PRINTER) — plus the top system tabs (FMS/ATCCOM/SURV/FCU BKUP). INIT is just one item under ACTIVE; it has no links to other pages. **Sighted pilots navigate via this header, not through INIT.** Crucially, the MFD scrape does NOT capture the header tabs (verified live: 0 header-tab elements scraped though 40 `_MFD_pageSelector` DOM nodes exist — they're the navigateById click targets, outside the scraped content area), so the **"Go to MFD page" combo is currently the ONLY way a blind pilot can reach most pages** (besides the quick buttons + Ctrl+arrows). It is the accessible equivalent of the always-visible header — strictly better than expanding 4 dropdowns one item at a time. **Do NOT remove the page picker** — it would strand the user. (Confirmed: keep it.)

**ATC COM / CPDLC + D-ATIS — navigate by UIService URI, NOT page-selector id.** The page-selector ids (`{CAPT|FO}_MFD_pageSelector{Tab}_{idx}`) only exist while that *system's* header is mounted, so the FMS-header `navigateById` click can't reach ATCCOM from an FMS page. The six ATCCOM pages are in `AllPages` with a non-empty `Uri` field (page-selector dispatch picks `navigate_uri` when `Uri` is set, else `navigate_by_id`); the **ATC COM button** (Alt+A) now fires `SendNavigateUri("atccom/connect")` instead of the old KCCU-only `navigate_by_id("",-1,"ATCCOM")`. **Fuel pumps + niche controls + pitch-trim correctness (post-#107 user follow-up).** (1) **Feed-tank FUEL PUMPS** — were entirely missing. (2) **Pitch-trim correctness** — MSFSBA's "Pitch Trim" read the stock `ELEVATOR TRIM INDICATOR` (normalized −1..1), which is the WRONG representation for the A380. Fixed to read **`ELEVATOR TRIM POSITION` (radians)** and decode in `TryGetDisplayOverride` to "X.X degrees up/down" (positive = UP) — matching the A380 SD `PitchTrim.tsx` (`thsPositionRadians * RAD_TO_DEG`, `Math.sign === 1 ? 'UP' : 'DN'`). The predicted-takeoff-trim readout (`A32NX_TO_PITCH_TRIM`, ARINC429 BNR ±180 = degrees) is correct as-is. The trim WHEEL set isn't a combo (a blind pilot reads the target + actual and adjusts with the global elevator-trim keys/axis — the readouts are the accessibility win). ### FG-into-PRIM variable migration (FBW #10855, synced 2026-08-19)

**FlyByWire moved the Flight Guidance (autopilot laws, state machine, autothrust) into the PRIM**, deleting the standalone `AutopilotLaws` / `AutopilotStateMachine` / `Autothrust` modules — architecturally the same move as #10797, which is what forced the earlier FAC→PRIM speed rename. It killed **14 A380 vars MSFSBA was using, plus 7 input EVENTS** (below). A naive read-side diff finds only six of the vars; the other eight (the ND EFIS filter buttons) surface only when you diff *every* A32NX_/A380X_ token in the FBW tree before vs after the commit and intersect that with the def's own references. Do that intersection, not a spot check, the next time FBW moves a subsystem.

**⚠️ And intersect the EVENTS, not only the variables — that omission is how the first pass shipped 7 dead controls.** A variable that disappears at least reads a suspicious 0. A deleted input event has *no* failure signal whatsoever: FBW removes its `addInputDataDefinition()` call, the sim silently discards the K-event, and the control just stops doing anything while its combo happily keeps reporting the aircraft's real state from a still-live read var. There is nothing to notice. Enumerate `GetVariables()` where `Type == SimVarType.Event`, and grep the def for `H:` literals, and check both lists against the FBW tree — `FlyByWireA380EventContractTests` now pins the result.

**⚠️ Requires FlyByWire A380X `1bbd304` (18 Aug 2026) or later** — the Development build from the FlyByWire Installer. This sync is deliberately lean: there is no version-sniffing and no compatibility fallback, because the vars below do not exist at all in older builds and the FCU value units changed outright (next paragraph), so a stale aircraft would report wrong numbers rather than obviously missing ones.

**⚠️ The FCU value vars changed UNITS, not names — a silent break a name diff cannot catch.** #10855 also turned `A32NX_AUTOPILOT_{HEADING,VS,FPA}_SELECTED` into FCU *display* shims (`idFcuShimHdgValue2 <- selectedFcuAfs.hdg_trk_value`; `idFcuShimVsValue` / `idFcuShimFpaValue <- selectedFcuAfs.vs_fpa_value`). They now carry degrees / feet-per-minute / degrees directly, where older builds wrote radians and m/s. All three MSFSBA conversions were removed: V/S had begun announcing a 500 fpm selection as **"98400 feet per minute"** (500 × 196.85). When FBW moves a subsystem, re-check the units of the vars that *survived*, not only the ones that disappeared.

**Do not re-add "looks like radians" magnitude guesses.** The old heading and FPA paths converted only when `|value|` fell in a radian-looking range. Against display units that silently corrupts small values: a selected heading of 006° and an FPA of 0.2° both fall inside the guess window and would be inflated to 344° / 11.5°. Read the value as-is and require the current aircraft build instead.

**⚠️ Never register the same var KEY twice.** `Read()` does `vars[key] = …`, so a second registration silently replaces the first — `A32NX_AUTOPILOT_VS_SELECTED` was registered both as `"feet per minute"` and as `"number"`, and only the later `"number"` ever took effect. The dead entry was removed; the surviving pair is annotated. (Distinct keys sharing one `Name` are fine and common — see the batch-collision note below.)

**The `_LIGHT_ON` vars are the cockpit's own indicator source**, not a backlight: `efis-cp.xml` / `fcu.xml` set `INDICATOR_CODE = (L:A32NX_FCU_..._LIGHT_ON)`, and the WASM writes them per frame (`idFcuAfsPanelLocLightOn->set(fcu1Afs.loc_light_on || fcu2Afs.loc_light_on)`). They are therefore **read-only**; the set path stays the unchanged `A32NX.FCU_*_PUSH` toggle events through `_fcuToggleEvents`, which fires only when the picked state differs from the cached one. Proof they are per-button state rather than a shared backlight: with ARPT lit, CSTR read 0 at the same moment.

**⚠️ The ND Filter IS a single mutually-exclusive selector — the old combo's shape was right.** This was briefly "corrected" to three independent On/Off controls on the strength of a live observation that all three could be lit at once. That observation cannot be reproduced and the source rules it out: `A380FcuComputer.cpp:2271-2281` holds ONE `pEfisFilter` enum (NONE/WPT/VORD/NDB) where pressing the active button clears it and pressing any other REPLACES the selection, and :2567-2572 derive each light as `efis_filter == <enum>`, so two lit at once is unreachable. A test pilot duly reported "turn Waypoints on, then turn NDB on, and Waypoints turns off" — the aircraft was correct and the app was offering a shape it does not have.

So the ND filter is ONE combo per side (Off / Waypoints / VOR-DME / NDB), state derived from the three lights, actuated by ONE press: `NdFilterSelection` owns the mapping and the evidence. Note the trap in the set path — there is no "off" button on the panel, so clearing the selection means re-pressing whatever is currently ACTIVE. CSTR, ARPT and V/V are genuinely independent (T flip-flops in the same function, `vvActive = !vvActive`) and remain separate On/Off controls.

**⚠️ The filter CANNOT be cleared back to Off on this build, despite the code reading as though it can.** `A380FcuComputer.cpp:2271-2274` says pressing the ACTIVE button sets the selection to NONE. It does not: measured live 2026-08-22, six presses across WPT, VORD and NDB, each with a distinct command string so coalescing is excluded, and the selection never cleared — while pressing a DIFFERENT button replaced it every single time, and CSTR (a real toggle) switched off happily in the same session. So `PushEvent` still sends the press (harmless, and it starts working if FBW changes), and `IsClearAttempt` + `ClearUnsupportedMessage` make MSFSBA SAY so, because a control that silently does nothing is worse for a blind pilot than one that explains itself. Live-verified mutual exclusion in the same session: WPT went 1→0 the instant NDB went 0→1. The three lights are never announced INDIVIDUALLY — one filter change moves two of them, so that would speak twice (old off, new on). The DERIVED selection IS announced, once, on a real change: the combo is write-only and only ever speaks the pilot's own pick (through the screen reader), so without that call-out a filter changed in the 3-D cockpit, on a hardware EFIS-CP or by the aircraft itself would reach a blind pilot through no channel at all. It is baseline-first — silent until all three lights of the side have reported once, because they arrive one at a time and a partial view reads as Off — and it suppresses the echo of the pilot's own combo pick with its own short window, since MainForm's global `_uiSetEcho` gate keys on the var the combo SET (`ND_FILTER_{side}`) while what comes back is a different var.

**⚠️ The READOUT is keyed on the WPT light, never on the `ND_FILTER_{side}` combo.** That combo is an `Act()` action control, so `Name = key` and nothing ever writes `L:ND_FILTER_L` — and a data definition bound to a nonexistent L:var never delivers (`SimConnectManager.RebindVariableDataDefinition`, from the 2026-06-12 bridge-probe finding). `UpdateDisplayText` only calls `TryGetDisplayOverride` once a value exists for the key, so a display row keyed on the combo reads `--` for the whole session and the decoder never runs. The WPT light is a real batched var, so it carries the row and the `{who} ND Filter Position` DisplayName, and it is the one of the three that is NOT `ExcludeFromMonitorManager` — it is the Ctrl+M row that mutes the call-out. This is exactly the wiper split: `Act("WIPER_LEFT")` writes, `WIPER_L_SW` (a real `CIRCUIT SWITCH ON:141`) reads. `FlyByWireA380DisplayReachabilityTests` pins it.

**⚠️ Never put two BATCHED var keys on the same underlying `Name`.** The first attempt here gave speed-protection and mode-reversion a key each, both pointing at FG discrete word 5. That puts two identical `L:…` entries into the continuous batch, and `SetupDataDefinitions` sorts that batch by full name to mirror SimConnect's own ordering — precisely the data-definition position drift the `ExcludeFromBatch` docs warn about, which would silently shift every later var's struct slot so unrelated readouts return each other's values. The shipped design is ONE var (`FMA_FG_ALERTS`) decoded into two spoken alerts in `ProcessSimVarUpdate`; Ctrl+M mutes both together.

Note the qualifier: distinct keys sharing one `Name` are routine and deliberate (`PFD_VLS` and `A32NX_SPEEDS_VLS` both read `A32NX_SPEEDS_VLS`, one for the PFD readout and one for the monitor). It is only a defect when BOTH copies are `Continuous` and batched. Measured fleet-wide, the A380 has zero such collisions; the A320 and A330 each carry one pre-existing autobrake-mode collision, allow-listed in `VarNameCollisionTests` and worth fixing on their own branch.

**⚠️ FG word 5 bit 28 is ASSERTED on a cold, parked aircraft** (measured: payload `0x48000000`, so bits 28 and 31 set, SSM Normal Operation). Bit 28 is confirmed to be `ap_fd_mode_reversion` — `A380PrimComputerFctl.cpp:4327` assigns it to concatenate index 17, and index 18 is `vs_target_not_held`, so the 28/29 mapping is right. But a reversion flag that is true at rest means the "FMA Reversion" call-out's SENSE is unverified: baseline-first keeps it silent at startup, yet the first thing a pilot may hear is "FMA Reversion: off" as modes engage. Judge it on a real approach before trusting it; do not assume the mapping is wrong, because it is not.

**Bit numbering is ARINC 1-based and must stay SSM-gated.** `Arinc429Word.BitValueOr` computes `_raw32 >> (bit - 1)` with an SSM guard, identical to FBW's `arinc429.ts`. A word that is not Normal Operation / Functional Test must announce NOTHING rather than a false "off" — FG word 3 and 5 both read SSM NormalOperation live.

**⚠️ Repeated identical calc-path presses are COALESCED — and this bit the app, not just hand-testing.** Pressing the same `'A32NX.FCU_EFIS_L_CSTR_PUSH'` twice in a row leaves the light on: MobiFlight drops the second identical command string (the same invariant the RMP/DCDU writes already carry). This was first written off as a testing artifact on the grounds that MSFSBA's own presses are "one-per-user-action and seconds apart" — **that reasoning is wrong**, and the note is kept here as the correction. The dedup keys on the command TEXT, not on elapsed time, which is exactly why the RMP and DCDU needed a `<seq> 0 *` prefix rather than a delay. It applies to every TOGGLE reached through `SendEvent`, because "on" and "off" are the same event and therefore the same string: an EFIS filter or LOC/APPR the pilot switched on could never be switched off again.

The prefix now lives centrally in `SimConnectManager.BuildCalcEventCode`, so every H: and dotted event `SendEvent` fires is unique per call and no call site has to remember. Pinned by `CalcEventCodeTests`, and **proven live** on 1bbd304 (2026-08-22) in three steps against the CSTR toggle: `0 (>K:…CSTR_PUSH)` moved the light 0→1; the BYTE-IDENTICAL string again left it at 1 (dropped); `11 0 * 0 (>K:…CSTR_PUSH)` moved it 1→0. That is the whole failure and the whole fix in one experiment — reuse it if the behaviour is ever doubted again.

**The baro STD flag is read from `A32NX_FCU_EFIS_{L,R}_DISPLAY_BARO_IS_STD`** (`FlyByWireInterface.cpp:813`, written every frame at `:2408` from the FCU's own `baro_std`; FBW's `FcuSimvarPublisher` reads the same names). MSFSBA previously read the stock `KOHLSMAN SETTING STD:{1,2}` mirror. The FCU's own per-frame output is the more direct source, so the switch stands — but be clear about what it did NOT fix.

**⚠️ CORRECTION — a wrong diagnosis was published here and is retracted.** This section briefly claimed the stock mirror had lost its only writer with `MsfsBaroManager.ts` and could "never change again", and that this was why a tester reported the altimeter stuck on QNH. **Both claims are false**, disproven live on 1bbd304 (2026-08-22): firing `BARO_PUSH` moved `KOHLSMAN SETTING STD:1` 0→1 and `BARO_PULL` moved it 1→0, on both sides, with nothing in MSFSBA writing it. The aircraft keeps that mirror in sync in both directions.

The tester's actual fault was that they were running a build predating the fix — `MSFSBlindAssist.dll` reported `470a5cfa` (main, pre-#198) and `debug.log` showed it emitting the DELETED `H:A380X_EFIS_CP_BARO_PUSH_1`. The real cure was the event migration already made above. **The lesson is procedural: check which binary is running before diagnosing behaviour.** `startup.log` names the Application Directory and the DLL carries the commit in its ProductVersion; one look at either would have saved the whole investigation. Reach for `debug.log`'s `Sending event:` lines early — they say what the app actually emitted, which no amount of source reading can.

The `BARO_MB_WATCH_*` mirrors and the MainForm STD-flag watchdog were removed alongside. That removal is still right — nothing reads the stock flag now, so their back-fill write would converge on nothing and a genuine QNH of 1013 would retry it every 2 s — but note the removal was NOT needed to fix any reported bug.

**Still live, do not "fix":** `A380X_EFIS_{L,R}_LS_BUTTON_IS_ON`, `..._TRAF_BUTTON_IS_ON` and `..._ACTIVE_OVERLAY` survived the commit. The A32NX keeps `A32NX_FCU_APPR_MODE_ACTIVE` and `A32NX_FMA_EXPEDITE_MODE`, so the A320 def is deliberately untouched.

### The FCU ALTITUDE managed/selected state is DERIVED, not read (FBW #10855 aftermath, 2026-08-23)

**⚠️ `L:A32NX_FCU_ALT_MANAGED` is hardcoded to 0 on this aircraft and can never be read again.**
#10855 deleted the TypeScript FCU that used to publish it and replaced it with a WASM shim
that writes the var, in `updatePrimFgShim`, every single frame:

```cpp
const bool lvlChManaged = false;
simConnectInterface.sendEvent(Events::AP_ALTITUDE_SLOT_INDEX_SET, lvlChManaged ? 2 : 1, …);
idFcuShimAltManaged->set(lvlChManaged);
```

So the stock `AUTOPILOT ALTITUDE SLOT INDEX` beside it is dead too, and neither is a usable
substitute for the other. This is the *fourth* distinct shape #10855 broke — a var that was
deleted, a var that changed units, an event that was deleted, and now a var that still exists,
still reads, and always lies. Measured live at FL360: `altManaged=0`, `altSlot=1`, while the
three sibling flags (`hdgDashes=1`, `spdDot=1`, `vsManaged=1`) were all correct. **Altitude was
the only one of the four stranded, which is exactly why only that readout went wrong** and why a
sweep of "the managed flags" finds nothing. `A32NX_FCU_HDG_MANAGED_DOT` is hardcoded the same
way (`const bool hdgTrkManaged = false`) but nothing reads it — heading uses `…_DASHES`.

**The replacement is FBW's own formula, not an invention.** `AltitudeManagedState` transcribes
the deleted `FCU/Managers/AltitudeManager.ts` (at `1bbd304c4^`), which is the authoritative
definition of what the var meant:

```
(verticalArmed & (AltCst|Clb|Des|Gs)) > 0 || MANAGED_MODES.includes(verticalMode)
```

Both inputs survive as `A32NX_FMA_VERTICAL_MODE` / `A32NX_FMA_VERTICAL_ARMED` and were already
monitored, so nothing new is registered to get them.

**⚠️ The key `A32NX_FCU_ALT_MANAGED` must never be aliased onto `A32NX_FMA_VERTICAL_MODE`, and
must never be `ExcludeFromBatch`.** That pairing was the first attempt and it broke the feature
outright. `ExcludeFromBatch` gives a var a standing `PERIOD.SECOND` subscription bound to its
data-def id (`SimConnectManager.Setup.cs`), while `RequestVariable(key, forceUpdate: true)`
re-issues that SAME id with `PERIOD.ONCE` (`SimConnectManager.DataRequests.cs`) — which replaces
the recurring request. Nothing re-arms it; the codebase's own cancel idiom
(`SafelyClearDataDefinition`) works by re-issuing `PERIOD.NEVER` on the same id, which is the
proof the replacement semantics are real here. The key is listed in the FCU display list, and the
panel force-reads every display var on open and on its 1 Hz auto-refresh — so **opening the FCU
panel once froze the derivation for the rest of the session** and the call-out never fired again.

The derivation therefore reads `A32NX_FMA_VERTICAL_MODE` under its OWN key, which is batch-covered
and structurally immune: `RequestVariable` early-returns for batch-covered vars before it can issue
the `PERIOD.ONCE`. That branch must NOT return true — it falls through so the generic monitor still
speaks "Vertical Mode: …". `A32NX_FCU_ALT_MANAGED` survives only as an inert definition: it keeps
the pilot's Ctrl+M mute row (keyed on the var key, so renaming it would silently un-mute anyone who
had turned the call-out off) and the FCU panel row, which renders from `TryGetDisplayOverride` off
the derived tracker. `ProcessSimVarUpdate` returns true for it so the generic monitor never speaks
its dead 0, and **nothing reads its value at all** — so the old warning about
`GetCachedVariableValue(...) > 0.5` reading "managed" for every mode but None no longer applies to
it. Shift+A reads the derived state at emit time rather than awaiting a second delivery.

**Still live elsewhere:** `A32NX_FCU_HDG_MANAGED_DASHES`, `A32NX_FCU_SPD_MANAGED_DOT` and
`A32NX_TRK_FPA_MODE_ACTIVE` are all `ExcludeFromBatch` and all force-read by
`RequestFCUHeadingWithStatus` / `RequestFCUSpeedWithStatus` / `RequestFCUVSWithStatus`, so by the
identical mechanism the first Shift+H / Shift+S / Shift+V of a session should permanently kill the
corresponding "… Mode: Managed/Selected" auto-announce. Unlike altitude these three genuinely need
their individual def for the readout's two-half pair-gate, so the fix is not the same one and wants
its own investigation. Not yet verified in the sim.

**⚠️ LAND / FLARE / ROLL OUT cannot arrive on the vertical mode at all — that is why the lateral
mode is an input.** The #10855 shim's vertical-mode if-chain assigns `lateralMode` in its
32/33/34 branches, a verbatim copy-paste of the three branches in the lateral chain directly
above it, so `A32NX_FMA_VERTICAL_MODE` falls through to 0 ("None") once G/S track drops on an
autoland. Without the rescue the altitude mode would flip to Selected during the flare **and
announce it** — a spurious call-out at the worst moment of the approach. The rescue stays correct
if FBW fixes that chain, because on a real autoland the lateral and vertical LAND/FLARE/ROLL OUT
modes engage together. LOC capture/track (30/31) are deliberately excluded: localizer tracking
says nothing about the vertical side. This is an upstream defect worth reporting, not a shape to
design around permanently.

**The call-out is coalesced against the last value SPOKEN, not the last computed, and is silent
while the vertical mode is None.** All three inputs — vertical mode, armed bitmask, lateral mode —
now ride the continuous batch, but each still arrives on its own `ProcessSimVarUpdate` branch, so
an autoland would otherwise announce "Altitude Mode: Selected" and then "Altitude Mode: Managed"
one frame apart. The state is still updated during the silence, so a Shift+A in that window is
answered correctly. Baseline-first, as every other MSFSBA monitor is, and only once BOTH primary
inputs have reported at least once (`IsKnown`): a half-delivered view would announce a mode that
was already showing when the app connected.

That whole sequence — readiness, the autoland transient, spoken-vs-computed, and `Reset()` —
lives in the pure `AltitudeModeTracker` (`MSFSBlindAssist/Aircraft/AltitudeModeTracker.cs`, pinned
by `AltitudeModeTrackerTests`) rather than in the definition, which is what makes it testable
without a sim. `Reset()` is reached from `ResetAnnouncementBaselines()`, called on SimConnect
reconnect, so a reconnect re-baselines instead of announcing a mode that never changed.

**⚠️ `A32NX_FMA_VERTICAL_ARMED` no longer carries the ALT CST bit.** The shim builds it as
`altArmed | (clbArmed << 2) | (desArmed << 3) | (gsArmed << 4) | (finalArmed << 5) |
(tcasArmed << 6)` — bit 1 is skipped. `ManagedArmedMask` keeps it for fidelity with the formula
above (an ALT CST arm reaches us through the ALT CST vertical *mode* instead, and the bit costs
nothing if FBW restores it), but the existing "Altitude constraint armed" call-out in
`_vertArmedBits` can no longer fire on this build. That gap is closed in the next section: the
dead bit was removed and the constraint now RENAMES the armed-ALT bit instead.

### There is no "ALT CST armed" bit — the constraint RENAMES the armed ALT call-out (2026-08-23)

**⚠️ Do not go looking for one.** The A380 PRIM FG's armed-modes bus (`base_prim_armed_modes`,
`A380PrimComputerFctl_types.h`) carries exactly `alt_acq_armed`, `alt_acq_arm_possible`,
`glide_armed`, `app_des_armed`, `clb_armed`, `des_armed`, `op_clb_armed`, `tcas_armed`,
`nav_armed`, `loc_armed`, `rwy_armed`, `land_armed` — and that is the whole list. FG discrete
word 2 maps them in that order from bit 11:

| bit | signal | | bit | signal |
| --- | --- | --- | --- | --- |
| 11 | `alt_acq_armed` | | 17 | `op_clb_armed` |
| 12 | `alt_acq_arm_possible` | | 18 | `tcas_armed` |
| 13 | `glide_armed` | | 22 | `nav_armed` |
| 14 | `app_des_armed` | | 23 | `loc_armed` |
| 15 | `clb_armed` | | 24 | `rwy_armed` |
| 16 | `des_armed` | | 28 | `land_armed` |

Bit 12 is the obvious-looking candidate and it is **not** ALT CST — it is
`alt_acq_arm_possible`, a permission flag. Check the concatenate block that builds the word
(`A380PrimComputerFctl.cpp:4240-4259`) before assuming any bit's meaning from its neighbours.

**The constraint is a separate qualifier in FG word 3**, and the PFD's own armed-vertical cell
(`FMA.tsx` `B2Cell`) is where the combination is defined:

```
altAcqArmed        = PRIM_1_FG_DISCRETE_WORD_2 bit 11   (reaches us as VERTICAL_ARMED bit 1)
altCstrApplicable  = PRIM_1_FG_DISCRETE_WORD_3 bit 28
altIsCrzAlt        = PRIM_1_FG_DISCRETE_WORD_3 bit 29

altAcqArmed && altCstrApplicable -> "ALT" rendered MAGENTA
altAcqArmed && altIsCrzAlt       -> "ALT CRZ"
altAcqArmed                      -> "ALT" rendered CYAN
```

So on the A380 the constraint case is signalled by **colour alone** — the text stays "ALT" —
which is exactly the difference a blind pilot has no other channel for. (The A320 writes
"ALT CST" into the text, which is why the older bit table had a name for it.) `ArmedAltitudeMode`
owns the rule, constraint outranking cruise because that is the order the PFD tests them in, and
both bits are read SSM-gated so a failed word degrades to the plain "Altitude armed" rather than
inventing a constraint.

**⚠️ Neither qualifier is an armed state and neither may ever announce on its own.** Measured live
at FL360 immediately after a step climb: `alt_cstr_applicable` was TRUE while
`A32NX_FMA_VERTICAL_ARMED` was 0 and nothing at all was armed. `FMA_CRUISE_ALT_MODE` is therefore
Continuous but `ExcludeFromMonitorManager` and silent — `ProcessSimVarUpdate` caches the two bits
and returns true. It was promoted from OnRequest because the qualifier has to be live when the
armed bitmask moves; its "Cruise Altitude Mode" panel row is unaffected and is now live too.

**The dead bit 2 was removed, not repaired.** FBW's shim builds `A32NX_FMA_VERTICAL_ARMED` as
`altArmed | (clbArmed << 2) | (desArmed << 3) | (gsArmed << 4) | (finalArmed << 5) |
(tcasArmed << 6)` — bit 1 is skipped because there is no signal to put there, so the old
`(2, "Altitude constraint")` entry could never fire. The A32NX WASM builds its bitmask with the
**identical** expression (`fbw_a320/src/FlyByWireInterface.cpp`), so the A320 def's bit 2 was
removed in the same change. Its qualifier comes from a different place — the SSM of
`A32NX_FMGC_{1,2}_FM_ALTITUDE_CONSTRAINT` rather than a discrete bit — and is source-verified
against `FmgcComputer.cpp` rather than sim-verified. See [a32nx.md](a32nx.md).
**Known remaining gap:** `op_clb_armed` (word 2 bit 17) is dropped by that shim and
`FgVerticalArmedFlags` has no slot for it either, so "OP CLB armed" cannot be announced from this
bitmask on either airframe.

**⚠️ Known unfixed: the armed-ALT qualifier is read one delivery stale.** The armed bitmask is
always dispatched BEFORE its qualifier — on the A380 they are in different continuous batches
(requested 1 then 2, so separate SimConnect messages); on the A32NX the bitmask sorts ~3 slots
ahead in the same batch (`Setup.cs` sorts by `CompareOrdinal` on the `L:`-prefixed name, and
"FMA_" < "FMG"). A definition only learns a value when its own `ProcessSimVarUpdate` branch runs,
so a constraint that becomes applicable in the SAME 1 Hz sample the ALT bit arms is named from the
previous tick and speaks "Altitude armed" for a constrained altitude. The call-out is
edge-triggered (`iv & ~prev`, with `_prevVertArmed` assigned before the edge test), so it never
re-fires and the wrong name is permanent; the panel row self-heals on the next repaint, so speech
and display then disagree. The converse — "Altitude constraint armed" for a plain ALT — is
arguably likelier, since a constraint clearing and ALT re-arming often share a cause.

**Do NOT "fix" this by reading the qualifier from `SimConnectManager.GetCachedVariableValue` at
announce time.** That was tried and reverted (`2f44736b`): it rests on a producer/consumer
threading model this app does not have. Dispatch is SYNCHRONOUS on the UI thread —
`ReceiveMessage()` has a single call site reached from `MainForm.WndProc`, `InvokeRequired` is
therefore false in `OnSimVarUpdated` so the event queue is never used, and `VarCache.cs` writes
the cache and fires the event in the same loop iteration. A var later in the batch is simply not
cached yet. The real fix is either a two-pass `ProcessContinuousBatchImpl` (cache-write pass over
the whole batch, then event-fire pass — fixes the A32NX, touches the hottest shared path, and
does nothing for the A380's cross-batch case) or latching the newly-armed ALT edge and naming it
on a later turn. Both need live-sim verification.

### The FBW-drift sweep — how to run it, and the four ways the obvious method lies (2026-08-23)

A full sweep of both FBW airframes after #10855 found **no further defects** beyond the two
fixed that day. The result matters less than the method: the recipe this file used to carry
("diff every `A32NX_`/`A380X_` token in their tree and intersect with the def's references")
produced 137 A380 and 135 A320 "unresolved" tokens, of which **zero** were real. Four distinct
false-positive sources, each of which has to be handled explicitly:

1. **A KEY is not a NAME.** `A32NX_FCU_LEFT_EIS_BARO_IS_STD` is a key whose `Name` is
   `A32NX_FCU_EFIS_L_DISPLAY_BARO_IS_STD`; the key exists nowhere in the FBW tree and never
   should. Grepping source text checks the wrong string. **Enumerate `GetVariables()` out of the
   built assembly and check `Name`** — that is exactly what MSFSBA asks the simulator for, and it
   drops comments and concatenation fragments in the same step.
2. **Both sides build names dynamically.** MSFSBA composes `"A32NX_FCU_EFIS_" + side + "_WPT…"`;
   FBW composes `"A32NX_PRIM_" + idString + "_FG_DISCRETE_WORD_1"` in C++ and whole indexed
   families (`BRAKE_TEMPERATURE_{1..16}`, `COND_MAIN_DECK_{n}_TEMP`, `PRESS_CABIN_ALTITUDE_B{n}`,
   `OVHD_FIRE_AGENT_{n}_ENG_{n}_IS_PRESSED`) in Rust. None appear literally anywhere.
3. **Events are registered in TWO places.** Checking only `SimConnectInterface.cpp` reports five
   live A32NX autobrake events as missing; they are registered in the Rust systems WASM
   (`a320_systems_wasm/src/autobrakes.rs`). Check both, or the pass invents casualties.
4. **`SimVar.GetRegisteredId` is not an existence oracle.** It is per-Coherent-view and returns a
   fresh id for a name nothing has touched — including one the WASM writes every frame — and it
   is polluted by your own earlier probes. A bogus name and a live one are indistinguishable.

**Scope the diff to a commit instead of the whole tree.** "Tokens this commit removed and never
restored, intersected with the registered names" is precise: dynamic names never appear as
removals, and a token that merely moved shows up on both sides. That pass reported 64 A380 and 3
A320 tokens removed by #10855, **none** of them registered by MSFSBA.

**Three passes a name diff cannot do, and must be run beside it:**

- **Constant writers** — the category that produced the ALT_MANAGED bug. Map every
  `idFoo = make_unique<LocalVariable>("NAME")` to its name, then flag every `idFoo->set(EXPR)`
  where EXPR is a literal or a local only ever assigned one. Across ~440 A380 and ~395 A320
  handles this found exactly three: `A32NX_FCU_ALT_MANAGED` and `A32NX_FCU_HDG_MANAGED_DOT`
  (A380, both `= false`; only the first is read by MSFSBA — heading uses `…_DASHES`), and one
  dead CONTRIBUTOR, the A32NX's `bool tcasArmed = false;` feeding `A32NX_FMA_VERTICAL_ARMED`.
  Extend the scan to contributors, not just whole-constant writes, or the third is missed.
- **Changed writers** — a name that survives with a new writer can change UNITS or ENCODING
  silently (this is how V/S came to announce 500 fpm as "98400"). Intersect the commit's changed
  `->set()` lines with the registered names. #10855 touched 50 that MSFSBA registers, but only
  **five** on both sides of the diff — the whole autothrust family
  (`STATUS`, `MODE`, `MODE_MESSAGE`, `THRUST_LIMIT`, `THRUST_LIMIT_TYPE`). All five were verified
  against FBW's `AutoThrustMode`/`AutoThrustModeMessage` enums and live at FL360: status 2
  (Active), mode 8 (Mach), message 0 (None), limit 93.5 %N1, limit type 1 (CLB). Correct.
- **Live read** — with the aircraft loaded, batch-read the candidate names through the Coherent
  debugger. A non-zero reading proves existence outright and cleared 39 of 107 A380 candidates in
  one round-trip. Zero proves nothing on its own (most are legitimately zero in the cruise), so
  use it to CLEAR candidates, never to condemn them.

**⚠️ The A32NX was untouched by #10855** — zero writer lines in `fbw-a32nx`. Its shim has the same
SHAPE (the `verticalArmed` expression is byte-identical) because both airframes were migrated to
the same pattern at different times, which is exactly what makes "it's shared" a tempting and
wrong conclusion. See [a32nx.md](a32nx.md).

**⚠️ Always confirm which FBW build is actually flying.** All of the above compares MSFSBA against
a local clone; the pilot runs whatever the FBW Installer put on disk. `build_info.json` is not
reachable from the Coherent debugger (sync XHR is blocked, and Chromium 49 has no async/await),
so the practical check is behavioural: read a var #10855 introduced and one it stranded, and see
that they behave as the clone predicts.
