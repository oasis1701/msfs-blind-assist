### FlyByWire A380X Specific Patterns

`FlyByWireA380Definition` (code `FBW_A380`), branch `fly-by-wire-A380-integration`.

**MSFS-2024-native modular rebuild (FBW #10758, 2026-06) — MSFSBA-impact audit.** The A380X was repackaged as a native MSFS 2024 modular aircraft (new SimObject layout, lighting/perf work, a cabinless "No Cabin" variant). **It is NOT a systems/variable overhaul — verified MSFSBA-safe:** (1) **detection unchanged** — both variants keep `icao_type_designator A388` / `atc_model A380` (the def is menu-selected, not title-detected, so the new marketing Title "FlyByWire A380X (A380-842)" is irrelevant; GSX/docking `A388` resolution intact); (2) **the whole Coherent stack still resolves** — every view title-needle exists unchanged (`A380X_MFD`/`EWD`/`SDv2`/`ND`/`PFD`/`FCU`/`RMP`/`SYSTEMSHOST`, `- EFB`); (3) **no renamed/removed L:vars** — the systems-variable docs (`a380-simvars.md`/`a380x-input-events.md`/`a380x-private-local-vars.md`) were last touched 2026-05-19 by the fuel-system #10641, NOT the rebuild. **New FWS abnormal non-sensed checklists (#10253: RELIGHT IN FLIGHT, TAILPIPE FIRE, VOLCANIC ASH ENCOUNTER, BOMB ON BOARD, SEVERE TURBULENCE)** render through the same FwsCore/`.EclLine` path, so the existing EWD/ECL scrape reads them automatically (no code). **Behaviour XML PATH MOVED:** `FlyByWire_A380_842\model\behaviour\` → `FlyByWire_A380X\attachments\flybywire\Part_Interior_Cockpit\model\behaviour\` (tool-doc references updated). **The only genuinely-new pilot vars** were 12 cockpit-furniture bool toggles in the new `interactive-parts.xml` that MSFSBA lacked — added to the Cockpit panel as `Sel` combos (meal tables, keyboard trays, CAS L/R + OIT + physical cockpit-door-open panels, and the 4 armrest STOW toggles); same `(L:VAR) ! (>L:VAR)` family as the existing table/footrest toggles, routed through the prefix-less calc-path allowlist in `HandleUIVariableSet`. Branch `feat/a380-native-2024-cockpit` (off main). **Stow polarity (0/1) on the armrest STOW combos is not visually confirmed — flip the value dict if a control reads inverted in-sim.**

**No-injection MCDU/flyPad transport.** The A380X MFD/MCDU and flyPad EFB are read AND driven live through the MSFS Coherent GT remote debugger (`http://127.0.0.1:19999`, WebKit inspector, `Runtime.evaluate`) — NOT via a Community-folder mod or HTTP bridge. `SimConnect/CoherentDebuggerClient.cs` (MFD, resolves the view by title needle `A380X_MFD`) and `SimConnect/CoherentEFBClient.cs` (flyPad, title needle `- EFB`) both implement `IMcduBridge`, so `FBWA380MCDUForm`/`FBWA380EFBForm` are transport-agnostic. The in-page agents are `Resources/coherent-a380-agent.js` and `coherent-flypad-agent.js` — **ES5 only** (Coherent GT = Chromium 49: `var`, no arrow funcs, no `String.includes`, top-level try/catch). MFD page-ids shift each session → always resolve by TITLE. **No Community-folder injection, no HTML patching, no sim restart** — the debugger is the sole A380 transport (all injection code was removed; PMDG uses its own Coherent debugger client — the HTTP `EFBBridgeServer` was deleted 2026-07). **Developer Mode is NOT required** — verified empirically on MSFS 2024 (cold boot, Dev Mode off): port 19999 is opened by the sim itself and `/pagelist.json` + the WebSocket `Runtime.evaluate` inspector protocol both work, so the debugger transport runs with no Dev Mode and no dev toolbar.

**flyPad = WebView2 "browser mode".** `FBWA380EFBForm` renders the scraped flyPad elements as a real semantic HTML document inside an embedded **WebView2** (already a dep; PMDG EFB precedent), so the screen reader gets native browse mode (H headings, K links, arrow-by-line, real `<input>`s, `aria-live` page-change). NO http server — `NavigateToString(PageHtml)` once, then `ExecuteScriptAsync("window.__render(<json>)")` per update; the page posts click/set/refresh back via `chrome.webview.postMessage` → `WebMessageReceived` → `EnqueueCommand`. The native flat-list is a SILENT auto-fallback only if WebView2 init fails (no user toggle). **Click index gotcha:** the agent's `clickElement`/`setValue` look up the STAMPED `data-fbwa380-efb-idx`, which diverges from the list position (the list is sorted+deduped after stamping) — so `CoherentEFBClient` carries it as `items.N.aidx` and the form sends THAT, not the loop index. **flyPad div-buttons:** many action buttons (e.g. modal Cancel/Confirm) are styled `<div>`s with no `button`/`btn` token or role — the agent classifies a `hover:`-styled leaf with its own short text as a button (interactive flyPad elements carry Tailwind `hover:` classes; static text never does). Value inputs (PAX/KGS) have no label metadata → `labelFor` reads the field's parent unit text before falling back to the section heading.

**ND OANS / BTV (Ctrl+Shift+B) — DATA-ONLY, ZERO-RENDER (2026-06, latest; supersedes all earlier scrape/TabControl OANS notes).** `Forms/FBWA380/FBWA380OansForm.cs` is a native WinForms `TabControl` (**Map and BTV / Airport / Status**) driven by `SimConnect/CoherentNDClient.cs` + `Resources/coherent-oans-agent.js` — but the agent is now **data-only**: it READS OANS/BTV state from the ND JS instance objects (`document.querySelector('a380x-nd').fsInstrument.oansRef.instance` → `btvUtils` / `labelManager.labels` / `fmsDataStore` / `dataAirportIcao` / `dataAirportName`) plus OANS L:vars, and WRITES via `btvUtils` methods + the msfs-sdk EventBus (`bus.pub`). **It NEVER writes `A32NX_EFIS_L_ND_RANGE`, forces panel `.style.visibility`, or scrapes the control-panel DOM.** ⚠️ The earlier `ensureAirportZoom`+DOM-scrape design forced a continuous full-airport map render on every poll and exhausted host commit memory (paging-file-too-small errors that froze the whole machine) — **do NOT reintroduce any forced render/zoom/visibility or DOM `scrape`/`enumerate`.** Agent API: `ping()`, `snapshot()` → `{ok,available,failed,airport,fms,btv,manual,airac}`, `armRunway(name)`, `armExit(name)`, `clearBtv()`, `displayAirport(icao)` (one-shot AMDB load — USER ACTION ONLY, never on a poll), `setManualStopDistance(m)`. The client polls `snapshot()` read-only (1 s), raises a dedup'd **`oans_state`** push (+ **`oans_connected`**), and exposes commands `get_snapshot` / `oans_arm_runway` / `oans_arm_exit` / `oans_clear` / `oans_display_airport` / `oans_set_manual_stop`. **Two tiers:** with Navigraph maps loaded (`A32NX_OANS_AVAILABLE=1`) the runway/exit pick-lists + arming + predicted dry/wet/live stop, ROT, turnaround and the runway-ahead QFU all work; without Navigraph the form shows a **Manual BTV** section — runway length (ARINC `A32NX_OANS_RWY_LENGTH`), type a stop distance → `oansManualStoppingDistance` bus pub, then "select the landing runway in the FMS". The top banner states which tier is active. **Visual-only OANS controls are intentionally REMOVED** (the RWY/TWY/STAND/OTHER entity picker, ADD CROSS/FLAG, CENTER MAP, the permanently-disabled LDG SHIFT) — they have no audio meaning for a blind pilot (STAND = parking stands, OTHER = de-icing areas — both map-locate-only). The runway-ahead advisory naming (`btvUtils.rwyAheadQfu`) shows in the window readout; an **always-on** named advisory (window closed) is deferred (it would need a persistent ND read socket — the generic SimVar `A32NX_OANS_WORD_1` bit-11 advisory in the def stays the always-on path). **Navigraph is user-side:** the AMDB airport maps are fetched from the online `https://amdb.api.navigraph.com` API using the user's Navigraph login in the flyPad EFB (Shift+T) — there is NO local file to fetch and MSFSBA must never try to; the aircraft loads the maps and MSFSBA reads what's loaded. **Exit pick-list is FILTERED to valid exits for the armed runway** — `snapshot().btv.exits` returns `agent.validExitsForArmed()`, a READ-ONLY (pure airport-local-metre math, NO canvas draw, NO mutation) verbatim port of FBW `OansBrakeToVacateSelection.selectExitFromOans`'s accept/reject test (400 m touchdown-zone, 50 m centerline, 120° gates; falls back to the full list only if the armed-runway threshold refs aren't set). Without it the combo listed all airport exits alphabetically and the first (e.g. OMDB K-series for rwy 12L) were silently rejected. **Multiple exit-line features can share ONE name (live-verified KSFO 28R / exit "Q", 2026-06): a taxiway often exposes a far-off-runway segment AND a valid on-runway one under the same text.** `validExitsForArmed` whitelists a NAME when ANY of its features passes (and sets the `seen` dedup only on ACCEPT, so an invalid first feature can't block a valid later one), so the list correctly shows "Q". But `armExit` used to pick the FIRST feature by name (`findLabel`) — at KSFO that was the off-runway "Q" (230 m off the 28R centerline) → `selectExitFromOans` rejected it → "Exit Q not valid … (wrong side or too close to threshold)" even though Q *was* valid. **FIX:** `armExit(name)` now iterates EVERY same-named exit-line feature and arms the first one `selectExitFromOans` accepts (mirroring a sighted pilot clicking the correct map label). **The per-feature `selectExitFromOans` call is wrapped in its OWN `try/continue` (not one try/catch around the whole loop)** — a throw on an early/malformed same-named feature must fall through to the next candidate, not abort the loop and reject a valid later feature; the last error is reported only if NO feature armed. Likewise `armRunway`'s threshold-search loop guards `feats[k] && feats[k].properties` (it runs outside the method's try, so an unguarded `.properties` deref on a partial AMDB feature would throw uncaught out of `armRunway`). This is SAFE re the memory rule below: it loops only over the 1–2 features sharing the SELECTED name (not all ~290 exits), and a REJECTED feature returns from `selectExitFromOans` BEFORE `drawBtvLayer` — so at most ONE canvas redraw (the accepted feature) occurs, same as before. **Exit list is sorted closest-first with distance:** `validExitsForArmed` returns `[{name, dist}]` sorted ascending by `dist` = the BTV exit distance in metres (raw threshold→exit minus the 400 m touchdown zone == `btvExitDistance`, so the pick-list and the armed-exit readout report the SAME number); the snapshot carries a parallel `btv.exitDists` array, and the form's exit combo items read "Q, 2,289 m / 7,510 ft" (unit per the metric toggle) so the screen reader announces how far down the runway each exit is while arrowing the dropdown. **Rejection feedback:** `EnqueueCommand` captures the arm result and raises `oans_action`; the form announces non-success results (e.g. "Exit K1 not valid for this runway …") so a rejected exit is never silent. ⚠️ NEVER loop `armExit`/`armRunway` over the FULL exit list (~290 calls) — each ACCEPTED arm triggers a BTV canvas redraw and a tight full-sweep exhausts host memory; the validity FILTER above is the read-only way to enumerate valid exits (arming only the 1–2 same-named features, as the fix does, is fine). **Loading an airport: call `oansRef.instance.loadAirportMap(icao)` DIRECTLY, NOT the `oans_display_airport` bus event.** When the OANS is in performance-hide mode (FBW perf mode on + the ND not rendering the OANS — the normal case for us since we never render), the `oans_display_airport` handler (Oanc.tsx) only sets `dataAirportIcao` and SKIPS the load, leaving the ICAO showing with `data===undefined` / 0 labels / `btvReady` false (symptom: "(KLAX)" with no runway list). `agent.displayAirport()` therefore calls `loadAirportMap(icao)` directly (bus pub is the fallback), which loads the AMDB + builds labels regardless of perf-hide (live-verified KLAX → 4789 features / 828 labels, persists; `getAirportData` itself was never the problem). Same gate disables the cockpit auto-load under perf-hide, so the user must press "Display airport" (or Origin/Dest/Alternate) to load — the banner says "maps available — load an airport" until they do.

**Accessible BTV exit arming — native combos + buttons + auto-announce (2026-06, live-verified at VCBI).** On the real A380 you SELECT the BTV landing runway + exit by **clicking the runway-end + exit LABELS on the moving map** (`Oanc.tsx` → `btvUtils.selectRunwayFromOans` / `selectExitFromOans`). Those are SVG on the map canvas with no control-panel widget, so a blind pilot cannot reach them — and selecting RWY/TWY in the control panel only filters the *map*, it does not arm BTV (the user's "if i select rway nothing is shown" / "can't select taxiways after the landing runway is selected" — that dropdown is a map-filter, not an arming control). **`coherent-oans-agent.js` calls the same `btvUtils` methods directly** via the ND instrument instance (`document.querySelector('a380x-nd').fsInstrument.oansRef.instance` → `btvUtils`):
- `oanc()` / `btvReady()`; `btvRunwayList()` / `btvExitList()` (from `labelManager.labels` filtered by `associatedFeature.feattype`: RunwayThreshold=2, runway-centerline=4, RunwayExitLine=19);
- `armRunway(name)` (finds the centerline label + the `data.features` threshold with `idthr===name`, calls `selectRunwayFromOans(icao+name, centerline.associatedFeature, threshold)`); `armExit(name)` (requires a runway armed first; `selectExitFromOans(name, exitLabel.associatedFeature)` — returns "wrong side / too close to threshold" if FBW rejects it); `clearBtv()`;
- `snapshot().btv → `{ready, runways:[], exits:[], runway, exit, lda, exitDist, dry, wet, stop, computing}` — the pick-lists, the armed runway/exit (these are **NOT L:vars**, only OANS observables `btvRunway`/`btvExit`/`btvRunwayLda`/`btvExitDistance`), and the predicted **DRY / WET / live STOP-bar** distances read from the plain-metre L:vars `A32NX_OANS_BTV_{DRY,WET,STOP_BAR}_DISTANCE_ESTIMATED` (0 until the FMS computes the landing on approach; stop-bar only surfaced once dry/wet compute, since it carries a ~40 m ground offset).
`snapshot()` returns the BTV block (data-only — see the zero-render note above). `CoherentNDClient` parses it (`Snapshot.btv`), folds it into the dedup hash, pushes `btv.*` keys, and exposes commands **`oans_arm_runway`** / **`oans_arm_exit`** (value=name) / **`oans_clear`** (plus `oans_display_airport` / `oans_set_manual_stop`). `FBWA380OansForm` builds a **BTV runway combo + "Arm runway"**, an **exit combo + "Arm exit"** (enabled once a runway is armed), and **"Clear BTV"** from the snapshot; the readout shows the armed runway (+ LDA), exit (+ distance), and dry/wet/stop predictions; and it **auto-announces on change** ("BTV armed, runway 22, exit E, 2835 metres" / "BTV cleared"). **Live-verified end-to-end at VCBI** (driving the agent directly): `snapshot().btv returns runways `["04","22"]`, after `armRunway("22")`+`armExit("E")` → `runway:"VCBI22", exit:"E", lda:3351, exitDist:2835`, exits `["A".."E"]`; `clearBtv()` resets to `runway:null`. (Source: `fbw-common/.../OANC/OansBrakeToVacateSelection.ts` + `Oanc.tsx`; selected idents live only on the event bus / observables, so the snapshot reads them from the ND JS instance, not SimVars.)

**OANS refinements (2026-06): units, ROT/turnaround, tab header, tab-aware search.**
- **Distance UNITS follow the metric toggle.** The OANS/BTV distances (LDA, exit distance, dry/wet/live-stop-bar) are stored in METRES but the real ND shows them in **M or FT per the metric setting** (FBW: `CONFIG_USING_METRIC_UNIT` → `UnitType.METER/FOOT`, factor 3.280839895). `snapshot().btv` reads **`A32NX_EFB_USING_METRIC_UNIT`** (the var MSFSBA already follows for weights, which tracks the EFB "US Units" toggle) as `metric`; the form's `Dist()` shows metres or feet accordingly. So OANS distances honour the same unit toggle as the rest of MSFSBA — verified `metric:true` live.
- **BTV ROT + TURNAROUND times (ARINC429-decoded).** `A32NX_BTV_ROT` (runway occupancy time, **seconds**) and `A32NX_BTV_TURNAROUND_{MAX,IDLE}_REVERSE` (brake-cooling time to next departure, **minutes**, idle = hotter brakes = longer) are **ARINC429** words. `coherent-oans-agent.js` `A._arinc(raw)` decodes them (low 32 bits = IEEE-754 float32 via `DataView`, SSM = bits 32-33; valid when SSM 3/2). Surfaced in the readout, **gated on an EXIT being armed** (matching the real OANS, which only shows them then). Live-verified the decode: `rot:30, turnMax:171, turnIdle:197` with an exit armed. Phrasing: "Runway occupancy time 30 seconds" / "Turnaround: 171 minutes max reverse, 197 minutes idle reverse".
- **Current-tab header + tab-aware search.** The readout drops the three tab lines (kept in the controls list to switch) and shows one **"Current tab: MAP DATA"** header derived from the `(active tab)` marker (live-verified clicking a tab moves the active marker). The **search box is tab-dependent** — the "Runway or exit" InputField on MAP DATA is the *airport-code* field on ARPT SEL (with ICAO/IATA/CITY radios) — so the form labels the search box from the live input's own label (`_searchField`, the text before the colon) and disables it when no input is present. `setValue` on the field is live-verified ("ok"); the taxiway search drives the FBW InputField (its accessible payoff is map-centering, so the future airport-diagram reader is the real "tell me about taxiway B" win).

**MFD navigation is via the always-present HEADER, NOT an "INIT hub" — KEEP the page picker (#105).** Investigated the theory that "every MFD page is reachable from INIT" (true-ish on the A320/A330 MCDU via the physical page keys): it is **FALSE for the A380**. Source (`FmsHeader.tsx`) shows every FMS page carries a persistent header of 4 dropdown tabs — **ACTIVE** (F-PLN/PERF/FUEL&LOAD/WIND/INIT), **POSITION** (MONITOR/REPORT/NAVAIDS/IRS/GNSS/TIME), **SEC INDEX** (SEC 1/2/3), **DATA** (STATUS/WAYPOINT/NAVAID/ROUTE/AIRPORT/PRINTER) — plus the top system tabs (FMS/ATCCOM/SURV/FCU BKUP). INIT is just one item under ACTIVE; it has no links to other pages. **Sighted pilots navigate via this header, not through INIT.** Crucially, the MFD scrape does NOT capture the header tabs (verified live: 0 header-tab elements scraped though 40 `_MFD_pageSelector` DOM nodes exist — they're the navigateById click targets, outside the scraped content area), so the **"Go to MFD page" combo is currently the ONLY way a blind pilot can reach most pages** (besides the quick buttons + Ctrl+arrows). It is the accessible equivalent of the always-visible header — strictly better than expanding 4 dropdowns one item at a time. **Do NOT remove the page picker** — it would strand the user. (Confirmed: keep it.)

**ATC COM / CPDLC + D-ATIS — navigate by UIService URI, NOT page-selector id.** The page-selector ids (`{CAPT|FO}_MFD_pageSelector{Tab}_{idx}`) only exist while that *system's* header is mounted, so the FMS-header `navigateById` click can't reach ATCCOM from an FMS page. The six ATCCOM pages are in `AllPages` with a non-empty `Uri` field (page-selector dispatch picks `navigate_uri` when `Uri` is set, else `navigate_by_id`); the **ATC COM button** (Alt+A) now fires `SendNavigateUri("atccom/connect")` instead of the old KCCU-only `navigate_by_id("",-1,"ATCCOM")`. **Fuel pumps + niche controls + pitch-trim correctness (post-#107 user follow-up).** (1) **Feed-tank FUEL PUMPS** — were entirely missing. (2) **Pitch-trim correctness** — MSFSBA's "Pitch Trim" read the stock `ELEVATOR TRIM INDICATOR` (normalized −1..1), which is the WRONG representation for the A380. Fixed to read **`ELEVATOR TRIM POSITION` (radians)** and decode in `TryGetDisplayOverride` to "X.X degrees up/down" (positive = UP) — matching the A380 SD `PitchTrim.tsx` (`thsPositionRadians * RAD_TO_DEG`, `Math.sign === 1 ? 'UP' : 'DN'`). The predicted-takeoff-trim readout (`A32NX_TO_PITCH_TRIM`, ARINC429 BNR ±180 = degrees) is correct as-is. The trim WHEEL set isn't a combo (a blind pilot reads the target + actual and adjusts with the global elevator-trim keys/axis — the readouts are the accessibility win). ### The flight directors are ONE FCU pushbutton (FBW #10855, found 2026-09-25)

**Symptom.** On the latest development build (a380x `2baa2b35e`, installed 2026-09-24) MSFSBA could no
longer turn the flight directors on. The live `debug.log` of the First Officer's cockpit-preparation
flow shows exactly what it did: `Sending event: TOGGLE_FLIGHT_DIRECTOR with data: 1` at 14:12:11.579 and
`… with data: 2` at 14:12:11.788 — and the flight directors stayed off.

**Cause.** #10855 ("add FG part to PRIM", `1bbd304`, 2026-08-18) replaced the A380's flight-director
wiring, and kept both old names alive while doing it:

| | before #10855 | since #10855 |
|---|---|---|
| cockpit FD pb (`PUSH_FCU_FD`, `fcu.xml`) | `1 (>K:TOGGLE_FLIGHT_DIRECTOR)` then `2 (>K:TOGGLE_FLIGHT_DIRECTOR)` | `'A32NX.FCU_FD_PUSH' (>F:KeyEvent)` |
| its light / state | stock `A:AUTOPILOT FLIGHT DIRECTOR ACTIVE:1` | `L:A32NX_FCU_FD_LIGHT_ON` |
| `TOGGLE_FLIGHT_DIRECTOR` | passed to the sim, which toggled the indexed stock FD | **masked** (`addInputDataDefinition(…, true)`, `SimConnectInterface.cpp`) and turned into `fcuAfsPanelInputs.fd_button_pressed = true` — one press of the single FD button, **the side parameter ignored** |
| who writes the stock FD var | the TS FCU's power-up toggle and the WASM's FD connect/disconnect latches | **nobody** — all three were deleted with the legacy autopilot |

The light is `fcu1Afs.fd_light_on || fcu2Afs.fd_light_on` (`FlyByWireInterface.cpp`), each of which is the
master PRIM's "FD 1 engaged OR FD 2 engaged" (`A380FcuComputer.cpp`, FG discrete word 1 bits 13/14). So
MSFSBA's per-side combos judged a stock value frozen at whatever the flight loaded with, and — when that
frozen value said "off" — sent one "per-side" toggle each: **two presses of one button, which cancel.**
When it happened to say "on", they sent nothing at all. Either way, "Flight directors: ON" did nothing.

**Why no check caught it.** Both names still exist: `TOGGLE_FLIGHT_DIRECTOR` is still registered (so
`FlyByWireA380EventContractTests` had it inventoried as a live actuator), and a stock SimVar never
disappears. The post-#10855 sweep diffed `A32NX_`/`A380X_` TOKENS, so a STOCK name — `AUTOPILOT FLIGHT
DIRECTOR ACTIVE:n`, `TOGGLE_FLIGHT_DIRECTOR` — was structurally invisible to it. See the "Stock names"
pass in [the FBW-drift sweep](#the-fbw-drift-sweep--how-to-run-it-and-the-four-ways-the-obvious-method-lies-2026-08-23).

**The shipped shape** (`Aircraft/A380FlightDirector.cs`, pinned by `A380FlightDirectorTests`):
- ONE "Flight Directors" combo on the **FCU** panel (beside AP 1 / AP 2 / A/THR, where the button is),
  reading `A32NX_FCU_FD_LIGHT_ON` and pressing `A32NX.FCU_FD_PUSH` only when the pick differs. The EFIS
  panels no longer carry an FD row: two "Flight Director 1 / 2" controls for one button would each
  switch both.
- The decision reads the definition's commanded-or-cached state (`FlightDirectorCommand`), not the bare
  cache, and records what it commands. The batch refreshes once a second, so without that a second set
  inside the same second — two quick combo picks, or a caller setting "both sides" — would press again
  and undo the first.
- `FD_1_CTL` / `FD_2_CTL` survive as ALIASES: same light, OnRequest (so the batch still carries the name
  once — `VarNameCollisionTests`), in no panel, routed through the same commanded state. The First
  Officer's cockpit-prep step sets both, 200 ms apart; that is now one press.
- Per-side ENGAGEMENT is a readout, not a control: `FD_1` / `FD_2` on the PFD status box decode
  `A32NX_PRIM_1_FG_DISCRETE_WORD_1` bits 13/14 (engaged) and 17/18 (inop) — the PFD FMA's own "1FD2"
  cell (`FMA.tsx`, `E2Cell`) — "on", "inoperative", "off", or "not available" when the word carries no
  data.
- The Ctrl+P Autopilot window's FD line, a read-only Label (so out of the tab order) that read the
  frozen stock var, is now an **FD** toggle button in the slot EXPED left, labelled from the light. It
  presses through the definition (`ToggleFlightDirectors`), which records the state it commands like
  the combo does — a combo pick a second after a window press is then no second press.
- A Ctrl+M mute on the old `FD_1_CTL` / `FD_2_CTL` rows moves to the new row at settings load
  (`SettingsManager.CarryRenamedMonitorMutes`, which also moves the altitude increment's): the old key
  leaves the list, or it would re-mute the new row on every launch after the pilot un-ticked it.
- The stock combined `FD_ACTIVE` readout is gone: nothing writes it.

**Not live-verified yet** — source-verified against `2baa2b35e`, and the old failure is proven from the
live log. The in-sim check: cold and dark, power up, then Flight Directors On from the FCU panel (the
PFD status box then reads Flight director 1 and 2 "on"), Off, and On again; then the First Officer's
cockpit-prep flow from FDs off.

### Discrete ARINC words were read from the wrong bits (MSFSBA's own bug, found 2026-09-25)

**Every FBW discrete word stores its bitfield as a float's VALUE.** The C++ `Arinc429DiscreteWord::
setBit` writes `static_cast<float>(bitfield)`, Rust converts `value as f32`, and the TS
`Arinc429Register` assigns the number to a `Float32Array`; the L:var then carries that float's IEEE
bits. All three READERS convert back numerically — `static_cast<uint32_t>(word.Data)`,
`f32::from_bits(v) as u32`, `this.value >> (bit - 1)` — and test the integer. `Arinc429Word.BitValueOr`
instead tested the RAW low 32 bits, i.e. the float's exponent and mantissa. It is now fixed
(`Arinc429Word.DiscreteBits`, the value converted back) and pinned by `Arinc429WordTests`; the old
reading fails 40 of the tests written against it.

What the raw reading did, bit by bit: bit 28 is exponent bit 4, so it read TRUE for any word with a
set bit at 18 or above; bit 29 (exponent bit 5) could never read true; bits 11-23 are mantissa bits,
which hold the set bits BELOW the highest one, shifted to the top of the mantissa — so raw bit n read
true only when some set bit sat exactly (24 − n) positions below the highest, e.g. bit 22 two below
it, bit 11 thirteen below. That is bit n itself only when the highest set bit happens to be bit 24.
So:

- **FMA Reversion** (FG word 5 bit 28) fired on selected/managed speed changes — bit 18 is
  `manual_spd_control_active`, bit 17 its managed twin — and **Speed Protection** (bit 29) never
  fired at all.
- **The armed-ALT qualifiers** (FG word 3 bits 28/29) called any armed ALT with a bit ≥ 18 set a
  "constraint" and never a "cruise altitude"; the Cruise Altitude Mode row could only say "off".
- **ROW/ROP and RWY AHEAD** (bits 11-15, and bit 11) could never fire — nor the OANS window's
  "runway ahead" line: `coherent-oans-agent.js` had the same raw-bit test in JavaScript
  (`A.rwyAheadActive`), now decoded through its own `A.arinc` first and then tested with FBW's own
  `(value >> 10) & 1` (no `Math.trunc`: the agent is ES5). Pinned by `tools/oans-agent-test`, which
  loads the shipped agent into a bare Node `vm` context (no DOM, no dependencies) and runs in CI's
  EFB-reader job. Against the old agent it fails exactly the four tests where the advisory should show.
- The A32NX's LAND 2/3 capability, CPC selection and cabin-fan and hot-air rows, and the A380's
  pack, fan, valve and fuel-pump rows, read noise. (The A32NX's FWC word 124 call-out was SILENT
  rather than noisy, for a different reason: PseudoFWC never sets that word's SSM, so every
  SSM-gated read of it returns its fallback. It is read ungated now, as the PFD reads it —
  `Arinc429Word.BitValue`, see a32nx.md.)

**Two "live puzzles" recorded in this file were this bug.** FG word 5 on a cold parked aircraft,
raw `0x48000000`, is the float 131072 = bit 18 (`manual_spd_control_active`) — not "bits 28 and 31,
reversion asserted at rest". FG word 3 at FL360 after a step climb, raw `0x4D804000`, is
2^28 + 2^19 = bits 29 (cruise, the PFD's `altIsCrzAlt`) and 20 (`alt_hold_active`) — level cruise,
not "the constraint qualifier set with nothing armed". Both readings are corrected where they stood.

### Take-off roll callouts: V1, Rotate, V2 (added 2026-09-25)

The A380 calls "V1", "Rotate" and "V2" on the take-off roll, as the MD-11 and the iFly do, through
the same `TakeoffVSpeedCallouts` machine; `A380TakeoffCallouts` wires it:

- **Speeds** are the FMS's `L:AIRLINER_V1_SPEED`/`_VR_`/`_V2_` (knots), the vars MSFSBA already
  announces as the pilot types them on the PERF page ("V1: 142 knots", keys `PFD_V1`/`PFD_VR`/
  `PFD_V2`). They are peeked, never consumed, so that announcement is unchanged. Cleared speeds
  (-1 for V1/VR, 0 for V2: a departure-runway change sends them back for confirmation) arm nothing.
- **Airspeed** is `AIRSPEED INDICATED` on its own per-frame subscription (`A380_TAKEOFF_CALLOUT_IAS`:
  `HighFrequency`, `ExcludeFromBatch`, hidden from Ctrl+M). On the 1 Hz batch, Rotate could come up
  to ~5 kt late.
- **The rule is the shared machine's**: armed on the ground below 40 kt with V1 and VR set, fired on
  upward crossings, one utterance per sample ("V1, Rotate" when V1 = VR), interrupting. An action
  cue whose value is its timing must not queue behind a speed call already being spoken.
- **Mutes**: each call rides its speed's Ctrl+M row (V1 → "V1", Rotate → "VR", V2 → "V2").
- **Resets**: the ARM is dropped, the speeds kept, on every context reset (`OnSimContextReset`, e.g. a
  flight load) AND on a reconnect (`ResetAnnouncementBaselines`). A flight load delivers the per-frame
  airspeed ahead of the 1 Hz ground flag, so an arm kept from a parked aircraft would call all three
  at the loaded cruise; the iFly carried only the reconnect half until 2026-09-11.

The aircraft's own warning system also calls "V1" aloud; MSFSBA's call arrives alongside it. Pinned
by `A380TakeoffCalloutsTests`; not yet flown.

### Ctrl+M mutes: the A380 joined MainForm's central wrap (2026-09-25)

Every other self-announcing airframe is muted by MainForm wrapping `ProcessSimVarUpdate` in
`announcer.Suppressed` (`DefAnnounceMuteSets`). The A380 was left out and relied on each branch
checking `A380DisabledMonitorVariablesSet` itself — and several never did, so their rows muted
nothing: the baro setting, STD and unit (six rows), Spoilers, Thrust Lever 1-4 Angle, Autoland
capability, Baro Minimum, Radio Minimum (DH) and Weight Units. It is wrapped now; the branches that
check locally are unaffected.

The wrap assumes a branch's call-outs are its OWN row's. A branch that also speaks a call-out
ANOTHER row owns is kept out of it (`IsMuteWrapExempt`), or muting its row would silence the other
row as well:

- the FMA vertical mode, lateral mode and armed vertical modes speak the derived altitude mode,
  whose row is "Altitude Mode". Wrapped, muting "Vertical Mode" or "Armed Vertical Modes" silenced
  "Altitude Mode: Managed" too (caught in review, before it shipped);
- the take-off airspeed feed speaks V1, Rotate and V2 (the V-speeds' rows);
- the VOR/DME and NDB lights speak the ND filter (the WPT light's row);
- the E/WD lines speak ECAM messages (the "ECAM memos" row).

What an exempt branch says for ITSELF must go through the generic monitor, which checks its row
after the return, or check that row inline. A new branch that speaks another row's call-out joins
the list (`A380MuteWrapTests` pins it; `A380BaroMuteTests` pins the baro rows).

**Residual:** "All thrust levers Climb" is spoken from whichever lever's delivery completes the
set, so muting ONE lever's row silences it only when that lever arrives last. Mute all four to
silence the thrust-lever call-outs.

### Wing anti-ice is the STOCK switch (2026-09-03 re-correction)

**⚠️ A 2026-07 "correction" broke this control by copying the A32NX's wiring.** Both packages ship a template called `FBW_Airbus_AntiIce_Wing`, and the bodies are DIFFERENT:

| | actuator | state |
|---|---|---|
| A32NX | writes `L:A32NX_BUTTON_OVHD_ANTI_ICE_WING_POSITION` | `A32NX_PNEU_WING_ANTI_ICE_SYSTEM_SELECTED` |
| **A380X** | **`(>K:TOGGLE_STRUCTURAL_DEICE)`** | **`A:STRUCTURAL DEICE SWITCH`** |

`A380_Cockpit_Behavior.xml` uses that template at node `PUSH_OVHD_ANTIICE_WING`, so the A380's overhead PB drives the stock switch and has never touched the L:var. The 2026-07 change moved MSFSBA's combo onto the L:var on the belief that it was "the var the real cockpit button writes" — true of the A32NX, false here. The pilot's report was the plain consequence: wing anti-ice selected in icing, nothing happened.

**Why it passed review is the lesson.** The L:var is a DEAD MIRROR — nothing on the A380 writes it, so a write STICKS and the read-back is perfect. The change was recorded as "live-verified settable + held", and it was; that check simply cannot distinguish a working control from a variable no system reads. This is exactly the inverse trap the troubleshooting playbook's Golden Rule 2 names: **read back the DOWNSTREAM effect, not the var you wrote.** Measured on a380x 2f139a41: writing the L:var to 1 read back 1 while `A:STRUCTURAL DEICE SWITCH` stayed 0, and `(>K:TOGGLE_STRUCTURAL_DEICE)` moved the real switch 0 → 1.

**The checked-in answer was right the whole time and nobody read it.** `tools/a380-simvars-catalog.md` — built from the cockpit behaviour XML — has always carried `| STRUCTURAL_DEICE_SWITCH | bool | 0/1 | R/W | Wing anti-ice (stock SimVar). |` and has NO row for the A32NX L:var. Neither the break nor the first fix consulted it. Check that catalog before re-deriving an A380 control's wiring from the other airframe.

**The shipped shape.** The combo is backed on the stock SimVar (the `ELEC_ENG_GEN` toggle precedent — *not* `ELEC_APU_GEN`, which is an absolute `..._SET` and reads no live state) so it shows the real switch, and the write goes through the shared `A380ToggleCommand.ShouldFire` decision: fire the stock toggle only when the pick differs from the live value, treating an unknown live value as "differs" so a cold cache still actuates, and force-read the key when nothing is sent so the combo cannot latch on a position the aircraft never took. The live value comes from `CommandedOrCachedValue`, never a bare `GetCachedVariableValue` — two combo commits inside one 1 Hz batch period would otherwise both read the pre-first-commit value and drop the second pick. Transport is `SendEvent` (`MapClientEventToSimEvent` + `TransmitClientEvent`) like every other stock toggle in that method — **not** the MobiFlight calculator path, which reaches nothing without the WASM module and is the only reason the coalescing/`…Unique` question ever arose. `FlyByWireWingAntiIceWiringTests` pins both airframes' registrations and the decision table so neither gets "harmonised" onto the other.

**Re-verified live on 2026-09-04** (a380x, on ground, four engines running), against the shipped transport rather than the calc path:

| test | result |
|---|---|
| `TOGGLE_STRUCTURAL_DEICE` via `MapClientEventToSimEvent` + `TransmitClientEvent` (what `SendEvent` does, no MobiFlight) | `A:STRUCTURAL DEICE SWITCH` **0 → 1** |
| Three consecutive identical presses on that transport | **0 → 1 → 0 → 1** — no coalescing, every press took |
| Write `L:A32NX_BUTTON_OVHD_ANTI_ICE_WING_POSITION` = 1 | reads back **1** and **holds**, while the real switch **stayed 0** |
| Same write, downstream | `A32NX_PNEU_WING_ANTI_ICE_SYSTEM_SELECTED` stayed **0** — it does not even reach the A32NX's own next var |
| Real switch ON | `_SYSTEM_SELECTED` **0**, `_SYSTEM_ON` **0** |

The third row is the whole lesson in one line: a perfect read-back beside a motionless switch. The second row is why the `…Unique` wrapper is unnecessary once the transport is right.

**⚠️ The pneumatic gap is REAL and SEPARATE — do not read this fix as making the system work.** With the real switch ON, `A32NX_PNEU_WING_ANTI_ICE_SYSTEM_ON` still reads 0 (re-measured the same session) and `a380_systems` has no wing-anti-ice pneumatic. The switch is now faithful to the cockpit; the read-only "Wing Anti-Ice Flowing" status honestly reports no flow. Those are two different facts and only the first was a bug.


### FG-into-PRIM variable migration (FBW #10855, synced 2026-08-19)

**⚠️ And intersect the EVENTS, not only the variables — that omission is how the first pass shipped 7 dead controls.** A variable that disappears at least reads a suspicious 0. **⚠️ Requires FlyByWire A380X `1bbd304` (18 Aug 2026) or later** — the Development build from the FlyByWire Installer. This sync is deliberately lean: there is no version-sniffing and no compatibility fallback, because the vars below do not exist at all in older builds and the FCU value units changed outright (next paragraph), so a stale aircraft would report wrong numbers rather than obviously missing ones.

**⚠️ The FCU value vars changed UNITS, not names — a silent break a name diff cannot catch.** #10855 also turned `A32NX_AUTOPILOT_{HEADING,VS,FPA}_SELECTED` into FCU *display* shims (`idFcuShimHdgValue2 <- selectedFcuAfs.hdg_trk_value`; `idFcuShimVsValue` / `idFcuShimFpaValue <- selectedFcuAfs.vs_fpa_value`). They now carry degrees / feet-per-minute / degrees directly, where older builds wrote radians and m/s. All three MSFSBA conversions were removed: V/S had begun announcing a 500 fpm selection as **"98400 feet per minute"** (500 × 196.85). When FBW moves a subsystem, re-check the units of the vars that *survived*, not only the ones that disappeared.

**Do not re-add "looks like radians" magnitude guesses.** The old heading and FPA paths converted only when `|value|` fell in a radian-looking range. Against display units that silently corrupts small values: a selected heading of 006° and an FPA of 0.2° both fall inside the guess window and would be inflated to 344° / 11.5°. Read the value as-is and require the current aircraft build instead.

**⚠️ Never register the same var KEY twice.** `Read()` does `vars[key] = …`, so a second registration silently replaces the first — `A32NX_AUTOPILOT_VS_SELECTED` was registered both as `"feet per minute"` and as `"number"`, and only the later `"number"` ever took effect. The dead entry was removed; the surviving pair is annotated. (Distinct keys sharing one `Name` are fine and common — see the batch-collision note below.)

**The `_LIGHT_ON` vars are the cockpit's own indicator source**, not a backlight: `efis-cp.xml` / `fcu.xml` set `INDICATOR_CODE = (L:A32NX_FCU_..._LIGHT_ON)`, and the WASM writes them per frame (`idFcuAfsPanelLocLightOn->set(fcu1Afs.loc_light_on || fcu2Afs.loc_light_on)`). They are therefore **read-only**; the set path stays the unchanged `A32NX.FCU_*_PUSH` toggle events through `_fcuToggleEvents`, which fires only when the picked state differs from the cached one. Proof they are per-button state rather than a shared backlight: with ARPT lit, CSTR read 0 at the same moment.

**⚠️ The ND Filter IS a single mutually-exclusive selector — the old combo's shape was right.** This was briefly "corrected" to three independent On/Off controls on the strength of a live observation that all three could be lit at once. That observation cannot be reproduced and the source rules it out: `A380FcuComputer.cpp:2271-2281` holds ONE `pEfisFilter` enum (NONE/WPT/VORD/NDB) where pressing the active button clears it and pressing any other REPLACES the selection, and :2567-2572 derive each light as `efis_filter == <enum>`, so two lit at once is unreachable. A test pilot duly reported "turn Waypoints on, then turn NDB on, and Waypoints turns off" — the aircraft was correct and the app was offering a shape it does not have.

So the ND filter is ONE combo per side (Off / Waypoints / VOR-DME / NDB), state derived from the three lights, actuated by ONE press: `NdFilterSelection` owns the mapping and the evidence. Note the trap in the set path — there is no "off" button on the panel, so clearing the selection means re-pressing whatever is currently ACTIVE. CSTR, ARPT and V/V are genuinely independent (T flip-flops in the same function, `vvActive = !vvActive`) and remain separate On/Off controls.

**⚠️ The filter CANNOT be cleared back to Off on this build, despite the code reading as though it can.** `A380FcuComputer.cpp:2271-2274` says pressing the ACTIVE button sets the selection to NONE. It does not: measured live 2026-08-22, six presses across WPT, VORD and NDB, each with a distinct command string so coalescing is excluded, and the selection never cleared — while pressing a DIFFERENT button replaced it every single time, and CSTR (a real toggle) switched off happily in the same session. So `PushEvent` still sends the press (harmless, and it starts working if FBW changes), and `IsClearAttempt` + `ClearUnsupportedMessage` make MSFSBA SAY so, because a control that silently does nothing is worse for a blind pilot than one that explains itself. Live-verified mutual exclusion in the same session: WPT went 1→0 the instant NDB went 0→1. The three lights are never announced INDIVIDUALLY — one filter change moves two of them, so that would speak twice (old off, new on). The DERIVED selection IS announced, once, on a real change: the combo is write-only and only ever speaks the pilot's own pick (through the screen reader), so without that call-out a filter changed in the 3-D cockpit, on a hardware EFIS-CP or by the aircraft itself would reach a blind pilot through no channel at all. It is baseline-first — silent until all three lights of the side have reported once, because they arrive one at a time and a partial view reads as Off — and it suppresses the echo of the pilot's own combo pick with its own short window, since MainForm's global `_uiSetEcho` gate keys on the var the combo SET (`ND_FILTER_{side}`) while what comes back is a different var.

**⚠️ ND MODE and ND RANGE are FCU-shim OUTPUTS — the direct L:var write next to the filter's is DEAD (2026-09-03).** The prefix catch-all in `HandleUIVariableSet` carried the claim *"EFIS Control Panel controls are ALL direct L:var writes on the A380X (no events — confirmed from efis-cp.xml: ND mode/range, navaid 1/2, …)"*. That is right for the VV/CSTR/ARPT option buttons and the baro-unit selector, and **wrong for ND mode and range** — and, as the "Seven more EFIS-CP / FCU controls" section below records, wrong for the navaid, OANS-range, LS, TRAF and overlay keys too, which are shim outputs on the same footing: `fbw.wasm`'s `FlyByWireInterface::updateFcu` decodes the FCU's ARINC `efis_discrete_word_1` and writes `A32NX_EFIS_{L,R}_ND_{MODE,RANGE}` every frame (`idFcuShimLeftNdMode->set(getNdMode(...))`, `FlyByWireInterface.cpp:2614-2625` — the `idFcuShim…` naming is the tell), so the write is overwritten within one frame. Measured live on the running aircraft: `3 (>L:A32NX_EFIS_L_ND_MODE)` through the calculator path read back **2** immediately. Both panel combos were inert: the pilot picked a mode or a range, the aircraft overwrote it within the frame, and the combo snapped back with nothing announced and nothing logged.

The knobs are `ASOBO_GT_Knob_Infinite` firing `A32NX.FCU_EFIS_#SIDE#_#TYPE#_{INC,DEC}` (efis-cp.xml's `FBW_AIRLINER_Knob_ND_Template`), and the FCU **also registers the absolute `A32NX.FCU_EFIS_{L,R}_{MODE,RANGE}_SET`** — which is what FBW's own init uses (`FlyByWireInterface.cpp:940` `sendEvent(A32NX_FCU_EFIS_L_MODE_SET, 3)` for in-flight ARC). `SimConnectInterface.cpp:2526` puts the parameter on `simInputAutopilot.efis_mode_left_set`, and `A380FcuComputer.cpp:2184` assigns it straight into `pMode`/`pRange`, so **the SET parameter IS the Simulink enum**. Live-verified in the same session: `A32NX.FCU_EFIS_L_RANGE_SET` param 6 moved the published range 1 → 2, where the L:var write could not move it at all. `SendEvent` is the right transport — a dotted `A32NX.FCU_*` name on the A380 bypasses the calc-path probe via `IsFbwFcuEvent` and gets a per-call sequence prefix, so two identical sets cannot coalesce.

**⚠️ MODE and RANGE do NOT share a convention, and that is the second bug hiding behind the first.** For MODE the two enums are the SAME — `a380_efis_mode_selection` (`A380FcuComputer_types.h`) and `getNdMode` are both `0 Rose ILS / 1 Rose VOR / 2 Rose Nav / 3 ARC / 4 Plan` — so the value passes through untouched. For RANGE they are not: `a380_efis_range_selection` begins with **five OANS zoom levels** (`RANGE_ZOOM_POINT_2` … `RANGE_ZOOM_5` = 0..4) and only then `RANGE_10`..`RANGE_640` at 5..11, while `getNdRange` collapses every zoom level to a single 0 and publishes 1..7 for 10..640. So **40 NM reads as 3 and must be set as 7**; forwarding the read value verbatim selects a 2 NM OANS zoom. FBW's own `RANGE_SET, 6` (in flight) and `RANGE_SET, 5` (on the runway) decode to 20 NM and 10 NM under this mapping, which is what makes it credible — under the naive reading they would be 320 and 160 NM.

`Aircraft/A380NdKnobSelection` owns the remap, so panel definitions keep speaking the **published** enum and nothing else has to know the FCU's numbering. Published 0 (Zoom) is deliberately NOT settable FROM THIS KNOB — that readback covers five zoom levels, so it names no single range in NM — and it is SPOKEN rather than silently dropped, the same call the ND filter's `ClearUnsupportedMessage` makes. ⚠️ The zoom itself IS settable, on the OANS Range control two rows down the same panel, so the message NAMES that control: a refusal telling the pilot to pick a range in nautical miles sends them the opposite way from what they just asked for. Only those four keys are claimed; every other `A32NX_EFIS_*` / `A380X_EFIS_*` key must keep falling through to the direct write, and widening the branch would kill the navaid, OANS-range, LS and TRAF controls.

**⚠️ Do not chase `A32NX_FCU_EFIS_L_EFIS_MODE` / `_EFIS_RANGE` on the A380.** They are the A32NX's keys and appear nowhere in the A380X package; a live read still returns a value (MSFSBA registers the A320 base variables, which creates them), and during this investigation they read 3 and 2 against the real vars' 2 and 1 — an apparent, meaningless off-by-one that looks exactly like a real enum offset. The A380 vars to read are `A32NX_EFIS_{L,R}_ND_{MODE,RANGE}`, which the shim genuinely publishes and `terronnd.wasm` genuinely consumes.

**⚠️ The overhead ANN LT switch had TWO combos, one of them a phantom (removed 2026-09-03).** `A32NX_OVHD_INTLT_ANN` is the real input for the annunciator-light switch (cockpit node `SWITCH_OVHD_INTLT_ANNLT`, Test/Bright/Dim); `A380X_OVHD_ANN_LT_POSITION` is listed in FBW's `a380-simvars.md` and used by nothing in the aircraft — checked case-insensitively across the whole installed package. MSFSBA's own write CREATED it, so it read back whatever was last set and looked like it worked, which is why a dead duplicate sat next to a working control unnoticed. The survivor inherits the cockpit's label ("Annunciator Lights"), so the name a pilot already used still resolves — to the one that works.

Two follow-on rules. `A380X_OVHD_INTLT_ANN` is NOT an input either: `A380_Cockpit_Behavior.xml`'s `VARIABLE_MAPPING` copies `A32NX_OVHD_INTLT_ANN` into it at 18 Hz for the button emissives, so a write there is overwritten every frame. And a name that appears only in FBW's simvar documentation is not evidence the aircraft uses it — check the package before it becomes a control. `A380AnnunciatorLightTests` pins all three.

This is the PHANTOM class, and it is worth naming separately from the shim-output class above: a shim output is written by the aircraft every frame, so a write visibly reverts; a phantom is written by NOBODY, so a write STICKS and every read-back agrees with you. The sweep that finds shim outputs (intersect the WASM's `->set()` names with the definition's writable keys) structurally cannot see phantoms. The sweep that finds phantoms is the complement: take the registered NAME behind every writable key and check whether it appears anywhere in the aircraft package at all. Run case-insensitively — MSFS named variables are case-insensitive (proven live: writing `…_XBLEED_POSITION` moved `…_XBLEED_Position`), so a case-sensitive scan reports false phantoms for every mixed-case FBW name.

**⚠️ Seven more EFIS-CP / FCU controls were DEAD writes for the same reason (2026-09-03).** The catch-all in `HandleUIVariableSet` carries the claim *"EFIS Control Panel controls are ALL direct L:var writes on the A380X (no events — confirmed from efis-cp.xml)"*. It is true for some keys and false for these, because `fbw.wasm`'s `FlyByWireInterface::updateFcu` decodes the FCU's ARINC output words and rewrites them EVERY FRAME (the `idFcuShim…` family — the naming is the tell). The write is overwritten within one frame, the combo snaps back to the aircraft's value, and the pilot has a control that does nothing with no error: nothing announces and nothing logs. Found by intersecting the 102 L:vars `FlyByWireInterface.cpp` declares AND `->set(`s against the 270 writable keys the A380 definition builds, then confirming live.

`A380EfisCpControls` owns the mapping. Five things in it are worth keeping straight:

**⚠️ ONE event is not the same as an ABSOLUTE event, and the four TOGGLES need a live value the batch cache cannot give them on its own.** The navaid and OANS setters are absolute and ignore the current state; LS, TRAF, the ND overlay and `A32NX_PUSH_TRUE_REF` are toggle pushbuttons, so `Command` has to know where the control already is — never drop its `current` parameter as vestigial, that drives all four to the opposite of the pilot's pick. But `GetCachedVariableValue` is the wrong source alone: it reads `lastVariableValues`, which only the two inbound delivery handlers write (never a UI set), and these vars are batched at `PERIOD.SECOND`. A combo commits **per arrow-key press**, so two picks inside one batch period both read the value from before the first. For the toggles that silently drops the second pick (`want == have`); for the overlay it is worse, because the CLEAR leg names the button to press *from that stale value* and a press of the non-active button REPLACES the selection — so asking for Off switches the overlay **on**. `FlyByWireA380Definition.CommandedOrCachedValue` layers what was just commanded over the cache (cleared when the sim confirms it or after 3 s — the `_fcuStateCache` shape, but fed from the SET rather than from `ProcessSimVarUpdate`, which is exactly the lag being closed) and is what the caller must pass.

**⚠️ A null `current` means UNKNOWN, not Off, and a refused set must FORCE-READ the key.** On a cold cache the toggles fire anyway — the `?? (desiredOn ? 0.0 : 1.0)` convention every other toggle-if-differs branch in `HandleUIVariableSet` uses (FD_1_CTL, ELEC_ENG_GEN, SEATBELT_SIGN, the fuel-pump circuits) — because reading unknown as 0 makes "Off" permanently unsendable while "On" toggles an already-on control back off. The overlay is the one exception: with no known state there is no button to name, so it sends nothing rather than guessing. And when nothing is sent, for a refusal or a no-op, the var never changes, so `ProcessContinuousBatch`'s `hasChanged || isForceUpdate` gate never re-fires `SimVarUpdated`, `UpdateControlFromSimVar` never runs, and the combo sits on the position the pilot picked but the aircraft never took — for the rest of the session and across panel re-opens, since MainForm re-seeds from the `currentSimVarValues` the commit already wrote. `RequestVariable(key, forceUpdate: true)` records the force flag *before* its individual-def early return, so it works for these batch-covered vars. The ND filter's refusal is exempt only because `ND_FILTER_{side}` is an `Act()` key with no backing var, explicitly listed as a synthetic selector in `UpdateControlFromSimVar`; a real backed var has no such protection. Same reasoning gives the OANS Range combo its `5 = "Not zoomed"` entry: that is what the var reads for most of a flight, and MainForm only falls back to item 0 when the key has *no* value at all — so an undescribed live value leaves the combo at `SelectedIndex` -1, and one arrow key on an unselected combo then commits "Max" and really does fire `RANGE_SET 0`, yanking the ND to 0.2 NM. The position exists so the combo can show it; picking it is refused out loud, naming the ND Range knob that does leave the zoom.

**The navaid selector WAS a cycle and is now an absolute set.** One push steps it (Off → VOR → ADF → Off, live-measured), so the first version reached a position in 0-2 presses. FBW #10914 (2026-09-01) added `…_NAVAID_{n}_SET`, whose parameter is the same enum the var publishes (0 Off / 1 ADF / 2 VOR — live-verified all three on 2f139a41), so the walk is gone. That raises the floor: on an A380X build older than 2026-09-01 these two selectors are unreachable. The PUSH events still exist if that ever has to be undone.

**A multi-press walk must be SPACED (historical — nothing in the shipped code walks anything any more).** The FCU samples its panel inputs once per frame and a push is a bool, not a counter, so two presses landing in the same frame register as ONE. Measured while probing: a second navaid push sent immediately after the first did nothing, while the same push seconds later stepped the knob. The walk that needed this — `FireEfisCpCommands`, its serialize gate, its request counter and its inter-press delay — was DELETED when the absolute navaid SET replaced it; do not go looking for the symbol, it lives only in git history (commit `7411d9b9`). Every control is now one `SendEvent` with no spacing, no serialization and no async, so there is no latest-selection-wins guarantee to rely on either. **If a future control here can only be reached by stepping, restore that walk from history rather than re-deriving it inline** — it was a plain async local, NEVER `Task.Run`, following the PMDG emergency-lights rule, so the awaits resume on the UI thread and `SendEvent`'s lazy registration cannot race `SimConnectManager`'s unlocked `eventIds` from a pool thread; and it was serialized latest-selection-wins, so a burst of combo commits could not interleave two walks into one selector.

**⚠️ The ND overlay CAN be cleared — do not copy the ND filter's refusal onto it.** The two look like the same shape (two/three buttons over one selection, clear by re-pressing the active one), and the filter famously cannot clear on this build. The overlay can: live-verified Off → TERR → Off and Off → WX → TERR → Off. So it needs no `ClearUnsupportedMessage`, and adding one would speak a refusal over a control that works.

**⚠️ A var's WRITER can change under a name that survives, and this is the worked example.** `A32NX_PUSH_TRUE_REF`'s registration carried a 2026-06 comment stating *"writing PUSH_TRUE_REF=1 latched and is what the displays read"* — a real live measurement at the time. FBW #10855's new FCU then took ownership of the var, and the same write now reverts within a frame (measured 2026-09-03). The name, the readback and the consumers are all unchanged; only the writer moved. Re-measure before trusting a "verified" note that predates a known FBW rework. The same key was also registered TWICE (a `Sel` in the source-switching block plus a `ReadEnum` in the instrument block); `vars[key] = …` meant the later one silently won, so the first had no effect — the "never register the same var KEY twice" trap, one block above this one. The dead duplicate is gone with no behaviour change.

**This is a PANEL-ONLY fault** — no auto-flow or checklist code in this repo writes any of these keys — which is why it went unreported for so long: a dead combo is silent, and nothing else read the write back.

**⚠️ The READOUT is keyed on the WPT light, never on the `ND_FILTER_{side}` combo.** That combo is an `Act()` action control, so `Name = key` and nothing ever writes `L:ND_FILTER_L` — and a data definition bound to a nonexistent L:var never delivers (`SimConnectManager.RebindVariableDataDefinition`, from the 2026-06-12 bridge-probe finding). `UpdateDisplayText` only calls `TryGetDisplayOverride` once a value exists for the key, so a display row keyed on the combo reads `--` for the whole session and the decoder never runs. The WPT light is a real batched var, so it carries the row and the `{who} ND Filter Position` DisplayName, and it is the one of the three that is NOT `ExcludeFromMonitorManager` — it is the Ctrl+M row that mutes the call-out. This is exactly the wiper split: `Act("WIPER_LEFT")` writes, `WIPER_L_SW` (a real `CIRCUIT SWITCH ON:141`) reads. `FlyByWireA380DisplayReachabilityTests` pins it.

**⚠️ Never put two BATCHED var keys on the same underlying `Name`.** The first attempt here gave speed-protection and mode-reversion a key each, both pointing at FG discrete word 5. That puts two identical `L:…` entries into the continuous batch, and `SetupDataDefinitions` sorts that batch by full name to mirror SimConnect's own ordering — precisely the data-definition position drift the `ExcludeFromBatch` docs warn about, which would silently shift every later var's struct slot so unrelated readouts return each other's values. The shipped design is ONE var (`FMA_FG_ALERTS`) decoded into two spoken alerts in `ProcessSimVarUpdate`; Ctrl+M mutes both together.

Note the qualifier: distinct keys sharing one `Name` are routine and deliberate (`PFD_VLS` and `A32NX_SPEEDS_VLS` both read `A32NX_SPEEDS_VLS`, one for the PFD readout and one for the monitor). It is only a defect when BOTH copies are `Continuous` and batched. Measured fleet-wide, the A380 has zero such collisions; the A320 and A330 each carry one pre-existing autobrake-mode collision, allow-listed in `VarNameCollisionTests` and worth fixing on their own branch.

**⚠️ CORRECTED 2026-09-25 — FG word 5 bit 28 is NOT asserted at rest.** This paragraph used to say it was (a cold parked aircraft reads raw `0x48000000`, recorded as "bits 28 and 31 set"). That reading was the decoder bug described under "Discrete ARINC words were read from the wrong bits": `0x48000000` is the float 131072, i.e. bit 18 alone, `manual_spd_control_active`. The 28/29 mapping itself was always right — `A380PrimComputerFctl.cpp` assigns `ap_fd_mode_reversion` to concatenate index 17 (bit 28) and `vs_target_not_held` to index 18 (bit 29) — but under the old decoder the call-out fired on selected/managed speed changes and Speed Protection never fired. `A380FgAlertsTests` pins both.

**Bit numbering is ARINC 1-based and must stay SSM-gated.** `Arinc429Word.BitValueOr` tests `DiscreteBits >> (bit - 1)` — the float VALUE converted back to the bitfield, exactly as FBW's `arinc429.ts` does with `this.value >> (bit - 1)` — with an SSM guard. (It tested the raw low 32 bits until 2026-09-25, and this paragraph wrongly called that identical to FBW's.) A word that is not Normal Operation / Functional Test must announce NOTHING rather than a false "off" — FG word 3 and 5 both read SSM NormalOperation live.

**⚠️ Repeated identical calc-path presses are COALESCED — and this bit the app, not just hand-testing.** Pressing the same `'A32NX.FCU_EFIS_L_CSTR_PUSH'` twice in a row leaves the light on: MobiFlight drops the second identical command string (the same invariant the RMP/DCDU writes already carry). This was first written off as a testing artifact on the grounds that MSFSBA's own presses are "one-per-user-action and seconds apart" — **that reasoning is wrong**, and the note is kept here as the correction. The dedup keys on the command TEXT, not on elapsed time, which is exactly why the RMP and DCDU needed a `<seq> 0 *` prefix rather than a delay. It applies to every TOGGLE reached through `SendEvent`, because "on" and "off" are the same event and therefore the same string: an EFIS filter or LOC/APPR the pilot switched on could never be switched off again.

The prefix now lives centrally in `SimConnectManager.BuildCalcEventCode`, so every H: and dotted event `SendEvent` fires is unique per call and no call site has to remember. Pinned by `CalcEventCodeTests`, and **proven live** on 1bbd304 (2026-08-22) in three steps against the CSTR toggle: `0 (>K:…CSTR_PUSH)` moved the light 0→1; the BYTE-IDENTICAL string again left it at 1 (dropped); `11 0 * 0 (>K:…CSTR_PUSH)` moved it 1→0. That is the whole failure and the whole fix in one experiment — reuse it if the behaviour is ever doubted again.

**The baro STD flag is read from `A32NX_FCU_EFIS_{L,R}_DISPLAY_BARO_IS_STD`** (`FlyByWireInterface.cpp:813`, written every frame at `:2408` from the FCU's own `baro_std`; FBW's `FcuSimvarPublisher` reads the same names). MSFSBA previously read the stock `KOHLSMAN SETTING STD:{1,2}` mirror. The FCU's own per-frame output is the more direct source, so the switch stands — but be clear about what it did NOT fix.

**⚠️ CORRECTION — a wrong diagnosis was published here and is retracted.** This section briefly claimed the stock mirror had lost its only writer with `MsfsBaroManager.ts` and could "never change again", and that this was why a tester reported the altimeter stuck on QNH. **Both claims are false**, disproven live on 1bbd304 (2026-08-22): firing `BARO_PUSH` moved `KOHLSMAN SETTING STD:1` 0→1 and `BARO_PULL` moved it 1→0, on both sides, with nothing in MSFSBA writing it. The aircraft keeps that mirror in sync in both directions.

The tester's actual fault was that they were running a build predating the fix — `MSFSBlindAssist.dll` reported `470a5cfa` (main, pre-#198) and `debug.log` showed it emitting the DELETED `H:A380X_EFIS_CP_BARO_PUSH_1`. The real cure was the event migration already made above. **The lesson is procedural: check which binary is running before diagnosing behaviour.** `startup.log` names the Application Directory and the DLL carries the commit in its ProductVersion; one look at either would have saved the whole investigation. Reach for `debug.log`'s `Sending event:` lines early — they say what the app actually emitted, which no amount of source reading can.

The `BARO_MB_WATCH_*` mirrors and the MainForm STD-flag watchdog were removed alongside. That removal is still right — nothing reads the stock flag now, so their back-fill write would converge on nothing and a genuine QNH of 1013 would retry it every 2 s — but note the removal was NOT needed to fix any reported bug.

**Still live, do not "fix":** `A380X_EFIS_{L,R}_LS_BUTTON_IS_ON`, `..._TRAF_BUTTON_IS_ON` and `..._ACTIVE_OVERLAY` survived the commit. The A32NX keeps `A32NX_FCU_APPR_MODE_ACTIVE` and `A32NX_FMA_EXPEDITE_MODE`, so the A320 def is deliberately untouched.

### FCU hardware-dial callouts (PR #140, 2026-09)

Turning an FCU knob on hardware speaks the new value — see [a32nx.md](a32nx.md), "FCU
hardware-dial callouts", which covers the staging/release machinery, the echo table and the
settle rules shared by both airframes. This section is the A380-specific half.

**Sources.** The heading and speed shims (-1 while dashed, or 0 while the FCU is off — the A380
writer has no separate FCU-failed term), `FCU_ALT_VALUE` (stock, metric under MTRS), and PRIM 1's
selected-V/S and selected-FPA ARINC429 words — never the `A32NX_AUTOPILOT_{VS,FPA}_SELECTED`
shims, which read 0 while dashed and so spoke "Vertical speed 0 feet per minute" at every
level-off. All five are now BATCH-COVERED (`ExcludeFromBatch` removed from the heading/speed
shims and from `FCU_ALT_VALUE`), so every sample of the five lands in the same continuous batch as
`A32NX_FCU_AFS_CP_ACTIVE` and is judged with it at that batch's end — the whole reason a
callout can now be released only once the FCU's own health is known. A Shift+H/S/A force-read of
one of them is honoured by the next batch delivery, not a `PERIOD.ONCE` reply, since a batch-
covered var has no individual data def of its own to re-request.

**FCU availability.** `A32NX_FCU_AFS_CP_ACTIVE` is `fcu1||fcu2 afs_cp_active`, 0 exactly when the
FCU publishes all-zero outputs (unpowered or failed) — a callout is released only while it reads
1, and its RETURN to 1 begins a settle. Switching the batteries off zeroes every source in one
sample (heading/speed shims → 0, `FCU_ALT_VALUE` → 0, `A32NX_FCU_AFS_CP_ACTIVE` → 0) and says
nothing; the FCU coming back the same way says nothing either, because the settle absorbs it.
`TryComposeFcuValuePhrase` also treats `FCU_ALT_VALUE` ≤ 0 as `FcuValuePhrases.Unavailable`
outright — the FCU's selected altitude is never below 100 ft, so 0 can only be the FCU off, never
a real selection.

**MTRS re-baselines the altitude callout's WORDS without treating the flip as a turn.** The unit
is part of what the altitude callout says but not part of `FCU_ALT_VALUE` itself, so the definition
now remembers the last delivered altitude (`_lastFcuAltFeet`) and, when the metric mode changes
(PRIM FG discrete word 5 bit 14 since the 2026-09-25 correction — `UpdateMetricAltitude`),
re-composes and silently `RebaselineFcuValue`s the SAME altitude in the new unit. Without this, a
panel's forced re-read of an altitude the MTRS flip did not otherwise change was compared against
the OLD unit's phrase, read as a change, and spoken as a callout the pilot never turned a knob for.

**Every A380 FCU panel button arms a `ValueReadout` echo, because every one of them is followed by
a readout that speaks the resulting value** (`OnPanelButtonFiring` → `FcuEchoKeys.For(evt, Fcu,
FcuConfirmation.ValueReadout)`), including for the PRIM V/S and FPA words the V/S readout does not
itself read — without covering those a panel V/S pull was announced twice, once by the readout and
once by the dial callout the readout's own batch delivery released.

**Shift+V (and Shift+H/S) now say "managed"/"not available" instead of reading the live shim
value.** Each readout suppresses its own echo and asks `FcuWindowStateOf` (backed by the same
tracker the dial callouts use) rather than composing straight from the delivered number — a
pending V/S readout mutes BOTH the V/S and the FPA dial callouts (`_reqVs`, in
`ProcessSimVarUpdate`'s `readoutPending` check) even though it only speaks one of them, since the
readout takes its dashes/not-available words from whichever PRIM word is active either way.

**TRK/FPA now fires the cockpit's own toggle event.** Since FBW #10855 `L:A32NX_TRK_FPA_MODE_ACTIVE`
is an FCU-shim OUTPUT rewritten every frame (see the CLAUDE.md "FCU-SHIM OUTPUTS" bullet), so the
old direct L:var write did nothing — verified only by this pass, not by an earlier "works" claim.
`FlyByWireA380Definition.SetTrkFpaMode` now fires `A32NX.FCU_TRK_FPA_TOGGLE_PUSH` (a toggle, so only
when the requested mode differs from `CommandedOrCachedValue`, and a live read-back when it does
not) and arms the echo for the heading, V/S and FPA values the flip re-syncs — reached from both the
Ctrl+H window's button and the FCU panel's settable combo, so neither path can bypass the write or
the echo.

### The FCU ALTITUDE managed/selected state is DERIVED, not read (FBW #10855 aftermath, 2026-08-23)

**⚠️ `L:A32NX_FCU_ALT_MANAGED` is hardcoded to 0 on this aircraft and can never be read again.**
#10855 deleted the TypeScript FCU that used to publish it and replaced it with a WASM shim
that writes the var, in `updatePrimFgShim`, every single frame:

```cpp
const bool lvlChManaged = false;
simConnectInterface.sendEvent(Events::AP_ALTITUDE_SLOT_INDEX_SET, lvlChManaged ? 2 : 1, …);
idFcuShimAltManaged->set(lvlChManaged);
```

So the stock `AUTOPILOT ALTITUDE SLOT INDEX` beside it is dead too, and neither is a usable
substitute for the other. This is the *fourth* distinct shape #10855 broke — a var that was
deleted, a var that changed units, an event that was deleted, and now a var that still exists,
still reads, and always lies. Measured live at FL360: `altManaged=0`, `altSlot=1`, while the
three sibling flags (`hdgDashes=1`, `spdDot=1`, `vsManaged=1`) were all correct. **Altitude was
the only one of the four stranded, which is exactly why only that readout went wrong** and why a
sweep of "the managed flags" finds nothing. `A32NX_FCU_HDG_MANAGED_DOT` is hardcoded the same
way (`const bool hdgTrkManaged = false`) but nothing reads it — heading uses `…_DASHES`.

**The replacement is FBW's own formula, not an invention.** `AltitudeManagedState` transcribes
the deleted `FCU/Managers/AltitudeManager.ts` (at `1bbd304c4^`), which is the authoritative
definition of what the var meant:

```
(verticalArmed & (AltCst|Clb|Des|Gs)) > 0 || MANAGED_MODES.includes(verticalMode)
```

Both inputs survive as `A32NX_FMA_VERTICAL_MODE` / `A32NX_FMA_VERTICAL_ARMED` and were already
monitored, so nothing new is registered to get them.

**⚠️ The key `A32NX_FCU_ALT_MANAGED` must never be aliased onto `A32NX_FMA_VERTICAL_MODE`, and
must never be `ExcludeFromBatch`.** That pairing was the first attempt and it broke the feature
outright. `ExcludeFromBatch` gives a var a standing `PERIOD.SECOND` subscription bound to its
data-def id (`SimConnectManager.Setup.cs`), while `RequestVariable(key, forceUpdate: true)`
re-issues that SAME id with `PERIOD.ONCE` (`SimConnectManager.DataRequests.cs`) — which replaces
the recurring request. Nothing re-arms it; the codebase's own cancel idiom
(`SafelyClearDataDefinition`) works by re-issuing `PERIOD.NEVER` on the same id, which is the
proof the replacement semantics are real here. The key is listed in the FCU display list, and the
panel force-reads every display var on open and on its 1 Hz auto-refresh — so **opening the FCU
panel once froze the derivation for the rest of the session** and the call-out never fired again.

The derivation therefore reads `A32NX_FMA_VERTICAL_MODE` under its OWN key, which is batch-covered
and structurally immune: `RequestVariable` early-returns for batch-covered vars before it can issue
the `PERIOD.ONCE`. That branch must NOT return true — it falls through so the generic monitor still
speaks "Vertical Mode: …". `A32NX_FCU_ALT_MANAGED` survives only as an inert definition: it keeps
the pilot's Ctrl+M mute row (keyed on the var key, so renaming it would silently un-mute anyone who
had turned the call-out off) and the FCU panel row, which renders from `TryGetDisplayOverride` off
the derived tracker. `ProcessSimVarUpdate` returns true for it so the generic monitor never speaks
its dead 0, and **nothing reads its value at all** — so the old warning about
`GetCachedVariableValue(...) > 0.5` reading "managed" for every mode but None no longer applies to
it. Shift+A reads the derived state at emit time rather than awaiting a second delivery.

**Still live elsewhere:** `A32NX_FCU_HDG_MANAGED_DASHES`, `A32NX_FCU_SPD_MANAGED_DOT` and
`A32NX_TRK_FPA_MODE_ACTIVE` are all `ExcludeFromBatch` and all force-read by
`RequestFCUHeadingWithStatus` / `RequestFCUSpeedWithStatus` / `RequestFCUVSWithStatus`, so by the
identical mechanism the first Shift+H / Shift+S / Shift+V of a session should permanently kill the
corresponding "… Mode: Managed/Selected" auto-announce.

The obvious candidate fix is the one altitude took — drop `ExcludeFromBatch` — and **the reason
those three were given an individual def no longer holds.** `d7f4549c` set the flag on them because
`RequestVariable(forceUpdate)` was believed to no-op for batch-covered vars ("the pair-gate never
closed"); `929be066` fixed that four days later by recording the force flag BEFORE the
individual-def check, so `ProcessContinuousBatch` consumes it and re-fires even an unchanged value
(`DataRequests.cs:107-118`, `VarCache.cs:418-429`; CLAUDE.md carries it as a standing rule). The
`ExcludeFromBatch` was simply left behind, along with the def comment still asserting the
superseded rationale. So the residual cost of dropping it is **latency, not silence**: the
readout's two-half pair would close on the next 1 Hz batch delivery rather than on an immediate
`PERIOD.ONCE` response. Whether that delay is acceptable for Shift+H/S/V is untested — as is the
prediction above.

Since 2026-09 `RequestVariable` never issues a `PERIOD.ONCE` on the OWN request id of a var on its own
periodic subscription (`Continuous + IsAnnounced + ExcludeFromBatch`), so the freeze above cannot recur on any
airframe (the HS787 forces `ExcludeFromBatch` on every Continuous+IsAnnounced var, so every one of its panel
opens used to freeze that panel's vars - and the Alt+E EICAS window and the "IRS aligned" callout with them).
A `PERIOD.SECOND` one lets the next periodic delivery honour the force flag instead, and the cost is exactly
the latency this paragraph predicts: a force-read of it answers within one period, never immediately. A
SIM_FRAME + CHANGED one has no next delivery while it stands still, so it is read on a separate seed or fresh
request id, which leaves the subscription alone (md11.md, the walker's read protocol).

**⚠️ LAND / FLARE / ROLL OUT cannot arrive on the vertical mode at all — that is why the lateral
mode is an input.** The #10855 shim's vertical-mode if-chain assigns `lateralMode` in its
32/33/34 branches, a verbatim copy-paste of the three branches in the lateral chain directly
above it, so `A32NX_FMA_VERTICAL_MODE` falls through to 0 ("None") once G/S track drops on an
autoland.

**But do not read that as "the rescue is what keeps the flare quiet" — it is not, and mistaking
which mechanism does the work is how one of them gets deleted.** What actually prevents the
spurious flare call-out is `AltitudeModeTracker`'s `_vertical == NoVerticalMode` early return
plus its PRESERVATION of the last published `IsManaged`, and that return sits ABOVE the only
production call to `AltitudeManagedState.IsManaged`. So on the one path the lateral rescue was
written for — vertical mode at None during an autoland — the rescue cannot run at all. It is
defence-in-depth, not the mechanism, and `Lateral_land_flare_rollout_is_managed_when_the_vertical_mode_has_dropped`
pins a path production does not currently reach.

Preservation gives the same answer the rescue would, and not by luck: reaching LAND means passing
through G/S CAPT (30) or G/S TRACK (31), both managed vertical modes, so the value being preserved
is already "Managed". The rescue is kept because it costs nothing and is the correct answer if the
None-suppression is ever narrowed — but if you remove the early return believing the rescue covers
the flare, the flare will announce. The rescue also stays correct if FBW fixes that chain, because
on a real autoland the lateral and vertical LAND/FLARE/ROLL OUT modes engage together. LOC capture/track (30/31) are deliberately excluded: localizer tracking
says nothing about the vertical side. This is an upstream defect worth reporting, not a shape to
design around permanently.

**The call-out is coalesced against the last value SPOKEN, not the last computed, and is silent
while the vertical mode is None.** All three inputs — vertical mode, armed bitmask, lateral mode —
now ride the continuous batch, but each still arrives on its own `ProcessSimVarUpdate` branch, so
an autoland would otherwise announce "Altitude Mode: Selected" and then "Altitude Mode: Managed"
one frame apart. `IsManaged` is deliberately PRESERVED rather than recomputed during that silence
(pinned by `IsManaged_is_preserved_not_recomputed_while_vertical_mode_is_none`), so a Shift+A in
the window answers with the last mode that genuinely applied rather than one derived from a view
the FMA is not currently publishing. Baseline-first, as every other MSFSBA monitor is, and only once BOTH primary
inputs have reported at least once (`IsKnown`): a half-delivered view would announce a mode that
was already showing when the app connected.

That whole sequence — readiness, the autoland transient, spoken-vs-computed, and `Reset()` —
lives in the pure `AltitudeModeTracker` (`MSFSBlindAssist/Aircraft/AltitudeModeTracker.cs`, pinned
by `AltitudeModeTrackerTests`) rather than in the definition, which is what makes it testable
without a sim. `Reset()` is reached from `ResetAnnouncementBaselines()`, called on SimConnect
reconnect, so a reconnect re-baselines instead of announcing a mode that never changed.

**⚠️ `A32NX_FMA_VERTICAL_ARMED` no longer carries the ALT CST bit.** The shim builds it as
`altArmed | (clbArmed << 2) | (desArmed << 3) | (gsArmed << 4) | (finalArmed << 5) |
(tcasArmed << 6)` — bit 1 is skipped. `ManagedArmedMask` keeps it for fidelity with the formula
above (an ALT CST arm reaches us through the ALT CST vertical *mode* instead, and the bit costs
nothing if FBW restores it), but the "Altitude constraint armed" call-out that used to sit in
`_vertArmedBits` could never fire on this build. That gap is closed in the next section: the dead
bit was removed and the constraint now RENAMES the armed-ALT bit instead.

### There is no "ALT CST armed" bit — the constraint RENAMES the armed ALT call-out (2026-08-23)

**⚠️ Do not go looking for one.** The A380 PRIM FG's armed-modes bus (`base_prim_armed_modes`,
`A380PrimComputerFctl_types.h`) carries exactly `alt_acq_armed`, `alt_acq_arm_possible`,
`glide_armed`, `app_des_armed`, `clb_armed`, `des_armed`, `op_clb_armed`, `tcas_armed`,
`nav_armed`, `loc_armed`, `rwy_armed`, `land_armed` — and that is the whole list. FG discrete
word 2 maps them in that order from bit 11:

| bit | signal | | bit | signal |
| --- | --- | --- | --- | --- |
| 11 | `alt_acq_armed` | | 17 | `op_clb_armed` |
| 12 | `alt_acq_arm_possible` | | 18 | `tcas_armed` |
| 13 | `glide_armed` | | 22 | `nav_armed` |
| 14 | `app_des_armed` | | 23 | `loc_armed` |
| 15 | `clb_armed` | | 24 | `rwy_armed` |
| 16 | `des_armed` | | 28 | `land_armed` |

Bit 12 is the obvious-looking candidate and it is **not** ALT CST — it is
`alt_acq_arm_possible`, a permission flag. Check the concatenate block that builds the word
(`A380PrimComputerFctl.cpp:4240-4259`) before assuming any bit's meaning from its neighbours.

**The constraint is a separate qualifier in FG word 3**, and the PFD's own armed-vertical cell
(`FMA.tsx` `B2Cell`) is where the combination is defined:

```
altAcqArmed        = PRIM_1_FG_DISCRETE_WORD_2 bit 11   (reaches us as VERTICAL_ARMED bit 1)
altCstrApplicable  = PRIM_1_FG_DISCRETE_WORD_3 bit 28
altIsCrzAlt        = PRIM_1_FG_DISCRETE_WORD_3 bit 29

altAcqArmed && altCstrApplicable -> "ALT" rendered MAGENTA
altAcqArmed && altIsCrzAlt       -> "ALT CRZ"
altAcqArmed                      -> "ALT" rendered CYAN
```

So on the A380 the constraint case is signalled by **colour alone** — the text stays "ALT" —
which is exactly the difference a blind pilot has no other channel for. (The A320 writes
"ALT CST" into the text, which is why the older bit table had a name for it.) `ArmedAltitudeMode`
owns the rule, constraint outranking cruise because that is the order the PFD tests them in, and
both bits are read SSM-gated so a failed word degrades to the plain "Altitude armed" rather than
inventing a constraint.

**⚠️ Neither qualifier is an armed state and neither may ever announce on its own.** Measured live
at FL360 immediately after a step climb, with `A32NX_FMA_VERTICAL_ARMED` at 0 and nothing at all
armed, word 3 read raw `0x4D804000`. ⚠️ CORRECTED 2026-09-25: that was recorded as
"`alt_cstr_applicable` TRUE", which was the decoder bug (see "Discrete ARINC words were read from
the wrong bits"). Decoded as FBW decodes it, it is bits 29 (cruise — the PFD's `altIsCrzAlt`) and
20 (ALT hold): level cruise, the constraint qualifier CLEAR. The rule stands on the corrected
reading just as well — the cruise qualifier was set with nothing armed. `FMA_CRUISE_ALT_MODE` is therefore
Continuous but `ExcludeFromMonitorManager` and never announces a state of its own —
`ProcessSimVarUpdate` caches the two bits, flushes any held armed-ALT call-out (the hold is
described at the end of this section — that flush is its low-latency half, not an optional extra)
and returns true. It was promoted from OnRequest because the qualifier has to be live when the
armed bitmask moves; its "Cruise Altitude Mode" panel row is unaffected and is now live too.

**The dead bit 2 was removed, not repaired.** FBW's shim builds `A32NX_FMA_VERTICAL_ARMED` as
`altArmed | (clbArmed << 2) | (desArmed << 3) | (gsArmed << 4) | (finalArmed << 5) |
(tcasArmed << 6)` — bit 1 is skipped because there is no signal to put there, so the old
`(2, "Altitude constraint")` entry could never fire. The A32NX WASM builds its bitmask with the
**identical** expression (`fbw_a320/src/FlyByWireInterface.cpp`), so the A320 def's bit 2 was
removed in the same change. Its qualifier comes from a different place — the SSM of
`A32NX_FMGC_{1,2}_FM_ALTITUDE_CONSTRAINT` rather than a discrete bit — and is source-verified
against `FmgcComputer.cpp` rather than sim-verified. See [a32nx.md](a32nx.md).
**Known remaining gap:** `op_clb_armed` (word 2 bit 17) is dropped by that shim and
`FgVerticalArmedFlags` has no slot for it either, so "OP CLB armed" cannot be announced from this
bitmask on either airframe.

**The armed-ALT qualifier is dispatched AFTER the bitmask that arms it, so the ALT entry's
call-out is HELD.** The ordering is measured, not inferred: on the A380 `A32NX_FMA_VERTICAL_ARMED`
sits at continuous-batch 1 index 257 while the qualifier `FMA_CRUISE_ALT_MODE`
(`L:A32NX_PRIM_1_FG_DISCRETE_WORD_3`) sits at batch **2**, GLOBAL index 488 — batches hold
`BATCH_SIZE` 300 (`SimConnectManager.Setup.cs:529`), so that is slot 188 within batch 2, and the
two arrive as separate SimConnect messages, requested 1 then 2. On the A32NX the bitmask is at
batch 1 index 169 and the two FMGC constraint words at 172/173 (164/167/168 before PR #140),
three slots later in the SAME batch (all three below 300, so global and within-batch indices coincide there). A definition only
learns a value when its own `ProcessSimVarUpdate` branch runs, and dispatch is synchronous and
inline, so it cannot see a qualifier still queued behind it.

Naming ALT inline therefore read the PREVIOUS sample's qualifier, and because the call-out is
edge-triggered (`iv & ~prev`, with `_prevVertArmed` assigned before the edge test) the wrong name
was permanent — "Altitude armed" for a constrained altitude, which on the A380 the PFD signals by
COLOUR ALONE. That is not an exotic case: `alt_cstr_applicable` is CAUSALLY DRIVEN by arming.
`A380PrimComputerFg.cpp:1942` builds it as `(clb_armed || des_armed || clb_active || des_active ||
...) && next_alt_cstr_ft != 0 && ...`, reading `Delay_DSTATE_c.armed_modes.clb_armed` — one PRIM
cycle behind, i.e. far inside one MSFSBA sample. So a constrained ALT arm moves the bitmask and
the qualifier in the SAME 1 Hz sample essentially every time.

**⚠️ The flush is released by the qualifier's BATCH, not by a clock and not by the qualifier's own
`ProcessSimVarUpdate` branch.** Both of those were tried and are wrong:

- *The qualifier's own branch* only runs when the value CHANGED (`VarCache.cs`, the
  `hasChanged || isForceUpdate` gate), so it cannot tell a held call-out that an UNCHANGED
  qualifier has arrived and is current — which is most samples.
- *A wall-clock backstop* has to guess how far batch 2 trails batch 1, and that gap is neither
  small nor knowable from here. Each batch is a SEPARATE `RequestDataOnSimObject` at
  `SIMCONNECT_PERIOD.SECOND` issued INSIDE the per-batch setup loop, behind an unconditional
  `SafelyClearDataDefinition(..., delayMs: 300)` wait plus ~6 × `Thread.Sleep(5)` throttles and 300
  `AddToDataDefinition` calls — measured at **405 ms** between "Batch 1 monitoring started" and
  "Batch 2 monitoring started" in a real session log. Whether `PERIOD.SECOND` preserves that
  per-request phase or co-phases every SECOND request onto one server tick is NOT determinable
  from this repo, and the original 300 ms backstop would have lost the race under the first
  reading — firing with the stale qualifier and clearing the pending flag, so the qualifier's own
  later arrival found nothing to correct. Do not reintroduce an interval here.

`SimConnectManager.ContinuousBatchDelivered` is the event that actually answers the question: it
is raised once per delivered batch message, AFTER every `SimVarUpdated` that message carried, and
it arrives on schedule whether or not anything in the batch moved. A definition names the variable
it is waiting on via `IAircraftDefinition.DeferredFlushWatchVariable`; MainForm resolves that key's
batch (`TryGetContinuousBatch`) and calls `OnDeferredFlushBatchDelivered` when that batch lands.
Cost: nothing on the A32NX (its qualifier shares the arming batch, so the flush is the tail of the
same message) and at most one batch period on the A380. Every other armed mode still announces
inline. An ALT that arms and disarms inside the window is dropped, not spoken late, and the Ctrl+M
mute is re-checked at flush time.

**⚠️ Do NOT "simplify" this by reading the qualifier from `SimConnectManager.GetCachedVariableValue`
at announce time.** That was tried and reverted (`2f44736b`): it rests on a producer/consumer
threading model this app does not have. `ReceiveMessage()` has a single call site reached from
`MainForm.WndProc`, so `InvokeRequired` is false in `OnSimVarUpdated` and `ProcessSimVarUpdate`
runs INLINE; and `VarCache.cs` writes the value cache and fires `SimVarUpdated` in the SAME loop
iteration. A var later in the batch is simply not cached yet, so the cache returns exactly what the
definition's own cached bool already held.

**⚠️ On the A32NX the flush must re-check the Ctrl+M mute itself.** That aircraft is muted
centrally — `MainForm.Announcers.cs` wraps `announcer.Suppressed` around the
`ProcessSimVarUpdate` call — and the batch hook runs OUTSIDE that wrap. The A380 is unaffected
because its armed branch checks `A380DisabledMonitorVariablesSet` locally, but both defs route the
decision through the one `ArmedAltitudeMode.ShouldSpeakHeldAlt(pending, muted, currentArmed)` so
the three gates cannot drift apart.

A held call-out is dropped without speaking on every path where the context it belongs to is gone:
`CancelDeferredFlush()` is called from each def's `StopAllMotion()` (aircraft swap), from
`ResetAnnouncementBaselines()` (reconnect), from MainForm's SimConnect "Disconnected" edge, and
from `OnFormClosing`. The last two matter because the hold is fed by the batch stream: a disconnect
stops the only thing that would consume it, and "Altitude armed" arriving after "Disconnected"
describes an aircraft that is gone.

`HeldAltStillArmed` guards on `currentArmed > 0` as well as the bit, and that half is load-bearing:
`_prevVertArmed` is dual-purpose (a bitmask, plus `-1` for "no baseline taken"), and `-1 & 1 == 1`,
so the bare bit test calls the sentinel "ALT armed" and a hold outliving a re-baseline would speak
a phantom call-out. The decision helpers (`AltArmedBit`, `ArmedVerticalKey`, `ImmediateArmedBits`,
`ShouldHoldAltAnnouncement`, `HeldAltStillArmed`, `ShouldSpeakHeldAlt`) are pure and pinned by
`ArmedAltitudeModeTests`, which also reflects into both defs' real `_vertArmedBits`/`_latArmedBits`
tables — the latter because bit 1 laterally is NAV, which is why `ImmediateArmedBits` may only ever
be applied to a vertical mask.

### The FBW-drift sweep — how to run it, and the four ways the obvious method lies (2026-08-23)

A full sweep of both FBW airframes after #10855 found **no further defects** beyond the two
fixed that day. The result matters less than the method: the recipe this file used to carry
("diff every `A32NX_`/`A380X_` token in their tree and intersect with the def's references")
produced 137 A380 and 135 A320 "unresolved" tokens, of which **zero** were real. Four distinct
false-positive sources, each of which has to be handled explicitly:

1. **A KEY is not a NAME.** `A32NX_FCU_LEFT_EIS_BARO_IS_STD` is a key whose `Name` is
   `A32NX_FCU_EFIS_L_DISPLAY_BARO_IS_STD`; the key exists nowhere in the FBW tree and never
   should. Grepping source text checks the wrong string. **Enumerate `GetVariables()` out of the
   built assembly and check `Name`** — that is exactly what MSFSBA asks the simulator for, and it
   drops comments and concatenation fragments in the same step.
2. **Both sides build names dynamically.** MSFSBA composes `"A32NX_FCU_EFIS_" + side + "_WPT…"`;
   FBW composes `"A32NX_PRIM_" + idString + "_FG_DISCRETE_WORD_1"` in C++ and whole indexed
   families (`BRAKE_TEMPERATURE_{1..16}`, `COND_MAIN_DECK_{n}_TEMP`, `PRESS_CABIN_ALTITUDE_B{n}`,
   `OVHD_FIRE_AGENT_{n}_ENG_{n}_IS_PRESSED`) in Rust. None appear literally anywhere.
3. **Events are registered in TWO places.** Checking only `SimConnectInterface.cpp` reports five
   live A32NX autobrake events as missing; they are registered in the Rust systems WASM
   (`a320_systems_wasm/src/autobrakes.rs`). Check both, or the pass invents casualties.
4. **`SimVar.GetRegisteredId` is not an existence oracle.** It is per-Coherent-view and returns a
   fresh id for a name nothing has touched — including one the WASM writes every frame — and it
   is polluted by your own earlier probes. A bogus name and a live one are indistinguishable.

**Scope the diff to a commit instead of the whole tree.** "Tokens this commit removed and never
restored, intersected with the registered names" is precise: dynamic names never appear as
removals, and a token that merely moved shows up on both sides. That pass reported 64 A380 and 3
A320 tokens removed by #10855, **none** of them registered by MSFSBA.

**Four passes a name diff cannot do, and must be run beside it:**

- **Constant writers** — the category that produced the ALT_MANAGED bug. Map every
  `idFoo = make_unique<LocalVariable>("NAME")` to its name, then flag every `idFoo->set(EXPR)`
  where EXPR is a literal or a local only ever assigned one. Across ~440 A380 and ~395 A320
  handles this found exactly three: `A32NX_FCU_ALT_MANAGED` and `A32NX_FCU_HDG_MANAGED_DOT`
  (A380, both `= false`; only the first is read by MSFSBA — heading uses `…_DASHES`), and one
  dead CONTRIBUTOR, the A32NX's `bool tcasArmed = false;` feeding `A32NX_FMA_VERTICAL_ARMED`.
  Extend the scan to contributors, not just whole-constant writes, or the third is missed.
- **Changed writers** — a name that survives with a new writer can change UNITS or ENCODING
  silently (this is how V/S came to announce 500 fpm as "98400"). Intersect the commit's changed
  `->set()` lines with the registered names. #10855 touched 50 that MSFSBA registers, but only
  **five** on both sides of the diff — the whole autothrust family
  (`STATUS`, `MODE`, `MODE_MESSAGE`, `THRUST_LIMIT`, `THRUST_LIMIT_TYPE`). All five were verified
  against FBW's `AutoThrustMode`/`AutoThrustModeMessage` enums and live at FL360: status 2
  (Active), mode 8 (Mach), message 0 (None), limit 93.5 %N1, limit type 1 (CLB). Correct.
- **Live read** — with the aircraft loaded, batch-read the candidate names through the Coherent
  debugger. A non-zero reading proves existence outright and cleared 39 of 107 A380 candidates in
  one round-trip. Zero proves nothing on its own (most are legitimately zero in the cruise), so
  use it to CLEAR candidates, never to condemn them.
- **Stock names** (added 2026-09-25, after it missed the flight directors for five weeks) — every
  pass above keys on `A32NX_`/`A380X_` tokens, so a STOCK SimVar (`AUTOPILOT FLIGHT DIRECTOR
  ACTIVE:n`) or STOCK K-event (`TOGGLE_FLIGHT_DIRECTOR`) the definition depends on is invisible to
  all of them, and a stock name never disappears. Enumerate what the def reads with
  `Type == SimVarType.SimVar` and every stock event it sends, then ask the aircraft two questions
  per name: for an EVENT, is it masked (`addInputDataDefinition(…, true)`), what does the handler
  set, and does anything downstream still CONSUME that input; for a VAR, does anything still WRITE
  it (`git log -S "<name>"` over the commit finds a writer that was removed). See
  [The flight directors are ONE FCU pushbutton](#the-flight-directors-are-one-fcu-pushbutton-fbw-10855-found-2026-09-25).

**⚠️ The A32NX's WASM was untouched by #10855** — zero writer lines in `fbw-a32nx`'s C++. (Its
TypeScript was not: #10855 changed the A32NX FMS's cleared V1/VR from 0 to -1 —
`A32NX_FMCMainDisplay.ts` — which is how every A32NX climb-out came to be announced "V1: -1 knots"
until `NotSetBelow`, 2026-09-25. "Zero writer lines" was a C++-only count.) Its shim has the same
SHAPE (the `verticalArmed` expression is byte-identical) because both airframes were migrated to
the same pattern at different times, which is exactly what makes "it's shared" a tempting and
wrong conclusion. See [a32nx.md](a32nx.md).

**⚠️ Always confirm which FBW build is actually flying.** All of the above compares MSFSBA against
a local clone; the pilot runs whatever the FBW Installer put on disk. `build_info.json` is not
reachable from the Coherent debugger (sync XHR is blocked, and Chromium 49 has no async/await),
so the practical check is behavioural: read a var #10855 introduced and one it stranded, and see
that they behave as the clone predicts.
