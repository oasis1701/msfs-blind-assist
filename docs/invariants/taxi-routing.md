# Taxi routing — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/taxi-routing.md`, which Claude Code loads when it reads matching code. Background: [taxi-guidance.md](../taxi-guidance.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.
RTE-31 to RTE-33, RTE-35 and RTE-36 came with the taxi/landing port (`feat/taxi-landing-port`) and are verbatim from that branch's CLAUDE.md as of `4854ec3d`; RTE-36 was the branch's RTE-30, renumbered when it merged main, which had taken that number, and the branch's RTE-34 lives in [taxi-graph.md](taxi-graph.md). They sit on top of main's own designs, which win wherever the two overlap; their figures were measured on the owner's local build, and of the sweeps they name only `tools/VirtualPilot` and `tools/ExitConsistencySweep` are in the repository, so re-measure with VirtualPilot ([virtual-pilot.md](../virtual-pilot.md)) before touching one.

## RTE-1

- No airport-specific hardcoding — every taxiway/parking/runway name must flow through from the user's DB unchanged. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-3

- A bridge-only stand stub — every node in an island `BridgeOrphanParkingIslands` successfully bridged, `TaxiGraph.IsBridgeOnlyStandStub` — must never be picked as a route START, only reachable as a destination: bridging merges it into the main component, so the `requiredComponentId` filter alone can no longer tell it apart from a real network node, and a "P" (stand lead-in) row is NOT always unnamed (1,810 of 319,004 real fs2024 rows carry a name), so a stub's node can register on a real taxiway name too, including one a real network node also carries. `FindNearestNode`, `FindNearestNodeInDirection` and `FindNearestNodeOnTaxiway` all take an `excludeBridgeOnlyStandStubs` opt-in (default false, so destination lookups are unaffected) that every route-start caller must pass true; a node `SplitEdgeAt` mints on an edge interior to an already-bridged island inherits the same membership. Any future picker that can feed an A*/Dijkstra start inherits the same obligation — stated once on `TaxiGraph.IsBridgeOnlyStandStub`'s own doc, not re-derived per call site. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-5

- Never announce runway info (length/surface/ILS) from taxi guidance — out of scope. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-8

- An accepted recalc must announce the new taxiway sequence by name ("Route changed. Now via X, Y…") — never the old generic "Recalculating… Taxiway X." wording. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-9

- The Progressive Taxi terminator block is self-contained with its OWN runway/taxiway combos — never reuse the per-row "Hold short of runway" combo for the terminator target; that per-row combo must be hidden (and reset) in Progressive Taxi mode so a stale pick can't leak into the route. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-10

- Never restore an "already used taxiway" filter on the Add-Taxiway dropdown — ATC clearances legitimately reuse a taxiway across a runway crossing (KBOS pattern); only the immediately-previous taxiway is conditionally hidden. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-13

- `LoadRoute`/`TryRecalculateRoute` must filter start-node candidates to the destination's `ComponentId` — without the connected-component filter, A* can't reach an isolated taxiway island (GCLP S5) and route calc silently fails. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-14

- Node ID 0 is a permanent "not set" sentinel in `TaxiGraph` — never reuse it as a real node id. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-15

- Taxiway exit/intersection picking must use GRAPH distance (Dijkstra from the destination), never Euclidean — Euclidean silently fails on a graph dead-end (KDEN case). → [taxi-guidance.md](../taxi-guidance.md)

## RTE-16

- `FindBestIntersection` has no Euclidean fallback by design — returning -1 (unreachable) on a malformed graph is intentional; don't add one back (the old Euclidean path produced silently wrong routes). → [taxi-guidance.md](../taxi-guidance.md)

## RTE-17

- The last cleared taxiway must be honored as the route terminus when it branches off the destination — never let the final unconstrained leg silently drop the cleared last taxiway (EIDW N2, LFPG R1 cases). → [taxi-guidance.md](../taxi-guidance.md)
- A terminus is only right where the clearance really ends. When the last cleared taxiway leads over ANOTHER runway towards the destination, it is driven and the route goes on from its far end (`TaxiRouter.OnwardLegOverAnotherRunway`): OMDB 2026-11-23, the south apron to Runway 30R "via K, K7" and "via K4". K4 and K7 cross runway 12R/30L and a crossing further east is shorter, so each read as a branch: the route ended at the 12R/30L hold, which guidance spoke as "Hold short of Runway 30R" and then lined up on, or K4 was never driven. The way on is the shortest path that does not come back along the last taxiway's own leg, and it is REFUSED unless it is all new ground, using no node the route has already used (else EGKK "…J, G" to 08R went over 08L twice more: the route comes over 08L onto G and G's far end is back at 08L; closing the whole route to the search instead of refusing forced a way round at RKTP, 4.2 km to 7.5 km). It must meet another runway's pavement before the destination's own (sampled along each edge: a crossing is often one edge with no node on the runway) and within `OTHER_RUNWAY_MAX_WALK_M` (400 m, the figure measured for `RUNWAY_REACH_MAX_WALK_M`) of the far end. Without the 400 m bound a way on that crosses another runway only far on, after wandering once its way back is closed, is taken; `A_last_taxiway_whose_way_on_crosses_another_runway_once_but_far_on_still_ends_the_route` pins the bound (the PHNL-shaped case in `TaxiRouterCrossingClearanceTests` pins the "met twice" refusal of (1) below, which refuses it first). No way on, or one that meets no other runway, keeps the terminus and `RunwayReachGate`'s warning.
- Four more gates, each pinned in `TaxiRouterCrossingClearanceTests` (PR #367 review). (1) The way on is refused when the last leg and the way on together meet one other runway TWICE (`RunwaysMet`): a stub to another runway's hold with the destination on the near side goes over that runway and back at the next link on all new ground, and the hold is metres from the pavement, so the 400 m bound never sees it. (2) A last taxiway that keeps its NAME over the other runway has its far end already on the other side, so the way on meets no other runway: it is accepted when the last leg itself crossed one within the same 400 m of its far end. (3) A destination node on two runways' pavement counts BOTH as the destination's; the router is not told which was selected, and taking the first listed could drop an EIDW-shaped terminus. (4) A lone cleared taxiway is judged from its junction even when the aircraft is already on it past that junction; when the way on is ACCEPTED the route is driven from the aircraft, never back down the taxiway (when it is refused the plain route stands, and that one does run back to the junction), and its far end is picked by `FarEndOfLastTaxiway` in every branch, never the farthest node alone (a link whose name also runs to the apron was driven down that arm). `OTHER_RUNWAY_MAX_WALK_M` and `RUNWAY_REACH_MAX_WALK_M` both read `RunwayReachGate.MaxWalkMeters`; every refusal writes its reason to taxi_router.log.
- A lone cleared taxiway JOINED SHORT of the node the way on leaves it by is driven on over the runway too, when the runway it leads over is one the way on crosses as well, elsewhere (`LeadsOverARunwayTheWayOnCrosses`). Found live at OMDB on 2026-11-24: the online names carry K4 south of K down to the apron taxiway Z (15 nodes carry the name; navdata's own names give it 9, from K north), so the route joins K4 at Z and drives it up to K. K is still K4's node nearest the destination, the entry is no longer the node it leaves by, and the route read "via K4, then K, K9 ... crossing runway 12R at K9". The same clearance had crossed at K4 an hour earlier with other names loaded, and did so with navdata's names alone. The gate is the shared runway, not the way on alone: a taxiway left for a way on that crosses nothing of its own keeps its route even when a way round from its far end exists (pinned by `A_single_cleared_taxiway_left_for_a_way_on_over_no_runway_of_its_own_keeps_its_route`, where the onward-leg test alone would accept). Never when the taxiway going on would reuse a node already driven.
- Five more, from the review of 2026-11-25, each pinned in `TaxiRouterCrossingClearanceTests` by the test named. (5) Every runway that is not the destination's must be CROSSED, and the destination's own met once, judged by `RunwayRouteClassifier.ClassifyAll` on the last leg and the way on: `RunwaysMet` merges one continuous stretch of pavement into one meeting, so a way on that goes onto another runway and leaves it on the same side was a single meeting inside the bound and was taken (`A_last_taxiway_whose_way_on_goes_onto_another_runway_and_back_off_the_same_side_ends_the_route`). (6) `OnwardLegKeepsTheRouteShort`, at all three call sites: the route the way on makes is at most `REPEAT_HONOUR_MAX_RATIO` times the plain one (`PlainWayOn`) plus `REPEAT_HONOUR_MAX_PAD_M`. It also refuses a route that makes a runway ENTRY the plain one does not (a leg that starts on a runway's pavement shows `OnwardLegOverAnotherRunway` no passage there; over the whole route it is one: OMDB "N5" to 12R, LEBL "UB" to 24R). The length limit is what refuses a lone taxiway driven past its best exit to a much longer crossing (6.2 km for 2.8) and a lone taxiway the aircraft is on driven AWAY from its exit (4.7 km for 2.8): the router is not told which way the aircraft faces, so nothing else can (`A_single_cleared_taxiway_is_not_driven_past_its_exit_to_a_much_longer_crossing`, `A_single_cleared_taxiway_the_aircraft_is_on_is_not_driven_away_from_its_exit`). (7) A lone taxiway joined BEYOND the node the way on leaves it by (a fillet meeting its line past the junction) is cut where the route first touches the leg to the far end and driven on from there; it used to be driven back down to the junction and then left, because the leg reused ground (OMDB "K4" from the west apron on navdata's own names; `A_single_cleared_taxiway_joined_beyond_its_junction_is_driven_on_over_the_runway`). (8) A destination node on a centreline up to `DESTINATION_BEYOND_END_M` (100 m, [STR-20]'s figure) past the runway's recorded end is that runway's (`A_destination_on_the_centreline_just_past_the_runways_recorded_end_is_still_that_runways`). (9) The 400 m bound has its own test since then: a way on that crosses the other runway once, 440 m on, inside the length limit (`A_last_taxiway_whose_way_on_crosses_another_runway_once_but_far_on_still_ends_the_route`; the PHNL-shaped test was refused by "met twice" first and passed with the bound removed). Rule (3) alone is pinned by `A_destination_on_two_runways_still_lets_a_last_taxiway_over_another_runway_go_on`: counting one of the two runways only, the other is one the route ends on, an entry, and the classifier keeps the terminus. `A_way_on_that_first_meets_a_second_runway_the_destination_node_is_on_ends_the_route` pins an outcome the classifier also gives, so it passes without rule (3). (10) A leg to the far end that passes a node TWICE is not driven on (`PassesANodeTwice`): `AStarSearchWithGapChaining` can bridge a gap in a taxiway through nodes it then comes back to (LEMD "LA": LA, A13, LA, M13, LB, LA). Every refusal, in every branch, writes a line naming the taxiway and the case. Measured (lone-clearance sweep, 2026-11-25: every named taxiway as a single cleared taxiway from three stands to every runway end, the 100 airports with the most taxi paths in the fs2024 navdata, 95 with stands, 106,297 routes, plain navdata): the PR as first written changed 1,840 routes against main; these fixes put 725 back (they were longer by a median of 703 m and up to 7,473 m, 217 past the length limit, 349 with a runway entry main's route does not make), changed 569 more (the joined-beyond-the-junction case: 425 longer by a median of 198 m and at most 1,609 m, 143 shorter) and kept 1,115. Against main the result is 1,684 routes at 60 airports: all reach the destination, none is past the limit, none passes a node twice where main's did not (586 of main's that did no longer do), none makes a runway entry main's does not (39 make one fewer), and the crossings are 118 more, 52 fewer, 1,514 the same. The entry rule in (6) and rule (10) were found by this sweep (KMSP "W" to 22, LEMD "LA"); each now has a test that fails with that gate alone removed: `A_way_on_whose_route_goes_onto_a_runway_and_back_off_the_same_side_ends_the_route` (the last leg starts on the pavement of the runway the route came onto, and leaves it on that side) and `A_single_cleared_taxiway_whose_leg_is_gap_chained_through_a_node_twice_is_not_driven_on`.
- Three more, from the review of 2026-11-26, each pinned by a test that fails with that change alone undone. (11) The runway a last taxiway leads over must be one the path CROSSES or stands on at a node and leaves (`GoesOver` in `OnwardLegOverAnotherRunway`), for the leg's own crossing and for the first runway the way on meets alike. `RunwaysMet` also sees pavement the path never stands on or crosses (an edge cutting a corner with both ends clear of it on one side, a path that changes side only beyond the runway's end); the classifier gives those no passage, and (5) never refused them (`A_last_taxiway_whose_way_on_only_clips_a_corner_of_another_runway_ends_the_route`). A leg that STARTS on a runway's pavement and leaves it is one that goes over it, though the classifier gives a path starting on a runway no passage either (EBBR "B8, B9", EDDF "L3"; `A_last_taxiway_that_starts_on_another_runway_and_leaves_its_far_side_goes_on`): requiring a classifier crossing alone refused 616 onward legs on the fs2024 navdata, nearly all of that shape. (12) `FarEndOfLastTaxiway`'s nearest-to-the-destination pick skips the end of a fillet beside the junction: a node within `FILLET_END_MAX_M` (150 m) of the entry where the taxiway's name ENDS (one edge of it) on another taxiway the entry is on. Taking it ended a lone "R1" routed from the R/R1 junction 56 m along R1, never driven (`A_lone_taxiway_routed_from_its_own_junction_is_driven_to_its_far_end_not_to_a_fillet_beside_it`). The skip is bounded three ways, each measured on the fs2024 navdata and pinned by a test: a node the taxiway runs on through is no fillet (LFPG "B" at QB9, KORD "A" at G2; `A_node_a_lone_taxiway_runs_on_through_is_no_fillet_and_stays_its_far_end`); a node farther than 150 m is the taxiway's real far end (WSSS "D5"; `A_taxiways_end_on_the_junctions_taxiway_far_from_the_junction_is_its_real_far_end`); and when the skip would leave a far end more than `FILLET_SKIP_MAX_FAR_END_M` (1 km) from the entry, the fillet pick stands, since the taxiway is a long one and its farthest node the far side of the field (OMDB "M" from M4, 4.6 km; `A_fillet_beside_the_junction_of_a_long_taxiway_stays_its_far_end`). ## RTE-18

- The post-recalc sanity gate needs BOTH the length-blowup indicator AND the backwards-bearing indicator, OR'd (not AND'd) — either alone misses real dead-end-backtrack recalcs. One exception: a recalculation in which a Turn pick was missed (the aircraft left the route in the turn, not by a corner cut onto the picked taxiway) waives the backwards-bearing indicator only, because the route being replaced is one the pilot has already left at the turn; the length indicator still rejects. Without a pick in play the gate is unchanged. See [TURN-3](taxi-turn-picks.md#turn-3). → [taxi-guidance.md](../taxi-guidance.md)

## RTE-19

- The initial-load sanity advisory must compare against the PRE-truncation `fullRouteMeters`, not the truncated total — truncation can hide a genuine backtrack detour (EHAM 18L case). → [taxi-guidance.md](../taxi-guidance.md)

## RTE-20

- `TryRecalculateRoute` must fall back to shortest path (never the full original clearance sequence) when the aircraft isn't near any sequence taxiway — reapplying the full sequence routes the pilot backwards through the whole clearance. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-21

- `TaxiAssistForm.OnCalculateClicked` must refresh the aircraft position from `LastKnownPosition` immediately before building the route, or the route starts from a stale pre-pushback position and off-routes on frame one. → [taxi-guidance.md](../taxi-guidance.md)

## RTE-22

- No-op recalc suppression: a recalculated route identical to the current remaining sequence must skip the "Route changed" callout, latch resets, and tone re-slew entirely — otherwise a sharp corner-cut trips a spurious "Route changed" on an unchanged route (LFPG case). One exception: a recalculation in which a Turn pick was missed, or a pick still ahead is not kept, is never discarded as a no-op, because the route being replaced is wrong in a way its taxiway names cannot show; a corner cut onto the picked taxiway counts as the turn made (`TurnPickCarryOver.MadeByCut`), so it stays a no-op. See [TURN-3](taxi-turn-picks.md#turn-3). → [taxi-guidance.md](../taxi-guidance.md)

## RTE-23

- Do NOT remove the first-taxiway pre-snap — it's the LEPA anchoring fix; the pavement lead-in only replaces it when the first cleared taxiway is far (>75 m from the aircraft). → [taxi-guidance.md](../taxi-guidance.md)

## RTE-24

- `FindRunwayBridge`'s cap (`MAX_BRIDGE_METERS`, 400 m) must not be dropped, and a bridge must never again be scored by its gap alone: candidates are scored by total route cost (the cost to the exit on the current taxiway, plus the gap, plus the cost from the entry on the next taxiway to the destination), and the cap still prevents a silent half-airport jump when an ATC clearance is genuinely wrong (those must fall back to shortest path with a log line). The cap was 200 m until #76 raised it with that scoring: at KDEN BN→G the right handoff is about 330 m from G, while the nearest BN node (73 m) needed a 600 m loop to reach. → [taxi-guidance.md](../taxi-guidance.md)

Corrected 2026-10-08: the rule said the 200 m cap must not be raised; #76 raised it to 400 m and added total-cost scoring, and the doc comment above `FindRunwayBridge` still said 200 m until this date. Evidence: `TaxiRouter.FindRunwayBridge` (`MAX_BRIDGE_METERS = 400.0`), commit `5aff86be`.

## RTE-25

- One taxiway has ONE spelling: `TaxiGraph.BuildCanonicalTaxiwayNames` folds every case variant onto a single spelling as names enter `Build` — PROVENANCE first (a spelling with a navdata row behind it beats one with none, however many online rows carry the latter: `TaxiPath.NameFromOnlineSource`, set at the one place `AugmentingAirportDataProvider.ApplyMergedNames` adopts an online name), then THE SPELLING THE DATA MOSTLY USES, then ordinally smallest. Without the provenance step a taxiway navdata names on two segments and OSM/apt.dat fills on three loses 3-2 and the whole taxiway takes the online spelling — undoing "navdata is AUTHORITATIVE" one layer above the merger that enforces it. Ordinal-smallest ALONE was tried and is wrong — uppercase sorts first at the first differing letter, so ONE stray `LINK 5` row renamed every `Link 5` segment at the airport, and `TaxiwayName` is SPOKEN VERBATIM, so a screen reader then reads it letter by letter; `docs/taxi-guidance.md` states the rule that breaks ("The stored name is always the original human-readable form from the authoritative source"). A row `Build` DISCARDS gets no vote (zero-length rows are skipped only AFTER the fold runs, so one could otherwise decide the spelling while contributing no node and no edge) but still MAPS, so whatever `Build` does with it lands on the same spelling. This does NOT only arise where an airport's own data is inconsistently cased: the list reaching `Build` is the AUGMENTED one, so an un-normalised OSM/apt.dat name competes here with a navdata one — the provenance step is what keeps navdata winning, whatever the count. Every consumer that COMPARES `TaxiwayName` does so `OrdinalIgnoreCase`, which is what makes folding safe — that is not a class invariant, this file's own edge dedups and `SayIntentionsTaxiPathSnapper` compare ordinally, and the fold is what makes THOSE safe. → [sayintentions.md](../sayintentions.md)

Corrected 2026-10-08: removed the clause that credited the vote with keeping navdata winning and said this code could not tell a row's provenance, written before the provenance step existed. Evidence: `TaxiGraph.BuildCanonicalTaxiwayNames`, which weighs `TaxiPath.NameFromOnlineSource` before the vote.

## RTE-26

- `RouteReachability` in `LoadRoute`/`TryRecalculateRoute` classifies where the aircraft is before a route is adopted. When the aircraft is not on the destination's piece of network, the route still starts on the destination's piece and its straight unmapped first leg is checked: refused, naming the runway, when that leg touches a runway (LFBP Parking 40 from N3), otherwise spoken as a warning ("X isn't connected to the taxiway network you're on. The first N metres of the route aren't mapped." for a destination off the network, "Your position isn't connected…" when leaving an unconnected position). A destination off the network with no start node in range, or with no buildable route, is refused by name, never with the old "Could not find a nearby taxiway node."
