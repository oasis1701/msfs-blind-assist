# First Officer automation — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/first-officer-automation.md`, which Claude Code loads when it reads matching code. Background: [first-officer.md](../first-officer.md).
These rules moved here, with their IDs and texts, from `first-officer.md` on 2026-10-18, when that rule file reached its 8,000-character budget: the automation that runs beside the flows and checklists (auto-flaps, the auto-autopilot, the 10,000 ft lights, the transition altimeters). A trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below" or "above" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## FO-15

- PMDG auto-flaps was REMOVED (2026-07-08, user decision) — never reintroduce a 737/777 flap schedule; the "Auto-manage flaps" setting acts on the FBW A380 and A32NX only (Fenix stores-but-ignores it, the PMDG managers now do the same). → [first-officer.md](../first-officer.md)

## FO-16

- The FO AP engagement height is the user setting `FOAutoApEngageAltitudeAgl` (default 350 ft AGL, one global value) — never hardcode an engagement altitude in a `FOAutoManager`; the 737's LNAV/VNAV push height (400 ft AGL) is deliberately FIXED and each push is annunciator-guarded (NaN = skip). → [first-officer.md](../first-officer.md)

## FO-17

- Auto-AP-engage is floored by `IAircraftDefinition.MinimumAutopilotEngageAltitudeAgl` (**PMDG 737 = 400 ft** — its AFDS INHIBITS CMD below 400 ft RA after takeoff; 777 = 200) — never let the user setting press below an aircraft's own engage limit, and never lower the 737's floor: at ~1 Hz the old 350 ft default landed in [350, 400) on every takeoff, so the press was silently rejected while the app announced success. → [first-officer.md](../first-officer.md)

## FO-18

- Auto-AP-engage is CLOSED-LOOP wherever `IAircraftDefinition.IsAutopilotEngaged` returns non-null: announce only on a CONFIRMED engagement, retry a rejected press (bounded, `MaxApEngageAttempts`), and report a Captain action if it never takes — never re-add the announce-on-press + one-shot latch (a blind pilot was told "Autopilot engaged" with the AP off and no retry ever came). `IsAutopilotEngaged` must return **null**, never false, before the first CDA snapshot — the PMDG engage switches are TOGGLES and a guessed false would disconnect an engaged AP on retry. → [first-officer.md](../first-officer.md)

  **Per aircraft (2026-10-09, [FO-21]).** How often the service presses, and what it does on a null, is set by the definition. `IAircraftDefinition.AutopilotEngageRetryIntervalMs` is the least time between attempts: 0, a retry on every tick, is the default and what the PMDG jets, the iFly and the MD-11 keep; the FlyByWire family sets 3000. `AutopilotEngageWaitsForState` says what a null reading means to the service. False, the default, treats it as no readback: one open-loop press, announced on the press, whether the aircraft really exposes no engaged state (the Fenix, the HS787) or only has no data yet (the PMDG jets, the iFly, the MD-11). True, on the FlyByWire family, treats it as "not read yet": the service never presses on it, because the AP 1 push is a toggle too, and waits for a definite reading. Its give-up then says "Autopilot state unknown. Captain action required: check the autopilot." when it never pressed or the latest reading is null again, and "Autopilot did not engage. Captain action required: engage the autopilot." when it pressed and the autopilot reads off. Both settings are pushed from the current definition every second and on every aircraft switch. On every aircraft the confirmation ("{height} feet. Autopilot engaged.") is spoken without interrupting, so it queues behind the aircraft's own call; the gear calls and the two Captain calls interrupt (FO-21).

## FO-19

- The 10 k landing-light switching is gated by `FOAutoLights10kEnabled` (default ON) and ONLY the light actions/announcements are gated — the crossing latch always runs, and the light setting never gates the transition altimeters, which have their own setting since 2026-10-16 ([FO-23]). The checklist tree must NEVER use `TreeView.CheckBoxes = true` — a TVS_CHECKBOXES tree announces every selected/expanded-once header as "check box" in NVDA regardless of hidden state images (2026-07-16 fix); checkboxes come from `CheckboxStateImages` + per-node `ShowCheckBox`/`HideCheckBox`, and `.Checked` must never be set programmatically on headers/separators. → [first-officer.md](../first-officer.md)

  **The checklist-tree sentence (2026-10-18).** It left the rule line when FO-19 moved here: it guards the First Officer window, not the lights, and [CORE-18], which loads on every file, states it (never `TreeView.CheckBoxes = true` on a tree mixing checkable items with plain headers; `NativeAccessibleTreeView.CheckboxStateImages` + `ShowCheckBox(node)`). The history above stays.

## FO-21

- The FlyByWire family's universal auto-autopilot (FBW A32NX, FBW A380X, and the Headwind A330, which inherits the A32NX definition) presses the cockpit's AP 1 pushbutton, `A32NX.FCU_AP_1_PUSH` — the event the AP 1 button and the ToggleAutopilot1 hotkey already send — through `Aircraft/FbwAutopilotEngage`, never the stock `AUTOPILOT_ON`. FlyByWire captures and masks `AUTOPILOT_ON` and sets `simInputAutopilot.AP_engage = 1`, a flag nothing has read since FBW #7587 on the A32NX (2024-11-15; the last reader, `AP_ENGAGE_push`, is at [FlyByWireInterface.cpp L1854 @ 84888a77](https://github.com/flybywiresim/aircraft/blob/84888a77b229b29f7b10d575f8bf8eaf15244cd7/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L1854)) and FBW #10855 on the A380X. Checked at the owner's build, FBW master 255546cb: the A32NX handler [SimConnectInterface.cpp L1739-1743](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/interface/SimConnectInterface.cpp#L1739-L1743), the `AP_1_push` reader [FlyByWireInterface.cpp L1742-1743](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L1742-L1743); the A380X and Headwind's A339X (382bacbd) have the same shape. FlyByWire's own flight-deck API docs still list `AUTOPILOT_ON` ("1st call AP1, 2nd call AP2"); their code no longer does that, so never take the docs as the reason to send it. Until 2026-10-09 the app sent `AUTOPILOT_ON` (commit 0d5ed829 of 2026-07-12 moved the engage out of the FBW First Officer managers' `EngageAp1`), and with `IsAutopilotEngaged` null it announced "350 feet. Autopilot engaged." on the press while the autopilot stayed off: FO-18's failure exactly. The pilot hears the aircraft's own "Autopilot 1 on", then the service's "{height} feet. Autopilot engaged." (owner's choice, 2026-10-09; neither is suppressed). The service speaks that confirmation WITHOUT interrupting (a delegate of its own, wired to the non-interrupting `Announce`; FO-4 makes the same choice for "flow complete" and for the same reason): the aircraft's call arrives with the 1 Hz batch and the confirmation 0-1 s later, and an interrupting one cut "Autopilot 1 on" off mid-word. So it now queues behind the aircraft's call. This changes the timing, not the text, for every aircraft that uses the universal auto-engage, the open-loop press on a null readback included. The gear calls and the two Captain calls still interrupt. Like any non-interrupting announcement the confirmation is dropped while `announcer.Suppressed` is on (the five-second first-detect grace after an A380 detect or switch); the Captain calls are not.

  **The push is a TOGGLE, and four mechanisms exist because of it.**

  **1. Only on a definite OFF (`FbwAutopilotEngage.PressFor`).** `IsEngaged` is true when `A32NX_AUTOPILOT_1_ACTIVE` or `_2_ACTIVE` reads above 0.5, false only when both are read and off, and null while either is unread or NaN (FO-18: never a guessed false). `PressFor` returns the push for false only: an engaged autopilot is never pressed (the push would disconnect it), and neither is one whose state is unknown.

  **2. Never blind (`AutopilotEngageWaitsForState`, `UniversalAutomationService.WaitForApState`).** On the FBW family a null state means "not read yet": the AP variables reach the cache with the 1 Hz batch, while the service's altitude, vertical speed and height above ground come from separate requests, so after an app restart, or an aircraft detected mid-climb with the autopilot already on, the first tick can come before the AP variables are read. A press then would switch the autopilot off while the service said "Autopilot engaged". So where the definition sets the flag (the A32NX, the A380X and, by inheritance, the A330), the service never presses on a null: it spends an attempt waiting, spaced like a press, and looks again. If no reading comes within the five attempts it speaks "Autopilot state unknown. Captain action required: check the autopilot." (it pressed nothing and the autopilot may well be on, so it does not tell the Captain to engage it). The give-up follows the LATEST reading, not only whether the service pressed: a leg that pressed but whose latest reading is null again (a SimConnect disconnect clears the cache, and only `SwitchAircraft` resets the service) speaks the same "state unknown" line, because the autopilot may already be on and "engage the autopilot" would disconnect it. A leg that pressed and reads the autopilot off at the give-up speaks "Autopilot did not engage. Captain action required: engage the autopilot." Every other aircraft keeps `false`, where a null takes the open-loop press and announce; its give-up is unchanged, since it is reached only after the engage was invoked and so always says "did not engage". "Autopilot engaged" is spoken only for an engage the service itself invoked (`_apPressed`, cleared by `Reset()` and on touchdown), so a leg that only waited and then finds the autopilot on stays silent: the pilot, or the app's restart, had it on already.

  **3. Never into the probe queue (`PressWouldWait`; the A32NX and A330 only).** `A32NX.FCU_AP_1_PUSH` is a dotted event there, and `SimConnectManager.SendEvent` holds a dotted event in its queue while the MobiFlight bridge object exists and the calc-path probe has neither verified nor concluded ([SIM-13]). The bridge object exists on every connection, with or without the WASM module, so with no module the probe runs its full ~60 s (40 attempts, 1.5 s apart) before it concludes. The queue is sent in one loop when the probe ends (`FlushPendingCalcEvents`). Queued retries would NOT toggle AP 1 on and off again: FlyByWire resets its autopilot inputs at the start of each update ([FlyByWireInterface.cpp L923](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L923)) and drains every pending event in it (`readData()` at [L936](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L936), whose loop is [SimConnectInterface.cpp L1052](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/interface/SimConnectInterface.cpp#L1052)), and the `A32NX.FCU_AP_1_PUSH` handler only sets the flag `AP_1_push = 1` ([L1775-1777](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/interface/SimConnectInterface.cpp#L1775-L1777), reset at L1176), so pushes that land in one update count as a single press. The real reason for the guard is the late push: one push that arrives up to a minute after it was queued, after the service has given up and told the Captain to engage the autopilot, can switch off the autopilot the Captain engaged since. So `PressFor` sends nothing while both autopilots read off and `PressWouldWait(CanExecuteCalculatorCode, CalcPathVerified, CalcPathProbeConcluded)` is true. A withheld press still uses up one of the five attempts, so a leg whose attempts all fall inside the probe window ends with its Captain call at about 15 s and nothing auto-engages, which is the safe side. That window is the ~60 s after a load or an aircraft switch with no module (with a working module it ends when the probe verifies). Once the probe has concluded, the legacy transport sends the push normally (`SimConnectManager.SendEvent`, the fall-through after the dotted branch), so every later leg auto-engages as usual even with no module. The A380 passes no `pressWouldWait`: its `A32NX.FCU_*` events never wait on the probe ([SIM-10]).

  **4. Three seconds apart (`AutopilotEngageRetryIntervalMs` = `FbwAutopilotEngage.RetryIntervalMs` = 3000).** It spaces the presses, the waits and the give-up alike: the engaged state reaches the cache with the 1 Hz batch, so a retry on the next tick could land on an autopilot the first press had already engaged and switch it off. `MaxApEngageAttempts` stays 5, waits included: attempts at 0, 3, 6, 9 and 12 s, the give-up call at 15 s. Every other aircraft keeps 0, a retry on every tick as before.

  **The limits follow the aircraft.** `MainForm.PushUniversalAircraftLimits` (in `MainForm.UniversalAutomation.cs`, the one MainForm partial `first-officer-automation.md` globs; `first-officer.md` until 2026-10-18) pushes the engage floor ([FO-17]), the interval and `WaitForApState` from the current definition every second and from `SwitchAircraft` right after `universalAutomation?.Reset()`: an `Update` between a switch and the next tick would otherwise act on the previous aircraft's values, for example an open-loop press on an FBW aircraft while the flag was still off.

  **Also seen on, not changed here.** The PMDG 737 and 777 and the iFly 737 return null until their data is ready and keep the open-loop path (one invoke, announced on it), so a restart mid-climb with the autopilot already on is a blind toggle there: the 737 and 777 guards read an annunciator that is 0.0 before the data is ready, and the iFly's guard stops only on a definite true. The TFDi MD-11's engage presses only on a definitely-off `MD11_AP_STATE`, so on an unread state it presses nothing while the service still announces "Autopilot engaged". All of it is left for a separate change, and there is no issue for it yet: name it here when one is filed.

  **Checked against the source, not yet in the sim.** The FlyByWire and Headwind code above was read at the commits named; the update-loop lines in mechanism 3 (the input reset, the drain and the flag handler) were read for the A32NX at the owner's build 255546cb on 2026-10-10, and not for the A339X. The send path (`EngageAutopilot` to `SendEvent`) and the MainForm push cannot be unit-tested ([CORE-5]); the in-sim check owed is one flight per aircraft: take off with "Engage autopilot" on and expect "Autopilot 1 on", then "350 feet. Autopilot engaged.", both heard in full (the second must not cut the first off), with AP 1 flying and no second press. Pinned by `FbwAutopilotEngageTests` (the helper, including `PressWouldWait` and the hold-back it drives; each definition's interval, wait flag and engaged-state read; every other aircraft unchanged. Whether each `EngageAutopilot` passes `PressWouldWait` in is NOT pinned) and `UniversalAutomationServiceTests` (the interval, the wait, both give-up lines and what decides them, `_apPressed`, the separate confirmation delegate). The engage is diagnosable from debug.log: `Automation` lines for each wait on an unknown state (one per attempt), each press held back for the probe queue, and each give-up with the line it said and why; a press that goes out is already logged by `SendEvent` ("Sending event: A32NX.FCU_AP_1_PUSH"). → [first-officer.md](../first-officer.md)

## FO-23

- The pilot's "Automatically set altimeters at transition altitude and level" checkbox (Settings, First Officer tab; `UserSettings.FOAutoAltimetersEnabled`, default ON so nothing changed for anyone who never touches it; owner request 2026-10-16: "an option for users if they want it turned off") gates every altimeter write the phase monitors make at a transition crossing, on all eight aircraft. `FirstOfficerForm` copies it into `IFoPhaseMonitor.AutoAltimetersEnabled` at construction and in `ApplySettings`, so a change takes effect on OK, mid-flight included.

  **Off means reminded, not silent.** A screen-reader pilot has no other cue that the transition has come, so each crossing is still spoken, through the shared pure helper `TransitionAltimeters.ReminderInstead`: "Transition altitude. Set standard altimeters." climbing, "Transition level. Set local altimeter pressure now." descending (the sentence the PMDG 737, iFly 737 and MD-11 already spoke at the transition level, where they are announce-only either way). The 18,000 ft no-plan reminder (`TransitionAltimeters.NoTransitionLoadedReminder`) drops its "Load SimBrief … for automatic altimeter changes" sentence while the setting is off, since a plan would change nothing.

  **Only the altimeters are gated.** The MD-11's transition-altitude Dial-A-Flap 15 still goes in, and its sentence becomes the existing `TransitionAltitudeSentence(false, daf)` ("Transition altitude. Dial-A-Flap 15. Set standard altimeters."). `TransitionCrossingDetector.Update` runs every sample whatever the setting, so its arming latches keep tracking and turning the setting back on mid-flight never acts on a crossing already passed (the same reason the 10 k light latch tracks under [FO-19]).

  **Pinned by `TransitionAltimetersTests`:** the default, both reminders, no reminder with the setting on or with no crossing, both no-plan sentences, the MD-11's transition-level sentence equal to the reminder, and a source scan that every `IFoPhaseMonitor` implementation (eight, counted by reflection) reads the setting at its crossings and routes the no-plan reminder through the helper. Not unit-tested: the form and Settings-panel wiring and the monitors themselves (they need a `ScreenReaderAnnouncer`, CORE-5); the in-sim check is a climb and a descent through SimBrief's transition altitude and level with the setting off, hearing the reminders and finding the altimeters untouched. → [first-officer.md](../first-officer.md)
