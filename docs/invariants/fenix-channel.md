# Fenix display channel rules — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/fenix-channel.md`, which Claude Code loads when it reads the channel's code: the `FenixChannel*` services, the Fenix definition's display channel partial (`FenixA320Definition.DisplayChannel.cs`) and their tests. The data-service rules are in [fenix-data.md](fenix-data.md), which loads on this code too; its [FNX-3] records the decision to read this channel. Background: [a32nx.md](../a32nx.md).

## FNX-21

- The display channel is the Fenix's own local gRPC service on 127.0.0.1:18083, the feed its displays are drawn from (HTTP/2 without TLS; the contract is protobuf-net "code first", so there is no .proto file). `FenixChannelClient` opens only the two calls `FenixChannelCall` has: `DisplayData` (`/ProsimRemoting.GrpcAircraftDataSource/Subscribe`, a stream of display pushes, about 17 a second) and `EcamEntries` (`/ProsimRemoting.GrpcSdk/SubscribeEcamEntries`, a stream sent when the ECAM list changes). `FenixChannelFields.PathOf` gives the path of each and throws for any other value, and no API of the client takes a path, so a third call is a decision, never an edit: it needs a new enum member, and `FenixChannelReadOnlyTests` fails at that first. The address is the numeric 127.0.0.1, never `localhost`, as [A320-40] has it for 8083.
- The service has other calls that write a value, run an action or hand out a credential, and the client never makes one: WriteDataRef, SetSetting, SetDefault, SaveManualFailure, StartRefueling, StopRefueling, StartGsxServices, StopGsxServices, DisconnectNavigraph, GetNavigraphAccessToken and DoRpc. The rule is the two paths, not this list, which is only the calls the design names. The channel client makes none of these gRPC calls, and the names are plain words here and in the rule line because the scan below looks for a call path, never a bare name. Two of the names, SetSetting and SetDefault, exist in the app only as the 8083 data service's GraphQL settings operations (`FenixOptionEdits.SetSettingDocument` and `SetDefaultDocument`, which the Fenix options window sends; the documents window's pin write reuses the first), outside this channel. The 8083 gateway's two navigraph operations are never sent either ([FNX-3]).
- Fenix's own protections are never touched: its license and startup checks, its anti-debugging and its entitlement pipe. The channel answers any program on the same PC without a key (measured 2026-11-01), which is why it can be read at all; the decision to read it is [FNX-3]'s, and it covers the two read calls and nothing around them. The app never works around, imitates or probes one of those protections, and never tries to get past a refusal.
- A refusal ends the channel for the session: both calls, whichever of them was refused. grpc-status 7 (permission denied) or 16 (unauthenticated), or HTTP 401 or 403 (which gRPC maps to 16 and 7), whether it comes in the headers of an answer that carries no message or in the trailers behind the messages, makes `FenixChannelClient` report `Refused` once and stop that call's loop for good: no retry, no other path, no other way in. `FenixChannelMonitor` then ends the rest: it marks the channel refused, so every later callback of the client is ignored; it tells the gate the channel is not answering, with the refusal as the reason, so every display reads "channel not answering: <the refusal>" and keeps its AI read ([FNX-22]); it writes "<call>: refused (<reason>); stopped for this session" once; and it disposes the client, so the other call stops too and neither asks again. A key Fenix adds is Fenix's decision, and the app does not go around it. Other answers are not refusals: status 12 (the call is not offered, as after an update that changed the channel) logs one line and asks again every 30 s; any other status, a broken stream and a refused connection (the Fenix not running) reconnect after 3, 6 and 12 s and then every 30 s, quietly.
- The default handler (`FenixChannelClient.CreateDefaultHandler`) sets `AllowAutoRedirect = false`. A followed redirect could open a path `PathOf` never gave, so a 3xx answer is a failure like any other status that is not 200: the client reports "HTTP 307" and asks its own path again.
- Pinned by `FenixChannelReadOnlyTests` (`PathOf_gives_the_two_allowed_paths`; `There_are_exactly_two_calls_and_no_path_for_any_other_value`; `The_channel_is_addressed_by_its_numeric_address`; `Only_the_two_allowed_call_paths_exist_in_the_app`, a scan of every .cs file under `MSFSBlindAssist/` for a `/ProsimRemoting.<service>/<method>` path, in code or in a comment, which also requires `FenixChannelFields.cs` to be the only file that names the service), `FenixChannelClientTests` (`Status_16_stops_the_channel`; `An_http_refusal_stops_the_channel` for 401 and 403; `A_refusal_after_the_messages_ends_the_call_too` for 16 and 7 in the trailers; `The_default_handler_follows_no_redirect`; `A_redirect_is_not_followed_and_is_reported_as_an_http_status`) and `FenixChannelMonitorTests` (`A_refusal_of_the_data_call_stops_the_ecam_entries_call_too`; `A_refusal_of_the_ecam_entries_call_stops_the_data_call_too`; `After_a_refusal_every_callback_of_the_client_is_ignored`). A path assembled from pieces escapes the scan: `PathOf` throwing for any value but the two is the guard there. → [a32nx.md](../a32nx.md)

## FNX-22

- `FenixChannelTrust` is the gate: a pure state machine (the time passed in, no I/O) that answers, display by display (PFD, E/WD, SD), trusted or not with a reason. Its purpose is that a Fenix update can never make the app speak a wrong value, so in doubt a display is not trusted and its key falls back to the AI read. A display is trusted only when every channel-wide condition and every condition of its own holds, and `VerdictFor` gives the first one that fails, in this order, with this text:
  - not connected: "channel not answering", or "channel not answering: <the client's reason>";
  - no data message yet since the connection opened: "no data yet";
  - the stream stalled, no data message for more than `StreamStaleMs` (2,000 ms; the client itself drops a data call that is silent for 10 s and reconnects): "stream stalled";
  - the build unknown, the build query not yet answered on this connection: "build unknown";
  - the build not in `FenixChannelFields.VerifiedBuilds`, an exact match ([FNX-23]): "build <build> not checked";
  - a shape latch, below: "malformed message", "field <path> has the wrong shape", "malformed ECAM entries message" or "ECAM entries field <path> has the wrong shape";
  - the first of the display's own conditions: no powered display unit shows the display (Display live, below): "display off";
  - the display's cross-checks, in the order below, the first one that is not OK (latched, else disagreeing, else never passed): "<check> latched until reconnect: <pair>", "<check> disagrees: <pair>" or "<check> not checked yet";
  - the PFD only: the latest good frame has no FMA slot at all (Shapes, below): "no FMA";
  - an unknown text code in a line the display covers ([FNX-24]): "unknown code '<letter>' in the FMA", "… in the upper ECAM" or "… in the FOB line"; otherwise the reason is "trusted".
- What each display has. Each display's first condition of its own is that it is live. Then the PFD's checks are FD captain, FD first officer, altitude and heading, in that order, then that its frame has an FMA, and then the FMA's 16 texts; the E/WD's are fuel, and then the upper ECAM's left and right lines and the FOB line; the SD has none in this set, so being live is its one condition of its own. The check names are the ones in the texts above ("FD captain", "FD first officer", "altitude", "heading", "fuel"), and a pair reads "channel 1,023 ft, sim 2,050 ft".
- Display live. RemoteData field 12 (`FenixChannelFields.Remote.DuData`) is DUData { Power (1) repeated bool, Content (2) repeated DisplayTypeEnum, Brightness (3) repeated double }, one entry per display unit. DisplayTypeEnum, in the contract's order: PFDCapt 0, PFDFO 1, NDCapt 2, NDFO 3, ECAMUpper 4, ECAMLower 5, DiagonalLine 6, SelfTest 7, EcamOnND 8, DCDUCapt 9, DCDUFO 10, DCDUWaitingData 11, SelfTestDCDU 12, DraimsCapt 13, DraimsFo 14, DraimsOvhd 15. A display is live while a powered unit shows it: the PFD on a unit showing PFDCapt, the E/WD on ECAMUpper, the SD on ECAMLower (`FenixChannelFrame.PfdLive`, `EwdLive`, `SdLive`); the gate keeps the three from the latest frame with its shapes. A display shown only on another unit type (the PFD as PFDFO, an ECAM page as EcamOnND) counts as off: the conservative choice, which only falls back to the AI read (ruled 2026-11-02). Measured on 3.0.0.7613 at a gate at EDDF on 2026-11-02: the Fenix sends Power and Content unpacked, one varint per element; cold and dark, Power was false on all 11 units and Content DiagonalLine (6) on the six main units, then 9, 10, 13, 14, 15; powered, Power was true on all 11 and Content 0, 2, 3, 1, 4, 5, then 9, 10, 13, 14, 15. The decoder accepts protobuf's packed form of the two lists too, since it encodes the same contract; any other wire type is a wrong shape at "12.1" or "12.2", and field 12 itself not length-delimited is one at "12"; Brightness and unknown sub-fields are skipped. Power[i] pairs with Content[i] up to the shorter list, and any Power but 0 is on. No field 12, or no unit powered, leaves every display off, and is never a wrong shape. Why the condition exists: cold and dark the channel still sends the sim's altitude and heading, which agree with SimConnect, so the PFD and the SD read "trusted" with every display dark, and a read would have spoken what no display shows; and a RemoteData holding only fields the app does not read decodes to a frame of defaults, which read trusted on the SD, which has no cross-check, and on an E/WD whose fuel check had passed (its empty FOB text only waits). "display off" comes first among a display's own conditions; the cross-checks still run on every frame, so a disagreement or a latch built while a display was off shows as soon as it is live.
- Shapes. A malformed message, or a field in the wrong shape, in a data message or an ECAM entries message latches the whole channel until the next connection, and the first cause stays. On a checked build a wrong shape means the check itself cannot be trusted, so it takes down every display, the SD included, not only the one the field belongs to. An FMA of 1 to 15 or of 17 or more slots is such a wrong shape ("field 111 has the wrong shape"); an FMA with no slot at all is not: protobuf-net leaves out an empty or null array, so an unpowered PFD can send none, and a latch would cost every display for the session. The PFD alone reads "no FMA" instead, from the latest good frame, until a frame brings its 16 slots again; it never latches, and the E/WD and the SD keep their verdicts. The entries stream has texts of its own, so a fault in it is never taken for one in the display data. A frame that fails its shape check gives the gate no values: the latch holds every display already, and the defaults it carries would only disagree. That stream sends only when its list changes, so after each reconnect the monitor gives the gate the last entries message again: a wrong-shaped one that came before the reconnect is still the last thing the stream said, and the gate's fresh start would otherwise erase the latch. A push with no display data (`FenixChannelFrame.NoData`) is not a message to the gate: no shape check, no sign of life, no cross-check, and the monitor keeps the frame before it as the latest, so five seconds of them leave a trusted display "stream stalled" and never latched (the log still takes such a push as the call working).
- Cross-checks. Each compares a value of the channel with SimConnect's: the PFD's two flight director flags with the two FD lights, its altitude with the true altitude (PLANE ALTITUDE, never the indicated altitude: [FNX-25]) and its heading with the magnetic heading; the E/WD's FOB line with the total fuel. A check is one of three. Agree: both values present and within tolerance, and the check is marked passed for this connection. Waiting: a value is missing (SimConnect has not delivered it, an FD light reads neither 0 nor 1 or the annunciator light test is on, a channel value is not finite, or the FOB text is not a whole number of KG or LBS). Disagree: both present and outside tolerance. Waiting neither passes nor fails, and a display whose check has never passed is not trusted ("altitude not checked yet"): trust is earned by agreement, never by silence. A check that passed stays passed while its values wait, unless a disagreement is in force.
- The tolerances: altitude 100 ft; heading 3 degrees on the circle (359 and 1 are 2 apart); fuel 100 kg or 2 percent of SimConnect's value, whichever is larger, both sides in kilograms (SimConnect's pounds and a FOB read in LBS are converted); FD flags equal, compared only while the light reads exactly 0 or 1 and the annunciator light test is off. The FOB number is whole digits only (`FOB:\s*([0-9]+)\s*(KG|LBS)`, run over the line with its codes taken out, and read with `NumberParsing.TryParseExternal`, [CORE-17]): a grouped "12,340" or "12 340" reads as waiting, never as 12.34 kg. They are the design's starting values, and the in-sim measurements below changed none of them: a re-check never loosens a tolerance ([FNX-23]).
- Measured on 3.0.0.7613 at a gate at EDDF on 2026-11-02 (MSFS 2024), the questions the design left open:
  - The altitude field (197) is the true altitude and never moves with the baro: [FNX-25] has the figures, and why the check compares it with PLANE ALTITUDE.
  - The fuel: in a five-minute idle run (both engines and the APU running) the FOB line moved in 20 kg steps, from 2,980 to 2,900 kg, and stayed within 12 kg of the sim's total, about an eighth of the 100 kg tolerance; the line rounds (the sim read 2,998.0 kg while it read 3,000). An instant load of 2,100 kg through the EFB moved both sides within the same second, and nothing latched.
  - The heading: cold and dark, 155.5 against the sim's 155.8 degrees. Field 194.1 tracks the sim's magnetic heading from cold and dark on, and nothing in the channel moved through the ADIRS alignment.
  - The flight directors: the channel's FD flags follow the pushbuttons, also with no mode engaged (at power-up the FCU turned both on with every bar NaN, and the sim's lights followed within about a second); after a press the check agreed again within about a second, and FdInhibit and FdFlash never appeared. In the annunciator light test both FD lamps read exactly 1 with both flight directors off while the flags stayed off, and the FD captain check latched 3 s into the test: hence the light test below.
  - Cold and dark: the FMA is 16 empty slots (not zero slots), the FD bars are NaN and the FD flags absent (off), the FOB amount is amber crosses ("aXXX", so the fuel check waits), and fwcPhase 6 and fwcPage 12 are stale while the FWCs are unpowered. The altitude and the heading still track the sim's, which is why a display must be live (above).
- The annunciator light test. Its switch is `S_OH_IN_LT_ANN_LT` (0 Dim, 1 Bright, 2 Test). The test lights both FD lamps, which then read exactly 1 whatever the FD buttons say, while the channel's FD flags follow the buttons, so while the switch reads exactly 2 both FD checks wait (`FenixChannelMonitor.OnLightTestSwitch`, `FenixChannelTrust.OnLightTest`): the test's lamp is never a disagreement, a check that passed stays passed, and, as for any waiting value, a disagreement already in force stays in force and its hold clock restarts. Any other position, one the switch does not have included, is not the test, and no other check is touched. The flag is SimConnect's, so it outlasts a reconnect as SimConnect's values do. No grace period follows the test: the switch and the lamps ride the same 1 Hz batch, so they arrive together, and the 3 s hold absorbs a one-second lag (ruled 2026-11-02).
- A disagreement is judged in two steps. While it is pending its display is not trusted ("altitude disagrees: channel 1,023 ft, sim 2,050 ft"), so nothing is spoken from a value under doubt. It counts only after it has lasted `MismatchHoldMs` (3,000 ms) without a break; then the check latches ("altitude latched until reconnect: …") and the display stays untrusted until the channel reconnects. The reasoning for both: a comparison of two moving values is noisy, so one bad pair must not cost the display for the session, but nothing may be spoken from it while it stands; and a disagreement that lasted is evidence that the field no longer means what the app thinks, which a later agreement by chance must not undo, so it stands until the checks start again from scratch. Only an agreeing comparison ends a pending disagreement (the display reads trusted again), and only a reconnect clears a latch: it clears every latch and every passed mark, and since a real layout change fails again within seconds, and a display whose checks have not passed is not trusted anyway, there is no window in which unchecked data is trusted. A waiting value or a stall of the stream (a data message more than `StreamStaleMs` after the one before it) is a break in the run and nothing more: it restarts the hold clock, so an interrupted run never latches, and the display keeps reading "disagrees" until a message agrees (ruled in review, 2026-11-01). A latched check stays latched through a stall.
- Comparisons are time-aligned. SimConnect's continuous batch comes about once a second, so each SimConnect value is stamped when it arrives and compared with the channel's value from the data message nearest that arrival (the gate keeps each message's value for `ComparisonWindowMs`, 1,500 ms; on a tie the later message). A SimConnect value older than the window has not changed (an unchanged value is not delivered again) and is compared with the channel's value now. Without this, a standard-rate turn or a strong climb, which moves both values between the two readings, would read as a disagreement and latch the PFD for the session. Frames and SimConnect's values are stamped with one clock (`Environment.TickCount64`), and SimConnect's values survive a reconnect, since SimConnect goes on delivering through it.
- The gate's SimConnect inputs. The FD lights (`I_FCU_EFIS1_FD`, `I_FCU_EFIS2_FD`) are only peeked on their way to their own handling. The heading, the fuel and the altitude come through three keys of the channel's own, `FENIX_CHANNEL_HEADING` (degrees, [DCK-34]), `FENIX_CHANNEL_FUEL` (pounds) and `FENIX_CHANNEL_ALTITUDE` (PLANE ALTITUDE in feet, the true altitude, [FNX-25]), because the Fenix's own heading and fuel keys are on request and a background seam has no `SimConnectManager` to request them with; `INDICATED_ALTITUDE` no longer feeds the gate. A fourth key, `FENIX_CHANNEL_ANN_LT`, carries the annunciator light switch (the L:var `S_OH_IN_LT_ANN_LT`, whose Fenix key is on request too), which the definition hands to the monitor's `OnLightTestSwitch`. The four are continuous and announced only so they ride the 1 Hz batch, consumed silently, hidden from Ctrl+M ([VAR-9]), and the only batched key with their SimConnect name ([VAR-7]). They keep the default change tolerance ([SIM-7]): the gate treats the last value SimConnect delivered as the current one, so a wider tolerance would leave a slowly moving value undelivered, and the gate would read that stale value against the channel's live one, a false disagreement that latches.
- The monitor. `FenixChannelMonitor` owns one session of the channel: it runs both calls, decodes each message before taking its one lock and feeds the gate under it, keeps the latest frame (swapped in whole; cleared on each connection of the data call, and replaced only by a frame with data and every shape right, since the gate takes no values from the others), and asks the Fenix for its build through `FenixDataService.GetSoftwareVersionAsync` on each connection of the data call, again every 30 s until it answers. A build answer belongs to the connection that asked: after a newer connection, a disconnect or Dispose it is dropped and never reaches the gate. A reader takes `Snapshot`: a display's verdict and the latest frame, read under the one lock at the same instant. Nothing in it throws at a caller, speaks or touches a control, and a disposed monitor trusts nothing ("channel stopped").
- Nothing is spoken from an untrusted display. A display key reaches the channel only through `FenixChannelReads`: its table `All` lists the keys that have a channel read, and `Choose` answers the text to speak only when the table has a read for the key, the snapshot of the read's own display (taken once, for that display only) trusts it and holds a frame, and the read composes text from that frame that is not blank. Every other case, a read or a snapshot that throws included, answers null, which is the AI read the key had before. Today `All` is empty, so every display key keeps its AI read; a read joins it only by an edit there, with its own test and its own in-sim check. The verdict and the frame come from one snapshot (`FenixChannelMonitor.Snapshot`), taken at one locked instant, so the frame a read composes is the very frame the gate judged in giving that verdict: never a frame of an earlier connection, never a damaged one, never an older frame beside a verdict that turned trusted on a later one (an unknown code that went away, a disagreement that agreed again), and never a newer frame beside an older verdict. A fallback to the AI read always beats a possibly wrong exact value.
- The log is `fenix_channel.log` (`Log.Channel("fenix_channel")`, in `%APPDATA%\MSFSBlindAssist\logs`, [CORE-14], [CORE-15]). It holds: each call's connection changes ("display data: connected" is written with a connection's first message, not with the response headers, since a call that opens and says nothing is dropped and asked again; "ECAM entries: connected" with its headers; "not answering (<reason>)", written only when it differs from the last failure written since a message arrived; and "refused (<reason>); stopped for this session", written once, when a refusal of either call ends the channel, [FNX-21]); the build and whether it is checked ("build <build>: checked", or "build <build>: not checked; every display uses the AI read"); each change of a display's verdict with its reason ("PFD trusted", "E/WD not trusted: <reason>"; a change is the trusted flag or the headline of the reason, the text before its first colon, so the numbers of a disagreement moving every second are one line, and the first tick writes all three displays); the comparison pairs, one line every 30 s while the data call is connected ("comparisons: altitude: channel 1,023 ft, sim 1,020 ft; …", both values as they stand then, not time-aligned, in the invariant culture), which ends with SimConnect's deliveries since the line before ("SimConnect: 42 values, longest gap 1.1 s", from `FenixChannelTrust.DescribeSimDeliveries`, whose call starts the next period: every arrival of the five comparisons, and the longest interval between two arrivals in a row within that period, in the invariant culture; "1 value, no gap" or "0 values, no gap" with fewer than two; the gate treats an old SimConnect value as unchanged, so a long gap, a UI stall in a turn, could become a false latch, and a flight with turns reads the largest gap from these lines); "channel stopped" when the monitor is disposed (an aircraft switch or quit), always the last line; and each distinct problem once (a failing build query, a failing tick or build loop). Neither channel call carries a credential. The build query does pass one by: its answer is the 8083 data service's full settings answer, which holds the pilot's credentials ([FNX-19]), but `GetSoftwareVersionAsync` hands the monitor only the build string from it, and that string is all the monitor logs of it, so nothing in the log needs masking.
- Pinned by `FenixChannelTrustTests` (every reason text and the order of the channel-wide conditions, the shape latches and their texts, the hold, stall and waiting rules, the time alignment, each tolerance, the FD, heading and fuel checks, the FOB text and every logged number under de-DE and sv-SE, the unknown-code reasons, "no FMA" for the PFD alone and after its cross-checks; "display off" for each display cold and dark, before the display's other conditions and after the channel-wide ones, a latch built while dark showing once live (`A_dark_display_is_not_trusted`, `Display_off_comes_before_a_disagreement`, `A_frame_of_defaults_trusts_no_display`); the light test (`The_light_test_never_reads_as_an_fd_disagreement`, `After_the_light_test_a_real_fd_disagreement_still_latches`, `The_light_test_outlasts_a_reconnect`); the SimConnect deliveries with a fake clock and under de-DE and sv-SE), `FenixChannelDecoderTests` (`An_fma_without_sixteen_slots_is_a_wrong_shape`, `An_fma_with_no_slots_is_not_a_wrong_shape`; the display units as measured cold and powered, unpacked and packed, a wrong wire type, lists of two lengths and no field 12), `FenixChannelWireTests` (`IsAtEnd`, the end of a packed list), `FenixChannelMonitorTests` (frames fed to the gate, the latest frame cleared on each connection and never a damaged one, a snapshot's verdict and frame taken at one instant, the build asked on each connection and a stale answer dropped, the ECAM entries latch surviving a reconnect, the light switch at Test only, a push with the displays dark, each log line above with the deliveries ending the comparisons line) and `FenixChannelReadsTests` (the choice with a stand-in table and a stand-in snapshot, and that `All` is empty); `FenixChannelDefinitionTests` pins the four channel keys (the batch, Ctrl+M, the default tolerance, silent consumption). What the live channel gives the gate is not pinned: it is read from `fenix_channel.log` in the sim ([CORE-5]). → [a32nx.md](../a32nx.md)

## FNX-23

- Fenix ships its display program and its systems program together, so any Fenix update can renumber the channel's fields without breaking anything of Fenix's: the Fenix goes on working, and the app's reader would go on decoding numbers that now mean something else, and speak them. The cross-checks of [FNX-22] cover five values only, and the shape check catches a changed wire shape, not a field that moved to a number the app reads for something else. So the app trusts a display only on a build whose numbers a developer has compared with that build itself. `FenixChannelFields.VerifiedBuilds` is the list of those builds, spelled as `FenixDataService.GetSoftwareVersionAsync` gives them (for example "3.0.0.7613") and matched exactly, ordinal: "3.0.0.7613 " and "3.0.0.76130" are other builds.
- `VerifiedBuilds` is empty. No build has been confirmed in the sim yet, so on every build the gate says "build <build> not checked", the log says "build <build>: not checked; every display uses the AI read", and every display key keeps its AI read, which changes nothing a pilot hears.
- First checked build: none yet. It is committed to the set only when the owner confirms that the field numbers in `FenixChannelFields` were checked against that build with the local tools. The confirmation (the build, the date and who gave it) will be recorded here when it happens, in the same change that adds the build and replaces `FenixChannelReadOnlyTests.No_build_is_checked_before_someone_confirms_one` with a test that names it.
- The re-check, after a Fenix update that changes the build, in this order:
  - Compare every call path, field number and wire shape in `FenixChannelFields` against the installed build (the two call paths, each field the decoder reads with the shape it expects, and the FMA's 16 slots), using the team's local channel tools, and fix any number that moved in `FenixChannelFields` alone: no other file names a call path or a field number. The tools read Fenix's own program files and the live channel, so they and everything they produce (the decoded contract, captures, the field map) stay outside this repository and are never committed.
  - Add the build to `VerifiedBuilds` in the working copy only, build the app and run it in the sim. The in-sim check cannot be made before this: on a build outside the set the gate answers "build <build> not checked" for every display before it judges anything else, so the log shows no "trusted", no latch and no disagreement for it, and only the 30-second comparison pairs show anything of the checks.
  - Read `fenix_channel.log`: "build <build>: checked", the three displays "trusted" once they are powered and their checks pass ("display off" while dark), the comparison pairs agreeing, and nothing latched by an FD press or the annunciator light test.
  - Commit the addition only when all of that holds and the owner confirms. Otherwise take it out of the working copy again: the build stays on the AI read.
- Never commit a build on a version bump alone, and never loosen a check or a tolerance to make a build pass. A build that fails a check is the check doing its work. The nets are separate, and none is complete alone: the build check keeps every display of a build no developer has re-checked on the AI read; the shape check latches the channel when a field arrives in another wire shape; and the cross-checks catch, within seconds, a moved field among the five values they compare. A field that moved to another number of the same shape, outside those five, passes both the shape check and the cross-checks, and only the re-check finds it. Widening a tolerance, skipping a comparison or committing the build without the re-check takes one of the nets away, and the app would speak what a stale field number reads. A failing build stays on the AI read until its numbers are re-checked and fixed in `FenixChannelFields`. Changing a tolerance is its own decision, made with in-sim measurements, never part of the change that adds a build.
- Pinned by `FenixChannelReadOnlyTests.No_build_is_checked_before_someone_confirms_one` (the set is empty), `FenixChannelTrustTests` (`An_unchecked_build_is_not_trusted`, `A_build_must_match_a_checked_one_exactly`, `An_empty_checked_list_trusts_nothing`, and `The_channel_wide_reasons_come_in_the_order_of_the_table`, in which an unchecked build outranks the shape latch) and `FenixChannelMonitorTests.A_build_the_app_has_not_checked_is_logged_as_such`. That a developer really re-checked the numbers cannot be pinned: it is the owner's confirmation. → [a32nx.md](../a32nx.md)

## FNX-24

- The channel's text carries a lowercase letter before a run as a format code, and `FenixChannelText.Parse` turns one line into runs, each with its text, color, underline and size. The colors are `w` white, `g` green, `c` cyan, `a` amber and `r` red (seen on the channel, amber and red on 2026-11-02), and `m` magenta and `y` yellow (expected, not yet seen); all but red are the letters `FenixMcduFormat` also handles for the Fenix MCDU markup. `u` toggles underline (seen around "T.O" and "CONFIG"); `s` and `l` set small and large. Display text is uppercase, so an uppercase letter is never a code, and a lowercase letter outside a to z is text. U+2800, the blank braille cell the display uses as a spacer, becomes a space. A run before any color code has no color. Each code holds until another changes it, and a code that restates the line's current color or size does not split a run (`u` always does, since it toggles); no run is empty.
- Why the codes are data. On the displays the color is part of what a line says: red, amber, cyan, magenta, green and white tell a warning from a caution, a memo or an action. Stripped to plain text, a line would sound the same whatever it means. So the codes are parsed, never stripped for speech: `FenixTextLine.JoinedText` (the runs' text without color, underline or size) is only for parsing a number out of a line (the FOB) and for the log. A read that speaks channel text says each run's color. How it words them is settled by ear with the first read; no read exists yet, so nothing says a color today.
- A letter the parser does not know is dropped from the text and listed on the parsed line (`FenixTextLine.UnknownCodes`, once each, in the order first used). The gate does not trust a display while any line it covers holds one: the FMA's 16 slots for the PFD; the upper ECAM left and right lines and the FOB line for the E/WD ("unknown code 'x' in the upper ECAM"). A letter the app does not know means the line is drawn in a way the app cannot tell, perhaps in a color that matters. It does not latch ([FNX-22]): it is an exact condition, not a noisy one, and trust returns when the line goes away.
- Red's letter is `r`, measured on 3.0.0.7613 on 2026-11-02 with the capture this rule waited for: the TO CONFIG test with the flaps up, which lights a red warning ([FNX-4] measured the warning lighting), sent "urCONFIGu ", "rSLATS NOT IN T.O CONFIG", "urCONFIGu " and "rFLAPS NOT IN T.O CONFIG" above the amber gear lines (the format codes are plain lowercase letters, and `u` toggles the underline). Until then the parser had not guessed the letter, and those lines read "unknown code 'r' in the upper ECAM" for the two seconds the warning showed, as the rule meant a letter outside the list to; with red in `FenixTextColor` they hold no unknown code. The same holds for any letter: one joins the list only after a capture shows what it draws, never by analogy with the MCDU markup or another display. A `d` was seen only in the ND's GS/TAS block, meaning unknown, and is not in the list.
- Pinned by `FenixChannelTextTests` (each color letter; underline toggling; sizes; the braille blank; a run before any code; a code that changes nothing not splitting a run; uppercase never a code; an unknown letter listed once, in order; sample lines in the channel's format, `The_red_lines_of_a_takeoff_config_warning_parse` among them) and `FenixChannelTrustTests` (`An_unknown_code_untrusts_its_display_without_latching`, `An_unknown_code_in_the_fma_untrusts_the_pfd`, `An_unknown_code_names_the_line_it_came_from`, `An_unknown_code_is_judged_after_the_cross_checks`, `The_red_lines_of_a_takeoff_config_warning_keep_the_ewd_trusted`). That a read says the colors is not pinned: no read exists yet. → [a32nx.md](../a32nx.md)

## FNX-25

- The altitude cross-check of [FNX-22] compares the channel's altitude field (`FenixChannelFields.Remote.Altitude`, field 197) with SimConnect's true altitude, PLANE ALTITUDE in feet, which the channel asks for through a key of its own, `FenixChannelMonitor.AltitudeKey` (`FENIX_CHANNEL_ALTITUDE`). Never with INDICATED ALTITUDE. Field 197 is the true altitude: measured on 3.0.0.7613 at a gate at EDDF on 2026-11-02, it read 352.2 ft at QNH 1013, 1045 and 1029 alike while the sim's PLANE ALTITUDE read 356.0 ft, and it never moved with the baro. It is not the altitude the PFD shows, which is the ADRs' baro altitude, a field the app does not read.
- Why never the indicated altitude. The Fenix writes its own baro setting into the sim's altimeter (KOHLSMAN SETTING MB:1 and :2 followed 1013, 1045 and 1029), so INDICATED ALTITUDE follows whatever QNH is set on the Fenix. At power-up the Fenix set 1013 against an actual 1028.8 hPa, and the indicated altitude fell from 364 to -65 ft, about 420 ft below field 197: the altitude check, which compared the two then, latched the PFD 3 s later on a normal power-up. It would latch again in flight at STD, and with any setting that is not the actual pressure. The true altitude moves with neither, so the check compares like with like within its 100 ft tolerance (352 against 356 ft at the gate).
- The base class's `INDICATED_ALTITUDE` key keeps its own handling (the 1,000 ft callouts among it), untouched; the channel no longer peeks it. Feeding the gate from it again would look like a harmless simplification, and it is exactly the latch measured above.
- The key is registered like the heading and fuel keys ([FNX-22]): continuous and announced only so it rides the 1 Hz batch, consumed silently, hidden from Ctrl+M ([VAR-9]), the only batched key named PLANE ALTITUDE ([VAR-7]), and with the default change tolerance ([SIM-7]).
- Pinned by `FenixChannelMonitorTests` (`The_altitude_check_reads_the_true_altitude_never_the_indicated_one`, `Maps_the_five_comparison_keys`, and `Maps_no_other_key` with INDICATED_ALTITUDE) and `FenixChannelDefinitionTests` (the key: PLANE ALTITUDE in feet, the batch, Ctrl+M, the default tolerance, silent consumption). That field 197 is the true altitude on a given build is not pinned: the re-check of [FNX-23] confirms it for each build. → [a32nx.md](../a32nx.md)
