# Fenix windows rules — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/fenix-windows.md`, which Claude Code loads when it reads the code of a Fenix window (the Cabin, Fenix documents, Engines, Failures and Fenix options windows, opened from the Fenix windows list, and their services). It holds the cabin, documents and failures rules (FNX-12, 14, 15, 17, 18). FNX-13 (settings lag), FNX-16 (engine readouts) and FNX-19 (settings secrets) are in [fenix-data.md](fenix-data.md) with the data service, definition, variant and EFB rules, which load on this code too: FNX-13 and FNX-19 bind code outside the windows (the shared read-back wait, the settings query), and FNX-16 belongs with the data-service rules. Background: [a32nx.md](../a32nx.md).

## FNX-12

- The Fenix documents window reads with GETs only, through `FenixDataService.GetRestAsync` and the paths `FenixDocumentEndpoints` builds: `/fenix/documents` (the list), `/fenix/documents/search?q=<term>&limit=10` and `/fenix/documents/content/<path, each segment escaped>`; pictures under `/fenix/documents/asset/…` load inside the reading page. No Fenix code calls `/fenix/documents/OpenDocumentsFolder` (it opens Explorer on the pilot's PC) or the upload POST to `/fenix/documents` (it writes files on the PC; the EFB itself says upload works only from a browser), and the window does not use the PDF outline, the PDF page pictures (`?page=`) or `?matchIndex=`. A pilot adds documents by copying files into the Fenix's documents folder (`C:\ProgramData\Fenix\EFB\Documents`, from Fenix's guide) with Explorer, which is accessible.
- The one write is a pin (Ctrl+D; the owner kept it after testing, 2026-10-22): the persistent `pinned_documents` setting, written as the EFB writes it, a `setSetting` with `persist: true` whose value is the EFB's own JSON array (`FenixDocumentPins.Serialize`: `{"path":…}`, then `"matchIndex"` and `"label"` when set, no spaces; a new pin goes first), so a pin made in the window also shows in the cockpit EFB. Its result is read back as [FNX-13] says. A newly pinned ECAM procedure is never announced (owner, 2026-10-21: without the ECAM itself, readable only through AI display reads, the pins are a partial picture).
- A served document is shown only as an inert page (`FenixDocumentPage.Build`: a content security policy of `default-src 'none'` with pictures only from http://127.0.0.1:8083, scripts off in the WebView2, every navigation but that page cancelled and http or https links handed to the default browser, served `<meta>` tags replaced by a space, since a refresh meta is the one navigation the policy cannot stop). That is pinned by `FenixDocumentPageTests` and `FenixDocumentsFormSourceTests.Reader_runs_without_scripts_and_cancels_navigation`, so it has no rule line.
- The endpoints come from the EFB bundle (`efb/964.*.js` on Fenix 3.0.0.7426: `getDocumentsIndex`, `searchDocuments`, `getMarkdownDocument`, `getPdfOutline`, `openDocumentsFolder` POST, `uploadDocument` POST; `tools/fenix-gateway/fetch_gateway_bundles.py` fetches the bundles, read-only). Measured 2026-10-22: 772 documents; "spd brk" found 10 in 0.39 s. The pins' lifecycle, from the gateway's log (2026-10-21): one automatic pin per titled crew alert that has a document, unpinned when the alert clears on the ground with the engines off, every automatic pin cleared when the gateway starts.
- Pinned by `FenixDocumentsFormSourceTests.Never_calls_what_acts_on_the_PC_and_never_leaves_the_UI_thread` (a scan of the documents files only) and `FenixDocumentPinsTests.Serialize_writes_what_the_EFB_writes`; other Fenix code is not scanned. → [a32nx.md](../a32nx.md)

## FNX-14

- Every Fenix cabin write the Cabin window makes is built by `FenixCabinWrites` (a data-service name, the typed write the FAP or EFB uses for it, and the value) or by `FenixCabinPram` (the FAP bundle's GraphQL mutation text verbatim, its answer's `success` checked), from the Fenix 3.0.0.7426 FAP and EFB bundles: the FAP's cabin ready and cabin lights writes; its temperature store (a zone's offset in half-degree steps between -2.5 and +2.5, greyed at a target of 30 or more, or 18 or less); its water preselect (steps of 25 from 25 to 100); its Set-Up store (the loudspeaker in 5 percent steps, written as a fraction); the boarding music and announcement mutations; and the EFB's ground-service doors. Names and shapes come only from those bundles ([FNX-3]). A write the service refuses is said, and nothing is read back.
- Doors: the EFB writes a door's ground-service control (`doors.control.<key>`) as the Int enum Armed 0, Disarmed 1, Open 2, and its toggle writes Open or Disarmed, never Armed, and the app never writes Armed either. Cargo doors are Bool writes.
- No door or cargo door write above 100 ft above the ground, or while that height (`aircraft.altitude.aboveGround`) is unknown: the EFB shows its door toggles only at or below 100 ft (EFB chunks 856 and 964), and the FAP has no door controls at all. The owner kept this hard refusal after the in-sim run (2026-10-23); above 100 ft the pilot hears "Doors can only be opened or closed on the ground.", and with the height unknown "Height above ground is not known." (`FenixCabinForm.RefuseOffTheGround`).
- Owner checks 2026-10-23 (Fenix A320 3.0.0.7454 at the gate, bundles fetched again with every chunk cited byte-identical): door 1 left and the forward cargo door opened and closed, each read back once it settled, never an intermediate state; boarding music, its volume, the loudspeaker (95 and 100 percent, "already at maximum"), cabin lights, temperature, water preselect and the memo all wrote as expected. Not yet heard: the refusal above 100 ft.
- Pinned by `FenixCabinWindowTests.Cabin_writes_go_through_the_bundle_builders`, `FenixCabinPramTests.Mutations_are_the_FAP_bundle_documents`, `FenixCabinWritesTests.Door_toggle_follows_the_EFB` and `FenixCabinWindowTests.Door_and_cargo_presses_refuse_above_100_feet_or_with_the_height_unknown`; a new cabin control is not. → [a32nx.md](../a32nx.md)

## FNX-15

- `FenixCabinLayout.Resolve` gives the loaded airframe's passenger doors, slides, ground-service doors, lavatories and whether it has a bulk cargo door: from the Fenix settings `emergency_exits_type` and `aircraft_variant` first (each spelled exactly as the Fenix writes it), then the variant's aircraft type (an unknown type, and the A318, take the A320 layout). The settings are read at start, when the Fenix starts answering and on a variant change, never by a render. The Cabin window's lists, its Doors button and the app-wide door, slide and caution announcements use only the doors and lavatories it gives.
- Why: the data service answers for door names an airframe does not have. The IAE A321 read overwing slides it lacks as armed (2026-10-21), and the A320's overwing slides read armed at the gate with its main doors disarmed (2026-10-23). So a known value never proves a part exists, and the "Slides armed" and "Slides disarmed" summary covers the passenger doors' slides only.
- The layouts follow the FAP's designations and order and the EFB's ground-service list: the live A321 lists eight doors and no overwing slide; the owner's A320 (settings DoubleOverwing, SingleClass) lists doors 1 left and right and 4 left and right, two overwing slides, the forward, aft and bulk cargo doors, and lavatories A, D and E (owner check, 2026-10-23).
- Pinned by `FenixCabinLayoutTests` (`Settings_win_over_type`, `A321_double_fullsize`, `A320_double_overwing`), `FenixCabinLinesTests.Door_lines_of_the_live_A321_list_eight_doors_and_no_overwing_slide` and `FenixCabinEventsTests` (`Only_the_layouts_passenger_doors_are_said_in_their_order`, `The_overwing_slides_are_not_part_of_the_summary`); a new reader of door names is not. → [a32nx.md](../a32nx.md)

## FNX-17

- `FenixFailuresForm` writes only when the pilot presses Fail now (Alt+N), Arm (Alt+A, after the condition dialog) or Clear (Alt+C), or Enter on a failure, and only after a Yes/No box whose default button is No (`MessageBoxDefaultButton.Button2`; "Fail Lavatory/Galley fan now? This changes your flight."). Then it posts once to `FenixFailureRequests.SavePath` (`/fenix/failures/saveManual`, the EFB's `saveManualFailure`) and speaks what the Fenix's reply says (`FenixFailureRequests.ParseSaved`, worded by `FenixFailureText.SavedLine`), never the state it asked for; a reply that is not that failure speaks "The Fenix did not confirm the change to <title>." and the window reloads. Opening, the 10 s re-read, search, Show, F5 and closing never post; the timer stops while a dialog is up, and the failure is looked up again after Yes.
- The body is the GET's own failure object, deep-cloned, with only `failed` and `failureCondition` changed, as the EFB's Apply does (`FenixFailureRequests.BuildSaveBody`): unknown fields kept, numbers as JSON integers, an armed condition removed by Clear, `time` never written. That is pinned by `FenixFailureRequestsTests`, so it has no rule line of its own.
- Why the reply and not the request: they differ. Owner checks 2026-10-22 (Fenix A320 IAE): a fail-now body without the EFB's page-only `displayTitle` was accepted, and the reply was the saved failure object (sent `{"id":"F_PNEUMATIC_LAV_GAL_FAN","title":"Lavatory/Galley fan","failureCondition":null,"failed":true}`, reply identical; failing it raised an ECAM message, and Clear, `failed:false`, repaired it). A timed arm sent `{"afterEventSeconds":30}`, and the reply moved it to `time`: a numeric `time` is the seconds left, a float counting down one per wall-clock second at sim rate 1 (30.84 to 0.78 over 30.1 s), and at zero the Fenix sets `failed` and removes the condition. The EFB's own code reads `time` as a clock time; the window reads a numeric one as "armed: fails in N seconds" and never speaks a countdown tick (`FenixFailureText.Changes`).
- Unmeasured: whether condition fields combine as AND or OR, the units of IAS and altitude (the window keeps the EFB's unitless labels), whether the countdown pauses with the sim, and what `time` holds when an event is chosen.
- Pinned by `FenixFailureWindowTests` (`Window_keeps_the_screen_reader_rules`, `Only_one_write_and_only_to_saveManual`), `FenixFailureCatalogTests.Parse_reads_the_real_countdown_reply` and `FenixFailureTextTests.Changes_ignore_a_ticking_countdown`; that the form speaks the reply rather than the request is not. → [a32nx.md](../a32nx.md)

## FNX-18

- `GET /fenix/failures/manual` returns the manual-failure catalog of the loaded airframe. Read 2026-10-21 and 22: the A320 CFM and the A320 IAE have 549 failures, the A321 IAE 555 (it adds `F_CIDS_DEU_A_13` to `_16`, `F_CIDS_DEU_B_MID_CABIN_1` and `_2` and `F_FLUSH_CONTROL_UNIT_LAV_M`, and drops `F_CIDS_DEU_B_OVERWING`), in 20 chapters in the Fenix's own order (21, 22, 24, 26, 28, 29, 32, 34, 36, 38, 49, 23, 30, 27, 80, 31, 35, 46, 52, 70), which the window keeps. So shipped code never hard-codes a failure id, a count or a chapter. The test fixture holds only the first chapter (ATA 21: 14 groups, 57 failures) of the 65,828-byte catalog, which is Fenix's content in a public repository.
- While open, the window reads the catalog again every 10 s and speaks failures that changed without its doing, three named at most ("And N more changes."). `FenixFailureText.Changes` compares only ids present in both reads, so another variant loaded between two reads rebuilds the tree silently instead of announcing hundreds of ids; a countdown that only ticks is not a change ([FNX-17]).
- Pinned by `FenixFailureTextTests` (`Changes_ignore_ids_in_only_one_read`, `Changes_cap_at_three`) and `FenixFailureCatalogTests.Parse_keeps_the_Fenix_chapter_order`; a hard-coded id elsewhere is not. → [a32nx.md](../a32nx.md)
