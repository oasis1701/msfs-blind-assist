# iniBuilds A300-600 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/a300.md`, which Claude Code loads when it reads matching code. Background: [a300.md](../a300.md).
The text is verbatim from CLAUDE.md as of `8f6ad85e`; a trailing "→ doc" pointer is the original's.

## A300-1

- A map-driven A300 row is written by firing the control's OWN B: event, `value (>B:AIRLINER_<Name>_Set)`, through `ExecuteCalculatorCodeUnique` (`A300WritePlan`) — never `SetLVar` and never a bare L:var write. The one exception is a position only another clickspot reaches (`A300PanelLayout.PositionEvent`): the gravity extension handle's own event only pulls it, and its Stowed position fires the stow clickspot, `AIRLINER_Man_Gear_Handle_Hide_Set` (2026-10-10). A TWO-POSITION switch's Set event FLIPS it whatever value it is given (iniBuilds' own `_ON`/`_OFF` bindings flip too, measured 2026-10-03), so a toggle or command row is sent only when its current position is KNOWN and differs, refused aloud ("Switch not ready, please try again in a moment.", the PMDGs' words) otherwise. A value that is none of the control's positions (a valve part way across) is not known either: `A300WritePlan.ForSet` refuses it as not ready, and the read-back after a pick (`CheckMovedAsync`) neither says "did not move" for it nor remembers it. A just-commanded position is trusted for 2.5 s over the 1 Hz cache (`A300CommandedState`), kept per STATE VARIABLE and never per row (`IniA300Definition.CommandKey`): the courier low pressure supply and crew oxygen supply buttons fire their own events but flip ONE variable, `L:INI_OXYGEN_COURIER_LOW_PRESSURE_SUPPLY` (a Set of 1 on the courier event turned it on, and a Set of 1 on the crew event then turned it off, measured 2026-10-13), as do the dome light, terrain mode and autoland light pairs, so a hold kept per row left the second row planning from its own stale cache and flipping the first row's pick back; a flip sent the wrong way inverts the switch. Selectors and knobs are absolute; hold buttons are Set 2, 250 ms, Set 0, except the six fire tests (`A300WritePlan.TestHoldMs`: the aircraft's own checklist's 5 s for the APU loop test and 3 s for the squib tests, 250 ms never finished one, measured 2026-10-04; 7 s for the engine loop tests, whose fire warning comes at about 4.4 s and lasts while held, so 5 s lit the handle only half a second, measured 2026-10-09), and the takeoff config, landing gear warning and smoke tests, held 5 s (a 250 ms takeoff config press reported nothing even in landing configuration); spring switches are held 1 s and returned to rest. The flaps lever, ground spoiler arm and speed brake are the hand-written exception (`A300Levers`: `K:FLAPS_SET` index x 4096, `K:SPOILERS_ARM_SET` read back from `L:INI_SPOILERS_ARMED` because the stock armed flag stays 0, `K:SPOILERS_SET`). Every write is refused aloud ("{name} unavailable") when `CalcWriteCanLand` is false and the row is asked for again so its combo snaps back. → [a300.md](../a300.md)

## A300-2

- `MSFSBlindAssist/Resources/a300_control_map.json` is GENERATED by `tools/a300-gen` from the aircraft's compiled cockpit behavior, tooltips and checklist (each control's first checklist step, which orders its panel, [A300-3]) — never hand-edit it; regenerate after an iniBuilds update and review with `diff_maps.py`. iniBuilds' files and any decoded copy of them stay out of the repo. → [a300.md](../a300.md)

## A300-3

- `A300PanelLayout` is the ONLY source of A300 panels: WHICH panel a control is on follows iniBuilds' own component tree (so an update is picked up by regenerating), except where `ControlPanels` (`A300PanelLayout.Systems.cs`) sends a control of a place-grouped iniBuilds panel to its system's panel, and `PanelSections` puts that panel in its fleet section. Design decision, 2026-10-09: the fleet's Airbuses group by system, so the overhead lights panel is Signs, Interior Lighting and Exterior Lighting, the bleed panel is Bleed and Air Conditioning, Cargo Smoke leaves Fire, "Main Panel" is the FBW "Instrument" section (Warnings, Gear, Autobrake, Thrust Rating Panel, Landing Elevation, Standby Instruments, Source Switching, Clock, GPWS, Captain Side, First Officer Side) and the throttle quadrant is Engines, Thrust Levers (with the go levers, which iniBuilds puts on the captain's EFIS panel), Flaps and Speed Brake and Parking Brake, its cancel buttons and takeoff config test joining the ECAM Control Panel; the fleet's names (Pressurization, EFIS Captain, Transponder, Audio Control Panel Captain, Recorder) and the manual's where the A300 differs (IRS, Flight Controls, SAS Control, Thrust Rating Panel). Window and probe heat and the landing elevation knob stay where the A300 has them (design decision, same day). Rows both sides share a panel with say their side first ("Captain chrono"). The ORDER is `A300PanelLayout.Order.cs`: `PanelOrder` is the FBW A320's order where the A300 has the same panel; within a panel the rows follow the aircraft's own checklist (design decision, 2026-10-10): each control's first checklist step is GENERATED into the map's `checklist` field by `tools/a300-gen` (a step names a control by the part it points at, a variable it tests or sets, or the event it fires), the named rows come first by step, a row inside a group one step names stays in it (`ChecklistStep`: the ADF transfer buttons), and `LeadRows` still opens Electrical, Warnings, Gear, Engines and Flaps and Speed Brake; everything else keeps cockpit-file order, and a panel or row the lists miss stays after the listed ones, never dropped. It also splits the pedestal's "STD" radio and audio group by what each control is, names every unclear or clashing control in `A300PanelLayout.Names.cs` (iniBuilds' titles repeat, and two are wrong: "ALTITUDE KNOB" on the V/S knob, "CPT BAROMETER" on the first officer's), and puts a guard directly before its switch. Guard COVERS are never rows (they only move the model); the two cargo smoke agent guards are real switches the agent switch depends on. The VHF and NAV frequency knobs are left out on purpose too (`A300PanelLayout`'s `Excluded`; design decision, Robin, 2026-10-14): every one of those radios has a typed frequency box (`A300TypedValues`), so their 14 megahertz and kilohertz knobs were 28 increase and decrease rows to step through. The ADF knobs (there is no typed ADF box), the course knobs, the transponder code knobs, the transfer buttons and the squelch switches stay, and the generated map keeps every knob ([A300-2]); the layout alone leaves them out, so a regeneration needs no edit. → [a300.md](../a300.md)

## A300-7

- The master warning and master caution speak only as they come ON: pressing the light writes 0 to the same `INI_MASTER_*_ACTIVE` variable, so speaking it going out would announce the pilot's own press. Lamps and the announced levers (`A300Announcements.AnnouncedKeys`: flaps, ground spoiler arm, gear, parking brake, and since 2026-10-10 the SAS pitch trim and yaw damper levers, which the aircraft drops by itself; their branch runs before the FMA sources', as the pitch trim levers are both) speak from `ProcessSimVarUpdate` inside MainForm's mute and echo wrap (`DefAnnounceMuteSets` lists `INI_A300`); a context reset wipes the baselines and `Md11SeedGate` decides when the unchanged ones are seeded from the cache. The gate releases that seed only on evidence that the aircraft's own module has republished, so a delivery counts as such evidence only when its variable is one of the aircraft's own L:vars (`IniA300Definition.IsAircraftOwned`: the variable's definition is an `LVar`, the MD-11's rule), asked at every `NoteValue` call: the light board, the announced keys, the altitude window and the V1 and VR read-backs. The sim core writes the stock SimVars from the flight file before that module runs, so a change of one (a lamp's stock input such as external power or a gear position, and the levers read from stock variables: the flap handle index, the gear handle, the parking brake) only restarts the quiet count and never releases the seed; the ground spoiler arm and the SAS levers are L:vars and do count. The light board used to report every input as owned, stock ones included, so a flight load could release the seed before the module had published and the lights and levers were then narrated as changes (found in review, 2026-10-13). A cockpit in which nothing of the aircraft's own changes waits for the gate's ceiling (30 s after the first full batch cycle) instead, where seeding from a cache nothing has moved is trivially right. → [a300.md](../a300.md)

## A300-12

- The A300 fault lights (`A300FaultLights`, 55; 58 until the fire handle lights moved to `A300PanelLamps`, 2026-10-09) stream on their OWN once-a-second subscriptions (`ExcludeFromBatch`), never the continuous batch, to keep the FMA's sources in one batch. Each change is collected in `ProcessSimVarUpdate` only when `announcer.Suppressed` is false THERE (MainForm's mute and echo wrap) and spoken at the next continuous batch end as ONE sentence (`A300LampCallouts`), so a muted light must never be collected and spoken later outside the wrap. Names come from mapping the cockpit model's emissive nodes to the light variables; never name a light from its variable alone (`INI_ENGINE1_BLEED_LIGHT` lights a wing anti-ice node and is left out for that reason). → [a300.md](../a300.md)

## A300-13

- A300 autopilot and autothrottle engagement call-outs (`A300EngagementTracker`) are silent for the pilot's own MSFSBA pick, judged by `A300CommandedState` (the row or hotkey recorded the commanded position within 2.5 s); never by a value compare against the cache alone, which cannot tell a yoke button from the panel. Their Ctrl+M rows ride `INI_AUTOPILOT_DISCONNECT` and `INI_AUTOTHROTTLE_DISCONNECTED`, registered only to carry the rows; nothing reads their values, which were never measured. → [a300.md](../a300.md)

## A300-20

- The LO, MED and MAX autobrake buttons show what their lamps show, read from the aircraft's own code (1.0.11): each button's lower segment lights while `L:INI_AUTOBRAKE_LEVEL` equals its level (1, 2, 3; 0 is off) and its DECEL segment is dark, and the DECEL segment lights from `L:INI_AUTOBRAKE_LOW_DECEL` / `MED_DECEL` / `HI_DECEL` (the cockpit's emissive code), which `update_ab_datarefs` sets only at that level, engaged, past 1.36 of deceleration. So the label reads "Armed", "Decel" or "Off" (`A300Autobrake.Describe`), and nothing while the level or the AC light power is unread. `L:INI_autobrake_armed` is never the state: only the three button handlers (`INI_autobrake_low_handler` and its siblings) write it, while the aircraft's own disarms in `INI_autobrake` (the gear handle leaving down, its disconnects) set the level to 0 and leave it at 1. A press writes `INI_ABRK_LOW/MED/HI_COMMAND`: the active level pressed again disarms by the aircraft's design (measured in flight, 2026-10-06), so it is never blocked and is silent; any other level arms only with the gear handle down, green hydraulic pressure at 2,200 psi or more, no autobrake fault and, with the parking brake off, `INI_brake_system` at 0. A press says nothing about its own button's armed light, because the screen reader reads the relabeled button ([CORE-7]; design decision, 2026-10-13, as for every light-labeled A300 button): `HandleUIVariableSet` records `_pressedLampUntil[ArmedLampId]` for `PressedLampMs` (3 s), beside the `A300PanelLamps.ByButton` record, and a light change it then skips makes `A300LampSpeech` forget that light's earlier unspoken change ([A300-24]). The rest is spoken as it changes, through the same `A300LampBoard` as the fault lights ([A300-23]): an armed light that lights or goes out with no MSFSBA press behind it (a cockpit click, a hardware button, the aircraft's own disarm), the armed light of the level that was active going out when another level is pressed ("Autobrake low armed light off" after a MAX press), and each DECEL light, which is the aircraft's and never the press's own. The armed light is undecided until its DECEL input has been read (an unread input sets no baseline, [A300-23]), whereas a button's label (`A300Autobrake.Describe`) reads an unread DECEL as "Armed". Both segments are on AC light power, so a label also reads "Off" on a dark AC bus. A press the aircraft refuses changes no light, so nothing is said (a "did not arm" read-back was dropped on 2026-10-09: no other aircraft says it for its autobrake). The level and the three DECEL lights stream on their own subscriptions, never the batch ([A300-9]); the level's Ctrl+M row ("Autobrake armed lights") mutes the three armed lights, and each DECEL light has its own row. → [a300.md](../a300.md)

## A300-21

- The thrust rating panel, read from the aircraft's own code (1.0.11). A TRP button's Set writes `L:INI_TRP_<X>_BUTTON` 1, which `TRP::Update` consumes (measured 2026-10-04: a write of 1 is consumed): TOGA, MCT, CL, CR, AUTO and FLEX TO set `L:INI_TRP_MODE` to 1 to 6, and each button's lamp is `INI_TRP_MODE` == its number (the cockpit's emissive code), so the label reads "On" only for that mode (`A300Trp.ButtonState`). In AUTO the mode STAYS 5 (the AUTO handler writes 5, and `TRP::Update` writes 5 itself in a profile climb past the thrust reduction altitude), while `L:INI_TRP_AUTO_MODE` holds the limit the aircraft chose by flight phase, 1 TOGA, 3 climb, 4 cruise (`updateN1limit`; measured 1 on the ground and 3 in the climb, 2026-10-04): reading the limit as a lit button would say "climb: On" while the cockpit lights AUTO. The autopilot logic can also write 1 and the MCDU's MODE page 2. `L:INI_THRUST_MAXIMUM_N1` is the active limit's N1 (`updateN1limit` copies the mode's own N1 into it), but with PW engines (`L:INI_IS_PW` 1) the TRP shows EPR limits, so the N1 limit is read only while `INI_IS_PW` reads 0. `L:INI_FLEX_TEMPERATURE` is the FMS's flex temperature, copied there on every update (`FMGS::Update`), so a direct write is undone; the knob steps it one degree, 0 to 72, and each step is read back once it lands, as the FCU knobs' are ([A300-14]). The Thrust Rating Panel's status box has one "TRP" line (`A300Trp.Line`: "AUTO, climb, N1 limit 95.3 percent", "FLEX, 45 degrees"). The mode, AUTO's limit, the N1 limit and the engine type stream on their own subscriptions, consumed silently, never the batch ([A300-9]). → [a300.md](../a300.md)

## A300-23

- Every A300 cockpit lamp, in the aircraft's emissive code (1.0.11, `A300_Interior.behavior.xml`), is `(state OR INI_ANNLT_SWITCH == 0) × INI_GENERAL_LIGHT_MULTIPLIER × its bus's light power`. The power flags are written by one block: `INI_DC_LIGHTS_FAILURE` = battery on OR the AC emergency bus powered, `INI_AC_LIGHTS_FAILURE` = the AC essential bus powered (1 = powered, despite the name); the multiplier is 1 (ANN LT DIM) or 10, never 0, so it is not a power term. Each `A300FaultLights` entry carries its bus from its own expression (26 AC, 29 DC; the three fire handle lights have no power term), and the autobrake segments are on AC (armed: level == n AND its DECEL dark; DECEL: its variable). ONE `A300LampBoard` decides the fault and autobrake lights: lit = state AND power; a light's first value with every input read is a silent baseline, and an unread input leaves it undecided, so a cold-and-dark start or a power change never reads lights the cockpit does not show. Measured 2026-10-09 at the gate: switching the aircraft off read "2 lights on: Cabin regulator 2 fault, Battery 1 fault" and more as systems lost power while the panel went dark; switching on read lights "off" that were never heard on. With the board, power coming on speaks the lights that light, power going off speaks the lit ones going out, and a fault set or cleared on a dark bus says nothing. A power flag, the autobrake level or a DECEL light changes several lights at once, so those keys are `IsMuteWrapExempt` and each change checks its own light's Ctrl+M row (`IsMuted(MuteKey)`, VAR-8); the status box of a fault light reads On only while lit (`TryDescribeControlState`, repainted on its power key through `StateVariables`). The annunciator test term is left out, as before: the test says nothing. The two flags stream on their own subscriptions, consumed silently, no Ctrl+M row, never the batch ([A300-9]). → [a300.md](../a300.md)

## A300-24

- The light power flags (`INI_AC/DC_LIGHTS_FAILURE`) and the fault flags each reach MSFSBA on their own once-a-second subscriptions ([A300-12], [A300-23]), so the order the aircraft set them in is lost. Measured on external power, 2026-10-09, sampling the cockpit every 250 ms: the rudder travel limiter 2 and cabin regulator 2 faults cleared at 1043 ms and the AC light power rose at 1548 ms, but MSFSBA heard the power first and said "10 lights on: ... Rudder travel limiter system 2 fault, Cabin regulator 2 fault, ... ECAM clear", then within a second "Rudder travel limiter system 2 fault light off", "2 lights off: Cabin regulator 2 fault, Cockpit door fault", "ECAM clear light off". External power off had the same pair inside ONE sentence ("Cabin regulator 2 fault light on. 9 lights off: ... Cabin regulator 2 fault").
- `A300LampSpeech` takes every board change the definition keeps (after the mute checks), and `FlushLamps` asks it for a sentence at each continuous batch end. It nets per light: a light that changed an even number of times since the last sentence ends where it started and says nothing; otherwise its last change stands, in the order of the last changes. When `A300LampBoard.PowerFlips` says a delivery turns a bus's light power on or off (a first value is a baseline, never a flip), the definition calls `NotePowerChange`, and nothing is spoken until `SettleMs` (2500 ms: two subscription periods and a batch end) has passed; the changes gathered meanwhile are netted and spoken as one sentence. The flags arrive in either order: on external power off (2026-10-09) the rudder travel limiter 2 fault reached MSFSBA a second BEFORE the AC light power flag, and was said on, then, in the settled sentence, off. So a light's first change since the last sentence also waits `GatherMs` (1500 ms, one subscription period and a little) from its own arrival, which lets a power flag still on its way extend the hold and net with it. Exactly: a change of a NEW light (one with no change pending) moves the hold to its own `now + GatherMs`, never earlier than a hold already set; a further change of a light that already has one pending moves nothing. Only the very first change since the last sentence used to open that wait, so a different light that changed late in it was spoken with the first, before a power flag that was still on its way (2026-10-13). Moving the hold for every change starved the speech instead: while a power change settles an off is queued, not held, so a light flashing through the settle (the autoland warning light, every 0.6 s) queued a change every 0.6 s, each one moved the hold on, and the settle ended only when the flashing stopped (measured on the built class in review, 2026-10-13: the first sentence came at 22 s, not 3 s). So the sentence comes at the first batch end once 1.5 s have passed since the newest light's first change: about 1.5 s after a light changes when no other light changes meanwhile (the MD-11 waits 1.5 s before speaking a lamp going dark), and a cascade of different lights, an engine start, is read as one sentence once it has been quiet for 1.5 s. A context reset clears both the pending changes and the hold.
- This is the fleet's behavior, settled: the Fenix speaks every lamp a power change lights or darkens (its lamp variables already include power, so it needs no settling; measured 30 to 55 announcements per power step), and the MD-11, which composes its lamps with a DC gate as the A300 does, also waits before speaking a lamp going dark (`DarkSettleMs`). This was chosen on 2026-10-09 over a silent power-up (design decision).
- Live comparison, same four steps (external power off, batteries off, batteries on, external power on), 2026-10-09: 13 announcements before, 9 after, no on-then-off pairs; a power change's sentence comes about 4 to 5 s after the press instead of about 2 s. Lights changing with power steady are unaffected.
- A board change the definition does not keep (the announcer suppressed, the light's Ctrl+M row muted, a just-pressed button's own light, [A300-20]) still calls `A300LampSpeech.Forget(name)`: the light has moved on from its earlier change, so that light's held off and every pending change of it are dropped. Without it the earlier opposite change was spoken later although wrong (pressing ECAM HYD, then ENG within the off hold, said "Engine page light off" while the Engine page light was lit), and, netted with a later kept change, a skipped one flipped the parity and silenced a light that had really changed (2026-10-13). Other lights are untouched. → [a300.md](../a300.md)

## A300-25

- Most of the cockpit's lamps are not one variable times its bus's light power. External power AVAIL is "ground power available AND external power not on", with no power term (the ground power unit lights it); the gear greens are the stock `GEAR POSITION:n` at 100 percent; many lamps light while a variable is clear. So `tools/a300-gen` copies every annunciator lamp's own state rule from its emissive code into `a300_control_map.json` (`lamps`: node, state in the cockpit's RPN, bus), 496 of them, leaving out the test-only lamps (a bare number, or only the test switch, as iniBuilds' SELCAL lamps) and panel backlights (no test term). A Material's OwnerID is the index of its Component in document order, the root component included (an index that skips the root names the wrong node: the battery's OFF legend came out as battery 2's).
- `A300LampRule` evaluates a rule over what MSFSBA reads: variables, stock variables in their unit, numbers, and only the operators the lamps use (`! and or == != > < /`); anything else is refused, and `A300LampRuleTests` parses every shipped lamp. `A300LampBoard` decides each named lamp as rule AND power, through the same netting and settling as every light ([A300-24]).
- `A300PanelLamps` names the lamps a pilot reads, panel by panel as each is swept (design decision 2026-10-09: every light that can be read is spoken): the button, its legend, "light" ([VAR-1]). A switch's OFF or ON legend that mirrors its position is left out (the row says the position; the FBW Airbuses do not speak them either). A lamp already read by `A300FaultLights` is never named again (a test pins it).
- Registration: each named lamp's key streams the rule's FIRST variable on its own subscription (never the batch, [A300-9]) and carries its Ctrl+M row and status box line; the rule's other variables stream once each under `A300_IN_<id>` keys, consumed silently. A shared input changes several lights, so it is mute-wrap exempt and each light checks its own row (as the light power flags, [A300-23]). → [a300.md](../a300.md)

## A300-26

- Measured 2026-10-10: VHF 1's knobs change `INI_COM1_FREQUENCY` (the knobs iniBuilds' tooltips call VHF1 MHZ and KHZ) and `INI_COM1_STBY_FREQUENCY` (VHF1 STBY MHZ and KHZ). The transfer button toggles `INI_CPT_VHF_TRANSFER_SWITCH`, and the stock `COM ACTIVE FREQUENCY:1` follows the first window while it is 0 and the second while it is 1; neither window's value moves. So after one transfer the "standby" knobs retune the frequency in use, a pilot who believes the name loses the frequency they are talking on. The ADF panels work the same way with the switch the other way round: `INI_ADF1_TRANSFER_SWITCH` 1 uses `INI_ADF1_FREQUENCY`. The cockpit's window lights agree (`CPT_COMM1_LX` lit at 0, `CPT_ADF1_LX` lit at 1).
- `A300Radios` composes each status line (active, standby) from both windows and the switch, and each knob step's and transfer's read-back the same way ("VHF 1 active 124.805" for the "standby" knob after a transfer). The windows and switches stream on their own subscriptions, consumed silently; the read-back reads them together (one after another, it came 3 s after the press). The ADF row names stay iniBuilds' ("ADF 1 standby hundreds increase"). The VHF knobs are no longer rows (design decision, Robin, 2026-10-14): a typed standby box sets a VHF frequency, and the ADF knobs keep this read-back by role. → [a300.md](../a300.md)

## A300-28

- The autoland warning light (`INI_AUTOLAND_LIGHT`) flashes about 0.6 s on, 0.6 s off during its EFIS test and on a real autoland warning (glareshield sweep). Sampled once a second the A300 said it "on", then "off" while it was still flashing: a 1.2 s flash sampled every second aliases to about 3 s on, 3 s off, and the netting ([A300-24]) only nets inside one gather period. The aircraft's code names no other flashing lamp (its other flashing timers drive the PFD's FMA and flight director).
- The iFly 737's model was adopted on 2026-10-10 (design decision; `IFly737MAXDefinition.HandleLightEdge`: "on" once, "off" only after the light has stayed off; the iFly holds 2 s, the A300 about 3). `A300LampSpeech` holds every off `OffHoldMs` (3000 ms); a light lighting again while its off is held is dropped, so the pilot hears one "on" and one "off" once it stops. Only an off that comes after a light power change and before that change's sentence is spoken (`NotePowerChange` until the flush past its hold) is not held: it nets in that sentence, which keeps the power-flag order cases of [A300-24] silent. The first build also let an off net with an "on" still unspoken in its gather period; live on 2026-10-10 that delayed the autoland light's "on" by 4 s (each dark phase netted the unspoken "on" away until a batch end fell in a lit phase), so a light that blinks once now says "on", then "off" after the hold, as the iFly does. A held off joins the next sentence without a gather period of its own, so lights coming on and lights going dark at the same moment are now two sentences, the offs 1.5 s after the ons.
- `A300Lamp.Flashes` marks the autoland light, whose definition sets `HighFrequency` (SIM_FRAME with CHANGED, seeded per [SIM-19]): its 0.6 s dark phase is then seen as it is and always relit inside the hold. Every other light stays once a second (`A300FaultLightTests`). → [a300.md](../a300.md)

## A300-29

- Design decision, Robin, 2026-10-14: the A300 speaks a VHF frequency or a squawk that something other than MSFSBA changed, as the Fenix (`N_PED_RMP*`) and the PMDG 737 already do. Before, the VHF windows were silent subscriptions (`A300Radios`) and the transponder code was read only on request (`A300Readouts.SquawkCodeKey`), so an ATC program setting the next frequency into the standby window, or a new squawk, went unheard.
- Measured at the gate, 2026-10-14 (package 1.0.11, powered, VHF 1's transfer switch at 0 so window 1 in use), by writing the stock events over SimConnect and reading the aircraft's variables; every value was restored afterwards:
  - `COM_STBY_RADIO_SET_HZ` 121.5 MHz, what an ATC program sends: within about a second `L:INI_COM1_STBY_FREQUENCY`, window 2 (the one not in use), read 121500. The stock standby read the same.
  - `COM_RADIO_SET_HZ` 124.85 MHz: `L:INI_COM1_FREQUENCY`, window 1 (in use), read 124850.
  - `COM_STBY_RADIO_SWAP`: the A300 EXCHANGED the two windows' contents (window 1 went 122800 to 121500, window 2 went 121500 to 122800) and the transfer switch stayed at 0. So an outside swap changes BOTH windows and not the switch.
  - `XPNDR_SET` 8192 (code 2000): `TRANSPONDER CODE:1` (BCO16) read 8192 within about a second.
  - A read in the same instant as a write still showed the old value: every change took up to about a second to appear.
- What is watched. For each VHF radio (VHF 1 and VHF 2; the ADFs are not watched) the aircraft's OWN two windows and its transfer switch, never the stock `COM ACTIVE/STANDBY FREQUENCY`: the A300 mirrors the stock standby into its window and shows its own windows, so they are what the cockpit shows whoever moved them. Active and standby come from the switch as `A300Radio.Active` and `Standby` derive them ([A300-26]). Also `TRANSPONDER CODE:1` (BCO16), decoded as `A300Readouts` decodes it. Each is compared as FORMATTED text, never as raw doubles; a frequency is `A300Radio.Frequency` (invariant culture, three decimals), so a comma-decimal Windows locale never reads "121,500".
- What is said, as ONE sentence for what changed, and the new reading is the baseline: "VHF 1 standby 121.500", "VHF 1 active 124.805", or both after a swap, "VHF 1 active 124.805, standby 121.500"; the squawk "Squawk 5473", the digits as one number, exactly as a typed code's confirmation and a code knob's read-back say it (`A300Readouts.SquawkPhrase`).
- The hold (`A300FrequencyWatch`, a VHF radio only). A swap changes both windows, and each window streams on its own once-a-second subscription, so the two new values can reach the definition either side of a batch end; spoken at the first flush that saw a changed pair, one swap was two sentences, the first of them half of it. So a radio speaks only once its derived (active, standby) pair has read the same at two consecutive flushes: a pair that differs from the one seen at the previous flush is remembered and nothing is said; a pair that equals it and differs from the baseline speaks the difference and becomes the baseline. A pair that changes back before it holds says nothing. The cost is about a second. A swap is then one sentence naming both ("VHF 1 active 121.500, standby 122.800"), whichever side of a batch end each window's new value lands. The two windows are each read once a second, so their new values arrive less than a second apart, and a pair that stood for a whole batch period holds both. The flush therefore runs once per batch period: the A300 has two batches (305 batch-covered variables, 300 to a batch), each delivered once a second, so only the end of batch 1 (`IniA300Definition.RadioWatchBatch`) runs the watches; on every batch end "two consecutive flushes" would be half a second apart. The squawk is a single value and needs no hold.
- Baseline. After construction, after a context reset (`OnSimContextReset`: a flight load, a reconnect) and while the post-load seed gate is armed (a load still settling, as the FMA treats it), every reading only re-baselines silently. A radio has no baseline until all three of its inputs have been read, and an input that goes unread again drops it. The flush runs before the seed gate can release in `OnContinuousBatchDelivered`, so the release's own flush is still settling. The baselines form from the cache whether or not a delivery has named an announcer yet, so the first change after the initial snapshot is not swallowed.
- MSFSBA's own changes are quiet. For 2.5 s (`A300CommandedState.HoldMs`, inclusive) after MSFSBA itself changes a watched value, that watch only re-baselines, at every flush inside the window: those changes already have their own confirmation or read-back, and [CORE-7] says never repeat. It is time only, never a value compare, so an encoding or rounding difference can never make an own change speak twice. The mark is made as the change is sent: the typed VHF 1 or VHF 2 standby box (`SendPlanAsync`, the one send of the panel rows and the value boxes), a VHF transfer button press (`A300Radios.ByTransfer`; the ADF transfer buttons mark nothing), the typed squawk box and a transponder code knob step (`A300_TCAS_BIG`, `A300_TCAS_SMALL`, increase or decrease), and the surroundings window's COM 1 tune (MainForm sends the stock standby-set and swap events, which the A300 mirrors into VHF 1's windows, and says what COM 1 holds itself). A change that reaches the definition more than 2.5 s after MSFSBA sent its own is spoken, the limit the altitude window's echo has too ([A300-14]); an outside change inside the window of an own one is swallowed.
- Speaking. At the end of batch 1 (`OnContinuousBatchDelivered`, beside `FlushLamps`), through the announcer the latest delivery of a watched input came with, and never after `_disposed`. The flush runs OUTSIDE MainForm's mute wrap, so it checks `IsMuted(rowKey)` itself, as the FMA does: a muted row moves its baseline on all the same, so what it missed is never replayed on unmuting. Ctrl+M has one row each, "VHF 1 frequencies", "VHF 2 frequencies" and "Squawk", carried by the radio's transfer switch (`OwnSubscription(..., ctrlMRow: true)`) and by a new subscription to `TRANSPONDER CODE:1`, Type SimVar, Units BCO16. Neither is ever batch-covered ([A300-9], [VAR-7]) and neither has a change tolerance ([SIM-7]): every step of a window or the code is a delivery.
- Consumption. A key that carries a Ctrl+M row is not in `_silentKeys` ([VAR-9]), so `ProcessSimVarUpdate` consumes the three row keys and the four window keys in one branch, ahead of the silent set and returning true without speaking; MainForm's generic announce never sees them. A delivery never speaks by itself; only the batch-end flush does. → [a300.md](../a300.md)
