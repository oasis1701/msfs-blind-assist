# GSX Remote API, gate selection and GSX logs — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/gsx-remote.md`, which Claude Code loads when it reads matching code. Background: [gsx.md](../gsx.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## GSX-1

- Gate selection sends GSX's own `gate.select` verb with values GSX itself published — never a label rebuilt from `Describe()`/`Name`/`Number`/`Suffix` (which value goes on the wire is the next bullet), and never `force: true` automatically (it would override a stand GSX assigned to AI traffic). `GsxRemoteGateSelector.SelectGateAsync` still needs its reentrancy guard — not to protect a menu walk any more (there is none), but so two overlapping calls can't have the second `revokeServices` the first mid-flight; it SERIALIZES the second call rather than rejecting it, so a pilot's correction is never silently dropped. → [gsx.md](../gsx.md)

## GSX-2

- `gate.select` answers to a stand NUMBER (JSON int) or a `bglName`, and to NOTHING ELSE — live-probed against a running GSX (KATL, 2026-08-27): `uiGateName` verbatim, its trimmed form and `uiName` all return `not_found`. `bglName` is NOT published in `handlerData.airport.parkings` (it serialises there as the string `"method"`, an unserialised Python accessor); it reaches a client only inside an `ambiguous` reply's candidate list, which is why `GsxGateSelectPlan` sends the NUMBER first, then a matched candidate's `bglName`, then `ParkingSpot.GsxIdentifier` verbatim as a last resort so no airport is worse off than before. That last-resort rung fires on `BadArgs` as well as `NotFound` — both mean "that argument bought nothing", and gated on `NotFound` alone a build that rejects the int outright ended the sequence having never made the attempt the old code always made. A **SUFFIXED** stand never sends its number at all (`GsxGateSelectPlan.SendsNumberFirst`, the ONE predicate both methods share so the sequence cannot drift): `Number` is `StandId.Parse`'s reading of `uiGateName`, so "Gate 12A" yields 12 and the suffix is DISCARDED — the request is then wrong by construction rather than ambiguous, and for a stand with no `uiName` the echoed number CLEARS the contradiction check, so GSX prepares "Ramp 5" for a pilot who picked "Ramp 5B" with nothing spoken. A suffixed stand goes as its verbatim identifier, which fails loudly with `not_found`; losing the stand is recoverable, silently servicing the wrong one is not. Before this was found the feature had never once worked: 14 attempts in `gsx-gate-select.log`, 9 `not_found`, 5 `bad_args`, 0 `Prepared`. The "verbatim identifier" rule STANDS and is unchanged in PURPOSE — never rebuild a label from `Name`/`Number`/`Suffix`/`Describe()` — but a number GSX published and a `bglName` GSX handed back are GSX's values, not ours. The int and the string are DIFFERENT requests on the wire (the number 5 resolves, the text `"5"` returns `not_found`), so the `gate` argument is typed `object` all the way into the anonymous type and `RequestedNumber` is STAMPED rather than re-parsed out of the rendered `RequestedIdentifier`. A spot with no `GsxIdentifier` sends NOTHING, not even its number — a navdata/`.ini` spot's number is the scenery author's, and it carries no `GsxUiName` to check the answer against, so the `BadArgs` degradation to manual selection stands. An ambiguity that does not resolve to EXACTLY one candidate is surfaced, never guessed: `GsxGateCandidateMatcher` returns null — including for a candidate carrying no `bglName`, which could not be re-sent anyway — and the announcer's `Ambiguous` arm speaks as it always did. → [gsx.md](../gsx.md)

## GSX-3

- `uiGateName` is NOT unique — 235 of KATL's 294 stands share theirs, and `" Gate 5"` (leading space; 281 of 294 carry one) names both Concourse T and Delta Tech Ops. `ParkingSpot.GsxUiName` carries GSX's `uiName` ("Concourse T (T1-T21) | Gate 5"), unique for 281 of 294, and it is what `GsxGateCandidateMatcher` matches on and what `ResolvedGateContradictsRequest` now compares FIRST — which CLOSES the collision limit that property's own doc called structural. It takes no part in `Describe()`, is not copied by `GsxStandNameOverlay`, and does not reach `GetNamedSpots` — so a stand still has ONE name app-wide and nothing a pilot hears changed. → [gsx.md](../gsx.md)

## GSX-4

- `GsxGateSelectAnnouncer.Describe` words every `gate.select` outcome that ENDS the request, and `TaxiAssistForm.SelectGsxGateAsync` speaks it queued (`Announce`), never immediate — `Prepared` (naming the stand GSX resolved to), `already_parked`/`already_selected`, `not_found` and `bad_args`, plus a `too_small` warning, an `assigned_to_other` occupied stand (never offering to force it), an `ambiguous` identifier (surfaced, never guessed) and a successful `services_active` retry. Never let a terminal outcome go silent again: `Prepared`, `NotFound`, `BadArgs` and `AlreadyThere` were all silent for one branch, which made "GSX prepared your stand" acoustically identical to "GSX is not running" and to "the request timed out", and the pilot's first evidence either way was the absence of services on arrival. `no_airport`, a double `services_active`, `gsx_not_running`/`auth_required`/`Unavailable`/`TransportFailure` stay silent by design — see `Describe`'s switch for why each. That switch must keep naming its cases explicitly with NO `default:` arm: that is what makes a new `GsxGateSelectOutcome` member silent until someone deliberately gives it a voice. → [gsx.md](../gsx.md)

Corrected 2026-10-10: the rule said `GsxGateSelectAnnouncer` speaks the outcomes. It is a pure, stateless mapper, and its caller speaks the phrase (the announcer's own summary, and `SelectGsxGateAsync` in `Forms/TaxiAssistForm.cs`), so the line now names both and loads on TaxiAssistForm.cs too.

## GSX-5

- What GSX says it selected must be CHECKED against what was sent (`GsxGateSelectResult.RequestedIdentifier`/`RequestedNumber`/`ExpectedUiName` + `ResolvedGateContradictsRequest`), on `Prepared` AND on `AlreadyThere` — `uiGateName`'s uniqueness is AIRPORT-DEPENDENT (98/98 distinct at ENGM; 128 of KJFK's 231 stands and 235 of KATL's 294 share one), so GSX resolving a collision to a different stand is normal operation, not paranoia. THREE identities clear it now, in a load-bearing ORDER, and CLAUDE.md's old "matching EITHER echoed string" wording is retired — restoring it would reintroduce a Critical defect in which a CORRECT selection announces a false wrong-stand warning. (1) `ExpectedUiName` vs the echoed `uiName` DECIDES whenever both sides carry one — that is what closes the collision, since `uiName` is unique for 281 of KATL's 294 stands where `uiGateName` is shared by 235. (2) Below it, a matching echoed `Number` against `RequestedNumber` — the USUAL path now, and without it a correct resolution announced *"Careful: you selected 1, but GSX prepared Ramp 1."* and wrote `resolvedMismatch=true`. It must stay strictly BELOW (1): two stands sharing a number is the exact ambiguity this exists for, so clearing on the number first would disarm the check in its own motivating case. (3) Last, either echoed string (`gate` or `uiName`, trimmed, ordinal-ignore-case), plus the echoed `bglName` — which **CLEARS ONLY** and is deliberately kept OUT of the interpretability guard, so it can turn a mismatch into a match and never the reverse. It is one of the identities we actually send: a `bglName` resend stamps `RequestedIdentifier` with it and leaves `RequestedNumber` null, so with a blank echoed `uiName` neither (1) nor (2) can run and comparing `gate`/`uiName` alone announced *"Careful: you selected …, but GSX prepared …"* over a CORRECT selection — GSX echoing back the very value it had just been handed. Letting it count as "something interpretable" instead would start JUDGING blank-string echoes against a GSX-internal namespace that need not resemble what we sent, i.e. new false alarms. An uninterpretable echo is not a mismatch — a false alarm teaches the pilot to ignore the real one. Never dodge this by sending `index` instead: it is not among the four identity fields §8.14 says `gate.select` accepts, and guessing an undocumented match field is worse than a verified one. The limit is now NARROWER BUT REAL: a stand GSX publishes no `uiName` for (KATL's unnamed GA ramps, 13 of 294) falls through to the NUMBER comparison, which is the weaker guarantee — an echoed number matches whichever same-numbered stand GSX picked — so still never read a clean result on THAT path as "GSX prepared the stand the pilot picked"; it only means GSX did not name a different one. → [gsx.md](../gsx.md)

## GSX-6

- Gate selection is FEATURE-DETECTED on `hello.capabilities` containing `gate`, NEVER on a version number (the vendor guide's own instruction) — and the gate has TWO outcomes that must not be conflated: a NON-EMPTY capability set lacking `gate` is positive evidence of a connected 4.0.1-4.0.7 build (`GateSelectUnsupported`, spoken), while an EMPTY/unreadable set means nothing is known about GSX at all, usually because the Remote API isn't connected (`Unavailable`, silent). Telling the second pilot to install 4.0.8 would send them after a version they may already have. → [gsx.md](../gsx.md)

## GSX-7

- **4.0.8 is named in exactly two user-facing strings and nowhere else in code** — `GsxService.ReasonNoRemoteApi` and `GsxGateSelectAnnouncer.GateSelectUnsupportedMessage`. Never 4.0.1: the Remote API shipped in 4.0.1 but `gate.select` did not, so that number sends a pilot to a build where the Access GSX window works and gate selection silently does nothing. The `GateSelectUnsupported` message is latched ONCE per `TaxiAssistForm` instance (the latch lives on the FORM — `GsxGateSelectAnnouncer` must stay pure and stateless) and must never be routed through `UnavailableReason` or the Access GSX status text: on a 4.0.1-4.0.7 build the GSX window works perfectly and only this one verb is missing. → [gsx.md](../gsx.md)

## GSX-8

- `gsx.log` (`Services/Gsx/Remote/GsxDiagnosticLog.cs`) is the FIRST STOP for "it said nothing"/"it kept saying it". ONE hard rule: NEVER log a per-tick suppression — GSX republishes `/services` at ~1 Hz and the gates discard most of it, so one 186-pax deboard would write ~580 lines and the integration ~18 MB/h, evicting the 5 MB × 3 rotation in about an hour; suppressions are COUNTED per gate and flushed as ONE `ev=summary` per service run (and on `Reset`). The announcer's `Diagnostic` sink stays null-by-default so it remains pure and can never alter speech; its counters are write-only. → [gsx.md](../gsx.md)

## GSX-9

- `gsx.log` logs every GSX announcement IN FULL — invoice totals, ground-connection amounts, handling companies, menu and message prose. GSX is a flight-sim add-on: the money is SIMULATED and the companies are FICTIONAL, so there is no privacy interest to protect. An earlier version tiered the text by `GsxSpeechSource` and hashed anything money-carrying or GSX-authored; that was a category error which made an invoice bug unreadable in the one log built to explain it, and it was removed. `GsxSpeechSource` remains a diagnostic `src=` tag (which composer produced the phrase), NEVER a redaction tier — `GsxDiagnosticLogTests` pins the figures as PRESENT so a well-meaning "fix" cannot re-hide them. The remaining exclusions are: no raw frames (a SIZE rule — `handlerData` is ~1.7 MB, `receipt` embeds invoice HTML + a base64 logo), no gate.select duplication, and no command `args` (a `settings.set` carries `simbrief_username`, the one genuinely real-world value, and it was never needed to diagnose an announcement). → [gsx.md](../gsx.md)

## GSX-10

- `gsx.log` records `ev=publish … route=background|window|none`, and must NEVER assert that a phrase was SPOKEN — background monitoring is OFF by default and `AccessGSXForm` is lazily built, so a default-configured pilot has NO route and the whole GSX stream is discarded by configuration; logging that as "spoke" sends an investigator after a speech-engine fault that does not exist. `route=window` must not claim delivery either (a hidden form drops it, and that layer cannot see visibility). → [gsx.md](../gsx.md)

## GSX-11

- `ev=summary` carries TWO denominators and they must not be conflated: `ticks`/`spoke`/`silent` count TICKS and reconcile (`silent = ticks - spoke`), while `gate*` count REJECTED QUANTITIES and can exceed `ticks` — a live boarding row publishes pax and bags together and the pax branch falls through to bags, so one tick is charged twice (measured: `ticks=187 … gateMilestone=246`). Naming the gate counts as though they were ticks reads as a gate ~8× more aggressive than it is. → [gsx.md](../gsx.md)

## GSX-12

- **Every value in `gsx.log`/`gsx-gate-select.log` is a bare token or a `GsxDiagnosticLog.Quote`d string — no unquoted value may contain a space, and no hand-rolled quoting.** An IDENTIFIER is the one exception to WHICH quoter: `QuoteVerbatim`, never `Quote`. The trim inside `Quote` is right for a phrase and wrong for an identifier — GSX's `uiGateName` is `" Gate 5"` on 281 of KATL's 294 stands and the leading space IS the value, so `identifierSent="Gate 5"` hid the entire reason `gate.select` was being investigated, in the one log built to explain it (live KATL 2026-08-27). For the same "no unquoted space" reason the resolved stand is now quoted `resolvedUiName=`/`resolvedGate=`/`resolvedNumber=`/`resolvedBglName=` tokens rather than the free prose `{UiName} (gate=… )` the shape test did not reach. `route=` once rendered as `window(heard only while Access GSX is open)`, so `grep -o 'route=[^ ]*'` returned `route=window(heard` on the one field that answers "did anybody hear this?"; a token's MEANING belongs on the `SpeechRoute` enum, read once, not glossed into every line. The gate-select log's hand-rolled quoting escaped neither `"` nor `\t`, and the field it wraps is GSX's own vendor free text — so a message containing a quote closed the field early exactly on the malformed input that prompted the report. A new record type gets a NEW `ev=` tag: the socket flap is `ev=connection` because it used to share `ev=session` with the per-flight header while carrying a disjoint field set, and the in-file contract advertised `ev=spoke` — the RETIRED spelling, dropped for asserting audibility — while the code emitted `ev=publish`, so the documented grep returned nothing. → [gsx.md](../gsx.md)

## GSX-13

- **Menu speech is the one GSX source that does not go through `GsxService.Announce`, so `AccessGSXForm` must log it itself** — and the `ShouldAnnounce` judgement must run BEFORE the hidden-form gate, or that gate's log line becomes a per-tick write (`/menu` republishes ~3×/s), which `GsxDiagnosticLog` forbids outright. Judged first, a "nobody heard this menu change" line is low-rate and is the most useful line the path can write. → [gsx.md](../gsx.md)

## GSX-14

- `GsxRemoteConnection.SendAsync` must release its `GsxPendingRequests` registration on EVERY exit — `Abandon(id)` on the timeout arm, and `BuildCommand` inside the `try` so a serializer throw cannot escape past both the registration and every diagnostic write. The store's only other exits are a matching result frame and the whole-store `FailAll` a socket drop triggers, which on a stable socket never comes. Use `task.WaitAsync(timeout)`, never `WhenAny(task, Task.Delay(…))`: the latter armed a 5 s timer per command and never cancelled it on the success path, and `GsxSettingsForm` sends one `settings.set` per undebounced arrow tick. → [gsx.md](../gsx.md)

## GSX-15

- `gsx-gate-select.log` is still the FIRST STOP for "gate not found" and must carry GSX's OWN error `Message` alongside the outcome and raw code — it is the most useful field for diagnosing `not_found`/`bad_args`/`no_airport`, and it was parsed but discarded from the day the result model was written. Never log a raw frame there: frames can carry `handlerData`, which holds user data. → [gsx.md](../gsx.md)

## GSX-16

- Access GSX's menu/tooltip/status/settings/billing/gate-selection/gate-list all run on GSX's own Couatl Remote API (WebSocket, `127.0.0.1:8744`) — GsxService touches SimConnect nowhere at all any more (the last remnant, the read-only `FSDT_GSX_SetGate_*` confirmation client the old menu-walking selector polled, was deleted with that selector: `gate.select`'s own synchronous result payload replaced the polling). State is FLAT (a patch replaces one top-level key outright; never deep-merge — GSX's own client works this way and its patches are coarse, so merging resurrects members GSX just removed), only ONE `ReceiveAsync` may be outstanding on the socket (a second faults it), and a menu index must be re-resolved against LIVE state at pick time, refusing an ambiguous match as well as a missing one (a navigation can land between an entry being read aloud and the key being pressed). → [gsx.md](../gsx.md)

## GSX-17

- `GsxRemoteConnection.Start()` must never REFUSE to start while the previous receive loop unwinds — it CHAINS the new loop onto the old task's completion. `Stop()` deliberately does not join the loop, so a SimConnect disconnect→fast-reconnect routinely lands in that window; a refusal left `GsxService._remoteStarted` latched with nothing running and the whole GSX integration dead for the session while announcing "needs GSX 4.0.8". `GsxService.Stop()` and `OnRemoteConnectedChanged(false)` share ONE teardown (`ResetSessionModels`, which clears the `GsxRemoteState` store too — `Stop()` once did not, and the next hello re-derived every model from the dead session's state, re-announcing its invoice into a dedup set just emptied), both raise `MenuHidden` when a menu was showing, and `OnFrame`/`OnRemoteConnectedChanged` drop a marshalled continuation whose lifecycle generation is stale. → [gsx.md](../gsx.md)

## GSX-18

- A service row's `statusText` carries GSX's PER-VEHICLE ground-crew narration ("front loader raising belt", "rear stairs in position", "front train on the way") and it is announced by `GsxServiceAnnouncer.StatusNarrationPhrase` via `GsxStatusNarration` — NEVER by the tooltip alone, which is where it lived unspoken from the Remote API migration until 2026-08-18. The old transport scraped ONE tooltip string and read the lot; the migration split it into the `message` banner (which got an announcer) and per-row `statusText` (which did not). THREE lines must be dropped and each for its own reason: a QUANTITY line (`pax 0/93`, `bags 100%`) belongs to the typed announcers; the BUS line belongs to `detail.busPhase`, which GSX publishes in BOTH places and `BusPhrase` already speaks, so keeping it doubles every bus callout; and a line differing only in a standalone digit run is a countdown tick (`GsxPhraseGate.IsDigitRunOnlyChange`, or the embedded "ETA 33 secs" reads once a second). The quantity filter is ANCHORED — "rear loader leaving while 5 boarded" must stay narration. Clauses split on COMMAS as well as newlines (GSX ships the block as one comma-separated line; newline-only split re-read the whole block on every vehicle move — 55 of 83 clauses repeated, live), with a negative lookahead so a thousands separator never splits a number. `GsxPhraseGate.IsDigitRunOnlyChange` additionally collapses a whole RUN of time-duration terms, or a countdown crossing a unit boundary ("ETA 1 min 5 secs" vs "ETA 55 secs") reads as news — spelled-out time units ONLY, never bare m/s/h, since "Start after 49.0 meters" is a distance. The call sits OUTSIDE the one-phrase-per-tick else-chain in `Update`: the chain arbitrates three views of ONE fact, the crew narration is a different fact, and chaining it lets a pax milestone swallow a loader. → [gsx.md](../gsx.md)

## GSX-19

- Every GSX announcer is BASELINE-FIRST and the hello frame is NOT a baseline (it carries no state keys — the snapshot after it is): `ApplyReceipt` records a receipt already in GSX's state at a session's first snapshot without speaking it (`_receiptsBaselined`, reset ONLY with the digest set in `Stop()` — a plain socket drop keeps both, and the digests are payload hashes that are no longer cleared on the Couatl 1→0 edge either); the COUNTDOWN/REPEAT filter is ONE general rule (`GsxPhraseGate.ShouldAnnounce`, shared by the message slot and the service BUS PHASE) applied to TEXT phrases only — never a quantity whose number IS the message (pax/bags/fuel stay milestone/time-gated; collapsing their digits would silence real readings). GSX embeds a live countdown in `detail.busPhase` ("on the way, ETA 15 secs"), which used to re-announce every second; it now speaks once, ticks fall through so pax/bags still announce. The "message"-slot announcer suppresses a phrase ONLY when that phrase is the slot CYCLING BACK to one it already showed (`GsxSlotRotationTracker`), NEVER on the strength of which service is running — no per-service gate, in either its blanket "any service is performing" form or the per-row `GsxServiceState.PublishesTypedProgress` form that replaced it (both deleted). Both failed the same way one level apart: a service's ground-crew narration ("Operator walking to pump", "Lowering platform") rides the SAME slot as its pax/bags/fuel figures, so any row-level yes throws the prose away with the ticker — measured on a live gsx.log at NINE performing windows of Refueling/Boarding/Deboarding, SEVEN with not one spoken slot line, 1 h 00 m 49 s of silence. Splitting by TEXT fails too ("drop anything with a digit" takes "Waiting for your action: open R Entry 5"). The split is STRUCTURAL: a ticker re-shows a phrase only after OTHER phrases intervened, an action nag re-shows the SAME phrase with nothing between, so a phrase matching an EARLIER remembered phrase but NOT the most recent is a rotation and stays silent and everything else falls through to `GsxPhraseGate`. RECORD EVERY PHRASE GSX OFFERS, spoken or not, or a suppressed lap leaves no trace and the next lap reads as a nag; blanks are never recorded and never clear the history (a blank clearing it is exactly how the single-predecessor rule let the ticker through). The ticker's FIRST lap speaking is the accepted cost, not a bug. Pushback (`Departure`) and de-icing carry no quantity at all — which is what made a row-level gate look workable — and for them the slot is the ONLY channel carrying "set the parking brake"/"release the parking brake", while `detail.phase` has no consumer. `RecomputeTooltip` is NOT gated at all and never was part of this rule. The caller resets on a blank slot so a repeated reminder is spoken again, and the Couatl 1→0 edge must clear `_lastAnnouncedMessage` + the tooltip as well (an in-place engine restart keeps the socket, so `ResetSessionModels` never runs and the restarted engine's re-shown banner was compared against the dead session's text and swallowed); `GsxBillingTimerAnnouncer` is fed ONLY from the snapshot and `billing` patches and baselines only when a `billing` key was actually published. Refuel quantity comes from `detail.fuel.{current,aircraftTotal,unit}` — the generic `progress` object never carries it — spoken as "N kg loaded, aircraft M kg", TIME-throttled (30 s) with NO revision bypass: `detail.fuel.target` ROLLS with `current` in progressive mode (live, 1 Hz), so it is never spoken and never breaks the interval; pax/bags stay milestone-gated. → [gsx.md](../gsx.md)

Split out on 2026-10-09: GSX-25 (which resets the receipt digests, the baselines and the message slot). This text keeps it as written; it has its own section below.

## GSX-20

- "GSX available" for the `.ini` gate overlay / deice pads / profile stop positions is `GsxService.CouatlStarted` OR `SimConnectManager.GsxCouatlStartedLVar` (`L:FSDT_GSX_COUATL_STARTED`, one fixed def on the main SimConnect connection) — never the Remote flag alone: those are local-file features every GSX build supports, and the Remote-only gate silently floored them at 4.0.1 against the "neither is a version floor" rule. `GsxService` itself still touches SimConnect nowhere. → [gsx.md](../gsx.md)

## GSX-21

- `SettingsChanged` fires on every SNAPSHOT and `/settings` patch — never on the hello (an empty-store hello rebuilt an open settings window twice per reconnect) — and `AccessGSXForm` may CREATE the settings window only in answer to a recent `C` press (`_settingsRequestedUtc`, 10 s, consumed on use, cleared on close): without the gate every reconnect after Access GSX had been opened once popped the window and `Activate()`d it mid-flight. `C` opens AT ONCE from the held schema and `GsxService.OpenSettings` AWAITS `settings.get`'s RESULT (which the pending-request matcher consumes, so `OnFrame` never sees it) and feeds `payload.settings` back through the frame path — a gate that waited for GSX to volunteer a `/settings` patch left `C` doing nothing. → [gsx.md](../gsx.md)

## GSX-22

- `GsxSettingsForm` rebuilds ONLY on a STRUCTURAL schema change (`GsxSettingsSchemaSignature.Structural` — never the live `NumericValue`/`TextValue`); a value-only republish is applied IN PLACE under `_applyingRemoteValues` and NEVER into a control that `ContainsFocus`. GSX echoes every `settings.set` as a `/settings` patch, so a value-inclusive signature disposed the focused control and yanked focus to the section list on every arrow-step. → [gsx.md](../gsx.md)

## GSX-23

- `GsxMenuAnnounceResolver.ShouldAnnounce` returns false whenever the CURRENT menu is empty — the "GSX Menu hidden" prompt is read, never spoken (menu-hide is silent by design), and `MenuChanged` fires on both hello and snapshot of every connect. `OnMenuChangedUi` still re-renders while hidden, speaks a hidden-window menu change only under `GsxService.AnnounceWhenFormHidden` (the background-monitoring setting every other background GSX announcement obeys — a menu GSX opens on its own must reach a pilot who opted in), and there is deliberately NO re-render in `VisibleChanged` (it would re-snapshot the live `Menu` that `OnMenuHiddenUi`'s reset keeps out of reach). → [gsx.md](../gsx.md)

## GSX-25

- Every GSX announcer is baseline-first (GSX-19). The receipt digests and `_receiptsBaselined` are reset ONLY together, in `Stop()` (`ResetSessionModels(clearReceiptDigests: true)`): a plain socket drop keeps both, and the digests, payload hashes, are no longer cleared on the Couatl 1→0 edge either. That edge, an in-place engine restart that keeps the socket so `ResetSessionModels` never runs, clears `_lastAnnouncedMessage`, the slot rotation and the tooltip, so the restarted engine's re-shown banner is not swallowed as a repeat of the dead session's; it deliberately does NOT reset `_messageBaselined`: the session continues, and re-baselining would record, not speak, the restarted engine's first message. A blank slot resets `_lastAnnouncedMessage`, so a reminder shown again after a gap ("release parking brake") is spoken in full, but never clears the rotation history: a blank clearing it is how the single-predecessor rule once let the ticker through. → [gsx.md](../gsx.md)
