# Visual guidance, hand fly and the liftoff handoff — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/visual-guidance.md`, which Claude Code loads when it reads matching code. Background: [visual-guidance.md](../visual-guidance.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## VG-1

- The liftoff handoff's cue WORDING and the announcement mute that protects it are ONE decision in `Services/LiftoffHandoffBreadcrumb` (`For(...)` returns both) — never split them back into a phrase and a separate duration, and never size a mute by ESTIMATE. Every mute there is derived from a phrase rendered through `System.Speech` at `Rate = 0` (what `ScreenReaderAnnouncer` hardcodes, so the only SAPI rate this app produces) with trailing silence trimmed, plus about a fifth: "Airborne." 0.63 s → 900 ms, "Airborne, hand fly." 1.68 s → 2000 ms, "Airborne, hand fly, quick keys failed." 3.09 s → 3500 ms. A words-per-minute estimate does NOT work here and has already misled once — it put "Airborne, hand fly." at ~1.05 s when it is 1.68 s, and a 1500 ms mute was shipped against that guess. Two costs dominate and neither is word count: SAPI's inter-sentence pause is ~0.9 s (the two-sentence "Airborne. Hand fly." does not BEGIN its second clause until 1.56 s, so under a 1500 ms mute those words were never spoken at all), and a spelled letter list with commas ("H, V, Q") is far slower than it looks — it was most of why the old quick-keys warning ran 8.15 s. The ceiling on every mute is 3504 ms, the hole measured on the live Fenix A320 takeoff this area exists to close; when a phrase will not fit under it, SHORTEN THE PHRASE, never widen the mute. The quick-keys warning is now the single shared fragment "quick keys failed" (`QuickKeysWarning`) — FAILED, not "off", because it is an error condition and there is no such setting for a pilot to have turned off, used by BOTH the rotation cue and `MainForm.Hotkeys`'s manual-arm announcement so one condition never gets two phrasings; it names neither the keys nor a remedy, and must not regain them — hand fly captures NINE keys (H, V, Q, S, D, B, P, A, F), so the old "Use output mode for H, V, Q" was wrong as well as long, and which keys are captured belongs in the docs rather than in an announcement spoken over a rotation. The mute never affects the TONE, only the spoken callouts. ⚠️ CORRECTION to an earlier telling: the phrase and the mute never actually drifted — `git log -S` shows 3500 ms was introduced already sized for the phrase it shipped with, so the 3.504 s hole was the mute working exactly as designed, and it had to shrink because it lands on ROTATION. The cue deliberately does NOT say takeoff assist stopped, and the "centerline tone stopping says it too" justification is FALSE in three configurations (legacy mode builds no tone; the default heading-tone-threshold holds it at volume 0 through an on-centerline rotation; a pre-armed hand fly's own tone masks it) — an accepted gap, recorded so it is not re-derived as sound. → [visual-guidance.md](../visual-guidance.md)

## VG-2

- **Every path that activates hand fly or visual guidance must leave OUTPUT HOTKEY MODE first.** `RegisterHandFlyHotkeys`/`RegisterVisualGuidanceHotkeys` early-return false while `outputHotkeyModeActive` is set, skipping quick-access registration wholesale — and NOTHING re-acquires those keys when output mode later exits, so all nine stay dead for the rest of the session while the pilot has been told only "quick keys failed". `HotkeyManager` guards its own two entry points (`HOTKEY_HAND_FLY_MODE`, `HOTKEY_VISUAL_GUIDANCE`) by calling `DeactivateOutputHotkeyMode()` before triggering; the liftoff auto-handoff bypasses the dispatcher by calling `handFlyManager.Toggle()` directly, so it calls `hotkeyManager.ExitOutputHotkeyMode()` itself. Output mode has NO auto-timeout ("stays active until used or escape pressed"), so a pilot who armed it and was then distracted really can still be in it at rotation. The call is SILENT by construction — `OnOutputHotkeyModeChanged` speaks only for `Activated`/`Cancelled` and this raises `Deactivated` — which is what makes it safe on a path that must not gain speech; keep it that way. → [visual-guidance.md](../visual-guidance.md)

## VG-3

- Visual guidance must NOT require HandFly mode — never reintroduce a `!handFlyManager.IsActive` gate; that produced a confusing three-tone overlap. → [visual-guidance.md](../visual-guidance.md)

## VG-4

- HandFly's tone must auto-mute while VG is active (`SuppressAudio`/`ResumeAudio`) — VG's two tones share HandFly's Hz/pan mapping, so all three together is acoustically incoherent. → [visual-guidance.md](../visual-guidance.md)

## VG-5

- The quick-access hotkey set must stay reference-counted/shared between HandFly and VG — never split it back into per-mode key sets, which caused a double-register conflict. → [visual-guidance.md](../visual-guidance.md)

## VG-6

- There is no single-tone VG mode — never reintroduce a flag to gate off the current tone; the dual-tone is the design. → [visual-guidance.md](../visual-guidance.md)

## VG-7

- Always route `cachedBank` through `VisualGuidanceManager.StandardBank()` before any tone/bank-error use — SimConnect's `PLANE_BANK_DEGREES` is left-positive but the tone API is right-positive. → [visual-guidance.md](../visual-guidance.md)

## VG-8

- `VisualGuidanceManager.Initialize` must stay idempotent: it disposes any existing tones first (`DisposeTones()`) — don't remove that guard, and never replace it with `Stop()`, which announces "Visual guidance off" just before Initialize's own "Visual guidance active" and nulls the state Initialize is about to set. → [visual-guidance.md](../visual-guidance.md)

Corrected 2026-10-08: the guard is `DisposeTones()`, not `Stop()`; following the old wording would bring back the off-then-active announcement pair. Evidence: `VisualGuidanceManager.Initialize`, whose comment says not to call `Stop()` and which calls `DisposeTones()`.

## VG-9

- Never re-add a `Start()` call inside `Initialize` — tone start must stay deferred to the first `ProcessUpdate` or a brief fused-tone glitch reappears. → [visual-guidance.md](../visual-guidance.md)

## VG-10

- The follower (current) tone must only start if the desired tone started — don't reorder `StartTonesIfNeeded`'s try blocks. → [visual-guidance.md](../visual-guidance.md)

## VG-11

- VG auto-deactivation on the airborne→on-ground edge must not be gated on GS or any other condition — landings of any speed must trigger it. → [visual-guidance.md](../visual-guidance.md)

## VG-12

- Never split VG's lateral and vertical guidance into separate tones — the matching idiom needs one oscillator per role (desired + current). → [visual-guidance.md](../visual-guidance.md)

## VG-13

- Desired and current tone waveforms must default to different shapes (triangle + sine: `UserSettings.VisualGuidanceToneWaveform` and `VisualGuidanceCurrentToneWaveform`, both pilot-settable in `HandFlyPanel`) — identical waveforms at a matched state phase-cancel exactly when the pilot most needs the difference audible. → [visual-guidance.md](../visual-guidance.md)

Corrected 2026-10-08: triangle and sine are the defaults of two user settings, not fixed values. Evidence: `UserSettings.VisualGuidanceToneWaveform` (Triangle) and `VisualGuidanceCurrentToneWaveform` (Sine), set from `Forms/Settings/HandFlyPanel`.

## VG-14

- Never bake aircraft-specific VG numbers back into `VisualGuidanceManager` as consts — they belong on `IAircraftDefinition.GetVisualGuidanceProfile()`. → [visual-guidance.md](../visual-guidance.md)

## VG-15

- `GlideslopeAltitudeBiasFt` and `FlareAltitudeBiasFt` are applied in different code paths (glideslope error vs. phase detection) and were measured separately — never collapse them into one shared constant. → [visual-guidance.md](../visual-guidance.md)

## VG-16 (retired: the descent clamp went with the vertical-speed law in stage 5; the path angle limit replaced it)

- Was: the `MAX_DESCENT_RATE_FPM` safety clamp must stay dynamic (`min(-1500, natural×1.3)`) so a legitimate steep-approach descent rate (e.g. a 5.5° ILS) is never clipped. Stage 5 of the visual guidance redesign (2026-11-06) replaced the vertical-speed law with a path angle: the target descent angle stays between level and the runway's own glide path angle + 2° (`VisualGuidanceVerticalTuning.PathLimitDeg`), so a steep runway's descent is never clipped (`VisualGuidanceVerticalTests.Steep_runway_uses_its_own_angle`).

## VG-17 (retired: the FPM PID went with the vertical-speed law in stage 5; VG-24 pins the vertical sign)

- Was: the pitch PID's `fpmError`/`fpmErrorRate` coefficients must stay POSITIVE (same sign as the error); the old leading minus produced wrong-direction guidance masked by tight-tracking autopilot tests. The PID went in stage 5 of the visual guidance redesign (2026-11-06); VG-24 pins the sign of its replacement.

## VG-18

- Visual guidance must fail as a missing audible reference, never as a wrong steering command. Tone work leaves the guidance math (the vertical law, the phase machine, the lateral arc capture and precision track) alone. → [visual-guidance.md](../visual-guidance.md)
- Rewritten 2026-11-04 for the visual guidance redesign, which changes the guidance math on purpose. A deliberate change to it keeps left and right as `VisualGuidanceHarnessHookTests` pins them (right of final and parallel banks LEFT toward the line; right of final on an intercept heading banks RIGHT at capture, on two runways), and is measured first in the VirtualPilot approach harness against the baseline with `compare_approach.py` ([virtual-pilot.md](../virtual-pilot.md), "Approaches"). If a sign test fails, never flip the test: work out by hand which way the aircraft has to turn. The original wording ("tone work must leave the PID math, phase machine and lateral arc capture untouched") kept its intent: a broken tone is silence, never a wrong command.

## VG-19

- VG's manual-query grace window must only suppress the bank callouts — phase changes and distance callouts must still fire during a manual hotkey readout. → [visual-guidance.md](../visual-guidance.md)
- Originally (before 2026-11) the window covered "the two chatty per-second callouts (bank guidance, centerline deviation)". The centreline deviation callouts ("0.4 nm left of center", "on runway center") were removed in stage 3 of the visual guidance redesign, because F now speaks the sideways position in every phase (VG-22; decided with the owner, 2026-11-02, on that condition). `VisualGuidanceCalloutTests.No_centreline_callout_is_ever_spoken` pins the removal.
- Inside the window the bank callout gate keeps tracking but may not speak (VG-21), so when the window ends a callout that came due during it speaks the error as it is then, at once.

## VG-20

- Every rate limit, smoothing filter and derivative in `VisualGuidanceManager` runs on the measured frame time through `VisualGuidanceTiming`: a rate limit moves at most rate × dt, a smoothing factor is per second (α = factor^dt), and a derivative is a rate over a time window (`VisualGuidanceWindowedRate`), never a frame-to-frame difference or a sample count. → [visual-guidance.md](../visual-guidance.md)
- Why: `StartVisualGuidanceMonitoring` requests the visual guidance data at `SIMCONNECT_PERIOD.SIM_FRAME`, and MainForm calls `ProcessUpdate` on every frame's AGL event (per-frame since at least 2025-11-16). Every limit and filter had been written for one update a second, so at 30 frames a second the 3°/s bank limit and 2.5°/s pitch limit allowed about 90°/s and 75°/s, the 0.7 vertical-speed smoothing averaged over about 0.1 s instead of 3 s, the vertical-speed damping term divided a frame-to-frame change by about 0.033 s, and the 5-sample cross-track window covered about 0.15 s instead of 4 s.
- Measured in the VirtualPilot approach harness at the stage 1 baseline: the commanded pitch's RMS rate of change on a clean jet final was 0.153, 0.275 and 0.761°/s at 20, 30 and 60 frames a second, and with assumed sensor noise 27.6°/s at 30 and 90.1°/s at 60. A command on real time reads about the same at every frame rate.
- The numbers are the 1 Hz design's, now per second: the bank and pitch rates come from `VisualGuidanceProfile` (VG-14), the vertical-speed and AoA smoothing are 0.7 per second, the cross-track rate is taken over 4 s and smoothed at 0.85 per second, and the vertical-speed error's rate over 1 s. From stage 2 to stage 5 the flare's pitch limit was an exception, 10°/s, because at 1.5°/s on real time the cue took 2.7 s to reach the fixed flare pitch, after a jet's wheels touched. Stage 6 (the flare, VG-27) removed it: the flare's profile starts where the aircraft is, so the cue no longer jumps to a fixed pitch, and it runs at the profile's pitch rate (2.5°/s on the A320; in the harness the jets' flare cue moved about 1.1°/s at most). `VisualGuidanceFlareManagerTests.The_flare_cue_is_the_same_at_every_update_rate` and `VisualGuidanceRealTimeTests.The_flare_cue_starts_where_the_aircraft_is_at_any_update_rate` pin it.
- `VisualGuidanceTiming.FrameSeconds` caps dt at 1 s, so a pause, a stalled frame stream or a menu moves the command no more than one second's worth, and counts a backwards clock step as 0, never a reverse step. A `VisualGuidanceWindowedRate` given a sample earlier than its newest (the clock stepped back) starts afresh, so the damping rates never read samples stamped in the future. Two updates at the same instant (SimConnect can deliver two frames in one message-pump turn) therefore move nothing the second time.
- The first update after `Initialize` takes the guidance's command with no rate limit: there is nothing yet to be continuous with, and the guidance tone should start where the guidance says instead of ramping up from level. `VisualGuidanceRealTimeTests` pins all of this, each test on its own fake clock (`ClockForHarness`).

## VG-21

- Bank callouts ("3 right", "1 left", "matched", "Matched, level"; the last was "On commanded path" until 2026-11-06, when the owner said it threw them off, expecting "matched") are spoken only when `VisualGuidanceBankCalloutGate.Next` returns one; `VisualGuidanceManager.AnnounceBankGuidance` feeds it every update and speaks what it returns, interrupting. With the error e = desired − actual: "matched" is entered at |e| ≤ 0.4° and left only at |e| ≥ 1.0° (a band, not a wait), "matched" and "On commanded path" count as one callout, and otherwise the callout is the error rounded to a degree, at least 1. A callout is spoken the update it differs from the last one spoken, never repeated while it stays the same, and only when the caller may speak: outside a manual-query grace window (VG-19), outside the hold of one of visual guidance's own lines, and not while deciding or in a deliberate turn while joining (VG-23). The first update it may, it speaks the error as it is then. → [visual-guidance.md](../visual-guidance.md)
- The owner, 2026-11-06, after the first sim flight (Fenix A320, KATL): "changing the way bank commands read was a bad idea. now it waits then tells us the command. before it said it instantly. we need to make it instant again." Stage 3's holds (0.25 s, 1.5 s under a degree), its fixed 1 s gap and its wait for a steady bank past the tone range were removed. The recording showed the cost of the wait: in a turn the owner sat at 10° of bank for about 8 s while 25° was asked, since both tones were pinned past the 5° tone range and "15 right" waited for the bank to settle. The matched band (0.4° in, 1.0° out) and the holds for visual guidance's own lines stay: neither delays a change in the error. The bullets below are stage 3's reasons, kept as history; the harness's quieter-callout measure (stage 3's check B) no longer holds, by the owner's decision.
- Why stage 3 gated them: the stage 1 harness heard "3 right", "6 right", "9 right" within 0.07 s, a median of 52 lines a run cut off by the next, and callouts flipping between "matched" and "1 right" around half a degree many times a second, each cutting off the one before before "left" or "right" was spoken. The gap is a fixed second, not an estimate of speaking time, because VG-1 forbids sizing anything by estimate.
- The spec (2026-11-02) said "an error within about 2°" for the 0.25 s hold. The owner changed it on 2026-11-04 to the tone bank range: a gust that knocks the aircraft 2 to 4° must be heard at once, and only an error past what the tones can show waits for the bank to stop changing. Their worry: gated callouts make small corrections slower to hear.
- Measured in the VirtualPilot GUST runs with the callouts before the gate (`approach_stage2_v2`): the first callout came 0.04 to 0.12 s after a knock began, while it was still building (a 4° knock was spoken "1 right", "2 right", "3 right", "4 right" within 0.27 s, each cutting off the last); a pilot steering by speech alone took about 11 s to recover from a 4° knock, because the old callouts stayed silent while the error rounded to the "1" already spoken ([virtual-pilot.md](../virtual-pilot.md), "Gusts with today's callouts").
- Each callout is said once, never repeated on a timer. On 2026-11-04 a 3 s repeat of an unchanged error callout was built and measured, after the harness's pilot who steers by speech alone (it hears no tones) sat 0.6 to 1.4° off in silence once "1 right" had been said; the owner removed it the same day: "I just want the degree to be announced as soon as plane goes off course while in final." Since 2026-11-06 drifting a degree off after "matched" is spoken the update the error reaches 1° (stage 3 waited a quarter of a second), which `Drifting_a_degree_off_after_matched_is_spoken_when_it_reaches_a_degree` pins. Below a degree the tones show the error, which the guide calls very sensitive near the matched state.
- A bank callout interrupts (`AnnounceImmediate`), and with NVDA or SAPI that drops whatever is queued. So each of visual guidance's own lines holds the bank callouts back for that line's measured speaking time, measured as VG-1 measures (`System.Speech` at `Rate = 0`, trailing silence trimmed, plus about a fifth), through the manual-query window `routineAnnouncementsSuppressedUntil`, which a line only ever extends. Measured on 2026-11-04 (the `HOLD_` constants in `VisualGuidanceManager`): "Visual guidance active, runway 27L" 3.31 s → 4.0; "Extending, turn to heading 175" 3.67 s and "Intercepting final, 1.8 miles to final" 3.37 s → 4.4 for both; "Established on centerline" 1.67 s → 2.0; "On vertical profile" 1.30 s → 1.6; "2.5 miles behind threshold" 2.38 s → 2.9; "Approaching threshold" 1.26 s → 1.5; "5 miles" 1.03 s → 1.3; "Touchdown" 0.72 s → 0.9; "Flare" 0.49 s → 0.6; "Visual guidance off" ends guidance and holds nothing. `VisualGuidanceCalloutTests.A_bank_callout_waits_for_the_activation_and_phase_lines` and `A_bank_callout_waits_for_flare_to_be_spoken` pin it. A new or reworded line is measured the same way. Before this, the stage 3 review's traces showed bank callouts cutting off the activation sentence, "Extending, turn to heading …", "Flare" and "Touchdown".
- Stage 4 (joining final, 2026-11-04) removed the Extending, Intercepting, "Established on centerline", "On vertical profile" and behind-the-threshold lines, and measured its own the same way: "On final" 0.70 s → 0.9; "Joining final" 0.90 s → 1.1; "Vectoring to final" 1.15 s → 1.4; "Unable to join final from here" 1.89 s → 2.3; "Turn onto final in 30 seconds" 2.13 s → 2.6; "Turn onto final in 15 seconds" 2.23 s → 2.7; "Turn onto final" 1.11 s → 1.4; "Heading does not cross final" 1.68 s → 2.1; "Established on final" 1.39 s → 1.7; "5 miles out" 1.11 s → 1.4; "3 miles out" 0.99 s → 1.2; "1 mile out" 0.85 s → 1.1. The activation sentence measured 3.31 s again. The simple pattern (2026-11-05) added "Turn base", 0.78 s → 1.0, and removed "Unable to join final from here".
- Since stage 4 a queued line's hold starts where the previous queued line's ends, because the screen reader speaks them one after the other: Ctrl+V's activation sentence (4.0 s) followed by "Vectoring to final" (1.4 s) holds the bank callouts 5.4 s, not 4.0. Before, two lines queued together held only for the longer of the two, and a callout could cut the second. An interrupting line clears the queue, so the next queued line's hold starts after it. `A_bank_callout_waits_for_the_activation_and_phase_lines` pins the 5.4 s.
- While visual guidance waits for the wings to be nearly level after Ctrl+V (the Deciding phase, VG-23), the command is the aircraft's own bank, so the bank callouts may not speak; the gate keeps tracking.
- A mile call is said only when its mark is crossed. Before stage 4, pressing Ctrl+V inside 5 nm said "5 miles" at once (and at 0.3 nm "5 miles", "3 miles", "1 mile" a second apart), which with queued holds would also have held the bank callouts for all three lines. `A_mile_call_is_said_only_when_its_mark_is_crossed` pins it.
- On the simple pattern's downwind and base no mile call is said: a mark passed there is dropped, and armed again once the distance is 0.3 nm back above it, so the pattern's flight out past 5 nm brings the calls back on final. The far-side harness jets otherwise heard "3 miles out" flying over the field away from final. `The_mile_calls_wait_for_final_on_the_pattern` pins it.
- F's own window stays 3 s (VG-19), though F's sentence on final takes 8.75 s at `Rate = 0`: a callout cuts it only when the aircraft goes off course during the readout, and saying that at once is the owner's priority.
- `VisualGuidanceBankCalloutGateTests` pins the timing (VG-21, since 2026-11-06): an error spoken on the first update and never repeated, a sub-degree error spoken at once as one degree, every degree of a roll spoken as it changes, a large error spoken without waiting for the bank to settle, quick changes each spoken with no gap, a 2° knock spoken as it builds, an error hovering around half a degree settling on "matched", and a callout held back by a manual readout speaking the current error when the window ends.

## VG-22

- F (`HotkeyAction.ReadTargetFPM`, a quick-access key while visual guidance is on) speaks `VisualGuidanceManager.GetStatusReadout()`, which `VisualGuidanceStatusText.Compose` builds: the phase first, in the words visual guidance speaks it, then the sideways position, then the vertical. For example "On final, 6.2 miles. On the centreline. 40 feet high, target 750 down.", "Joining a 6.4 mile final. 30 degree intercept, turn in about 85 seconds.", "Flare, 20 feet. On the centreline. Target 350 down." (the flare's target since stage 6, to 50 fpm). Before the first update has placed the aircraft it says "Visual guidance starting.", never "0.0 miles". Every number is culture-invariant ("6.2", "2,260"), tested under sv-SE and de-DE. → [visual-guidance.md](../visual-guidance.md)
- Rule: whatever visual guidance speaks on its own in a phase belongs in that phase's readout, so every automatic announcement can be heard again from one key. The redesign's spec calls this "one key answers everything" (2026-11-02), and it is the owner's standing rule for anything the app speaks on its own.
- The centreline deviation callouts were removed on that condition (VG-19): F gives the sideways position in every phase, on final included. Cross-track is signed as the lateral law takes it (+ right of the centreline facing the runway); `VisualGuidanceCalloutTests.Right_of_the_centreline_reads_right` pins the side.
- The spec says F works "in the quick-access set while visual guidance is on, and in Output mode". Output mode's F is Fuel Quantity, so F stays a quick-access key only; which Output-mode key, if any, reads the status is the owner's decision (asked at the end of stage 3, 2026-11).
- Stage 4 (joining final, 2026-11-04) added a sentence for each new phase. Waiting for wings level: "Visual guidance starting, waiting for wings level." Joining: "Joining final 6.4 miles out. 30 degree intercept, turn in about 85 seconds." (the time left out when it is not known); on a heading that no longer crosses final, "Joining final. Heading does not cross final. Final 2.6 miles to your left."; after the turn, "Joining final, turning onto final. 0.2 miles right of final." Vectoring: "Vectoring to final, joining 6.2 miles out. 2.0 miles right of final, turn in about 85 seconds. 2,260 feet high, target 1,500 down."; after the turn, "Vectoring to final, turning onto final. On the centreline. On path, target 750 down." The simple pattern (2026-11-05) names its leg: "Vectoring to final, downwind, joining 6.0 miles out. 3.0 miles right of final." and "Vectoring to final, base, joining 6.0 miles out. 1.5 miles right of final, turn in about 10 seconds.", with no vertical half: there the pitch tone sits on the aircraft's own pitch until the vertical path (stage 5) plans the pattern's descent, so the old law's target is not what the tone shows. Its "joining" distance is the sum that placed the base (`VisualGuidanceJoin.PatternJoinAlongNm`), and the countdown runs on the base. "Unable to join final from here" went with it.
- 2026-11-06, the owner: "joining final 6.4 miles out" was vague. The distance is now said as the length of final in the pilot's and ATC's words, the phase word still first: "Joining a 6.4 mile final.", "Vectoring to a 6.2 mile final.", "Vectoring to a 6.0 mile final, downwind." and "..., base.", with "an" before eight, eleven and eighteen ("an 8.8 mile final"). The sentences above are stage 4's record. The sentences without a distance ("Joining final, turning onto final.", "Joining final. Heading does not cross final.") and the spoken phase lines ("Joining final", "Vectoring to final") are unchanged.
- "Joining 6.4 miles out" is where the aircraft will be lined up on final for the heading and speed flown now (`VisualGuidanceJoin.JoinAlongNm`, from the intercept being flown when joining, the chosen angle when vectoring, counting the turn onto it as the decision does). The owner asked for it on 2026-11-04; it replaces the spec's "Final 1.8 miles ahead", which the time to the turn already covers. The intercept is rounded to 5°, the time to 5 s, each at least 5. Until 2026-11-07 "to your left" or "right" was the side of the aircraft's track the nearest point of final lay on (the threshold, once past it); see the last bullet. The countdown and F use the same time (`VisualGuidanceJoin.SecondsToTurn`).
- Stage 5 (the vertical path, 2026-11-06) gives joining and vectoring, every leg, a vertical half: the path's altitude at the join point (MSL, what the altimeter, A and ATC use, to 10 ft) and the height against it now, "Path there 2,470 feet, you're 300 high." ("you're on it" within 30 ft); vectoring adds BA's target ("..., target 800 down."), joining none, the altitude being ATC's or the pilot's (plan decision 8). A heading that does not cross final still says no height. Its warnings are spoken on their own, so F repeats them in place of the height: "Path there 2,470 feet, you'll be 1,700 feet high at final." while joining, and on final "Too high, 600 feet above the path, target 1,250 down." or "Too low, 400 feet below the path, target level.". `VisualGuidanceStatusTextTests` pins every sentence and line, including under sv-SE and de-DE.
- 2026-11-07, the owner heard "Vectoring to a 6.0 mile final, downwind. 6.1 miles left of final." as 6.1 miles of final left to fly. Joining and vectoring now say where the extended centreline is from the cockpit (`VisualGuidanceStatusText.CentrelineFromYou`): "Centreline 6.1 miles to your left", "to your right", "ahead" within `AheadBehindDeg` (30°) of the nose, "behind" within it of the tail, from `VisualGuidanceStatus.CentrelineBearingDeg`, the bearing of the line's nearest point from the track (straight across to the line, either side of the threshold). The owner chose "Centreline" over "Final" (the word F uses on final, so the line has one name) and the same form for joining ("Final 2.6 miles to your left" became "Centreline 2.6 miles to your left"). "Ahead" exists because on a base leg the aircraft flies straight at the line, where a side would be a rounding. On final, in the flare and at touchdown F keeps the side facing the runway ("0.1 miles left of the centreline"); nothing on final speaks of the centreline by itself, and the owner wants it kept so. Pinned by `VisualGuidanceStatusTextTests.The_centreline_is_placed_from_the_cockpit` (the 30° edges), `VisualGuidanceJoiningTests` (the downwind "to your right", the base "ahead") and `VisualGuidanceCalloutTests.Right_of_the_centreline_reads_right` (parallel inbound: right of final, the centreline to the left).

## VG-23

- While joining final, visual guidance holds the heading being flown, ATC's or the pilot's: the desired bank is 0 until "Turn onto final". The turn comes when the capture law, clamped to the intercept being flown, first asks 5° of bank toward final (`VisualGuidanceJoin.TurnCueCrossNm`), or within 0.05 nm of the line. It never asks for a steeper intercept than the one flown, and Joining never becomes Vectoring by itself; pressing Ctrl+V off and on decides again. → [visual-guidance.md](../visual-guidance.md)
- Why: it was the owner's first complaint about the original guidance. On an ATC intercept heading it demanded its own 60° or 45° intercept (the stage-4 harness's SHALLOW runs: a 15° cut turned into a 60° one and joined final 14 nm out instead of 8.8). FlyByWire's A320 holds the flown track the same way: its localizer capture clamps the desired intercept to the current one, so far out it asks for nothing, and LOC* engages when the law asks 5° of bank (FmgcOuterLoops.cpp, FmgcComputer.cpp; notes in the redesign's spec folder). The spec, piece 3, calls this state Waiting; the owner chose to speak it "Joining final" (2026-11-02).
- Flying the law's small early bank before the turn would let a pilot who follows it shrink their own intercept and keep putting the turn off, so before the turn the law runs only to find the turn. At the turn the intercept being flown is frozen, and the law's limit from then on is that intercept, at least 30°.
- Pressed in a turn (the bank 5° or more), visual guidance decides nothing yet: both tones sit on the aircraft's own attitude, and the decision comes at the first update with the bank under 5°. While deciding, joining and on the simple pattern's downwind and base, the pitch tone sits on the aircraft's own pitch, since the altitude is ATC's or the pilot's there until stage 5 (on the pattern the old glide-path law would ask for a dive toward a path far below a far-side start).
- The turn onto final comes whenever the track still meets final ahead of the threshold (`VisualGuidanceJoin.MeetsFinalAhead`), even when the crossing point has slipped inside the minimum final, which only decides the spoken "Heading does not cross final" and F's sentence. Gating the cue on the minimum final too (as first built) held the bank at 0 until 0.05 nm and then asked for a sudden steep turn, the missing-then-violent cue VG-18 exists to prevent (stage-4 checkpoint review; `A_join_that_drifts_inside_the_minimum_final_still_gets_its_turn`).
- While joining before the turn, banked 5° or more, the bank callouts do not speak: the pilot is turning on purpose, for a new heading from ATC, and BA holds whatever heading they settle on, so "20 right" against that turn would be wrong (`Joining_does_not_call_against_a_deliberate_turn`). The tones still show the bank.
- Pinned by `VisualGuidanceJoiningTests` (`Right_of_final_on_an_ATC_heading_holds_it`, `A_shallow_ATC_heading_is_never_steepened`, `A_heading_that_stops_crossing_is_held_and_joining_never_becomes_vectoring`, `Right_of_final_on_an_ATC_heading_turns_right_onto_final`, `Pressed_in_a_turn_decides_once_the_wings_are_level`), and on runway 36, where the course wraps through north, by `VisualGuidanceHarnessHookTests`. Measured in the VirtualPilot approach harness: the joining families' `joinHoldBankMaxDeg` and `leftJoining` ([virtual-pilot.md](../virtual-pilot.md), "Stage 4").

## VG-24

- Above the reference means a larger target descent angle and a lower desired pitch: on final the reference is the path, while vectoring and on the pattern BA's planned descent, while joining the held altitude. `VisualGuidanceVertical.TargetDescentDeg` adds the correction (+ steeper for + height error) to the feed-forward angle, and the cue is desired pitch = learned trim − target descent. → [visual-guidance.md](../visual-guidance.md)
- Why: the sign is the one thing a vertical cue must never get wrong, and it was wrong once (VG-17, retired: the old PID's leading minus steered a pilot away from the glideslope, masked by tight-tracking autopilot tests). The redesign's spec ("Sign conventions") fixes it: height error + above, descent angle + down, the glide path angle + (3.0).
- Pinned by `VisualGuidanceVerticalTests.Above_the_path_is_steeper` and `VisualGuidanceVerticalPathTests.Above_the_path_asks_for_less_pitch` (on final, 100 ft high: 0.90° less pitch at 140 kt with the 27 s correction, 1.21° at the spec's 20 s), `VisualGuidanceLevelHoldManagerTests.The_hold_asks_back_from_both_sides` (joining, 80 ft above or below the held altitude) and `VisualGuidancePlannedDescentTests.Above_the_plan_asks_for_less_pitch_on_the_downwind`. If one fails, never flip the test: work out by hand which way the aircraft has to go.

## VG-25

- The desired pitch is the learned trim (`VisualGuidanceTrimLearner`: the aircraft's pitch minus its flight path angle, smoothed over about 6 s; the flight path angle atan(vertical speed / ground speed), smoothed over about 1 s) minus the target descent angle. It never uses the instantaneous vertical-speed derivative or the live angle of attack. In the flare (VG-27) the cue also corrects for the sink error, from the same 1 s smoothed flight path angle, never the raw vertical speed. → [visual-guidance.md](../visual-guidance.md)
- Why: the old law was `desiredPitch = (−glideslope + live AoA) + 0.005 × (targetFPM − smoothedFPM) + 0.002 × d/dt(error)`, built from the vertical speed the pilot was changing. At 140 kt each degree of pitch changes the descent rate by about 250 fpm, so each degree the pilot pitched moved the command about 1.2° the other way: the pilot chased a target that came toward them and past them (the owner confirmed hearing it). The approach harness measured the jet's self-feedback at −1.52 after 10 s on the stage-1 app and −1.37 at stage 4; the path law reads about −0.1 (`docs/virtual-pilot.md`, "Stage 5").
- The live AoA (`UpdateAoA`) is kept for the flight record only. `VisualGuidanceRealTimeTests.The_angle_of_attack_never_moves_the_cue` pins it; `VisualGuidanceVerticalPathTests` runs with a live AoA 2° off the trim, so a cue built on it would sit 2° high.

## VG-26

- On final and while vectoring (and on the pattern) the vertical cue never asks for a climb: below the path, or below BA's plan, the target descent is 0, level flight, until the path comes down to the aircraft, which then follows it (capture from below, as on an ILS). Only the joining level hold asks back up, within 2°, to the altitude it holds. → [visual-guidance.md](../visual-guidance.md)
- Why: the spec gives both "limited to ±2° of the glide path angle" and "below the path, BA asks for level flight"; the stage-5 plan (decision 1) took level, so the 2° limit binds only on the steep side. A climb cue on final is what a pilot least expects, and being low is spoken instead ("Too low", stage 5).
- Pinned by `VisualGuidanceVerticalTests.Below_the_path_is_level_not_a_climb`, `VisualGuidanceVerticalPathTests.Below_the_path_never_asks_for_a_climb`, `VisualGuidancePlannedDescentTests.Below_the_plan_asks_for_level` and `VisualGuidanceVerticalTests.A_jet_on_the_floor_is_fed_the_path_angle` (flying away from the threshold the floor rises and the plan asks for level, not a climb); measured in the approach harness as `maxTargetClimbDeg`, which `compare_approach.py` flags above 0.05 ("asks for a climb").

## VG-27

- The flare (visual guidance stage 6, designed with the owner on 2026-11-06) starts when the time to touchdown first reaches 4.3 s under 100 ft of wheel height, or at the profile's flare height (`FlareTriggerWheelHeightFt`, 30 ft on the A320, 40 on the A330 and 777, 35 on the MD-11), whichever comes first (`VisualGuidanceFlare.Starts`). The time to touchdown is the wheel height over the smoothed descent rate: the trim learner's 1 s flight path angle times the ground speed, never the raw vertical speed (VG-25), so a gust does not start it early. At the start, with wheel height h0 and sink s0, τ = h0 × 60 / (s0 − 150), infinite at 150 fpm or less; the target sink at wheel height h is the landing assist's own `LandingGuidanceLaws.FlareTargetVsFpm(h, τ, 150)`, from the aircraft's own sink down to 150 fpm at touchdown, always a descent. The cue (`VisualGuidanceFlare.CueDeg`) is the level attitude learned before the flare, held (the learner's trim half skips the flare), minus the target's descent angle, plus `FlareCorrectionGain` (1) times how much steeper the smoothed descent still is than the target's, only that way, at the profile's pitch rate. The target is always a descent; the cue can briefly sit above the level attitude while the aircraft still sinks faster than the target, and floating or ballooning it is the target's own attitude, asking gently back down. Ctrl+V pressed in the flare takes its first sample of the level attitude there. A balloon or a bounce stays in the flare with the same τ; above 100 ft of wheel height it is final again, the path's cue leaving from the flare's pitch. Never a fixed flare pitch. → [visual-guidance.md](../visual-guidance.md)
- Why the time: a fixed height leaves too little time when descending fast and too much when slow; the owner's words, a sighted pilot's flare is in effect timed by how fast the runway rises. The fixed 6° pitch from 30 ft (4.5° on the 777) asked the same attitude whatever the aircraft's own, and in the harness every light aircraft ballooned in it and floated (38 runs past the runway at stage 5). The 4.3 s and 150 fpm are FlyByWire's A320 flare law's (FmgcOuterLoops.cpp; notes in the redesign's spec folder), the profile's flare height the backstop; the owner dropped the spec's extra second of reaction.
- Why the correction: without it the cue asks only for the attitude that would hold the target sink once the aircraft has settled. A jet's lag in the harness, the pilot's reaction, the nose, then the flight path (about 0.5 + 0.7 + 2.5 s), is most of the 4.3 s, so the jets touched down at a median 518 fpm against 382 with the old fixed flare; starting 7 s out still gave 363. FlyByWire's flare law also corrects for the sink error. At gain 1 the jets touch down at 246 fpm (344 with the 1.0 s pilot) and every run that landed before still lands; at 1.5 and 2 they floated and drifted (the tailwind jet off the runway's side). The owner chose gain 1 on 2026-11-06. The cue moves after the pilot moves, but only inside the flare; at its start the two descents are equal, so it does not jump. The stage's final review found the correction first built both ways: a balloon to 30 ft climbing 200 fpm was asked 0.3°, 4.7° below the level attitude, a push near the ground, where the spec asks gently back down; one-sided it asks 3.0°, and no harness landing changed (none floats shallower than the target). `VisualGuidanceFlareManagerTests.A_balloon_asks_gently_back_down` pins it.
- "Prepare to flare" and "Flare" are said once per approach each, queued with their measured holds (1.3 s and 0.6 s), when the flare is 4 s and 1 s away at the smoothed descent rate (`VisualGuidanceFlare.TimeToStartS`, `PrepareDue`, `CallDue`: the start by time needs both touchdown 4.3 s away and the wheels under the 100 ft band, by height the flare height): about 100 ft and 65 ft at 740 fpm, earlier when coming down faster; "Flare" also on the flare's first update if not yet said (Ctrl+V pressed low), and no "Prepare to flare" after it. Neither is said again for a balloon or a bounce; a climb of more than 200 fpm above the 100 ft band (a go-around) arms both again, not merely being above it, since "Prepare to flare", and "Flare" on a fast descent, are said above the band on the way down. They go through `Say`, not `AnnouncePhaseChange`, whose one-second gap between phase lines could drop them for good. F on final ends "Prepare to flare." (or "Flare." in its last second) once said; F in the flare adds the target: "Flare, 20 feet. On the centreline. Target 350 down."
- Until 2026-11-06 "Flare" came 2.5 s before touchdown, on the first update in the flare: about 2 s after the tone had started rising. The owner: "why does flare get announced in the middle of the action ... we should announce it before the action"; on the second sim flight they waited for the word and pulled late (touchdown 745 fpm). They also asked for an early call: "depending on the speed and vertical speed of the aircraft, 100 to flare takes more than that", first as "Ready to flare", then worded "Prepare to flare". A separate early warning was first advised against (the A320's own "one hundred" callout lands near it); the owner chose it.
- The time constant is set once, at the start: a first draft's max(s0 − 150, 60) would have asked an aircraft sinking 160 fpm for 210. Ctrl+V pressed inside the flare's band starts the flare on the first update, since the flight path is read before the phase is decided.
- Pinned by `VisualGuidanceFlareTests` (the start at 4.3 s and at the backstop, the profile starting at the aircraft's own sink, a floating aircraft asked gently down, the correction, finite numbers for a stopped or level aircraft), `VisualGuidanceFlareManagerTests` (the start by time and by height, the target falling as the wheels come down, no jump at the start, more nose-up while coming down faster than the target, a balloon staying in the flare, Ctrl+V pressed low, the same cue at 10, 30 and 60 updates a second, "Prepare to flare" and "Flare" 4 s and 1 s before the flare at 300, 742, 1,000 and 1,500 fpm, queued and in order, once each above the band, not again for a balloon, again after a go-around, F on final repeating "Prepare to flare", F's target), `VisualGuidanceStatusTextTests.Flare_readout_is_culture_invariant`, `VisualGuidanceRealTimeTests.The_flare_cue_starts_where_the_aircraft_is_at_any_update_rate` and `VisualGuidanceVerticalPathTests.Back_above_the_flare_the_cue_leaves_from_the_flare_pitch`. Measured in the approach harness as `touchdownVsFpm`, `flareStartWheelFt` and `maxFlareClimbDeg` ([virtual-pilot.md](../virtual-pilot.md), "Stage 6").

## VG-28

- The capture law's gain (deg·kt/nm, `VisualGuidanceJoin.DefaultCaptureGain` 10,259, FlyByWire's k1) is capped by `VisualGuidanceJoin.TurnLimitedCaptureGain` at `TurnRateMargin` (0.9) × 3600 × the turn rate g·tan(bank) ÷ V that the profile's `MaxApproachBankDeg` gives at the ground speed. `VisualGuidanceManager.CaptureGain` is that capped gain at the ground speed now, and every turn goes through it: the legs' and final's capture, the turn cues ("Turn base", "Turn onto final"), the countdown and F's join distance. While the pattern's downwind is the leg flown (until "Turn base"), `VisualGuidanceJoin.ResizePattern` rebuilds the pattern every update from the speed now and the capped gain: the base moves in as the aircraft slows and out if it speeds up, and the downwind widens when the turns need more room but never narrows (the aircraft may be on it). Only the decision (`Decide`, once, at the press: on final, joining, vectoring and its cut, or the pattern) takes the full gain, so it plans for a pilot who slows down for the turns. → [visual-guidance.md](../visual-guidance.md)
- Why the decision keeps the full gain: the owner, 2026-11-06, "usually when we're near a visual approach clearance, aircraft is around 210 to 240 knots already, and then it slows to 200, 190, 180, where usually the turns happen. at final, usually aircraft is at 180, then goes to 140 or lower", and "speed management is important, and the pilot is responsible for it. you're not really supposed to be flying at 250 when nearing approach". Decided with the capped gain at 230 kt, a "cleared visual" 12 nm out and 4 nm beside final found no cut that joined 6 nm out and took the pattern, whose base (11.35 nm) was where the aircraft already was: its turn onto the base carried it a mile past, BA steered it back out, and it overshot final 3,800 to 4,100 ft in the harness (SLOW-VEC). With the full gain it vectors and joins with no overshoot. Planning with the full gain but steering capped, without resizing the pattern, overshot final up to 3,196 ft holding 250 kt (the downwind sized for the full gain's turn cue, the base-to-final turn starting 3.2 nm out): the plan and the steering must come from the same speed, hence the resize.
- Why: coming off a 90° intercept the law's desired track turns at gain × sin(intercept) ÷ 3600 degrees a second, the ground speed cancelling, so 2.85°/s at any speed. A 25° bank gives that only below about 180 kt (2.04°/s at 250 kt). The first sim flight (2026-11-06, Fenix A320, Ctrl+V 12.5 nm past KATL 27L at 260 kt) turned 1.97°/s at full bank onto the pattern's downwind and overshot the line by 0.9 nm, and BA steered back across it (with the pilot's lag and the pinned bank tones, minutes of 25° swings). Every harness pattern had flown 140 kt.
- Measured in the approach harness's FARFAST family (the far side at 210 and 250 kt, 4,000 ft above the field, flying away): with the fixed gain the jets overshot final by 201 to 1,739 ft and were established 5.4 nm out at 250 kt; capped at 1.0 one run still overshot 682 ft (the turn was still under way inside 0.05 nm, where the precision track's ±10° clamp took over); at 0.9 none overshoots, established 7.5 to 8.8 nm out, and the 227 older runs are identical (the cap first binds at about 161 kt; the SPEED-A-JET160 and WIND-TW runs fly 155 to 160). At 0.8 those two changed slightly (the high join's path error 1,250 to 1,309 ft).
- Measured with the pilot slowing down (the SLOW family, `ApproachSlowing`: pressed at 210 or 230 kt, 190 for the turns, 180 on final, 140 from 6 to 4 nm, at most 0.75 kt/s; starts from the far side, a "cleared visual" 12, 14 and 18 nm out and 4 nm beside final, ATC's 30° intercept 12, 14 and 18 nm out with a "descend and maintain", and a downwind abeam): all 32 join final with no overshoot, 5.9 to 10.2 nm out, final tracking within 63 ft, the gate within 44 ft (`approach_resize_plannormal`). The FARFAST runs and the 227 older ones are identical to the fully capped version.
- Pinned by `VisualGuidanceJoinTests` (the full gain at 140 and 160 kt and for a stopped or unknown speed; above it the law asks exactly 90% of the bank's turn rate; 1.83°/s at 250 kt; the pattern resized for the speed now: the base in when slowing, out and wider when faster, the downwind never narrower; nothing changed at approach speed or for another plan).

## VG-29

- `VisualGuidanceManager.LateralTrackDeg` is the ground track (the heading only when no track has arrived) at every height: the lateral law, the established test, F and the recording all take it, so in a crosswind the aircraft keeps its crab and its path stays on the centreline to touchdown. → [visual-guidance.md](../visual-guidance.md)
- Why: from the first visual guidance until 2026-11-06 it switched to the heading at 100 ft above the ground (`PLANE ALT ABOVE GROUND`), to line the nose up with the runway. Visual guidance can only ask for bank, and bank turns the path with the nose, so once the nose pointed down the runway the wind carried the aircraft sideways at the crosswind's speed. The first sim flight (2026-11-06, Fenix A320, KATL 27L, a 1.8° crab, about 4 kt of crosswind): at 100 ft it asked 1.4° of left bank with the aircraft 11 ft left and tracking the centreline; the owner followed, the aircraft drifted to 62 ft left by touchdown (its left wheels at the runway's edge) and left the runway's side 3.6 s later at 122 kt. On the second flight the switch asked 1.9° left at 100 ft, the owner did not follow it, and the aircraft touched down 15 ft right. The stage 6 harness's tailwind-base jet showed the same thing (its deferred minor 1: banking 5° left from 0.12 nm, about 100 ft, touching down 70 ft left).
- The owner, 2026-11-06, told that the rudder decrab belongs in the flare, the last few seconds before touchdown, not at 100 ft: "it makes a lot of sense not to do that". Visual guidance gives no rudder cue; a cue for the crab in the flare would be new work, for the owner to ask for.
- Pinned by `VisualGuidanceCrosswindTests.A_crab_on_the_centreline_asks_no_bank_down_to_the_flare` (a 2° crab tracking the centreline at 220, 110, 90 and 75 ft asks no bank; before the change it asked 2° left under 100 ft).
