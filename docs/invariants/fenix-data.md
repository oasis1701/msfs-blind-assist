# Fenix A320 data service, definition, variants and EFB rules — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/fenix-data.md`, which Claude Code loads when it reads matching code. The cabin, documents and failures window rules are in [fenix-windows.md](fenix-windows.md). FNX-13 (settings lag) and FNX-19 (settings secrets) bind code outside the windows (the shared read-back wait, the settings query), and FNX-16 (engine readouts) belongs with the data-service rules, so all three stay here. Background: [a32nx.md](../a32nx.md).

## FNX-1

- A read of a name the Fenix data service does not know returns the empty string `""`. `FenixDataValue.FromJson` maps it, and a missing token, to `FenixValueKind.EmptyOrUnknown`; a JSON null stays `Null`; `IsKnown` is false for both. No caller may treat either as 0, false, off, closed or empty: show "no data" (a numeric reader uses NaN or skips the row). `FenixDataService.ReadAsync` and `ReadManyAsync` also give `FenixDataValue.Unknown` when the Fenix is not loaded or the gateway is down, so "no data" covers "no Fenix" too.
- Measured 2026-10-21 (Fenix 3.0.0.7426, A320 CFM WF, sim running, reads only): a name the gateway does not know answers `""`, not an error. `doors.entry.d1l` and `system.config.Units.Weight`, both gone in v3, read `""`. The previous Fenix (2.4.0.4720) answered null for an unknown name, so an older note or code that tests for null is about this same case.
- Why: `FenixDataValue` is a struct, so reading `Number` or `Bool` off it without checking `Kind` gives 0 or false. A renamed or mistyped name would then read as a closed door, an off switch, 0 percent or a quiet caution, and nothing would say so. Before v3 nothing in the app depended on the difference (it read only the MCDU screens there); every later reader must.
- Pinned by `FenixDataQueriesTests` (`FromJson_reads_each_kind`, `Only_a_value_that_is_neither_empty_nor_null_is_known`, the `ParseReadMany_` cases) and `FenixDataServiceClientTests` (`ReadAsync_returns_unknown_when_the_service_is_down`). → [a32nx.md](../a32nx.md)

## FNX-2

- `FenixDataService.Subscribe` delivers every change to its `onChange` callback on a thread-pool thread, the one running the shared WebSocket loop, never the UI thread. A form or window that shows or acts on a value marshals to its own thread with `BeginInvoke` inside try/catch(InvalidOperationException) ([A380C-6]): an `IsHandleCreated` check alone races the handle's destruction. Disposing the returned handle ends the subscription, but a callback already running, or one value already on its way, may still arrive afterwards (or after the window closed), so the marshal must tolerate a form that is gone. An exception from a callback is logged once and swallowed; it never stops the loop.
- The service itself never speaks and never touches a control: it holds no announcer and no form. A spoken change is the caller's decision, made on its own thread and under the app's announcement rules, so a subscription can be added to a window without that window changing what the pilot hears.
- Why: the callback runs inside the socket loop, so a blocked or slow callback stalls every subscription of the session, and a control touched from a pool thread throws. The same trap, with the same fix, applies to every bridge push in the app ([A380C-6]).
- Pinned by `FenixDataServiceClientTests` for the message parsing; the thread contract is documented on `Subscribe`, and no unit test can pin a form's marshal. Verify in the sim: open a Fenix window while values change and close it mid-update. → [a32nx.md](../a32nx.md)

## FNX-3

- Names for the Fenix data service come only from open sources: the gateway's own EFB and FAP web bundles (the pages the service itself serves at 127.0.0.1:8083; `tools/fenix-gateway/fetch_gateway_bundles.py` fetches them, read-only), names the app already uses, and HubHop. Each is then checked against the running service, which is possible because an unknown name reads `""` ([FNX-1]). Never guess a name, and never ask the service for its schema (an introspection query, the `?sdl` text, the IDE page) to find one: that was ruled out on purpose, as the next bullet says.
- Schema introspection was ruled out on purpose in the v2 investigation (Fenix 2.4.0.4720) and has not been retried or worked around since (2026-10-21). Whether the service, or v3's new gateway executable, would answer it is not known, and the choice does not depend on it. No reason was written down with that ruling; the one that applies is the principle behind the Fenix display program's refusal of .NET inspection (measured 2026-10-11): a vendor's deliberate block is the developer's decision, and an accessibility purpose does not change who makes it, so the app does not go looking for what the vendor has not published. If a value the app needs is not published under a name found this way, the route is the existing AI picture reads.
- The app also never sends the gateway's navigraph operations. The operations in the EFB and FAP bundles include two: an `accessToken(forceRefresh)` query that returns the pilot's Navigraph access token and expiry, and a `disconnect` mutation that ends the Fenix's Navigraph connection. Nothing the app does needs either, and reading a credential or signing the pilot out of their Navigraph connection is not a side effect to risk. This is pinned by `FenixDataServiceClientTests.No_Fenix_code_sends_a_navigraph_operation`, a source scan of the Fenix code for a GraphQL `navigraph` selection (comments are ignored, so a comment may still say "never"), not by a rule line.
- Observed 2026-10-21 on 3.0.0.7426: the operations in the EFB and FAP bundles touch `dataRef` (reads and writes), the `dataRefs(names:)` subscription, `settings`, `fap` and `navigraph`, plus REST paths under `/fenix`. `FenixDataQueries` builds only `dataRef` and `settings` queries and the subscription. → [a32nx.md](../a32nx.md)

## FNX-4

- The Fenix TO CONFIG test has two callers, the panel's ECAM TO CONFIG button (`FenixA320Definition.RunTakeoffConfigTestAsync`) and the First Officer's "Takeoff config test" (`FenixActionExecutor.TakeoffConfigTest`), and both take their verdict from `FenixTakeoffConfigVerdict.WatchAsync`. The watch reads fresh, on-request `_READOUT` twins of the `S_ECAM_TO` button and of the captain's master warning and master caution lights (the [A320-41] pattern) every 200 ms, timed from the press it observed itself: a button already held needs a release first, and a press it never sees gives "no result read". Any lit light gives a check (a late warning outranks a caution); "Takeoff config normal." comes only when both lights read dark at or past `VerdictAfterMs`; an unread light never gives "normal". There is no pre-press baseline: a warning lit before the press still gives "Takeoff config: check configuration.".
- Why: Fenix v3's warning computer delays MASTER WARN and MASTER CAUT after the button (Fenix V3 changelog). The old verdict was one cached read of the 1 Hz lights at 1.5 s, and on v3 it said "Takeoff config normal." over a bad configuration in all three bad runs below.
- Measured 2026-10-21 on Fenix 3.0.0.7426 (A320, engines running, parking brake set, the app's old TO CONFIG code; a probe polling the data service every 150-200 ms, so times are detection to detection). Flaps 0, three runs: press to the first lit light 1,015, 1,009 and 809 ms (MASTER WARNING, captain and first officer; a lit warning reads 2, not 1); the warning went out about 1 s after release (+1,017, +974, +905 ms), and MASTER CAUTION followed about 0.5 s after release and stayed lit until reset. Flaps 1 with trim and speeds set lit nothing in 27 s. So `VerdictAfterMs` is 2,100 (the slowest press-to-light time plus 1 s, rounded up to 100) and `HoldMs` 1,500. A shorter `VerdictAfterMs` lets a slow warning arrive after "normal" was spoken: re-measure before changing it, and after a Fenix update that changes the warning computer.
- The watch reads SimConnect twins, never the Fenix data service, so the verdict never depends on the gateway being up.
- Owner checks 2026-10-22: flaps 0 gave "Takeoff config: check configuration." (the warning lit within about 1 s), flaps 1 gave "Takeoff config normal.", and the First Officer's Taxi "Takeoff config test" with flaps 0 gave the failure verdict; the panel's 200 ms press gap never beat the watch's first read in five presses.
- Pinned by `FenixTakeoffConfigVerdictTests` (`Normal_comes_only_after_the_verdict_time`, `A_warning_that_lights_late_is_still_caught`, `Unread_lights_never_give_normal`, `A_warning_lit_before_the_press_is_check`, `No_press_seen_is_no_result`) and `FenixTakeoffConfigWiringTests` (`Panel_button_runs_the_shared_watch`, `First_Officer_runs_the_shared_watch`, `Each_twin_is_a_one_off_read_of_its_original`). The value of `VerdictAfterMs` is not pinned. → [a32nx.md](../a32nx.md)

## FNX-5

- Every Fenix rotary knob and push/pull the app turns is a counter: the cockpit adds or takes 1 per click on the same L:var, and the Fenix acts on the difference between successive values. They are the FCU knobs `E_FCU_SPEED`, `E_FCU_HEADING`, `E_FCU_ALTITUDE` and `E_FCU_VS`, the EFIS baro knobs `E_FCU_EFIS1_BARO` and `E_FCU_EFIS2_BARO`, the ISIS baro `E_MIP_ISFD_BARO`, the V/S push/pull `S_FCU_VERTICAL_SPEED`, the FCU speed, heading and altitude push/pulls (`AdjustFcuPushPullCounter`), and the baro STD push/pulls `S_FCU_EFIS1_BARO_STD` and `S_FCU_EFIS2_BARO_STD` (a pull adds 1, a push takes 1 away).
- So a step is `CounterStepCode`'s RPN, `(L:x) n + (>L:x)` (or `n -`), sent with `ExecuteCalculatorCodeUnique` (SIM-17; invariant digits, [VAR-5]): it moves the knob n clicks from wherever the sim's count is. Never write an app-side count as an absolute value (the old `rmpCounters`): after any cockpit click or app restart it is wrong, and the knob moves by the difference, possibly the wrong way. The panel's knobs (`IncrementCounter`, `DecrementCounter`, `JumpCounter`, so the typed-value jumps too, whose size and checking [FNX-20] sets), the EFIS "Baro Pull (STD)" and "Push (QNH)" buttons, the typed baro and the altimeter window's QNH/STD pick (`FenixBaroWindow`), and the First Officer's `SetBaroStdBoth` all step this way.
- The baro mode is a state the counter does not hold: read STD or QNH from the EFIS QNH light `I_FCU_EFISn_QNH` (1 QNH, 0 STD; announced as "EFIS1 BARO STD Status"), never from `S_FCU_EFISn_BARO_STD`, which holds any number after cockpit pulls and pushes (it read 3 in STD, 2026-10-21) and can be 0 while STD is selected. The First Officer's `FenixStateEvaluator.BaroText` reads the light.
- Measured 2026-10-21 (A320-214 CFM on the ground, every value restored, then again on a reloaded flight through a direct SimConnect connection): `E_FCU_SPEED` read 3 after three cockpit clicks (speed 100 to 103), and the app's first "increase", which wrote its own count of 1, moved the speed from 103 to 101, down 2. With the baro STD counter at 2 after two cockpit pulls, the app's old "STD" (a straight write of 1, a decrease) selected QNH. HubHop gives the baro push/pull as pull `++`, push `--`: any increase selects STD, any decrease QNH, and extra pulls stay STD, extra pushes QNH.
- Owner checks 2026-10-22: after an app restart in flight, one FCU Speed increase moved the knob one step from the sim's own count; baro Pull and Push from a counter of 2 gave STD and QNH on both sides; a typed QNH with one side in STD leaves STD; the altimeter window's QNH/STD pick after cockpit pulls stays as picked.
- Pinned by `FenixV3FixPanelControlsTests` (`Counters_step_from_the_sims_value`, `Baro_std_is_a_pull_and_a_push`, `Typed_baro_leaves_std_with_a_push_step`, `Baro_window_mode_pick_steps_the_std_counter`) and `FenixFoBaroStdTests` (`Std_comes_from_the_qnh_light`, `The_evaluator_source_names_the_lights_and_no_knob_counter`); a new writer or reader elsewhere is not. → [a32nx.md](../a32nx.md)

## FNX-6

- A control the Fenix model builds from its `Button_Momentary` template is a press button in the app: `RenderAsButton`, no `ValueDescriptions`, a handler that runs `ExecuteButtonTransition` (the 0→1→0 pulse, [A320-3], [A320-4]) on `value == 1`, and its own light as its `StateVariable` where it has one. Never an Off/On combo: the template is a counter (the cockpit adds 1 on press and 1 on release), so a held 1, which an "On" pick wrote, flips the function once whatever its state, and 0 ("Off") does nothing. The Fenix v3 work turned the Bus Tie, Service Interphone Override, Avionics Compartment Light, the pedestal's Pedestal Video (formerly "Cockpit Door Video"), the radar's GCS, ACP PA Transmit and CALLS Mech, All, Fwd and Aft from combos into press buttons, and added CALLS Mid and Exit (A321), the clock's Chronometer Start/Stop, Chronometer Reset and Date, and ISIS Baro Push as press buttons. A press button with no light of its own says "<name> pressed" once (`confirmPress`, [CORE-7]); one with a light stays quiet and its light speaks.
- A spring-loaded position springs back only when the cockpit mouse lets go, so a written end stays where it was written: the model's `Switch_3Position_Hold` (Cargo Discharge 1 and 2, DCDU brightness) and the clock's Elapsed Time knob (`Knob_3Position_SingleHold`) at RST. `PulseSpringSwitch` writes the end, writes the middle (1) after `ButtonPressHoldMs`, then forces one read so the open combo shows the middle again: WinForms ignores a pick of the index already shown, so a combo left on the end would commit nothing on the next pick of the same end.
- Measured 2026-10-21 (A320-214 CFM on the ground, ground power, every value restored): the ECAM DOOR page button `S_ECAM_DOOR` pulsed 0, 1, 0 with holds of 200, 100 and 50 ms flipped `I_ECAM_DOOR` each time, and a 20 ms hold (about one frame) was missed. The bus tie `S_OH_ELEC_BUSTIE` behaved the same (`I_OH_ELEC_BUSTIE_L`), but toggling it disturbs ground power: never test with it. Cargo Discharge's model tooltips give 0 "Agent 2", 1 "Rest", 2 "Agent 1"; the old Off/On combo fired agent 2 on "Off" and could not choose agent 1. The clock's Elapsed Time written 2 (RST) stayed at 2.
- Owner checks 2026-10-22: Calls Forward chimed once, said "pressed" once and was released after 200 ms; DCDU brightness took one step per pick and went back to Mid; Elapsed Time Reset sprang back to Stop; GCS said "pressed" once; the Bus Tie pressed lit its OFF legend and pressed again put it out.
- Pinned for today's controls by `FenixV3FixPanelControlsTests` (`Momentary_buttons_are_press_buttons`, `Only_a_button_with_no_light_confirms_its_press`, `Spring_switches_return_to_the_middle`, `A_spring_switch_combo_resyncs_to_the_middle`); the clock's Elapsed Time Reset is pinned only as "not a plain write" (`FenixVariantControlsTests.Elapsed_time_reset_and_buttons_are_not_plain_writes`). A new control is not pinned: read its template in the Fenix model before choosing a combo or a button. → [a32nx.md](../a32nx.md)

## FNX-7

- Never infer which light a Fenix control owns, or what its legend means, from the light's suffix (`_U`, `_L`), from the real aircraft or from another control ([FO-11] says the same for the First Officer's APU AVAIL lamp). A new light is labelled by position from its switch's label, built from one constant ("Econ Flow Lower", "ACT Pump Upper", "Engine N1 Mode 1 Lower"; [VAR-1]'s pair rule), until a press in the sim shows which light comes on and when; only then may its words change.
- A button whose `StateVariable` is an OFF legend sets `SimVarDefinition.StateLitText` to "Off" and `StateDarkText` to its dark text ("On", or "Auto" for the Bus Tie), so the button reads "Off" while the light is lit, and the light's own announcement uses the same words ("Electrical Bus Tie: Off"). Today: ADR 1-3 (`I_OH_NAV_ADRn_L`), IR 1-3 (`I_OH_NAV_IRn_SWITCH_L`) and the Bus Tie (`I_OH_ELEC_BUSTIE_L`). The overhead VIDEO pushbutton's light (`I_OH_COCKPIT_DOOR_VIDEO`) is an OFF legend too (VIDEO set to 0 lights it, measured 2026-10-22), so its announcement says "Off" when it is lit, as the VIDEO switch reads. `StateLitText` and `StateDarkText` are shared and opt-in: only the Fenix sets them, and every other aircraft's `StateVariable` button keeps "On" and "Off".
- Found in the owner's checks of 2026-10-22: ADR 1-3, IR 1-3 and the Bus Tie read the wrong way round (a working ADR read "ADR 1: Off"), because their light is the OFF legend. ADR 1 and IR 1 were measured by a press, and the Bus Tie from the Fenix's XML and then by a press in flight (pressed, the OFF legend lit: "Off"; pressed again, out: "Auto"). The pedestal Cockpit Door Video button had been paired with the overhead VIDEO pushbutton's light, but a pedestal press left that light unchanged (measured), so it has no light of its own and says "pressed". The ADR and IR OFF lamps were renamed after their system ("ADR 1", "IR 1", the owner's choice), their keys unchanged so Ctrl+M mutes stay. Two lights never answer on the ground with ground power: `I_OH_LIGHTING_AVIONICS_COMPT` and `I_OH_SVCE_INT_OVRD` stayed 0 for every press (2026-10-21), so they are not those buttons' state.
- Measured by a press on 2026-10-24, so their words changed: the Econ Flow and ACT Pump lower lights only mirror their switch (each switch names its light as `UiEchoVariable`, so the light is quiet after the pilot's own pick); `I_OH_FUEL_ACT_U` never lit, so "ACT Pump Upper" keeps its position name. The FD and LS lamps (`I_FCU_EFISn_FD`, `_LS`) are the buttons' own "on" lights, never a fault, and are named like their buttons ("EFIS Left FD" ... "EFIS Right LS", from one constant each, [VAR-1]'s pair rule; keys unchanged). `FenixPressEchoTests` pins them. → [a32nx.md](../a32nx.md)
- Pinned for today's buttons by `FenixV3FixStateLightTests` (`Off_legend_buttons_say_off_while_the_light_is_lit`, `An_off_legend_lamp_speaks_as_its_button_reads`, `Only_the_off_legend_buttons_change_their_words`) and `FenixVariantControlsTests.Each_light_is_labelled_from_its_switch`; a new light is not. → [a32nx.md](../a32nx.md)

## FNX-8

- `FenixEFBForm.EfbUrl` is exactly `http://127.0.0.1:8083/?target=external#/efb`, the target in the query, before the `#`.
- Why `external`: the EFB chooses its behaviour from the target (`detectTargetDevice`, read in the v3 bundle). A sim target (the cockpit tablets' `sim-capt`, `sim-fo`, `msfs2024-efb`) swallows Tab unless its on-screen keyboard is open, blocks PageUp, PageDown, Home and End on a focus that is not editable, and releases the focus 2 s after a click (`AUTO_UNFOCUS_DELAY_MS`). `external` keeps Tab and those keys and the physical keyboard, simulates no battery or sleep, keeps its own chart and map theme settings (never the cockpit tablets'), and never touches `fenix.efb.hidden_*` or `connected_*`; like any browser it reports its script errors to Fenix's error tracker. With no target the EFB falls back to `external` for any browser that is not Coherent GT and has no `_capt` in the URL, so WebView2 already got it; naming it removes that reliance.
- Why 127.0.0.1: the gateway listens on IPv4 only ([A320-40]). WebView2 (Chromium) starts IPv4 300 ms after IPv6 (from Chromium's source, not measured in WebView2), so `localhost` costs up to 0.3 s per new connection there; a plain client pays the whole refusal (measured 2026-10-21: 2,002 to 2,005 ms in three tries, against 0.3 to 10 ms for 127.0.0.1). The page builds every gateway address from its own origin (`getHostUrl`, `backendUrl`), so the choice reaches its GraphQL socket and REST calls too. A one-time cost of the change: the EFB's only per-origin state, its custom-background flag in `localStorage`, started empty.
- Any other window that hosts a Fenix gateway page takes the same address and target.
- Owner checks 2026-10-22 (Fenix 3.0.0.7438, NVDA): every app reachable with Tab, the page's keys working, the "not reachable" message naming http://127.0.0.1:8083.
- Pinned by `FenixEfbAddressTests` (`The_efb_page_is_the_external_target_on_ipv4`, `The_window_never_addresses_the_gateway_by_name_and_shows_no_label`). → [a32nx.md](../a32nx.md)

## FNX-9

- The Fenix v3 EFB is not accessible on its own. `MSFSBlindAssist/Resources/fenix-efb-accessibility.js` (one IIFE guarded by `window.__msfsbaFenixEfb`, plain ES2017, no dependencies, the top document only) is injected by `FenixEFBForm` on document creation, before the first navigation. A MutationObserver runs its rules at most once per 50 ms, each rule in its own try/catch, so a failing rule never stops the others or throws into the page. Every element it handled carries `data-msfsba="1"`, so a second pass adds no second listener.
- What it does: adds `role`, `aria-*`, `tabindex` and key handlers whose Enter or Space call the element's own `click()` (never when the key comes from a text box); names come from the page's own visible text, and it never overrides a page's own `aria-label`, `aria-hidden` or `role`. Its deliberate exceptions: ids for `aria-owns` (the Takeoff results grid's and an open Settings "More options" menu's), written only as `msfsba-<n>`; the runway condition's roving Tab stop; one focus helper, `moveFocus`, the only place the focus moves (the runway condition's arrow keys, a "More options" menu opening and closing); one change listener that only schedules a pass; Alt+Home sets `location.hash` to `#/efb`. What it never does: a network request, removing or moving a node, writing text or a value, firing events, changing classes, storing anything. So a press does what the page does.
- The window itself catches the two pages a screen reader cannot read, the EFB's own MCDU and FAP (`FenixEfbRoutes`): it goes back to the EFB home and says where to go instead, once per route within 1.5 s.
- The layer keys on the page's own classes and structure, so a Fenix update can break it silently. After each update: re-take the trimmed captures in `tools/fenix-efb-test/fixtures` (the snippet and the screen list are in `tools/fenix-efb-test/capture.md`), run the Node suite there (`npm install`, `node --test`; its sweep checks every control has a name), and do capture.md's live check in Chromium with the layer injected, because jsdom sees no CSS (`display:none`, `visibility`, icon fonts). CI runs only the C# guards, not the Node suite. Removing or renaming `Resources\fenix-efb-accessibility.js` beside the app turns the layer off (a `Log.Warn("FenixEFB", …)` line, and the plain page loads), if an update ever makes it misbehave.
- Built and checked 2026-10-21 and 22: captures from Fenix 3.0.0.7426; the owner's seven NVDA checks on 3.0.0.7438 passed, after a fix wave for what the first run found (an unlabelled background picture, "clickable" wrappers, Settings switches the page hides with `display:none`, the "More options" menus out of reach).
- Pinned by `FenixEfbLayerTests` (the script's bans, the click-only key handler, the one focus helper, the `msfsba-` ids, the project copying the script, the injection before the first navigation) and `FenixEfbRoutesTests`. → [a32nx.md](../a32nx.md)

## FNX-10

- `FenixDataService.Subscribe` runs the gateway's `dataRefs(names:)` subscription (`FenixDataQueries.SubscriptionQuery`, the one the Fenix EFB itself uses), and it is not a stream of every name it carries. Measured 2026-10-22 on the IAE A321 with two ACTs (a raw subscription held through an engine start and a shutdown, beside a recorder polling the data service twice a second, and MSFSBA's debug.log): it sent `aircraft.engines.{n}.n2` once, when it opened, and never again (one value through a whole shutdown, 62.3 % to 5 %), and opened cold and dark even that first value failed (`Any cannot coerce the runtime value of type System.Double`; a query answers null there). The running flags (on change), EGT (about every second while it moves) and the fuel total (every 2 s) did stream. A query (`ReadAsync`, `ReadManyAsync`) answered a fresh N2 every time, and null (unknown) with the engine off.
- So a value that must stay fresh is read with `FenixDataPoller`: one `ReadManyAsync` of its names a second (`DefaultInterval`), reads never overlapping, an answer arriving after `Dispose` dropped, a failing read or a throwing callback logged and swallowed. Its callback runs on a pool thread, as a subscription's does ([FNX-2]), and only stores. A subscription may still carry the names that do stream; an older poll answer never overwrites a newer subscription value (the Engines window's `FenixEngineSnapshot.ApplyAllIfUnchangedSince`), and the running flags come only from the subscription there, since a stale poll would speak a false "stopped".
- Before this was measured, the First Officer never had the Fenix's N2 (every trace line "Fenix N2 unread, source stock") and the Engines window kept its first N2 until F5. Today the First Officer polls N2 (`FenixFoLiveReadings.PolledNames`), the Engines window its 16 values that are not running flags (`FenixEngineNames.Polled`), and the Cabin window and the app-wide cabin monitor their names (`FenixCabinNames.All`), at one localhost query a second each.
- Which names stream was measured for these few only. For another name, hold a raw subscription beside a polling recorder, or poll it.
- Pinned for the poller by `FenixDataPollerTests`; which values a caller polls is not. → [a32nx.md](../a32nx.md)

## FNX-11

- `FenixA320Definition.IsFitted(varKey, variant)` (`FenixA320Definition.Variants.cs`) decides which variant-dependent controls a panel shows (`IsVariantControlVisible`) and which `HandleUIVariableSet` refuses aloud ("Not fitted on this aircraft.", `TryRefuseNotFitted`: a validation error, so [CORE-7] lets it speak). Each arm reads only its own field of the definition's `Variant` (a `FenixVariant` from the eight config L:vars; never read `N_CONFIG_*` or `B_CONFIG_*` directly), and hides a control only when that field has been read and says the airframe lacks it: null or Unknown shows it, and a key the table does not name is always fitted. `Variant` stays Unknown until `N_CONFIG_AIRCRAFT_TYPE` reads 1-4, about a second after load, so a panel opened earlier shows everything until it is reopened; there is no live rebuild (owner, 2026-10-22). `GetPanelStructure` also drops a panel whose every control `IsFitted` hides (DCDU Left without a DCDU, ISIS with the round standby gauges; owner, 2026-10-24), by the same rule: an unread field lists it, and a panel with no controls at all is never dropped (pinned by `FenixVariantControlsTests`).
- Each arm comes from that airframe's own package panel, never from the real aircraft or another type by analogy (read 2026-10-21, Fenix 3.0.0.7426):
  - ECON FLOW (`S_OH_PNEUMATIC_ECON_FLOW`) and CALLS MID and EXIT: `Part_Interior_Panel_Pneumatic_A321` and `Part_Interior_Panel_Calls_A321`, attached only by the A321 interiors, so A321 (or Unknown). PACK FLOW (`S_OH_PNEUMATIC_PACK_FLOW`) is only in `Part_Interior_Panel_Pneumatic_A32X` (A319 and A320), so not A321, although the data service still reads it 1 on the A321.
  - ACT PUMP (`S_OH_FUEL_ACT`): `Part_Interior_Panel_Fuel_ACT_Enabled`, visible when `N_CONFIG_ACT_COUNT` is above 0.

## FNX-13

- A Fenix settings write (`setSetting`, the EFB's own mutation, `FenixOptionEdits.SetSettingDocument`) answers `success` at once, but the settings query can still return the old value for up to about 2 s afterwards. Measured 2026-10-22 on 3.0.0.7438 with the documents window's pin (Ctrl+D): every pin and unpin took effect, yet the read straight after the write still showed the old list, and the new one 0.4 to 1.9 s later (debug.log 19:36:57 to 19:37:47); the first build spoke "The Fenix did not accept the change." on every press.
- So the result of a settings write is read back with a bounded wait, `FenixSettingReadBack.AwaitAsync`, which the documents window and the options window both use: it re-reads every 250 ms, up to 16 reads (3.75 s, past the longest lag measured), until the wanted state shows, with an injectable delay and a cancellation check right before each read (after its delay), so a cancel during a delay that ignores the token never starts another read. Never report a write as refused, or speak the old value as its result, from the first read alone.
- The two windows differ only in a read that gets no answer. The documents window (`FenixDocumentPins.AwaitStateAsync`, which judges the pin) goes on through it: no read answering at all is "no answer", and answers that never show the wanted state are the opposite state. The options window (`FenixOptionsForm.ReadBackAsync`, judged by `FenixOptionEdits.Applied`) stops at it, as each such read can take the data service's 10 s time-out: it says the Fenix did not read the change back. It also stops at an answered read that lacks the option's key (`FenixOptionEdits.ReadBackSettled`: the option is applied or missing), and says the same at once instead of after 16 reads (about 4 s); the documents window's wait is unchanged. After 16 answered reads that never show the change it speaks "Fenix kept …", "Not made permanent: …" or "Not reset: …". The same wait follows a write that got no answer (a time-out may still have landed), and its wording is unchanged.
- The options window waits with silent reads that touch neither the tree, the status nor the screen reader, then writes the last read to the tree once. That one rewrite of the focused row is what NVDA reads, and what `FenixOptionEdits.ScreenReaderReadsRow` judges against the row text from just before the write ([CORE-7]); an intermediate rewrite would have been read too, and flickered the tree. Until the 2026-10-24 change the window read again once, 500 ms after a read that did not show the change, which is inside the measured lag: a change that landed after about 0.5 s was spoken as not applied.
- Not measured: whether the gateway's own automatic pins lag the same way; the options window's wait in the sim (the NVDA checks of 2026-10-22 were with the single retry), and its early end on a read without the option (2026-10-24, unit tests only).
- Pinned by `FenixSettingReadBackTests` (the wait: lands on read 1 and 5, never lands in exactly 16 reads, cancellation, including a cancel during a delay that ignores the token, a read with no answer, the options judgement with `FenixOptionEdits.Applied` and an answered read without the option ending the wait at once), `FenixDocumentPinsTests` (`Read_back_waits_until_the_Fenix_shows_the_pin`, `Read_back_gives_up_with_the_opposite_after_the_attempts`, `Read_back_confirmed_at_once_never_delays`) and `FenixOptionEditsTests.All_three_keys_read_back_through_one_path_that_waits_until_the_change_has_applied` and `The_reads_while_the_Fenix_catches_up_never_write_the_tree` (source scans of the options window). → [a32nx.md](../a32nx.md)

## FNX-16

- Every value the Fenix Engines window reads out (running, N1, EGT, N2, fuel flow, oil quantity, pressure and temperature, TAT and OAT) comes from the Fenix's own data-service values, the 18 names in `FenixEngineNames` (`aircraft.engines.{1,2}.running`, `.n1`, `.egt`, `.n2`, `.ff.kg`, `.oil.quantity`, `.oil.pressure`, `.oil.temperature`, `aircraft.temperature.tat` and `.oat`), never the stock engine SimVars (`TURB ENG *`, `GENERAL ENG *`, `ENG *`, and `AMBIENT TEMPERATURE` for an engine page).
- Why: the stock SimVars run the sim's generic engine model, which does not match the Fenix's own displays. Stock N2 also falls to 0 one second after a master goes off, while the Fenix's takes about 20 s to fall below 20 % (2026-10-22).
- Measured 2026-10-21 (IAE A321, both engines at idle, read-only) and checked against the Fenix's SD ENGINE page on 2026-10-22 (CFM A320 C-FFWM): oil quantity, pressure and temperature, fuel flow and TAT matched (QT, PSI, °C, KG/H). `aircraft.engines.{1,2}.vibration.n1` reads `""` on v3 (not published), so there is no vibration row. Output O (`AMBIENT TEMPERATURE`) matched the Fenix's OAT, so it stays stock.
- The First Officer judges "running" and "stopped" on the Fenix's own flag and N2, and falls back to stock N2 only while that is unknown or 5 s old (`FenixFoLiveReadings`): a judgment with a fallback, not a readout.
- Pinned for the Engines window by `FenixEngineWindowTests.Engine_readouts_never_use_stock_engine_simvars` (a scan of the window and the `FenixEngine*` services); a readout elsewhere (a hotkey in the definition, another window) is not. → [a32nx.md](../a32nx.md)

## FNX-20

- The Fenix option Encoder Acceleration (`encoder_acceleration_enabled`, `FenixOptionKeys.EncoderAcceleration`) multiplies a large or a quick turn of an FCU knob. Measured by the owner on 2026-10-24 (Fenix 3.0.0.7454, A321 IAE, acceleration on unless said), with the old typed-set path (one `JumpCounter` write of the whole difference, two cache checks 750 ms apart, then a "batched retry" of 10-count writes about 46 ms apart):
  - Typed altitude 15000 to 7000: one write of -80 counts landed at 100, the floor; the batched retry (+10 six times, +9) then ran it up to 30600. Nothing was spoken.
  - Typed speed 100 to 250: went to 399, then down to 100.
  - Typed altitude +40 counts in one write: overshot to 49000, the ceiling; the batched -10 retry ran it to 100.
  - Typed altitude +20 and +5 counts in one write: exact. The panel's FCU Altitude Inc, one +1 write: exactly +100 ft; five +1 writes about 150 ms apart: exactly +500 ft.
  - The baro knobs (`AdjustBaroCounter`, one RPN delta) are NOT accelerated: -30 and +69 counts in one write landed exactly, with acceleration on and with EFIS baro linking on.
  - With acceleration off the old path worked (15000 set exactly, and the earlier plans' checks).
  So a single write somewhere between 20 and 40 counts is multiplied, and so are quick successive writes; a single write of up to 20 counts, given time to settle, lands exactly.
- So a typed FCU set (heading, speed, altitude, V/S: `SetFCUHeading`, `SetFCUSpeed`, `SetFCUAltitude`, `SetFCUVS`, all through `SetFcuKnobAsync`) is a closed loop, `FenixA320FcuKnobSet.RunAsync`:
  - With acceleration on or unread, each write carries at most 20 counts (`AcceleratedChunkLimit`), and the next write waits 500 ms (`AcceleratedSettleMs`) and a fresh read of the knob through its on-request twin ([A320-41]), and is worked out from the value READ, never from a count kept in the app ([FNX-5]). With acceleration off, one write carries the whole difference (it lands, and it is quicker: about 0.3 s for 80 counts against about 2.2 s in four chunks, before the settings query), read back the same way after 250 ms.
  - A knob that has not moved after a write is never written again: the loop polls every 250 ms up to 1.5 s after the write (`NoMoveWaitMs`) and then gives up. Writing again on an unmoved knob is how a slow write turns into two.
  - A move other than the one written is judged only once two reads agree; a move larger than written, or the wrong way, is acceleration after all (a stale "off", or a time window longer than the settle): the chunk halves and the wait doubles (up to 2 s), and an "off" set falls back to 20-count chunks.
  - Bounded: four writes in a row that bring the knob no closer (`StallWrites`), 50 writes or 30 s end the set as a miss. A back-off that changes the chunk or the wait starts that count afresh: the overshoot is not a stall, and the smaller writes correcting it would otherwise hit the bound (review trace, Factor 5 and a 900 ms window, 15000 to 11000, ended Missed at 9000). There are at most four such changes (20, 10, 5, 2, 1).
  - The V/S window's dashes ([a32nx.md](../a32nx.md), "The V/S and the baro windows on v3"): while dashed, `N_FCU_VS` is the live V/S, so the first write is aimed from it; a window still dashed after a write ends the set ("Vertical speed still dashed, not -1000."), since the read-back is then not the knob. What the Fenix shows after the first click on a dashed window is not measured.
  - The 46 ms batched retry is gone; nothing in the definition writes a burst of knob counts.
- The option's state comes from the Fenix, `FenixEncoderAcceleration` over `FenixDataService.GetSettingsAsync`, never waited on for more than 1.5 s: an "off" is kept 5 s (a stale off lets one whole-difference write through before the loop sees it multiplied), an "on" or an unread answer 60 s. Anything but a readable true or false is unread, and unread counts as on: the chunked path lands either way, only more slowly. After a settings write the query can lag ([FNX-13]); the loop's multiplied-write check covers that window.
- One set per knob at a time (`FenixA320FcuKnobSet.Turns`): a newer set of the same knob ends the older before its next write, a set of another knob carries on, an aircraft switch (`OnSwitchedAway`) or a disconnect ends them all, silently. A write less than 500 ms old is waited out before the new set's first read, so that read cannot predate it. The four windows skip their "Already at …" check while a set of that knob is running (`Turns.IsRunning`): the 1 Hz cache can show one of its steps, so typing 9000 while a 15000-to-7000 set passed 9000 said "Already at altitude 9000" and the old set turned on to 7000; the new set takes over and lands silently if its fresh read already shows the target. A superseded altitude set does not restore `S_FCU_ALTITUDE_SCALE` (the newer set needs 100 ft mode, and after a switch the aircraft may not be the Fenix).
- Spoken: nothing on success ([CORE-7]: the screen reader read what was typed). The knob's own once-a-second value announcement (`N_FCU_HEADING`, `_SPEED`, `_ALTITUDE`, `_VS`, Continuous and IsAnnounced) would speak every step a chunked set passes through ("FCU ALTITUDE: 13000 … 11000 … 9000 … 7000"), so while a set of that knob runs, `ProcessSimVarUpdate` consumes each delivery that is not the target (`Turns.Swallows`; within 0.5, a heading modulo 360) and passes the target to the generic announcement, so a landed set is heard once ("FCU ALTITUDE: 7000"), as before, as `SetFCUBaro` does with `isSettingBaro`. After a Missed or StillDashed end the knob stays quiet for `QuietAfterMissMs` (1.2 s, past the 1 Hz delivery period), so the miss sentence is the only thing heard; any later change speaks again. A miss is said once, invariant, in the pilot's terms: "Altitude set to 7100, not 7000.", "Speed set to 0.80, not 0.78.", "Heading set to 005, not 010.", "Vertical speed set to -1200, not -1000."; a read that failed: "Altitude not confirmed.", or "Altitude not set: no read-back." when nothing was written.
- Not measured: the Fenix's own acceleration rule (the count and the time window); a 20-count write 500 ms after another (the loop adapts if it is multiplied).
- Pinned by `FenixA320FcuKnobSetTests` (a fake knob that multiplies a write of more than 20 counts or one within 100 ms of the previous by 3: 15000 to 7000, speed 100 to 250, the heading wrap, a knob that never moves, a late write never sent twice, the stall and time bounds, a Factor-5 multiplied correction that still lands, a stale off, a newer set, the dashed V/S, the spoken texts and "Already at" under de-DE and sv-SE; the value filter, its target pass-through and the quiet after a miss, in `Turns` and through `ProcessSimVarUpdate`; source scans of the four sets, the "Already at" skip, the scale restore and `SetFcuKnobAsync`) and `FenixEncoderAccelerationTests`. A new FCU writer elsewhere is not. → [a32nx.md](../a32nx.md)
