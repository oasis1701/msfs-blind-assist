# Fenix data service rules — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/fenix-data.md`, which Claude Code loads when it reads matching code. Background: [a32nx.md](../a32nx.md).

## FNX-1

- A read of a name the Fenix data service does not know returns the empty string `""`. `FenixDataValue.FromJson` maps it, and a missing token, to `FenixValueKind.EmptyOrUnknown`; a JSON null stays `Null`; `IsKnown` is false for both. No caller may treat either as 0, false, off, closed or empty: show "no data" (a numeric reader uses NaN or skips the row). `FenixDataService.ReadAsync` and `ReadManyAsync` also give `FenixDataValue.Unknown` when the Fenix is not loaded or the gateway is down, so "no data" covers "no Fenix" too.
- Measured 2026-10-21 (Fenix 3.0.0.7426, A320 CFM WF, sim running, reads only): a name the gateway does not know answers `""`, not an error. `doors.entry.d1l` and `system.config.Units.Weight`, both gone in v3, read `""`. The previous Fenix (2.4.0.4720) answered null for the same case, so any older note or code that tests for null means this case too.
- Why: `FenixDataValue` is a struct, so reading `Number` or `Bool` off it without checking `Kind` gives 0 or false. A renamed or mistyped name would then read as a closed door, an off switch, 0 percent or a quiet caution, and nothing would say so. Before v3 nothing in the app depended on the difference (it read only the MCDU screens there); every later reader must.
- Pinned by `FenixDataQueriesTests` (`FromJson_reads_each_kind`, `Only_a_value_that_is_neither_empty_nor_null_is_known`, the `ParseReadMany_` cases) and `FenixDataServiceClientTests` (`ReadAsync_returns_unknown_when_the_service_is_down`). → [a32nx.md](../a32nx.md)

## FNX-2

- `FenixDataService.Subscribe` delivers every change to its `onChange` callback on a thread-pool thread, the one running the shared WebSocket loop, never the UI thread. A form or window that shows or acts on a value marshals to its own thread with `BeginInvoke` inside try/catch(InvalidOperationException) ([A380C-6]): an `IsHandleCreated` check alone races the handle's destruction. Disposing the returned handle ends the subscription, but a callback already running, or one value already on its way, may still arrive afterwards (or after the window closed), so the marshal must tolerate a form that is gone. An exception from a callback is logged once and swallowed; it never stops the loop.
- The service itself never speaks and never touches a control: it holds no announcer and no form. A spoken change is the caller's decision, made on its own thread and under the app's announcement rules, so a subscription can be added to a window without that window changing what the pilot hears.
- Why: the callback runs inside the socket loop, so a blocked or slow callback stalls every subscription of the session, and a control touched from a pool thread throws. The same trap, with the same fix, applies to every bridge push in the app ([A380C-6]).
- Pinned by `FenixDataServiceClientTests` for the message parsing; the thread contract is documented on `Subscribe`, and no unit test can pin a form's marshal. Verify in the sim: open a Fenix window while values change and close it mid-update. → [a32nx.md](../a32nx.md)

## FNX-3

- Names for the Fenix data service come only from open sources: the gateway's own EFB and FAP web bundles (the pages the service itself serves at 127.0.0.1:8083), names the app already uses, and HubHop. Each is then checked against the running service, which is possible because an unknown name reads `""` ([FNX-1]). Never guess a name, and never ask the service for its schema (an introspection query, the `?sdl` text, the IDE page) to find one: that was ruled out on purpose, as the next bullet says.
- Schema introspection was ruled out on purpose in the v2 investigation (Fenix 2.4.0.4720) and has not been retried or worked around since (2026-10-21). Whether the service, or v3's new gateway executable, would answer it is not known, and the choice does not depend on it. The stated reason is the principle behind the Fenix display program's refusal of .NET inspection (measured 2026-10-11): a vendor's deliberate block is the developer's decision, and an accessibility purpose does not change who makes it, so the app does not go looking for what the vendor has not published. If a value the app needs is not published under a name found this way, the route is the existing AI picture reads.
- The app also never sends the gateway's navigraph operations. The operations in the EFB and FAP bundles include two: an `accessToken(forceRefresh)` query that returns the pilot's Navigraph access token and expiry, and a `disconnect` mutation that ends the Fenix's Navigraph connection. Nothing the app does needs either, and reading a credential or signing the pilot out of their Navigraph connection is not a side effect to risk. This is pinned by `FenixDataServiceClientTests.No_Fenix_code_sends_a_navigraph_operation`, a source scan of the Fenix code for a GraphQL `navigraph` selection (comments are ignored, so a comment may still say "never"), not by a rule line.
- Observed 2026-10-21 on 3.0.0.7426: the operations in the EFB and FAP bundles touch `dataRef` (reads, writes and the `dataRefs(names:)` subscription), `settings`, `fap` and `navigraph`, plus REST paths under `/fenix`. `FenixDataQueries` builds only `dataRef` and `settings` queries and the subscription. → [a32nx.md](../a32nx.md)
