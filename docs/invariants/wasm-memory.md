# WASM module memory, the PMDG 737 FMA, engine displays and navigation display — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/wasm-memory.md`, which Claude Code loads when it reads matching code. Background: [wasm-memory.md](../wasm-memory.md).
WASM-1 to WASM-7 were written on 2026-10-23 with the FMA reader they guard; WASM-6 and WASM-7 record decisions its reviews forced while it was built, each with its reason below. WASM-9 to WASM-11 were written on 2026-10-24 with the engine display reader and the shared module session; WASM-2 and WASM-7 were widened to cover the engine display reader then. WASM-12 to WASM-14 were written on 2026-10-25 with the navigation display reader. WASM-21 was written on 2026-10-31 with the layout file format. The same day, when the app started loading layout files, WASM-2 and WASM-11 were reworded for layout files and WASM-26 was written with the layout store. WASM-29 was written that day too, at the owner's request during the in-sim test of the layout files; WASM-9, WASM-12 and WASM-18 were reworded with it, and WASM-2's and WASM-26's account of what the pilot hears was brought in line. The numbers this file skips (WASM-8, WASM-16, WASM-17, WASM-22 to WASM-25, WASM-27, WASM-28, WASM-32 and WASM-33) are taken: never give them to a new rule.

## WASM-1

- `SimProcess` opens the simulator with `PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ` and nothing else. With those rights Windows itself refuses a write, a thread suspension, a debugger attach or an injection, even from a bug in the app, so the read-only promise holds by construction rather than by care. Never widen the access mask, and never add a write, `DebugActiveProcess`, `CreateRemoteThread`, `SuspendThread`, a hook or any other way of acting on the simulator: the owner accepted reading PMDG's memory (2026-10-23) on the condition that the app can only read. `SimProcess` stays self-contained: no app types, no logging. → [wasm-memory.md](../wasm-memory.md#safety-model)

## WASM-2

- The app never derives or hardcodes a wasm address, field offset, object size, word-table base or word. Every number it reads memory by comes from a layout file: the generator, an optional program beside the app that writes layout files, wrote it from a `737NG3.wasm` of the installed build (or the file came from the layouts store, bundled beside the exe: [WASM-31]), and `LayoutStore` loaded it because it fits the installed file and is current ([WASM-26]). Each reader takes its own layout from the build (`ModuleBuild.Layout`); a reader whose layout is a failure, or a file with no current layout, is unavailable. The log gets the reason, and the display keys use the AI read. With no layout file loaded the pilot hears one line for the four readers, "PMDG display files could not be loaded; the display keys fall back to AI reading." ([WASM-29]; until 2026-10-31 each reader said its own); a reader whose own layout is a failure in a file that loaded says its own "… announcements unavailable: PMDG file not recognised" (or the engine display, ND or PFD equivalent). It is never a guess, never a fallback to known numbers, and never a layout typed into the app's code: a PMDG update moves the numbers, and a hardcoded copy would read a wrong field as a mode. Every word spoken is read from PMDG's own tables into the layout, with one exception in kind: the value-1 words "CWS P" and "CWS R", which the generator supplies and puts in the layout only once those UTF-32 strings are found in the file. → [wasm-memory.md](../wasm-memory.md#the-shared-module-session)

  History. Written on 2026-10-23 for the FMA and widened on 2026-10-24 to the engine displays, a failed engine display layout leaving the FMA running ([WASM-11]). Reworded on 2026-10-31, when the app started loading layout files: the generator runs once per PMDG build and saves the layouts in a file, and the app takes its numbers from a current layout file and from nowhere else.

## WASM-3

- The app finds the module's linear memory only through `WasmMemoryLocator.FindLinearBase`: for each distinct committed, `MEM_PRIVATE`, readable allocation, it checks that the anchor's range lies in committed readable memory of that same allocation (`ModuleMemory.IsInsideModule`) and then reads just the anchor's 96 bytes at `allocation base + anchor address`; exactly one match gives the base. `MEM_IMAGE` regions are never searched: MSFS compiles the module to a native DLL (`%APPDATA%\Microsoft Flight Simulator 2024\WASM\MSFS2024\pmdg-aircraft-738\m*.dll`) that embeds a copy of the data segment, and that copy must never match. The app never scans all of memory. → [wasm-memory.md](../wasm-memory.md#safety-model)

  Measured in the spike, on the `737NG3.wasm` of 2026-08-30: the linear memory is one `MEM_PRIVATE` allocation, and the linear base equals the allocation base, so a wasm address `a` is at `base + a` in the simulator. The locator's review (commit `a6a1d0d59`) reproduced a false match on a `MEM_IMAGE` copy when the anchor read was not bounded to its own allocation, which is why the bounds check comes before the read.

## WASM-4

- The FMA object (PMDG's autopilot singleton, from its pointer to pointer + object size) must lie in committed, readable memory of the anchor's own reservation, the allocation whose `AllocationBase` is the linear base, and that bound is re-walked on every check (`ModuleMemory.IsInsideModule`, which `ModuleFmaSampler.TryRead` calls on every read, as every `ModuleMemory` read does; inside one ND reading's `RememberRegions` scope, once per region per reading: [WASM-15]). Never bound it by the region found at the anchor, and never capture the bound once: the object is heap memory (`operator new`) that PMDG's `memory.grow` commits after start. In the spike the object sat at `0x6bd740` while the region at the linear base was `0x280000` long, and linear memory can keep growing. A read that falls outside, or of freed memory, fails cleanly (`ReadProcessMemory` returns false); the monitor then searches again. → [wasm-memory.md](../wasm-memory.md#safety-model)

## WASM-5

- The FMA announcements never suppress, replace, delay or reword the 737's MCP-light announcements (the AP, A/T, LNAV, VNAV, LVL CHG, HDG SEL, VS, ALT HOLD, VOR/LOC and APP lights). Owner, 2026-10-23: "these both are seen in the real aircraft, and our blind pilots should also hear them too." FMA changes and the monitor's status lines speak through the announcer's non-interrupting `Announce`, as the MCP-light announcements in `PMDG737Definition.ProcessSimVarUpdate` do, so neither cuts the other off. There is no ordering between them: the FMA speaks about 300 ms after memory changes, while an MCP light waits for the next SDK update (about a second), so the FMA often comes first. Output P, which read the whole FMA with the interrupting `AnnounceImmediate`, was freed on 2026-10-30 (owner: the announcements and the PFD window already give the FMA). Do not "de-duplicate" the two (for example, by dropping the APP light's announcement because "Roll armed: VOR/LOC" follows it): the MCP lights and the FMA are different instruments, and the real crew sees both. → [wasm-memory.md](../wasm-memory.md#what-the-pilot-gets)

  Mirrored to `pmdg-737-call-sites.md`, so it loads with `PMDG737Definition.cs`, which holds the MCP-light announcements.

## WASM-6

- Every FMA announcement, the baseline and the PFD window's FMA rows come only from a good reading, and there is ONE gate for it: the display pointer equals the autopilot pointer (`FmaSample.PointersAgree`), `Pmdg737FmaCrossCheck.Passes` agrees with the PMDG SDK, and no value is corrupt (`Pmdg737FmaSpeech.Lookup`). The cross-check compares the FD switches in memory with the SDK's `MCP_FDSw_0`/`MCP_FDSw_1`, the MCP altitude with `MCP_Altitude` and the MCP heading with `MCP_Heading` (0 equal to 360). The SDK lags memory by about a second, so each field must match at least one memory sample of the last 3 s, and different fields may match different samples. → [wasm-memory.md](../wasm-memory.md#the-monitor-at-runtime)

  A reading that is not good only counts toward the two stop limits: no reading agreeing with the SDK for 2 s stops the announcements ("FMA announcements stopped: values do not match the SDK", recoverable: when a good reading returns the pilot hears "FMA announcements resumed" followed by whatever changed meanwhile, and that reading becomes the baseline), and ten corrupt readings in a row stop the reader ("FMA announcements stopped: unexpected values", then unavailable until the reader restarts, on a flight reload or when the 737 is selected again). Both are spoken once. In Verifying, only a good reading becomes the baseline. While stopped on a mismatch, the readout (`DescribeForReadout`, the PFD window's FMA row) gives the last good reading only after "Last known:", never as the current FMA.

  Why (2026-10-23): the monitor's first version let a reading that failed the cross-check, or carried `PointersAgree == false`, be spoken and read by Output P inside the 2 s tolerance; the review of commit `525bbd6a4` found it, and a corrupt Verifying baseline produced a phantom "Pitch: ALT HOLD". The design's own rule, every announcement gated by the cross-check, won: one gate (`IsGood` in `Pmdg737FmaMonitor`, with `OnRunning` applying the same three conditions). The cost: a change seen only on a failing tick is spoken one good tick later (100 ms in normal flight), or, if the reader stops on a mismatch first, with "resumed" when it recovers. Pinned by `Pmdg737FmaMonitorTests`.

## WASM-7

- `Pmdg737FmaEnvironment.ReadSdk` returns null while SimConnect is disconnected, and checks that FIRST, before the PMDG data manager. So does `Pmdg737EngineDisplayEnvironment.ReadSdk` (through its testable `Snapshot(connected, ready, field)`, pinned by `Pmdg737EngineDisplayEnvironmentTests`), for the same reason. The data manager is replaced only on a connect or an aircraft switch: after a disconnect the old one stays in place, still `IsReady`, still holding its last snapshot. Without the connection check a closed simulator reads as live SDK data, the monitor keeps searching memory that is gone, and two minutes later the pilot hears "FMA announcements unavailable: aircraft memory not found". With it, the monitor drops the memory and waits silently in WaitingForSdk for the next connection. → [wasm-memory.md](../wasm-memory.md#the-monitor-at-runtime)

  Found in the review of commit `9f84562ad` (2026-10-23); the reviewer traced `IsConnected` going false before `ConnectionLost` on both drop paths of `SimConnectManager`. `ReadSdk` is sim-facing and has no unit test; the in-sim test plan checks it (close the simulator with the 737 loaded: no "unavailable" after two minutes, and the `pmdg737-fma` log ends at WaitingForSdk). A related open point: after a flight reload `IsReady` stays true on a stale snapshot, so the search can start during the loading screen; a load longer than the 120 s window says "unavailable" once, and the 30 s retries that follow find the FMA and say "resumed".

## WASM-9

- The engine display reader (`Pmdg737EngineDisplayMonitor`) never suppresses, replaces, delays or rewords the 737's existing announcements: the SDK start valve ("Engine 1 Start Valve: Open", `ENG_StartValve_0/1`), the overhead engine lights ("Engine 1 REVERSER: on"), the MCP lights and the FMA. During an engine start the pilot hears both "Engine 1 Start Valve: Open" and "Upper DU alert: engine 1 START VALVE OPEN" on purpose: the first is the valve's real position from PMDG's data (no cockpit light shows it), the second is the message the crew sees on the upper display; users' feedback decides later (owner, 2026-10-23). Everything the reader says by itself (alerts appearing and going, gauge colours, the thrust mode, its status lines) uses the announcer's non-interrupting announce, as the FMA does ([WASM-5]): owner, "nothing interrupts". When the reader cannot work, Output Alt+E says nothing of its own and goes straight to the AI read of the upper display ([WASM-29]). → [wasm-memory.md](../wasm-memory.md#the-engine-displays)

  History. Until 2026-10-31 Alt+E first said "Engine displays unavailable: <reason>", interrupting as a key-press answer, the reader's one interrupting line. The owner, during the in-sim test of the layout files: "when pilot presses the display keys, no need to throw an error at them. just allow the AI read to continue". Nothing the reader says interrupts now.

  Mirrored to `pmdg-737-call-sites.md`, so it loads with `PMDG737Definition.cs`, which holds the start-valve and overhead-light announcements and the Output Alt+E fallback.

## WASM-10

- Every engine display announcement, the baseline, the window's lists and the manual N1's read-back come only from a good reading, and there is ONE gate for it (`IsGood` in `Pmdg737EngineDisplayMonitor`, with `OnRunning` applying the same conditions): the EFIS object's six display units carry their own indexes 0 to 5 in order (`Pmdg737EngineDisplayCrossCheck.Fingerprint`), the three tank quantities each match the PMDG SDK's `FUEL_QtyLeft` / `FUEL_QtyCenter` / `FUEL_QtyRight` within 1 lb in at least one memory sample of the last 3 s (`Pmdg737EngineDisplayCrossCheck.Passes`; left is tank 1, right tank 2), and no value is corrupt (`Pmdg737EngineDisplayMonitor.Corrupt`: a non-finite double, N1 or N2 outside -1 to 130, EGT outside -100 to 1 300, a page, crew alert, tank warning or autoland value outside 0 to 255; a page value outside the derived map is not corrupt, the list names it "page 14"). A reading that is not good only counts toward the two stop limits, as the FMA's ([WASM-6]): 2 s without a good reading stops the announcements ("Engine display announcements stopped: values do not match the SDK", then "resumed" followed by whatever changed), ten corrupt readings in a row make the reader unavailable. → [wasm-memory.md](../wasm-memory.md#the-engine-displays)

  The tolerance was measured live on 2026-10-24 (737-800, the APU burning tank 1): memory and SDK both hold PMDG's indicated quantity and agree to 0.02 lb, so the tolerance is the 1 lb floor. The spec's N2 check against `TURB ENG N2` was dropped in planning: the 737 definition does not request that SimVar, and the tanks already prove the engine object; the glass object (SYS page, memos) is held only by the range checks.

  **The displays dark (2026-10-24, live).** The fuel check passes at 0 = 0 while the aircraft is cold and dark, and the owner's cold-and-dark 737 showed twice why that is not enough. First, before PMDG's aircraft initialises, PMDG updates none of the display objects, so they hold their starting values (X-BLD START set on both engines, EGT limits 933/860, N1 red line 100, the upper display on page 4); the layout gives the aircraft's initialised flag (`AircraftFields.Initialised`). Second, once initialised, PMDG's logic runs with the displays unpowered: every display unit sat on page 0 (off), A/T LIM was set (PMDG sets it while the FMC is unpowered) and the empty tanks read LOW, and the first build said "Upper DU alert: A/T LIM" to a dark cockpit. So `Pmdg737EngineDisplayPages.DisplaysLit` (initialised, and the upper or lower unit on a page other than off or blank) gates every comparison in `Pmdg737EngineDisplaySpeech.Changes`, the lists say "Upper display: off", and the monitor absorbs every change for 10 s after the displays light up (`LightUpQuietMs`): PMDG keeps them blank for about half a minute after ground power comes on, and the FMC and fuel indication may settle a moment after the display units, so power-up is never spoken as alerts coming and going. Live, the owner powered up a cold 737 and heard nothing. Cost: a genuine alert in the first 10 s after the displays light up becomes the baseline unspoken (it is in the window). A display unit's power and failure change the page PMDG assigns it (page 0 unpowered), which the lists follow.

## WASM-11

- `ModuleSession` is the one place that finds a WASM module's installed files (through its `IModuleHost`, for the 737 the `737NG3.wasm` copies), gets each file's build once from its `ILayoutSource` (in the app, `LayoutStore`), opens the simulator read-only and searches for the module's linear memory, for every reader of the module. A reader asks it (`AnalyseAsync`, `LocateAsync`) and turns the result into its own layouts and samplers (`Pmdg737FmaEnvironment.ToFmaAnalysis` / `ToFmaCandidates` and the engine display, ND and PFD equivalents, each taking its layout by reader id from `ModuleBuild.Layout`). A reader never opens the simulator, reads the installed file or a layout file, or runs the generator itself. One search serves every reader: a search in flight is joined, a completed one that FOUND something is reused for 5 s from its start (`ReuseMs`) unless `Invalidate` ran (a flight reload or reconnect), and every located build shares one read-only handle through reference-counted leases, the session holding one until it searches again or is disposed. Readers are independent: a build is kept when any reader has a layout, it is located by any of its anchors in the module's reader order, and a reader whose result is a failure costs only that reader. Two installed copies loaded from the same layout file are one build (`ModuleBuild.SameLayoutsAs`), searched for once. Only a module that cannot be found, or no build with a layout, makes every reader unavailable. → [wasm-memory.md](../wasm-memory.md#the-shared-module-session)

  Why (owner, 2026-10-23): the FMA's search took about 8 s; two readers each searching would double the cost and the handles, and one reader's layout failing after a PMDG update must not take the other display with it. The owner expects more displays ("maybe like the ND") and the PMDG 777 to copy this shape. The FMA moved onto the session first, its behaviour and tests unchanged, and its smoke test through the session passed live on 2026-10-24. The navigation display (2026-10-25) was the third reader on it, located by its own "EXCESS DATA" anchor too, and the PFD the fourth. On 2026-10-31, when the app started loading layout files, the session became generic: a build is the set of results its module declares, not four fixed fields, so the 777 can use the same session with its own reader list. The generator now works out each reader's layout, one reader's failure never stopping another's; the session keeps the search half. Pinned by `WasmModuleSessionTests`.

## WASM-12

- The navigation display reader (`Pmdg737NavDisplayMonitor`) adds speech beside what the pilot already hears and takes nothing away: PMDG's own TERRAIN, WINDSHEAR and TCAS aural callouts, the app's MCP-light, FMA ([WASM-5]) and engine display ([WASM-9]) announcements and the EFIS mode, range and VOR/ADF selector announcements all stay exactly as they are. Everything it says by itself (an ND message appearing or going, the active waypoint changing, its status lines) uses the announcer's non-interrupting `Announce`, so it never cuts one of those off; the only interrupting answers are every Output Ctrl+W answer (the top-right corner, "No active waypoint", "ND waypoint unavailable: <reason>"), as key-press answers. When the reader cannot work, Output Alt+N says nothing of its own and goes straight to the AI read ([WASM-29]); Ctrl+W has no AI read to fall back to, so it still says why. The window's button read-back, said only for a press that changed nothing (NVDA reads a changed button's text itself, [CORE-7]), is the non-interrupting announce too. → [wasm-memory.md](../wasm-memory.md#the-navigation-display)

  Why (owner, 2026-10-25, the ND design): the ND repeats much of what the pilot hears elsewhere (PMDG's TCAS and GPWS voices, the FMA); speaking over any of it would cost more than the ND line gives.

  History. Until 2026-10-31 Alt+N first said "Navigation display unavailable: <reason>", interrupting, before the AI read. The owner, during the in-sim test of the layout files: "when pilot presses the display keys, no need to throw an error at them. just allow the AI read to continue".

## WASM-13

- Every navigation display announcement, the baseline, the window's rows and Output Ctrl+W's answer come only from a good reading, through ONE gate in `Pmdg737NavDisplayMonitor`: the EFIS object's six display units carry their own indexes 0 to 5 in order (`Pmdg737NavDisplayCrossCheck.Fingerprint`), the Captain's EFIS mode and range in memory match the PMDG SDK's `EFIS_ModeSel_0` and `EFIS_RangeSel_0` in one memory sample of the last 3 s (`Pmdg737NavDisplayCrossCheck.Passes`; the range is the knob's index, the SDK's numbering), and the sampler reports no `corrupt` check. A corrupt reading is never remembered, shown or spoken and only counts toward the unexpected-values stop (ten in a row); 2 s without a reading matching the SDK stops the announcements ("ND announcements stopped: values do not match the SDK", then "resumed" followed by whatever changed). Nothing is compared while `Pmdg737NavDisplayCrossCheck.DisplaysLit` is false (the Captain's EFIS panel unpowered, or every display unit off or blank), nor for 10 s after it turns true (`LightUpQuietMs`), so power-up is never spoken as news. → [wasm-memory.md](../wasm-memory.md#the-navigation-display)

  Why: the mode and range selectors are the only ND fields the SDK also carries, and they are always present (cold and dark too: measured live 2026-10-25). The SDK's distance to the destination (`FMC_DistanceToDest`) was measured as a second route check and rejected: it adds the last waypoint to the destination, which no route node holds (344 NM against the nodes' 187.3, live at KATL). Mode and range are small integers a wrong candidate could match by chance, so the engine display gate's fingerprint is kept beside them.

## WASM-14

- `ModuleNavDisplaySampler` reads PMDG's route as a chain of heap pointers, not a fixed block, so every walk is bounded and all-or-nothing: each pointer (the plans, the key nodes, every next node, the nearby lists' vectors and objects, the TCAS list and targets, the CDU FIX page and its entries, the route's airports and runways) must lie inside the module's committed memory ([WASM-4]); each node is read as one block; a walk stops at the layout's cap (`MaxNodes`, the lists' `ListCap`, the traffic's `MaxTargets`) and fails on a node visited twice (a loop); every node, object and target the sample carries must look real where PMDG prints it (a printable name within its field, a position marked valid with latitude and longitude in range, finite traffic values; the distance from 0 to half the earth's circumference and the clock within the day on the TO node only, the one node PMDG prints them for: a later node's clock out of the day reads as no ETA, its distance is not printed). The TCAS list's target pointers are read up to its count, and a CDU FIX page entry whose fix position is not valid is left out (PMDG places it without a test; the reader cannot). Any failed check discards the whole reading as corrupt, with the check named; never a partial route or list, so PMDG changing the route while it is read (sequencing, an executed edit) costs one reading, and the settle means a half-changed route is never spoken. Nodes PMDG passes over without drawing (hidden, discontinuities, conditional legs) need only lie inside the module. → [wasm-memory.md](../wasm-memory.md#the-navigation-display)

  Why: the spec's main risk (2026-10-25). The caps are the reader's, found in no PMDG limit: 512 route nodes, 4096 list elements (441 fixes were measured at KATL at range 40), 64 traffic targets; a longer chain reads as corrupt. The checks follow what PMDG prints since the Task 4-8 review (2026-10-25): the corrupt stop is final, so a check on a value PMDG never prints (every node's distance, the traffic head read for the most targets past the end of committed memory) could end the reader for good over nothing the pilot sees.

  A nearby list's objects are read only while PMDG draws that list (its STA, WPT or ARPT button on; fixes only up to their range); its count is read every time. PMDG keeps the vectors filled after a button goes off (441 fixes with WPT off, live at KATL 2026-10-25), so an object PMDG does not draw is neither read nor checked.

  The route line (each route's lateral path) is read the same way: its points up to the count as one block that must fit inside the flight plan, stopping at the first point not in use as PMDG's draw does; a drawn line's ends are positions in range (one not valid cannot be placed and is left out); the node a point heads for is resolved in the map walk's chain; a node off that chain must lie inside the module, but PMDG prints nothing of it (only its direct-to intercept drawing takes it), so a name it could not print leaves the line heading for nothing and a position out of range is none, never a corrupt reading (whole-branch review, 2026-10-28).

## WASM-15

- `ModuleMemory.RememberRegions` remembers each region's answer (VirtualQueryEx, through `IProcessMemorySource.RegionAt`) until the scope it returns is disposed, and only on the thread that opened it; `ModuleNavDisplaySampler.TryRead` opens one scope per reading, around everything it reads. Never keep a scope across readings or open it for a monitor's lifetime: PMDG's `memory.grow` commits memory after start ([WASM-4]), so each reading must ask afresh. Inside one reading, a region found missing is asked again, and a region answered "not committed" stays so until the reading ends; that costs at most one reading (corrupt or lost), which the monitor's stops already absorb. A scope opened inside a scope shares the outer one. The FMA and engine display samplers open none: their readings are a few blocks. → [wasm-memory.md](../wasm-memory.md#the-navigation-display)

  Why: measured live 2026-10-25 (KATL, the -800): a VirtualQueryEx on the simulator costs about 208 µs and a ReadProcessMemory of 104 bytes about 0.9 µs, and every `ModuleMemory` read asked one to three (`IsInsideModule`, then `TryRead`'s own walk). An ND reading took 25 ms with the map buttons off and 90 ms with WPT on at range 40 (441 fixes), every 500 ms on the UI thread; the owner felt the list stall while scrolling. With the scope: 0.7 ms and 1.8 ms.

## WASM-18

- The primary flight display reader adds; it never suppresses or replaces PMDG's own callouts (WINDSHEAR, PULL UP, MINIMUMS) or the app's MCP, FMA, engine display, ND, EFIS selector or altimeter announcements. Everything `Pmdg737PfdMonitor` says by itself (a message appearing or going, its status lines) is the non-interrupting announce; a message whose `PfdMessage.Spoken` is false (WINDSHEAR, PULL UP, the FMA strip's extras) is a row only; only Output Alt+P's line with PMDG's classic EFIS look on the Captain's screen, "Classic EFIS is selected, falling back to AI reading", interrupts, a key-press answer, and the AI read follows. When the reader cannot work, Alt+P says nothing of its own and goes straight to the AI read ([WASM-29]). NVDA reads a focused button's new text itself, so a stateful button's press is read back only when it changed nothing, 3 s later (never silent, owner 2026-10-30; [CORE-7]); MINS RST, whose text never changes, is always read back. → [wasm-memory.md](../wasm-memory.md#the-primary-flight-display)

  Why: the spec's Safety list (owner, 2026-10-29), as [WASM-9] and [WASM-12] for the engine displays and the ND. PMDG calls WINDSHEAR and PULL UP out itself; a second voice saying them would cut across the warning. Ground session 2 (2026-10-30) heard "FPV: on" from NVDA and "FPV on" from the window for one press, and "Altimeter standard" then "STD on" for STD, so the stateful buttons' read-back was dropped; the owner then asked (2026-10-30) that a press that did not take never be silent, so it returned for that case only, as the 737 MCP windows' [P737-7], and the ND window's map buttons got the same rule.

  History. Until 2026-10-31 Alt+P first said "Primary flight display unavailable: <reason>" when the reader could not work, and "Primary flight display: the classic EFIS display is selected, not read" with the classic look, both interrupting, before the AI read. The owner, during the in-sim test of the layout files: "when pilot presses the display keys, no need to throw an error at them. just allow the AI read to continue", and "when classic pfd is selected, still announce it, and change 'not read' to something else ... something like, classic effis is selected, falling back to AI reading". So the classic line stayed, in the owner's words (`Pmdg737PfdSpeech.KeyClassic`), and the unavailable one went.

## WASM-19

- Every PFD row, message, baseline and setter value comes only from a good reading, through ONE gate in `Pmdg737PfdMonitor`: PMDG's Captain IAS and altitude against the simulator's `AIRSPEED INDICATED` and `INDICATED ALTITUDE` in one memory sample of the last 3 s (`Pmdg737PfdCrossCheck.Passes`), a value whose instrument flag is up (SPD, ALT: a message that replaces the instrument in that tape's place) not compared, both at or under a tape's floor (the speed tape's 45 kt) counting as within, and no sampler `corrupt` check. A simulator value not yet delivered never passes. A running reader counts a reading that is not `Pmdg737PfdSpeech.Visible` (displays dark, the Captain's PFD on no screen, the classic look) without the check: PMDG draws no PFD then, and the window says where it is; a candidate still has to pass. Messages are compared only while both readings are visible, and not for 10 s after the displays light up (`LightUpQuietMs`). 2 s without a passing reading says "PFD announcements stopped: values do not match the simulator"; ten corrupt readings in a row stop it until a reload. → [wasm-memory.md](../wasm-memory.md#the-primary-flight-display)

  Why: the PFD has no SDK field of its own to check against (the ND's EFIS knobs, the FMA's MCP), so the check uses what the simulator itself knows, and only while PMDG draws the value, so a failed instrument shows its flag instead of stopping the reader (the spec's Review Focus 1). Ground session 2 measured the tolerances' basis (2026-10-30): settled, PMDG's altitude and the simulator's differed by at most 0.6 ft at three baro settings, the simulator's following PMDG's baro; a baro turn opens up to about 250 ft for about a second because the simulator's altitude updates about once a second, which the 3 s window absorbs; cold and dark, PMDG's values follow the simulator too. The flight (2026-10-30, 713 check lines from the takeoff roll to the approach) measured the IAS: above the tape's floor the two differed by at most 6.9 kt, on the takeoff roll (PMDG 54.2, the simulator 47.3, accelerating), and within about 1 kt otherwise, so `IasToleranceKt` is 21 (3 × 6.9, rounded up); the altitude differed by up to 23 ft in the descent. No stop line was heard in the whole flight. The landing roll is not yet measured. Pinned by `Pmdg737PfdCrossCheckTests`, `Pmdg737PfdMonitorTests.An_instrument_failing_is_spoken_never_stopped` and `An_undrawn_pfd_is_not_checked_against_the_simulator`.

## WASM-20

## WASM-21

- `LayoutFileFormat.Write` gives byte-identical text for the same layouts, on any PC and under any culture. The header comes in one order (`formatVersion`, `module`, `generatorVersion`, `codeHash`, `dataRanges`, `dataHash`, `searches`, `readers`), and the readers in the module's order (`ModuleDescription.Readers`) whatever order the `LayoutFile` lists them in. A layout's properties come in its record's declaration order, which System.Text.Json reads by reflection and which is fixed for one build of the layouts library. A read-only dictionary (the engine display's page values and page rows, the ND's marker labels) is written in key order (text keys ordinally, never by the PC's culture), so two equal layouts whose entries were added in different orders give the same text. Every number goes through `Utf8JsonWriter` or System.Text.Json, never through string formatting, so the PC's culture never reaches it. Indents are two spaces and line ends `\n`, with one after the closing brace; "°" and other non-ASCII text is written as it is (`JavaScriptEncoder.UnsafeRelaxedJsonEscaping`). Nothing depends on when or where the file was written: there is no timestamp and no path, and each layout's source file is saved as "" (`TryRead` returns it empty and the store fills it in for the log). → [wasm-memory.md](../wasm-memory.md#the-layout-file)

  Why: a build always gets the same file name (its code hash and the first 16 characters of its data hash), so a second write of that build must give the same file under that name, and the generator's golden tests compare its output with saved files byte by byte, so a culture or an ordering that leaked into the text would fail them on another PC. The design spec (2026-10-31) asks for it in the same words: the same `.wasm` file always gives a byte-identical layout file. Pinned by `LayoutFileFormatTests`: `Saving_twice_gives_identical_text`, `Saving_under_sv_SE_and_de_DE_gives_the_en_US_text`, `Load_then_save_gives_the_same_text`, `Equal_layouts_give_the_same_text_whatever_order_their_maps_were_built_in` and `The_source_file_is_saved_empty`.

## WASM-26

- For an installed file, `LayoutStore` reads only the files in `<root>\<module id>\` whose names are `<code hash>-*.json` for that file's code hash, sorted ordinal, and uses the first that is current. A file is current when it reads, `LayoutFileFormat.TryRead` accepts it (a known format version, this module, exactly the module's readers, every member present, well-formed hashes), `LayoutFit.Fits` says it fits the installed file (the same code hash, the same bytes in every recorded data range, every recorded search finding the same addresses), and, when the generator is present and answered its version, the file's generator version is not older than the generator's. Any other file counts as missing, and the store logs why it skipped it: it is never loaded in part, and a layout from a file that failed any of these checks never reaches a reader. With no current file and a generator present, the store runs it once and looks again; with no generator, the lookup fails with "no layout for this build and no generator", the file analysis logs it as not recognised, and the readers are unavailable with "PMDG file not recognised" as before, the pilot hearing [WASM-29]'s one line. A generator that times out (and is killed), crashes, exits non-zero or writes nothing that fits makes the readers unavailable for this load only: the store writes and deletes nothing itself, so the next load (a flight reload re-runs a failed analysis) tries again. → [wasm-memory.md](../wasm-memory.md#the-layout-store)

  Why (design spec, 2026-10-31): a damaged or hand-edited file, a file from a format the app does not know, or one written for different code or data would otherwise feed the readers offsets that point at the wrong fields, and the cross-checks would be the only thing between a wrong reading and the pilot. Treating all of them as missing keeps one rule: the app reads memory only by a layout that was derived from exactly the bytes installed. A `.tmp` left by a killed generator is never a candidate: the store reads only `<code hash>-*.json`. Without a generator, as in a release, a version cannot be compared, so any file that fits is current; with a generator whose `--version` answer is not a number, the same holds, and it still runs for a build that has no file. Pinned by `WasmLayoutStoreTests`: `An_unknown_format_version_counts_as_missing`, `A_file_that_does_not_fit_counts_as_missing`, `A_damaged_file_counts_as_missing`, `An_older_generator_version_regenerates`, `Without_a_generator_an_older_version_file_is_used`, `Unknown_generator_version_uses_any_fitting_file`, `A_non_zero_exit_is_unavailable_and_saves_nothing`, `A_timeout_is_unavailable_and_logged` and `Leftover_tmp_files_are_ignored`.

## WASM-30

- `ProcessLayoutGenerator` puts every process it starts, a run or a `--version` ask, into its own Windows job object (`KillOnCloseJob`), right after `Process.Start` and before it reads the output. The job is made with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`JOBOBJECT_EXTENDED_LIMIT_INFORMATION` through `SetInformationJobObject`) and only the app holds its handle, so when that handle closes, as it does when the app exits, crashes or is killed, Windows ends every process still in the job. The shared instance (`ProcessLayoutGenerator.NextToApp`) is kept in a static for the app session and its job is never disposed: a profile switch or the end of a module session leaves a run going, since it finishes by itself in about a second and the file it writes is useful. If Windows refuses (no job made, or a process not assigned: access denied, or a job the app already runs in that forbids nesting), the generator writes one line to debug.log (category `LayoutGenerator`) and runs exactly as before, without the job; a job failure never fails a run or throws out of `AskVersion` or `Run`. `Execute` keeps the job reachable until its wait ends (`GC.KeepAlive`), so an instance its caller dropped mid-run cannot have its job closed by the finalizer and end its own run. The 60 s and 10 s timeouts and the tree kill at a timeout are unchanged. → [wasm-memory.md](../wasm-memory.md#the-layout-store)

  Why (owner, 2026-10-31): "if the app opens and then instantly closed, the .exe file should not hang and stay". Before this, nothing ended the child when the app went away: a normal run ends by itself in about a second, but a hung one would have stayed running (the final review's deferred Minor 8, "a generator can be orphaned"). A process joins the job only once it has started, so a process it started before joining would stay outside; `LayoutGenerator.exe` starts none. Measured (Task 14, 2026-10-31): the real Debug `LayoutGenerator.exe`, started by `ProcessLayoutGenerator` in a throwaway host and suspended so it could not finish, was gone a second after the host was killed with `Stop-Process -Force`; started by a plain `Process.Start`, it was still running. Pinned by `WasmKillOnCloseJobTests` (`Closing_the_job_ends_the_process_in_it`, `A_closed_job_refuses_a_process_without_throwing`) and `WasmProcessLayoutGeneratorTests` (`Closing_the_job_ends_a_running_generator`, `Without_a_job_runs_work_and_the_failure_is_logged_once`, `A_run_the_job_refuses_still_works_and_is_logged_once`).

## WASM-31

- `LayoutStore` reads a module's layout files from two folders: `%APPDATA%\MSFSBlindAssist\layouts\<module id>` (`LayoutStore.DefaultRoot`) and the `layouts\<module id>` folder shipped beside the exe (`LayoutStore.BundledRoot`, `Path.Combine(AppContext.BaseDirectory, "layouts")`; null in a test means no bundled folder). It evaluates every candidate of both, with the same tests as before ([WASM-26]), and uses the current file with the highest generator version; on a tie the `%APPDATA%` file, then the first by ordinal name. A file in the bundled folder that is damaged, unknown or does not fit is skipped with a `layouts: skipped` line, like any other. The store writes to neither folder, and the generator, when present, is still given the `%APPDATA%` root and writes only there. A bundled folder that does not exist has no files and logs nothing.

  Why (owner, 2026-10-31): a release carries the layout files beside the exe, because a release has no generator and would otherwise not recognise any PMDG build. A build that does have the generator must still regenerate past an older bundled file: the bundled file's generator version is lower than the generator's, so it is not current, the generator runs, and its new `%APPDATA%` file wins.
