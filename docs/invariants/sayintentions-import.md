# SayIntentions taxi-route import — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/sayintentions-import.md`, which Claude Code loads when it reads matching code. Background: [sayintentions.md](../sayintentions.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## SI-1

- `assigned_gate` is always an ARRIVAL gate at `flight_destination` — SayIntentions does not assign a departure gate at all (per an SI developer). Never infer the gate's role from where the aircraft is standing: at the origin that announced the arrival stand as "Departure gate J1 at LMML", naming an airport the stand does not belong to. It also means the gate may appear in the destination-resolution chain ONLY behind a check that the airport being routed at IS the destination — the old unconditional fallback would, at the departure airport, have matched whatever local stand shared the name (`A9` and friends recur across airports) and routed there silently. Same gate for the parked-at-the-right-stand comparison. The live EDDF capture cannot settle this either way: it was taken AT the destination, where the two readings coincide. → [sayintentions.md](../sayintentions.md)

## SI-2

- `assigned_gate` is the FULL label, not a stand id — a live EDDF arrival gave "Terminal 3 Gate J1". The stand id is whatever follows the LAST gate/stand keyword; a label carrying no keyword ("A-9", "J1") is used whole. Stripping noise words instead left "TERMINAL3J1", which matches no navdata spot, so the assigned gate could never resolve and destination resolution fell through to the STALE previous-leg `flight_plan_departing_runway` — routing a just-landed aircraft at a runway. → [sayintentions.md](../sayintentions.md)

## SI-3

- A gate candidate resolves in THREE steps — name, then this scenery's online ALIASES, then the published `assigned_gate_lat`/`assigned_gate_lon` — and BOTH fallbacks must be tried INSIDE `TryResolveExternalDestination`'s candidate loop, on the same candidate whose name just failed, never after the loop. On a NON-arrival chain the last candidate is the ARRIVAL RUNWAY, which is the exact failure they exist to stop (a just-landed aircraft routed at the runway it landed on, taxiways perfect, nothing sounding wrong), so a fallback below the loop lets the runway win first and reproduces it. `SelectDestinationType(false)` is made ONCE for the pair — `_destinationSpotMap` holds gate entries only while gate mode is selected, and a runway candidate probed in between repopulates it.

## SI-4

- ALL THREE of those steps see only what the gate list LISTED, so `TryResolveExternalDestination` must neutralise EVERY browsing filter on that list before probing — the gate SEARCH box, the OCCUPIED-stands filter (`_suppressOccupiedFilter`) and the WINGSPAN "show fitting only" filter (`_suppressFitFilter`, via `TaxiAssistForm.ShouldApplyFitFilter`). `PopulateDestinations` drops a filtered-out spot BEFORE its label reaches the combo, `_destinationSpotMap` and `_destinationThresholdMap`, so a hidden stand does not merely fail the NAME step: the alias and the published coordinate have nothing to match against either and all three go blind at once. The wingspan filter is the one that was missed, and it is the strongest case of the three — `ParkingSpot.FitsAircraft` reads a navdata parking RADIUS or a GSX MAX WING SPAN, both scenery-authored and frequently wrong, and the box is ticked BY DEFAULT whenever wingspan data exists, so this was the normal configuration and not an edge case: a SayIntentions clearance to a gate could not seat it, and on a known arrival that is the loud `ComposeUnresolvedArrivalGateMessage` abort for a stand the airport HAS and the aircraft FITS. A controller naming the stand outranks a scenery number saying it will not fit. Both suppressions are LATCHED on a successful seat, never restored — the Calculate-path and show-path gate-source refreshes both repopulate, and a rebuild dropping the seated stand clears the selection and aborts the very import that seated it — and cleared only by the pilot toggling that checkbox themselves or by an airport load; on a FAILED probe both are restored and the list rebuilt under them, because probing leaves no mark. Do NOT "fix" the ticked-but-inert checkbox by unticking it: that silently discards the pilot's own preference (`chkFitFilter` is deliberately exempt from `ResetRouteShapingControls` — it describes the aircraft, not the route) and changes a control with no screen-reader announcement.

## SI-5

- On a KNOWN ARRIVAL — the routed airport IS `flight_destination` AND an assigned gate exists — the candidate list (`BuildSayIntentionsDestinationCandidates`) carries GATE candidates ONLY: clearance gate first, then the assigned gate with its coordinate; NO clearance-runway, departure-runway or arrival-runway candidate. Both runway routes produced the just-landed-aircraft-routed-at-a-runway failure live (KSTL "Gate A2"→12R, KLAX "Gate 52A"→24R, 2026-08-15/19): an arrival clearance naming the landing runway outside a masked span won the old runway-first order, and an unseatable gate (scenery labels the stand differently or lacks it outright) fell through to the arrival runway. An unresolvable known-arrival gate must FAIL LOUDLY (`ComposeUnresolvedArrivalGateMessage`, naming the controller's gate when it differs from the assigned one), never seat a runway — and never re-add a runway fallback to "help" it. Accepted residual: a departure imported while the previous leg's arrival record still stands (turnaround before re-filing, round-robin plan) aborts loudly instead of seating its runway — documented in [sayintentions.md](../sayintentions.md), revisit only against a live capture. `destProbe=[…]` in sayintentions.log records every candidate probe and why it missed (incl. distance from the published coordinate to the nearest stand). → [sayintentions.md](../sayintentions.md)

## SI-6

- The ALIAS step exists because the alias is invisible to `MatchDestinationLabel`, not because it was missing: the combo carries `ParkingSpot.ToString()` (live KDTW: `A 24A - Gate Medium, also A24 (online)`) and `NormalizeParkingName` strips everything from the first SPACED DASH, which every `Describe()` branch puts ahead of the alias (`" - {type}"`). So the scenery's A24A never met SI's, OSM's and the controller's A24, and destination resolution took the arrival runway while the form's own gate search found that stand perfectly. Compare EXACT normalized alias against exact normalized identifier — never `Contains`: a one- or two-character stand id substring-matches almost any combo entry, and "A2" must never seat A24. → [sayintentions.md](../sayintentions.md)

## SI-7

- The coordinate step attaches to the assigned gate ALONE, behind the same `flight_destination` check the name sits behind — an arrival stand's coordinate is as wrong at the departure airport as its name is, and unlike the name it always finds something. Acceptance is the stand's own radius times `NoseStopRadiusFactor` (2.0), and the winner is the NEAREST admissible stand — never a tuned metre constant, and no longer plain containment: the point is the NOSE-STOP, whose offset scales with the parked AIRCRAFT, so live KDTW put it 30.1 m out from a 22.9 m-radius stand (EDDB: 18.9 m out, 21.6 m radius) and containment dropped the right stand into the arrival-runway fallback. The factor is calibrated on TWO real arrivals — re-check it when a third disagrees — and stays a radius multiple because that still self-scales (Gate Extra ~50 m, medium gate ~21.6 m, GA spot metres). "Exactly 1 of 139 EDDB spots contained the point" is NOT the property any more; nearest-among-admissible is (doubled, EDDB's GB 7A qualifies too and loses on distance). `MaxMatchMetres` (150 m) is only a pathological-navdata backstop, the same role `GateAliasResolver`'s 150 m plays. `ParkingSpot.Radius` is FEET on a navdata spot and METRES on a GSX one — convert by `Source` before building a `GatePositionCandidate` or every tolerance is 3.28× too wide and the EDDB runner-up this excludes gets admitted. `(0,0)` is rejected at the reader, because null island is a real coordinate to a distance test. → [sayintentions.md](../sayintentions.md)

## SI-8

- The pilot must HEAR either substitution, and the two say different things: alias → *"SayIntentions assigned Gate A24, which this scenery lists under another name."*, position → *"…which this airport does not have. This is the nearest stand to the assigned position."* An alias route must never claim the airport lacks the stand — it has it, spelled otherwise. Both go immediately after the lead, ahead of every other warning: the lead names only the label that WON, so this is the only thing telling the pilot they are being taxied to a stand the controller did not name. → [sayintentions.md](../sayintentions.md)

## SI-9

- `current_flight.taxi_path` is GEOMETRY (`{"heading":…,"point":{…}}`) — read its COORDINATES only. Never read a name-ish member (`id`/`label`/`name`) from it: the reader deleted in 2026-07 accepted `id`, which is exactly what a geometry array would gain, and ~200 point ids would have become "taxiway names" that silently replaced the clearance-derived route. Names come from the TaxiGraph, never from SI. → [sayintentions.md](../sayintentions.md)

## SI-10

- The imported taxiway sequence comes from SI's published ground track (`taxi_path` snapped to the airport's own graph) ONLY when the parsed clearance runs through that track IN ORDER, gaps allowed — otherwise the CLEARANCE wins and *"SayIntentions ground track differs from the clearance. Using the clearance."* is spoken. ORDER is what makes agreement evidence rather than coincidence: a set-overlap or "mostly agrees" rule takes the stale pre-clearance EGLL track, which shares F and G with the clearance but reaches them across the far side of the airfield. A rejected track must never be silent — a route that is not the one ATC gave must not be discovered out on the taxiway. → [sayintentions.md](../sayintentions.md)

## SI-11

- The taxi-path snap prefers DIRECTION over distance: among edges inside `SnapToleranceMetres` it takes the nearest whose bearing agrees with the point's published `heading` within `MaxHeadingDisagreementDeg` (25°, the same number `MergeOptions.MatchMaxBearingDeg` uses for the same judgement), and falls back to the plain nearest when NONE agrees. That fallback is the safety property and must never be turned into a rejection: a hard gate throws away 10 of KDTW's 124 captured points (8.8 %) that sit on `K`/`Q`/`U9`/`A5` — legs that belong to the route — and a rejected point becomes a null that breaks its run and can drop a real leg below `MinRunPoints`. A near-tie-only rule is the opposite error: safe but useless, because at a junction the crossing pavement is CLOSER, not nearly as close (KDEN `P7` wins on 148 of 154 sampled offsets), so no ambiguity margin contains it. Measured: bearing-preferred nearest changes 0 of LSZH's 40 picks and 0-1 of KDTW's 124 and moves neither sequence. `GeoPoint.HeadingDegrees` is GEOMETRY, so reading it does not breach the rule against reading `taxi_path` members — that names the NAME-ISH ones (`id`/`label`/`name`) and exists so taxiway names never come from SI; null heading must always degrade to the plain nearest. `TheLiveCapturesCarryAHeadingForEveryPoint` stops the capture guards silently falling back. → [sayintentions.md](../sayintentions.md)

## SI-12

- The junction-artifact filter's sandwich must be CONTIGUOUS in the run sequence — the anchor, the filling and the returning anchor neighbours in `runs`, nothing removed between them. Without it stage 3's own removals weld two runs the published track never showed as adjacent: `X, [lost], Y, [lost], X` read as a sandwich and DELETED a taxiway the aircraft really taxied, silently (2 lost points in 10 is a 20 % unsnapped share, under the 25 % that earns a spoken warning). Same rule the run-length stage states one level down, never re-established at the run level. It also keeps the pass self-consistent: `X, Y, Z, X` is deliberately not an excursion, so it must not become one because `Z` was short enough to stub-filter. FOUR shapes still escape it and are left alone ON PURPOSE, because every fix makes the pass delete MORE, which is the direction that costs a CLEARED leg: a split filling (`X, Y, [stub], Y, X`), a nested pair (`Z, X, Y, X, Z`), two spurs (`X, Y, Z, X`), and a leading anchor the trim removed (the spur then becomes leg ONE — pre-existing, uncovered, pinned by `AnExcursionWhoseLeadingAnchorTheTrimRemovedIsNotRecognised`). `MaxExcursionRunPoints` counts SAMPLES not metres (4 points = 3 gaps ≈ 84 m at the median 28 m spacing, not 112 m), and the 1-point bucket — 45.1 %, the biggest — belongs to `MinRunPoints`/`geoDroppedRuns`, NOT to this filter, so `geoExcursions=0` never means "no junction clips". Dropping a filling also merges the two anchors into ONE row, so a clearance with two hold-shorts on one taxiway (KBOS `N, hold short 15R, N`) loses the second to `MapHoldShortsToTaxiways`' forward-only scan — announced, not silent, but it is a runway hold-short. The filter is also SANDWICH-ONLY and must never be widened to reject any track that revisits a taxiway — measured across 17 revisit occurrences in a 56-import log: 14 are sandwiches (one run between the two visits, the junction-clip shape), and all 3 non-sandwiched revisits are legitimate (KBOS revisits E because the CLEARANCE does, "P, E, M, K, E"; KBOS K and KATL H are the stand lead-in as the final leg). A blanket revisit rule rejects 7 of 31 geometry-sourced imports to catch 3 artifacts, and of the 4 it wrongly rejects KMDW loses Q and Y6 — the route to the runway after a partial clearance. KNOWN LIMITATION, deliberately unfixed: the filter is geometric and can drop a CLEARED taxiway that is briefly sandwiched (live CYVR, `JB` between two `6` runs, one import in 56) — the walk then fails and the pilot hears a disagreement about a track that agreed. Protecting a cleared name was implemented and REVERTED: it removes the caution by handing over the geometry route, which at CYVR is `6, JB, 6, …` and walks the pilot off `6` onto `JB` and back at one junction. A spurious turn instruction is worse than a spurious warning, and the artifact may be the ANCHOR (the second `6`) rather than the filling — do not re-fix this from reasoning alone. → [sayintentions.md](../sayintentions.md)

## SI-13

- A TIMESTAMP can NEVER be the trust signal for that track, and the freshness gate built on one was BUILT, DISPROVEN and REMOVED — `flight_details.timestamp` is when SI wrote the FILE, not when it computed the path: three captured pairs carry a BYTE-IDENTICAL `taxi_path` under stamps 68 s, 116 s and 252 s apart, and a file write is always later than a transmission already on the frequency, so the gate passed on every stale path there is while reading, in code and in the log, like a safety gate. Nothing on the wire says when the path was computed. Never rebuild it — not on `timestamp`, not on the file's mtime, and never reason from "the stamp is newer so the path must be"; `TaxiPathStampUtc` is read and logged as diagnostic data only. → [sayintentions.md](../sayintentions.md)

## SI-14

- The agreement walk must run against the COLLAPSED clearance (`CollapseConsecutive`) — and ONLY the comparison collapses; the RAW list is what reaches the form. `ParseClearanceTaxiPlan` deliberately keeps a taxiway repeated across a hold-short (the KBOS "N, hold short 15R, N" pattern) so each stop gets its own row, but the snapper structurally cannot produce that repeat (it drops unsnapped/too-short runs BEFORE collapsing duplicates), so walked raw such a clearance could never agree with its own track — which spoke a disagreement about two descriptions of the same pavement AND switched the geometry path, plus the dropped-leg recovery it exists for, off for every clearance of that shape. Only ADJACENT repeats collapse; a genuine later revisit stays a leg the track must carry twice. → [sayintentions.md](../sayintentions.md)

## SI-15

- The walk needs the `2n + 1` length guard beside it (`TrackIsShortEnoughToDescribe`) — its discriminating power scales with how many legs the clearance has, so against the real 12-leg LSZH pre-clearance plan "via E, C", "via N, E, B" and even a bare "via E" all walked clean through and the stale plan was taken SILENTLY (with auto-start on, guidance began on it). Measured, real agreements run 1.0–1.33 track legs per cleared leg, stale readings 2.5–12. It counts the COLLAPSED clearance (a taxiway named twice is one leg of evidence and must not buy the track extra length), and a track rejected on length is reported as a disagreement, never dropped quietly. → [sayintentions.md](../sayintentions.md)

## SI-16

- The CLEARANCE always owns the destination and the hold-shorts, whichever source wins the taxiway sequence — geometry carries neither. On the geometry path the hold-short anchors therefore cross sources: an anchor naming a taxiway the track lacks maps to -1 and is announced as unsettable, never hung on whatever row is last. → [sayintentions.md](../sayintentions.md)

## SI-17

- What `taxi_path` does with pavement already flown is UNSETTLED — one capture of each behaviour, and never assume either: LSZH shrank 77 → 40 points as the aircraft taxied (the remaining route), while KDTW published 124 points of which 76 (61 %) lay BEHIND the aircraft, the first 1,510 m back (the route as issued). It is empty in the cruise. The old "a late press has a shorter track, so it fails the agreement walk and the clearance wins — intended, not a defect" reasoning rested entirely on the shrink and is DISPROVEN: at KDTW the long track ran through the short clearance, won, and delivered taxiways the aircraft had left. What makes a late press safe is `SayIntentionsTaxiPathSnapper.TrimToPointsAhead`, which snaps only from the published point NEAREST the aircraft onward — guarded by the snapper's own `SnapToleranceMetres` (25 m), because an aircraft that far off the track cannot say what is behind it and the path must then pass through UNTOUCHED (a wrong trim silently deletes cleared legs); an exact tie breaks to the EARLIER index so a route doubling back keeps its second pass; and a trim is never announced — a route starting where the aircraft stands is the expected answer, not a warning (`geoTrimmed` in the log). → [sayintentions.md](../sayintentions.md)

## SI-18

- The Ctrl+Shift+Y chord has ONE definition (`HotkeyManager.SayIntentionsBuildTaxiRouteChordText` + its registration consts) consumed by the registration AND the guide test — never reintroduce an independent spelling in either place. → [sayintentions.md](../sayintentions.md)

## SI-19

- The snapper's connector filter (`MinRunPoints`) is what stops OSM's unnamed-connector names ("Link 5", "Link 6", "Inner") entering the route — and run-lengths must be computed over the RAW per-point sequence, nulls included (a null BREAKS a run, never gets skipped over) and BEFORE consecutive duplicates collapse, or every run is length 1 and the filter has nothing left to measure. → [sayintentions.md](../sayintentions.md)

## SI-20

- The snapper takes an ALREADY-BUILT `TaxiGraph` (`GetNamedEdges()`) and never fetches names itself — the augmenting provider has already filled unnamed navdata segments from OSM, and a second fetch would put a network call on a hotkey. `GetNamedEdges` must stay sorted on a key INTRINSIC to the edge (name + endpoint coordinates), never node id: node ids follow `Build()` processing order and the snapper breaks a nearest-edge tie with a strict `<`, so a navdata re-import could silently flip which taxiway a blind pilot is told. Named-edge coverage is a REAL limit, not a bug (EGLL 91 %, EDDF 87 %, KJFK 77 %, LEPA 63 %, LSZH 0/1840 — LSZH's names exist only via the OSM augmentation): geometry removes the dependency on SI's phrasing, not on names existing at all. → [sayintentions.md](../sayintentions.md)

## SI-21

- On a GEOMETRY route the clearance's unresolved words must NOT be announced as "could not apply", and BOTH leg lists — the route being taken ("Via …") and the legs that could not be applied — are CAPPED at 3 names plus a count: every name in that sequence came from the airport's own graph, so naming a leg the route is not actually missing (the live LEPA "North" over a route that DOES include N) teaches the pilot to distrust the whole readout, and ten unheard graph names in a row is a recital rather than information — the real LSZH pre-clearance track is TWELVE legs, so the "Via" line had exactly the same problem. A CLEARANCE route names every one of both, uncapped: each is a word the controller said. Nothing is lost outright — the form's route-summary box and sayintentions.log carry the whole sequence. → [sayintentions.md](../sayintentions.md)

## SI-22

- The import's own summary must reach the pilot as ONE utterance a tactical callout cannot eat, WARNINGS FIRST. With auto-start on the order is `ApplyExternalRoute` → Calculate → `LoadRoute` (queued router summary) → `StartGuidance` (first-taxiway `AnnounceImmediate`, which DISCARDS the queue) → the form's standstill `AnnounceImmediate` — so a queued import summary was spoken *after* guidance began and was the first thing a callout killed, taking *"could not apply D, E"*, *"could not set hold short of runway 22L"* and the ground-track disagreement with it. It is folded into that same standstill utterance via `TaxiAssistForm.StartImportedRoute(Func<bool,string>)`, which passes whether guidance ACTUALLY started so a failed Calculate is never announced as "Guidance started."; every Calculate abort reachable from an import joins the two through `AnnounceCalculateAbort` rather than stomping one with the other. This is the third time this lesson has been paid for — see the length-advisory and reach-warning comments in `TaxiGuidanceManager.Routing.cs`. The lead names the destination ONLY when it seated, or the first two sentences contradict each other (*"SayIntentions route to Gate A9."* then *"Destination not set."*). → [sayintentions.md](../sayintentions.md)

## SI-23

- A failed destination probe must put back the ROUTE-SHAPING boxes as well as the destination — `TryResolveExternalDestination` promises "probing leaves no mark", but probing a gate candidate switches `cmbDestType`, and `OnDestTypeChanged` unticks `chkIntersection` (which also empties `cmbIntersection` + `_intersectionMap`) and `chkCatIiiHold` on the way out of runway mode; restoring the type re-SHOWS them unticked. A hand-built intersection departure + CAT III hold therefore vanished behind *"SayIntentions route unavailable"* — i.e. "nothing happened" — and the next Calculate lined the pilot up at the full-length threshold holding at the CAT I line. Restore the intersection state DIRECTLY with the `CheckedChanged` handler detached: routing it through the checkbox fires `ShowIntersectionListOrFallback`, which moves focus and can announce "No runway intersections available" — neither belongs to a silent restore. → [sayintentions.md](../sayintentions.md)

## SI-24

- The taxi-route import and `LoadAirportDataAsync` each need their own reentrancy guard. The import runs 5 s of comms history + 1.5 s of position + up to 8 s of taxiway-name prefetch + a graph build, all awaiting on the UI thread, which is long enough for a pilot who heard nothing to press again; and `LoadAirportDataAsync` CLEARS `cmbFirstTaxiway`/`cmbDestination`/the dynamic rows before its awaits and repopulates after, so a second load interleaving there makes `combo.Items.IndexOf` return -1 for every leg — announcing *"No taxiways from the clearance matched this airport. Using shortest path."* for a perfectly good clearance, and starting guidance on it. Airport loads CHAIN (a second load is usually a different airport; dropping it strands the form on the wrong one); a second import is refused out loud, never silently — silence is what made the pilot press twice. `SetAircraftPosition` and the `txtAirport.Leave` handler reach the same load path and are covered by the same chain. → [sayintentions.md](../sayintentions.md)

## SI-25

- The snapper's nearest-edge scan is NOT free and must not be moved onto a per-frame path: measured 20–90 ms (a 111-point capture × EGLL's 5,189 named edges ≈ 576k point-segment evaluations ≈ 40 ms), synchronous on the UI thread. It is acceptable only because it runs ONCE per import, at a standstill, inside an operation that has already spent seconds on HTTP. `SnapToleranceMetres` (25 m) has now been re-measured against navdata-sourced edges as the old comment asked — EGLL median nearest-edge distance 1.53 m, p90 2.31 m, 4/68 unsnapped (the stand lead-in, apron), route reproduced exactly — so it stands unchanged and does not need measuring a third time. → [sayintentions.md](../sayintentions.md)

## SI-26

- An imported route must reset the route-shaping controls first (`ResetRouteShapingControls`) — `OnDestTypeChanged` only clears the runway-only boxes when the destination TYPE changes, so a hand-built intersection departure or CAT III hold survives an import and silently moves the lineup point. `chkFitFilter` stays exempt: it describes the aircraft, not the route. → [sayintentions.md](../sayintentions.md)

## SI-27

- MainForm must never build its own `TaxiGraph` for a SayIntentions route — load the airport through `TaxiAssistForm.LoadAirportForExternalRouteAsync` and resolve against the names it returns; the form owns its destination label formats. → [sayintentions.md](../sayintentions.md)

## SI-28

- `TaxiAssistForm.LoadAirportDataAsync` must DROP `_graph` before its awaits and claim `_currentIcao` only after a graph is built — no failure exit (airport absent / no taxi paths / exception) may leave the previous airport's graph standing. `LoadAirportForExternalRouteAsync` reports success as "the graph knows some taxiway names", so a stale graph defeated the import's `knownTaxiways.Count == 0` guard entirely: an EDDF clearance resolved against LMML's taxiways, the snapper got LMML pavement for EDDF coordinates, guidance auto-started on it, and the method's own early return then matched forever so EDDF could never rebuild. → [sayintentions.md](../sayintentions.md)

## SI-29

- A ground-track route accepted with NO clearance behind it (`ChooseTaxiwaySource` rule 2) must SAY so — "No cleared taxiways to check it against, so this is SayIntentions' own plan, not ATC's." — and must never discard `GetLastTaxiClearanceAsync`'s `Error`. flight.json carries no clearance text, so every import rides a 5 s `getCommsHistory` round-trip; before the pilot requests taxi, `taxi_path` holds SI's OWN plan (a live LSZH capture: 12 legs across the airfield), and taken silently that announced a confident route no controller gave. The clause is ground-track-only (a shortest path is this app's, not SI's) and a clearance that WAS read adds no words. → [sayintentions.md](../sayintentions.md)

## SI-30

- `BuildTaxiRouteFromSayIntentionsAsync` is dispatched as a discarded Task, so EVERY statement must sit inside its top-level try — the DB-provider guard and `ValidateDatabaseSimulatorMatch()` (which reads SimConnect state and can open a modal dialog) once ran ahead of it, and anything they threw was captured into the discarded Task: no announcement, no log line. → [sayintentions.md](../sayintentions.md)

## SI-31

- `current_airport` holds the controlling ARTCC's ident in the cruise (live log: KZLC → KZOA mid-flight, real airport restored on the ground) — the import's airport chain validates every candidate against the navigation database and falls through, and the info window labels a `KZ[A-Z][A-Z]`-shaped UNKNOWN ident "Controlling facility"; never filter on the KZ prefix alone (KZPH and KZZV are real airports), and never let an unvalidated current_airport dead-end the import. → [sayintentions.md](../sayintentions.md)
