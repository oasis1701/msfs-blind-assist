# FlyByWire A380X FCU, EFIS and FMA — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/a380-fcu.md`, which Claude Code loads when it reads matching code. Background: [a380x.md](../a380x.md).
The text is verbatim from CLAUDE.md as of `1f37801a` (A380F-17 from PR #160's as of `642f48c1`); a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## A380F-1

- A380 FCU baro polarity is PUSH=STD/PULL=QNH — the OPPOSITE of the A32NX's PULL=STD/PUSH=QNH; never harmonize the two conventions. → [a380x.md](../a380x.md)

## A380F-3

- **FBW #10855 killed four more A380 controls without either of their names disappearing** (found 2026-09-25, beside the flight directors; pinned by `A380Fbw10855DeadNameTests`, which fails if any of these names comes back into A380 CODE): **SPD/MACH** is `A32NX.FCU_SPD_MACH_TOGGLE_PUSH` (the cockpit button, now handled by the WASM) — never the old RPN over stock `A:AUTOPILOT MANAGED SPEED IN MACH` + `K:AP_MANAGED_SPEED_IN_MACH_ON/OFF`, whose events are now MASKED and re-meant as the FMS's own speed/Mach crossover, so the condition froze and the button switched one way only; the **altitude increment** is `A32NX_FCU_ALT_INCREMENT_1000` (0 = 100 ft, 1 = 1000 ft) set through `A32NX.FCU_ALT_INCREMENT_SET 100/1000`, never `XMLVAR_AUTOPILOT_ALTITUDE_INCREMENT` (no reader); **metric altitude (MTRS)** is PRIM FG discrete word 5 bit 14, decoded from `FMA_FG_ALERTS` into `_metricAlt`, pressed with `A32NX.FCU_METRIC_ALT_TOGGLE_PUSH` only when the pick differs (`A380MetricAltitude`), never `L:A32NX_METRIC_ALT_TOGGLE` (no reader — and because MSFSBA read back its own write, one MSFSBA toggle made the Altitude window take a typed altitude as METRES while the FCU stayed in feet); keep its three flags apart — `_metricAlt` (the last word, kept across every reset, what `MetricAlt` falls back to), `_metricAltKnown` (from THIS context) and `_metricAltBaselined` (the call-out's baseline), the last two cleared ONLY by `OnSimContextReset`, never by `ResetAnnouncementBaselines` (it runs after a reconnect's first batch, so a clear there swallowed the first real MTRS change) — because one flag for all three sent the unit back to FEET on a metric FCU at every reconnect; every MSFSBA MTRS press mutes the PRIM's confirmation as an echo (the combo's screen-reader read, the Altitude window button's accessible name); and compose the FCU altitude CALL-OUT from `_metricAlt`, never `MetricAlt`, whose just-commanded unit turned the panel's next forced re-read into a spoken knob turn; and the baro unit above. The same commit also DELETED `L:A32NX_FCDC_{1,2}_FG_DISCRETE_WORD_4`, where the approach capability lived: LAND 2 / LAND 3 SINGLE / LAND 3 DUAL are now FCDC FG discrete word 1 bits 24/25/26, decoded once by `A380ApproachCapability` for the readout, the in-flight call-out and the hotkey. Earlier sweeps missed it because FBW's own OIT maintenance page still READS the dead name — a stale reader keeps a name "present" in a text search, so a sweep must compare removed WRITERS per commit (pieces of built names included), never ask whether a name still appears anywhere. → [a380x.md](../a380x.md)

## A380F-5

- The A380 ND filter buttons (WPT/VORD/NDB) are ONE mutually-exclusive selection (Off/Waypoints/VOR-DME/NDB), NEVER three independent toggles — the FCU holds a single `pEfisFilter` enum and each light is `efis_filter == <enum>`, so two can never be lit at once. Pressing the ACTIVE button clears to NONE, any other REPLACES; there is no "off" button, so clearing means re-pressing whatever is active (`NdFilterSelection`). CSTR/ARPT/V/V ARE independent (T flip-flops) and stay separate. A briefly-held "independent, live-verified all three lit" claim was wrong and shipped three switches that fought each other. The A380 FCU has no EXPED button at all. → [a380x.md](../a380x.md)

## A380F-8

- **Seven more A380 EFIS-CP / FCU controls are FCU-SHIM OUTPUTS, so the `A32NX_EFIS_`/`A380X_EFIS_`/`A32NX_` direct-L:var catch-alls are DEAD writes for them** — `fbw.wasm`'s `FlyByWireInterface::updateFcu` rewrites each every frame (the `idFcuShim…` family), the combo snaps back, and the pilot gets a silent no-op with nothing announced and nothing logged. `Aircraft/A380EfisCpControls` owns the actuators and MUST stay ahead of both catch-alls: navaid 1/2 per side → `A32NX.FCU_EFIS_{side}_NAVAID_{n}_SET` (absolute; the published `getNavaidMode` values and the `a380_efis_navaid_selection` enum are the SAME — 0 Off / 1 ADF / 2 VOR — so the value goes on the wire unchanged, live-verified all three on a380x 2f139a41), OANS zoom → `A32NX.FCU_EFIS_{side}_RANGE_SET` param 0-4 (`getOansRange`'s 0-4 ARE `a380_efis_range_selection`'s five zoom levels; 5 = "not zoomed" is a readback state and not settable), LS/TRAF → `..._{LS,TRAF}_PUSH`, ND overlay → `..._{WX,TERR}_PUSH`, `A32NX_PUSH_TRUE_REF` → `A32NX.FCU_TRUE_TOGGLE_PUSH`. ⚠️ EVERY control here is now ONE event, which is what lets the caller be a single `SendEvent` with no spacing, no serialization and no async — keep it that way. ONE event is NOT the same as an ABSOLUTE one: the navaid and OANS setters ignore the live value, but LS/TRAF/the ND overlay/`A32NX_PUSH_TRUE_REF` are TOGGLES that must read it, so never drop `Command`'s `current` parameter as vestigial — that drives all four to the opposite of the pilot's pick. That live value must come from `FlyByWireA380Definition.CommandedOrCachedValue`, never a bare `GetCachedVariableValue`: the cache is fed only by the 1 Hz batch and is never written on a UI set, so two combo commits inside one batch period both read the pre-first-commit value — which drops the second toggle pick silently and makes the overlay's CLEAR leg name its button from a stale state, switching the overlay ON instead of clearing it (a press of the non-active button REPLACES). A refused or no-op set must also force-read the key (`RequestVariable(..., forceUpdate: true)`), or the combo sits on a position the aircraft never took: nothing was sent, so the var never changes, so the batch's change filter never re-fires `SimVarUpdated` and nothing snaps the selection back. The navaid used to CYCLE `…_NAVAID_{n}_PUSH` 0-2 times and needed all three, because the FCU samples panel inputs once per frame and a push is a bool, not a counter, so two presses in one frame register as ONE (measured). FBW #10914 (2026-09-01) added the absolute SET and the walk went away with it; a build older than that reaches the navaid selectors not at all. If a future control here can only be stepped, do NOT re-introduce spacing inline — restore the serialized async-local walk from git history (never `Task.Run` — awaits must resume on the UI thread or `SendEvent`'s lazy registration races the unlocked `eventIds` dictionary). ⚠️ The ND OVERLAY **can** be cleared (live-verified all four legs) — do NOT copy the ND filter's `ClearUnsupportedMessage` refusal onto it. ⚠️ This is PANEL-ONLY — no auto-flow or checklist code in this repo writes any of these keys — which is why it went unreported: a dead combo is silent and nothing else read the write back. `L:A32NX_TRK_FPA_MODE_ACTIVE` (the HDG·V/S ↔ TRK·FPA mode, read by the FCU panel combo and the Ctrl+H window) is the same shape but not one of the seven above and not owned by `A380EfisCpControls`: `FlyByWireA380Definition.SetTrkFpaMode` is its own actuator, firing `A32NX.FCU_TRK_FPA_TOGGLE_PUSH` (a toggle) only when the requested mode differs from `CommandedOrCachedValue` — since #10855 the L:var write it replaced does nothing. `tools/a380-fcu-vars.md`'s "no event — direct L:var write" row for it predates #10855 and is wrong. → [a380x.md](../a380x.md)

## A380F-12

- **A380 FCU ALTITUDE managed/selected is DERIVED, never read** — `L:A32NX_FCU_ALT_MANAGED` (and the stock `AUTOPILOT ALTITUDE SLOT INDEX` beside it) are HARDCODED to 0/1 every frame by #10855's `updatePrimFgShim` (`const bool lvlChManaged = false;`), so reading either can only ever say "Selected"; altitude is the ONLY one of the four managed flags stranded (measured live at FL360: `altManaged=0` while `hdgDashes`/`spdDot`/`vsManaged` were all correct), which is why a sweep of "the managed flags" finds nothing. `AltitudeManagedState` transcribes the DELETED FBW FCU's own formula (`AltitudeManager.ts` at `1bbd304c4^`) — never invent a different one. ⚠️ The key `A32NX_FCU_ALT_MANAGED` must NEVER be aliased onto `A32NX_FMA_VERTICAL_MODE` via `.Name`, and must NEVER be `ExcludeFromBatch` — that pairing is what broke it. `ExcludeFromBatch` earns a var a standing `PERIOD.SECOND` subscription bound to its data-def id, and `RequestVariable(key, forceUpdate:true)` re-issues that SAME id with `PERIOD.ONCE`, which REPLACES the recurring request with nothing to re-arm it (the codebase's own cancel idiom, `SafelyClearDataDefinition`, works by re-issuing `PERIOD.NEVER` on the same id). The key sits in the FCU display list, which the panel force-reads on open and on a 1 Hz tick — so opening that panel once froze the derivation and the call-out never fired again that session. The derivation reads `A32NX_FMA_VERTICAL_MODE` under ITS OWN key instead, which is batch-covered and structurally immune: `RequestVariable` early-returns for batch-covered vars BEFORE issuing the `PERIOD.ONCE`. `A32NX_FCU_ALT_MANAGED` survives only as an inert definition carrying the Ctrl+M mute row and the panel row; `ProcessSimVarUpdate` returns true for it so the generic monitor never speaks its dead 0, and nothing reads its value at all. The same trap used to be live on `A32NX_FCU_HDG_MANAGED_DASHES` / `A32NX_FCU_SPD_MANAGED_DOT` / `A32NX_TRK_FPA_MODE_ACTIVE` (`ExcludeFromBatch` AND force-read by Shift+H/S/V) and on every HS787 panel var (the HS787 forces `ExcludeFromBatch` on all of them, so opening a panel froze that panel's vars, and the Alt+E EICAS window and the "IRS aligned" callout with them): since 2026-09 `RequestVariable` never issues a `PERIOD.ONCE` on an own subscription's OWN request id: a `PERIOD.SECOND` one lets the next periodic delivery honour the force flag, so a force-read of it answers within one period, never immediately, while a SIM_FRAME + CHANGED one is read on a separate seed or fresh request id instead (the MD-11 walker bullet) (recorded in [a380x.md](../a380x.md)). The LATERAL mode is a third input because the shim's vertical-mode chain assigns `lateralMode` in its 32/33/34 branches (a copy-paste of the lateral chain above it), so LAND/FLARE/ROLL OUT can NEVER reach the vertical mode. **But the rescue is NOT what keeps the flare quiet** — `AltitudeModeTracker`'s `_vertical == NoVerticalMode` early return sits ABOVE the only production call to `AltitudeManagedState.IsManaged`, so on an autoland the rescue cannot run; it is defence-in-depth, and its test pins a path production does not reach. What prevents the spurious "Selected" is that early return plus PRESERVING the last published `IsManaged` (never recomputing it there — test-pinned), which gives the same answer because reaching LAND means passing through G/S CAPT/TRACK, both managed. Remove the early return believing the rescue covers the flare and the flare WILL announce. The call-out compares against the last value SPOKEN and stays silent while the vertical mode is None — that is what keeps an autoland from announcing "Selected" then "Managed" one frame apart. → [a380x.md](../a380x.md)

## A380F-13

- **The A380 has NO "ALT CST armed" bit — do not go looking for one.** The PRIM FG's `base_prim_armed_modes` bus carries only alt_acq / alt_acq_arm_possible / glide / app_des / clb / des / op_clb / tcas / nav / loc / rwy / land, and FG word 2 bit 12 (the obvious-looking candidate) is `alt_acq_arm_possible`, a PERMISSION flag — always read the concatenate block (`A380PrimComputerFctl.cpp:4240-4259`) before inferring a bit's meaning from its neighbours. The constraint is a QUALIFIER in FG word 3 bit 28 (`alt_cstr_applicable`, with bit 29 `altIsCrzAlt`), combined with the armed-ALT bit exactly as the PFD's own `FMA.tsx` `B2Cell` does — on the A380 the constraint shows as MAGENTA "ALT" with the text unchanged, so colour alone carries it and a blind pilot has no other channel. `ArmedAltitudeMode` owns the rule (constraint outranks cruise, both bits SSM-gated so a failed word degrades to plain "Altitude armed"). **Neither qualifier is an armed state and neither may ever announce alone** — the CRUISE qualifier (bit 29) was measured TRUE at FL360 with `A32NX_FMA_VERTICAL_ARMED` at 0 and nothing armed (⚠️ this used to say bit 28: the raw capture `0x4D804000` was misread by the pre-2026-09-25 decoder, see the discrete-word bullet under Core; it is bits 29 and 20), so `FMA_CRUISE_ALT_MODE` is Continuous but `ExcludeFromMonitorManager` and never announces a state of its own (its `ProcessSimVarUpdate` branch caches the two bits, flushes any held armed-ALT call-out — see the hold below — and returns true). The old `(2, "Altitude constraint")` row in `_vertArmedBits` was REMOVED, not repaired: the shim's `altArmed | (clbArmed << 2) | …` skips bit 1 outright. The A32NX WASM builds its bitmask with the identical expression and its bit 2 was removed too, with its own qualifier read from the FMGC constraint word's SSM — see the A32NX bullet below; `op_clb_armed` has no slot in `FgVerticalArmedFlags` at all and cannot be announced on either airframe. **The armed-ALT qualifier is dispatched AFTER the bitmask that arms it, so the ALT entry's call-out is HELD and released by the DELIVERY of the qualifier's continuous batch — never by a wall clock, and never by the qualifier's own `ProcessSimVarUpdate` branch.** Measured: A380 bitmask at continuous-batch 1 idx 257 vs qualifier at batch 2, GLOBAL idx 488 (batches hold 300, so slot 188 of batch 2 — a separate SimConnect message); A32NX bitmask at batch 1 idx 169 vs the two FMGC constraint words at 172/173 (all under 300, so global and within-batch coincide; 164/167/168 before PR #140's FCU sources sorted in ahead of them — the indices move as variables are added, sharing batch 1 is what matters). The qualifier's own branch runs ONLY when the value CHANGED, so it cannot report an unchanged-but-now-current qualifier; a timer would have to guess the batch-1→batch-2 delivery gap, and each batch is a separate `PERIOD.SECOND` request issued inside the setup loop behind an unconditional `SafelyClearDataDefinition(delayMs: 300)` wait — measured at 405 ms apart in a real session log, with no way to tell from this repo whether `PERIOD.SECOND` keeps that phase, so the original 300 ms backstop could lose the race and clear the pending flag before the qualifier ever arrived. `SimConnectManager.ContinuousBatchDelivered` (raised per batch message, after all its `SimVarUpdated`, whether or not anything moved) + `IAircraftDefinition.DeferredFlushWatchVariable` is the deterministic answer: zero delay on the A32NX (same batch), ≤ one batch period on the A380. The qualifier is CAUSALLY coupled to arming — `A380PrimComputerFg.cpp:1942` builds `alt_cstr_applicable` from `clb_armed || des_armed || clb_active || des_active` one PRIM cycle behind — so the same-sample change is the norm, not an edge case. A definition only learns a value when its own `ProcessSimVarUpdate` branch runs and dispatch is synchronous and inline, so naming ALT inline read the PREVIOUS tick's qualifier — and the call-out is edge-triggered, so the wrong name was permanent ("Altitude armed" for a constrained altitude, which the A380 PFD signals by COLOUR ALONE). Only the ALT entry is held; every other armed mode still announces inline; an ALT that arms and disarms inside the window is dropped, not spoken late. ⚠️ Do NOT re-attempt the disproven fix of reading the qualifier from `GetCachedVariableValue` at announce time (reverted, `2f44736b`): dispatch is synchronous on the UI thread and `VarCache.cs` writes the cache and fires `SimVarUpdated` in the SAME loop iteration, so a var later in the batch is not cached yet and the cache returns exactly what the definition's own cached bool held. ⚠️ On the A32NX the flush re-checks the Ctrl+M mute ITSELF, because that airframe is muted centrally by MainForm wrapping `announcer.Suppressed` around `ProcessSimVarUpdate` and the batch hook runs OUTSIDE that wrap; the A380 checks `A380DisabledMonitorVariablesSet` locally and is unaffected. Both route the decision through the one `ArmedAltitudeMode.ShouldSpeakHeldAlt(pending, muted, currentArmed)`, whose `currentArmed > 0` half is load-bearing: `_prevVertArmed` doubles as a `-1` "no baseline" sentinel and `-1 & 1 == 1`, so a bare bit test would let a hold outliving a re-baseline speak a phantom call-out. A held call-out is dropped unspoken on aircraft swap, reconnect, SimConnect disconnect and app shutdown (`CancelDeferredFlush`). → [a380x.md](../a380x.md)

## A380F-17

- **A380 ND MODE and ND RANGE are FCU-SHIM OUTPUTS, never inputs — a direct L:var write is DEAD.** `fbw.wasm`'s `FlyByWireInterface::updateFcu` decodes the FCU's ARINC `efis_discrete_word_1` and writes `A32NX_EFIS_{L,R}_ND_{MODE,RANGE}` EVERY FRAME (`idFcuShimLeftNdMode->set(getNdMode(...))`), so the def's `A32NX_EFIS_`/`A380X_EFIS_` prefix catch-all — whose comment claimed "EFIS Control Panel controls are ALL direct L:var writes on the A380X (no events)" — was overwritten within one frame and the knob never moved. That claim is now CORRECTED — and #225 went further: it does NOT hold for the navaid/OANS-range/LS/TRAF/overlay keys either (see the next bullet), only for the VV/CSTR/ARPT option buttons and the baro-unit selector. Live-measured 2026-09-03: wrote 3 to `A32NX_EFIS_L_ND_MODE` through the calc path, read back 2 immediately. Cost: both panel combos inert, and the First Officer's `CP_EFISMODE`/`CP_EFISRANGE`/`AP_EFISMODE` reverted and spoke *"Unable to complete: EFIS mode: ARC"*. The knobs are `ASOBO_GT_Knob_Infinite` firing `A32NX.FCU_EFIS_#SIDE#_#TYPE#_{INC,DEC}` (efis-cp.xml) and the FCU also takes the ABSOLUTE `A32NX.FCU_EFIS_{L,R}_{MODE,RANGE}_SET`, which is what FBW's own in-flight init uses (`sendEvent(A32NX_FCU_EFIS_L_MODE_SET, 3)`); `A380FcuComputer.cpp:2184` assigns the event parameter straight into `pMode`/`pRange`, so the SET parameter IS the Simulink enum. Live-verified: `RANGE_SET` param 6 moved the published range 1 → 2 where the L:var write could not move it at all. ⚠️ **MODE and RANGE do NOT share a convention and this is the trap**: for MODE the SET enum and the published enum are the SAME (`a380_efis_mode_selection` = `getNdMode` = 0 Rose ILS / 1 Rose VOR / 2 Rose Nav / 3 ARC / 4 Plan), but for RANGE they are NOT — `a380_efis_range_selection` begins with FIVE OANS zoom levels (0..4 = 0.2/0.5/1/2/5 NM) and puts RANGE_10..RANGE_640 at 5..11, while `getNdRange` collapses every zoom level to a single 0 and publishes 1..7 for 10..640.
