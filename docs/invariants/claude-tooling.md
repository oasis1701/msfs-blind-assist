# Claude Code tooling — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/claude-tooling.md`, which Claude Code loads when it reads matching code. Background: [development.md](../development.md), "Claude Code hooks".

## CCT-1

- `.claude/hooks/rules-hook.ps1` runs inside every Claude Code session in this repository, on every contributor's machine (it is registered in the committed `.claude/settings.json`), so a bug in it must never stop work. Every hook mode fails open. The script body sits in one try/catch that exits 0; a mode that cannot parse its input, find a checkout root (a folder holding both `.claude\rules` and a `.git` entry) or read a rule file adds nothing and refuses nothing; and `shell-guard` refuses a command only when it has positively matched one of the command's write targets to a file some rule file covers. An unterminated quote, a target with an unexpanded variable (`$HOME`, `%TEMP%`) and a write made by a script (Python, `dotnet`) are all allowed: the guard is a net, and CORE-16's instruction still covers what it cannot see. `MSFSBA_RULES_HOOK=off`, set before Claude Code starts, silences every hook mode on that machine. Added 2026-10-08 with the hook.

## CCT-2

- The hook decides which rule files load for a path with its own copy of the guard test's matching. `Convert-GlobToRegex` mirrors `ClaudeContextBudgetTests.GlobRegex`: `*` stays within one path segment, `**/` spans any number of segments, a trailing `**` covers everything below, `?` is one character, everything else is escaped, and the pattern is anchored and case-sensitive. `Split-FrontMatter` mirrors `SplitFrontMatter`: front matter only when the file starts with `---` and a line feed, and `paths:` items as `- "<glob>"` lines. If the two drift, the hook adds rules the guard never budgeted, or misses rules the guard counts as loading. `ClaudeRulesHookTests.For_machine_output_matches_the_guard_matcher_for_every_repo_file` runs the hook's `for -Machine -Stdin` over every file in the repository and compares the result with the guard's matcher; change both together, never one. Claude Code's own matcher is a third implementation: the guard assumes it behaves the same, and the live checks in docs/development.md confirm that for the patterns this repository uses.

## CCT-3

- A change to `.claude/settings.json` can reach a session that is already running (on 2026-10-08 the session that created the file started running its hooks at once), so only a fresh session is a clean test of what loads. A filter can also fail silently. Measured on 2026-10-08 with Claude Code 2.1.252 in headless sessions: `Read(//**/.claude/worktrees/agent-*/**)` matched a worktree subagent's read and nothing in the main conversation, while the relative form `Read(**/.claude/worktrees/agent-*/**)` matched nothing; neither `Edit(//**/...)` nor `Write(//**/...)` matched a Write, so the read mode runs unfiltered on Write and NotebookEdit and exits at once outside agent worktrees; `Bash(cat >*)` and `Bash(echo *>*)` never matched, because redirects are stripped before matching, so the shell guard also starts on a plain `cat` or `echo` (about 0.2 s) and allows it. A filter naming more than the command runs on every command holding `$VAR`, `$()` or backticks, as the Claude Code docs say: the first registration, one handler each for `Bash(git diff*)`, `Bash(git -C * diff*)`, `Bash(git show*)`, `Bash(git -C * show*)` and `Bash(gh pr diff*)`, ran all five, in parallel, on a `git -C . show --name-only $(...)` command and added the same rule files five times. The diff mode is therefore registered under `Bash(git *)` and `Bash(gh *)`, which run only when a git or gh command is really there, and decides itself whether the command is a diff; and the step that checks and records what was added runs under a per-session mutex, so handlers running in parallel add each rule file once. `ClaudeRulesHookTests.Settings_register_the_pinned_hooks` pins the list so that a filter change is deliberate: run the live checks in docs/development.md in a fresh session, then update the pinned list.

## CCT-4

- `ClaudeContextBudgetTests`' limits (CLAUDE.md at 25,000 characters and 200 lines, a rule line at 400, a rule file at 12,000, and any one file's rules at 30,000) were set by the lean-CLAUDE.md design (#265, `docs/design/2026-09-30-lean-claude-md-design.md`) for adherence; they are not Claude Code's, which loads a CLAUDE.md of up to 4 MiB in full. When one bites, take the remedies its failure message lists, in order: shorten lines; mirror the few rules a file needs instead of globbing a whole area onto it; split a large area file; retire rules whose code is gone. Raising a cap is the owner's decision, never a change made to get a PR green.

## CCT-5

- Claude Code shows the model at most about 10,000 characters of a hook's added context. Anything longer is saved to a file under the session's `tool-results` folder, and the model sees only "Output too large … Full output saved to: <path>" and a 2 KB preview. Measured on 2026-10-08: 7,700 and 9,476 characters arrived in full, while 10,025 characters and more were saved to a file. In the live checks, a worktree subagent that read `TaxiGraph.cs` (24,216 characters of rules) saw only the preview, and the Plan agent's CLAUDE.md (17,000+ characters) was saved to a file; the first version of the hook, which added everything, recorded those checks as passes because it judged what the hook printed, not what the model received. So `Format-RuleContext` keeps every output within `$ContextBudget`, 9,000 characters. The output gives the header; the names of all matching rule files; then as many whole rule files as fit, in name order, passing over one that does not fit; then a line naming the rest by absolute path, telling Claude to Read them before changing or judging the file. Only rule files shown in full are remembered, so the rest are named again on the next matching read or diff. The Plan agent gets CLAUDE.md's "Rules for any file" and "Before changing behaviour" sections and the path to Read for the rest. `ClaudeRulesHookTests.Read_keeps_its_context_within_what_Claude_Code_shows_in_full`, `Diff_keeps_its_context_within_what_Claude_Code_shows_in_full` and `Plan_agent_starts_with_the_rules_for_any_file_and_is_told_to_read_CLAUDE_md` pin the budget on the heaviest real cases. To judge a live check, ask the model to quote something near the end of what the hook added, never the first lines, which a preview also contains.
