# Claude Code tooling — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/claude-tooling.md`, which Claude Code loads when it reads matching code. Background: [development.md](../development.md), "Claude Code hooks".

## CCT-1

- `.claude/hooks/rules-hook.ps1` runs inside every Claude Code session in this repository, on every contributor's machine (it is registered in the committed `.claude/settings.json`), so a bug in it must never stop work. Every hook mode fails open. The script body sits in one try/catch that exits 0; a mode that cannot parse its input, find a checkout root (a folder holding both `.claude\rules` and a `.git` entry) or read a rule file adds nothing and refuses nothing; and `shell-guard` refuses a command only when it has positively matched one of the command's write targets to a file some rule file covers. An unterminated quote, a target with an unexpanded variable (`$HOME`, `%TEMP%`) and a write made by a script the guard cannot resolve (a Python path built at run time, `dotnet`, Node) are all allowed: the guard is a net, and CORE-16's instruction still covers what it cannot see. `MSFSBA_RULES_HOOK=off`, set before Claude Code starts, silences every hook mode on that machine. Added 2026-10-08 with the hook. Changed 2026-10-09: Python writes resolved from literals are refused (CCT-7).

## CCT-2

- The hook decides which rule files load for a path with its own copy of the guard test's matching. `Convert-GlobToRegex` mirrors `ClaudeContextBudgetTests.GlobRegex`: `*` stays within one path segment, `**/` spans any number of segments, a trailing `**` covers everything below, `?` is one character, everything else is escaped, and the pattern is anchored and case-sensitive. `Split-FrontMatter` mirrors `SplitFrontMatter`: front matter only when the file starts with `---` and a line feed, and `paths:` items as `- "<glob>"` lines. If the two drift, the hook adds rules the guard never budgeted, or misses rules the guard counts as loading. `ClaudeRulesHookTests.For_machine_output_matches_the_guard_matcher_for_every_repo_file` runs the hook's `for -Machine -Stdin` over every file in the repository and compares the result with the guard's matcher; change both together, never one. Claude Code's own matcher is a third implementation: the guard assumes it behaves the same, and the live checks in docs/development.md confirm that for the patterns this repository uses.

## CCT-3

- A change to `.claude/settings.json` can reach a session that is already running (on 2026-10-08 the session that created the file started running its hooks at once), so only a fresh session is a clean test of what loads. A filter can also fail silently. Measured on 2026-10-08 with Claude Code 2.1.252 in headless sessions: `Read(//**/.claude/worktrees/agent-*/**)` matched a worktree subagent's read and nothing in the main conversation, while the relative form `Read(**/.claude/worktrees/agent-*/**)` matched nothing; neither `Edit(//**/...)` nor `Write(//**/...)` matched a Write, so the read mode runs unfiltered on Write and NotebookEdit and exits at once outside agent worktrees; `Bash(cat >*)` and `Bash(echo *>*)` never matched, because redirects are stripped before matching, so the shell guard also starts on a plain `cat` or `echo` (about 0.2 s) and allows it. A filter naming more than the command runs on every command holding `$VAR`, `$()` or backticks, as the Claude Code docs say: the first registration, one handler each for `Bash(git diff*)`, `Bash(git -C * diff*)`, `Bash(git show*)`, `Bash(git -C * show*)` and `Bash(gh pr diff*)`, ran all five, in parallel, on a `git -C . show --name-only $(...)` command and added the same rule files five times. The diff mode is therefore registered under `Bash(git *)` and `Bash(gh *)`, which run only when a git or gh command is really there, and decides itself whether the command is a diff; and the step that checks and records what was added runs under a per-session mutex, so handlers running in parallel add each rule file once. `ClaudeRulesHookTests.Settings_register_the_pinned_hooks` pins the list so that a filter change is deliberate: run the live checks in docs/development.md in a fresh session, then update the pinned list.

## CCT-4

- `ClaudeContextBudgetTests`' limits (CLAUDE.md at 25,000 characters and 200 lines, a rule line at 400, a rule file at 12,000, and any one file's rules at 30,000) were set by the lean-CLAUDE.md design (#265, `docs/design/2026-09-30-lean-claude-md-design.md`) for adherence; they are not Claude Code's, which loads a CLAUDE.md of up to 4 MiB in full. When one bites, take the remedies its failure message lists, in order: shorten lines; mirror the few rules a file needs instead of globbing a whole area onto it; split a large area file; retire rules whose code is gone. Raising a cap is the owner's decision, never a change made to get a PR green.

## CCT-5

- Claude Code shows the model at most about 10,000 characters of a hook's added context. Anything longer is saved to a file under the session's `tool-results` folder, and the model sees only "Output too large … Full output saved to: <path>" and a 2 KB preview. Measured on 2026-10-08: 7,700 and 9,476 characters arrived in full, while 10,025 characters and more were saved to a file. In the live checks, a worktree subagent that read `TaxiGraph.cs` (24,216 characters of rules) saw only the preview, and the Plan agent's CLAUDE.md (17,000+ characters) was saved to a file; the first version of the hook, which added everything, recorded those checks as passes because it judged what the hook printed, not what the model received. So `Format-RuleContext` keeps every output within `$ContextBudget`, 9,000 characters. The output gives the header; the names of all matching rule files; then as many whole rule files as fit, in name order, passing over one that does not fit; then a line naming the rest by absolute path, telling Claude to Read them before changing or judging the file. Rule files shown in full and rule files named are both remembered, so each arrives once per session or subagent, and again after compaction. The Plan agent gets CLAUDE.md's "Rules for any file" and "Before changing behaviour" sections and the path to Read for the rest. `ClaudeRulesHookTests.Read_keeps_its_context_within_what_Claude_Code_shows_in_full`, `Diff_keeps_its_context_within_what_Claude_Code_shows_in_full` and `Plan_agent_starts_with_the_rules_for_any_file_and_is_told_to_read_CLAUDE_md` pin the budget on the heaviest real cases. To judge a live check, ask the model to quote something near the end of what the hook added, never the first lines, which a preview also contains. Changed 2026-10-09: named files were repeated on every diff (7,300 to 8,600 characters a time in a long review).

## CCT-6

- `subagent-start` warns a subagent that its rules will not load only when its `cwd` is in a `.claude/worktrees/<name>` folder that is not an `agent-*` one and is not the session's own. Claude Code does load the rules of the session's own folder, so a warning there is false. The hook tells the two apart by the folder Claude Code files the session's transcripts under: the hook input's `transcript_path` lies in `~/.claude/projects/<key>/…`, and `<key>` is the session's folder with every character outside `A-Za-z0-9` replaced by `-` (`C--Claude-msfs-blind-assist--claude-worktrees-review-281-929a09` for `C:\Claude\msfs-blind-assist\.claude\worktrees\review-281-929a09`). A worktree whose own encoded path is that key is the session's own and gets nothing; one whose path differs is someone else's and gets the warning. `CLAUDE_PROJECT_DIR` cannot make this call. Measured 2026-10-09: in a desktop-app session running in a worktree it is the MAIN checkout, so every subagent of the audit session that day was told its rules would not load, while Claude Code loaded them; run by hand, the mode warned with that value and stayed silent with the worktree's own path. With no `transcript_path` (or none under `.claude/projects`) there is no verdict and the hook warns nothing: a false alarm in every subagent costs more than a missed warning for a hypothetical rename of Claude Code's folder, and the hook fails open (CCT-1). The cost of the choice: if Claude Code renames or shortens that folder, keys stop matching and every subagent in such a worktree gets the warning, noisy rather than silent. A session started in the main checkout that moves into a worktree keeps the main checkout's key, so its subagents get the warning; whether rules load natively there is unmeasured. The built-in Plan agent's CLAUDE.md comes from the checkout its `cwd` lies in; `CLAUDE_PROJECT_DIR` is only the fallback when that finds none. The same value means a desktop-app session in a worktree also runs the main checkout's copy of `rules-hook.ps1` (the path in `settings.json` is `${CLAUDE_PROJECT_DIR}/.claude/hooks/rules-hook.ps1`), so a change to the script reaches such a session only through the main checkout: try one by running the worktree's script by hand, or in a `claude -p` started in the worktree (docs/development.md). `ClaudeRulesHookTests` pins the key match, the mismatch, the missing `transcript_path`, the `agent-*` exemption and the Plan agent's source. Added 2026-10-09.

## CCT-7

- The shell guard also reads the Python a command runs and refuses it when it writes a covered file, but only when it can prove that from literals. It starts on `python`, `python3` and `py` (Bash and PowerShell) and takes the code from `-c`, a heredoc, a bash here-string (`<<<`), a `<` stdin file, a script file on disk (up to 1 MB), or a script written earlier in the same command (`cat > s.py <<'EOF' … EOF && python s.py`). Measured 2026-10-09 in this repository's local transcripts: 376 Python commands wrote somewhere while naming an app path, and 242 of them were one shape: `python - <<'PY'`, then `p = "MSFSBlindAssist/…"`, then `io.open(p, 'w', …)`. Before this rule none was caught, and a live `python -c "open('<covered>','w')…"` wrote the file. `.claude/hooks/python-writes.ps1` (`Get-PythonWriteTargets`) returns the paths a script writes. A write sink is `open(...)`, `io.open`, `codecs.open` or `RECV.open(...)` with a literal mode holding `w`, `a`, `x` or `+` (no mode, or `r`/`rb`, is a read), `RECV.write_text(` or `RECV.write_bytes(`, and the destination of `shutil.copy`, `copy2`, `copyfile`, `move`, `os.replace` and `os.rename`. The code is masked first: comments are removed and every string becomes a token, so a quote, a `#` or an `open(` inside a string or a docstring cannot derail the scan. A target resolves from a literal, `Path(...)` and its Pure and Windows variants, `os.path.join(...)` of parts that each resolve to one value, or a name, through its NEAREST earlier binding: a list literal binds each element, `for p in [...]:` or over a name bound to a list takes every item, a binding inside a `def` or `class` ends with it, and an assignment the guard does not follow (augmented, annotated, chained or tuple, a walrus, a comprehension variable, `as`, `global`, a parameter) leaves the name unresolved. Nearest, not any, because a script that reads a covered file through `p` and then reuses `p` for a scratch file must run, and refusing it for the earlier value would be a false refusal that sends a contributor round the guard. Each resolved target is placed against the command's folder and checked against the rule files' globs like any other write (CCT-1: refuse only what is positively matched). Left allowed, so CORE-16's instruction still covers it: a path built at run time (`os.walk`, a glob, an f-string, `Path(...) / 'x'`, string concatenation), a script that only reads covered files, a module (`python -m`), code piped into Python (`cat <<EOF | python -`), and an interpreter named anything but exactly `python`, `python3` or `py` (`python3.12`, `python.exe`, a full path). Known, contrived false refusals remain: a class attribute that shadows a module-level name of the same name inside the class's methods, and a bracket continuation line at column 0 inside a `def` body (it ends the body early). The analysis has a 3-second deadline and allows whatever is left unanalysed past it. `rules-hook.ps1` loads `python-writes.ps1` inside its own try/catch, so a missing or broken file costs only the Python analysis. Added 2026-10-09.
