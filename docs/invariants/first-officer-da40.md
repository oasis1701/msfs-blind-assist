# First Officer rules: COWS Diamond DA40 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/first-officer-da40.md`. Background: [first-officer.md](../first-officer.md), "COWS Diamond DA40", and [da40.md](../da40.md).

## FOD-1

Added 2026-10-20 (the DA40 First Officer). `DA40FoActionExecutor` writes every switch and lever through `CowsDA40Definition.HandleUIVariableSet`, the same method the panels call: the toggle-only switches written as a compare-then-toggle in RPN (the masters, the exterior lights, the alternate static, the fuel pump), the held buttons (the ECU test held until the model reports Complete, DA40-13; the standby horizon cage), the interlocks (the XLS's split master, DA40F-3) and the refusals (the ECU button's two functions, DA40E-7). So the First Officer can never write a control differently from the panel. A key the definition does not claim is refused (the step is skipped, "Skipping: …"), never written as an L:var: on this airframe the obvious variable is usually a read-only mirror (`STATE_*`, `STARTER_SWITCH`, `THROTTLE_LEVER`, DA40-1), and a write to it reads back as success and drives nothing, the FlyByWire First Officers' dead-write lesson (FOA-4). The pseudo-keys (`CrankKey`, `PrimeKey`, `EcuTestKey`, `CloseDoorsKey`, `StandbyBaroKey`) are composites of definition writes; only `TransponderKey` writes outside it, to the stock `TRANSPONDER STATE:1` the G1000 reads, because the transponder mode has no panel control (it lives on the PFD's softkeys, DA40-22).

Pinned by `DA40FoStructureTests.Every_written_key_is_claimed_by_the_definition` (a source scan: running a handler needs the SimConnect SDK, which the test run lacks) and `Every_write_is_a_pseudo_key_or_a_variable_of_this_airframe`. Not unit-tested: that each write lands in the sim (CORE-5).

## FOD-2

Added 2026-10-20. The First Officer's flow narrates each step ("Strobe: on"); the definition's own confirmation of the same write ("Cranking", "Trim centred", "Caging standby horizon") would say it a second time, and so would the background change the write causes ("Strobe Lights: On"), which MainForm speaks for every announced DA40 switch (DA40-9). So `Apply` wraps the write in `ScreenReaderAnnouncer.OwnerMute` (which, unlike `Suppressed`, also silences `AnnounceImmediate`, the DA40 handlers' call) and first marks the key in MainForm's echo gate through `CowsDA40Definition.UiEchoMark` (MainForm's `SuppressUiEcho`, handed over where the DA40's monitors are attached, both in `MainForm_Load` and `SwitchAircraft`, DA40S-7), exactly as a panel write is marked. The exceptions are `DA40FoActionExecutor.SpeakingKeys`: the ECU test (its press says what condition is not met, which no step label can), the propeller cycle and Set Best Mixture (their refusals, "Engine not running"), the flaps (an overspeed selection's error) and the standby altimeter (a numeric setting's confirmation, CORE-7). Speech a write's handler starts later (the ECU test's result, the best-mixture read-back, the propeller cycle's drop) is the aircraft's, outside the mute, and speaks.

`OwnerMute` is restored to its previous value after each write: the DA40's load settle (DA40-14) owns it too, and both run on the UI thread.

## FOD-3

Added 2026-10-20. `CowsDA40Definition.HandleDoorSet` fires `TOGGLE_AIRCRAFT_EXIT` unconditionally, because the panel's combo reaches it only when the pilot picked the other state (DA40F-4). A First Officer write of "closed" to a door that is already closed, or whose position was never read, would therefore OPEN it. `DA40FoActionExecutor.CloseDoors` reads both doors (`DoorKeys`, the canopy and the rear door, the checklist's "Doors: Closed and latched") from the cache, refuses the step when either is unread, and writes only a door that reads open. No flow step names a door key (`Doors_are_closed_only_through_the_guarded_pseudo_key`).

## FOD-4

Added 2026-10-20. The DA40's read-back checklists are the aircraft's own COWS pages, read from the installed package when the First Officer window builds its groups (`NativeChecklistReader.LoadPages`, keyed by the SimObject folder, which is the aircraft code; DA40S-9), in COWS's words and order, block headings and clues included: "Subject: Expectation. Clue". Nothing is transcribed, so a COWS update reaches the window with the aircraft, and the window keeps the reference pages the old Shift+C checklist window showed (Weights/Speeds, Tips and help) now that the First Officer replaced it (PR #160).

A page title maps to a group by its normalized words (`DA40FoReadback.GroupFor`: "Before take-off" and "Before Take off" are one page). A line the First Officer delivers is matched to a fixed id in `DA40FoReadback.Links` by its page, its block (the XLS's three start procedures repeat the same words) and its normalized subject and expectation; it auto-detects where the aircraft says it is done, and its flow step links it. Every other line is a Captain line, which the pilot ticks; a note and a block heading are Informational. A COWS edit that renames a line therefore only loses that line's link (it becomes a Captain line), never produces a wrong tick. A page the table does not know keeps its text as an Informational group (`DA40_PAGE_<title>`), so nothing COWS writes is lost. The reference pages are Informational (`FoDepartureGroups.Reference`), never ticked or latched. With no package found the action groups stand alone.

Pinned by `DA40FoReadbackTests`, against a sample document and, when the COWS package is installed, against both real files: every page is a known group, every line a flow links is on its page, and every checkpoint is kept.

## FOD-5

Added 2026-10-20. `DA40FoPhase` builds each phase once into both its flow and its action group: a write step is its own action line (the tick fires the same write, the auto-detect is the step's own "Already set" condition), a Captain step is a Captain line, a wait or read-only check has no action line and completes the read-back lines it confirms (`cl`). FO-7 is then structural: no action line without a step behind it. The guards and dependencies (`LeaveAlone`, `Requires`, `StopOnFailure`) are modifiers on the step just added; `LeaveAlone` applies to its line too (FO-25's checklist ticks).

Pinned by `DA40FoStructureTests`: every line a flow latches has a step (`FlowChecklistLinkAudit.UndeliveredLines` empty on both airframes), every link names a line its flow latches, every action line is a step of its own flow, ids are unique, dependencies name earlier steps.

## FOD-6

Added 2026-10-20. The owner's standing rules for the DA40 (report, don't decide; never baby the pilot) and FO-2. The First Officer sets switches, runs the composite procedures the COWS pages spell out (the flap travel test, the ECU voter swap, the ECU test, the magneto check, the propeller cycle, the XLS priming and start) and checks what it can read. It moves the power lever or throttle only to the positions the XLS start gives (the priming mark and the starting position, which COWS's tips say to repeat exactly, and the flooded start's half throttle), never for power. It never sets a transponder code, an altimeter setting (it sets the standby to match the G1000's, which the Captain set), a frequency, the autopilot or the flight plan. A lever the page asks to be checked ("Power lever: Idle", "Throttle: 2000RPM") is a Captain item, "Already set" when the lever is there, followed by a read-only check that waits for the pilot (`PilotLeverWaitSeconds`) and links the read-back line. Pinned by `The_power_lever_moves_only_for_the_XLS_start` and `No_flow_sets_a_code_a_pressure_or_a_frequency`.

## FOD-7

Added 2026-10-20. The start key is a two-position hold: COWS's NG page says "Hold starter till 500RPM", the XLS's "Max 10s". `CrankKey` presses the key through the definition (the NG's `DA40_START_STARTER_ENGAGE`, the XLS's `DA40_MAG_KEY` START, both `L:STARTER_SPAD:1`, DA40E-12 and DA40X-1), polls the engine's RPM (`DA40FoStateEvaluator.RpmKey`) every 200 ms, and releases at `StarterReleaseRpm` or `MaxCrankSeconds`, whatever happened. The release is recorded in `HeldPresses`, so the flow's Stop, a disconnect and the window's close all release the key at once. On the XLS, "When engine fires: Mixture: Full rich" happens in the same composite, before the release, because an engine that fires on its prime with the mixture at cut-off dies again in a second. A crank that never reached 500 RPM fails its step, whose policy STOPS the flow. `PrimeKey` holds the XLS mixture full rich for its seconds and always ends at cut-off, also on Stop and close. Not unit-tested: the timing in the sim (CORE-5).
