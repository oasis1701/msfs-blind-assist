## A320-5

- The A32NX MCDU is read and driven over the COHERENT DEBUGGER (`CoherentA32nxMcduClient` on the `A32NX_MCDU` view, agent `coherent-a32nx-mcdu-agent.js` rebuilding `sendUpdate()`'s relay payload from `legacyFms`'s own fields, keys via the instrument's H-event publisher), with SimBridge's relay as the FALLBACK and the only printer source — `FlyByWireMCDUService` is a facade over both (injected transports, tested over fakes) and `FbwMcduTransportArbiter` picks the live one (Coherent whenever up; the other transport's frames are dropped). ONE parser (`FbwMcduUpdate`) decodes both; `tools/a32nx-mcdu-agent-test` pins the agent against a HAND TRANSCRIPTION of `sendUpdate()` on the fields the decoder reads — it catches the agent drifting from the transcription, not FBW changing the payload, which must be re-transcribed by hand; `read()` answers NOT-READY when `_labels`/`_lines`/`scratchpadDisplay` are missing, never a confident blank screen (that keeps Coherent live over a working SimBridge). On a transport switch the arbiter asks the newcomer for a FRESH frame (`RequestFreshFrom`) and NEVER replays a remembered one — a hung SimBridge keeps its socket open while its last frame grows hours old, and FBW sends SimBridge a blank screen when it detaches. "Readable" (Coherent live, window "Connected") is owned by `CoherentLinkState` alone: one lock, events tagged with their socket's generation, every teardown reported to it (the run loop's and `EnsureConnected`'s through `DropSocket`; `Stop` calls `_link.Stop()`; a cancel after connecting and the end of the receive loop report `OnSocketClosed` for their own socket's generation) — never a flag set from two threads. Coherent GT allows ONE inspector socket per VIEW (the A380 holds E/WD, MFD and flyPad sockets concurrently — the old "no persistent A32NX socket" policy is retired, 2026-09-25), so the client CLAIMS its view from Start to Stop once its agent has loaded (`CoherentViewOwnership`, reconnect gaps included): `CoherentEvalClient` refuses a claimed view, the client does not connect over a one-shot still in flight (the one-shot wakes it as it ends), and once the MCDU service exists the D/Shift+D flight-info script ALWAYS rides `EvalOnMcduViewAsync` ("not ready" while it reconnects; a client that could not load its agent claims nothing and sends it as a one-shot) — never re-add a "does it hold a socket right now?" check at a call site, which let a one-shot race every reconnect. The client reads the screen while the window is CLOSED too (1 s; 250 ms open; showing it wakes the loop, `WakeableDelay`, and asks a live SimBridge for the current screen), and `FbwMcduReadBack` decides what is said: a closed window speaks FMS scratchpad messages only (DEST EFOB BELOW MIN) — never a page title or "Scratchpad cleared"; a change is spoken once it has shown for 400 ms — the tick re-samples the LAST frame, so a tick count is a duration, never a count of reads, and with the window open (read every 250 ms) a value seen in a single Coherent read is not spoken; each typed key holds the read-back 600 ms, from before it is sent and again once delivered. Keys go over Coherent whenever it holds the view (not by the arbiter's lagging `Live`); a certain miss is resent over SimBridge, an ambiguous one never; the first Coherent key after a relayed one waits `RelaySettleMs` — FBW's keypad applies each key 150-200 ms after it arrives and keeps order only at ≥ 50 ms spacing, which is also why the typing loop's 50 ms is load-bearing. The press script writes the cockpit key's `L:A32NX_MCDU_PUSH_ANIM_1_<model name>` (what FBW's relay handler sets on a press; FBW's model plays the key's push animation and its `mcdubuttons` click from it — traced in source, not yet heard in the sim) as a TOP-LEVEL evaluate statement after a delivered press (Coherent drops a SetSimVarValue made inside a stored agent function); it is pinned by a golden fixture the node suite executes. Neither transport can separate Captain and FO: `panel.cfg` declares ONE mcdu.html gauge, so one instrument and one view draw both screens — never add a side selector. → [a32nx.md](../a32nx.md)

## A320-32

- Coherent GT allows ONE inspector socket per VIEW, so the A32NX MCDU client CLAIMS its view (`CoherentViewOwnership.Claim`) from Start to Stop once its agent has loaded, reconnect gaps included; a client that could not load its agent claims nothing. One-shots go through `CoherentEvalClient`, which enters by `TryEnterOneShot` and is refused on a claimed view, and the client does not connect while a one-shot is in flight (`OneShotInFlight`; the one-shot wakes it as it ends). Once the MCDU service exists, the D/Shift+D flight-info script ALWAYS rides `EvalOnMcduViewAsync` ("not ready" while it reconnects; with no agent loaded it goes out as a one-shot). Never re-add a "does it hold a socket right now?" check at a call site: it let a one-shot race every reconnect. `CoherentViewOwnershipTests` pin the registry and `CoherentA32nxMcduClientViewTests` the client's claim; nothing pins `CoherentEvalClient`'s use of the registry, the client's in-flight check or the MainForm call site. → [a32nx.md](../a32nx.md)

Split from A320-5 on 2026-10-09: one mechanism per ID.

## A320-33

- "Readable" (Coherent live, the window says "Connected") is owned by `CoherentLinkState` alone: one lock, every event tagged with its socket's generation, every teardown reported to it (the run loop's and `EnsureConnected`'s through `DropSocket`; `Stop` calls `_link.Stop()`; a cancel after connecting and the end of the receive loop report `OnSocketClosed` for their own socket's generation). Never keep a readable or agent-loaded flag in the client, and never set one from two threads. `CoherentLinkStateTests` pin the class only; nothing stops the client keeping a flag of its own. → [a32nx.md](../a32nx.md)

Split from A320-5 on 2026-10-09: one mechanism per ID.

## A320-34

- `CoherentA32nxMcduClient` reads the screen while the window is CLOSED too: every 1 s idle and every 250 ms with the window open (`IdleIntervalMs`, `PollIntervalMs`); showing the window (`SetActive`) wakes the loop (`WakeableDelay`) and asks a live SimBridge for the current screen. Never stop polling a closed window: `FbwMcduReadBack` speaks FMS scratchpad messages (DEST EFOB BELOW MIN) from a closed window, and nothing else brings them to the pilot. No test fails if a closed window stops polling. → [a32nx.md](../a32nx.md)

Split from A320-5 on 2026-10-09: one mechanism per ID.

## A320-35

- `FlyByWireMCDUForm.SendTextToMCDU` types one key at a time: it awaits each key, holds the read-back (`FbwMcduReadBack.HoldForTyping`, 600 ms, so a half-typed entry is not read) before the send AND again once the key is delivered, then waits 50 ms before the next. FBW's keypad applies each key 150-200 ms after it arrives and keeps order only at ≥ 50 ms spacing, so the 50 ms gap is load-bearing; never shorten it or drop either hold. `FbwMcduReadBackTests.A_later_hold_extends_an_earlier_one` pins the hold; the two call sites and the gap are untested. → [a32nx.md](../a32nx.md)

Split from A320-5 on 2026-10-09: one mechanism per ID.
