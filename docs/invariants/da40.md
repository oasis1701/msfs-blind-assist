# COWS Diamond DA40 rules — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/da40.md`, which Claude Code loads when it reads matching code. Background: [da40.md](../da40.md).
The text is verbatim from the CLAUDE.md invariants PR #242 added; where two bullets told one rule they sit together under one ID. A trailing "→ doc" pointer is the original's.

## DA40-1

- `STATE_*` L:vars are READ-ONLY MIRRORS — a write sticks on read-back and drives nothing; write the K: event or input L:var and read the mirror to confirm. → [da40.md](../da40.md)

## DA40-2

- **⚠️ THIS DEFINITION FOLLOWS COWS DA40 1.2.0, AND ITS FAILURES ARE INERT WITH THE MFD's FAILURES MODE OFF.** Every failure the model reads is multiplied by `L:FAILURES_ON`, which is 1 only while the Engine page menu's Failures Mode is not Off — so a failure row can be set, read back set, and do nothing (verified live on both airframes). Every failure panel carries the read-only Failures Active row (`EveryFailurePanelSaysWhetherFailuresAreLive`); never enforce the mode, it is the pilot's. Injectable indication failures are `FAILURES_SENS_*`; `FAILURES_DISP_*` is derived from them every frame and a write to it is overwritten (`NoFailureRowWritesTheDerivedIndicationCopy`). The trim switch is `L:INPUT_TRIM_SPAD` (+1 up, −1 down) and the model NEVER resets it — release writes 0. The NG's fire is `L:FIRE_ENG:1` (the model clears `ENG ON FIRE`); the XLS keeps the stock SimVar. Do not add 1.1.5 compatibility. → [da40.md](../da40.md)

## DA40-3

- **⚠️ EVERY FAILURE THE RANDOM PICKER CAN RAISE HAS A ROW OR A WRITTEN REASON, AND NO FAILURE ROW IS INERT** — `CowsDA40FailureCoverageTests` reads the picker out of the installed `Failures.xml` and fails both ways, stale exclusions included. "Inert" is real on this aeroplane: the XLS's `FAILURES_BLOCK` (block damage left the model in 1.2.0), `FAILURES_VACC_LEAK`, the single `FAILURES_FUEL_LEAK` and `FAILURES_ALT` are raised and read by nothing else, so their rows were removed. Three COWS bugs are recorded in da40.md, not worked around (the NG picker's `FAILURES_ALT:1`, the strobe's `FAILURES_ACL_LIGHT`, the XLS's unwritten `FIRE_ENG`). → [da40.md](../da40.md)

- **⚠️ A FAILURE ROW MUST BE ABLE TO DO SOMETHING — an inert variable EXISTS, so a presence scan cannot catch it.** On the NG, FAILURES_CB_ALT / ESS_TIE / MAIN_TIE, and on the XLS FAILURES_CB_ADF / AV_BUS, are set by the random-failure picker, persisted by `systems.cfg` `[LocalVars]`, and read by NOTHING: no breaker pops, no circuit changes, a sighted pilot sees nothing, so a row would announce a failure the aeroplane does not have. Removed (the first three are XLS-only rows, where each does pop its breaker). `NoBreakerTripRowIsInert` requires every bound FAILURES_CB_* to pop a breaker or be read outside the failure picker. → [da40.md](../da40.md)

## DA40-4

- **⚠️ EVERY L:VAR THE CODE WRITES MUST EXIST IN THE PACKAGE** (`EveryLvarTheCodeWritesExistsInThePackage` scans `SetLVar`/`HoldLVar` literals) — 1.2.0 deleted the trim switch's inputs and the writes went on landing nowhere. The presence tests check L:vars only, so a STOCK SimVar for a system the airframe has not got is scoped by hand in `VariantScope` (the XLS read a coolant reservoir at 0 percent). → [da40.md](../da40.md)

## DA40-5

- **⚠️ ONE AIRFRAME'S VARIABLES NEVER APPEAR ON THE OTHER, AND THE XLS WAS CARRYING 32 OF THE NG'S.** An L:var nothing writes reads 0 for ever, so a row bound to one is a plausible zero about a system the aeroplane has not got — measured live on the XLS, its battery bus, ECU bus, water jacket and turbo summed to exactly 0 beside its own buses at 23.4 V, and the master's read-back SPOKE "battery 0.0" on every power-up. Many builders are shared and were written on the NG, so `CowsDA40Definition.VariantScope` removes each airframe's foreign keys from the variables AND every panel list AFTER all builders have run, in BOTH directions (`NgOnlyKeys`, `XlsOnlyKeys`). Never gate a shared builder's ROWS alone — the FsCopilot passes did exactly that and left their variables registered on the XLS. `CowsDA40PackagePresenceTests` is the guard: every L:var a variant binds must be a WHOLE name in that variant's own package (a substring scan passed `FAILURES_FUEL_L` on the XLS because `FAILURES_FUEL_LEAK_L` contains it); a text scan is complete ONLY because this package ships no WASM, and the stock-template cabin levers pass by name with the template as the evidence. → [da40.md](../da40.md)

## DA40-6

- **⚠️ DA40 CONTROLS AND BREAKERS ARE NAMED BY THE COCKPIT'S PLACARD, VERBATIM — the model's own `TOOLTIPID`/`ANIMTIP`, never a paraphrase** (the pilot's ruling: "just as they appear in the cockpit"). Breakers keep their abbreviations exactly ("ADC Breaker", "GPS/NAV1 Breaker", "INST. Breaker") through ONE table, `DA40BreakerPlacards`, which also names each trip after the breaker it POPS (read from Failures.xml, never assumed — `FAILURES_CB_NAV1` pops GPS/NAV1); an overload trip that pops nothing takes the vendor's designation. ⚠️ Expanding was WRONG, not just wordy, on four XLS breakers whose names had come from the real Diamond AFM: this model wires `CB_APT` to ALTPROT (circuit 24, ALT PROT), `CB_ACN` to ALTCONT, `CB_FAN` to CDUFAN, `CB_TAS` to TAS (circuit 35, FIS) — so "Autopilot Breaker" pulled alternator protection beside the real autopilot breaker (AFCS). Never "correct" a name back to the AFM: the AFM describes the real aeroplane and the pilot is flying this one. `CowsDA40BreakerPlacardTests` reads every placard and trip mapping from the installed package. Case-only differences keep title case; the sim-owned tooltips (lights, flaps, NG engine master, cabin levers) ARE readable — MSFS 2024 `Content/Packages/fs-base/en-US.locPak`, keys `COCKPIT.TOOLTIPSV2.*_TITLE` — and five light-panel ones are COWS copy-paste slips (instrument knob "Cabin lighting", right cabin switch "Pilot floodlight", left and baggage both "Cabin lighting") or untitled generic fallbacks; those keep their breaker-placard names, see da40.md. → [da40.md](../da40.md)

## DA40-7

- **⚠️ THE DA40 CARRIES NO PANEL `HelpText` AT ALL, ON EITHER VARIANT, AND MUST NOT REGAIN ANY.** It had 78; they are gone. The rule is the pilot's own and it is *do not baby the pilot* one step further out: a pilot is expected to know the aeroplane exactly as a sighted pilot is, and a control that has to explain itself is a control that is NAMED WRONG. No other aircraft in this app leans on help text either (fifteen one-line button captions across three). Everything those lines carried lives in docs/da40.md, which is where a pilot who wants the background goes; the facts stay beside the code as COMMENTS, for the next developer rather than for the pilot. ⚠️ Three things are NOT help text and are untouched: a validation error, a REFUSAL's reason (a refused action must say why), and a code comment. Pinned by `CowsDA40PohFindingsTests.NoDA40VariableCarriesHelpText`. → [da40.md](../da40.md)

## DA40-8

- **⚠️ DO NOT BABY THE PILOT — AN ANNOUNCEMENT REPORTS THE AEROPLANE, IT DOES NOT COACH.** State what happened; never append what it means for the pilot or what they should now do. "Electric trim circuit off, autopilot will not engage" became "Electric trim circuit off" on the pilot's own ruling: that the GFC 700 needs trim authority is in the manual, and a pilot who has not read it owns that. The advisory clause also goes STALE and INCOMPLETE — it named one consequence while the same failure takes the stick trim switch too. This does NOT touch validation errors ("Hectopascals must be between 948 and 1066"), or a REFUSAL's reason ("Will not open at 34 knots. The limit is 30.") — a refused action must say why it was refused. It bans the explanatory tail on a STATE announcement. → [da40.md](../da40.md)

## DA40-9

- `IsAnnounced` governs BACKGROUND changes only — combo double-talk is handled globally by `_uiSetEcho`. Every settable switch is Continuous + announced; every numeric readout is silent (the power lever counts as a number, not a switch). → [da40.md](../da40.md)

## DA40-10

- **⚠️ "SWITCHES ANNOUNCE, NUMBERS DO NOT" LEAVES DESCRIBED STATES SILENT.** Listing every DA40 variable with ValueDescriptions that never announces found forty, of which six should interrupt a pilot and did not: the engine stopping, both ECU fault LATCH flags (the CAS only says ECU FAIL - latched vs unlatched is the difference between trying the voter switch and landing), both ECU test RESULTS, and the fuel transfer pump running (it stops itself above ~14 gal, which is why the aircraft's Tips page says to set a timer). Run that listing on any new aircraft. ⚠️ A trim runaway was correctly EXCLUDED - it shares a SimVar with an already-batched failure variable, so it already speaks and promoting the copy would corrupt the batch. → [da40.md](../da40.md)

- **⚠️ A FAILURE MODELLED AS A PERCENTAGE IS SILENT UNDER THE NUMERIC RULE.** Of the DA40's 94 failure variables, 85 are announced flags and 6 are reset buttons - but `FAILURES_COOLANT_LEAK`, `FAILURES_TURBO` and `FAILURES_BOOST_LEAK` are graded 0-100, so the same rule that keeps oil temperature quiet kept a coolant leak quiet. Announce the ONSET and a material worsening (25 points), never the value. `EveryFailureEitherSpeaksOrIsDeliberatelyGraded` now fails on any `DA40_FAIL_*` that is neither an announced flag, a graded percentage, nor a button. → [da40.md](../da40.md)

## DA40-11

- **⚠️ `AddFlag` LEAVES A FLAG OnRequest AND UNANNOUNCED** - right for a state a pilot looks up, wrong for one that should interrupt them. `AFCS_FAILED` was defined with it and would have sat silently in a panel nobody had open. Check the helper's defaults against what the state MEANS before using it. → [da40.md](../da40.md)

## DA40-12

- A panel listed in `GetPanelStructure()` with no controls AND no display vars renders BLANK, which reads as broken — every panel must be built or on the explicit not-yet-built list. → [da40.md](../da40.md)

- **`CowsDA40PanelStructureTests.NotBuiltYetOnXls` is EMPTY and must stay a truthful list** - it once named six XLS panels that were declared and blank, and the test checks it in BOTH directions, so a panel that is built comes off it and a panel added to the structure without content goes on it with its reason. The XLS's engine is a different engine (magneto key not FADEC, three levers not one, left/right selector not a transfer pump), so its six engine panels share NO code with the NG's; what they share is the panel NAME and position, which is how one pilot flies both. -> [da40.md](../da40.md)

## DA40-13

- **⚠️ A DA40 HELD BUTTON MUST BE REWRITTEN EVERY 15 MS, AND THE ECU TEST HELD UNTIL IT REPORTS COMPLETE.** The held-button template drains its variable a third per frame (1, 0.667, 0.333, 0), so a 40 ms rewrite let it reach 0 and the model's 2 Hz ECU test check restarted the test. The test takes 30.6 s in 1.2.0 (not the POH's 20-25); the hold ends on `FADEC_ECUTEST_STEP:1` reaching 10, with a 45 s ceiling. → [da40.md](../da40.md)

- Momentary controls need a REPEATING write (`HoldLVar`, 15 ms) — the airframe zeroes them every frame, so one write is discarded; and every write replays the click sound, so keep holds short and SAY what the button did. → [da40.md](../da40.md)

## DA40-14

- **⚠️ AFTER A FLIGHT LOAD OR RECONNECT THE DA40's ANNOUNCERS RECORD AND DO NOT SPEAK (`DA40LoadSettle`)** — never wipe their baselines instead: a value unchanged by the load is never re-delivered, so its next real change would be swallowed as a first reading. The mute is `ScreenReaderAnnouncer.OwnerMute`, never `Suppressed` (which lets `AnnounceImmediate` through by design), and every timer-driven DA40 announcer must tick through `UnderLoadSettle`, because a timer armed in the quiet period fires after it. → [da40.md](../da40.md)

## DA40-15

- **⚠️ A DA40 PROFILE FOLLOWS THE DA40 AIRFRAME THE SIM HAS LOADED — `DA40Airframe` + `MainForm.SwapDA40ProfileToMatch`.** MSFSBA keeps the last-picked profile, and the XLS profile on a loaded NG reads the XLS's variables as 0 — it spoke "Engine variations not generated … Clear Engine Damage" (measured live). Swapped on connect from the TITLE and on every in-session load from the AircraftLoaded file path (`cows_da40ng` / `cows_da40xls` folder), because the connect pipeline runs once per connection and never sees a later load. Only NG↔XLS; never into or out of the DA40. → [da40.md](../da40.md)

## DA40-16

- **⚠️ AN AIRCRAFT DECLARES ITS OWN INTERACTION SURFACE - ENUMERATE IT INSTEAD OF WAITING TO BE TOLD.** Every clickable thing in the COWS DA40 is a `<Component ID="...">` in the model's `_IN.xml`/`_Inputs.xml`, 61 across the two variants. `CowsDA40InteractionSurfaceTests` names all 61 with either the MSFSBA control covering it or the documented reason it is not exposed, and fails on (a) a component the table does not name - which is what a future COWS update adding a control looks like, (b) a table entry for a component that no longer exists, (c) an omission with no reason. It SKIPS when the package is not installed. This is the answer to gaps being found by a pilot in the air rather than by looking. → [da40.md](../da40.md)

- **⚠️ THE INTERACTION-SURFACE AUDIT CANNOT SEE A THING THE PILOT DOES OUTSIDE THE COCKPIT.** It enumerates `<Component ID>` entries, so refuelling - filler caps on the wings - was invisible to it. Sweep a SECOND axis on every aircraft: what does a pilot DO to this aeroplane (refuel, load, service, secure), and what does the model TRACK that has no control at all. On the DA40 that found refuelling and the entire engine-damage model; ground equipment (chocks, tie-downs, covers, tow bars, GPU, pre-heat, dipstick) turned out not to be modelled at all, which is itself worth knowing. → [da40.md](../da40.md)

## DA40-17

- **⚠️ FS COPILOT'S `Definitions/COWS_DA40*.yaml` IS A THIRD-PARTY INVENTORY OF THE AIRFRAME AND FINDS WHAT A CLICK-SURFACE AUDIT STRUCTURALLY CANNOT.** A shared-cockpit sync tool has to enumerate the state that matters or two aircraft drift apart, so its `get:` list is a coverage test for READOUTS — none of which is a `<Component ID>`, which is all `CowsDA40InteractionSurfaceTests` can see. Two method traps, both paid for: **"not in the package" needs a BINARY scan of every file** (a var used only by a WASM gauge reads as absent from a text grep over `.xml/.js/.cfg`), and **a BUTTON'S `Name` IS ITS OWN KEY** — the L:var it writes lives in the setter, so reading the `Name` column alone invents gaps and produced four duplicate reset buttons for resets this definition already had. Under COWS 1.1.5 sixteen names in the NG file were absent from the package (`AFCS_FAIL_*`, the whole `FAILURES_SENS_*` family, `LIGHTING_PANEL_1`/`_GLARESHIELD_1`, `ATT_CAGE_IsDown`); 1.2.0 added `AFCS_FAIL_*` (surfaced as the ROLL/PTCH CAS warnings) and `FAILURES_SENS_*` (now the injectable indication failures, bound). Binding an absent name would give rows sitting at 0 forever, reporting "no failure" about systems nothing watches, which is worse than absent because a pilot would scan them and be reassured. The file's `set:` entries are its whole CONTROL surface, and all eight real ones were already driven. → [da40.md](../da40.md)

- **The COWS DA40 package ships its OWN documentation and `DA40 LVAR bindings.txt` is the honest coverage test** - the vendor's line-by-line list of every control they expose. Read against it, only three things were missing: TO/GA (`KEY_AUTO_THROTTLE_TO_GA`, which despite the name commands the FLIGHT DIRECTOR - verified live, one press turns the FD on and sets 10 degrees NOSE UP), the Hobbs meter (`L:HOBBS`, which has its own VCockpit gauge and is NOT the MFD's "Total Service": 45.9 against 0.0 on the same airframe), and the barometric knob (`AS1000_PFD_BARO_INC`, same SimConnect transport as the radio knobs). Everything else was already exposed. -> [da40.md](../da40.md)

## DA40-18

- **⚠️ THE AIRCRAFT SHIPS ITS OWN TIPS AND HELP PAGE - READ IT BEFORE PROBING ANYTHING.** Not the G1000 checklist: the MSFS NATIVE checklist, `Checklist/DA40_NG_Checklist.xml` in the package, whose postflight section holds the vendor's own operating knowledge - warm-up (idle 2 min, then up to 50% load), rotate speeds (67 KIAS normal, 60 short field, pitch 7.5), the traffic pattern (downwind 45%, abeam 20% flaps T/O 85 KIAS, final 35% flaps LDG 77 KIAS), the ILS profile, that fuel transfer auto-stops above ~14 gal, and **"Reseting failures/Charging battery - press and hold the ECU test button for 10 seconds with the engine master turned off"**, which is the aeroplane's own documented way out of the flat-battery state that cost this project an afternoon. Every MSFS aircraft ships one of these files; a reader for it would generalise. → [da40.md](../da40.md)

- **The POH carries four facts no variable can express, and they belong in docs/da40.md rather than in a call-out or a help line.** (1) Engine-damage CAUSES differ by airframe — improper warmup, overheating, oil starvation, overspeeding and unfiltered dirty air on both; improper leaning, shock cooling and lead fouling on the XLS; sustained load above 92 % and improper cooldown on the NG (the water-cooled Austro is IMMUNE to shock cooling, so listing the Lycoming's causes on it describes the wrong engine). (2) State saving never carries the canopy and window positions, the parking position, the alternator masters, the ignition switch position or the electric/alternator/engine masters, and restores nothing at all when the flight starts on the RUNWAY or in the AIR. (3) **Reset: Damage is the only way to REGENERATE the performance variations** — the documented escape from an XLS whose randomly generated spread leaves it structurally unstartable. (4) The POH recommends not exceeding **1350 °F EGT**. ⚠️ CORRECTION to the first telling of this: MSFSBA DOES annotate that — `DA40_XLS_EGT_*` carry `BandRange(null, null, 1350, null)`, an upper CAUTION with nothing red above it — and the claim that it “stays a sentence rather than an invented band” was simply wrong about the code. It is the right shape: the AFM publishes no EGT limit at all, and a recommendation is a caution, not a prohibition. → [da40.md](../da40.md)

## DA40-19

- **`GENERAL ENG STARTER ACTIVE` / `RECIP ENG STARTER TORQUE` / `ELECTRICAL BATTERY LOAD` reading 0 while the aircraft's own XML mirrors still update means THE FLIGHT MODEL IS NOT RUNNING** — the sim is on the ready-to-fly/menu screen, not in the flight. The gauge layer ticks there (mirrors move, writes stick, ambient weather and position read correctly, and `ABSOLUTE_TIME` keeps advancing), so every ordinary probe says "alive" while no engine will ever start. `msfs_get_connection_status`'s `sim_running: false` is the honest signal for this and must NOT be dismissed as stale because the clock is moving. → [da40.md](../da40.md)

- **`msfs_get_connection_status`'s `sim_running: false` is load-bearing and must not be dismissed because other things look alive.** In that state the aircraft's XML/gauge layer runs fully — `L:` mirrors update, writes stick, the CAS window renders live messages, ambient weather and position read correctly, `ABSOLUTE_TIME` advances, `SIMULATION_RATE` is 1 and even `G_FORCE` reports ~0.999 with realistic noise — while the ENGINE and flight-model layer is completely inert. The tell is that `GENERAL ENG STARTER ACTIVE`, `RECIP ENG STARTER TORQUE` and `ELECTRICAL BATTERY LOAD` all sit at exactly 0 with the starter commanded, and `K:ENGINE_AUTO_START` does nothing either. ⚠️ G_FORCE noise was once taken as proof the flight model was live and it is NOT — that reasoning was wrong and led to a retracted correction. → [da40.md](../da40.md)

## DA40-20

- **The REPAIR_AND_REFUEL key binding cannot be triggered from outside** — neither `(>K:REPAIR_AND_REFUEL)` nor `TransmitClientEvent` reaches the aircraft's input binding (verified live); never add a button for it. → [da40.md](../da40.md)

## DA40-21

- **The COWS DA40 has ONE avionics fit and no equipment page** - stock Working Title G1000 (not NXi) plus GFC 700. What varies between liveries is the TAIL MODEL (`BOOM`, `HIGHTAIL`, `NOTAIL`, `BOOM2`), chosen in the sim's aircraft selection. The only things changeable from the cockpit are the nine COWS options on the MFD Engine page menu and the 77 Working Title G1000 settings. → [da40.md](../da40.md)

- **The DA40 has NO EFB** — no tablet, nothing in the package resembling one; it is a light single and the G1000 is the whole suite. Flight planning runs through MSFSBA's own EFB (Shift+E) and SimBrief import, both of which are AIRCRAFT-INDEPENDENT (`ShowElectronicFlightBagDialog` has no aircraft gate, `settings.SimbriefUsername` is global), so both have worked on the DA40 since it was added. The aircraft's own Navigraph plugin is a separate thing: Navigraph CHARTS on the MFD behind a device login, whose pages read but whose account linking is the pilot's to do. → [da40.md](../da40.md)

- **The DA40 has exactly TWO G1000 screens and no captain/first-officer split** — `AS1000_PFD` and `AS1000_MFD` in the sim's own view list, plus a Hobbs meter. ⚠️ They do NOT share a viewService: each is its own instrument with its own registered views and page state, and only the SETTINGS are shared over the instrument bus (which is why the units read from either). One inspector socket per screen, so the PFD window and the CAS watcher must hand it back and forth. → [da40.md](../da40.md)

## DA40-22

- Anything doable inside a G1000 display (MFD pages, the checklist, softkeys) does NOT get a panel — it belongs in a display window reached by a hotkey. → [da40.md](../da40.md)

- **Anything doable on a G1000 display does not ALSO get a panel — and that now costs the Aircraft Options panel eight of its ten controls.** The MFD Engine page's page MENU carries Failures Mode, State Saving, Engine Damage, Realistic Parking Brake, Panel Shake, Steering Mode, Trim Speed and Prop Speed, and the display window reads and drives it. Only Timer Expired Alert and Hide G1000 FMA stay, because they are the two that menu does NOT list. All ten VARIABLES remain defined and announced, so a change made on the MFD is still heard — what went is the duplicate control, never the ability to hear it. → [da40.md](../da40.md)

## DA40-23

- **The DA40 binds twelve colon-indexed L:vars** (`FADEC_ECUTEST_TIMER:1`, `FADEC_ECUTEST_STEP:1`, `ECU_VOTER:1`, `MASTER_COVER:1`, `FAILURES_PROP:1`, `FAILURES_OIL:1` and others): COWS indexes its own variables, so these are real L:vars, registered as `SimVarType.LVar`, and the narrowed VAR-2 (#269) is satisfied because the classification comes from the add-on's source, not the name's shape. Writing is the separate guard: `SetLVar` keeps every name with a colon on the data-def path (SIM-12), which DBG-1 calls unreliable for many add-on L:vars. For the DA40 it is not: every one the panels write (the ECU voter, the master guard, the failure flags through `HandleFailureSet` and the breakers) was pressed live through MSFSBA's own code with `tools/DA40Probe` and read back changed, on both airframes (2026-10-05/06). A NEW colon-indexed write is not covered by that measurement: read it back before trusting it (DBG-4). → [da40.md](../da40.md)
