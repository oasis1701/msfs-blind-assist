# Sim tablet (MSFS 2024's own EFB) — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/sim-tablet.md`, which Claude Code loads when it reads matching code. Background: [sim-tablet.md](../sim-tablet.md).

## STAB-1

- Never focus a sim tablet text box or send it a mousedown (`coherent-sim-tablet-agent.js`): focus fires `FOCUS_INPUT_FIELD`, which hands the pilot's keyboard to the tablet. Type with `.value` plus an `input` event; `releaseKeyboard` hands back a focus a page takes by itself after a press, `A.lateFocus` one within 5 s (GSX's search). → [sim-tablet.md](../sim-tablet.md)

Why. The tablet OS's `TextBox` (efb_os.js) calls `Coherent.trigger("FOCUS_INPUT_FIELD", …)` in its `onFocusIn`, and the sim then routes every key to the tablet: the pilot's sim keys and MSFSBA's own global hotkeys stop working until the box loses focus. Its `onmousedown` focuses the input, so a mousedown reaching a box is a focus too. None of this is needed: measured live on 2026-10-19, `input.value = x` plus `new InputEvent('input')` reaches the box's model through its own `_onInput` debounce, with no focus (a seat weight 170 → 160 moved the total mass 2079 → 2069 LBS; the route string box took a whole route). Some boxes focus themselves after an action (a box built with `focusOnClear`), so after every press and every set the reader runs `releaseKeyboard`: if a tablet input holds focus it calls `blur()` and dispatches `InputEvent('focusout')`, the box's own focus-out path, which sends `UNFOCUS_INPUT_FIELD`. It runs again on the next ticks, as the OS focuses after its own debounce. It only acts right after the reader's own action, never on a scrape, so a sighted helper typing on the tablet is left alone. Coherent can leave `document.activeElement` on the body while a box has focused itself (measured 2026-11-15: Settings' Add favorite focuses its search, `FOCUS_INPUT_FIELD` went out, `activeElement` stayed BODY), so the reader records each focus itself (a capturing `focus` listener, `window.__MSFSBA_LAST_FOCUS`) and also takes any OS box marked `textbox--focused`; a focusout on a box that is not focused is a no-op for the OS. A page can also focus a box LATE, after its server answers: GSX Remote's "Search parking..." asks Couatl, and only when the answer comes does the page focus its search box, whose focus listener has GSX's host app send `FOCUS_INPUT_FIELD` (measured 2026-11-16: the box held focus and the mask was on until the reader blurred it). So the capturing focus listener also hands back a box focused within 5 s (`A.LATE_FOCUS_MS`) of the reader's last press or set in that document (`window.__MSFSBA_PRESSED_AT`): it adds a one-shot `focus` listener to the box, which runs after the page's own (they were added first) and releases it through the box's own blur path, so the page sends its own `UNFOCUS_INPUT_FIELD`. A real (trusted) mouse, pointer or touch press in the second before the focus (`window.__MSFSBA_USER_POINTER_AT`) means the pilot or a helper clicked the box, which is left alone; the reader's own mousedown presses are synthetic and never count.

## STAB-2

- A press fires the ONE event the element listens to (`A.press`): `click()` for an onclick control, a lone mousedown for an onmousedown-only one (the Flight Planner's search results); never both, never a pointer sequence. → [sim-tablet.md](../sim-tablet.md)

Why. The OS's buttons set `onclick` to their callback (`AbstractButton.onAfterRender`), as do the tab strips, dropdown items and switches; `el.click()` runs it once. The Flight Planner's facility search results (`FacilityResultItem`) set only `onmousedown`, measured live: a `click()` on one did nothing, a mousedown selected KSEA. Firing both would run a control that listens to both twice, and the MD-11 reader's pointerdown/mousedown/pointerup/mouseup/click sequence would send a mousedown into text boxes, which focuses them (STAB-1).

## STAB-3

- Disabled is the OS's `disabled` ATTRIBUTE (on div list items too, or on a group around the control) or a shown `.disabled-layer`, read by `A.isDisabled`, never `el.disabled` alone; a press on a disabled control is refused (false), never sent. → [sim-tablet.md](../sim-tablet.md)

Why. The OS disables a component with `setAttribute("disabled", "")` (`GamepadUiComponent.disable`), on `<div>` dropdown items as well as buttons, where `el.disabled` is undefined. The Flight Planner disables ENTER ROUTE STRING while its plan is locked and LOAD FROM WEB and SEND TO AVIONICS during the cooldown after a send. The CSS shows the control's own `.disabled-layer` child while it is disabled, which is also what a captured fixture keeps. One container carries `disabled="false"` while enabled, so that value is not disabled. A refused press must report false, so the shell says "Unavailable" rather than the pilot pressing a dead item. The OS also disables a whole group: measured 2026-11-15, Settings' Tablet size and Tablet orientation rows carry `disabled=""` on the row and its button group, not on each button, while the sim shows the tablet nowhere (a press then changed nothing), so a disabled ancestor within four levels (stopping at the app's view) dims the control too.

## STAB-4

- The SimBrief import ACTS by structure (`A.route.*`: the Folder-icon Import menu's item at `ENTER_ROUTE_STRING`, the airport steps in order, runways by designator), never by the English labels, which the OS translates; the reader may READ labels. → [sim-tablet.md](../sim-tablet.md)

Why. Every label on the tablet goes through `Utils.Translate`, so "ENTER ROUTE STRING" and "Arrival airport" are English only on an English sim. The Flight Planner's own enum fixes the Import menu's order (LOAD_FROM_WEB, LOAD_PLN_FILE, ENTER_ROUTE_STRING, REQUEST_FROM_AVIONICS), and the menu is the route header's dropdown whose selector shows the Folder icon. The departure, arrival and alternate airports are the route steps holding an airport search box, in that order, and a runway is matched on its designator ("runway 01", SimBrief's "01" and "1" are all runway 1), never on the word "runway". Reading text for the pilot is fine: it is spoken in the sim's own language.

## STAB-5

- The SimBrief import never sends the route to the avionics: Send stays the pilot's own press on the Route page, after reviewing what loaded (the owner's choice, 2026-10-19). → [sim-tablet.md](../sim-tablet.md)

Why. Sending replaces the flight plan in the aircraft's avionics. The tablet can change the plan as it loads (it picked runway 10 at KSAV where SimBrief planned 01, and picked an ILS approach once runway 01 was set), so the pilot hears the summary first and then chooses Send to avionics, Send to ATC, or both, from the Route page's Send menu.

## STAB-6

- The import's waits live in `SimTabletSimBriefImport`, one reader call per step, never a timer chain inside the page: the client re-installs the reader on any eval timeout, which would drop a chain mid-import. → [sim-tablet.md](../sim-tablet.md)

Why. Every step is synchronous in the page once triggered (open the menu item, type, SAVE, pick a runway); only the waits between them are not: the route box's model takes the text on its next tick, SAVE enables after that, and the airports load asynchronously. `CoherentPmdgEfbClient` re-runs the agent script on a live socket whenever an eval times out, replacing `A`, so a `setTimeout` chain inside the page could be cut off halfway through. Waiting in C# also makes each step testable: `SimTabletSimBriefImportTests` plays the tablet with a scripted stand-in, and the jsdom tests in `tools/sim-tablet-test` pin each `A.route.*` step.

## STAB-7

- The tablet IGNORES a runway written into the route string ("KSAV/01", measured), so `SimTabletRoute.Build` writes none; the runways are picked afterwards on the airports' runway dropdowns, and the summary says every procedure the tablet then chose by itself. → [sim-tablet.md](../sim-tablet.md)

Why. Measured live on 2026-10-19: "KFFC/31 DCT SOONE DCT NOKIE DCT KSAV/01" loaded exactly like the same route without the suffixes, with runway 10 at KSAV. Picking runway 01 on the arrival airport's dropdown worked, and the tablet then chose the approach "ILS 1 via Direct" by itself (TERBE, MIZLU, RW01, the missed approach to TILLS), which went to the avionics with the route. A pilot who never hears that would fly an approach nobody planned, so the summary names every departure, arrival and approach procedure the Route page shows.

## STAB-9

- The route box opens holding the Flight Planner's current route, and its SAVE stays DISABLED while the text is that same route (measured), so `route.enter` compares the two and closes the box as unchanged, and the import skips SAVE; never retry SAVE on an unchanged route as a failure. → [sim-tablet.md](../sim-tablet.md)

Why. Measured live on 2026-10-19 with the KFFC-KSAV plan already loaded: the box opened holding "KFFC DCT SOONE DCT NOKIE DCT KSAV", and typing the same text left SAVE with `disabled=""` for good, while a different route enabled it within 600 ms and the same route disabled it again. A pilot pressing "Load latest SimBrief plan" twice, or after loading the plan another way, would otherwise hear "The sim tablet did not take the route" for a plan that is in fact loaded. The comparison ignores case and spacing; the import goes on to the runways and adds "The Flight Planner already had this route." to the summary. When SAVE never enables for a changed route, the import closes the box (`route.closeBox`) before failing, so no popup is left over the Route page.

## STAB-10

- A speed and level group goes into the route box ONLY with the cruise level in BOTH fields (`SimTabletRoute.CruiseGroup`, N0030F030): the tablet's parser takes the level from the SPEED digits (measured: N0112F030 gave FL112); SimBrief's own group is dropped. The SID goes right after the origin, the STAR right before the destination. → [sim-tablet.md](../sim-tablet.md)

Why. Read from atlasapp.js (`EfbRouteParserService`, EFB OS 1.0.3) and measured on 2026-10-19. `tryParseAirportWithProcedures` takes the word right after the departure airport (after an optional speed and level group) as a departure procedure when it names one of that airport's departures, and the word right before the destination as an arrival; it never sets their transitions or an approach. Its `tryParseStepClimb` matches `/^([KNM])([0-9]{3,4})([FSAM])([0-9]{3,4})$/`, reads `parseInt(n[2])`, the SPEED, as the level, and drops the speed: "KFFC N0112F030 DCT SOONE DCT NOKIE DCT KSAV" set the plan's cruise altitude (the Performance panel's box) to FL112, where SimBrief planned 3,000 ft. With the level in both fields, "KFFC N0030F030 …" set FL030, and would from a parser that read the right field too. "F" is used always: an "A" level is taken as raw feet (A030 would be 30 ft). The cruise box itself cannot be typed into without focus: the Route page's copy is a UnitBox that writes the plan only in its focus-out (`onFocusOut`), so typing showed 450 there while the plan kept FL112; the owner asked not to force a value the tablet does not take as it takes the route. SimBrief's ATC route starts with its own group (speed and level), so the import uses `<general><route>`, drops any group in it, and writes its own from `<general><initial_altitude>`. SimBrief keeps the SID and STAR in `<general><sid_ident>` and `<star_ident>` (`SimBriefOFP.SidIdent`, `StarIdent`), which may be absent from the route itself, so the builder adds each where the parser looks unless the route already starts or ends with it. The summary says the cruise altitude the Performance panel reads back (`A.route.cruise`), with any cruise warning the tablet shows, or the one sent when that panel has not been built yet. A jet plan through the box live is still to be measured.

## STAB-12

- An OS slider is set only by dragging its bar as a pilot does (`A.dragSlider`: mousedown on `.slider-bar`, then document mousemove and mouseup), never by writing `--ratio-value`; `A.setSlider` bisects along the bar against its read-out and refuses, putting it back, when the read-out does not move with it; "+5" is from where it is. → [sim-tablet.md](../sim-tablet.md)

Why. The tablet OS's Slider (efb_os.js) draws its position from the `--ratio-value` style on `.slider`, but keeps its value in the component, which takes it only from a drag: a mousedown on `.slider-bar`, then mousemove and mouseup on the document. Writing the style moves the picture and leaves the value, so the reader drags, with a first move one pixel aside because the slider ignores a move to the x it last saw. The pilot types a value, never a travel percentage, so a slider with a read-out beside it ("Haze strength 120") is set by searching along the bar for the position where the read-out says the typed number, or the nearest the slider's steps allow; measured on AtmosphereMod, the read-out follows the drag in the same tick, so the whole search runs in one call. The read-out has to be seen to move first, at both ends (an end that reads as a word, "Off", is measured 2 % inside it): one that updates later, belongs to another slider, or stays the same is not trusted, and the slider goes back to where it was and the set is refused, so the pilot hears that it was not set rather than a wrong value. "+5" and "-5" move it from where it is; "-5" is a value of its own where the read-out runs below zero. A slider without a read-out reads as its travel, 0 to 100 percent; one with a text box beside it is not a control at all, as the box takes its value (Settings' brightness).

## STAB-13

- A press fires the event the element listens to (`A.pressEventsOf`: on* properties, getEventListeners handed in on each call, else the addEventListener hook's record), `click()` when none is known or it has a default action; the hook only records and passes every listener on. Class names decide pressable only without getEventListeners. → [sim-tablet.md](../sim-tablet.md)

Why. The OS sets `onclick` (STAB-2), but the add-on apps bind with `addEventListener`, which leaves nothing on the element: MK Airport's tabs listen to click, its jetway buttons to mousedown only, and a click on those does nothing. The reader installs, once per document, a hook on `EventTarget.prototype.addEventListener` that records which press events an element is given and passes the call through untouched; it sees only what is bound after it is installed. The debugger's `getEventListeners` sees every listener, whenever it was bound, but exists only inside an eval that asks for the command line API, so the client hands it in as an argument on every scrape, press and set (`CoherentPmdgEfbClient.ListenerArg`, sim tablet only): measured 2026-11-15, 9670 elements in 30 ms, MK Airport's tabs answering "click". A press then fires that one event (a lone mousedown, a touchstart), and `click()` for an element that listens to click, to nothing known, or has a default action that only a click starts (a link with an href, a form's submit button). With exact listeners in hand, guesses from class names ("-btn", "-tab") only add false buttons that split a line into words, so they apply only without `getEventListeners` (the jsdom tests, an older client); `cursor: pointer` on an element of its own still counts.

## STAB-14

- A cross-origin frame (GSX Remote, Navigraph Charts) is read in its own context from Runtime.enable, matched to its marker by origin, else size (`SameFrameSize`), spliced in at the marker, idx slot x 1,000,000 (`SpliceFrames`); a context is forgotten only when the debugger drops it, on an error or 3 misses; never send Runtime.disable. → [sim-tablet.md](../sim-tablet.md)

Why. Some add-on apps are a page from another origin in an iframe: GSX Remote at `http://127.0.0.1:8744`, Navigraph Charts. The tablet's page cannot reach their documents, so the reader emits a marker, kind "frame", holding the frame's origin and its window size, and the client reads the frame in its own execution context. `Runtime.enable`, sent once per socket after the reader is installed, reports every context with its origin, and nothing else on this view (measured 2026-11-15: ten context events in ten seconds); a frame that has navigated to another origin is found by its window size (`innerWidth` by `innerHeight` against the frame's `clientWidth` by `clientHeight`, within 4 px, never 0 by 0). The frame's elements replace its marker, their idx moved to `slot * 1,000,000 + idx` (slot 1 for the first marker), far above anything the page stamps (the SimBrief action is 990001), so a press says by its idx alone which context it goes to. A frame eval waits 2 s; one timeout is not a dead frame (a busy page can miss one), so a context is dropped after an error reply or 3 misses: timeouts, or installs that answer without the reader's marker (the reader throws in that context, `InstallOutcome`). The debugger drops one itself too (`Runtime.executionContextDestroyed`, `executionContextsCleared` when the page reloads), and the client forgets it then. A forgotten context comes back only when the frame reloads or the client reconnects. Same-origin frames are read in place by the page's own walk and observed with it. Each connection installs its own reader into each frame once (tracked apart from the frame's element list, so a frame whose reads keep failing is never reinstalled on every poll, and one whose install keeps failing is forgotten after three), as into the page: a frame keeps whatever reader an earlier connection put there until it reloads (measured 2026-11-16: TechLog's frame kept the previous reader across a new client, so a new MSFSBA would have read it with the old one); the install costs about 250 ms on the first read. `Runtime.disable` is never sent: the debugger does not answer it, and an eval sent after one hung.

## STAB-15

- The tablet's view gets frames only while the sim shows it; while it gets none, the reader runs the OS's view update and the page's queued frame callbacks, each once (`A.pumpIfStalled`: before a read when stalled, before every press and set unless a frame came in 200 ms); never a timer or frame loop of its own. → [sim-tablet.md](../sim-tablet.md)

Why. The tablet's OS runs the app on screen once per animation frame (its view service's `update`), and the apps read the sim there. Coherent gives the view frames only while something shows it: measured 2026-11-15, the iniBuilds A350, which has a tablet of its own, gave the view 0 frames in 5 s, where the C172, which shows the sim's tablet in its cockpit, gave it 30 a second. Its apps froze: Ground Services said "Door 1 Closed" while the door opened, and its press then toggled from that stale state. The reader asks for a frame on every call and counts the view stalled when one asked for is 500 ms late; then it calls the view service's `update` itself, with a time on the view's own frame clock that only rises, and what that changes counts for the same read. Presses and sets run it unless a frame came in the last 200 ms, so a press acts on the current state; a heavy update (over 20 ms) runs on every third read only. The reader never starts a timer or frame loop in the page: the client re-installs it on any eval timeout (STAB-6), and a loop running while nobody reads would cost the sim. The page's own frame callbacks need running too: the OS's VirtualList builds the rows a scroll brings in a requestAnimationFrame callback (measured 2026-11-15 on the Pilot book's logbook: with the tablet shown nowhere, a scroll moved the list and left the old rows drawn). So the reader, once per document, wraps `requestAnimationFrame`: each callback queued from then on is recorded and wrapped to run ONCE, whoever calls it first (the browser at a frame, or the pump), and `cancelAnimationFrame` forgets it. The pump runs the recorded ones with the same frame time, three rounds at a time, so an animation loop advances a few steps and never spins: first, then again after the view update when the pump made that update itself (so what the update queued runs in the same pump), and once more when a list moved. The reader's own frame watch calls the browser's function, never the hook, so a pump never counts as a frame. A callback queued before the reader came, or through a reference taken before it (the bundled ResizeObserver polyfill binds its own at load), is not recorded; the hook is installed in the tablet's own window only, never an add-on's frame. Each callback the pump runs is also cancelled in the browser, so its queue never fills with callbacks already run; and the view update runs once per pump, whether the OS's own frame loop (recorded after any real frame) calls it or the pump does. A list moved without a frame never hears its scroll event either (the browser fires it at a frame), so each virtual list keeps the position the reader last saw, and the pump fires `scroll` on any that moved, whatever moved it. A press also pumps right after itself, so what it set going runs before the next read. What still needs real frames is STAB-16's: measured 2026-11-15, the Pilot book's own Back to the top (its VirtualList's `scrollToItem`) left the list's rows stale until frames came, where the reader's Scroll buttons worked without them.

## STAB-16

- Show/Hide the tablet in the sim presses the toolbar's tablet button (`SimTabletPanel`, one press at a time, one socket on the "Toolbar" view), which only toggles: each outcome is read from the view's frames, a press bringing none is undone, only a panel MSFSBA showed that still shows is hidden (window closed, exit); never assume a state. → [sim-tablet.md](../sim-tablet.md)

Why. Some parts of an app move only with real frames: the Pilot book's logbook list, sized by a ResizeObserver polyfill that waits for one, stayed "loading" on the A350 until the sim's tablet panel was opened from the toolbar, when it listed the flights (measured 2026-11-15, 135 of them). A sighted pilot opens that panel; the reader offers the same, once a frame asked for has been missing a full second. The toolbar is its own Coherent view, titled "Toolbar", which no MSFSBA client holds; its tablet button is the element around the `#EFB` icon that listens to clicks. Its markup is the same with the panel open and closed (diffed live), so a press only toggles, and the state is read from the tablet's view instead: frames arrive while the panel shows. So a Show is confirmed by a frame within 1.5 s; with none, the press may have closed a panel the sim shows but does not draw (paused, in a menu), so it is pressed again, leaving the panel as it was, and the pilot is told. Nothing is pressed while the reader does not answer, as such a press could be neither checked nor undone. A Hide counts only once the frames stop (after 0.5 s for the panel's close, within 2.5 s); a press that hides nothing keeps the mark and says it could not hide. Each press is stamped in the page (`window.__MSFSBA_TABLET_PRESS_AT`), and for 3 s the reader keeps the button listed by the mark alone, so the button the pilot just pressed never leaves the list while frames start or stop. Presses run one at a time (a busy flag, and one `CoherentEvalClient` socket on the view at a time, DBG-9). What MSFSBA showed is marked in the tablet's page (`window.__MSFSBA_TABLET_SHOWN`), so a new flight, which reloads the view, forgets it; while the mark is set and frames come, the same button, on the same idx and key, reads "Hide the tablet in the sim". Closing the window hides the panel only when MSFSBA showed it and frames still come (the pilot may have closed it from the toolbar, and pressing again would open it), and stops if the window opens again meanwhile; a window closed while a Show runs hides it at the end of that Show; exit tries for 2.5 s at most, without waiting for the frames to stop, then allows no further press (`SimTabletPanel.ShutDown`), since a Show or Hide frozen by that wait resumes in the exit's message pump. The press also releases any text box focus (STAB-1).

## STAB-8 (retired: the sim tablet is no longer opt-in per aircraft nor on Shift+T; it opens from Extras for every aircraft, STAB-11)

Retired 2026-10-19, before the PR merged, when the owner reported that the community wants the sim tablet available at all times and not as a replacement for any other tablet. The rule made the tablet opt-in per aircraft (`IAircraftDefinition.UsesSimTablet`, default false, both since removed) and put it on Input Shift+T as the last branch of the tablet hotkey, so an aircraft with a tablet of its own never reached it. STAB-11 replaces it.

## STAB-11

- The sim tablet opens from the Extras menu (In-Sim Tablet (FS2024 Native)) for EVERY aircraft, beside an aircraft's own tablet and never in place of it: never gate it per aircraft nor route it through Input Shift+T, which stays the aircraft's own (the owner's decision, 2026-10-19). On MSFS 2020 it says the tablet is MSFS 2024 only. → [sim-tablet.md](../sim-tablet.md)

Why. The tablet is the sim's, the same "Electronic Flight Bag" view on every MSFS 2024 aircraft, with the add-on apps installed into it (GSX and SayIntentions put theirs there), and the community asked for it at all times, not as a replacement for any other tablet (the owner, 2026-10-19). The first design, opt-in per aircraft on Input Shift+T (STAB-8, retired), hid it from every aircraft with a tablet of its own; the owner moved it to Extras, "for now", with no hotkey. Input Shift+T stays each aircraft's own tablet, so the menu item never competes with it. For the same reason an aircraft switch leaves the window and its client open (`MainForm.AircraftSwitch.cs` says so where it closes the MD-11's): the view outlives the aircraft, the client reconnects by itself when the sim rebuilds it, and exit is the one teardown (`MainForm.cs`). MSFS 2020 has no such view, and a window opened there would sit unconnected forever, so the menu item says so and opens nothing; while the sim is not connected the version is unknown and the window opens, connecting once MSFS 2024 is running.
