# First Officer: Fenix A320, FBW A32NX/A380, Headwind A330 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/first-officer-airbus.md`, which Claude Code loads when it reads matching code. Background: [first-officer.md](../first-officer.md).
The text is verbatim from PR #160's CLAUDE.md as of `642f48c1`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below" or "above" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it. FOA-1 was updated on 2026-10-06 (the Fenix now has the A32NX's ECAM page selection and lighting scenes) and on 2026-10-18 (the A32NX presses its ECP page keys), and FOA-8 is new from 2026-10-06; FOA-8's flows paragraph was rewritten, and its Taxi and Line-up paragraph added, on 2026-10-09. FOA-10 is new from 2026-10-14 (the Securing order and the Securing Checklist latch). FOA-9 is new from 2026-10-09; with it FOA-8's live-values paragraph names the A380, and its flows paragraph marks the A32NX and A330 rudder-trim link as a known exception (2026-10-10).

## FOA-1

- FBW A32NX First Officer (`FirstOfficer/FBWA320/`) is a hybrid — Fenix procedures/phase structure + the A380 write mechanism (`FlyByWireA320Definition.ApplyUIVariable`) — with A320-specific divergences: baro polarity is PULL=STD (opposite the A380's PUSH=STD). ECAM SD pages are selected by pressing the page's ECP key, as the pilot does (`FbwA320ActionExecutor.FireEcamPageAsync` sends `A32NX_ECP_<key>_PRESSED`, then `_RELEASED` from a `finally`, so a lost release cannot leave the key held). Since FBW #10700 (2026-07-18) the SD shows `A32NX_ECAM_SD_PAGE_TO_DISPLAY`, which the DMC's page logic computes from the ECP keys, the FWC's request and the flight phase; `A32NX_ECAM_SD_CURRENT_PAGE_INDEX` became one of its outputs. Until 2026-10-18 the FO wrote that index directly: the ECP key lit (FakeDmc reads the index) and the SD stayed where it was, while the step said done. A second press of a page the pilot already selected returns the SD to automatic, so the press leaves a page the SD already shows alone, and it reports success only when the SD then shows the page (or the read-back does not arrive). The Headwind A330 and the A380 still select pages by writing `A32NX_ECAM_SD_CURRENT_PAGE_INDEX`: their SDs read it (the A339X's `sd.js` at 0.9.0-382bacbd; the A380X's ECAM CP writes it itself), so neither changes. Its cockpit-lighting scene (ANN/dome/standby-compass + six analog knobs, against the A380's single ANN knob) and its ECAM page selection are no longer A32NX-only: **the Fenix selects the same ECAM pages and sets the same lighting scenes (2026-10-06)**, at the same flow points and with the same line ids, on its own mechanism (it pulses its own `S_ECAM_*` page pushbuttons, which are momentary, so `FenixActionExecutor` lists them as `LVarPulse`) and its own lighting encodings (annunciator 0 Dim/1 Bright/2 Test, dome 0 Off/1 Dim/2 Bright, four 0–1 knobs, and no standby-compass light, so that line is an allow-listed absence in `A320FamilyParityTests`). → [first-officer.md](../first-officer.md)

## FOA-2

- A380 FO seat-belt/nose-light encodings follow the PR #139 faithful switches: every "seatbelt signs ON" write is `SEATBELT_SIGN` = **0** (0=On/1=Auto/2=Off — writing 1 selects AUTO, the old bug shape) with detection ONLY on `SEATBELT_SIGN_LIGHT`, never the switch position; the nose light is the 3-position `NOSE_LIGHT` (0=T.O./1=Taxi/2=Off) — `LIGHT_TAXI_OVHD` no longer exists, and Lineup must drive BOTH `LIGHT_LANDING` and `NOSE_LIGHT`=0 (the indexed landing-light fix decoupled the nose beam from the wing switch). → [first-officer.md](../first-officer.md)

## FOA-3

- The Headwind A330 FO (`FirstOfficer/HWA330/`) is a DUPLICATE of the A32NX profile, not a shared-data variant — kept honest by `HwA330ParityTests`, which fails when the two drift apart on group/item/flow ids or the fired-event set unless the difference is in its `KnownStateFieldDivergences` allow-list WITH a reason (and fails again if an allow-list entry stops being a divergence). Five A339X divergences are corrected and must never be "harmonized" back to the A320: `A32NX_LIGHTS_NAV_LOGO` does not exist (stock `LIGHT NAV`/`LIGHT LOGO`, index 0); the SD page enum shifts because the A330 splits ElecAC/ElecDC and adds CB, so STS is **13** not 12 (12 is CRUISE) and HYD/FUEL are 5/11; the seat-belt switch is 3-position **0=On/1=Auto/2=Off**, the OPPOSITE of the A32NX's 1=On/0=Off, and its AUTO block re-drives the stock simvar every 500 ms so the position must be written BEFORE the lamp is reconciled — BOTH writes are load-bearing (LIVE 2026-08-30: `CODE_POS_*` fire on a COCKPIT CLICK ONLY, so the position write alone leaves the lamp untouched, while the toggle alone is undone by AUTO; the reconcile is NOT belt-and-braces, as this was first documented); landing lights are ONE 2-position ganged switch on stock `LIGHT LANDING:2/:3` with **no RETRACT position** (LIVE 2026-08-30: `L:LIGHTING_LANDING_2` reads 0 whether the lights are on OR off — frozen — and the A32NX item accepts 0 as ON, so the unported profile reports "Landing lights: ON" PERMANENTLY, a false positive on a before-takeoff checklist, not a missing tick); and potentiometers 10/11 are the Captain's CEILING and MAP lights (binary click-toggles), not glareshield floods, so the lighting scene writes four pots, not six. → [first-officer.md](../first-officer.md)

## FOA-4

- **An EVENT-typed key with no explicit `varKey ==` branch in `FlyByWireA320Definition.HandleUIVariableSet` is a SILENT DEAD WRITE THAT REPORTS SUCCESS — the FO executor's fallback calls `SetLVar(varKey, value)`, which merely prepends `L:`, so it creates an L:var named after the EVENT, and returns TRUE.** The flow step announces done and the checklist item ticks while the cockpit control never moves. The only catch-all (~`:8843`) requires `Type == LVar`, so Event-typed keys fall straight past it. FOUR shipped this way and were live-confirmed dead on the A339X 2026-08-31 (writing `L:ENGINE_MODE_SELECTOR` = 2 left both `L:XMLVAR_ENG_MODE_SEL` and `A:TURB ENG IGNITION SWITCH EX1:1` at 1): `ENGINE_MODE_SELECTOR`, `SPOILERS_ARM_TOGGLE` and `A32NX.FCU_EFIS_L/R_FD_PUSH`. It affected the A32NX as much as the A330 — the A380 was fine only because its definition already had such branches. Both FBW executors now REFUSE an unclaimed Event key instead of faking success (the stance `IFly737ActionExecutor` always took), and `FoFbwUnclaimedEventKeyTests` sweeps every key the FO writes and fails if a registered Event key is unclaimed — that sweep is the guard, not vigilance. ⚠ Two of the four are TOGGLES, not sets: the FD pushes must stay GUARDED on `A32NX_FCU_EFIS_{L,R}_FD_LIGHT_ON` (live-measured: one press took the light 1→0), because the FO writes them meaning ON, so an unguarded branch turns a silent no-op into switching the flight director OFF — actively worse than the bug. `ENGINE_MODE_SELECTOR` is an ABSOLUTE set (`TURBINE_IGNITION_SWITCH_SET1/2` + `L:XMLVAR_ENG_MODE_SEL`, two engines not the A380's four) and needs no guard; `SPOILERS_ARM_TOGGLE` is absolute but must go through `ExecuteCalculatorCodeUnique` — its RPN carries no operand, so two identical consecutive writes dedup and the second disarm is lost. → [first-officer.md](../first-officer.md)

## FOA-5

- The A330 PANEL inherits the A32NX's, so a control the A339X repurposed is offered wrongly there even after the First Officer stops touching it — `HeadwindA330Definition.BuildPanelControls` overrides three: the two `LIGHTING_LANDING_2/_3` retractable rows are replaced by the single read-back `LIGHT LANDING:2` (the A320 L:vars are FROZEN here — live-measured 0 with the lights on AND off), and potentiometers 10/11 (`BRIGHT_GLARESHIELD_{CAPT,FO}_SET`) are DROPPED because on this airframe they are the Captain's CEILING and MAP lights, binary click-toggles — writing the A320 scene's 50 lit the ceiling lamp while `L:A339X_CEILING_LIGHT_CAPTAIN` still read 0 (demonstrated live). Never over-apply either to the A32NX, where all of them are correct; both directions are pinned by test. → [first-officer.md](../first-officer.md)

## FOA-6

- **Per build too (2026-10-20, FOA-12).** The owner flies BOTH simulators with a different FlyByWire build in each, and #10890 is on the FS2024 branch only: the FS2020 builds (fs2020-master 2020.16.0) still write `A32NX_SPEEDS_LANDING_CONF3` (A32NX MCDU/mcdu.js; A380 MFD/mfd.js and SystemsHost), and neither renamed variable exists in them. So `FbwA320StateEvaluator.LandingConf3Field` and `FbwA380StateEvaluator.LandingConf3Field` are now synthetics (`FO_LANDING_CONF3`) that read the running build's variable (`FbwA320StateEvaluator.LandingConf3VarFor`, `A380BuildNames.LandingConf3Key`), NaN while the simulator is unknown (which the cap treats as FULL, as before); both definitions register and both evaluators poll both names. The Headwind A330 is unchanged. Pinned by `Conf3RegistrationTests`, `FbwA380BuildResolutionTests`. The history below is unchanged.

- **The CONF 3 landing selection is a different L:var on each airframe (2026-10-09).** FlyByWire #10890 ([c0421a940d](https://github.com/flybywiresim/aircraft/commit/c0421a940d), 2026-09-11) renamed the A32NX's `A32NX_SPEEDS_LANDING_CONF3` to `A32NX_FM_LANDING_CONF3` (its `A32NX_FMCMainDisplay.ts` writes the new name, `FlyByWireInterface.cpp` reads it); the A380X's is `A380X_FM_LANDING_CONF3` (FlyByWireInterface.cpp L368 at 255546cb, there since FBW #10855); a GitHub code search finds no writer of the old name anywhere in FlyByWire. Headwind's A339X still writes the old name: its `A32NX_FMCMainDisplay.ts` writes it from the PERF APPR flaps-3 selection, and its `A32NX_Speeds.ts` only resets it to 0; it has no `A32NX_FM_LANDING_CONF3` (all read on GitHub, 2026-10-09). So until 2026-10-09 the A32NX and A380 caps read NaN and took flaps FULL with CONF 3 selected, and the A380's "Landing Configuration 3" registration named the dead variable too. That registration is `OnRequest`, has no value descriptions and is in no panel display, hotkey or announcement, so the First Officer evaluator's poll is its only consumer: there was never a pilot-facing readout to be dead. Now `FlyByWireA320Definition` registers `A32NX_FM_LANDING_CONF3`, `HeadwindA330Definition` removes it and registers `A32NX_SPEEDS_LANDING_CONF3` for itself, the A380's registration names `A380X_FM_LANDING_CONF3`, and each evaluator polls its own (`FbwA320StateEvaluator.LandingConf3Field`, `FbwA380StateEvaluator.LandingConf3Field`, the A330's literal), pinned by `Conf3RegistrationTests` and `HwA330ParityTests.KnownPollFieldDivergences`; each FO auto manager reads its airframe's name too, pinned by a source-text guard in `Conf3RegistrationTests` (a manager on the wrong name reads NaN, which is FULL, the original bug). The A330 difference is recorded there and here, as FOA-7 records the VFE-next one; FOA-3's list of A339X control divergences is not extended. The bullet below is the 2026-08-30 record, written when the A32NX still wrote the old name.

- `A32NX_SPEEDS_LANDING_CONF3` is registered by `FlyByWireA320Definition` and polled by both FBW-family FO evaluators — it was unregistered until 2026-08-30, so `conf3` read NaN and the CONF 3 landing flap cap could never engage on the A32NX or the A330. It is `OnRequest`, matching its `A32NX_SPEEDS_*` siblings and the poll that actually delivers it: a first attempt registered it `Continuous` WITHOUT `IsAnnounced`, which is an UNBACKED declaration — both continuous paths (`Setup.cs` batch admission and `StartContinuousMonitoring`) require `IsAnnounced`, so nothing pushes it and it silently relies on the on-demand route its own declaration disclaims. ⚠ That shape is NOT inert: it still receives an individual data definition and `RequestVariable` never inspects frequency, so it DOES deliver while the FO window polls — do not describe it as undelivered (an earlier telling did). The real cost is latent: `MainForm.PanelBuilder` skips the initial `RequestVariable` for a `Continuous` L:var combo, so the first panel to list such a var reads blank forever. Live-confirmed 2026-08-31 in flight: the L:var flipped 0→1 the instant CONF 3 was selected on the MCDU. → [first-officer.md](../first-officer.md)

## FOA-7

- The A32NX First Officer's VFE-next flap-extension guard reads the FAC's `V_FE_NEXT` word (FAC 1, else FAC 2) through its evaluator's synthetic `FO_VFE_NEXT` — never `A32NX_SPEEDS_VFEN`, which FBW #10890 stopped publishing: it reads 0, and the guard (`ias >= vfeNext - 5` → hold) then holds on EVERY approach, so the FO silently never extends flaps. No data → NaN → hold. Both duplicated FBW-family auto managers read `FO_VFE_NEXT`; the Headwind A330's evaluator resolves it to the plain L-var it still publishes, and the A380 FO still reads the plain L-var its aircraft writes. → [a32nx.md](../a32nx.md)

## FOA-8

- The read-back (`*_CL`) checklists of the three A320-family First Officers (Fenix A320, FlyByWire A32NX, Headwind A330) are one card: **the current Airbus A320-family normal checklist (November 2021), with each "ECAM MEMO … NO BLUE" line spoken as the memo's own lines.** The Fenix and the A32NX are kept line for line equal by `A320FamilyParityTests` (group ids, names and order; item ids, order, labels and kinds; flow ids and step ids, order, labels, kinds and the checklist lines each step completes), and every difference has to sit in a named allow-list with a reason; a second test fails when an allow-listed entry stops being a difference. The A330 duplicates the A32NX, held by `HwA330ParityTests` as before ([FOA-3]). Settled 2026-10-06 (PR #160); the research and the owner's choices are below. → [first-officer.md](../first-officer.md)

**The card — ten lists, in tree order.** Labels are "Challenge: RESPONSE"; where Airbus prints a blank the label says SET and the live value (below) carries the real setting. Group ids: `COCKPIT_PREP_CL`, `BEFORE_START_CL`, `AFTER_START_CL`, `TAXI_CL`, `LINEUP_CL`, `APPROACH_CL`, `LANDING_CL`, `AFTER_LANDING_CL`, `PARKING_CL`, `SECURING_CL`.

**Single-pilot wording (the owner's choice, 2026-10-07).** The lines are spoken to one pilot flying with the First Officer window, so two marks of the printed card are left out: Airbus's "(BOTH)", which asks both pilots to answer (Baro reference twice, Takeoff speeds and thrust, Windows, Flight controls, Flaps setting, Takeoff runway), and a "Takeoff memo," / "Landing memo," prefix on each memo line, which repeated what the list name already says: the memo lines read "Autobrake: MAX", "Seat belts: ON" (Fenix "Signs: ON"), "Spoilers: ARMED", "Flaps: T.O", "T.O config: NORMAL" in Taxi, the takeoff memo's "Cabin: READY" in Line-up (since 2026-10-19, below), and "Landing gear: DOWN" to "Flaps: SET" in Landing. Never re-add either. In the same pass the cockpit-lights lines of the action lists say "annunciator", not "ANN" (a screen reader reads it as a name), and the CVR line reads "CVR test: listen for the test tone" in the Preflight list and the Preflight flow. `A320FamilyLabelWordingTests` pins all of it on the three profiles.

Each line is either **Auto** (ticks itself from live state, `action: null`, `RevertToState`) or a **Reminder** (the pilot confirms): every line is action-free ([FO-3]). A line the app cannot read is a Reminder; the cabin lines are Reminders on all three aircraft (FlyByWire's CABIN READY needs a CALLS press and resets at every flight-phase change, so reading it would mislead). The Fenix's "Rudder trim: NEUTRAL" is a line the pilot confirms: a Fenix rudder-trim var exists (`N_FC_RUDDER_TRIM_DECIMAL`) but its units and zero were never measured, so it is "unmeasured", not "unreadable"; the A32NX and A330 read the FAC rudder trim (`A32NX_FAC_1_RUDDER_TRIM_POS`, under 0.1 degree). The fixed wording of every line, and which are Auto, is in the three profiles' `*ChecklistDefinitions.cs`; this section does not copy it.

**The one named exception: "Start ACARS", the last line of Before Start (owner, 2026-10-14).** `BSC_ACARS`, a Captain reminder (the First Officer cannot see ACARS; every line is action-free, [FO-3]), ends the Before Start Checklist on all three aircraft, though the card ends at "Beacon: ON". The owner: "Put it in the last item of the actual checklist itself, not the flow or action group." The Before Start flow and action list are unchanged (they already end "Start ACARS", then "Obtain pushback and start clearance"), and a finished Before Start flow ticks and latches the line with the rest. The three profiles carry the same id and label, so `A320FamilyParityTests` and `HwA330ParityTests` stay equal; `FbwA320ReadbackTests`, `FenixReadbackTests` and `HwA330ReadbackTests` pin it as the list's last line (`BeforeStartAcarsReadbackTests` pins it on all eight aircraft). It is the only extra: every other line below stays banned.

**One line moved: the takeoff memo's "Cabin: READY" is read in Line-up (owner, 2026-10-19).** The owner moved the takeoff cabin call from the Taxi flow to the Line-up flow, "this includes the checklist if it appears in the taxi checklist", so the memo's cabin line went with it: `TXC_MEMO_CABIN` in the Taxi Checklist became `LUC_CABIN` in the Line-up Checklist, after "Takeoff runway: CONFIRMED" and before "TCAS: TA/RA", and the action line `TX_CABIN` became `LU_CABIN`, the first line of the Line-up group. It is a card line in another list, not an extra line, so "Never re-add" below is unchanged. It is still a Reminder the pilot confirms, delivered by the Line-up flow's call (below). Its place, first at line-up and before TCAS, is the order secondary training material gives (the pilot monitoring advises the cabin crew, then sets TCAS); it was not checked against an Airbus document. On FlyByWire the call is what makes the ECAM takeoff memo show CABIN READY, so from Taxi until the Line-up flow runs that memo shows its cabin line not ready; the app's Taxi Checklist no longer has a cabin line, so nothing there waits on it. `A320FamilyTaxiAndRunwayEntryFlowTests`, `A320FamilyReadbackLinkTests` and the three `*ReadbackTests` pin the move on all three aircraft.

**Never re-add** the Fenix's old `AFTER_TAKEOFF_CL` and `ATC_GEAR`, either aircraft's `BEFORE_TAKEOFF_CL`, the `BSC_LINE` / `BTC_LINE` "down to the line" and "below the line" separators, a Departure Change list, or any line that is not on the card, except Start ACARS above (Missed approach altitude, an "Autobrake: MAX" line outside the takeoff memo (the memo's own line, `TXC_MEMO_AUTOBRK`, reads "Autobrake: MAX"), "Altitude: READBACK", the header-like "Taxi checklist" / "Parking checklist" lines). The Fenix's old lists took JD's Guide wording (a community guide that cites no source); the A32NX's extra lines had no source either. The After Takeoff and Descent flows stay as flows; the gear-up wait at the end of After Takeoff links no checklist line ([FO-13]).

**Sources and their weight.** No Airbus FCOM or QRH page of the current card is publicly readable, so the card was rebuilt from the public evidence below. The specifics come from the owner's verification report; every source is linked so a future reader can check it:

- **Airbus itself.** [Safety First #10](https://skybrary.aero/sites/default/files/bookshelf/3825.pdf) (August 2010) prints the landing memo line for line (LDG GEAR DN, SIGNS ON, CABIN READY, SPLRS ARM, FLAPS FULL). The Flight Operations Briefing Note ["Normal Checklists"](https://skybrary.aero/sites/default/files/bookshelf/187.pdf) (2004) describes the old format's printed "down to the line" hold point and the electronic TAKEOFF and LANDING MEMO.
- **Accident reports.** The [AAIB India final report on VT-EXT](https://aaib.gov.in/What's%20New%20Assets/Final%20report%20VT-EXT%20rev%2003.pdf) (Air India: its December 2024 cockpit voice recording reads Line-up exactly as in the table above). The UK AAIB bulletins [4/2025 on G-EJCI](https://assets.publishing.service.gov.uk/media/67f65392555773bbf109e1ea/Airbus_A320-214_G-EJCI_04-25.pdf) and [6/2026 on G-EZUK](https://assets.publishing.service.gov.uk/media/6a1d915159fb7a60f827f5b2/Airbus_A320-214_G-EZUK_06-26.pdf) (A320-214s of a UK operator whose crews fly the Taxi and Line-up checklists). The [UAE AAIS report on the Air Arabia event](https://skybrary.aero/sites/default/files/bookshelf/33075.pdf) (it carries the operator's 2017 QRH, the pre-2021 card with its memo lines). [JTSB AI2016-3](https://jtsb.mlit.go.jp/eng-air_report/JA802P.pdf) (Peach: a four-line landing memo, no CABIN line).
- **Line pilots and the date.** The [PPRuNe "new SOPs" thread](https://www.pprune.org/archive/index.php/t-646592.html), where line pilots quote Airbus's own change notes: After Takeoff/Climb deleted, Before Start and Before Takeoff reworked, "AS RQRD" replaced by stating the value; one pilot says the new SOPs have been in use since December 2021. "November 2021", this card's name throughout the repository, is the date [Travel Radar](https://travelradar.aero/new-airbus-sop-and-checklist-2022/) (aviation news, January 2022) gives for Airbus's revision.
- **Current-format cards.** [FlyByWire's flyPad checklists](https://github.com/flybywiresim/aircraft/blob/master/fbw-a32nx/src/base/flybywire-aircraft-a320-neo/config/a32nx/a320-251n/checklists.json5) (`checklists.json5`: Cockpit Preparation, Before Start, After Start, Taxi, Line-up, Departure Change, Approach, Landing, After Landing, Parking, Securing). Two community cards, independent of FlyByWire and not Airbus documents: [aviationlads, October 2025](https://aviationlads.com/wp-content/uploads/2025/10/Airbus-Checklist-2025.pdf) (a community card) and [One Engine Out VA, June 2022](https://www.blackbox711.com/docs/pdf/a320/chklst/A320_Chklst_Briefing.pdf) (a virtual airline's card).

Read together, the sources show the November 2021 redesign: "down to the line" removed, Before Start split into Cockpit Preparation and Before Start, Before Takeoff split into Taxi and Line-up, After Takeoff/Climb deleted, "AS RQRD" replaced by stating the value. 39 challenges are agreed by every current source above (the owner's count); the ones the evidence cannot settle are the owner's choices below. Weights: the memos are the best documented part (Airbus, the accident files and the current cards agree on their lines, except that the Peach report's four-line memo has no cabin line); FlyByWire's flyPad is trusted for list names, order and item set, but its February 2024 changes ([PR #8481](https://github.com/flybywiresim/aircraft/pull/8481), merged 17 February 2024: a separate CABIN READY in Taxi and Landing, a yellow electric pump in Parking, EFBs dropped from Securing) cite only "Airbusworld & up to date FCTM", an airline portal nobody outside an airline can check, and its "AS RQRD" answers go against Airbus's own change (PPRuNe, above); FlyByWire's own ADIRS check tests IR 2 twice and never IR 3 (their code in `checklists.json5`, ours tests all three). The Fenix's own old read-back lists are not a reference for Airbus content either: they took JD's Guide wording, a community guide that cites no source (see "Never re-add" above).

**The owner's choices for the 13 points the sources could not settle (2026-10-06)**, each the research's recommendation: (1) "Seat belts: ON" in Cockpit Preparation, not "Signs ON/AUTO"; (2) no separate Cabin line, since CABIN READY is a memo line; (3) no yellow electric pump line in Parking; (4) "EFBs: OFF" kept in Securing; (5) TCAS answer "TA/RA", not "as required"; (6) speak the real value instead of "as required"; (7) fuel quantity without "balanced"; (8) the memo's signs line is labelled per aircraft, because the warning computers differ (the A32NX and A330 say "seat belts", FlyByWire's model; the Fenix keeps the printed-card wording "signs", never checked in the sim); (9) landing-memo flaps FULL or CONF 3, the real ECAM line; (10) "T.O config: NORMAL", not NORM; (11) no After Takeoff checklist; (12) the takeoff memo is read after the T.O CONFIG test, Airbus's own Taxi trigger; (13) the A32NX cabin line is not detected. Also decided: no Departure Change checklist; the A330 follows every A32NX change (its own five A339X divergences, [FOA-3], stay untouched); the Fenix and A32NX flows were brought together at the same time (engine start waits for the engine to run on both, takeoff flaps from SimBrief on both with a Captain reminder unless the lever then reads a takeoff position, ECAM pages, lighting scenes and the FCU altitude push on the Fenix, the gear-up confirmation, shared wording, and two new action lines, "TCAS: STANDBY" in Shutdown and "External power: OFF" in Securing).

**Live values.** `ChecklistItem.LiveValue` is an optional `Func<TState, string?>`. `FirstOfficerForm` uses it in exactly two places, both of which already speak or show the line: the tick speech, "Flaps setting: SET, flaps 1: checked", and the status line, "Flaps setting: SET, flaps 1 — Complete" (`ChecklistItemSpeech.TickText` / `StatusText`). **The tree text never changes**: a changing node text would make the screen reader re-read the tree. A null value (unknown, NaN, not readable) leaves today's text exactly as it was. Besides these three, only the FlyByWire A380 sets `LiveValue`, on the blank lines of its own ECL read-backs ([FOA-9]); no other aircraft does, so nothing else changes. The text comes from the pure formatters in `FirstOfficer/Airbus/AirbusReadbackFormat.cs` (flap lever, engine mode, TCAS, packs, anti-ice, baro, parking brake, autobrake, V-speeds, fuel), shared by the three profiles and the A380, and culture-invariant: its tests also run under de-DE and sv-SE, because CI runs under en-US and would never catch a comma decimal in speech. ## FOA-10

- The four Airbus Securing flows (Fenix A320, FBW A32NX, Headwind A330, FBW A380) switch the APU master OFF, **wait for the APU flap to close**, and only then switch external power and the batteries OFF. Owner, 2026-10-14: FlyByWire's own order. Source, FlyByWire's A32NX guide, Securing the Aircraft ([powering down](https://docs.flybywiresim.com/pilots-corner/a32nx/a32nx-beginner-guide/powering-down/)): APU MASTER off, "wait 2 minutes for the APU flap door to close before cutting power", which "requires either APU or external power", then EXT PWR off, then BAT 1 and 2 off. Cutting power first leaves the flap open. The wait is step `SC_APU_WAIT`, "APU flap to close", between the APU master step (`SC_APUMASTER` on the A320 family, `SC_APU_OFF` on the A380) and `SC_EXTPWR_OFF`; it links no checklist line.
- **FBW jets (A32NX, A330, A380):** a field wait on `A32NX_APU_FLAP_OPEN_PERCENTAGE` below 0.5, 150 s ceiling, Skip. It is NOT conditional (no `RunOnlyIfStepSent`): a flap that reads closed passes at once, so an APU that never ran costs no wait, and an unread flap simply times out and the flow carries on. The ceiling is a judgement (FlyByWire says 2 minutes; the flap's actual travel was not measured). The variable is `OnRequest` and silent ([FOA-6]'s rule: never `Continuous` without `IsAnnounced`), polled by all three evaluators; the A32NX and A330 get it from the System Display APU page rows' auto-registration, the A380 declares it (`Read(...)`). `AirbusSecuringPowerOffTests` pins registration, polling and silence. - **Fenix:** the Fenix publishes no APU flap or speed, and its lamps are never inferred ([FO-11]), so `SC_APU_WAIT` is a fixed 120 s, a judgement, with `FlowStep.RunOnlyIfStepSent = SC_APUMASTER`: it runs only after an APU master this run switched off, and passes silently otherwise.
