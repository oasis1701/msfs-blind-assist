# First Officer: Fenix A320, FBW A32NX/A380, Headwind A330 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/first-officer-airbus.md`, which Claude Code loads when it reads matching code. Background: [first-officer.md](../first-officer.md).
The text is verbatim from PR #160's CLAUDE.md as of `642f48c1`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below" or "above" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it. FOA-1 was updated on 2026-10-06 (the Fenix now has the A32NX's ECAM page selection and lighting scenes) and FOA-8 is new from that date.

## FOA-1

- FBW A32NX First Officer (`FirstOfficer/FBWA320/`) is a hybrid — Fenix procedures/phase structure + the A380 write mechanism (`FlyByWireA320Definition.ApplyUIVariable`) — with A320-specific divergences: baro polarity is PULL=STD (opposite the A380's PUSH=STD) and ECAM SD pages pulse via ECP press/release (not a sticky index). Its cockpit-lighting scene (ANN/dome/standby-compass + six analog knobs, against the A380's single ANN knob) and its ECAM page selection are no longer A32NX-only: **the Fenix has the same ECAM page selection and lighting scenes (2026-10-06)**, at the same flow points and with the same line ids, on its own encodings (annunciator 0 Dim/1 Bright/2 Test, dome 0 Off/1 Dim/2 Bright, four 0–1 knobs, and no standby-compass light, so that line is an allow-listed absence in `A320FamilyParityTests`). → [first-officer.md](../first-officer.md)

## FOA-2

- A380 FO seat-belt/nose-light encodings follow the PR #139 faithful switches: every "seatbelt signs ON" write is `SEATBELT_SIGN` = **0** (0=On/1=Auto/2=Off — writing 1 selects AUTO, the old bug shape) with detection ONLY on `SEATBELT_SIGN_LIGHT`, never the switch position; the nose light is the 3-position `NOSE_LIGHT` (0=T.O./1=Taxi/2=Off) — `LIGHT_TAXI_OVHD` no longer exists, and Lineup must drive BOTH `LIGHT_LANDING` and `NOSE_LIGHT`=0 (the indexed landing-light fix decoupled the nose beam from the wing switch). → [first-officer.md](../first-officer.md)

## FOA-3

- The Headwind A330 FO (`FirstOfficer/HWA330/`) is a DUPLICATE of the A32NX profile, not a shared-data variant — kept honest by `HwA330ParityTests`, which fails when the two drift apart on group/item/flow ids or the fired-event set unless the difference is in its `KnownStateFieldDivergences` allow-list WITH a reason (and fails again if an allow-list entry stops being a divergence). Five A339X divergences are corrected and must never be "harmonized" back to the A320: `A32NX_LIGHTS_NAV_LOGO` does not exist (stock `LIGHT NAV`/`LIGHT LOGO`, index 0); the SD page enum shifts because the A330 splits ElecAC/ElecDC and adds CB, so STS is **13** not 12 (12 is CRUISE) and HYD/FUEL are 5/11; the seat-belt switch is 3-position **0=On/1=Auto/2=Off**, the OPPOSITE of the A32NX's 1=On/0=Off, and its AUTO block re-drives the stock simvar every 500 ms so the position must be written BEFORE the lamp is reconciled — BOTH writes are load-bearing (LIVE 2026-08-30: `CODE_POS_*` fire on a COCKPIT CLICK ONLY, so the position write alone leaves the lamp untouched, while the toggle alone is undone by AUTO; the reconcile is NOT belt-and-braces, as this was first documented); landing lights are ONE 2-position ganged switch on stock `LIGHT LANDING:2/:3` with **no RETRACT position** (LIVE 2026-08-30: `L:LIGHTING_LANDING_2` reads 0 whether the lights are on OR off — frozen — and the A32NX item accepts 0 as ON, so the unported profile reports "Landing lights: ON" PERMANENTLY, a false positive on a before-takeoff checklist, not a missing tick); and potentiometers 10/11 are the Captain's CEILING and MAP lights (binary click-toggles), not glareshield floods, so the lighting scene writes four pots, not six. → [first-officer.md](../first-officer.md)

## FOA-4

- **An EVENT-typed key with no explicit `varKey ==` branch in `FlyByWireA320Definition.HandleUIVariableSet` is a SILENT DEAD WRITE THAT REPORTS SUCCESS — the FO executor's fallback calls `SetLVar(varKey, value)`, which merely prepends `L:`, so it creates an L:var named after the EVENT, and returns TRUE.** The flow step announces done and the checklist item ticks while the cockpit control never moves. The only catch-all (~`:8843`) requires `Type == LVar`, so Event-typed keys fall straight past it. FOUR shipped this way and were live-confirmed dead on the A339X 2026-08-31 (writing `L:ENGINE_MODE_SELECTOR` = 2 left both `L:XMLVAR_ENG_MODE_SEL` and `A:TURB ENG IGNITION SWITCH EX1:1` at 1): `ENGINE_MODE_SELECTOR`, `SPOILERS_ARM_TOGGLE` and `A32NX.FCU_EFIS_L/R_FD_PUSH`. It affected the A32NX as much as the A330 — the A380 was fine only because its definition already had such branches. Both FBW executors now REFUSE an unclaimed Event key instead of faking success (the stance `IFly737ActionExecutor` always took), and `FoFbwUnclaimedEventKeyTests` sweeps every key the FO writes and fails if a registered Event key is unclaimed — that sweep is the guard, not vigilance. ⚠ Two of the four are TOGGLES, not sets: the FD pushes must stay GUARDED on `A32NX_FCU_EFIS_{L,R}_FD_LIGHT_ON` (live-measured: one press took the light 1→0), because the FO writes them meaning ON, so an unguarded branch turns a silent no-op into switching the flight director OFF — actively worse than the bug. `ENGINE_MODE_SELECTOR` is an ABSOLUTE set (`TURBINE_IGNITION_SWITCH_SET1/2` + `L:XMLVAR_ENG_MODE_SEL`, two engines not the A380's four) and needs no guard; `SPOILERS_ARM_TOGGLE` is absolute but must go through `ExecuteCalculatorCodeUnique` — its RPN carries no operand, so two identical consecutive writes dedup and the second disarm is lost. → [first-officer.md](../first-officer.md)

## FOA-5

- The A330 PANEL inherits the A32NX's, so a control the A339X repurposed is offered wrongly there even after the First Officer stops touching it — `HeadwindA330Definition.BuildPanelControls` overrides three: the two `LIGHTING_LANDING_2/_3` retractable rows are replaced by the single read-back `LIGHT LANDING:2` (the A320 L:vars are FROZEN here — live-measured 0 with the lights on AND off), and potentiometers 10/11 (`BRIGHT_GLARESHIELD_{CAPT,FO}_SET`) are DROPPED because on this airframe they are the Captain's CEILING and MAP lights, binary click-toggles — writing the A320 scene's 50 lit the ceiling lamp while `L:A339X_CEILING_LIGHT_CAPTAIN` still read 0 (demonstrated live). Never over-apply either to the A32NX, where all of them are correct; both directions are pinned by test. → [first-officer.md](../first-officer.md)

## FOA-6

- `A32NX_SPEEDS_LANDING_CONF3` is registered by `FlyByWireA320Definition` and polled by both FBW-family FO evaluators — it was unregistered until 2026-08-30, so `conf3` read NaN and the CONF 3 landing flap cap could never engage on the A32NX or the A330. It is `OnRequest`, matching its `A32NX_SPEEDS_*` siblings and the poll that actually delivers it: a first attempt registered it `Continuous` WITHOUT `IsAnnounced`, which is an UNBACKED declaration — both continuous paths (`Setup.cs` batch admission and `StartContinuousMonitoring`) require `IsAnnounced`, so nothing pushes it and it silently relies on the on-demand route its own declaration disclaims. ⚠ That shape is NOT inert: it still receives an individual data definition and `RequestVariable` never inspects frequency, so it DOES deliver while the FO window polls — do not describe it as undelivered (an earlier telling did). The real cost is latent: `MainForm.PanelBuilder` skips the initial `RequestVariable` for a `Continuous` L:var combo, so the first panel to list such a var reads blank forever. Live-confirmed 2026-08-31 in flight: the L:var flipped 0→1 the instant CONF 3 was selected on the MCDU. → [first-officer.md](../first-officer.md)

## FOA-7

- The A32NX First Officer's VFE-next flap-extension guard reads the FAC's `V_FE_NEXT` word (FAC 1, else FAC 2) through its evaluator's synthetic `FO_VFE_NEXT` — never `A32NX_SPEEDS_VFEN`, which FBW #10890 stopped publishing: it reads 0, and the guard (`ias >= vfeNext - 5` → hold) then holds on EVERY approach, so the FO silently never extends flaps. No data → NaN → hold. Both duplicated FBW-family auto managers read `FO_VFE_NEXT`; the Headwind A330's evaluator resolves it to the plain L-var it still publishes, and the A380 FO still reads the plain L-var its aircraft writes. → [a32nx.md](../a32nx.md)

## FOA-8

- The read-back (`*_CL`) checklists of the three A320-family First Officers (Fenix A320, FlyByWire A32NX, Headwind A330) are one card: **the current Airbus A320-family normal checklist (November 2021), with each "ECAM MEMO … NO BLUE" line spoken as the memo's own lines.** The Fenix and the A32NX are kept line for line equal by `A320FamilyParityTests` (read-back group ids and order, item ids, order and labels, flow and step ids, action-group lines), and every difference has to sit in a named allow-list with a reason; a second test fails when an allow-listed entry stops being a difference. The A330 duplicates the A32NX, held by `HwA330ParityTests` as before ([FOA-3]). Settled 2026-10-06 (PR #160); the research and the owner's choices are below. → [first-officer.md](../first-officer.md)

**The card — ten lists, in tree order.** Labels are "Challenge: RESPONSE"; where Airbus prints a blank the label says SET and the live value (below) carries the real setting. Group ids: `COCKPIT_PREP_CL`, `BEFORE_START_CL`, `AFTER_START_CL`, `TAXI_CL`, `LINEUP_CL`, `APPROACH_CL`, `LANDING_CL`, `AFTER_LANDING_CL`, `PARKING_CL`, `SECURING_CL`.

| List | Lines |
|---|---|
| Cockpit Preparation | Gear pins and covers: REMOVED. Fuel quantity: CHECKED. Seat belts: ON. ADIRS: NAV. Baro reference: SET (both). |
| Before Start | Parking brake: SET. Takeoff speeds and thrust: SET (both). Windows: CLOSED (both). Beacon: ON. |
| After Start | Anti-ice: SET. ECAM status: CHECKED. Pitch trim: SET. Rudder trim: NEUTRAL. |
| Taxi | Flight controls: CHECKED (both). Flaps setting: SET (both). Radar and predictive windshear: ON and AUTO. Engine mode selector: SET. Then the takeoff memo, one line each: autobrake MAX, signs ON (A32NX and A330 word it "seat belts: ON"), cabin READY, spoilers ARMED, flaps T.O, T.O config NORMAL. |
| Line-up | Takeoff runway: CONFIRMED (both). TCAS: TA/RA. Packs 1 and 2: SET. |
| Approach | Baro reference: SET (both). Seat belts: ON. Minimum: SET. Autobrake: SET (read only, [FO-14]). Engine mode selector: SET. |
| Landing | The landing memo, one line each: landing gear DOWN, signs ON (A32NX and A330: seat belts), cabin READY, spoilers ARMED, flaps SET (FULL, or 3 when the GPWS LDG FLAP 3 switch is on). |
| After Landing | Radar and predictive windshear: OFF. |
| Parking | Parking brake or chocks: SET. Engines: OFF. Wing lights: OFF. Fuel pumps: OFF (all six). |
| Securing | Oxygen: OFF. Emergency exit lights: OFF. EFBs: OFF. Batteries: OFF. |

Each line is either **Auto** (ticks itself from live state, `action: null`, `RevertToState`) or a **Reminder** (the pilot confirms): every line is action-free ([FO-3]). A line the app cannot read is a Reminder; the cabin lines are Reminders on all three aircraft (FlyByWire's CABIN READY needs a CALLS press and resets at every flight-phase change, so reading it would mislead). The Fenix's "Rudder trim: NEUTRAL" is a line the pilot confirms: a Fenix rudder-trim var exists (`N_FC_RUDDER_TRIM_DECIMAL`) but its units and zero were never measured, so it is "unmeasured", not "unreadable"; the A32NX and A330 read the FAC rudder trim (`A32NX_FAC_1_RUDDER_TRIM_POS`, under 0.1 degree). The fixed wording of every line, and which are Auto, is in the three profiles' `*ChecklistDefinitions.cs`; this section does not copy it.

**Never re-add** the Fenix's old `AFTER_TAKEOFF_CL` and `ATC_GEAR`, either aircraft's `BEFORE_TAKEOFF_CL`, the `BSC_LINE` / `BTC_LINE` "down to the line" and "below the line" separators, a Departure Change list, or any line that is not on the card (Missed approach altitude, an "Autobrake: MAX" line outside the takeoff memo, "Altitude: READBACK", the header-like "Taxi checklist" / "Parking checklist" lines). The Fenix's old lists took JD's Guide wording (a community guide that cites no source); the A32NX's extra lines had no source either. The After Takeoff and Descent flows stay as flows; the gear-up wait at the end of After Takeoff links no checklist line ([FO-13]).

**Sources and their weight.** No Airbus FCOM or QRH page of the current card is publicly readable, so the card was rebuilt from the evidence that is: Airbus Safety First #10 (2010, the landing memo line for line), Airbus's Flight Operations Briefing Note "Normal Checklists" (2004), the Air India VT-EXT final report (the December 2024 cockpit voice recording reads Line-up exactly as above), the UAE AAIS Air Arabia report (its 2017 QRH, the pre-2021 card with its memo lines), JTSB AI2016-3 (Peach: a landing memo without a cabin line), UK AAIB bulletins 4/2025 and 6/2026, line pilots quoting Airbus's own change notes (PPRuNe), and three current-format cards (FlyByWire's flyPad `checklists.json5`, aviationlads October 2025, One Engine Out VA June 2022; the last two independent of FlyByWire). Airbus published the redesign in November 2021: "down to the line" removed, Before Start split into Cockpit Preparation and Before Start, Before Takeoff split into Taxi and Line-up, After Takeoff/Climb deleted, "AS RQRD" replaced by stating the value. 39 challenges are agreed by every current source; the ones the evidence cannot settle are the owner's choices below. Weights: the memos are the best documented part (Airbus, accident files and FlyByWire's warning-computer code agree on their lines); FlyByWire's flyPad is trusted for list names, order and item set, but its February 2024 changes (a separate CABIN READY in Taxi and Landing, a yellow electric pump in Parking, EFBs dropped from Securing) cite only an airline portal nobody outside an airline can check, and its "AS RQRD" answers go against Airbus's own change; the Fenix's EFB checklist is an unsourced airline-style card in the pre-2021 layout and is **not a reference for Airbus content**; FlyByWire's own ADIRS check tests IR 2 twice and never IR 3 (their code, ours tests all three).

**The owner's choices for the 13 points the sources could not settle (2026-10-06)**, each the research's recommendation: (1) "Seat belts: ON" in Cockpit Preparation, not "Signs ON/AUTO"; (2) no separate Cabin line, since CABIN READY is a memo line; (3) no yellow electric pump line in Parking; (4) "EFBs: OFF" kept in Securing; (5) TCAS answer "TA/RA", not "as required"; (6) speak the real value instead of "as required"; (7) fuel quantity without "balanced"; (8) the memo's signs line is labelled per aircraft, because the warning computers differ (the A32NX and A330 say "seat belts", FlyByWire's model; the Fenix keeps the printed-card wording "signs", never checked in the sim); (9) landing-memo flaps FULL or CONF 3, the real ECAM line; (10) "T.O config: NORMAL", not NORM; (11) no After Takeoff checklist; (12) the takeoff memo is read after the T.O CONFIG test, Airbus's own Taxi trigger; (13) the A32NX cabin line is not detected. Also decided: no Departure Change checklist; the A330 follows every A32NX change (its own five A339X divergences, [FOA-3], stay untouched); the Fenix and A32NX flows were brought together at the same time (engine start waits for the engine to run on both, takeoff flaps from SimBrief on both with a Captain reminder when no plan is loaded, ECAM pages, lighting scenes and the FCU altitude push on the Fenix, the gear-up confirmation, shared wording, and two new action lines, "TCAS: STANDBY" in Shutdown and "External power: OFF" in Securing).

**Live values.** `ChecklistItem.LiveValue` is an optional `Func<TState, string?>`. `FirstOfficerForm` uses it in exactly two places, both of which already speak or show the line: the tick speech, "Flaps setting: SET (both), flaps 1: checked", and the status line, "Flaps setting: SET (both), flaps 1 — Complete" (`ChecklistItemSpeech.TickText` / `StatusText`). **The tree text never changes**: a changing node text would make the screen reader re-read the tree. A null value (unknown, NaN, not readable) leaves today's text exactly as it was, and no other aircraft sets `LiveValue`, so nothing else changes. The text comes from the pure formatters in `FirstOfficer/Airbus/AirbusReadbackFormat.cs` (flap lever, engine mode, TCAS, packs, anti-ice, baro, parking brake, autobrake, V-speeds, fuel), shared by the three profiles and culture-invariant: its tests also run under de-DE and sv-SE, because CI runs under en-US and would never catch a comma decimal in speech. Each aircraft reads the value from its own variable (the A32NX fuel unit follows `A32NX_EFB_USING_METRIC_UNIT`; the A330 baro reads the Kohlsman settings, since the FBW baro display words never reach the cache on that airframe).
