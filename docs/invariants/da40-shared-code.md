# Rules the DA40 work found in shared code — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/da40-shared-code.md`, which Claude Code loads when it reads matching code. Background: [da40.md](../da40.md).
The text is verbatim from the CLAUDE.md invariants PR #242 added; where two bullets told one rule they sit together under one ID. A trailing "→ doc" pointer is the original's.

## DA40S-1

- `GetCachedVariableValue` is keyed by the MSFSBA VARIABLE KEY, never the SimVar name (`lastVariableValues[varKey]`), and a variable reaches that cache when it is **`Continuous && IsAnnounced`**. ⚠️ CORRECTION: this used to say `&& !ExcludeFromBatch`, and that clause was WRONG — it is the test for riding the shared 1 Hz BATCH, not for being cached. `SetupDataDefinitions` gives an `ExcludeFromBatch` var its OWN periodic subscription, and those deliveries land in `ProcessIndividualVariableResponse`, which writes `lastVariableValues` exactly as the batch path does (read there, not inferred). The narrow rule had reached two tests, which then failed a correct change for being FASTER. Continuous ALONE is not enough: without `IsAnnounced` it falls to an individual data def that is only read on request. A readout that must be cached but silent carries `IsAnnounced` and is silenced in `ProcessSimVarUpdate` instead; never turn a cache miss into a 0. → [da40.md](../da40.md)

## DA40S-2

- **⚠️ A SETTLE TIMER MUST OUTLAST THE SAMPLE PERIOD OF WHAT FEEDS IT — WHICH IS NOT ALWAYS ONE SECOND.** The DA40's radio frequencies and BOTH altimeter subscales now run on per-var **SIM_FRAME** subscriptions (`ExcludeFromBatch = true` + `HighFrequency = true`, the same pair `G_FORCE` uses because the 1 Hz batch missed the touchdown spike), with the `CHANGED` flag so a static radio costs nothing. That is what let their settles come DOWN to 250 ms and fixed the lag and the intermediate announcements together — on the batch those two demands could not both be met. A settle for a batch-fed value still must exceed 1000 ms; one for a fast-sampled value carries a `FAST-SAMPLED` marker beside it so the exemption sits next to its reasoning. Cost: 10 data definitions (~178 → ~188 of ~1000). ORIGINALLY WRITTEN AS **EVERY SETTLE MUST EXCEED ONE BATCH PERIOD, AND THREE DID NOT** — `RadioSettleMs` 300 ("it announces 700, 800" while tuning), `BaroSettleMs` 300 (the same on the altimeter subscale) and `PowerSettleMs` 900 (a bus read mid-climb, the settled voltage never spoken). A value swept by a knob arrives once a second, so a shorter settle expires BETWEEN deliveries and announces each intermediate instead of the resting one; just over the period means each delivery restarts it. ⚠️ It COSTS LAG and nothing at 1 Hz avoids that — shortening one does not buy speed, it buys the intermediates back; the cure is a faster SAMPLE, a def-budget question not a tuning one. An OWN-WRITE GRACE must in turn outlast the settle it protects, or it cannot suppress the echo it exists for. ⚠️ HOLD durations (ECU test 26 s, fuel wire 1.5 s, gyro cage 700 ms) are a DIFFERENT thing — a repeating write for a fixed duration — and are deliberately outside this rule. `CowsDA40SettleExceedsBatchTests` scans the source for the whole `*SettleMs` family so a new one cannot be added short. → [da40.md](../da40.md)

- **⚠️ A SETTLE TIMER MUST EXCEED ONE BATCH PERIOD.** The continuous batch samples at 1 Hz, so a knob swept for several seconds delivers a new value every second — and the DA40 radio settle at 300 ms expired between every pair, announcing each intermediate frequency the knob passed through instead of the one it stopped on (reported as "it announces 700, 800"; those were real readings a second apart, mid-sweep). Just over the period is the trick: each delivery restarts the timer while the knob moves, and it runs out only on the resting value. ⚠️ It COSTS LAG and nothing at 1 Hz avoids that — worst case is one batch period to notice the last change plus the settle. Shortening it does not buy speed, it buys the intermediate announcements back. → [da40.md](../da40.md)

## DA40S-3

- **An L:var must be registered `Units = "number"`, never a converting unit** - it holds a RAW NUMBER, so a data definition asking for `inHg`/`percent`/a velocity makes SimConnect convert from its own base unit. The DA40 standby subscale asked in `inHg` and read ZERO while set correctly ("Standby 0 hectopascals, 0.01 inches"); where a scale IS wanted, use `SimVarDefinition.Scale` and leave the unit `number`. Same trap as the A380 TCAS vertical-speed L:vars. -> [da40.md](../da40.md)

## DA40S-4

- `ABS_AMBIENT_TEMPERATURE` is KELVIN and the L:var's Units field is a LABEL, not a conversion — use the `AMBIENT TEMPERATURE` SimVar. → [da40.md](../da40.md)

## DA40S-5

- `SimVarDefinition.Format` DEFAULTS to `"F0"` — a fractional readout that does not set its own Format silently reads WHOLE numbers (the trim scan said "1" beside an announcement saying 1.74). → [da40.md](../da40.md)

- `SimVarDefinition.ValueDescriptions` is NEVER null — it initialises to an EMPTY dictionary — so any test for "has no descriptions" must check `Count`, not null. A `== null` test is always false: the DA40's unit-rendering fallback was written that way and was dead from the day it was added. → [da40.md](../da40.md)

## DA40S-6

- A non-percentage numeric control must NOT set `RenderAsSlider` — MainForm's `TrackBar` is hardcoded 0-100 and maps the value as a percentage of that range; a key ending `_SET` renders as a typed entry instead. → [da40.md](../da40.md)

- **`SimVarDefinition.HelpText` reaches the pilot on BUTTONS and nowhere else** — `MainForm.PanelBuilder` sets `AccessibleDescription` at exactly one of its eleven control sites, so a combo, typed entry, slider, readout or status row discards it. ⚠️ That was briefly "fixed" by wiring all eleven, and the fix was REVERTED on the pilot's ruling: the DA40's help text was then deleted outright and the rest of the app's fifteen lines are all on buttons, where they already worked. So the one-site render is CORRECT and must stay — do not re-wire the other ten to "rescue" a help line. If a fact cannot be carried by a control's NAME, it belongs in the aircraft's doc, not in a description the pilot has to hunt for. → [da40.md](../da40.md)

## DA40S-7

- **⚠️ A BACKGROUND MONITOR MUST BE STARTED IN BOTH `MainForm_Load` AND `SwitchAircraft`, or it never runs for the aircraft the app OPENS with.** `SwitchAircraft` runs only when the pilot picks an aircraft from the MENU; the startup path sets `currentAircraft` directly from the saved setting in the constructor. The DA40's CAS watcher was only in `SwitchAircraft`, which is the whole reason cautions never auto-announced - proved from the app log (the aircraft registered, the display window worked, and `StartCasMonitor`'s unconditional first-line log was never written). The A380 E/WD and HS787 IRS monitors were already in both places; the DA40 now is too. → [da40.md](../da40.md)

## DA40S-8

- A `CoherentDisplayClient` agent MUST return a string containing `MSFSBA_DISP_INSTALLED` — the client tests for that token, and any other return leaves it retrying for ever with NO error and no rows (a window stuck on "Connecting..."). The client now reports that once per socket; never remove the report. → [da40.md](../da40.md)

## DA40S-9

- **⚠️ EVERY MSFS AIRCRAFT MAY SHIP ITS OWN CHECKLIST AS PLAIN XML** under `SimObjects/Airplanes/<model>/Checklist/`, and reading it beats transcribing one: it is the vendor's, complete, and follows the aircraft through updates. `NativeChecklistReader` renders it into `ChecklistForm`'s format (Page to category, Checkpoint to "Subject ... Expectation", Clue to its own line). ⚠️ Two traps in the real files: Asobo puts the literal word "Clue" in the expectation column of a NOTE row, and two Pages can share a name across Steps - which the category dictionary downstream would silently swallow. The window's order lives in `Services/ChecklistContent` (native, then the bundled `Checklists/*.txt`, then main's A320 fallback, which upstream PR #266 owns — this branch does not change it), and the reader resolves the packages root from UserCfg.opt (active key only), Community before `Official\*` — the four default folders alone missed every pilot who installed packages elsewhere. → [da40.md](../da40.md)

- **⚠️ `NativeChecklistReader` WALKED ONLY A PAGE'S DIRECT CHILDREN AND THREW AWAY EVERY CHECKPOINT INSIDE A `<Block>`.** Measured on the installed COWS package: the DA40-**XLS lost 105 of its 220 checkpoints, nearly half** — the entire cruise power table (four blocks, 51 rows of manifold pressure, RPM and fuel flow by altitude to 17,000 ft, which IS the shaded "recommended band" of the POH's chart written out as text), all three start procedures, the weights, the stall and operating speeds, the climb figures and the whole Starting-tips and Leaning sets — and the **NG 29 of 137**, including its weights, its speeds and the High Altitude operations notes. Blocks are ONE level deep in both files and each carries its own `SubjectTT`, which is a real heading and is rendered as one; the walk must be over the page's children **IN ORDER**, because a page mixes loose checkpoints with blocks. The XLS table also CONFIRMS `DA40PerformanceTables`' POH transcription independently — every shared cell agrees exactly — which is a stronger check on a figure read off a scan than re-reading the image. ⚠️ The general lesson: a reader tested against a hand-built sample document passes while silently dropping a shape the REAL file uses; the tests now assert against the installed package (skipping when it is absent). → [da40.md](../da40.md)

## DA40S-10

- **⚠️ USE `tools/coherent-coverage.js` BEFORE CLAIMING ANY COHERENT DISPLAY IS FULLY READ.** It visits every page the instrument actually has and subtracts what the agent emits from what a sighted pilot can see. Every read-coverage hole in this project was previously found by a PILOT FLYING INTO IT — the CAS block read off a hidden duplicate, the flight plan page that reported itself empty, and the whole LATERAL HALF of the FMA sitting in an unclassed element, which made an uncaptured NAV mode look identical to a working one. ⚠️ Two things make it trustworthy and both are load-bearing: the visibility test walks the ANCESTOR CHAIN (a leaf-only test passes everything inside a hidden parent, and a G1000 keeps its selector, dialogs and a duplicate CAS block mounted at all times — that alone produced 60-80 false hits per page), and anything appearing on most pages is reported ONCE as chrome rather than per page. Together: ~1,200 raw hits down to 33 real ones across 17 pages. ⚠️ NOT a G1000 tool, and was one only by accident of implementation: the agent, its GLOBAL and the SAYS expression are all arguments, because no two agents here share an entry point (only the DA40's publishes `rows()`) — so it serves the A380 E/WD, the flyPad, the PMDG EFB and the HS787 CDU as well as the XLS and the DA42's different G1000. A display that cannot enumerate its own pages sweeps whatever is ON SCREEN. It reports CANDIDATES, not verdicts. → [tooling.md](../tooling.md)

## DA40S-11

- **⚠️ FBW MIRRORS THE LEFT AILERON AND THE F/CTL READOUT ANNOUNCED A DROOP AS A ROLL.** `a380_systems_wasm/src/ailerons.rs` says so in its own comment ("we just invert left side direction") and only the LEFT mapping carries the leading minus; `elevators.rs` has NO negation on either side. So both wings drooping DOWN together — which the A380 does whenever flaps extend — arrived as one positive number and one negative, and `Defl` printed them as BARE SIGNED PERCENTAGES with no direction named at all. Measured live at flaps 2: left 16/16/12, right -17/-17/-20, with `YOKE X POSITION` at -8.3e-7 and stock `AILERON POSITION` at -3.5e-6 — no roll commanded, nothing wrong, and the pilot reasonably concluded the aeroplane was broken. `A380SurfaceDeflection` owns the convention: `DescribeMirrored` (left aileron ONLY) undoes the inversion, `Describe` (right aileron, both elevators) does not, and UP IS POSITIVE on the un-inverted side because `hyd_deflection_to_msfs_deflection` maps [0,1] onto (hyd*50-20)/30 with 30 degrees up against 20 down. ⚠️ Passing an elevator through the mirrored form, or an aileron through the plain one, announces a roll as a droop or a droop as a roll on the one page a pilot opens to find out what the surfaces are doing — and a genuine roll must still read as OPPOSED surfaces after un-mirroring, which is the property the fix must not destroy. → [a380x.md](../a380x.md)
