# AI display reads, the camera and screenshots — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/ai-display.md`, which Claude Code loads when it reads matching code. Background: [gemini.md](../gemini.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## AI-1

- ONE AI capture at a time, app-wide (`Services/DisplayReadGate.Shared`): `BaseAircraftDefinition.ReadDisplay` AND `MainForm.DescribeSceneAsync` take the same gate, because the camera both of them capture is the SIMULATOR's. The scene path took no gate at all, so pressing it during a display read captured that read's INSTRUMENT VIEW — or a frame taken mid-switch — and described it as the scene. The holder must RELEASE IT BEFORE ANY MODAL DIALOG: `MessageBox.Show` does not return until the pilot dismisses it, so an error dialog shown inside the guarded region held the gate for as long as it stood and every later display read on every aircraft answered "already in progress" when nothing was — untrue, and unactionable for a pilot who has not noticed the dialog. → [gemini.md](../gemini.md)

## AI-2

- `ScreenshotService` captures with `PrintWindow(PW_RENDERFULLCONTENT)` FIRST and must keep the BitBlt screen-copy fallback behind `ScreenshotFrame.LooksBlank` — PrintWindow is what keeps an MSFSBA window sitting over the sim out of every AI display read and scene description (verified with the sim fully hidden), and the fallback is what keeps a fullscreen setup that hands back a black frame no worse than before. Never send a frame the blank check rejected to the AI: it reads "no display visible" with full confidence. `LooksBlank` is blank only when every sample is dark (R+G+B ≤ 30) AND uniform (the spread of R+G+B across the samples ≤ 6): a failed PrintWindow frame is flat black, a night cockpit is dark but not flat — dark alone sent every night read to the screen copy, which captures whatever window sits on top. ⚠️ It must be given the window's CLIENT RECTANGLE (`ScreenshotService.ClientRegionWithin`) and sample only inside it: PW_RENDERFULLCONTENT draws the NON-CLIENT area and the bitmap is sized from `GetWindowRect`, so on a WINDOWED simulator sample (0,0) is the TITLE BAR — never near black (a dark-theme caption is about RGB 32,32,32, sum 96) — and the first sample alone ended the test, so a frame whose client area came back BLACK was called a picture and sent to the AI on every aircraft, where the screen copy PrintWindow replaced had always produced a real one. A null region (fullscreen/borderless, or a client rect Windows will not report) samples the whole bitmap, which is correct there. `CaptureAsync` bounds its own work at 10 s and returns null on a timeout (PrintWindow is a synchronous cross-process call a hung simulator never answers, and it held the display-read gate for the session), and it runs the capture on its OWN background thread, never a pool thread — the worker it abandons is stuck for the life of the process, so on a pool thread each hang permanently consumed a pool slot and left that thread's DPI awareness never restored; the frame is `Format24bppRgb`, and the capture thread runs per-monitor DPI-aware so the window rect, PrintWindow and the screen-copy fallback agree in physical pixels. → [gemini.md](../gemini.md)

## AI-3

- A display read that needs a particular cockpit camera goes through `ReadDisplay`'s `InstrumentViewRequest` (`InstrumentViewPlan` pure + `InstrumentViewSwitcher`, camera IO on `SimConnectManager.Camera.cs`, fixed def 341) — the SimVar `CAMERA VIEW TYPE AND INDEX` is settable and its index is 0-BASED (the sim's "instrument view 1" is index 0); write type THEN index, verify by read-back, and REFUSE a non-cockpit camera out loud rather than forcing the cockpit. The camera IS put back after the capture — written, verified by read-back, and a failure spoken once ("Could not return to your previous view."), never assumed; the restore runs BEFORE the AI call, which is a multi-second network round-trip the camera has no reason to sit through. ⚠️ CORRECTION to the 2026-09-09 removal: its stated mechanism — a custom camera reading as a pilot-view index the write path refuses, evidenced by `CAMERA VIEW TYPE AND INDEX MAX:1` advertising 6 against a written index of 7 — is DISPROVEN. The iFly 737 MAX8 reads `MAX:1` = 6 with the camera on index 7 and writes 1/7 back correctly (measured 2026-09-18, MSFS 2024 1.8.16.0; a cabin quickview 3/2 came back pixel-identical), so MAX does NOT bound what the write path accepts and must never gate a restore. Why the MD-11 restore failed was ANSWERED on 2026-09-20 and was never MD-11-specific: the removed code wrote both registers on ONE frame (the trap below), and with the writes spaced the live MD-11 restores correctly over three reads. The `MAX` explanation stays disproven; do not resurrect it. An out-of-range index is CLAMPED, not ignored, and the read-back reports the CLAMPED value (a write of 20 landed on 8, read back as 8) — which is exactly why read-back verification works and why the failure must be announced. The write order is TYPE then INDEX (`ICameraViewIo.Set`) and that is load-bearing: in the instrument type an index write acts immediately, so writing the index first slides the camera to that instrument view and strands the pilot there if the type write is then refused. ⚠️ **The restore's two registers must ALSO be written on SEPARATE FRAMES, and its read-back must be CONFIRMED AFTER A SETTLE — the first shipped restore had neither and did nothing at all in flight** (live iFly 737 MAX8, 2026-09-20). Written back to back by `SetCameraView`, the TYPE write is REFUSED while the INDEX write applies: a single calculator write of type 1 / index 7 from instrument view 0 settled at type 2 / index 7, i.e. an instrument view the pilot never chose. Spaced as separate round-trips the identical pair restores the pilot's cabin view and still reads back 1.5 s later. Worse, the refused write READS BACK AS SUCCESS for under ~150 ms, so the immediate verify poll matched the transient, `RestoreAsync` returned true and NOTHING was announced — a pilot left on the instrument view in silence, which is the whole failure the verification exists to prevent. So the restore writes the type, waits `InstrumentViewSwitcher.DefaultWriteGapMs`, writes the index, settles, polls, and then re-reads after `DefaultHoldConfirmMs` and requires it to STILL match. Never verify a camera write on its first matching poll, and never collapse the restore back onto `Set`. The ENTRY keeps its back-to-back `Set` deliberately — it moves INTO the instrument type with both registers in range, is measured working on two aircraft, and the failure is specific to LEAVING it. There is no camera world-position SimVar, so a coordinate-based restore is impossible — do not propose it. Never re-add "press Ctrl+N first" for an aircraft that has a view index, and never key a restore to one pilot's preset file. Every camera read takes its OWN request id from a rotating range of eight starting at `REQUEST_CAMERA_VIEW` (341-348, below `INDIVIDUAL_VARIABLE_BASE`; `CameraReadWaiters`), and a delivery completes only the waiter registered under ITS id — one shared request id let an abandoned read's late reply complete the NEXT read (a false "could not switch", or a stale "already there" that skipped the write and read the wrong display). A switch that never verifies says "Could not confirm the cockpit view switch; reading what is on screen.", never "could not switch": Switch and Unknown both write, so the camera may well have moved. ⚠️ Whether the app must CONFESS to having moved the camera with no way back is decided by whether a move-write was DISPATCHED (`ICameraViewIo`'s writes return bool; `InstrumentViewPlan.MovedWithNoWayBack(target, moved)`), NEVER by the entry's own `Verified` flag — that proxy was wrong in both directions. It is FALSE for a write that landed while every read-back timed out, which is exactly what `RegisterCameraViewDefinition` failing produces (it has its own catch, and `SetSimVar` builds its OWN temporary data definition, so writes keep landing while every camera read returns nothing): that combination moved the camera on every display read of the session and never restored it, in silence. And it is TRUE for a camera that was already on the wanted view, where nothing moved at all. A failed restore also PUBLISHES the view it could not reach (`CameraHome`/`CameraHomePlan`), so the next read aims there instead of at the instrument view it was stranded on — without that the strand is permanent AND silent after its one warning, because the next read reads the instrument view as "where the pilot was", returns them to it and reports success. ONE settle-then-confirm rule serves both paths (`ConfirmHeldAsync`): poll, then settle and re-read and require it to STILL agree — never verify a camera write on its first matching poll. The entry gets that confirm for the price of one read, because it was already spending the settle on a rendered frame; the restore no longer spends a settle before its poll at all (that was a second use of `DefaultSettleMs`, the screenshot constant, and the confirm made it redundant). ⚠️ A read that returns NOTHING is not evidence of reversion — it is a 500 ms timeout, a disconnect or an aircraft switch — so the confirm retries once and then keeps the poll's verdict; scoring it as failure is how a CORRECT restore came to announce "Could not return to your previous view." ⚠️ **SOME aircraft REFUSE a write to the view TYPE register while the index register holds a high value**, so the restore drops the index to `InstrumentViewSwitcher.NeutralViewIndex` (0) BEFORE the type write and only then writes the pilot's own index — three writes, each on its own frame. Measured live (PMDG 737-800, 2026-09-20): on instrument view index 7, writing type 1 was refused every time under a 3 s settle with no other traffic; dropping the index to 3 first made the identical write succeed. That was a live defect on EVERY PMDG 737 Alt+P/Alt+N read (its captain-panel view is index 7): the type write was refused, the camera stayed in the instrument type, and the pilot's index was written into it, sliding them to an instrument view they never chose. It is also what docs/md11.md had recorded as an unreconciled observation. ⚠️⚠️ WHY it refuses is UNKNOWN and the inviting explanation is DISPROVEN — do not restate it: the first telling said the sim validates the (type, index) pair and refuses one whose index is out of range for the target type, since `MAX:1` reads 6 there. The **Fenix A320 refutes that** (measured 2026-09-21, same sim build, also `MAX:1` = 6, also a custom pilot camera at index 7): from instrument index 7 the identical type write is ACCEPTED and lands on 1/7, and from index 8 it lands on 1/8, beyond that same ceiling. So the refusal is AIRCRAFT-SPECIFIC and index-versus-MAX does not predict it. The neutral write is kept because what it BUYS is measured on both airframes: it rescues the PMDG and costs the Fenix one extra register write. This is the second inviting explanation of a camera refusal to turn out wrong, after the `MAX` theory itself. A non-cockpit camera reads view type 0 index 0 and REFUSES a type write (measured live, PMDG 737-800, 2026-09-20, `CAMERA STATE` 3 and 6), which is why `IsAt` not consulting the state cannot let an external camera pass for a cockpit one. → [gemini.md](../gemini.md)

## AI-4

- Never reinstate a silent multi-model fallback for Gemini calls — the model used must be exactly `UserSettings.GeminiModel`; a silent fallback hides which model produced a response (explicitly rejected by the user). → [gemini.md](../gemini.md)

## AI-5

- Do NOT send `thinkingConfig`/`thinkingBudget` to Gemini — `thinkingBudget` is deprecated/invalid on Gemini 3.x models (`thinking_level` is used instead) and can error if both are set. → [gemini.md](../gemini.md)

## AI-6

- The Gemini HTTP timeout catch must NOT gate on `ex.CancellationToken.IsCancellationRequested` (false on a modern .NET HttpClient timeout) — catch `TaskCanceledException` as the timeout instead. → [gemini.md](../gemini.md)
