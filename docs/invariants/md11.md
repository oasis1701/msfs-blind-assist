# TFDi MD-11 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/md11.md`, which Claude Code loads when it reads matching code. Background: [md11.md](../md11.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## MD11-1

- Every control write is a CEVENT through `Md11EventBus` with the `{seq} 0 *` prefix; never `SetLVar` a control var. `TDMD11.TRIGGER_EVENT` coalesces identical repeats exactly like CEVENT without the prefix — it is not a better channel. Exactly three writes bypass CEVENT, all through `Md11EventBus.WriteExternal` (seq-prefixed, calc path), and the set is CLOSED: the `MD11_EXTCTL_*` command inboxes TFDi designed for external control; the Dial-A-Flap thumbwheel's own backing var `MD11_DIALAFLAP_WHEEL_RNG` (`Md11FlapSystem.SetDialRawAsync` — a CEVENT walk of up to ~90 clicks jams the wheel at an end stop, proven live, so never put it back on the walk); and the walk's direct-write fallback (`TryDirectSetAsync`, reached only after a closed-loop walk failed), gated by `Md11DirectSet.Refuse` so it can write ONLY the var the control's own registered definition reads back and never a control in `Md11DirectSet.FallbackNeverWrites` — the speedbrake lever (its row reads `MD11_SPDBRK_RNG` while the map's state var is `MD11_SPDBRK_HANDLE`, the ground-spoiler pull; a detent written there blanked the Ground spoilers row), the flap lever (`MD11_FLAP_RNG` is ASSUMED to be the handle's animation — unmeasured, refused because refusing is the safe direction; md11.md §8 carries the probe that settles it) and the gear switch (`MD11_MIP_GEAR_SW` is the lever's 0-25 travel). Add to that list, never loosen the gate. The name half catches only a definition RE-POINTED off the map's state var: a state var that is the wrong QUANTITY under its own name is invisible to it (the EFIS minimums caps read the minimums VALUE), and such a row must be kept off the walk — `Md11ExportBacked` refuses export-backed rows at the top of `SetControl` — or added to the list. The sanctioned `MD11_EXTCTL_FLAP_HANDLE`/`SPOILER_HANDLE` inboxes are referenced nowhere and stay UNVERIFIED until probed in sim. → [md11.md](../md11.md)

## MD11-2

- A control's spoken state is composed by `Md11ControlState.Compose` in a fixed order — lit legends, then the PROVEN latch, then "unpowered", then the dark meaning. A lit legend always outranks the latch; **dark is never "normal" without the DC gate**, and that gate is TWO vars, never the voltage alone: `MD11_DC_BUS_VOLTAGE` ≥ 20 V **AND** `MD11_OVHD_ELEC_DC1_BUS_OFF_LT` dark. On the BATTERY ALONE the main bus already reads 24 V while the DC busses feeding the systems annunciators are dead — measured live: DC1/AC1 OFF lit, but `FUEL_TANK_1_PUMP_OFF_LT`, `HYD_EDP_1_L_OFF_LT` and `GEN1_OFF_LT` all 0 — so a volts-only gate composed "Tank 1 Fuel Pumps: On" for a pump that was off. No stock var separates the two states (`ELECTRICAL GENALT BUS VOLTAGE:1` reads 0 on external power too), so the gate uses the lamp the aircraft itself lights; a DC1 value not yet delivered counts as UNPOWERED. Cold and dark every lamp reads 0, `BATT_OFF_LT` included. → [md11.md](../md11.md)

## MD11-3

- A button's own L:var is a position ONLY where proven — TFDi's tooltip reads it, or a live probe did (the battery). External power, generators and the nav lights hold nothing useful there. Extend `LATCH_FIXED` only from a before/after probe. → [md11.md](../md11.md)

## MD11-4

- `state` blocks, lamp pairings, names and label repairs are GENERATED (`tools/md11-gen`) — regenerate `md11_control_map.json`, never hand-edit it or patch C#. One lamp node per L:var: two lamps on one var are two continuous batch entries with one Name, and which node survives is decided by rule (the node named after the var), never by file order. A tooltip label that reads an airframe variant flag has one wording per variant, so the generator REFUSES it until `LABEL_FIXES` names the control — never let a variant word become a label or a position. → [md11.md](../md11.md)

## MD11-5

- A position control whose `state_var` is one of the map's read-only `export_vars` (the FCP mode knobs reading `MD11_AP_HDG_TRK`/`IAS_MACH`/`VS_FPA`, the EFIS minimums caps reading `MD11_CAP/FO_MINIMUMS`) is a READ-ONLY ROW, never a walkable combo, and `SetControl` refuses it (`Md11ExportBacked`): its wheel turns the VALUE, not the mode, so a walk stalls and the direct-write fallback raw-writes the export (measured: the captain's minimums zeroed). The mode is switched by its own button beside the row. The generator lifts a trailing `%{if}A%{else}B%{end}` as positions only when the expression reads ONE L:var — the minimums caps' tooltips read a companion var for the Baro/Radio word, which belongs to the mode switch. That rule strips a `value_map` from FOUR controls, not two: also `MD11_OVHD_PNEU_ECON_BT`/`TRIM_AIR_BT`, whose nested tooltips name two vars and whose maps nothing consumed (a button never reads `values`; their `state` blocks are unchanged) — deliberate, and pinned by `CompanionVarTests`. → [md11.md](../md11.md)

## MD11-6

- A guard cover's `state_var` is its OWN node id, never the L:var its tooltip reads — four covers' tooltips (Fuel Dump, Fuel Dump Emergency Stop, Center Gear Uplock, Main Cargo Door Arm) read the control UNDER them, and keyed on that the auto-open read "button off" as "cover closed" and lowered an open cover onto the press. `finalize_controls` pins it; never re-key a guard in C# or by per-guard curation. → [md11.md](../md11.md)

## MD11-7

- `Md11PanelLayout` is the ONLY source of panel order; an unlisted control is appended, never dropped, and `Md11PanelLayoutTests` pins that the shipped map needs no fallback panel. A guard cover is a row ONLY where the transparent auto-open cannot lift it (`IsAutoOpenedGuard`), and there it still sits immediately before its control. `EnsureGuardOpenAsync` runs from the ACTUATION of the control underneath, so wherever an operable control names the guard in its `guard_id` the cover is read, lifted and settled without the pilot touching it — a row there is a second control for something already done, and one a pilot can leave in the wrong position. THREE keep theirs today — the engine fire handles, whose only namer `SetControl` refuses (read-only composites). The rule allows a second cause, a guard NO control names, and that shape no longer occurs: EVAC, GPWS and the Main Cargo Door arm are guarded in the aircraft but TFDi's XML declares no `GUARD_ID` for them, so nothing triggered an auto-open and MSFSBA's walk went out against a CLOSED cover, moved nothing, and blamed "guarded, unpowered, or inhibited". MEASURED before curating them (2026-09-18): the GPWS cover reads 0 on a loaded aircraft, the switch's own LEFT_BUTTON_DOWN moves nothing with it closed, the guard's event lifts it (0 → 1), and the same switch event then steps the switch normally — all three positions latching, so the switch itself was never at fault. The generator NEVER infers a link (it reads `fields.get("GUARD_ID")`), so those three come from `CURATED_GUARDS` and are indistinguishable downstream from a declared one. Both causes are read off the MAP, so the rule self-maintains: make a refused control operable, or link a future cover, and its row disappears with no edit here. Dropping the ROW must never drop the VARIABLE — the auto-open READS the guard through `ReadFreshAsync`, and registration walks the control map, not the panels (pinned). A lamp is a Status Display row (`Md11Placement.Displays` → `GetPanelDisplayVariables`, words from `Md11StatusRow`), never a control row or a tab stop; the MCDU keys, the transponder keypad and the six radio frequency TUNER knobs are superseded by the app's own UI (`IsSuperseded`) and are never rows — the tuners are rotary ENCODERS whose L:var is a SIGNED CLICK COUNTER, not a position (measured live: 0 on a loaded aircraft with COM1 standby already on 135.100, 0→1→2→3 on three WHEEL_UPs, back to 2 on a WHEEL_DOWN), so with an empty value map they rendered as read-only rows a pilot could not operate showing an odometer that reads 0 on every load; tuning is the typed standby field and the transfer button (`Md11Radios.PanelKeys`); no two rows in one panel, control or display, share a spoken name. → [md11.md](../md11.md)

## MD11-8

- A walked control's state var is CONSUMED by `ProcessSimVarUpdate` while its `DebouncedWalk` is registered (`_walkCts`) and force-read ONCE when the walk ends — never let a forced read reach MainForm's combo refresh mid-walk (NVDA narrates every intermediate position). The walker reads an individual-def var through `SimConnectManager.ReadFreshAsync` (completes on delivery — the answer to the read's OWN request id, issued from `SimConnectManager.FreshRequestIdBase`, never an abandoned earlier read's late answer and never a panel's ONCE under the data-definition id; a var on its own periodic subscription or in the batch is answered by its next sample; poll 80 ms, cap 1200 ms) and judges polarity by DIRECTION, persisting it in `Md11InvertedStepControls`; a first no-movement AT AN END STOP probes the OTHER event once before giving up — EXCEPT on a HANDLE (`Md11Kinds.Handle`), which never gets the probe at any index: on a two-position control every index is an end stop, and a fire handle's walked axis is the bottle discharge — and a mid-range stall gives up at once, because a probe there would actuate the control the wrong way. The flap lever and speedbrake stream on their own SIM_FRAME + CHANGED subscription, so their fresh read is the CACHE — `ReadFreshAsync` hands it back at once, because a PERIOD.ONCE on the SAME request id would replace the subscription and an unchanged value never delivers (`FreshReadPolicy`, pinned by `FreshReadPolicyTests`). ⚠️ That cache is only as good as the subscription's INITIAL delivery, which live sessions never received (2026-09-09 and again 2026-09-10 on the hardened build: the speedbrake lever's subscription set up three times, never once delivered, every walk "state var unreadable", "did not move" spoken for a lever nothing had touched, and with the direct-write fallback now rightly refused for it, nothing reached the aircraft at all). The APP threw it away: `Connect()` runs `SetupDataDefinitions()` — whose `StartContinuousMonitoring` pumps `DoEvents` — BEFORE `SetupEvents()` attaches `OnRecvSimobjectData`, so every answer landing in that pump is drained (the GSX COUATL note's drain). So every SIM_FRAME own subscription is SEEDED by a ONCE on a fixed per-var seed id (`FreshReadPolicy.SeedRequestId`, def id + 900000, mapped back to its definition id by `FreshReadPolicy.DataDefinitionIdOf` — no seed map) once the handler exists (`SeedSimFrameSubscriptions`: after `SetupEvents()` on a connect, after an aircraft switch's re-registration) and by any `RequestVariable` that finds the cache empty or is forced (a panel open, the walk-end refresh); a seed answers NO waiter, it only fills the cache. When the cache is still EMPTY, `ReadFreshAsync` falls through and asks under the read's OWN fresh id (a ONCE on a separate id delivers within a frame and leaves the subscription alive, measured live, while re-issuing the subscription's own id delivers nothing new). Never "simplify" either onto the subscription's id. `debug.log` writes `First delivery for <key>` once per cache lifetime for every SIM_FRAME var, naming the path that supplied it (subscription / seed read / fresh read) — written near connect, so a long session's rotated log may no longer hold it (its absence proves nothing alone), and it records nothing about later subscription samples; only a var that answers with the next 1 Hz delivery (batch-covered, or a PERIOD.SECOND own subscription) keeps the legacy cache-poll protocol, and no walked MD-11 control is one. A control with ONE click event (TFDi's single-click template — 25 today: IRS, fuel, starters, parking brake, gear lever, QNH/QFE, minimums, transponder mode switches, AFS overrides, cargo vents, EVAC horn, cargo-door arm, the thunderstorm dome light, the ADG lever) TOGGLES — `ToggleCoreAsync` clicks once when a DELIVERED fresh read differs from the target, refuses when no delivery arrives (`requireDelivery`), never touches polarity, and is not offered to a var without fresh reads; every click and its no-movement deadline are stamped at the bus's expected WRITE time (`Md11EventBus.Pending` × `MinGapMs`), never at enqueue. → [md11.md](../md11.md)

## MD11-9

- Every spoken read-back verdict (ground spoilers, COM tune/transfer, typed minimums, the direct-set 'held' check, the press feedback's latch, the guard decision, Ctrl+B's altimeters) reads through `SimConnectManager.ReadFreshAsync` — never a fixed sleep and the cache. A forced read of a batch-covered key is honoured only by the NEXT 1 Hz delivery, so a sleep-then-read-the-cache verdict judged a click the aircraft had taken as "Ground spoilers did not arm." — and the pull's own 'Ground spoilers armed' is echo-suppressed for 3 s after the pick, so that false failure was the only thing the pilot heard. A verdict is spoken only on a DELIVERED value: no delivery is silence plus a debug.log line. A read-back that follows a click QUEUED on the bus also waits from the click's expected WRITE (`Md11EventBus.ReadBackDelayMs`, settle + `Pending` × `MinGapMs`) — the walker's rule generalised, worth ~120 ms on today's paths, not the fix. Ceilings are per var class: `BatchReadBackTimeoutMs` (2500) for a batch key, the walker's `FreshReadTimeoutMs` (1200) for an individual-def one, and `GuardReadTimeoutMs` (300) for the guard's two reads and the press feedback's latch — those sit on an actuation's path, and the guarded press's whole chain (idle queue: 300+250+1200+300 = 2050 ms) must finish inside `Md11AnnouncementGate.EchoWindowMs` or the press's own lamp echo is spoken beside the feedback. That chain absorbs the backlog TWICE — `EnsureGuardOpenAsync`'s cover settle and the feedback's lamp settle — and `Pending` × `MinGapMs` is bounded only by the 256-id queue, so NO fixed sum can budget for it (behind an MCDU scratchpad send, ~1.4 s, the old unclamped arithmetic reached 4930 ms and doubled the sentence). The constraint is a DEADLINE: `TFDiMD11Definition.FeedbackDelayMs` takes the smaller of the settle-from-the-write and what the window has left (`Md11AnnouncementGate.RemainingFeedbackBudgetMs`, less a 400 ms reserve for the latch read), so an idle queue is untruncated and a burst makes the feedback read EARLY — the safe direction, since a lamp landing later with a different text is the correction. NEVER clamp the guard's own settle instead: that one paces two writes at the aircraft, and shortening it is how a covered control fails to actuate at all. Both terms are pinned by `Md11AnnouncementGateTests`; a timed-out guard read actuates UNGATED, exactly as an unreadable state always did. The settles that remain (ArmSettleMs 700, ComTuneSettleMs 1500, the 600 ms ANIM_LAG, GuardOpenSettleMs 250, the one EXTCTL-inbox allowance `Md11Fcp.VerifyAfterMs` 1200 shared by minimums and altimeters) are the aircraft's apply/animation time, unmeasured and therefore KEPT — never re-add batch-phase padding, and cut one only from the `… read-back:` timing lines in debug.log. The guard's log-only re-read is fire-and-forget, off the actuation's path. → [md11.md](../md11.md)

## MD11-11

- A lamp change speaks its OWNER's composed state; a press is confirmed once after settle and its own lamp echo is swallowed until that confirmation speaks, at most 2.5 s — `Md11AnnouncementGate.Feedback` CLOSES the echo window, because a guarded press spends 550 ms lifting its cover and its lamp routinely lands after the feedback has read the stale state, so a later lamp with a DIFFERENT text is the correction and must be spoken (the same text is still deduped). A lamp going DARK is never spoken on the spot: silent outright when the aircraft is already unpowered, otherwise deferred `DarkSettleMs` (1500 ms) and re-decided from what is true THEN (`SpeakDarkTransition`) — the 528 batch-covered variables (488 of them lamps) ride two SimConnect batches and the gate's DC1 lamp is in batch 1 while the HYD/PNEU lamps are in batch 2, so at shutdown a lamp can go dark a beat before the gate learns the busses died, and the old code narrated the whole panel losing power one control at a time. LIT transitions still speak immediately. Every lamp update is consumed in `ProcessSimVarUpdate`, so Ctrl+M only works through MainForm's `Suppressed` wrap — and the MD-11's own monitor form honours `ExcludeFromMonitorManager`, so that flag must mean "muted by plumbing" and never sit on a var that really speaks. → [md11.md](../md11.md)

## MD11-12

## MD11-13

- Stepper option lists come from the FIRST React fiber on the disabled input carrying an `options` array (`__reactFiber$…` → `memoizedProps.options`) — never hand-list them, and never walk PAST an empty array to keep looking: the EFB mounts its `Select` with an empty list before the list exists, and the next fiber up is an unrelated ancestor whose `options` would be offered as this field's choices. The fallback is the static value (`(empty)` when the field is blank) plus the "Runway previous (now …)" / "Runway next (now …)" arrows. A press is applied by React on the NEXT tick (live: the value read inline after a press was still the old one), so `A.stepTo` presses-waits-rereads and must never become a synchronous loop. **A press is the pointer/mouse sequence plus `el.click()` and NOTHING ELSE** — that is ONE click event, which React's `onClick` runs exactly once; the synthetic bubbling `click` MouseEvent dispatched alongside it until 2026-09-06 ran every handler TWICE, and was invisible only because this EFB's handlers close over state captured at render (a door tile toggles to the state it captured, so twice lands where once does). ⚠️ The "one call = one step on the Autobrake stepper" note dated 2026-09-05 was measured WITH that double dispatch and does not carry over — re-measured 2026-09-06 on the ground at UCFM instead: the Thrust Setting stepper walked FLEX → TO1 (two presses) and back with `el.click()` alone, a Weight Units dropdown set applied both ways, Save produced the spoken toast, and after one full scrape the next scrapes answered `unchanged:true` on the live page. `clickElement`/`setValue` REFUSE a target inside a `pointer-events-none` wrapper (`A.isInert`, sharing `A.isInertRoot` with the walk's dimming so the two cannot drift): that class blocks real hit-testing only, the EFB's door/GPU/state handlers have no ground check of their own, and the shell's native-list fallback reaches the reader by exactly that path — so without the refusal the reader opens a cargo door in the cruise. That fallback (`FbwEfbForm.CreateControlFor`, the WebView2-failed list mode) honours `Disabled` as the browser shell does: the control stays focusable, its label gains ", dimmed", and activating it says "Unavailable" without posting — never a WinForms `Enabled = false`, which drops it from the tab order. The two renderings are not word-for-word identical and the comment on `DimmedSuffix` says so: the shell appends ", dimmed" to BUTTONS and LINKS only and leaves a checkbox, select or field to the native disabled attribute a browser reader already announces, while list mode appends it to every control, because a WinForms control kept in the tab order carries no such attribute. `scrape()` DISCONNECTS the MutationObserver around `collect()` and re-observes in a `finally` (plus a forced full scrape every 10th poll): `collect()` stamps and clears attributes inside the observed subtree, so a permanently-armed `attributes:true` observer re-armed `_dirty` from the reader's OWN bookkeeping as a microtask after every scrape and `unchanged:true` could never fire — a full traversal every ~400-600 ms poll, ~100 KB of it on the OFP page. A harness test for that gate MUST await a tick between the two scrapes or no MutationRecord is delivered and it passes either way. The reconcile key is EXPLICIT where a label carries changing state: every element this reader emits whose label changes with state — the Services tile (`tile:<name>`), the State tile's action button (`tile-action:<name>`), the stepper arrows and value line (`step-prev:` / `step-next:` / `step-value:<field>`) and the read-outs (`readout:<caption>`) — carries a stable `key` (agent → `EFBElement` → page JSON, and in `CoherentPmdgEfbClient.ElementsSignature`, the push hash), and the shell's `keyOf` prefers it (`rk(it) + '|k:' + key`) over the text key; without it every flip was a new key and the node the pilot had just pressed was rebuilt under their focus with its new label never spoken. The shared `baseLabel` is back to exactly its pre-#189 rules (the parenthesised state suffixes and `: placed`/`: not placed`): the two text heuristics #189 added — strip `(now …)`, strip any after-colon tail — are gone, because the colon rule collapsed the flyPad ATC page's "UNICOM 122.800: Set Active" / "…: Set Standby" (and the State page's "Ready to Fly" / "Ready to Fly: Set as default") onto one key held apart only by DOM position. Never re-add a text heuristic to the SHARED shell for one reader — stamp a `key` in the reader. When the EFB swaps "Set as default" for its check mark, the reader keeps a BUTTON under the same key ("Ready to Fly is the default", `announceChange`); a press on it is refused (`clickElement` finds no stamped node), never passed to the EFB's check mark. → [md11.md](../md11.md) (Split 2026-10 from one bullet, words unchanged: its post-press announce sentences are now MD11-26.)

## MD11-14

- Test buttons are hold-to-test: `Md11TestButtons` holds ELEVEN of them 3 s through `Md11EventBus.PressAndHoldAsync` (their lights are on only while held; a 60 ms tap ends before the 1 Hz lamp batch sees them); the weather radar TEST mode is a selection and is never held; `MD11_AOVHD_FIRETEST_BT` tests every loop and is labelled "Engine and APU Fire Test" from TFDi's Systems Guide, not the tooltip's "APU Fire Test". The ANNUNCIATOR LIGHT TEST is deliberately NOT held and must not be added back — a hold lights all ~488 annunciators at once and `HandleLampUpdate` would speak a composed sentence for every one of them on the lit edge and again on the deferred dark edge, burying everything else; it stays a tap, and a hold under a lamp-speech mute ending in one summary sentence is the recorded follow-up. **Disposal releases the hold, UPs first:** `PressAndHoldAsync` registers the UP it owes and queues the DOWN under the held table's OWN LOCK — one atomic step, and the release path mirrors it — only when BOTH ids exist (a control with NO DOWN writes nothing at all: a button that was never pressed cannot be released; a hold that starts after disposal writes neither half), and the pump records under that same lock when it WRITES a DOWN a registered hold owns. `Md11EventBus.Dispose` stops accepting and stops the pump FIRST: it cancels the pump, takes off it, in order, everything it had not yet taken — under `_takeLock`, the lock the pump holds around its own take, so no id is stranded between the two or written out of order; the pump holds that lock through its wait, so this take MUST follow the cancel or it hangs the UI thread — and waits up to `PumpStopTimeoutMs` (500 ms) for the one write it may have in hand. A pump still stuck in a write past that gets NOTHING written beside it (a second writer would interleave on the one CEVENT slot): its queued ids and owed UPs are logged as discarded — the residual a hung channel always had. Otherwise, on the calling thread, it writes the UP of every hold whose DOWN was written — still held, or already ended with its release queued (a release is queued carrying its hold), once per button — the first thing written, so a 3 s test button is released at once however long the backlog (an UP fired onto the TAIL of the paced FIFO was dropped behind an MCDU scratchpad send's 48 ids when the drain bound ran out); drops every held DOWN still queued (never written, so nothing is owed) together with its UP; and drains the rest IN ORDER, paced, within `DrainTimeoutMs` (1000 ms). Disposal runs on the UI thread, so it is bounded at 500 + 1000 ms in all. An UP never precedes its own DOWN. The atomicity is what CLOSES the guarded test button's pool-thread race: registering and firing as two steps left a window in which `Dispose` swept a table that did not yet owe this UP and then let the DOWN through, and the mirror window let the queue drop an UP the sweep had already declined to fire — both leave the button held in the aircraft. Cancelling the pump before writing what was owed, as it once did, discarded every queued id and left a test button held in the aircraft whenever the MD-11 was re-selected from the Aircraft menu inside the 3 s hold (a manual switch disposes the definition with the MD-11 still loaded; on the auto-detect path the MD-11 is gone and an inert `L:CEVENT` write lands on an airframe that never reads it — no airframe this app supports reads `L:CEVENT`, checked against the FBW/PMDG/HS787/iFly/A380 defs 2026-09). The definition's `Dispose` also cancels every walk in flight (`CancelWalks` → `Md11WalkCancellation.CancelAll`, tolerant of a source the walk's own finally disposed a moment earlier) so none speaks "did not move" against the aircraft that follows. **Accepted residual, narrowed:** a SimConnect drop inside the hold still loses the UP — there is no channel to send one over, and the definition is not disposed on a drop. App exit is covered exactly when `MainForm.OnFormClosing` disposes the definition before `Disconnect()` (the exit-time disposal parity with the PMDG EFB clients): the same drain-and-release runs there, which is why it must stay bounded (recorded in md11.md §10). → [md11.md](../md11.md)

## MD11-16

- The three altimeter STD rows press a baro knob's PUSH over CEVENT (`PressControlEvents`), never a new direct write — the `WriteExternal` set stays closed. **EVERY MD-11 write path refuses ALOUD when it cannot reach the aircraft** — presses, held test buttons, walks and their direct-set fallback, the EXTCTL inboxes (`SetFcpValue`, minimums, the V/S engage), the Dial-A-Flap wheel write, the STD toggles, the ground-spoiler arm, the squawk keypad and the COM tuning — swept as one family on 2026-09-12 after three of them were found one at a time. TWO predicates, and a caller must ask the one matching its OWN transport: `SimConnectManager.CalcWriteCanLand` for anything on the CEVENT/calc bus, `CanSendEvent` for a stock SimConnect event (COM tuning needs no MobiFlight module). **Never the bare `CanExecuteCalculatorCode`** — that is what `ExecuteCalculatorCode` guards ITSELF with, and it is TRUE in a session with no WASM module installed (`mobiFlightWasm` is constructed unconditionally in `Connect()`; the same trap `IsMobiFlightConnected` carries), which is precisely the configuration where every calc write is discarded. `CalcWriteCanLand` adds the only end-to-end evidence there is, the bridge probe: it refuses when the probe has CONCLUDED and did not verify, and stays permissive while it is still PENDING, because refusing a write that would have succeeded is worse than the gap it closes (that window is ~40 × 1.5 s ≈ a MINUTE after detection, not seconds — writes made in it are still discarded silently, the accepted trade). **The verdict is per CONNECTION, not per aircraft, so a NEGATIVE one MUST be re-armed on every aircraft switch and a VERIFIED one MUST be kept** (`MainForm.ArmBridgeProbe` via `CalcPathVerdict.ShouldRearmOnAircraftSwitch`, called by both the probe timer and `SwitchAircraft` — a switch never disconnects, so `IsFullyConnected` never drops and the timer's own re-arm cannot see it).
