# TFDi MD-11 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/md11.md`, which Claude Code loads when it reads matching code. Background: [md11.md](../md11.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## MD11-3

- A button's own L:var is a position ONLY where proven — TFDi's tooltip reads it, or a live probe did (the battery). External power, generators and the nav lights hold nothing useful there. Extend `LATCH_FIXED` only from a before/after probe. → [md11.md](../md11.md)

## MD11-4

- `state` blocks, lamp pairings, names and label repairs are GENERATED (`tools/md11-gen`) — regenerate `md11_control_map.json`, never hand-edit it or patch C#. One lamp node per L:var: two lamps on one var are two continuous batch entries with one Name, and which node survives is decided by rule (the node named after the var), never by file order. A tooltip label that reads an airframe variant flag has one wording per variant, so the generator REFUSES it until `LABEL_FIXES` names the control — never let a variant word become a label or a position. → [md11.md](../md11.md)

## MD11-5

- A position control whose `state_var` is one of the map's read-only `export_vars` (the FCP mode knobs reading `MD11_AP_HDG_TRK`/`IAS_MACH`/`VS_FPA`, the EFIS minimums caps reading `MD11_CAP/FO_MINIMUMS`) is a READ-ONLY ROW, never a walkable combo, and `SetControl` refuses it (`Md11ExportBacked`): its wheel turns the VALUE, not the mode, so a walk stalls and the direct-write fallback raw-writes the export (measured: the captain's minimums zeroed). The mode is switched by its own button beside the row. The generator lifts a trailing `%{if}A%{else}B%{end}` as positions only when the expression reads ONE L:var — the minimums caps' tooltips read a companion var for the Baro/Radio word, which belongs to the mode switch. That rule strips a `value_map` from FOUR controls, not two: also `MD11_OVHD_PNEU_ECON_BT`/`TRIM_AIR_BT`, whose nested tooltips name two vars and whose maps nothing consumed (a button never reads `values`; their `state` blocks are unchanged) — deliberate, and pinned by `CompanionVarTests`. → [md11.md](../md11.md)

## MD11-6

- A guard cover's `state_var` is its OWN node id, never the L:var its tooltip reads — four covers' tooltips (Fuel Dump, Fuel Dump Emergency Stop, Center Gear Uplock, Main Cargo Door Arm) read the control UNDER them, and keyed on that the auto-open read "button off" as "cover closed" and lowered an open cover onto the press. `finalize_controls` pins it; never re-key a guard in C# or by per-guard curation. → [md11.md](../md11.md)

## MD11-7

- `Md11PanelLayout` is the ONLY source of panel order; an unlisted control is appended, never dropped, and `Md11PanelLayoutTests` pins that the shipped map needs no fallback panel. A guard cover is a row ONLY where the transparent auto-open cannot lift it (`IsAutoOpenedGuard`), and there it still sits immediately before its control. `EnsureGuardOpenAsync` runs from the ACTUATION of the control underneath, so wherever an operable control names the guard in its `guard_id` the cover is read, lifted and settled without the pilot touching it — a row there is a second control for something already done, and one a pilot can leave in the wrong position. THREE keep theirs today — the engine fire handles, whose only namer `SetControl` refuses (read-only composites). The rule allows a second cause, a guard NO control names, and that shape no longer occurs: EVAC, GPWS and the Main Cargo Door arm are guarded in the aircraft but TFDi's XML declares no `GUARD_ID` for them, so nothing triggered an auto-open and MSFSBA's walk went out against a CLOSED cover, moved nothing, and blamed "guarded, unpowered, or inhibited". MEASURED before curating them (2026-09-18): the GPWS cover reads 0 on a loaded aircraft, the switch's own LEFT_BUTTON_DOWN moves nothing with it closed, the guard's event lifts it (0 → 1), and the same switch event then steps the switch normally — all three positions latching, so the switch itself was never at fault. The generator NEVER infers a link (it reads `fields.get("GUARD_ID")`), so those three come from `CURATED_GUARDS` and are indistinguishable downstream from a declared one. Both causes are read off the MAP, so the rule self-maintains: make a refused control operable, or link a future cover, and its row disappears with no edit here. Dropping the ROW must never drop the VARIABLE — the auto-open READS the guard through `ReadFreshAsync`, and registration walks the control map, not the panels (pinned). A lamp is a Status Display row (`Md11Placement.Displays` → `GetPanelDisplayVariables`, words from `Md11StatusRow`), never a control row or a tab stop; the MCDU keys, the transponder keypad and the six radio frequency TUNER knobs are superseded by the app's own UI (`IsSuperseded`) and are never rows — the tuners are rotary ENCODERS whose L:var is a SIGNED CLICK COUNTER, not a position (measured live: 0 on a loaded aircraft with COM1 standby already on 135.100, 0→1→2→3 on three WHEEL_UPs, back to 2 on a WHEEL_DOWN), so with an empty value map they rendered as read-only rows a pilot could not operate showing an odometer that reads 0 on every load; tuning is the typed standby field and the transfer button (`Md11Radios.PanelKeys`); no two rows in one panel, control or display, share a spoken name. → [md11.md](../md11.md)

## MD11-12

- The EFB reader (`coherent-md11-efb-agent.js`) recognises the EFB's building blocks by DOM STRUCTURE (`A.BLOCKS`, first match owns the subtree), with colour only as the selected-state cue — never key a block on a Tailwind class alone, and never let a disabled `input` become an edit field (it is a read-out). Every block is pinned in `tools/md11-efb-test` (jsdom, run in CI); a live capture goes through `tools/coherent.ps1 capture`, stripped of `data-md11-efb-*`/`data-color`/`data-bg` and of the SimBrief username. → [md11.md](../md11.md)

## MD11-13

- Stepper option lists come from the FIRST React fiber on the disabled input carrying an `options` array (`__reactFiber$…` → `memoizedProps.options`) — never hand-list them, and never walk PAST an empty array to keep looking: the EFB mounts its `Select` with an empty list before the list exists, and the next fiber up is an unrelated ancestor whose `options` would be offered as this field's choices. The fallback is the static value (`(empty)` when the field is blank) plus the "Runway previous (now …)" / "Runway next (now …)" arrows. A press is applied by React on the NEXT tick (live: the value read inline after a press was still the old one), so `A.stepTo` presses-waits-rereads and must never become a synchronous loop. **A press is the pointer/mouse sequence plus `el.click()` and NOTHING ELSE** — that is ONE click event, which React's `onClick` runs exactly once; the synthetic bubbling `click` MouseEvent dispatched alongside it until 2026-09-06 ran every handler TWICE, and was invisible only because this EFB's handlers close over state captured at render (a door tile toggles to the state it captured, so twice lands where once does). ⚠️ The "one call = one step on the Autobrake stepper" note dated 2026-09-05 was measured WITH that double dispatch and does not carry over — re-measured 2026-09-06 on the ground at UCFM instead: the Thrust Setting stepper walked FLEX → TO1 (two presses) and back with `el.click()` alone, a Weight Units dropdown set applied both ways, Save produced the spoken toast, and after one full scrape the next scrapes answered `unchanged:true` on the live page. `clickElement`/`setValue` REFUSE a target inside a `pointer-events-none` wrapper (`A.isInert`, sharing `A.isInertRoot` with the walk's dimming so the two cannot drift): that class blocks real hit-testing only, the EFB's door/GPU/state handlers have no ground check of their own, and the shell's native-list fallback reaches the reader by exactly that path — so without the refusal the reader opens a cargo door in the cruise. That fallback (`FbwEfbForm.CreateControlFor`, the WebView2-failed list mode) honours `Disabled` as the browser shell does: the control stays focusable, its label gains ", dimmed", and activating it says "Unavailable" without posting — never a WinForms `Enabled = false`, which drops it from the tab order. The two renderings are not word-for-word identical and the comment on `DimmedSuffix` says so: the shell appends ", dimmed" to BUTTONS and LINKS only and leaves a checkbox, select or field to the native disabled attribute a browser reader already announces, while list mode appends it to every control, because a WinForms control kept in the tab order carries no such attribute. `scrape()` DISCONNECTS the MutationObserver around `collect()` and re-observes in a `finally` (plus a forced full scrape every 10th poll): `collect()` stamps and clears attributes inside the observed subtree, so a permanently-armed `attributes:true` observer re-armed `_dirty` from the reader's OWN bookkeeping as a microtask after every scrape and `unchanged:true` could never fire — a full traversal every ~400-600 ms poll, ~100 KB of it on the OFP page. A harness test for that gate MUST await a tick between the two scrapes or no MutationRecord is delivered and it passes either way. The reconcile key is EXPLICIT where a label carries changing state: every element this reader emits whose label changes with state — the Services tile (`tile:<name>`), the State tile's action button (`tile-action:<name>`), the stepper arrows and value line (`step-prev:` / `step-next:` / `step-value:<field>`) and the read-outs (`readout:<caption>`) — carries a stable `key` (agent → `EFBElement` → page JSON, and in `CoherentPmdgEfbClient.ElementsSignature`, the push hash), and the shell's `keyOf` prefers it (`rk(it) + '|k:' + key`) over the text key; without it every flip was a new key and the node the pilot had just pressed was rebuilt under their focus with its new label never spoken. The shared `baseLabel` is back to exactly its pre-#189 rules (the parenthesised state suffixes and `: placed`/`: not placed`): the two text heuristics #189 added — strip `(now …)`, strip any after-colon tail — are gone, because the colon rule collapsed the flyPad ATC page's "UNICOM 122.800: Set Active" / "…: Set Standby" (and the State page's "Ready to Fly" / "Ready to Fly: Set as default") onto one key held apart only by DOM position. Never re-add a text heuristic to the SHARED shell for one reader — stamp a `key` in the reader. When the EFB swaps "Set as default" for its check mark, the reader keeps a BUTTON under the same key ("Ready to Fly is the default", `announceChange`); a press on it is refused (`clickElement` finds no stamped node), never passed to the EFB's check mark. → [md11.md](../md11.md) (Split 2026-10 from one bullet, words unchanged: its post-press announce sentences are now MD11-26.)

Split out on 2026-10-09: FPD-10 (`FbwEfbForm`'s list mode keeps a disabled control focusable and dims every control), a rule of the shared EFB shell, so it lives in `flypad.md`. This text keeps it as written; it has its own section there.

## MD11-16

- The three altimeter STD rows press a baro knob's PUSH over CEVENT (`PressControlEvents`), never a new direct write — the `WriteExternal` set stays closed. **EVERY MD-11 write path refuses ALOUD when it cannot reach the aircraft** — presses, held test buttons, walks and their direct-set fallback, the EXTCTL inboxes (`SetFcpValue`, minimums, the V/S engage), the Dial-A-Flap wheel write, the STD toggles, the ground-spoiler arm, the squawk keypad and the COM tuning — swept as one family on 2026-09-12 after three of them were found one at a time. TWO predicates, and a caller must ask the one matching its OWN transport: `SimConnectManager.CalcWriteCanLand` for anything on the CEVENT/calc bus, `CanSendEvent` for a stock SimConnect event (COM tuning needs no MobiFlight module). **Never the bare `CanExecuteCalculatorCode`** — that is what `ExecuteCalculatorCode` guards ITSELF with, and it is TRUE in a session with no WASM module installed (`mobiFlightWasm` is constructed unconditionally in `Connect()`; the same trap `IsMobiFlightConnected` carries), which is precisely the configuration where every calc write is discarded. `CalcWriteCanLand` adds the only end-to-end evidence there is, the bridge probe: it refuses when the probe has CONCLUDED and did not verify, and stays permissive while it is still PENDING, because refusing a write that would have succeeded is worse than the gap it closes (that window is ~40 × 1.5 s ≈ a MINUTE after detection, not seconds — writes made in it are still discarded silently, the accepted trade). **The verdict is per CONNECTION, not per aircraft, so a NEGATIVE one MUST be re-armed on every aircraft switch and a VERIFIED one MUST be kept** (`MainForm.ArmBridgeProbe` via `CalcPathVerdict.ShouldRearmOnAircraftSwitch`, called by both the probe timer and `SwitchAircraft` — a switch never disconnects, so `IsFullyConnected` never drops and the timer's own re-arm cannot see it). What the probe establishes is that the MobiFlight WASM executes an RPN write and it LANDS — a property of the module and the connection, which a switch does not touch; the aircraft supplies only the data-def registration the read-back uses, which decides whether a verdict can be REACHED, not whether writes land once one has been. So clearing a POSITIVE verdict too bought nothing and cost a guaranteed degraded window on every Aircraft-menu switch: at least two probe ticks (1500 ms timer, read-back lagging its write by one round) in which FBW `SetLVar` falls back to the data-def write that reverts silently and every dotted A32NX FCU event is queued instead of sent, stretching to the probe's full ~60 s on a machine with no WASM module, after which `FlushPendingCalcEvents` replays a minute of queued sets at once and drops anything past the 64-entry cap. Clearing the negative one is the half that matters: a session begun on a profile that registers no `MSFSBA_BRIDGE_PROBE` target (PMDG, HS787, iFly, Fenix) concludes UNVERIFIED and SILENTLY, and that verdict standing made every MD-11 write picked from the Aircraft menu afterwards refuse "unavailable" for the rest of the connection, with the module installed and the path healthy — the same stale verdict that quietly dropped a PMDG→FBW switch's `SetLVar` to the unreliable data-def write. Pinned by `CalcPathProbeRearmTests`. The probe term must NEVER move into `ExecuteCalculatorCode` itself: the FBW defs' per-prefix catch-alls write through the calculator UNCONDITIONALLY by design, and that is what kept the A380/A32NX overhead panels alive through the ten-week probe outage. Each is the condition its own send method guards itself with, so the two can never drift. The refusal is the ONE sentence `Md11Fcp.Unavailable` owns ("Heading push unavailable", "Squawk unavailable") or the MCDU's `Md11McduKeys.UndeliverableRefusal`, over names each path owns (`Md11Squawk.Name`, `Md11SpeedbrakeSystem.ArmName`, `Md11FlapSystem.DialName`, `Md11Fcp`'s knob names) so a control is called the same thing whether it refused, did not move, or reported back. **Success stays SILENT** — the screen reader already read the pilot's own pick; only the error condition is spoken, which is what the announcement rule permits. **A refused write must leave NO false trace:** refuse BEFORE writing so no read-back is scheduled for a write that never happened (`PressStdToggle` returns before its verdict; a refused Ctrl+V engage does not schedule the value write; minimums, squawk and the ground-spoiler arm refuse before their writes), and the pilot's typed text stays in the box. Silence was not the only failure: the minimums and squawk read-backs SPOKE on an undelivered write ("… minimums set to 500 feet, the display did not report back", "Squawk 1200 entered, …"), claiming a set that never left — worse than saying nothing. `SetControl`'s gate sits LAST among its refusals, so a control-specific reason (read-only export, composite) still wins, and the walk no longer spends 1.5 s to report "did not move. It may be guarded, unpowered, or inhibited" — three causes that are all wrong when the transport is simply dead. "Captain Altimeter STD" and "First Officer Altimeter STD" are MSFSBA's own rows on the EFIS panels (`MD11_LECP_BAROSET_CAP` 86057/86058, `MD11_RECP_BAROSET_CAP` 86127/86128; the knobs' own rows stay read-only, `Md11ExportBacked`); the standby row, `MD11_MIP_ISFD_STD_BT` ("Standby Altimeter STD", labelled by the generator), is REDIRECTED to the standby baro knob's push (`MD11_MIP_ISFD_BARO_KB`, 94991/95002), because that node has no events of its own — it is the animation the push drives, so pressing it did nothing. STD itself is unreadable (`KOHLSMAN SETTING STD:1` is never driven), so a press is confirmed by the ALTIMETER VALUE it changes: the captain's through the settled `Md11AltimeterAnnouncer`, the first officer's and standby's through a settled `ReadFreshAsync` read-back spoken only on a delivered value. `L:MD11_LECP_BAROSET_BT` / `L:MD11_RECP_BAROSET_BT` / `L:MD11_MIP_ISFD_STD_BT` MIGHT be STD latches — unprobed; never read them as STD until a before/after probe says so. → [md11.md](../md11.md)

Corrected 2026-10-08: the one-line form now carries this text's ban on moving the probe term into `ExecuteCalculatorCode`, and drops "(more: see full)" to fit. Evidence: `SimConnectManager.CalcWriteCanLand`'s doc comment in `SimConnectManager.EventSend.cs`, and the FBW catch-alls' unconditional calculator writes (VAR-3).

## MD11-17

- The `MD11MCDU` ON_SET+CHANGED subscription NEVER delivers the current page — SimConnect hands it only the writes that follow it, and the aircraft writes the area only when a screen changes (measured live: nothing in 18 s on the subscription, all three pages in 22 ms from a `PERIOD.ONCE` read). `Md11McduDataManager.RequestAll` must keep the start-up ONCE snapshot beside each subscription, on a DIFFERENT request id — a request re-issued under an existing id REPLACES it, so a ONCE on the subscription's id freezes the window on its first page. The MCDU window puts the cursor back by ROW IDENTITY (`Md11McduRows.Restore`), never by index — blank label rows are dropped, so "6:" is item 12 on the F-PLN page and item 7 on MENU — and moves it to line 1's VALUE row — found by row kind and line (`Md11McduRows`), never raw index 1, a bare label row on most pages — only when the page NAME changed (`Md11McduTitle.SamePage`): MD-11 titles carry their page counter (`ACT F-PLN     1/2`), so a slew across a page boundary changes the title text on the same page. Never restore the index restore or the bare title compare the other CDU forms use. The window POLLS ONLY WHILE VISIBLE — `ShowForm` starts the 250 ms poll, `OnVisibleChanged` stops it on hide (as every sibling CDU form does; the shared scratchpad announcer rides that poll), and a re-show re-syncs SILENTLY through the same `ResyncToSelectedUnit` a unit switch uses, so nothing that changed while the window was closed is replayed: a poll left running after Escape narrated every page title, MSG lamp and scratchpad change to a window nobody had open. Because that re-sync says nothing, a first open — or a re-show onto a page the FMS moved to while hidden — puts the cursor on the TITLE row instead of line 1, so the screen reader's own focus read names the page with no app announcement; a Shift+M on an already-open window re-syncs nothing. And there is ONE `Md11McduDataManager` per SimConnect CONNECTION: `InitializePMDG` reuses the one bound to the live handle (`IsBoundTo`, then `Reset()` + `Register()` + `RequestAll()`), `DisposePMDG` never disposes it; only the END of the connection does — `Disconnect`, or the `COMException` path in `Connect`, which disposes and nulls it exactly as `Disconnect` does (the MCDU window keeps its last page; only its status line changes) — and `Register()` resumes after its last completed step on a retry (`Md11McduRegistrationSteps`) instead of re-issuing every step that had already succeeded, which added definitions again to ids already defined. A simulator CRASH reaches neither path: `ReceiveMessage` swallows its `COMException`, so `IsConnected` stays true — a pre-existing gap; never describe a crash as ending the manager. Its `Register()` latch is per instance, so a fresh manager per aircraft switch re-mapped `MD11MCDU` and re-added its three definitions under ids still carrying live subscriptions (DUPLICATE_ID / a definition changed under a live request) on every second MD-11 load. → [md11.md](../md11.md)

## MD11-21

- The MD-11's five AI display reads use instrument views 1, 3 and 4 (indices 0, 2, 3 in `Md11DisplayReads`, MEASURED on the live aircraft 2026-09-08, not read off cameras.cfg): view 1 frames the captain's PFD, ND and EAD together, view 3 the ND, EAD and SD, view 4 the forward pedestal with the standby instrument. The six DUs are ONE row (PFD, ND, EAD, SD, ND, PFD), so "upper ECAM" is the EAD and "lower ECAM" the SD beside it, never a stacked pair; Alt+S reads whatever SD page is showing (the cue buttons are in the Pedestal section), and the PFD prompt leads with the flight mode annunciator because it exists nowhere else on this aircraft (§2c). → [md11.md](../md11.md)

## MD11-24

- The three ENGINE fire handles (`MD11_AOVHD_ENG{1,2,3}FIRE_KB`) are READ-ONLY composite rows: the map's `composite` (pull words, the fully-pulled position handing over to the rotation's words — TFDi's own tooltip) is composed from BOTH vars by `Md11CompositeState`, watching exactly its two keys (never the DC power gate — a handle's position has nothing to do with power), and `SetControl` refuses them out loud ("<label> cannot be operated from this panel yet."). They once read the PULL var with the ROTATION words (a stowed handle said "Bottle 1") and walked the discharge wheel while reading the pull, so a walk never converged. Never give them a value map or put them back on the walk; explicit pull/push/rotate actions need a live-fire measurement first. The APU handle reads its own rotation var and stays a combo. The Elevator Feel knob (`MD11_OVHD_FLTCTL_ELEVFEEL_KB`) is the one other composite, behind an outer `%{if}` (D13): "Auto" while its MANUAL latch is off, then the knob's own words — the same read-only row, the same refusal, and the same rule: never a value map, never the walk. → [md11.md](../md11.md)

## MD11-25

- A flat 0 is no MD-11 reading: an export reads 0 until the aircraft publishes it, so the captain's altimeter announcer and the B key treat ≤ 0 as absent (never a baseline, never "0, 0.00"), as the COM announcer does for an out-of-band value and `DescribeAltimeterShortfall` for its read-back. → [md11.md](../md11.md)

## MD11-26

- The shell's other reader-driven line is the post-press announce: a changed label on the control the pilot just pressed is spoken ONLY when the agent flagged that element `announceChange: true` — set on the two stepper arrows, the tile button and the state tile's ACTION button (the controls whose label carries their own NEW STATE: "Runway next (now 06R)", "Passenger 1L: Open", "GPU: Connect") and nowhere else, never on the state tile's load button. It was briefly unconditional and spoke the PMDG tablet's "Performance (current page)" and the flyPad's "Baggage (called)" straight after the press the screen reader had already read (the Screen Reader Announcements rule); never gate it on a suffix or on "who was pressed" again. The existing per-item `live` hint cannot do this job — the shell applies `aria-live` to `<p>` only and a tile is a `<button>` with no static value line — so the flag has to sit on the pressed control itself. It is pinned against the SHIPPING shell — `tools/flypad-shell-test/efb-shell.test.js` extracts `PageHtml` out of `FbwEfbForm.cs` and drives `window.__render` against the real aria-live region — while `flypad-shell.html` (no live region, no click announce) is deliberately NOT asked to mirror it; that file pins the reconcile key only. → [md11.md](../md11.md)
