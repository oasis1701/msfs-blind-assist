# First Officer — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/first-officer.md`, which Claude Code loads when it reads matching code. Background: [first-officer.md](../first-officer.md).
The text is verbatim from PR #160's CLAUDE.md as of `642f48c1`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below" or "above" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it. FO-20 is new from 2026-10-06; FO-6's A320 sentence was brought up to date on 2026-10-09. FO-6 and FO-13 gained A380 paragraphs on 2026-10-09, and FO-6 names the A32NX and A330 rudder-trim link as a known exception (2026-10-10).

## FO-1

- Screen-reader First Officer (flows + checklists) across seven aircraft via `IFoProfile<TExec,TState>`; the form is identical, the profile injects executor/evaluator/data. Full architecture + gotchas in the doc. → [first-officer.md](../first-officer.md)

## FO-2

- No FMC programming, ever (deliberate user decision) — keep checklist text + V-speed reads + SimBrief load-only; never reintroduce CDU-keystroke automation. → [first-officer.md](../first-officer.md)

## FO-3

- `*_CL` readback groups are action-free (no item has a non-null `CheckAction`); state/action groups fire the switch on tick and auto-detect from live state. → [first-officer.md](../first-officer.md)

## FO-4

- The First Officer's "<flow> flow complete" (`FlowManager`) is NON-INTERRUPTING (`Announce`), never `AnnounceImmediate` — it runs straight after the last step, and `AnnounceImmediate` interrupts the screen reader and cancels its buffered speech, so the last step of a flow was routinely cut off on every aircraft: every flow-final Captain reminder, and worst of all a skipped wait's "Timed out waiting for… / Skipping…" (the PMDG 737 gear checks), which a blind pilot heard as silence and then "flow complete": success (owner decision 2026-09-22). FlowManager itself is not unit-testable (its ScreenReaderAnnouncer drives a real screen reader), so it is pinned by the source-text guard `FlowManager_FlowComplete_IsNonInterrupting` in `FoPr160ProcedureFixTests`. → [first-officer.md](../first-officer.md)

## FO-5

- `FlowManager`'s 2 s inter-step pause (`InterStepPauseMs`, includes "Already set" skips) is deliberate realism pacing for a screen-reader pilot — never remove or shrink it as an optimization; it layers on top of executor write spacing. → [first-officer.md](../first-officer.md)

## FO-6

- A flow step's checklist links are `FlowStep.LinkedChecklistItemIds` (`CompletesChecklistItemId` first, then `AlsoCompletesChecklistItemIds`): `FlowManager` marks — and on a SKIP excludes from the group latch — EVERY linked id, never only `CompletesChecklistItemId`. A WRITE step must link the line it sets, or a failed write is still latched done when the flow finishes — and "the lines a flow latches" is `FlowDefinition.CompletionGroupIds` (the flow's `RelatedChecklistGroupIds` PLUS the group named after the flow and its `_CL` read-back, the ONE rule `FirstOfficerForm` itself uses), never `RelatedChecklistGroupIds` alone: auditing that alone missed twelve 737 read-back lines. The PMDG 737, PMDG 777 and iFly 737 MAX8 link every switch-write step, each pinned by a `*FlowChecklistLinkTests` audit over the shared `FlowChecklistLinkAudit` (derives each step's lines from the fields its writes drive, and pins the short list of lines still latched with no step behind them); the engine-start SELECTOR lines are never linked (their StayComplete exception above), nor is a plan-gated step family whose non-planned siblings skip as "Already set" (777 Before Taxi flaps). The Fenix, FBW A32NX/A380 and Headwind A330 flows have NOT been audited this way, write by write (no per-aircraft map of the fields each write drives) — a known gap. On the Fenix, A32NX and A330 what a finished flow latches is pinned instead by `A320FamilyReadbackLinkTests` (2026-10-09, [FOA-8]): its audit holds the lines a finished flow latches with no step behind them (`FlowChecklistLinkAudit.UndeliveredLines`) EMPTY, and it pins the read-back links: the writes `BS_BEACON`, `AS_RUDDERTRIM`, `TX_AUTOBRAKE`, `TX_CABIN`, `TX_CONFIG`, `LU_TCAS` and `AP_SEATBELTS`; the engine-start waits `ES_ENG1_N2` and `ES_ENG2_N2`, each completing its "Engine n: running" line (a timeout stops the flow, so nothing is latched); and the read-only checks `TX_WXR_PWS_CHECK` and `AL_WXR_PWS_CHECK`, each right after the two radar writes whose combined state it confirms, and `TX_MEMO_CHECK`, which confirms what Preflight, Before Start and After Start set. The A32NX and A330 read-only gear-lever check `EPU_CHK_GEAR`, which completes "Gear lever: DOWN", is not in that class: its shape is pinned by `FbwA320FlowParityTests` and `HwA330FlowParityTests` (the audit above would also list the line if no step completed it). A line that only a LATER condition makes true (APU AVAIL, gear down, both radar switches off after two writes) is completed by the read-only wait that reads that condition, never by the write ([FO-11], [FO-13]). One known exception awaits its own fix: on the FBW A32NX and the Headwind A330 the rudder-trim reset `AS_RUDDERTRIM` completes the After Start Checklist's "Rudder trim: NEUTRAL" (`ASC_RUDDER`, which reads the FAC trim), so a finished flow can latch that line before the trim reads neutral (the Fenix's line is a Reminder the pilot confirms); the FlyByWire A380 completes its "Rudder trim: NEUTRAL" by a read-only check (below). The 777 flap-lever events are keyed by DEGREES (`_0/_1/_5/_15/_20/_25/_30`), not the 737's detent indices; a 777 FO write to an event missing from `PMDG777Definition.EventIds` fails at dispatch (`Every_written_event_is_in_the_777_event_table`). → [first-officer.md](../first-officer.md)

  **The FlyByWire A380X (2026-10-09, [FOA-9]).** The A380 is audited on the shared rule: `FbwA380FlowChecklistLinkTests` pins that no line in a group an A380 flow latches is left without a delivering step (`FlowChecklistLinkAudit.UndeliveredLines` is empty), that every write step with an action line completes it, and exactly which lines each step completes. Each write completes its own action line and any read-back line it sets; the read-only checks `CP_WAIT_SB`, `AS_RUDDERTRIM_CHECK`, `TX_MEMO_CHECK`, `LU_PACKS_CHECK`, `LD_MEMO_CHECK` and `LD_GEAR_DOWN_CHECK`, and the Parking wait `PK_WAIT_ENG`, complete the lines only a later condition makes true, and `CP_WAIT_SB`, `PK_WAIT_ENG` and `PK_WAIT_SB` also complete the action line of the write before them, which reads the same field, so a timed-out wait keeps that line out of the latch although the write ticked it ([FO-8], 2026-10-10). So the A380's "Rudder trim: NEUTRAL" (`ASC_RUDDERTRIM`) is completed by `AS_RUDDERTRIM_CHECK` (20 s, a judgement: the reset's time to neutral is not measured), never by the reset `AS_RUDDERTRIM`, which completes only its own line. Unlike the 737, 777 and iFly audits it does not map written keys to state fields.

## FO-7

- **A checklist item with no flow step behind it is still TICKED AND LATCHED when its flow finishes** (`ChecklistManager.MarkGroupComplete` excludes only the lines of steps the run SKIPPED: a Skip-policy step that failed or timed out, a step left alone by `LeaveAloneWhen`, a step skipped through its `RequiresStepId` dependency, and a step whose `TargetValueProvider` had no value (FO-20); all four are in `FlowManager.UnfinishedChecklistItemIds`), so every actionable item in a state group needs a delivering step or it becomes a silent false completion — `BS_TRANSPONDER` read "Transponder: XPNDR" complete with the selector untouched. Adding a step is the fix; never rely on the exclusion set, which a missing step never reaches. → [first-officer.md](../first-officer.md)

## FO-8

- A completed checklist group with participation (a user manual tick or a flow MarkComplete) is completion-LATCHED — RevertToState must not un-tick it until reset/manual untick; never latch on coincidental auto-ticks alone, and never reintroduce item-level StayComplete or an unconditional 100% latch. `MarkGroupComplete`'s group latch is UNCONDITIONAL even when a flow's `excludeItemIds` names a step it could not deliver — the phase's completed steps stay a flight-long historical record — and the one undelivered item is exempted PER-ITEM via `ChecklistItem.ExemptFromCompletionLatch` so IT ALONE keeps mirroring live state inside the otherwise-latched group; this is NOT the item-level StayComplete the rule above forbids (that would freeze every item, not free one). The exemption is set whenever the flow did not itself deliver the item — un-checked, OR checked only via a pilot hand-tick still `AwaitingActionConfirmation` — and its clear must be UNCONDITIONAL, never only when that same call is the one that ticks the item: a hand-tick can check the item before a later pass (state agreeing, or a real re-delivery) tries to clear the exemption, and gating the clear on `!IsChecked` leaves it permanently exempt despite doing exactly what it was supposed to do. → [first-officer.md](../first-officer.md)

## FO-9

- A checklist item the pilot hand-ticks that fires a linked `CheckAction` sets `AwaitingActionConfirmation`; if `RevertToState` later un-ticks it because the switch never actually moved, `ChecklistManager` raises `ItemActionFailed` and the form speaks `"Unable to complete: {label}"` — the only channel that reaches a blind pilot who has navigated away from the checklist tree, where the correction is otherwise silent and visual-only. Never raised for an ordinary revert (the pilot moved the switch back themselves), and it fires from inside a latched group exactly like an unlatched one whenever the item is exempted. → [first-officer.md](../first-officer.md)

## FO-10

- Checklist revert grace is action-aware: `ChecklistManager.RunCheckActionWithGraceAsync` holds revert until the tick's action completes AND the executor's dispatch gate drains (`IFoActionExecutor.WaitForDispatchDrainAsync`), covering the multi-second closed-loop selector walks (transponder / position lights) and anything queued behind them. → [first-officer.md](../first-officer.md)

## FO-11

- **A checklist item whose state field is a SLOW condition needs its CheckAction to hold open until that condition is true — the 10 s `ManualTickGrace` will not save it.** `ChecklistManager`'s own remarks say so ("SLOW actions are covered by ActionSettling, not by inflating this constant") and the Fenix APU is the case that proves it: `BS_APU`/`AL_APU` detect on the AVAIL lamp, which lights only when the APU reaches ~95% N about 45 s after START, while `StartApuAsync` returned at the START pulse. That left ~13 s of grace against a ~45 s condition, so a hand-tick un-ticked itself, `ItemActionFailed` fired, and the pilot heard *"Unable to complete: APU: ON and available"* over an APU starting perfectly — after which it silently re-ticked. `FenixActionExecutor.StartApuAsync` now polls the lamp to `ApuAvailTimeoutMs` (180 s, the SAME budget as the Before Start flow's `WaitForField`, so both paths give up together) and a genuine failure still surfaces with the same message, now truthfully. The dispatch gate is released between writes, so the wait never blocks `WaitForDispatchDrainAsync`. ⚠️ Three profiles detect an APU item on the AVAIL lamp rather than an instant switch position, and each holds the tick open the same way: the Fenix (`FenixActionExecutor.ApuAvailField`), and since 2026-10-06 the FBW A32NX and the Headwind A330 (`A32NX_OVHD_APU_START_PB_IS_AVAILABLE`, their executors' own `ApuAvailField`, held by their own `StartApuAsync` to the same 180 s `ApuAvailTimeoutMs`). The FBW A380 (`A32NX_OVHD_APU_MASTER_SW_PB_IS_ON`), the PMDG 737 (`APU_Selector`) and the iFly (`APU_Switch_Status`) still read the switch — do not "harmonize" a lamp profile onto a switch, the AVAIL gate before external power is dropped is the point. The FLOW never had this bug: it waits in its own `WaitForField` step, and on those three profiles that wait, never the APU master write, completes the line, so an APU that never comes up is never ticked or latched by the flow; the asymmetry between the two paths WAS the bug. → [first-officer.md](../first-officer.md) ⚠️ WHICH lamp that is was settled only by live measurement (2026-09-04, Fenix A319): **`I_OH_ELEC_APU_START_U` is AVAIL (persistent) and `_L` is the ON legend (transient, lit only while the start runs)** — reversed against both the real A320 and the Fenix’s own APU MASTER pushbutton, so the suffixes cannot be trusted on this button. Both readings had shipped once each on reasoning alone, each reproducing the other’s bug (with `_L`, a running APU read as not-available, so the item never auto-ticked and a hand-tick waited on a lamp that would never light again). Every site now reads the ONE constant `FenixActionExecutor.ApuAvailField`; never repeat the literal, and never infer a Fenix legend’s meaning — read it in the sim. → [first-officer.md](../first-officer.md)

## FO-12

- **A hand-tick must never re-do work the pilot already did (2026-09-04).** `ChecklistManager.ToggleItem` fired an item’s `CheckAction` unconditionally, so a pilot who had started the APU themselves — outside the First Officer window — and then ticked the item had the FO re-run the whole start sequence on a live APU (MASTER re-written, START pushbutton re-pulsed) before falsely announcing *“Unable to complete”*. The FLOW never had this bug — `FlowManager` honours a step’s `SkipCondition` and says *“Already set”* — and that asymmetry IS the bug. `ToggleItem` now skips the action, and the `AwaitingActionConfirmation` mark with it, when the item’s OWN state condition already reads DEFINITELY true; an indeterminate (NaN) read still runs it. Gated on `IsAutoDetectable`, so an ACTIONABLE item with no state field (the TCAS/WXR/GPWS self-tests) still fires every tick — those exist to be re-run. → [first-officer.md](../first-officer.md)

## FO-13

- Every First Officer checklist line that confirms the landing gear — the After Takeoff Checklist's "Landing gear: UP" and the Landing Checklist's "Landing gear: DOWN" — is backed by a READ-ONLY wait that is the LAST step of the flow that latches it (20 s, Skip, completes the line, never writes). PMDG 737 and iFly 737 read the gear LIGHTS ("gear up, lights out" / "three green" via `GearLightRules`; `GearConfirmation`, `IFly737GearConfirmation`, synthetic `FO_GEAR_UP`/`FO_GEAR_DOWN`; the iFly counts a DIM light as on). The Fenix reads "lights out" for UP and "three green" for DOWN (`FenixGearConfirmation`, `FO_GEAR_DOWN`, read by the Landing Checklist's `LDC_MEMO_GEAR`, "Landing gear: DOWN", the first line of the landing memo; it was `LDC_GEAR` until 2026-10-06): the green is each wheel's LOWER legend `I_MIP_GEAR_n_L`, and the upper `_U` legends plus `I_MIP_GEAR_RED` count as reds — MEASURED 2026-09-25 (Fenix A320 CFM, powered, gear down and locked: every `_L` = 1, every `_U` and the arrow 0; the annunciator light TEST lights all three `_U` and the arrow, proving they are live; the DIM setting leaves `_L` at 1), never inferred from the suffix or the real A320. `_U`'s colour in transit was not observed. The A32NX and the Headwind A330 read the gear LEGS instead (`FbwA320GearConfirmation`, shared by both: `FO_GEAR_UP` = handle up and `A32NX_GEAR_CENTER_POSITION`, `_LEFT_POSITION` and `_RIGHT_POSITION` all under 5 %; `FO_GEAR_DOWN` = handle down and all three over 95 %; any unknown input is NaN), and their `LDC_MEMO_GEAR` reads `FO_GEAR_DOWN`. On all three A320-family aircraft there is no After Takeoff checklist any more (FOA-8), so the After Takeoff flow's read-only `AT_GEAR_UP_CHECK` (20 s, Skip, never writes) is its last step but links no checklist line, and none of them has a Landing flow, so nothing latches `LDC_MEMO_GEAR`: it ticks and un-ticks from its own state alone, and a Landing flow, if one is added, needs a read-only gear-down check completing `LDC_MEMO_GEAR`. The PMDG 777, whose SDK exposes no gear lights, composes the same checks from the CDA lever AND the stock `GEAR LEFT/CENTER/RIGHT POSITION` SimVars (`Pmdg777GearConfirmation`, synthetic `FO_GEAR_UP`/`FO_GEAR_DOWN`: UP = lever up and every leg ≤ 1 %, DOWN = lever down and every leg ≥ 99 %, the System Display Gear page's own thresholds), fed by `FirstOfficerForm`'s 1 Hz `RequestFOGearPositions()` (777 only, FO-private definition/request 385) into `AircraftStateEvaluator.SetGearPosition` (`ATKOF_GEAR_UP_CHECK`, `LD_GEAR_DOWN_CHECK`, and the checklist lines `ATKOF_GEAR`/`LDG_GEAR`). The action-group LEVER lines are completed by the step that WRITES the lever — iFly "Gear lever: UP" by `AT_GEAR_OFF`, 777 "Gear: UP" by `ATKOF_GEAR_UP` and 777 "Flaps: UP" by `ATKOF_FLAPS_UP` (the After Takeoff Checklist's "Flaps: UP" is completed by the read-only lever check `ATKOF_FLAPS_UP_CHECK`, placed before the gear check) — so a failed write is skipped aloud and left live rather than latched. A synthetic gear field is NaN when any reading it rests on is unknown. Never add a gear WRITE to a check. → [pmdg-737.md](../pmdg-737.md), [ifly-737.md](../ifly-737.md), [a32nx.md](../a32nx.md), [pmdg-777.md](../pmdg-777.md)

  **The FlyByWire A380X (2026-10-09, [FOA-9])** reads the legs too: `FbwA380GearConfirmation` (`FO_GEAR_DOWN`) is the gear lever `A32NX_GEAR_HANDLE_POSITION` down and `A32NX_GEAR_CENTER_POSITION`, `_LEFT_POSITION` and `_RIGHT_POSITION` all over 98 %, the A380 System Display WHEEL page's own green threshold; any unknown input is NaN. Its Landing flow ends with the read-only `LD_GEAR_DOWN_CHECK` (20 s, Skip, never writes), which completes the Landing Checklist's `LDC_GEAR`, "Landing gear: DOWN". It has no After Takeoff checklist and no gear-up check. Pinned by `FbwA380GearConfirmationTests`, `FbwA380ReadOnlyCheckTests` and `FbwA380LandingChecksBehaviourTests`.

## FO-16

- The FO AP engagement height is the user setting `FOAutoApEngageAltitudeAgl` (default 350 ft AGL, one global value) — never hardcode an engagement altitude in a `FOAutoManager`; the 737's LNAV/VNAV push height (400 ft AGL) is deliberately FIXED and each push is annunciator-guarded (NaN = skip). → [first-officer.md](../first-officer.md)

## FO-17

- Auto-AP-engage is floored by `IAircraftDefinition.MinimumAutopilotEngageAltitudeAgl` (**PMDG 737 = 400 ft** — its AFDS INHIBITS CMD below 400 ft RA after takeoff; 777 = 200) — never let the user setting press below an aircraft's own engage limit, and never lower the 737's floor: at ~1 Hz the old 350 ft default landed in [350, 400) on every takeoff, so the press was silently rejected while the app announced success. → [first-officer.md](../first-officer.md)

## FO-18

- Auto-AP-engage is CLOSED-LOOP wherever `IAircraftDefinition.IsAutopilotEngaged` returns non-null: announce only on a CONFIRMED engagement, retry a rejected press (bounded, `MaxApEngageAttempts`), and report a Captain action if it never takes — never re-add the announce-on-press + one-shot latch (a blind pilot was told "Autopilot engaged" with the AP off and no retry ever came). `IsAutopilotEngaged` must return **null**, never false, before the first CDA snapshot — the PMDG engage switches are TOGGLES and a guessed false would disconnect an engaged AP on retry. → [first-officer.md](../first-officer.md)

  **Per aircraft (2026-10-09, [FO-21]).** How often the service presses, and what it does on a null, is set by the definition. `IAircraftDefinition.AutopilotEngageRetryIntervalMs` is the least time between attempts: 0, a retry on every tick, is the default and what the PMDG jets, the iFly and the MD-11 keep; the FlyByWire family sets 3000. `AutopilotEngageWaitsForState` says what a null reading means to the service. False, the default, treats it as no readback: one open-loop press, announced on the press, whether the aircraft really exposes no engaged state (the Fenix, the HS787) or only has no data yet (the PMDG jets, the iFly, the MD-11). True, on the FlyByWire family, treats it as "not read yet": the service never presses on it, because the AP 1 push is a toggle too, and waits for a definite reading. Its give-up then says "Autopilot state unknown. Captain action required: check the autopilot." when it never pressed or the latest reading is null again, and "Autopilot did not engage. Captain action required: engage the autopilot." when it pressed and the autopilot reads off. Both settings are pushed from the current definition every second and on every aircraft switch. On every aircraft the confirmation ("{height} feet. Autopilot engaged.") is spoken without interrupting, so it queues behind the aircraft's own call; the gear calls and the two Captain calls interrupt (FO-21).

## FO-19

- The 10 k landing-light switching is gated by `FOAutoLights10kEnabled` (default ON) and ONLY the light actions/announcements are gated — baro pushes, the no-transition reminder, and the crossing latch always run. The checklist tree must NEVER use `TreeView.CheckBoxes = true` — a TVS_CHECKBOXES tree announces every selected/expanded-once header as "check box" in NVDA regardless of hidden state images (2026-07-16 fix); checkboxes come from `CheckboxStateImages` + per-node `ShowCheckBox`/`HideCheckBox`, and `.Checked` must never be set programmatically on headers/separators. → [first-officer.md](../first-officer.md)

## FO-20

- A flow step whose `FlowStep.TargetValueProvider` returns null (the data it needs, a SimBrief plan, is not there) is a SILENT SKIP in `FlowManager` (owner decision 2026-10-06): nothing is sent and nothing is spoken (the step is paired with a Captain reminder, and that reminder is what the pilot hears; "Skipping: …" would tell the pilot the flow failed when it only had no plan), the step's `LinkedChecklistItemIds` are NOT marked and ARE kept out of the end-of-flow latch exactly like a skipped step's ([FO-6], [FO-8]: they land in `UnfinishedChecklistItemIds`, so `MarkGroupComplete` leaves them unticked and `ExemptFromCompletionLatch`), the step raises `StepSkipped` (the Steps list marks it "→", not "✓"), and its id joins the run's skipped set, so a step whose `RequiresStepId` names it is skipped too, as after any other skip: a step that builds on a value the flow never set must not run. The inter-step pause is unchanged ([FO-5]). It goes through the same `SkipWithoutRunningAsync` as the leave-alone and dependency skips, with no spoken text; a `RetryThenStop` retry that finds no value any more takes the same path.

  **Why.** Until 2026-10-06 a null provider was a QUIET SUCCESS: no announcement, success result, so `MarkComplete` ticked every line the step linked and the end-of-flow latch froze it. With no SimBrief plan loaded, the A320 After Start step `AS_FLAPS` ("Flaps: takeoff setting", `Done(Provider(...), "AS_FLAPS")` on the Fenix, the FBW A32NX and the Headwind A330) therefore ticked and latched "Flaps: takeoff setting" over a lever at 0, while its own Captain reminder `AS_FLAPS_CAPT` (skipped only when the lever reads 1–3) was asking the pilot to set the flaps. Now the line stays unticked and follows the lever, so it ticks itself when the pilot sets a takeoff flap.

  **Audit (2026-10-06), every `TargetValueProvider` user.** The three A320s' `AS_FLAPS` (provider null when the SimBrief flaps are not 1–3; links `AS_FLAPS`): the only steps whose behaviour changes in what is ticked or latched (superseded below). The PMDG 737 Preflight `PF_FLT_ALT` and `PF_LAND_ALT` (`DynSW`; null with no plan; link no line (superseded below), nothing requires them): nothing ticked, latched or spoken changes (superseded below); only their Steps-list mark goes from "✓" to "→". So with no SimBrief plan loaded, the PMDG 737 Preflight steps "Flight altitude: set" and "Landing altitude: set" now show as skipped (→) in the Steps list, the honest mark for a step that set nothing; FlowManager is shared, so this holds on every aircraft by design (confirmed 2026-10-06). The TFDi MD-11 `PF_DAF` (Dial-A-Flap; the provider is `TakeoffDialAFlap ?? 0`, never null, so a missing plan fails at the executor as "Skipping"): unchanged. The FBW A380 defines a `Provider` helper and uses it nowhere; the PMDG 777 sets takeoff flaps with plan-gated `SkipCondition` steps, and the iFly 737 MAX8 sets pressurization through its executor's `KeyPressAlts` pseudo-key (its old provider step was removed in 2026-08): neither uses a provider (superseded below for the iFly). Pinned by `FlowManagerTargetProviderTests` (a real FlowManager and ChecklistManager) and `A320FamilyTakeoffFlapsNoPlanTests` (the three A320s' real After Start steps, evaluators and checklists, no sim).

  **The 737 pressurization line (later 2026-10-06, supersedes the 737 half of the audit above).** Linking no line meant nothing kept the Preflight state line `PF_PRESS` ("Flight and landing altitudes: SET") out of the latch, so a no-plan Preflight run still ticked and froze it over windows nobody had set ([FO-7]). The PMDG 737's `PF_FLT_ALT` and `PF_LAND_ALT` now both name `PF_PRESS` (the line reads both windows, so either one skipping or failing keeps it open). The iFly 737 MAX8's single `PF_PRESS_ALTS` step still goes through the `KeyPressAlts` pseudo-key (FOB-17), but is now plan-gated by a provider (null with no plan, a fixed token otherwise; the pseudo-key reads the plan itself) and names `PF_PRESS`: before, with no plan the pseudo-key's quiet no-op "succeeded", so the pilot heard "Flight and landing altitudes: set" right before the Captain fallback asked for them. With no plan both aircraft now say only the Captain fallback and leave `PF_PRESS` unticked and exempt from the latch (NaN with no plan, so it never auto-ticks; a hand tick holds). Neither Preflight read-back has a pressurization-altitude line (`PFC_PRESS` is the mode selector). Pinned by `Pmdg737PressurizationNoPlanTests` and `IFly737PressurizationNoPlanTests` (real steps, evaluators, checklists and FlowManager, no sim). → [first-officer.md](../first-officer.md)

## FO-21

- The FlyByWire family's universal auto-autopilot (FBW A32NX, FBW A380X, and the Headwind A330, which inherits the A32NX definition) presses the cockpit's AP 1 pushbutton, `A32NX.FCU_AP_1_PUSH` — the event the AP 1 button and the ToggleAutopilot1 hotkey already send — through `Aircraft/FbwAutopilotEngage`, never the stock `AUTOPILOT_ON`. FlyByWire captures and masks `AUTOPILOT_ON` and sets `simInputAutopilot.AP_engage = 1`, a flag nothing has read since FBW #7587 on the A32NX (2024-11-15; the last reader, `AP_ENGAGE_push`, is at [FlyByWireInterface.cpp L1854 @ 84888a77](https://github.com/flybywiresim/aircraft/blob/84888a77b229b29f7b10d575f8bf8eaf15244cd7/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L1854)) and FBW #10855 on the A380X. Checked at the owner's build, FBW master 255546cb: the A32NX handler [SimConnectInterface.cpp L1739-1743](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/interface/SimConnectInterface.cpp#L1739-L1743), the `AP_1_push` reader [FlyByWireInterface.cpp L1742-1743](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L1742-L1743); the A380X and Headwind's A339X (382bacbd) have the same shape. FlyByWire's own flight-deck API docs still list `AUTOPILOT_ON` ("1st call AP1, 2nd call AP2"); their code no longer does that, so never take the docs as the reason to send it. Until 2026-10-09 the app sent `AUTOPILOT_ON` (commit 0d5ed829 of 2026-07-12 moved the engage out of the FBW First Officer managers' `EngageAp1`), and with `IsAutopilotEngaged` null it announced "350 feet. Autopilot engaged." on the press while the autopilot stayed off: FO-18's failure exactly. The pilot hears the aircraft's own "Autopilot 1 on", then the service's "{height} feet. Autopilot engaged." (owner's choice, 2026-10-09; neither is suppressed). The service speaks that confirmation WITHOUT interrupting (a delegate of its own, wired to the non-interrupting `Announce`; FO-4 makes the same choice for "flow complete" and for the same reason): the aircraft's call arrives with the 1 Hz batch and the confirmation 0-1 s later, and an interrupting one cut "Autopilot 1 on" off mid-word. So it now queues behind the aircraft's call. This changes the timing, not the text, for every aircraft that uses the universal auto-engage, the open-loop press on a null readback included. The gear calls and the two Captain calls still interrupt. Like any non-interrupting announcement the confirmation is dropped while `announcer.Suppressed` is on (the five-second first-detect grace after an A380 detect or switch); the Captain calls are not.

  **The push is a TOGGLE, and four mechanisms exist because of it.**

  **1. Only on a definite OFF (`FbwAutopilotEngage.PressFor`).** `IsEngaged` is true when `A32NX_AUTOPILOT_1_ACTIVE` or `_2_ACTIVE` reads above 0.5, false only when both are read and off, and null while either is unread or NaN (FO-18: never a guessed false). `PressFor` returns the push for false only: an engaged autopilot is never pressed (the push would disconnect it), and neither is one whose state is unknown.

  **2. Never blind (`AutopilotEngageWaitsForState`, `UniversalAutomationService.WaitForApState`).** On the FBW family a null state means "not read yet": the AP variables reach the cache with the 1 Hz batch, while the service's altitude, vertical speed and height above ground come from separate requests, so after an app restart, or an aircraft detected mid-climb with the autopilot already on, the first tick can come before the AP variables are read. A press then would switch the autopilot off while the service said "Autopilot engaged". So where the definition sets the flag (the A32NX, the A380X and, by inheritance, the A330), the service never presses on a null: it spends an attempt waiting, spaced like a press, and looks again. If no reading comes within the five attempts it speaks "Autopilot state unknown. Captain action required: check the autopilot." (it pressed nothing and the autopilot may well be on, so it does not tell the Captain to engage it). The give-up follows the LATEST reading, not only whether the service pressed: a leg that pressed but whose latest reading is null again (a SimConnect disconnect clears the cache, and only `SwitchAircraft` resets the service) speaks the same "state unknown" line, because the autopilot may already be on and "engage the autopilot" would disconnect it. A leg that pressed and reads the autopilot off at the give-up speaks "Autopilot did not engage. Captain action required: engage the autopilot." Every other aircraft keeps `false`, where a null takes the open-loop press and announce; its give-up is unchanged, since it is reached only after the engage was invoked and so always says "did not engage". "Autopilot engaged" is spoken only for an engage the service itself invoked (`_apPressed`, cleared by `Reset()` and on touchdown), so a leg that only waited and then finds the autopilot on stays silent: the pilot, or the app's restart, had it on already.

  **3. Never into the probe queue (`PressWouldWait`; the A32NX and A330 only).** `A32NX.FCU_AP_1_PUSH` is a dotted event there, and `SimConnectManager.SendEvent` holds a dotted event in its queue while the MobiFlight bridge object exists and the calc-path probe has neither verified nor concluded ([SIM-13]). The bridge object exists on every connection, with or without the WASM module, so with no module the probe runs its full ~60 s (40 attempts, 1.5 s apart) before it concludes. The queue is sent in one loop when the probe ends (`FlushPendingCalcEvents`). Queued retries would NOT toggle AP 1 on and off again: FlyByWire resets its autopilot inputs at the start of each update ([FlyByWireInterface.cpp L923](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L923)) and drains every pending event in it (`readData()` at [L936](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/FlyByWireInterface.cpp#L936), whose loop is [SimConnectInterface.cpp L1052](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/interface/SimConnectInterface.cpp#L1052)), and the `A32NX.FCU_AP_1_PUSH` handler only sets the flag `AP_1_push = 1` ([L1775-1777](https://github.com/flybywiresim/aircraft/blob/255546cb02db1c7b40d2505ac621a9d36748d258/fbw-a32nx/src/wasm/fbw_a320/src/interface/SimConnectInterface.cpp#L1775-L1777), reset at L1176), so pushes that land in one update count as a single press. The real reason for the guard is the late push: one push that arrives up to a minute after it was queued, after the service has given up and told the Captain to engage the autopilot, can switch off the autopilot the Captain engaged since. So `PressFor` sends nothing while both autopilots read off and `PressWouldWait(CanExecuteCalculatorCode, CalcPathVerified, CalcPathProbeConcluded)` is true. A withheld press still uses up one of the five attempts, so a leg whose attempts all fall inside the probe window ends with its Captain call at about 15 s and nothing auto-engages, which is the safe side. That window is the ~60 s after a load or an aircraft switch with no module (with a working module it ends when the probe verifies). Once the probe has concluded, the legacy transport sends the push normally (`SimConnectManager.SendEvent`, the fall-through after the dotted branch), so every later leg auto-engages as usual even with no module. The A380 passes no `pressWouldWait`: its `A32NX.FCU_*` events never wait on the probe ([SIM-10]).

  **4. Three seconds apart (`AutopilotEngageRetryIntervalMs` = `FbwAutopilotEngage.RetryIntervalMs` = 3000).** It spaces the presses, the waits and the give-up alike: the engaged state reaches the cache with the 1 Hz batch, so a retry on the next tick could land on an autopilot the first press had already engaged and switch it off. `MaxApEngageAttempts` stays 5, waits included: attempts at 0, 3, 6, 9 and 12 s, the give-up call at 15 s. Every other aircraft keeps 0, a retry on every tick as before.

  **The limits follow the aircraft.** `MainForm.PushUniversalAircraftLimits` (in `MainForm.UniversalAutomation.cs`, the one MainForm partial `first-officer.md` globs) pushes the engage floor ([FO-17]), the interval and `WaitForApState` from the current definition every second and from `SwitchAircraft` right after `universalAutomation?.Reset()`: an `Update` between a switch and the next tick would otherwise act on the previous aircraft's values, for example an open-loop press on an FBW aircraft while the flag was still off.

  **Also seen on, not changed here.** The PMDG 737 and 777 and the iFly 737 return null until their data is ready and keep the open-loop path (one invoke, announced on it), so a restart mid-climb with the autopilot already on is a blind toggle there: the 737 and 777 guards read an annunciator that is 0.0 before the data is ready, and the iFly's guard stops only on a definite true. The TFDi MD-11's engage presses only on a definitely-off `MD11_AP_STATE`, so on an unread state it presses nothing while the service still announces "Autopilot engaged". All of it is left for a separate change, and there is no issue for it yet: name it here when one is filed.
