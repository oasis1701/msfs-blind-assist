Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/first-officer.md`, which Claude Code loads when it reads matching code. Background: [first-officer.md](../first-officer.md).

Cross-references such as "the bullet below" or "above" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it. ## FO-1

- Screen-reader First Officer (flows + checklists) across seven aircraft via `IFoProfile<TExec,TState>`; the form is identical, the profile injects executor/evaluator/data. Full architecture + gotchas in the doc. → [first-officer.md](../first-officer.md)

## FO-2

- No FMC programming, ever (deliberate user decision) — keep checklist text + V-speed reads + SimBrief load-only; never reintroduce CDU-keystroke automation. → [first-officer.md](../first-officer.md)

## FO-3

- `*_CL` readback groups are action-free (no item has a non-null `CheckAction`); state/action groups fire the switch on tick and auto-detect from live state. → [first-officer.md](../first-officer.md)

## FO-4

- The First Officer's "<flow> flow complete" (`FlowManager`) is NON-INTERRUPTING (`Announce`), never `AnnounceImmediate` — it runs straight after the last step, and `AnnounceImmediate` interrupts the screen reader and cancels its buffered speech, so the last step of a flow was routinely cut off on every aircraft: every flow-final Captain reminder, and worst of all a skipped wait's "Timed out waiting for… / Skipping…" (the PMDG 737 gear checks), which a blind pilot heard as silence and then "flow complete": success (owner decision 2026-09-22). FlowManager itself is not unit-testable (its ScreenReaderAnnouncer drives a real screen reader), so it is pinned by the source-text guard `FlowManager_FlowComplete_IsNonInterrupting` in `FoPr160ProcedureFixTests`. → [first-officer.md](../first-officer.md)

## FO-5

- `FlowManager`'s 2 s inter-step pause (`InterStepPauseMs`, includes "Already set" skips) is deliberate realism pacing for a screen-reader pilot — never remove or shrink it as an optimization; it layers on top of executor write spacing. → [first-officer.md](../first-officer.md)

  The pause paces SPOKEN steps (including "Already set"). A step passed silently because its `FlowStep.RunOnlyIfStepSent` switch was not sent this run (the APU cool-down waits) has no pause of its own: nothing is spoken and the previous step's pause has already run (`FlowManager.cs`, the `RunOnlyIfStepSent` gate comment), so never add one "for FO-5".

## FO-6

- A flow step's checklist links are `FlowStep.LinkedChecklistItemIds` (`CompletesChecklistItemId` first, then `AlsoCompletesChecklistItemIds`): `FlowManager` marks — and on a SKIP excludes from the group latch — EVERY linked id, never only `CompletesChecklistItemId`. A WRITE step must link the line it sets, or a failed write is still latched done when the flow finishes — and "the lines a flow latches" is `FlowDefinition.CompletionGroupIds` (the flow's `RelatedChecklistGroupIds` PLUS the group named after the flow and its `_CL` read-back, the ONE rule `FirstOfficerForm` itself uses), never `RelatedChecklistGroupIds` alone: auditing that alone missed twelve 737 read-back lines. The PMDG 737, PMDG 777 and iFly 737 MAX8 link every switch-write step, each pinned by a `*FlowChecklistLinkTests` audit over the shared `FlowChecklistLinkAudit` (derives each step's lines from the fields its writes drive, and pins the short list of lines still latched with no step behind them); the engine-start SELECTOR lines are never linked (their StayComplete exception above), nor is a plan-gated step family whose non-planned siblings skip as "Already set" (777 Before Taxi flaps). The Fenix, FBW A32NX/A380 and Headwind A330 flows have NOT been audited this way, write by write (no per-aircraft map of the fields each write drives) — a known gap. On the Fenix, A32NX and A330 what a finished flow latches is pinned instead by `A320FamilyReadbackLinkTests` (2026-10-09, [FOA-8]): its audit holds the lines a finished flow latches with no step behind them (`FlowChecklistLinkAudit.UndeliveredLines`) EMPTY, and it pins the read-back links: the writes `BS_BEACON`, `AS_RUDDERTRIM`, `TX_AUTOBRAKE`, `TX_CABIN`, `TX_CONFIG`, `LU_TCAS` and `AP_SEATBELTS`; the engine-start waits `ES_ENG1_N2` and `ES_ENG2_N2`, each completing its "Engine n: running" line (a timeout stops the flow, so nothing is latched); and the read-only checks `TX_WXR_PWS_CHECK` and `AL_WXR_PWS_CHECK`, each right after the two radar writes whose combined state it confirms, and `TX_MEMO_CHECK`, which confirms what Preflight, Before Start and After Start set. The A32NX and A330 read-only gear-lever check `EPU_CHK_GEAR`, which completes "Gear lever: DOWN", is not in that class: its shape is pinned by `FbwA320FlowParityTests` and `HwA330FlowParityTests` (the audit above would also list the line if no step completed it). A line that only a LATER condition makes true (APU AVAIL, gear down, both radar switches off after two writes) is completed by the read-only wait that reads that condition, never by the write ([FO-11], [FO-13]). One known exception awaits its own fix: on the FBW A32NX and the Headwind A330 the rudder-trim reset `AS_RUDDERTRIM` completes the After Start Checklist's "Rudder trim: NEUTRAL" (`ASC_RUDDER`, which reads the FAC trim), so a finished flow can latch that line before the trim reads neutral (the Fenix's line is a Reminder the pilot confirms); the FlyByWire A380 completes its "Rudder trim: NEUTRAL" by a read-only check (below). The 777 flap-lever events are keyed by DEGREES (`_0/_1/_5/_15/_20/_25/_30`), not the 737's detent indices; a 777 FO write to an event missing from `PMDG777Definition.EventIds` fails at dispatch (`Every_written_event_is_in_the_777_event_table`). → [first-officer.md](../first-officer.md)

  **The FlyByWire A380X (2026-10-09, [FOA-9]).** The A380 is audited on the shared rule: `FbwA380FlowChecklistLinkTests` pins that no line in a group an A380 flow latches is left without a delivering step (`FlowChecklistLinkAudit.UndeliveredLines` is empty), that every write step with an action line completes it, and exactly which lines each step completes. Each write completes its own action line and any read-back line it sets; the read-only checks `CP_WAIT_SB`, `AS_RUDDERTRIM_CHECK`, `TX_MEMO_CHECK`, `LU_PACKS_CHECK`, `LD_MEMO_CHECK` and `LD_GEAR_DOWN_CHECK`, and the Parking wait `PK_WAIT_ENG`, complete the lines only a later condition makes true, and `CP_WAIT_SB`, `PK_WAIT_ENG` and `PK_WAIT_SB` also complete the action line of the write before them, which reads the same field, so a timed-out wait keeps that line out of the latch although the write ticked it ([FO-8], 2026-10-10). So the A380's "Rudder trim: NEUTRAL" (`ASC_RUDDERTRIM`) is completed by `AS_RUDDERTRIM_CHECK` (20 s, a judgement: the reset's time to neutral is not measured), never by the reset `AS_RUDDERTRIM`, which completes only its own line. Unlike the 737, 777 and iFly audits it does not map written keys to state fields.

  **The TFDi MD-11 (2026-10-18).** Until then every MD-11 write completed only its action line, and no step stood behind any read-back (`*_CL`) line, so a finished flow ticked and latched 74 read-back lines over whatever the aircraft showed: "Spoilers: Armed" over an arm the executor refused with the speed brake out, "Emergency Power Selector: Off" right after Power Up armed it. Now each write completes the read-back line it sets too (`Also`), and read-only checks (`Check`: "Already set" when the field already holds, else a 5 s wait skipped aloud, never a write) complete the lines no write of that flow sets: the Cockpit Entry switches the First Officer finds (the emergency power selector checked OFF before the flow arms it), Preflight's battery, IRS, ignition and start switches and the EVAC and GPWS guards, "IRS: aligned", "Engine start switches: IN", the takeoff flaps and wing anti-ice, and Parking's exterior lights. Each engine's stabilized wait completes "Engine n: Running", the APU running wait "APU: Running", After Takeoff waits up to five minutes for the Captain's flaps, and both gear lines are FO-13's read-only gear checks. The three start-switch lines, StayComplete on the engine running, are linked to no step, as on the Boeings: a pull marked them, a failed light-up then stopped the flow, and they stayed ticked over an engine that never ran. `Md11FoFlowChecklistLinkTests` pins that those three are the only undelivered lines, that no step links a StayComplete line, that every link names a line its flow latches, that each `_CHK_` check completes only lines reading its own field, and that the gear checks are last and read only.

## FO-7

- **A checklist item with no flow step behind it is still TICKED AND LATCHED when its flow finishes** (`ChecklistManager.MarkGroupComplete` excludes only the lines of steps the run SKIPPED: a Skip-policy step that failed or timed out, a step left alone by `LeaveAloneWhen`, a step skipped through its `RequiresStepId` dependency, and a step whose `TargetValueProvider` had no value (FO-20); all four are in `FlowManager.UnfinishedChecklistItemIds`), so every actionable item in a state group needs a delivering step or it becomes a silent false completion — `BS_TRANSPONDER` read "Transponder: XPNDR" complete with the selector untouched. Adding a step is the fix; never rely on the exclusion set, which a missing step never reaches. → [first-officer.md](../first-officer.md)

## FO-8

- A completed checklist group with participation (a user manual tick or a flow MarkComplete) is completion-LATCHED — RevertToState must not un-tick it until reset/manual untick; never latch on coincidental auto-ticks alone, and never reintroduce item-level StayComplete or an unconditional 100% latch. `MarkGroupComplete`'s group latch is UNCONDITIONAL even when a flow's `excludeItemIds` names a step it could not deliver — the phase's completed steps stay a flight-long historical record — and the one undelivered item is exempted PER-ITEM via `ChecklistItem.ExemptFromCompletionLatch` so IT ALONE keeps mirroring live state inside the otherwise-latched group; this is NOT the item-level StayComplete the rule above forbids (that would freeze every item, not free one). The exemption is set whenever the flow did not itself deliver the item — un-checked, OR checked only via a pilot hand-tick still `AwaitingActionConfirmation` — and its clear must be UNCONDITIONAL, never only when that same call is the one that ticks the item: a hand-tick can check the item before a later pass (state agreeing, or a real re-delivery) tries to clear the exemption, and gating the clear on `!IsChecked` leaves it permanently exempt despite doing exactly what it was supposed to do. → [first-officer.md](../first-officer.md)

## FO-9

- A checklist item the pilot hand-ticks that fires a linked `CheckAction` sets `AwaitingActionConfirmation`; if `RevertToState` later un-ticks it because the switch never actually moved, `ChecklistManager` raises `ItemActionFailed` and the form speaks `"Unable to complete: {label}"` — the only channel that reaches a blind pilot who has navigated away from the checklist tree, where the correction is otherwise silent and visual-only. Never raised for an ordinary revert (the pilot moved the switch back themselves), and it fires from inside a latched group exactly like an unlatched one whenever the item is exempted. → [first-officer.md](../first-officer.md)

## FO-10

- Checklist revert grace is action-aware: `ChecklistManager.RunCheckActionWithGraceAsync` holds revert until the tick's action completes AND the executor's dispatch gate drains (`IFoActionExecutor.WaitForDispatchDrainAsync`), covering the multi-second closed-loop selector walks (transponder / position lights) and anything queued behind them. → [first-officer.md](../first-officer.md)

## FO-11

- **A checklist item whose state field is a SLOW condition needs its CheckAction to hold open until that condition is true — the 10 s `ManualTickGrace` will not save it.** `ChecklistManager`'s own remarks say so ("SLOW actions are covered by ActionSettling, not by inflating this constant") and the Fenix APU is the case that proves it: `BS_APU`/`AL_APU` detect on the AVAIL lamp, which lights only when the APU reaches ~95% N about 45 s after START, while `StartApuAsync` returned at the START pulse. That left ~13 s of grace against a ~45 s condition, so a hand-tick un-ticked itself, `ItemActionFailed` fired, and the pilot heard *"Unable to complete: APU: ON and available"* over an APU starting perfectly — after which it silently re-ticked. `FenixActionExecutor.StartApuAsync` now polls the lamp to `ApuAvailTimeoutMs` (180 s, the SAME budget as the Before Start flow's `WaitForField`, so both paths give up together) and a genuine failure still surfaces with the same message, now truthfully. The dispatch gate is released between writes, so the wait never blocks `WaitForDispatchDrainAsync`. ⚠️ Three profiles detect an APU item on the AVAIL lamp rather than an instant switch position, and each holds the tick open the same way: the Fenix (`FenixActionExecutor.ApuAvailField`), and since 2026-10-06 the FBW A32NX and the Headwind A330 (`A32NX_OVHD_APU_START_PB_IS_AVAILABLE`, their executors' own `ApuAvailField`, held by their own `StartApuAsync` to the same 180 s `ApuAvailTimeoutMs`). The FBW A380 (`A32NX_OVHD_APU_MASTER_SW_PB_IS_ON`), the PMDG 737 (`APU_Selector`) and the iFly (`APU_Switch_Status`) still read the switch — do not "harmonize" a lamp profile onto a switch, the AVAIL gate before external power is dropped is the point. The FLOW never had this bug: it waits in its own `WaitForField` step, and on those three profiles that wait, never the APU master write, completes the line, so an APU that never comes up is never ticked or latched by the flow; the asymmetry between the two paths WAS the bug. → [first-officer.md](../first-officer.md) ⚠️ WHICH lamp that is was settled only by live measurement (2026-09-04, Fenix A319): **`I_OH_ELEC_APU_START_U` is AVAIL (persistent) and `_L` is the ON legend (transient, lit only while the start runs)** — reversed against both the real A320 and the Fenix’s own APU MASTER pushbutton, so the suffixes cannot be trusted on this button. Both readings had shipped once each on reasoning alone, each reproducing the other’s bug (with `_L`, a running APU read as not-available, so the item never auto-ticked and a hand-tick waited on a lamp that would never light again). Every site now reads the ONE constant `FenixActionExecutor.ApuAvailField`; never repeat the literal, and never infer a Fenix legend’s meaning — read it in the sim. → [first-officer.md](../first-officer.md)

## FO-12

- **A hand-tick must never re-do work the pilot already did (2026-09-04).** `ChecklistManager.ToggleItem` fired an item’s `CheckAction` unconditionally, so a pilot who had started the APU themselves — outside the First Officer window — and then ticked the item had the FO re-run the whole start sequence on a live APU (MASTER re-written, START pushbutton re-pulsed) before falsely announcing *“Unable to complete”*. The FLOW never had this bug — `FlowManager` honours a step’s `SkipCondition` and says *“Already set”* — and that asymmetry IS the bug. `ToggleItem` now skips the action, and the `AwaitingActionConfirmation` mark with it, when the item’s OWN state condition already reads DEFINITELY true; an indeterminate (NaN) read still runs it. Gated on `IsAutoDetectable`, so an ACTIONABLE item with no state field (the TCAS/WXR/GPWS self-tests) still fires every tick — those exist to be re-run. → [first-officer.md](../first-officer.md)

## FO-13

- Every First Officer checklist line that confirms the landing gear — the After Takeoff Checklist's "Landing gear: UP" and the Landing Checklist's "Landing gear: DOWN" — is backed by a READ-ONLY wait that is the LAST step of the flow that latches it (20 s, Skip, completes the line, never writes). PMDG 737 and iFly 737 read the gear LIGHTS ("gear up, lights out" / "three green" via `GearLightRules`; `GearConfirmation`, `IFly737GearConfirmation`, synthetic `FO_GEAR_UP`/`FO_GEAR_DOWN`; the iFly counts a DIM light as on). The Fenix reads "lights out" for UP and "three green" for DOWN (`FenixGearConfirmation`, `FO_GEAR_DOWN`, read by the Landing Checklist's `LDC_MEMO_GEAR`, "Landing gear: DOWN", the first line of the landing memo; it was `LDC_GEAR` until 2026-10-06): the green is each wheel's LOWER legend `I_MIP_GEAR_n_L`, and the upper `_U` legends plus `I_MIP_GEAR_RED` count as reds — MEASURED 2026-09-25 (Fenix A320 CFM, powered, gear down and locked: every `_L` = 1, every `_U` and the arrow 0; the annunciator light TEST lights all three `_U` and the arrow, proving they are live; the DIM setting leaves `_L` at 1), never inferred from the suffix or the real A320. `_U`'s colour in transit was not observed. The A32NX and the Headwind A330 read the gear LEGS instead (`FbwA320GearConfirmation`, shared by both: `FO_GEAR_UP` = handle up and `A32NX_GEAR_CENTER_POSITION`, `_LEFT_POSITION` and `_RIGHT_POSITION` all under 5 %; `FO_GEAR_DOWN` = handle down and all three over 95 %; any unknown input is NaN), and their `LDC_MEMO_GEAR` reads `FO_GEAR_DOWN`. On all three A320-family aircraft there is no After Takeoff checklist any more (FOA-8), so the After Takeoff flow's read-only `AT_GEAR_UP_CHECK` (20 s, Skip, never writes) is its last step but links no checklist line. Since 2026-10-16 each has a Landing flow ([FOA-11]) whose last step is the read-only `LD_GEAR_DOWN_CHECK` completing `LDC_MEMO_GEAR` (until then nothing latched that line, and this paragraph said there was no Landing flow). The PMDG 777, whose SDK exposes no gear lights, composes the same checks from the CDA lever AND the stock `GEAR LEFT/CENTER/RIGHT POSITION` SimVars (`Pmdg777GearConfirmation`, synthetic `FO_GEAR_UP`/`FO_GEAR_DOWN`: UP = lever up and every leg ≤ 1 %, DOWN = lever down and every leg ≥ 99 %, the System Display Gear page's own thresholds), fed by `FirstOfficerForm`'s 1 Hz `RequestFOGearPositions()` (777 only, FO-private definition/request 385) into `AircraftStateEvaluator.SetGearPosition` (`ATKOF_GEAR_UP_CHECK`, `LD_GEAR_DOWN_CHECK`, and the checklist lines `ATKOF_GEAR`/`LDG_GEAR`). The action-group LEVER lines are completed by the step that WRITES the lever — iFly "Gear lever: UP" by `AT_GEAR_OFF`, 777 "Gear: UP" by `ATKOF_GEAR_UP` and 777 "Flaps: UP" by `ATKOF_FLAPS_UP` (the After Takeoff Checklist's "Flaps: UP" is completed by the read-only lever check `ATKOF_FLAPS_UP_CHECK`, placed before the gear check) — so a failed write is skipped aloud and left live rather than latched. A synthetic gear field is NaN when any reading it rests on is unknown. Never add a gear WRITE to a check. → [pmdg-737.md](../pmdg-737.md), [ifly-737.md](../ifly-737.md), [a32nx.md](../a32nx.md), [pmdg-777.md](../pmdg-777.md)

  **The FlyByWire A380X (2026-10-09, [FOA-9])** reads the legs too: `FbwA380GearConfirmation` (`FO_GEAR_DOWN`) is the gear lever `A32NX_GEAR_HANDLE_POSITION` down and `A32NX_GEAR_CENTER_POSITION`, `_LEFT_POSITION` and `_RIGHT_POSITION` all over 98 %, the A380 System Display WHEEL page's own green threshold; any unknown input is NaN. Its Landing flow ends with the read-only `LD_GEAR_DOWN_CHECK` (20 s, Skip, never writes), which completes the Landing Checklist's `LDC_GEAR`, "Landing gear: DOWN". It has no After Takeoff checklist and no gear-up check. Pinned by `FbwA380GearConfirmationTests`, `FbwA380ReadOnlyCheckTests` and `FbwA380LandingChecksBehaviourTests`.

  **The TFDi MD-11 (2026-10-18)** has no gear lamp the First Officer can read (its gear shows on the system display), so it reads the legs like the 777: `Md11GearConfirmation` (`FO_GEAR_UP_CONFIRMED` / `FO_GEAR_DOWN_CONFIRMED`) is the lever by TFDi's own threshold (`Md11GearLever`, travel 20 and above is DOWN) and the stock `GEAR CENTER/LEFT/RIGHT POSITION` legs (registered for the First Officer as `TFDiMD11Definition.FoGearLegKeys`, polled each second) all under 5 % for UP and over 95 % for DOWN; any unknown input is NaN. The After Takeoff and Before Landing flows end with the read-only `AT_GEAR_UP_CHECK` and `BL_GEAR_DOWN_CHECK` (20 s, Skip, never writes), completing `ATC_GEAR` and `BLC_GEAR`, which read those fields; the action lines `AT_GEAR` / `BL_GEAR` keep the lever and the steps that write it. Until then both read-back lines read the lever alone and no check backed them, so "Gear: Down" latched over gear still in transit. The stock legs are unmeasured on this airframe; the MD-11 test plan measures them first. Pinned by `Md11GearConfirmationTests` and `Md11FoFlowChecklistLinkTests`.

## FO-20

- A flow step whose `FlowStep.TargetValueProvider` returns null (the data it needs, a SimBrief plan, is not there) is a SILENT SKIP in `FlowManager` (owner decision 2026-10-06): nothing is sent and nothing is spoken (the step is paired with a Captain reminder, and that reminder is what the pilot hears; "Skipping: …" would tell the pilot the flow failed when it only had no plan), the step's `LinkedChecklistItemIds` are NOT marked and ARE kept out of the end-of-flow latch exactly like a skipped step's ([FO-6], [FO-8]: they land in `UnfinishedChecklistItemIds`, so `MarkGroupComplete` leaves them unticked and `ExemptFromCompletionLatch`), the step raises `StepSkipped` (the Steps list marks it "→", not "✓"), and its id joins the run's skipped set, so a step whose `RequiresStepId` names it is skipped too, as after any other skip: a step that builds on a value the flow never set must not run. The inter-step pause is unchanged ([FO-5]). It goes through the same `SkipWithoutRunningAsync` as the leave-alone and dependency skips, with no spoken text. (The `RetryThenStop` failure policy, which no flow used, was removed on 2026-10-18.)

  **Why.** Until 2026-10-06 a null provider was a QUIET SUCCESS: no announcement, success result, so `MarkComplete` ticked every line the step linked and the end-of-flow latch froze it. With no SimBrief plan loaded, the A320 After Start step `AS_FLAPS` ("Flaps: takeoff setting", `Done(Provider(...), "AS_FLAPS")` on the Fenix, the FBW A32NX and the Headwind A330) therefore ticked and latched "Flaps: takeoff setting" over a lever at 0, while its own Captain reminder `AS_FLAPS_CAPT` (skipped only when the lever reads 1–3) was asking the pilot to set the flaps. Now the line stays unticked and follows the lever, so it ticks itself when the pilot sets a takeoff flap.

  **Audit (2026-10-06), every `TargetValueProvider` user.** The three A320s' `AS_FLAPS` (provider null when the SimBrief flaps are not 1–3; links `AS_FLAPS`): the only steps whose behaviour changes in what is ticked or latched (superseded below). The PMDG 737 Preflight `PF_FLT_ALT` and `PF_LAND_ALT` (`DynSW`; null with no plan; link no line (superseded below), nothing requires them): nothing ticked, latched or spoken changes (superseded below); only their Steps-list mark goes from "✓" to "→". So with no SimBrief plan loaded, the PMDG 737 Preflight steps "Flight altitude: set" and "Landing altitude: set" now show as skipped (→) in the Steps list, the honest mark for a step that set nothing; FlowManager is shared, so this holds on every aircraft by design (confirmed 2026-10-06). The TFDi MD-11 `PF_DAF` (Dial-A-Flap; the provider is `TakeoffDialAFlap ?? 0`, never null, so a missing plan fails at the executor as "Skipping"): unchanged. The FBW A380 defines a `Provider` helper and uses it nowhere; the PMDG 777 sets takeoff flaps with plan-gated `SkipCondition` steps, and the iFly 737 MAX8 sets pressurization through its executor's `KeyPressAlts` pseudo-key (its old provider step was removed in 2026-08): neither uses a provider (superseded below for the iFly). Pinned by `FlowManagerTargetProviderTests` (a real FlowManager and ChecklistManager) and `A320FamilyTakeoffFlapsNoPlanTests` (the three A320s' real After Start steps, evaluators and checklists, no sim).

  **The 737 pressurization line (later 2026-10-06, supersedes the 737 half of the audit above).** Linking no line meant nothing kept the Preflight state line `PF_PRESS` ("Flight and landing altitudes: SET") out of the latch, so a no-plan Preflight run still ticked and froze it over windows nobody had set ([FO-7]). The PMDG 737's `PF_FLT_ALT` and `PF_LAND_ALT` now both name `PF_PRESS` (the line reads both windows, so either one skipping or failing keeps it open). The iFly 737 MAX8's single `PF_PRESS_ALTS` step still goes through the `KeyPressAlts` pseudo-key (FOB-17), but is now plan-gated by a provider (null with no plan, a fixed token otherwise; the pseudo-key reads the plan itself) and names `PF_PRESS`: before, with no plan the pseudo-key's quiet no-op "succeeded", so the pilot heard "Flight and landing altitudes: set" right before the Captain fallback asked for them. With no plan both aircraft now say only the Captain fallback and leave `PF_PRESS` unticked and exempt from the latch (NaN with no plan, so it never auto-ticks; a hand tick holds). Neither Preflight read-back has a pressurization-altitude line (`PFC_PRESS` is the mode selector). Pinned by `Pmdg737PressurizationNoPlanTests` and `IFly737PressurizationNoPlanTests` (real steps, evaluators, checklists and FlowManager, no sim). → [first-officer.md](../first-officer.md)

## FO-22

- A First Officer window that first sees the aircraft FLYING without having watched it take off marks the departure checklists complete and latched, once, and says so once (owner, 2026-10-14: "Through After Takeoff"; Descent onwards stay open). "Departure" is every group from power-up through After Takeoff in `FoDepartureGroups.Departure`, action lists and read-backs alike; `FoDepartureGroups.Arrival` holds the rest, and `FoDepartureGroupsTests` fails on any group of any of the eight profiles in neither set or in both, so a new group has to be classified by when its phase happens (before takeoff: departure) the day it is added. `FoDepartureGroups.MarkComplete` calls `ChecklistManager.MarkGroupComplete` with nothing excluded for each departure group the profile has: every non-separator item is ticked, the group is latched and counts as worked ([FO-8]), so live state cannot un-tick it. That is the intended effect: the window did not watch the flight, and the lists would otherwise sit open over an aircraft that is already past them.

  **The detector (`InFlightStartDetector`, pure).** Fed `SimOnGround`, the AGL and the IAS once per position sample; it fires at most once per time in the air. Never seen yet: fires at 100 ft AGL and 50 kt IAS or more; lower or slower waits (the window was opened just after liftoff), and on the ground it never fires, so the main menu and a parked aircraft stay quiet. Seen on the ground: fires only if, within 5 s of the first airborne sample at flying speed, the aircraft reads 500 ft AGL and 50 kt or more, a flight put into the air rather than climbed there; after the 5 s it was a takeoff and nothing fires. "At flying speed" means AGL and IAS both known and IAS 50 kt or more: an airborne sample that is unknown (NaN) or slower neither fires nor starts the window, and while the window has not started nothing advances it. The thresholds are judgements (an airliner is far below 500 ft five seconds after liftoff), not measurements. After a landing the detector is armed again: a second flight loaded in the air fires again, and a bounce on landing (a few feet, then the ground) never does.

  **Why a window, not one sample.** The first airborne sample after a flight is loaded in the air can still carry the old on-the-ground AGL (and a 0 kt IAS). Judging on that one sample would call a loaded flight a takeoff and leave the lists open; waiting out the 5 s for a fresh sample fires it. The window itself, that a fresh sample 5 s after the first flying-speed sample is still inside it and one a hair later is a takeoff, is pinned by `Window_boundary_exactly_5_s_after_the_first_flying_speed_sample_is_still_inside` (a stale 60 kt sample starts the window); `Ground_then_stale_low_sample_then_high_within_window_fires` pins only the zeroed sample (2 ft, 0 kt), which starts no window, so it passes with any delay and does not pin the 5 s. The opposite, a brisk but real takeoff that must never fire, is pinned by `Watched_takeoff_never_fires`.

  **Why the window starts at flying speed, not at the first airborne sample (fix round 1, 2026-10-14).** With the window already open on the ground, a flight load can deliver zeroed samples (not on the ground, about 0 ft, 0 kt) for longer than 5 s before the real cruise data lands. A window started by the first airborne sample, whatever it read, would have expired by then, the cruise sample would have been judged a takeoff and the catch-up would never have fired. A real takeoff is at 50 kt or more from liftoff, so starting the window at the first known sample of 50 kt or more leaves its behaviour unchanged. Pinned by `Ground_then_zeroed_airborne_samples_for_10_s_then_cruise_fires`, `Ground_then_unknown_airborne_sample_does_not_start_the_window`, `Slower_than_50_kt_in_the_air_neither_starts_nor_advances_the_window_and_50_kt_does`, and, for the boundary (exactly 5 s after the window start is inside, a hair later is a takeoff), `Window_boundary_exactly_5_s_after_the_first_flying_speed_sample_is_still_inside` and `Stale_low_then_fresh_high_just_past_the_window_is_a_takeoff`. Known limit: the window is wall-clock time, so at a raised sim rate a watched takeoff could climb 500 ft inside it and be taken for a flight put into the air; like the other thresholds this is a judgement, not a measurement. `FirstOfficerForm` keeps `_latestIas` at 0 for the auto manager (it reads 0 as "not flying"), so it hands the detector NaN until `FO_AIRSPEED_IAS` has been read once (`_iasReceived`): a 0 that was never read must not pass for a measured 0 kt.

  **Threading.** The detector runs on the SimConnect thread in `OnAircraftPositionReceived`; a firing sets a volatile pending flag. The window's 1 s UI timer consumes it first thing in its tick, before `EvaluateAutoDetection`: it marks the groups there (the tree refreshes through the existing `ItemStateChanged` and `GroupProgressChanged` handlers) and speaks the one announcement with `Announce`, never `AnnounceImmediate`: it is a background change the pilot did not trigger, so it queues behind what is being read ([CORE-7]). The window is built the first time the pilot opens it and starts its timer and position feed in its constructor, so it samples from the moment it exists, which is what "first sees" means.

  **Reset still works.** Reset Section and Reset All clear the ticks and the latch as ever; the lists are marked again only if the aircraft is put into the air again without a takeoff the window watched. Not unit-tested: the form wiring (CORE-5); the detector, the classification sweep and the catch-up over every profile's real group ids are. → [first-officer.md](../first-officer.md)
