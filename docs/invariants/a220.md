# Synaptic A220-300 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/a220.md`, which Claude Code loads when it reads matching code. Background: [a220.md](../a220.md).
The text is verbatim from CLAUDE.md on `feat/synaptic-a220` as of `fda36823`; a trailing "→ doc" pointer is the original's. The FMS, ECL and EFB rules (A220-18 to A220-32) are in [a220-fms.md](a220-fms.md).

## A220-1

- A220 L:var names contain SPACES (`L:A22X APU Switch`) — every A220 write goes through `ExecuteCalculatorCode` directly (the def's `HandleUIVariableSet` claims EVERY settable control); never let one reach `SetLVar`, whose space/colon guard routes it to the unreliable data-def write (and `CalcPathVerified` never goes true for non-FBW defs anyway). Do NOT weaken the global guard — it protects stock-SimVar shapes for every other aircraft. Classification exception: `A22X `/`INI_` prefix = L:var despite spaces. → [a220.md](../a220.md)

This is the A220's exception to VAR-2, which since 2026-10-07 classifies by an add-on's own prefix or source and leaves an aircraft whose L:vars contain a space or a colon to say so in its own rules. The rule line names VAR-2 since the same date; the bullet above is unchanged.

## A220-2

- Never register the `L:A22X Aural *` native playback flags — the aircraft speaks its own callouts (V1, radio heights, TAWS, takeoff config); announcing them doubles the audio. Three same-prefix names ARE real controls (Aural Warn Inhibit + Lamp, Aural Internal Test). Test-pinned. → [a220.md](../a220.md)

## A220-3

- APU start is HOLD-to-start (sustain 2 for ~3 s with seq-prefixed re-writes, release to 1) inside the control write, and every A220 calc string carries the `{seq} 0 *` anti-coalescing prefix. → [a220.md](../a220.md)

## A220-4

- A220 cache-fresh quiet vars must be `Continuous+IsAnnounced=true` swallowed in `ProcessSimVarUpdate` (`_silentReadoutKeys`) — `IsAnnounced=false` Continuous vars get NO subscription at all (stale cache). → [a220.md](../a220.md)

## A220-5

- NAV radios are STANDBY-set only — no NAV active-set or swap control may ever exist; manual active ILS tuning breaks the A220's NAV-to-NAV transfer incl. the 400 ft go-around retune. No spoiler-arm control (the aircraft masks the stock arm events). Both test-pinned. → [a220.md](../a220.md)

## A220-6

- A mode/TOGA press is never followed by silence — FG transitions announce via the monitor, `AnnounceModeResult` adds the deferred honest "no change" call, TOGA diffs an FG snapshot and always speaks. → [a220.md](../a220.md)

## A220-7

- FCP dialogs walk, never set — RE-PROVEN 2026-08-10: every stock SET event leaves the WASM's FCP untouched (re-proven 2026-09-21: 12000 written to `AP_ALT_VAR_SET_ENGLISH`, the selector did not move), inc/dec ignore their parameter, and the JS→WASM CommBus surface has no FCP channel. The ALTITUDE walk is grid-based (the selector SNAPS to round 1000s/100s per ring — coarse for thousands, fine for hundreds); every other knob keeps the self-calibrating measured walk; never reintroduce open-loop step-count math. The VS thumbwheel is DEAD until VS/FPA mode engages — engage first, then walk (LVFR lesson). → [a220.md](../a220.md)

## A220-8

- The FCP walk's read-back PREFERS the aircraft's own `A22X.FCP Data` CommBus block at 30 Hz. Without it, a walk may read a stock var only where `A220Afdx.KnobWalkMayUseStockVar` allows, and that fallback is a SOUND source for altitude and heading, not a degraded guess: measured live 2026-09-21, the stock `AUTOPILOT ALTITUDE LOCK VAR` and `HEADING LOCK DIR` each track their FCP knob click for click (0→1000→2000→2100→2200→2300→3000 on the altitude selector; 245→246), and the heading again on 2026-09-24 (178 = 178). **This bullet used to say they were NOT published and that cost every link-less session the good walk** — `ReadAfdxLiveAsync()` returning null dropped the altitude entry straight onto the inferior measured fallback, so a user without the Coherent display agent could never get the grid walk at all. The fallback read is a DELIVERED one (`SimConnectManager.ReadFreshAsync`, 1.5 s timeout), never a fixed sleep and the cache: only the TIMING degrades, to the 1 Hz batch's next sample, and a read that does not come back is "not confirmed", never a guess. The speed knob has NO fallback: `AUTOPILOT AIRSPEED HOLD VAR` read 80→81 for one click on 2026-09-21, but on 2026-09-24 it read 445 kt with 142 kt in the window and never moved with the knob, so the speed walk refuses aloud without the FCP block. → [a220.md](../a220.md)

Reworded 2026-10-16 (the knob-walk review, R7 and R9). The line used to keep the 1 Hz cache with a 1.3 s settle as the fallback and listed the speed var among those that track the knob. The code stopped reading the stock speed var on 2026-09-24 (commit 8870332e), and since 2026-10-16 every fallback verdict reads through `ReadFreshAsync`: on a 1 Hz batch a 1.3 s sleep left only about 300 ms past one delivery, and the cache read could predate the burst it was judging ([MD11-9] dropped the same pattern). The old line's "measure the step, never assume it" is not lost: [A220-9] and [A220-10] keep the measured step, and the one-unit speed and heading knobs, whose step is known, never overshoot (`A220Afdx.ExactKnobClicks`).

## A220-9

- The A220 knob walk must AIM, never hunt: fire `round(|delta|/step)` clicks (`A220Afdx.AimClicks`) to land on the nearest selectable value, and treat 0 clicks as "already closest — stop and say so". `floor()` plus a one-click creep straddles the target forever on a coarse step (live: asked 6000 ft, got 5085 ft — the FCP altitude selector was in METRES, where 5085 ft = 1550 m and the day-one "492 ft/click" is 150 m; a round number of feet is often not selectable at all, so the walk must NAME the metres mode in its result). Walk DIRECTION is calibrated on the first move (swap inc/dec if it went the wrong way), never assumed. → [a220.md](../a220.md)

## A220-10

- An A220 walk must never quit before it has moved the knob — "nothing closer is selectable" is only valid from a step measured ON THIS walk; an inherited `_fcpStepCache` step larger than the remaining delta makes round 0 fire ZERO clicks and announce a result untested (live: "set heading 270, stopped at 239"). And never batch several `(>K:EVENT)` statements into one calc string — MEASURED 2026-09-21: four `(>K:AP_ALT_VAR_INC)` in one string moved the selector by exactly ONE click (2100→2200), so the WASM samples the event once per frame and a batch of n applies as 1, feeding the step estimator a value n times too small. → [a220.md](../a220.md)

## A220-11

- The A220 ALT knob's PUSH is the fine/coarse ring (`FCU_ALT_PUSH` `BTN_VAR = L:A22X FG Altitude Fine`, `BTN_TOGGLE`), and that L:var is a **LEVEL, not a pulse** — measured live 2026-09-21: write 1 and clicks become 100 ft, write 0 and they become 1000 ft, and the value persists across clicks (the WASM resets it to 0 at power-up, not per click). So the walk's ring writes are sound, but they must be CHECKED: a ring that did not flip makes every later click a tenth (or ten times) the assumed size, so the walk measures what a burst actually moved and re-selects the ring once when the step is off by more than 2× (`A220Afdx.StepIsWrongRing`). In METRES the coarse ring steps ~492 ft, which is where "round altitudes are unreachable" comes from; in FEET the grid is exact (coarse = round thousands, fine = round hundreds), so the walk uses coarse for the thousands and fine for the hundreds and puts the pilot's own ring back afterwards. → [a220.md](../a220.md)

## A220-12

- **No stage of the altitude walk may stop "close enough".** Its coarse stage used to exit at `|delta| < step/2` — 500 ft — while the final verdict demands 50 ft, so an off-grid start within 500 ft of a round thousand fired ZERO clicks and then announced *"Altitude did not reach 5000 — selector reads 5085 feet"* for a target ONE click away (the metres-leftover case, and the "always something close but not quite right" report). Every stage exits only when it is genuinely ON its value (5 % of a step); `GridClicks` has always been able to make that click, it was never asked to. → [a220.md](../a220.md)

## A220-13

- A220 stabilizer trim is set by the same calibrated walk over the RATE events `ELEV_TRIM_UP`/`_DN` reading `efcs.pitch_trim` back — there is no set event and no trim L:var. It must REFUSE when the display link is down (no read-back = open-loop on a stabilizer), and the number to type is the EFB takeoff-perf figure, which that EFB renders as `abs(trimUnitsNoseUp).toFixed(1) + "UP"`. → [a220.md](../a220.md)

Owner decision, 2026-10-16: keep this rule and change the code. From 2026-09-22 (commit 49298a0b) the walk had fallen back, with the link down, to `L:A22X Horizontal Stabilizer` × 17 (`A220Afdx.StabTrimFullScaleUnits`), the trim animation ratio over the EICAS's 0-17 travel. That estimate rests on one measurement (5/17 at rest, tracking about 28 clicks monotonically), and docs/a220.md says never to present the ratio as the trim setting; the rule, copied on 2026-10-02, still said refuse, so code and rule disagreed. The owner chose the refusal. Since then `A220Afdx.KnobWalkMayUseStockVar` is false for the stab trim (pinned by `A220KnobWalkTests`): with `efcs.pitch_trim` missing before the first click, the walk says `A220Afdx.StabTrimLinkDownText` ("Stabilizer trim not set — the display link is down, so the trim cannot be read back. Try again when the link is back.") and sends nothing; a link lost part-way stops the walk with "not confirmed", never a value from the ratio. "Missing" means after the resync-and-retry read (`ReadAfdxFieldAsync`: 8 tries 150 ms apart, a whole-copy request after the first and fifth miss, `A220Afdx.AfdxResyncAfterMiss`), for every read of the walk and with no latch: the agent calls a store quiet for 3 s stale and the flight-control store goes quiet with the trim at rest, so one missed read must never refuse while the link is up (review of 2026-10-16).

## A220-14

- A220 stab/rudder trim exist ONLY on the CommBus (`efcs.pitch_trim`/`efcs.rudder_trim`) — there is no trim SimVar on this aircraft, and `L:A22X Horizontal Stabilizer` is the ANIMATION ratio, never the cockpit's units. The stab read-out must quote the `pitch_trim_dn`..`pitch_trim_up` takeoff band so it ANSWERS a CONFIG STAB TRIM warning; don't expose aileron trim (the EICAS renders that block `visibility: "hidden"`). → [a220.md](../a220.md)

## A220-15

- `RegisterViewListener` is ASYNCHRONOUS — a CommBus `.on()` made before its ready callback fires is silently dropped. Subscribe from the ready callback, retry while nothing has ever arrived, and ship a `diag` block with the tap (the A220's `A.afdx()` → `A220Afdx.DescribeTap` names the failing layer on Alt+F). A silently-dead tap cost a full live session of shipping fixes on top of fallbacks; build the diagnostic WITH the feature, never after it fails. → [a220.md](../a220.md)

## A220-16

- A220 FD state must come from `A22X.Autoflight Data` `l_fd`/`r_fd`, NEVER from `L:A22X L/R Flight Director` — that L:var is bound to `A220_ButtonMomentary` (a press pulse), so it reads 0 whatever the FD is doing and a level write to it is meaningless; the FD panel entries are momentary BUTTONS plus separate CommBus-fed state rows, and a missing link renders "Unknown", never "Off". → [a220.md](../a220.md)

## A220-17

- A220 FD-command, trim and rudder-trim signs/scales were decoded from the aircraft's own rendering maths and are test-pinned — `cmd_lateral` + = bank RIGHT, `cmd_vertical_fpa` + = UP, `cmd_vertical_pitch` + = NOSE UP (the TO/GA cue, null otherwise), `rudder_trim` + = nose RIGHT with ±1 = FULL SCALE. Never re-derive one by eye: a wrong sign in a guidance readout is confidently wrong, not obviously broken. → [a220.md](../a220.md)
