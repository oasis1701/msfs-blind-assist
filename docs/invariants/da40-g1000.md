# COWS DA40 G1000 display rules — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/da40-g1000.md`, which Claude Code loads when it reads matching code. Background: [da40.md](../da40.md).
The text is verbatim from the CLAUDE.md invariants PR #242 added; where two bullets told one rule they sit together under one ID. A trailing "→ doc" pointer is the original's.

## DA40G-1

- **The DA40's G1000 answers its SOFTKEYS over SimConnect and NOTHING ELSE on the bezel** (and the same socket now also carries the page jump, the field list and typed entry — see the view-model rules below). `1 (>H:AS1000_MFD_SOFTKEYS_11)` through the calculator path presses the key; `1 (>H:AS1000_MFD_FMS_Lower_DEC)` down the same path is inert, and it is NOT the MobiFlight duplicate-command trap — the same write carrying a `901 0 *` uniquifying prefix is equally inert. Fired in-page through the instrument's own `onInteractionEvent` all of them work, so the FMS knob, MENU, ENT, CLR, Direct-To, FPL, PROC, the range knob and the map joystick go over the Coherent socket (`CoherentDisplayClient.InvokeAsync` → `A.key(...)`) and the softkeys stay on SimConnect. This is a MEASURED exception to "read over Coherent, write over SimConnect", the same shape as the A380's KCCU keys. Event names come from the instrument's own `FmsHEvent` table in `mfd.js`/`pfd.js` (18 MFD, 13 PFD), never guessed — and ⚠️ `AS1000_MFD_CLR` carries NO `_Push` suffix unlike every other button in the family, so the plausible `AS1000_MFD_CLR_Push` is a silent no-op. → [da40.md](../da40.md)

- **⚠️ THE DA40's G1000 RADIO KNOBS GO OVER SIMCONNECT, THE OPPOSITE WAY ROUND FROM THE REST OF THE BEZEL.** Measured both ways on COM 2 standby: `onInteractionEvent("AS1000_PFD_COM_Small_INC")` left it at 124.850, `1 (>H:AS1000_PFD_COM_Small_INC)` moved it to 124.855 (same for NAV: 113.90 → 113.95). Moving the whole bezel onto the Coherent socket silently killed radio tuning from the display window. The knob PUSH is the exception to the exception - it moves the tuning box, works over the socket, and reads back there. So the display has TWO measured transport exceptions pointing opposite ways: FMS/MENU/ENT/CLR/DTO/FPL/PROC/range/joystick + the radio PUSH over the socket; the twelve softkeys + the radio TURNS over SimConnect. → [da40.md](../da40.md)

- **⚠️ THE G1000's DATABASE-ACKNOWLEDGE SCREEN TAKES ENT OVER SIMCONNECT ONLY.** After a reload the XLS MFD sat on "Press ENT or rightmost softkey to continue" and the whole display read as "starting up" on every page - `A.press("ENT")` over the Coherent socket left it there, `1 (>H:AS1000_MFD_ENT_Push)` cleared it. The same split the softkeys have, and `CowsDA40DisplayForm.EntGoesOverSimConnect` routes Ctrl+Enter accordingly from the agent's first row. A coverage sweep run against that screen reports every page unread (236 items) - acknowledge it first. → [da40.md](../da40.md)

## DA40G-2

- **A G1000 softkey press MUST go through `ExecuteCalculatorCodeUnique`** — MobiFlight coalesces consecutive byte-identical calc strings, and pressing the SAME softkey twice running is exactly that. Measured on the DA40 PFD: typing a squawk of 1-0-0-0 with plain writes left the code at `0010` (the two repeat zeros dropped); the same presses uniquified commit `1000`. Not an edge case — a squawk with a repeated digit, or stepping the CDI past a source, both press one key twice. The transponder keypad is OCTAL and OFFSET BY ONE (softkey 1 = "0" … softkey 8 = "7", softkey 10 = backspace), and the code SHIFTS IN FROM THE RIGHT, committing on the fourth digit, so a half-typed code sits right-aligned and looks like a valid code. → [da40.md](../da40.md)

- **A softkey press must never be SILENT, and a changed-row diff must key on label AND OCCURRENCE.** Silence made CDI and OBS (which cycle a value in place, leaving the twelve labels untouched) read as dead keys; the window now speaks the first row that changed, falling back to the pressed key's own label. Keyed on label alone the CAS block breaks that diff — every message reads "Caution: ...", so the map keeps only the first and matches the SECOND caution against it, announcing a standing caution after every keypress. → [da40.md](../da40.md)

## DA40G-3

- **Which G1000 display an agent is on is decided by the INSTRUMENT ELEMENT (`wtg1000-mfd` vs `wtg1000-pfd`), never by page markup** — testing for `.eis`/`.mfd-page` read the PFD as an MFD (both views carry some of the other's markup, unused and invisible) and rendered the entire PFD as MFD rows: no CAS, no FMA, no navigation source, on the one display where those are the point. → [da40.md](../da40.md)

## DA40G-4

- **ASK THE G1000 FOR ITS STATE; NEVER READ IT OFF A CSS CLASS.** `wtg1000-mfd` IS the instrument object and carries a `viewService`: `activeViewKey`/`openPageKey` say which page or dialog is up, and each view's `scrollController` answers `getIsScrollEnabled()` (the cursor), `getFocusedUiControl()` (which field), `getActivatedUiControl()` (is it open for editing) and `props.data` (its choices). The cursor had been sniffed from markup and was wrong on five separate pages — `cyan`, `highlight-active`, `input-component-value`, `number-input-active`, `hidden-element` — each fix being "learn one more class name" and each next page using a different one. The DOM reader survives ONLY as the fallback for a display whose instrument element is not up yet (`A.M.cursor()` returning null, which is a different answer from false). → [da40.md](../da40.md)

- **The G1000's interaction rules come from its own source (`Function.prototype.toString` on the live instrument), never from experiment alone:** `UPPER_PUSH` toggles the cursor; with the cursor OFF any knob opens the PAGE SELECTOR (upper = page, lower = group); with it ON the LOWER knob moves BETWEEN fields and the UPPER knob acts ON the focused one (opens its choice list, or cycles a character); inside a list LOWER moves and ENT accepts. Two consequences that read as bugs and are not: the FIRST turn of the upper knob on a text box only ACTIVATES it and changes nothing (`InputComponent.onUpperKnobInc`), and PRESSING the FMS knob on a setup field does NOT open its list — `UPPER_PUSH` is absent from `UiControl.onInteractionEvent`, so it falls through to the page and toggles the cursor. → [da40.md](../da40.md)

## DA40G-5

- **⚠️ THE G1000 HAS TWO CONTROL FRAMEWORKS AND A READER MUST WALK BOTH.** Setup pages, dialogs and Direct-To use `scrollController.controls[]`; the flight plan page, the checklist and every list use `G1000UiControl` (`registeredControls`, `focusedIndex`, `getChild`, `_UICONTROL_`). The FPL page's scrollController is EMPTY, so counting controls reported it as having nothing on it — that is the "active flight plan page doesn't even arm" report; it arms fine, `MFDFPLPage.setScrollEnabled` focuses the other framework's root. The CURSOR flag stays on the scroll controller for both, which is why that and never the control count is what to ask. → [da40.md](../da40.md)

## DA40G-6

- **A G1000 page name with an EMPTY KEY in the page selector's `pageGroups` table has NO PAGE BEHIND IT** — 17 of the 32 names are stubs the stock Working Title instrument draws and never implemented, including SEVEN of the nine in Aux (Trip Planning, Utility, GPS Status, XM Radio, System Status, Connext Setup, Databases). The knob lands on them and does nothing for a sighted pilot too. Never treat that as a reader fault, and never HIDE them either: say "not in this G1000", or a blind pilot cannot tell a page the aeroplane never built from one MSFSBA is failing to read. → [da40.md](../da40.md)

- **⚠️ 15 of this G1000's 32 advertised pages are STUBS with an empty key** (Weather Data Link, TAWS-B, VRP/User WPT Information, Trip Planning, Utility, GPS Status, XM Radio, System Status, Connext Setup, Databases, and four Nearest pages). They are left OUT of the Ctrl+G jump list — a menu entry that cannot be gone to is a dead key with a name on it — but the rule that the READOUT still says "not in this G1000" when the KNOB lands on one is UNCHANGED and must stay: a page the aeroplane never built has to be tellable from one MSFSBA is failing to read. → [da40.md](../da40.md)

## DA40G-7

- **A PFD "page" is a SUBVIEW and an MFD page is not** — `viewService.open(key, true)` vs `open(key)`; opening one the other way leaves the view registered but never shown. The PFD has no pages at all (`openPageKey` is permanently empty), only 15 windows, several of which (TimerRef, ADFDME, Nearest, Alerts, PFDSetup) have no bezel button and hide behind softkeys. → [da40.md](../da40.md)

## DA40G-8

- **The simulated G1000 DOES take typed entry, contrary to the real unit** — every waypoint box carries a keyboard icon, and its `InputComponent` exposes `activateKeyboardInput`, `setValueFromOS` and `setText(value, highlightIndex, emitEvent)`. Driving `setText` runs the aircraft's OWN debounced database search, autocomplete and facility lookup untouched, so typing an ident is a documented capability and not a workaround. ⚠️ Read the result back AFTER a delay (~900 ms measured): asking immediately returns the PREVIOUS search's match, which is how VCRI first read back as Bandaranaike. → [da40.md](../da40.md)

## DA40G-9

- **The DA40 MFD's first FMS-knob turn does NOT change the page** — it opens the page SELECTOR; the next turn moves. Never "fix" that by auto-sending a second turn: a sighted pilot gets the same two-step, and the extra turn would skip a page every time the selector had closed. It does mean a readback of the page TITLE after a turn names the page the pilot is still on, which sounds like a dead key — so while the selector or the page menu is up, `A.summary()` speaks THAT window instead, and the read-back settle is 1200 ms because the selector commits about a second after the last turn. → [da40.md](../da40.md)

## DA40G-10

- **A G1000 horizontal EIS gauge carries NO NUMBER** — the real display draws Oil Temp, Oil Press, Coolant Temp, Fuel Temp and Fuel Qty as a needle on a coloured scale with no digits, so the reading IS the band the needle sits in. Take the needle's TRANSFORM, never its bounding box (the svg is as wide as the whole gauge), and select it as `svg[style*='translateX']`, never as `.pointer` — the two-needle fuel gauges use `.pointers > .pointer-one-div`/`.pointer-two-div`, so a `.pointer` lookup made both fuel gauges read "no reading" while every other gauge worked. This is NOT a duplicate of the Engine panel: that panel reads the sensor L:vars at full resolution and answers what the engine is doing, this answers what the SCREEN shows. → [da40.md](../da40.md)

## DA40G-11

- **Some G1000 pages leave `.nav-data-bar-page-title` BLANK (every NRST page does)** — fall back to the page selector, which keeps its active tab and highlighted entry in the DOM while CLOSED; answering "not shown" reports a fault that does not exist. → [da40.md](../da40.md)

## DA40G-12

- **A DASH IS NOT GLUE in the display agent's text joiner.** Binding it tidied `31 - AUG - 26` into a date and in the same stroke closed the CAS Alerts pane's `PITOT HT OFF - Pitot heat is off.` into `PITOT HT OFF-Pitot heat is off.`, destroying the separator on the one pane whose whole job is spelling an abbreviation out. Brackets, commas and the degree sign DO bind; a run of underscores or dashes is one blank field (`__:__` is an empty time, not `blank :blank`). And a G1000 LIST ROW is read FIELD BY FIELD from its child elements, never through the joiner — the last digit of an identifier and the first of a bearing are both digits, so the rule that keeps a clock from becoming `0 : 0 0` welds `VCBI 020` into one token. → [da40.md](../da40.md)

## DA40G-13

- **A G1000 procedure's leg sequence is a list that is NOT built as one** — SID/STAR/approach legs sit in a plain container rather than a `ui-control-list`, so a generic reader runs the whole procedure into one token; read `.proc-sequence-item` per leg. Those are the legs the aeroplane is about to fly, and which leg is the FAF and which the MAP are the two facts on the page that matter most. → [da40.md](../da40.md)

## DA40G-14

- **⚠️ THE FIRST `querySelector` MATCH IS NOT ALWAYS THE ONE ON SCREEN on the G1000.** The PFD carries TWO `.cas-display` blocks of 32 rows each — one rendered, one `display:none` with stale content — and the HIDDEN one comes first in document order, so `document.querySelector(".cas-display")` read the dead copy, found every row hidden, and reported "CAS messages: none" while ECU A FAIL, ECU B FAIL and PITOT HT OFF were on screen. On an aeroplane whose only channel for most failures IS the CAS window this is the worst possible failure, and it read as a clean scan rather than an error. Everything duplicable now goes through `firstVisible(sel)` (CAS, FMA, nav source, softkeys, EIS strip, page title), and `A.cas()` merges EVERY visible copy de-duplicated by text. This is also the likely root cause of the background CAS auto-announce never working — the monitor shares `A.cas()`, so it had never seen a message at all. → [da40.md](../da40.md)

## DA40G-15

- A G1000 popout dialog is OPEN iff its `opacity` is non-zero; all four stay `display:block`, `visibility:visible`, full-size and classed `quickclosed` whether open or shut. → [da40.md](../da40.md)

## DA40G-16

- **A G1000 page menu (`*MenuDialog`) is never row-named, and a self-naming value ("X: Y") neither names a row nor takes one's name** — the field-naming walk lending a neighbour's name made every menu row say "Failure mode …" and the checklist "Normal, Normal". The checklist's selectors and its Go to Next Checklist button are read by `A.checklistSelectorSay`. → [da40.md](../da40.md)

## DA40G-17

- **A G1000 field is read with the BOX it lives in** (`groupbox` + `groupbox-title`, the instrument's own pairing, used on every page family): "Nearest Airport, Minimum Length: 3000FT". A bare field name is close to meaningless on a setup page and a sighted pilot never has to ask. → [da40.md](../da40.md)

- **A G1000 field's group label comes from `groupbox` + `groupbox-title`, EXCEPT on the PFD's own windows**, which name their rows themselves (`timerref-timer-title`). Fall back to any ancestor title element - but ONLY when no groupbox was found in the whole climb, because the setup page's ROWS carry a title element too and an unrestricted fallback answers "Time Format, Time Format: UTC". → [da40.md](../da40.md)

## DA40G-18

- **The Aux System Setup page DRAWS ten boxes and only five have controls behind them** - BARO Transition Alert, Airspace Alerts, Arrival Alert, Flight Director and GPS CDI render values and register nothing, so the knob walks past them for a sighted pilot too. Setup 2 (softkey 7) is a stub as well: pressed over SimConnect, the transport that does work for softkeys, the page stays on System Setup 1. → [da40.md](../da40.md)

- **The G1000's "77 settings" are a STORE, not a page** - System Setup has 14 editable fields; the rest live on the PFD softkeys (SVT, wind, ALT Units, STD Baro), the Map Settings page (~45), the Traffic page menu and the nav data bar. Do not tell a pilot to look for 77 rows. → [da40.md](../da40.md)

- **Every G1000 page has a MENU and Ctrl+E opens it in the display window** - the MFD Engine page's menu is where all nine COWS simulation options live. Ctrl+Enter toggles a row; the three with values take Ctrl+Up/Down. Verified by driving PANEL_SHAKE_OFF 0-1-0 through it. → [da40.md](../da40.md)

## DA40G-19

- **Every function `CowsDA40DisplayForm` calls on the injected agent is a by-NAME contract across a socket that no compiler checks**, and all three ways it has broken are now asserted in `CowsDA40G1000AgentContractTests`: the window parsed the answer by field COUNT and the agent grew a field (`ok|cursor|view|summary` is FOUR); `A.press` was defined TWICE so the first was silently unreachable; and a renamed function left a key dead with no error anywhere. → [da40.md](../da40.md)

## DA40G-20

- **⚠️ INDENTATION IS NOT A CAS MESSAGE.** The DA40's display scrape indents every nested list it emits - the PFD popout panes, and the field list every page now carries - so the CAS monitor's original "row starts with two spaces" rule announced `Weight: Pounds(LB)` as a caution the moment a setup page was opened. The block starts at the `CAS messages:` header and ends at the first row that is not part of it (`ExtractCasMessages`, static and tested). → [da40.md](../da40.md)

## DA40G-21

- **Never prefix a per-item state to every announcement on a scrolling display** - "Cursor on." on every field meant hearing it fourteen times down one setup page. Announce a state on its TRANSITION (both directions, since neither marks itself), and announce the ITEM the rest of the time. Related: the G1000's FMS knob does NOT wrap, so the agent's state answer carries the focused-field INDEX and the window says "end of the page" when a field-moving turn left the focus where it was - otherwise a pilot at the bottom hears the same field a dozen times with nothing to explain it. → [da40.md](../da40.md)

## DA40G-22

- **A live-updating `DisplayListBox` re-announces items as "not selected" while the pilot arrows through it** - the poll adds or removes rows, `DisplayList.UpdateInPlace` moves the selection to follow the row they were on, and a ListBox whose selection is re-set under a screen reader re-announces the item WITH its state. The DA40 display window holds the redraw for 2.5 s after the last arrow/Home/End/Page key (F5 cancels the hold). ⚠️ Feed the CAS watcher and any other announcer BEFORE the hold - delaying a caution to tidy a redraw is the wrong trade. → [da40.md](../da40.md)

## DA40G-23

- **The MSFS G1000's source IS public - `microsoft/msfs-avionics-mirror`, `workingtitle-instruments-g1000`** - so which stock pages are implemented can be READ rather than probed for. ⚠️ The aircraft's own plugin is NOT in there: `Da40NgMfdPlugin.js` (Engine page, checklist, COWS options menu) is COWS's own code in the package, and is the half that has to be learned by probing. -> [da40.md](../da40.md)

## DA40G-24

- **⚠️ A "read the view's text when it has no controls" FALLBACK MUST BE A WHITELIST.** The G1000's page selector, while fading out, has no list (so `A.M.list()` is null), no compiled map and short text - so an inferred fallback read the whole selector back as one run-on blob. Name the views whose content IS their text (`Auth` only, on the DA40) rather than inferring them. → [da40.md](../da40.md)

- **⚠️ THE `while (viewKey != pageKey) closeActiveView()` ESCAPE CANNOT FREE A STUCK VIEW THAT IS THE PAGE.** Navigraph's `Auth` registers as the open page and re-asserts itself every few seconds while a device-code sign-in runs; `goPage("NavMapPage")` is the way out, and `view.cancelSource.cancel()` ends the sign-in. Never leave one running after probing. → [da40.md](../da40.md)

## DA40G-25

- **The DA40's IFR toolkit is essentially complete and every view was opened and read**: Direct-To with typed idents, PROC (Select Approach/Arrival/Departure, Activate Approach, Activate Vector-to-Final, Activate Missed Approach), HoldAt (course, inbound/outbound, leg time or distance, turn direction), SelectAirway, the flight plan page's per-leg ALT constraint column, the transponder keypad, and PFD bezel radio tuning. ⚠️ Altitude constraints and radial intercepts are reachable and readable but NOT yet flown end to end; do not claim them until they are. → [da40.md](../da40.md)

## DA40G-26

- **A SimBrief plan reaches the DA40's G1000 through the Navigraph plugin's Flight Plan Catalog and NOTHING ELSE** — Catalog page, cursor on, the flight focused, softkey 5 Activate (disabled until a flight is focused; CLR drops the cursor), the dialog "Activate SimBrief flight plan?, OK, or CANCEL", ENT. The XLS ships the plugin inside the COWS package, the NG gets the identical one from Navigraph Hub's `navigraph-avionics-g1000` in Community. Measured dead ends: SimConnect `FlightPlanLoad` of SimBrief's `.pln` (both files) changed nothing on the running G1000, and the Catalog's softkey 10 "Import" is the stock plan-file import. The display window reads each step; a message dialog is read as its QUESTION then its buttons (`A.dialogSay`, placed as a `Dialog:` row ahead of the fields block because the window speaks the FIRST ROW THAT CHANGED after a softkey press), and the first readback after a view change leads with the page title. Never add a one-press import macro: the pilot's ruling is that the workflow is the sighted pilot's, read properly. → [da40.md](../da40.md)

## DA40G-27

- **The XLS's G1000 plugin spells its pages `Da40EnginePage` / `Da40ChecklistPage` (and the two checklist popups the same way); the NG's are `Da40Ng…`** - the agent must accept both, or the XLS Engine page (EGT, CHT, the lean assist) is left out of the enumeration entirely. Its EIS strip nests MAN IN and RPM as `.eis-dial-gauge`, not `.eis-gauge`, and its Engine page (`.da40-engine-page`) draws double dials whose labels are the UNITS with the name in a sibling, and bar charts with no digits at all - read `L:DISP_EGT:n` / `L:DISP_CHT:n` back from inside the instrument, which is exactly what each bar is drawn from. → [da40.md](../da40.md)

## DA40G-28

- **A `<ShortText>` alert is NOT in the CAS window.** panel.xml declares two kinds: a `<Text>` alert goes in the CAS list, a `<ShortText>` alert is drawn in ONE box beside the altimeter, `.warnings-display`, highest priority only, its class giving the severity (`yellow` a caution: `L:COWS_TRAFFIC_WARN` 1 drew TRAFFIC; `red` a warning: holding `L:AFCS_FAIL_ELE` drew PTCH; measured on the NG, 2026-10-06). The set is ROLL/PTCH/PTRM (`AFCS_FAIL_AIL/ELE/TRIM`), <--AIL/AIL-->/UP ELE/DN ELE (`AFCS_FORCE_*`), TRAFFIC, TERRAIN, PULL UP, TAWS NA, AFCS and PFT. Nothing read that box, and docs claimed ROLL and PTCH came through the CAS reader. ⚠️ The box shows the TOP alert only (with TRAFFIC and PTCH both raised it showed TRAFFIC), so reading it made a covered alert look cleared and announced it so, then new again when uncovered. `A.shortAlerts()` therefore tests each alert's own panel.xml condition - identical on both airframes - including `CIRCUIT ON:37` where required and the servo forces' 6 s `<Timer>`, and `A.cas()` adds what holds; measured with TRAFFIC and PTCH raised together, both listed, each clearing on its own. AFCS and PFT stay out because `AFCS_TEST` and `AFCS_PFT` are announced rows. → [da40.md](../da40.md)

## DA40G-29

- **A knob step says only what moved.** Reported from the cockpit as "checklist, checklist" and "failure mode, failure mode": the checklist group list repeated "Checklist group," on every click, ENT on the Engine page menu "Failures Mode:", a choice list "Choose,", a setup page its group box. `DropRepeatedLead` drops the run of leading `, `/`: ` segments the read-back shares with the previous one in the SAME view (the previous one is also tried without its first segment, because the first read-back after a view change leads with the page title), always keeps the last segment, and answers a repeat in full. A new view, a cursor change, and the checklist page's own lines (`WARNING:` there is content) are never shortened. The Ctrl+G page list became a tree for the same reason. → [da40.md](../da40.md)
