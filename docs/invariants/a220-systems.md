# Synaptic A220-300 systems over the CommBus — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/a220-systems.md`, which Claude Code loads when it reads matching code. Background: [a220.md](../a220.md), section "Systems over the CommBus".
Written 2026-10-12 from that day's live session at KATL (Synaptic A220 v1.0.10, MSFS 2024) and the aircraft's DisplayUnits bundle (`instrument.js`, its `// src/avionics/...` module comments). The rules A220-1 to A220-17 are in [a220.md](a220.md), A220-18 to A220-32 in [a220-fms.md](a220-fms.md).

## A220-33

- QNH, the altimeter unit, STD and the minimums are set only through the CTP's own settings call, `A22X.L CTP Action` / `A22X.R CTP Action` with `{type: "SetConfig", ...}` and one of `qnh: {type: "InHg" | "Hpa", value}`, `minimums_mode: 0 | 1` (BARO, RAD) or `minimums: feet` (bundle `src/avionics/lib/afdx/ctp.ts`, the settings window's `wl(side, {...})`). The agent's `ctpSet(side, cfg)` sends it and accepts only those three keys, so no caller can send an arbitrary configuration (`qnh_std` was dropped 2026-10-15: it moves nothing). Every set is read back from `A22X.L/R CTP Data` and `A22X.L/R ADS Data` and the result is spoken: QNH, the unit and the minimums value are numeric confirmations (CORE-7) and always speak; STD speaks its success only when Ctrl+B sets it (a panel combo's pick was read by the screen reader) and the minimums mode is silent when it lands; a refusal always speaks, and the STD and minimums combos are re-sent the truth.
- Measured live 2026-10-12: `KOHLSMAN_SET` (mb×16) is ignored by the A220; `L:A22X L Altimeter Set` = ±1 is one CTP click (0.01 inHg) and a walk on the 1 Hz Kohlsman read-back hunts; `SetConfig qnh {InHg, 30.13}` set `CTP Data.qnh` to 30.130001 and stock `KOHLSMAN SETTING HG:1` to 30.13 exactly, the R side likewise on Kohlsman:2; `minimums_mode 0` then `minimums 1210` landed in CTP Data and in `PFD Data.minimums`.
- Measured live 2026-10-15 (gate, ground power): QNH is per side (`{InHg, 29.95}` on side 1 left side 2 alone; `KOHLSMAN SETTING HG:2`/`MB:2` follow the first officer's CTP). The MINIMUMS are shared: a mode sent to either side, and a value sent to the captain's, landed on both sides, and a mode change reset the value to 0 on both (so a pilot sets the mode first, then the value).
- The entry is 940 to 1090 hPa or 27.00 to 32.00 inches (`A220Systems.TryParseQnhInput`), and each side is sent the value in that side's OWN unit (whole hectopascals, or inches to two decimals), because the CTP's input parses in its current unit. A value that comes out as exactly 1013 hPa or 29.92 inches is sent as 1013.25 hPa or 29.921253 inches (`A220Systems.AvoidStandard`), because the exact value selects STD (below); the PFD shows those as 1013 and 29.92, and the CTP stores 1013.25 as 1013.
- STD truth: the PFD draws STD from `ads.qnh_std` and the unit from `ads.qnh_unit` (0 IN, 1 HPA) in `A22X.L/R ADS Data` (bundle `PFD/ADI/Altimeter`, `r.on("ads.qnh_std")`). `CTP Data` carries no `qnh_std` field at all (live 2026-10-15), so `A220Systems.IsStd` reads the ADS flag alone, and the unit is the ADS unit first (`A220Systems.UnitHpaOrNull`). 29.92 inches is a legal QNH, so the old "29.92 means STD" inference misreported.
- STD measured live 2026-10-15 (gate, MSFSBA closed, the probe harness): `SetConfig {qnh_std: true|false}` changed nothing on either side. A QNH `SetConfig` of EXACTLY 29.92 inches or 1013 hPa selects STD on THAT side only (the other side unchanged) and leaves `CTP Data.qnh` as it was; any other value (29.921253 inches, 1013.2 or 1013.25 hPa included) is a QNH and takes that side out of STD. So STD on is the exact standard value in the unit the side's PFD shows, STD off is the side's own kept QNH sent back in that unit (`A220Systems.StdWrite`), and a unit change while in STD sends the standard value in the new unit (it stays STD). The CTP baro knob push `L:A22X L/R Altimeter STD` also selects STD, but on BOTH sides at once, so it is not used. A side whose unit or QNH the link has not reported is not sent a guess.
- `L:A22X L/R Altimeter HPA` is the WASM's unit mirror: the unit combos READ it, but writing it corrupted the unit readout (2026-09-22) and never changed the CTP. The unit is changed by re-sending the current QNH in the other unit's type, and live 2026-10-15 that works (outside STD): `{Hpa, 1014}` after 29.95 inches gave `CTP Data.qnh {Hpa, 1014}`, `ads.qnh_unit` 1 and the HPA mirror 1 within about 150 ms, on each side. A unit the CTP did not take is still spoken ("The A220 did not change the altimeter unit — still inches"), never assumed.
- A read-back that never arrives (the side's CTP or ADS block missing, or the field the verdict reads absent) is "<side> … not confirmed: the A220 display link did not report it", per side, never "did not change — still …". The risk, identified in review rather than seen live: at transition altitude a lost STD read-back that said "still QNH" would send the pilot to press again, and a toggle would then turn STD back off. The success lines name what each side READ BACK (two sides are "both sides" only when they read alike), never the value that was wanted.
- Every number in a payload is serialized with System.Text.Json ([VAR-5]): a comma-decimal Windows culture must still send 30.13.
- Writes are latest-wins per side, and a write holds its combo's bridge key while it is in flight: see [A220-39].
- `PFD Data.minimums_alert` is never announced: the aircraft calls MINIMUMS itself, the reason [A220-2] gives for its aural flags.

## A220-34

- `L:A22X Autobrake` is the selector's position on a five-detent scale: 0 RTO, 1 OFF, 2 LO, 3 MED, 4 HI (live 2026-10-12: 0 sensed AUTOBRAKE_RTO, 1 sensed AUTOBRAKE_OFF; the cockpit knob XML has NUM_STATES 5 and binds INCREASE/DECREASE_AUTOBRAKE_CONTROL).
- The WASM rewrites the L:var every tick, so a direct write is overwritten at once, and `AUTOBRAKE_LO_SET` does nothing. The knob's own events move it one detent: DECREASE OFF→RTO and INCREASE RTO→OFF passed live; INCREASE OFF→LO was REFUSED on the ground, twice.
- So the combo write is a step walk (the HorizonSim 787's HS-8 pattern): read the position fresh, fire ONE event (`A220Systems.AutobrakeStepEvent` picks it), wait 400 ms, read again. An unchanged position means the aircraft refused that step: say so ("Autobrake LO not available on the ground — still OFF", `A220Systems.AutobrakeRefusal`) and stop; never fire the next step on the assumption the last one took. At most five steps; a walk that ends short says "Autobrake stopped at …, asked for …".
- A read-back that never arrives (a timeout, a disconnect) says nothing about the knob, which may well have moved, so it is spoken "Autobrake LO not confirmed: the selector is not reporting its position", never as a refusal and never as a position (`A220Systems.AutobrakeStepVerdictFor`). The same goes for a first read that never arrives: "Autobrake not set: the selector is not reporting its position".
- The walk keeps its own read-backs from moving the combo until it ends (the MD-11's [MD11-8] pattern): while a walk is in flight `ProcessSimVarUpdate` consumes `A22X_AUTOBRAKE`, otherwise MainForm would re-sync the combo to every detent the knob passes under the pilot's focus, the reader would speak each one and the pick would be yanked back mid-walk. The walk releases that gate first, then re-reads the combo once, so the combo shows the selector's truth whether or not a step was refused; a newer pick cancels the walk in flight and keeps the slot. Success is silent (the screen reader read the pick, CORE-7).
- One event per calc string, each seq-prefixed ([A220-3], [A220-10]: a batch of n is applied as one click).
- The ECL's AUTOBRAKE_RTO..HI items map to 0..4 and run through the same walk.
- Whether LO, MED and HI are selectable in flight is checked on the first flight; until then the refusal text names "on the ground" only when the aircraft is on the ground. Re-measured live 2026-10-15 at the gate: OFF→RTO, RTO→OFF, and OFF→LO refused again.

## A220-35

- The transponder and TCAS are set through the CNS XPDR/TCAS CONTROL dialog's own call: `A22X.Display Tune` with `{index: 5, cmd: {type: "ConfigAtc", action}}` (bundle `src/avionics/lib/afdx/atc.ts`, `MFW/Pages/CNS/Dialogs/TransponderControl.tsx`). The agent's `atcAction(action)` accepts only SetMode, SetCode, SetTssLimits, Ident and SetAtcId. Every write is read back from `A22X.ATC Data` (`mode`, `code`, `ident`, `id`, `tss_limits_sel`). Live 2026-10-12: SetMode 2 gave `mode` 2 and `tss_mode` 2; SetMode 0 restored AUTO.
- Enums (bundle): mode 0 AUTO, 1 STBY, 2 TA/RA, 3 TA ONLY, 4 ALT ON, 5 ALT OFF; TCAS ALT LIMIT `tss_limits_sel` 0 NORM, 1 ABOVE, 2 BELOW, 3 ABOVE/BELOW.
- The code: the dialog accepts `/V|[0-7]{4}/` and sends `parseInt(text, 10)` ("V" = 1200), so the bus `code` 2000 IS squawk 2000. The bus code travels as its four digits read as a decimal number; a digit 8 or 9 is refused before anything is sent ("A squawk is four digits, each 0 to 7").
- BCD16 is the encoding of the STOCK words, not of the bus: the `XPNDR_SET` parameter (`A220Systems.SquawkToBcd16`) and the stock `TRANSPONDER CODE:1` SimVar (`A22X_XPDR_CODE`, registered with units "Bco16", as every other aircraft here reads it), which reads back as the BCD16 word. Live 2026-10-15: squawk 2000, 2345 and 1234 read 8192, 9029 and 4660 in "Bco16", but 2000, 2345 and 1234 in "number", the unit this registration first had, which the decode rejected (X with the link down said "not available", and the fallback's verdict could never land). `A220Systems.Bcd16ToSquawk` decodes it before it is spoken (X with the display link down) or compared (`A220Systems.StockCodeLanded`, the fallback's verdict); a word that is no four-nibble octal code decodes to nothing and is "not available", never a guessed squawk.
- A mode or ALT LIMIT write whose ATC Data read-back never arrives (no block, or no `mode` / `tss_limits_sel` in it) is "… not confirmed: the A220 display link did not report it", never "did not change — still unknown".
- ALT LIMIT: the dialog disables the dropdown while the mode is AUTO (`disabled: e === 0`), so MSFSBA refuses it in AUTO with that reason instead of sending what the aircraft's own UI never sends. (Live 2026-10-15 the WASM does take SetTssLimits in AUTO into `tss_limits_sel`, but the applied `tss_limits` stays 0 NORM; in TA/RA both follow.)
- Flight ID: 2 to 8 of A-Z and 0-9; the dialog clears it with SetAtcId "00000000". The Flight ID dialog has its own "Clear flight ID" button that sends it (the entry box refuses an empty value, so an empty entry could not clear), and the button's state text is the current ID, refreshed live. A clear counts as done only when a PRESENT ATC block reads an empty ID (nothing, an empty string or "00000000"); with no ATC block the write is "Flight ID not confirmed: the A220 display link is not connected", never "cleared" (an absent ID reads as empty, so without the block check a clear would "land" on a stale store). Live 2026-10-15 the aircraft reads "00000000" back after a clear (an unset ID read ""), and both count as empty.
- Stock events: the squawk entry falls back to `XPNDR_SET` only when SetCode did not land, and is then judged on the ATC Data code when that block is there, else (display link down) on the decoded stock word; IDENT tries `XPNDR_IDENT_ON` before the bus Ident action and counts only when ATC Data reads `ident` back, saying so when it cannot be confirmed. Live 2026-10-15 both stock events reach the A220: `XPNDR_SET 4660` (BCD16 of 1234) set `ATC Data.code` 1234, and `XPNDR_IDENT_ON` set `ident`, which, like the CNS Ident action's, held for about 18 s.
- Writes are latest-wins per control (mode, ALT LIMIT, squawk and flight ID each have their own generation), and a superseded squawk never fires the stock fallback, which would overwrite the newer code: see [A220-39].

## A220-36

- CAS truth is `A22X.CAS Data`: `{msg: [18 u32], info: [21 u32], ecl: [7 u32]}`, full arrays in every message. A set bit `word << 5 | bit` of `msg` indexes `SynapticA220EclData.CasMessages` (574 entries; the decoded list matched the EICAS exactly, live 2026-10-12). Level: 3 warning, 2 caution, 1 advisory, 0 status; the EICAS shows warnings first, newest first within a level (bundle `EICAS/Components/CasStack.tsx`).
- `A220Systems.CasMonitor` diffs each observation: new warnings and cautions are spoken at once with their severity ("Caution: EMER LTS OFF"), advisories are queued behind them, status messages are never spoken (the EICAS never flashes them either), and a warning or caution that clears queues "<text> cleared". At most four new messages per observation, then "... and N more" (an electrical failure raises six or more in one second).
- The first observation after a connect or a flight load is a BASELINE: one summary line of the warnings and cautions already showing ("2 cautions: EMER LTS OFF, FMS PERF DEP CONFIG"), never one call per message. A poll with no CAS block (a tap hiccup, a resync) keeps the old baseline: it must never speak "cleared" for a missing store.
- A flight load or reconnect (`OnSimContextReset`) re-baselines BOTH sources: the monitor resets, and the EICAS-scrape CAS baseline is dropped too, so the tap-down fallback re-baselines silently instead of diffing a loaded flight's text against the old flight's. The pump's scrape block runs before the monitors in the same poll, so each consumer honours the request itself (a counter, not a flag a first consumer could swallow).
- The EICAS SVG scrape diff is the fallback only: it speaks only while the CAS store is missing, so one message is never spoken twice from two sources. It drops its baseline whenever the store takes over (a later fallback re-baselines silently), never speaks memo lines, and each severity answers to its own Ctrl+M row.
- Ctrl+E toggles the CAS call-outs (the warnings/cautions row and the advisories row together); the Alt+E window shows everything, status messages included, from the store (while the store is missing, from the scraped EICAS list, saying so). It is the shared `FbwEwdWindow`; F5 speaks "CAS refreshed".

## A220-37

- The take-off "Rotate" call is the only call MSFSBA makes on the roll: the aircraft calls V1 itself, and adding a second V1 doubles the audio ([A220-2]). VR comes from `A22X.L PFD Data.vr` (the PFD's own bug, present once the FMS V-speeds are set; live 2026-10-12: `v1 131, vr 135, v2 139`).
- The speed is the per-frame `A22X_TAKEOFF_IAS` feed (ExcludeFromBatch + HighFrequency, the iFly pattern through `TakeoffVSpeedCallouts`), never the 1 Hz batch: at 4 kt/s of take-off acceleration the batch was up to 4 kt late, and the old 1 Hz "Rotate" in the display pump is removed.
- Where the speeds come from is decided per BLOCK (`FeedTakeoffSpeeds`). With the PFD block present, each of V1, VR and V2 is the store's value, else the tape's bug, else 0: the store reports an unset speed as null, so a wiped FMS, a flight load or a fly-again clears the previous flight's speeds. With NO PFD block (the tap down, a poll without it) nothing is known: a speed takes the tape's bug when the tape shows it, otherwise the machine keeps the value it holds. That is absence of evidence, not "unset": treating it as unset disarmed a roll in progress (a roll re-arms only on the ground below 40 kt), and the next poll restored the speeds too late. A one-poll store gap mid-roll never disarms Rotate.
- A take-off roll (on the ground, accelerating through 40 kt) with V1 or VR unset says "V-speeds not set — no Rotate call" ONCE (`A220Systems.RollWithoutVrGate`; the machine arms only with both set), and the Rotate row mutes it; a landing roll never trips it (airspeed decreasing).
- Both are reset on reconnect and on a sim context reset (flight load) — the TKO-5 rule for every aircraft — so a new flight never inherits a spent latch.
- The Rotate call has its own Ctrl+M row.

## A220-38

- The aircraft's stores arrive as DIFFS (bundle `src/avionics/lib/afdx/index.ts`, `rk`/`B$`): an object updates key by key, and an ARRAY update is an object of index keys plus a `"~"` key holding `[start, deleteCount, items]` (a splice). A plain deep merge turns every array into an object with numeric keys and drops the splice, which corrupted the flight plan's legs and paths. The agent merges with `mergeObj`/`mergeArray`, which apply the index keys and the splice exactly as the aircraft does.
- A splice that does not fit (its start plus delete count past the end of the array) or an index update that meets a non-object element means a message was missed: the agent resyncs (asks the stores for a full copy, throttled to once per 3 s) instead of guessing.
- A store's message handler is a closure of the agent that registered it, so a change to the handler (this merge was one, v2 to v3; the one-merge token below, v3 to v4) needs a FRESH listener and data object: bump `CB_VERSION` with every handler change, or the old listener keeps writing into its own, now orphaned, data object. One listener leaks per upgrade, never per reconnect.
- ONE merge per message. `ensureCommBus` subscribes every store at once and again from the listener's ready callback, and live 2026-10-15 BOTH subscriptions delivered (`subs` 36 for 18 stores; each Status Data message read the data twice as often as a single handler does). A splice is not idempotent: the flight plan came out with 12 segments and 56 legs and paths for a plan of 7 and 29, and its total read 528.9 NM where the aircraft's own copy gave 564.6. Each subscription now takes a token (`cbState.subTok`) and only the store's latest one merges. Pinned by `A220AgentContractTests.EachMessage_IsMergedOnce_ByTheStoresLatestSubscription`; measured again live after the fix: one merge per message, and the merged plan equal to a fresh resync after splicing approach changes.
- WHOLE stores for a new listener. In steady state every store sends only an empty `{}` heartbeat about once a second (live 2026-10-15), so a listener created then has fresh stamps and empty data: the systems blocks went out with every field null ("V1 not set", squawk ----, door unknown), and `fplnProgress()` read a plan of 0 NM, until something else asked for a resync. `cbResync` records a resync sent while the listener is delivering (`wholeAsked`; a call before that can be dropped) and `sysBlocks()` keeps asking until there is one. A resync re-sends every store whole about 90 ms later. Pinned by `A220AgentContractTests.SysBlocks_AsksForWholeStores_UntilAResyncWasSentWhileDelivering`.
- The systems stores can sit quiet for ~3 s between messages (the DUs ask for a full copy after 3 s of quiet), so they go stale at 6 s and the flight plan at 10 s, never 3 s; `tapGaps()` measures the real gaps. Live 2026-10-15 every store heartbeated about once a second: the longest gap was 1.1 to 1.4 s on every store with the avionics powered (the autoflight store went quiet for 24 s only while ground power was off and the aircraft was on battery).
- The captain's CTP and nav stores (`A22X.L CTP Data`, `A22X.L Nav Data`) belong to the `afdx` group, whose 3 s window stays for its own readers (the knob walks' fast `afdx()` read, the Radios window). `sysBlocks()` ships them with the systems blocks on the systems window instead (`SYS_STALE_MS`, 6 s, passed as `cbBlock`'s max-age argument): at 3 s a quiet captain CTP flickered to "not available" (the Minimums row, Ctrl+B's "Now" box, the QNH prefill), and the unit write, which reads the captain's QNH once, could refuse with "the A220 display link is not connected".
- The flight plan store (`A220.Flight Plan Update`) is read only by `fplnProgress()` and never shipped whole. Its total and its top-of-descent distance stop at the first MISSED APPROACH segment (`segments[i].typ === 6`, found by the segments' cumulative `len`), because `arr.dtg` ends at the destination: counting the missed approach made every TOD figure come out short by its length. With no segments there is no known boundary and the whole plan counts.

## A220-39

- Ctrl+M's mute wrap (the A220 joined `DefAnnounceMuteSets` on 2026-10-14) covers only `ProcessSimVarUpdate`. The A220's CAS, flight-mode, gear, engine-start, IRS and door call-outs are spoken from the display pump, outside that wrap, so each checks its own synthetic row (`A220MonitorRows`) before speaking; a new pump or timer call-out gets a row there and checks it.
- Rotate and the final-approach calls do speak from `ProcessSimVarUpdate`, but on feeds the wrap does not reach, so they check their own rows too: Rotate on the per-frame `A22X_TAKEOFF_IAS` feed, which `IsMuteWrapExempt` exempts because its call belongs to the Rotate row ([VAR-8]); the approach calls on quiet `AddQuiet` vars (`A22X_RA` and its companions) that have no Ctrl+M row of their own, so they answer to the approach row.
- Bus-only control states (transponder mode, TCAS ALT LIMIT, STD, minimums mode and value) have no SimVar for MainForm to read. The definition raises `CommBusValueChanged`, and MainForm feeds it into its update path as a silent snapshot update (`IsInitialSnapshot = true`, the iFly SDK bridge's pattern): the combo shows the truth, and nothing is announced. A change the pilot made was already read by the screen reader (CORE-7). A change made elsewhere (a click in the virtual cockpit, the aircraft's own logic) is shown on the panel but NOT announced: no monitor watches these states for background changes. A value is sent only when it changed since the last send; a rebaseline clears the sent values so every state is re-sent.
- The latest write per control wins. A combo commits on every arrow press, so arrowing AUTO, STBY, TA/RA starts overlapping writes. Each write takes a generation from its control's `LatestWrite` when it starts and asks whether it is still current before it speaks or does anything else: a write the pilot has already moved past reads back a LATER pick, so judging it would report a failure about a value nobody asks for. A superseded write speaks nothing (a link-down refusal included) and never fires a stock fallback. The CTP controls are per SIDE (`SidedWrites`): one call may write both sides, and it owns only the sides no newer call has taken, so a first-officer write never silences a captain write nobody overrode.
- While a write is in flight its bridge key is HELD (`HoldBridge`, released by `ReleaseBridge`; a count, so overlapping writes each hold it). MainForm sets a snapshot value straight onto the combo with no just-set or focus guard, so an emission between two arrow presses would snap the combo back to an intermediate value under the pilot's key. A held value is not recorded as sent. When the last write is judged, `ResendBridge` makes the next poll send every bus state, so the combo shows the aircraft's truth, refused or not.
