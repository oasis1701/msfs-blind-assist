Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/pmdg-737.md`, which Claude Code loads when it reads matching code. Background: [pmdg-737.md](../pmdg-737.md).

## P737-1

- Two CDUs (no observer), no FPA mode, annunciator names differ from the 777 (LVL_CHG/HDG_SEL/VOR_LOC), DU selectors reverse sequence for the F/O, and fire handles need an active fire to test — see docs/pmdg-737.md for the full gotcha list. → [pmdg-737.md](../pmdg-737.md)

## P737-2

- The PMDG 737 CDU form sends every CDU key (letters, LSKs, function keys, CLR/DEL/EXEC) as a `TransmitClientEvent` carrying `MOUSE_FLAG_LEFTSINGLE` (0x20000000), a self-contained press-and-release click, and NEVER as the CDA `{eventId, 1}` write the 777 form uses for most keys. The NG3 FMC ignores the CDA write for CDU keypad events: the click sound plays but nothing registers (the same momentary-button behavior proven for the MCP buttons). A copy of the 777 form's CDA path, or a cleanup that "harmonizes" the two forms, brings back keys that do nothing. The 777's own FMCCOMM and HOLD keys use the same transmit path for a different reason ([P777-6]). A single `LEFTSINGLE` is a complete click; no separate `LEFTRELEASE` is needed. Live-verified against the NG3 (CLR and letter entry) with `tools/CDUTest`. Evidence: `PMDG737CDUForm.SendCDUKey` (`Forms/PMDG737/PMDG737CDUForm.cs`), which calls `SendEventViaTransmitWithTarget`, and "CDU keys must use TransmitClientEvent, not the CDA write" in `docs/pmdg-737.md`. Added 2026-10-09.

## P737-3

- `PMDG737Definition.HandleUIVariableSet` falls back to a click-walk for any 3+ position selector with no special handling: one `TransmitClientEvent` per detent, LEFTSINGLE to step up and RIGHTSINGLE to step down. That direction is right for only some NG3 knobs. On 2026-10-18 a live sweep with `tools/PMDGDispatchTester` (its `watch` command reads the struct field back) sent one LEFTSINGLE and one RIGHTSINGLE to every selector on that path. On 14 of them LEFTSINGLE stepped DOWN: the MCP bank limit, EFIS mode and range on both sides, both wipers, the position lights, pressurization mode, the outflow valve, N1 set, speed reference and the DC and AC meters. A walk on those drives every pick toward position 0 and pins it there; the pilot report was "the bank limit is stuck at 10°", and the sweep left the wipers running. Each of the 14 now dispatches by absolute target (`TransmitClientEvent` with the position as the parameter), which was read back across non-adjacent positions in one send. The position-light event counts from the other end: parameter 2 lands STEADY (struct 0), 1 OFF, 0 STROBE & STEADY, hence `_reversedAbsolutePositionSet` (`AbsoluteSelectorParameter` takes the top position from the selector's own detent count). The outflow valve switch, spring-loaded in the real cockpit, latches when set from outside (an absolute send and a CDA write of OPEN or CLOSE both held 3+ s until Neutral was sent), so the pilot picks Neutral to stop the valve. Knobs confirmed to step the right way and left on the walk: dome, no smoking, fasten belts, window heat test, packs, isolation valve, landing light retract, the four VOR/ADF pointers, disengage test, lights test, fuel flow. The temperature source selector moved for neither click and is unresolved. The same bug was fixed earlier for the overheat-detect, cargo-detect, DU and NAV/DISPLAY source selectors, the engine start and ignition selectors, and (by a closed-loop walk) the transponder mode. Evidence: `_absolutePositionSelectorSet` and its comment in `PMDG737Definition.cs`. Added 2026-10-18.

## P737-4

- A third write transport exists for PMDG switches, the stock `K:ROTOR_BRAKE` event (66587) with `param = (pmdgEventId - 69632) * 100 + mouseCode` — this is NOT a new discovery: `PMDG777Definition.cs:6188-6209` already drives three 777 soundpack switches through it (crediting the FSCopilot 777 profile), including the same wheel codes (07/08). The 2026-08-25 737 session independently re-confirmed mouse code 01 = left-single live on the 737 speedbrake (679201/679101 arm/disarm) — check here before rediscovering it; it does NOT rescue the gear lever. → [pmdg-737.md](../pmdg-737.md)

## P737-5

- The `Ctrl+B` baro dialog and the First Officer's transition-altitude set are ONE knob rotation (`PMDG737Definition.RotateAltimetersToStandardAsync` for the First Officer, which turns both knobs to 29.92 inHg or 1013 hPa) with ONE click count (`BaroKnobClicks`) and ONE guard (`BaroKnobBusy`): a `Ctrl+B` entry or a Standard press while either rotation runs says "Still setting altimeter, please wait.", and the First Officer's rotation waits out a dialog rotation already running before it reads the altimeter. Before 2026-10-18 the executor kept its own copy, and the two could run together and step the knob twice. → [pmdg-737.md](../pmdg-737.md)

  **29.92 is not always STD.** The NG3 has no STD flag. The dialog used to infer STD from a 29.92 reading and press STD to deselect it before rotating. A knob ROTATED to 29.92 reads the same with STD off, and the press then SELECTED STD: after the First Officer's rotation, the pilot's QNH entry at the transition level went in behind the STD mask, the altimeter stayed on standard and nothing was said (PR #160 second review). The definition records that the app itself rotated the captain's knob to standard, and the dialog rotates straight to the QNH over that 29.92 (`BaroSetPressesStdFirst`). The record holds until the knob is known to have left standard: a dialog rotation away from it, an STD press or check through the app, a reading away from standard once the app's rotation has settled (3 s), `OnSimContextReset` and `OnSwitchedAway`. An STD press made in the cockpit over a rotated 29.92 cannot be seen by the record. Any other 29.92 is no longer pressed on a guess: since main's #313 (merged into the PR 2026-10-18) the dialog asks the knob first (`Pmdg737Baro.SetFromStandardAsync`, one click and a fresh read), and the Standard button asks it from every 29.92, the record ignored (`Pmdg737Baro.EngageStdAsync`). Mirrored to the First Officer executor in `pmdg-737-first-officer-call-sites.md`. Pinned by `Pmdg737SecondReviewTests`, `Pmdg737SecondReviewStaticStateTests` and `Pmdg737BaroTests`.

## P737-6

- The 737 manual warning-test panel toggles (stick shaker / overspeed clacker) actuate via transmit LEFTSINGLE (engage, holds open-ended) / LEFTRELEASE (release) — never a CDA write; state is app-tracked in the def (no SDK readback), the keys stay OUT of `_simpleEventMap`, and `SwitchAircraft` must release any engaged test so it can't leak into the next aircraft. → [pmdg-737.md](../pmdg-737.md)

  **App exit too (2026-10-18).** `MainForm.OnFormClosing` releases an engaged test as well, before `Disconnect()`, while the sim can still receive the release; until then only the swap path did, so a test held when MSFSBA closed kept the stick shaker or clacker sounding in the sim. The exit path also runs the definition's `OnSwitchedAway`, the swap path's other teardown hook.

  **First Officer and panel holds too (2026-10-18, PR #160 second review).** The First Officer's held preflight tests (the fire test, held 2 s at OVHT/FIRE through the CDA; the stall, overspeed and long GPWS tests, transmit press, hold, release) and the panel's `HeldTransmitAsync` presses record each hold with `PMDG737Definition.BeginHeldPress`. `ReleaseEngagedWarningTests` releases every recorded hold as well as the toggles, so quitting MSFSBA or switching aircraft inside one no longer leaves the fire bell, stick shaker or clacker sounding. Whoever ends a hold first (`EndHeldPress` on its own timer, or the exit/switch release) sends the release; the other sends nothing, so the timer never releases into the next aircraft's data manager. Mirrored to the First Officer executor in `pmdg-737-first-officer-call-sites.md`. Pinned by `Pmdg737SecondReviewStaticStateTests`.
