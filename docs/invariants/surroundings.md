# Airport surroundings, places and passing callouts — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/surroundings.md`, which Claude Code loads when it reads matching code. Background: [taxi-guidance.md](../taxi-guidance.md).
The text is verbatim from CLAUDE.md as of `1f37801a`; a trailing "→ doc" pointer is the original's. Cross-references such as "the bullet below", "above" or "under Core" point at CLAUDE.md's old single list, whose rules now live in several files: search `docs/invariants/` for the rule's key name to find it.

## SUR-1

- Surroundings features (`Navigation/Surroundings`) are READOUT ONLY — never handed to `TaxiGraph.Build`, never a node, never a routing/hold-short input. The ONE way a place becomes a destination is `PlaceListBuilder`, which resolves it BY POSITION onto a stand of the SELECTABLE list within `MaxStandMetres` (150 m), else a stand only navdata lists, else a taxi node within `MaxNodeMetres` (100 m) that `PlaceListBuilder.NearestRoutableNode` has cleared of runway pavement and of hold-shorts — by navdata identity (`TaxiGraph.IsNavdataHoldShort`), never `TaxiNode.Type` alone, which the parking pass stamps Parking on a hold node near a stand — never the building's own coordinate, and NEVER through a `(Name, Number, Suffix)` join: that identity collides (measured on fs2024, 104 groups at 34 airports in navdata ALONE, the widest 4 km apart at OIIE) and usually finds no twin across the two lists at all, because GSX leaves a ramp stand's `Name` empty where navdata's `P` maps to "Parking" — so the route, docking and `gate.select` went to a stand the label never named, or to an identifier-less spot GSX answers "could not prepare" for. A stand entry targets the stand's OWN position and heading, exactly as the Gate / Parking type does; a node-only place carries NO heading, so arrival simply stops instead of lining the nose up on a building; `gate.select` is sent for a Place only when its stand carries a `GsxIdentifier` (`TaxiAssistForm.ShouldSendGateSelect`, the ONE pure rule Gate and Place share); de-ice pads are not Places (`IsRoutable`) — they have their own destination type. Nor is a cargo ramp or concourse that only the navdata describes (`PlaceListBuilder.DuplicatesGateList`): it is a group of stands the gate list already offers under a vaguer name (KMEM listed 40 "Cargo ramp" places, live 2026-09-26), so it stays a Place only with a real name from OSM, the scenery or GSX; fuel is exempt, because with GSX supplying the gate list a fuel place is the only route to a fuel stand. The Place list is built from the catalog; with nothing fresh cached it starts ONE load off the UI thread (`LoadPlaces`) and meanwhile lists from the catalog it last loaded for that airport, and a settling load never starts another (`_placesSettling`). After any rebuild the pilot's label is put back or NOTHING is selected, never item 0 — item 0 plus Calculate routes, and `gate.select`s, somewhere the pilot never chose — and a lost selection is spoken ("Places updated. Please choose the destination again."). → [taxi-guidance.md](../taxi-guidance.md)

## SUR-2

- OSM BUILDINGS have their OWN request, in-memory store and event (`OsmFeatureSource` + `OnlineFeatureStore`) and must NEVER ride the taxiway-name query again: fused, `out tags geom center` returned ways with NO geometry (Overpass honours only the LAST geometry modifier, so every OSM taxiway name was lost), a mirror with no area database answered the whole fused query with an empty HTTP 200 that was then cached, and taxiway names waited on a second request. `OsmTaxiSource.BuildQuery` is byte-identical to its pre-feature text and still ends `out tags geom;` (pinned character for character by `OsmTaxiSourceParseTests`), while both BUILDINGS queries end `out body geom;` (`OsmFeatureSource.OutputStatement`) — `body`, never `tags`, because `tags` prints none of a RELATION's members, and `body` does: under `out tags geom;` a multipolygon terminal or apron arrived as type, id, bounds and tags alone (measured live 2026-09-22, KATL relation 10189710) and could only be measured to its bounding-box centre; `OsmFeatureClassifier` now joins its `outer` member ways into the footprint (`OsmRingAssembler.LargestRing`: the largest closed ring; a way closed on its own is a ring as it stands and never spliced into a chain, a chain a way's end brings back to a node it passed splits there, so rings that touch at a node never become one figure-eight; inner ways never count; a way or member with a gap in its geometry is never joined across it). It is still ONE `out` with ONE geometry modifier, and a way gains only a `nodes` id array no parser reads; `OverpassClient` treats a body whose `remark` starts "runtime error" as a FAILED mirror, never as an answer. A well-formed EMPTY element list is HELD, not believed, until ONE more FRESH mirror has been asked (a regional instance answers empty about everywhere outside its extract), or returned unconfirmed at once when none remain — never a cooled-down mirror and never a second confirmation: an all-mirror sweep cost a genuinely empty field up to six round-trips and held `FetchCoreAsync`'s `Task.WhenAll`, apt.dat names included, past the taxi dialog's bounded name wait. A `PostAsync` caller that cancels during that confirmation gets the held empty answer, never null — for either reader, each of which now makes ONE query. NEITHER source's `FetchAsync` may THROW on a bad body: `OverpassClient.ClassifyBody` only asks for an object with an `elements` array, which is not the same as parseable (an element with no `type`, a non-array `geometry`, a coordinate that is not a number), and before the `OverpassClient` extraction `Parse` ran inside the per-mirror try so such a body merely failed that mirror — thrown instead, it reaches `Task.WhenAll` in `AugmentingAirportDataProvider.FetchCoreAsync` and discards the SUCCESSFUL apt.dat result together with the cache write, the name merge and `AirportDataUpdated`, for pilots who never use this feature. Both catch, warn once with the ICAO and return null, which is what "this source failed" already meant — of the RETURN VALUE, not of the mirror rotation: the catch sits OUTSIDE the mirror loop, so unlike `main` the source gives up with no retry and no cooldown mark, which is deliberate (a body shape that breaks `Parse` is a protocol-level change every mirror shares, not one mirror being ill, so rotating buys nothing — and the apt.dat result surviving is the point). The buildings query is ONE BOUNDING BOX (`OsmFeatureSource.BuildBoxQuery`): the navdata airport box grown `OsmFeatureSource.BoxMarginMetres` (500 m — that box is the exact hull of the airport's own records, so KTIW's own tower sits 15 m outside it), and its answer is kept only inside that same grown box (`KeepInsideBox`), because a filling station on the road outside the field must never become "Fuel, ahead"; with no box nothing is asked (the `icao=` aerodrome AREA query was removed, not kept as a fallback). Never bring the area query back: it needs an area database (overpass.openstreetmap.fr has none and answers `runtime error … area_tags_local.bin`) and an `icao=` tag on the RIGHT aerodrome (live UKRB/UKRK named fields 1,279 and 4,171 km away), and its old `around:3000` fallback reached only part of a large field — measured 2026-09-25, when overpass-api.de refused this machine, kumi and private.coffee timed out on a one-node query, and the one reachable mirror was osm.fr, the audit of all 360 installed-scenery airports stalled on exactly that. The box query answers in 1.3-3.3 s at EGLL/KDEN/KATL (the area query took 17-23 s), so its per-mirror timeout (`OsmFeatureSource.PerMirrorTimeout`, 20 s, through `OverpassClient.PostAsync`'s timeout overload; the taxiway query keeps the client's 12 s) fits THREE mirrors in `FetchBudget`, and a mirror's TCP CONNECTION gets `OverpassClient.ConnectTimeout` (5 s, on the handler `OverpassClient.CreateHttpClient` builds for both OSM readers) — Windows' own 21 s let three refusing overpass-api.de hosts spend the whole budget before a working mirror was asked. A query every mirror refused is a FAILURE (`FetchAsync` returns null, remembered for `OnlineFeatureStore.FailureMemory` and retried), never "this airport has no buildings", which would silence it for the session; a query that ANSWERS with zero elements is an empty, non-null list. "RETRIED" is true END TO END only because of the DEGRADED LIFETIME: `GetAsync` returns an `OnlineFeatureStatus` beside the features (`Served` — a mirror answered, with buildings or with the fact that there are none — `Pending`, `Failed`, `Disabled`), `SurroundingsCatalogBuilder` marks the build `Degraded` on Pending/Failed or when `SurroundingsTier.Read` caught an exception, and `SurroundingsCatalogCache.FreshOrNull` treats a degraded entry as stale after `DegradedLifetime`, which is `OnlineFeatureStore.FailureMemory + OnlineFeatureStore.FetchBudget` — both referenced, never copied, and never `FailureMemory` alone: the fetch a build gave up on can still FAIL up to `FetchBudget` (60 s) later and is remembered for `FailureMemory` from then, so a `FailureMemory`-only lifetime expired first, rebuilt against a failure the store still remembered, and put the real retry at ten minutes instead of five. Without it a null fetch raised NO `FeaturesUpdated` (that continuation requires a non-empty result), nothing invalidated the airport, and the careful null-versus-empty distinction bought nothing: the OSM-less catalog was the catalog for the session. Degraded is never inferred from an EMPTY list — a served airport can legitimately have no buildings — and a late fetch that SUCCEEDS still invalidates at once through `FeaturesUpdated`, unchanged. `OnlineFeatureStore.Clear()` runs on a database switch beside `surroundingsCache.Clear()`, bumping an epoch and dropping in-flight entries, so a fetch filtered against the OLD database's box writes nothing back. The give-up is `task.WaitAsync(maxWait)`, never `WhenAny(task, Task.Delay(…))`. `SurroundingsCatalogBuilder` STARTS the fetch before its other tiers (`OnlineFeatureStore.Prefetch`) and collects it after the scenery tier with only what is left of `CatalogWait` (3 s, counted from the prefetch — `RemainingWait`), so a first-time scenery scan and a slow mirror overlap instead of adding up; the features are still concatenated navdata, GSX, OSM, scenery (the rank sort is stable). `Prefetch` must NEVER arm `FeaturesUpdated` — only a caller that GAVE UP waiting is owed it, and armed at the prefetch an answer landing during the scenery scan would invalidate, i.e. discard, the very build about to include it. `OsmFeatureClassifier` reads `name:en` before `name`, for the spoken name AND the kind — never one for each: OSM's `name` is the local script (RJTT's terminals are 第1旅客ターミナル; RJAA's cargo sheds 第3貨物ビル were not features at all until `name:en` "Cargo Building No.3" was read). OSM data stays IN MEMORY; only the scenery index (the user's own local files) is disk-cached. → [taxi-guidance.md](../taxi-guidance.md)

## SUR-3

- Feature identity needs the NAME and the DISTANCE together (`AirportFeatureCatalog.SameFeature`): differently named neighbours never merge (distance alone dropped KMSP's Concourse B, 109 m from A, and 7,236 numbered helipads), two proper names merge only when EQUAL (a hyphen or underscore between LETTERS counts as a space — live LOWI OSM spelt one club's hangars "Flugsportzentrum Tirol" and "Flugsportzentrum-Tirol" — never between digits, "Hangar 1-2" is not "Hangar 12") and within `SameNameRadiusMetres` (KJFK's two "Concourse B" piers are 1.3 km apart), a proper name ABSORBS a synthesized one (`NameIsGeneric`: "Fuel", "GA ramp", "Helipad 2"), and `Tower` alone is name-insensitive. `Rank` weighs the NAME first (proper > synthesized > none) and the source (OSM > scenery > GSX > navdata) only then, so a named scenery building beats an unnamed OSM one. A merging feature joins the NEAREST kept feature `SameFeature` accepts (`NearestSameFeature`), never the first in rank order — two cargo sheds 80 m apart can both accept the ramp between them, and rank order handed its stands to the shed on the far side. Navdata features are clustered IN SPACE (`SurroundingsGeometry.SingleLinkage`), never one centroid per name — a name-wide centroid put LLBG's "North ramp" 904 m from its nearest stand. A navdata concourse is a GUESS from the BGL gate letters and is REMOVED outright when a GSX feature is built from at least half the same stands, because the two differ in kind AND name and the merge can never reconcile them — judged against the RAW, pre-merge navdata and GSX clusters, NEVER the merged `kept` list (review PC-4 fix round 1: judging the merge let a donor feature that `UnionMembers` later folds in dilute a real 100% match below half — Case J, a generic scenery "Concourse" merging into navdata's guess drags a genuine 3-of-3 GSX match to 3-of-8 — let several GSX sections that each cover only part of a merged concourse together outvote a cluster none of them alone would have superseded — Case F — and let one GSX section covering only part of a merged concourse wrongly outvote gates it never named — Case F2 — and, for free, closes a case where an OSM ring that outranks and absorbs GSX's own feature during the merge made that GSX Source vanish from `kept` and skipped the check outright; the GSX clusters are read straight off the raw, pre-merge list, which the merge loop never mutates, so there is no list to compact out from under the predicate). Distance and bearing are always taken to the SAME point (`SurroundingsGeometry.Nearest`: footprint edge, else nearest member stand, else the representative point) — pairing distance-to-the-wall with bearing-to-the-centroid read a pier 60 m to the left as "ahead, 60 metres". GEOMETRY IS ONLY DONATED WHERE IT DESCRIBES THE WINNER, because identity is decided from names and representative points while a merge hands over the geometry `Nearest` then measures to: a winner that has `Members` NEVER adopts a `Footprint` (its own stands ARE its geometry, and `Nearest` reads a footprint FIRST), a loser's `Members` JOIN the winner's — the UNION (`UnionMembers`; a stand at an identical coordinate is kept once), never the winner's own alone (that dropped the loser's: a pair of LFPG's "Concourse K" clusters — real fs2024 LFPG splits into two such pairs, ~456 m apart, that never merge with each other, never all four clusters into one — and GCXO's "T" lost 11 gates between them) — and only when EVERY one lies within `SameNameRadiusMetres` of the winner's own geometry (`MembersDescribe`, through `Nearest`, never centroid to centroid), and `GeometryMayBeOneBody` refuses THREE combinations outright — an UNNAMED ring beside a stand cluster of kind `Apron`/`DeicePad` (the ring is pavement, the cluster is stands on some pavement, and one ring covers several rows; kept apart, the ring stays a polygon `SurroundingsReport.Zone` can put the aircraft inside and the cluster stays "GA ramp" measured to its stands), ring-versus-ring unless the two OVERLAP (each one's OWN representative point counts only when it lies inside its OWN outline too — a concave L/U outline's point can be `OsmFeatureClassifier`'s bounds-centre fallback landing in its own excluded notch, which used to read as "inside" whatever smaller apron was glued there and merge it regardless of distance, M26 amendment — and then also inside the OTHER's outline; or a vertex of either lies more than `RingOverlapMarginMetres`, 5 m, inside the other: a node two outlines SHARE is on both edges and a ray cast answers it arbitrarily, measured at KTIW) or are PIECES OF ONE BUILDING (two UNNAMED Terminal/Concourse outlines that touch — never aprons), or are the two halves of ONE split way (the SAME proper name on outlines that TOUCH — a shared node, or a vertex within that margin of the other's edge; kept apart, one routable building would be two Place entries — whereas ONE proper name used to merge any two rings, which swallowed a DISJOINT unnamed apron beside a named one, and the zone of a pilot parked on it, at EHRD/EHLW/LSZG), and a STAND CLUSTER the other feature does not describe. A REFUSAL THERE IS A REFUSED MERGE, not merely a refused donation: geometry that does not describe the other feature is evidence they are different BODIES, and different bodies are two places, never one that quietly swallowed the other — KMEM's cargo rows run 686 m and a proper-named building 30 m from ONE end absorbed the whole row on the strength of that one stand, leaving a pilot at the far end 600 m away with no cargo area near them at all. The good case is untouched: a cluster whose every member really is within `SameNameRadiusMetres` still merges into ONE feature carrying the proper name and taking the stands as its geometry. `GeometryMayBeOneBody` is asked LAST, of the few pairs the name and the distance already accepted (it can walk a whole cluster against a ring), and both halves are symmetric, so `SameFeature(a, b) == SameFeature(b, a)`. Measured at KTIW: the 6-stand "GA ramp" adopted the 66,471 m² main apron — which holds the OTHER row's 5 stands too — and the 5-stand ramp adopted a 2,335 m² neighbour holding none of its own, so parked on the southern row a pilot heard "On the GA ramp." and then that ramp named 74 m right (P2), 38 m (P4), 12 m ahead (P6), 47 m (P8), 85 m (P10); two of the four unnamed aprons sit 26.4 m apart and a third 27.9 m from one of them, so with OSM alone the element ORDER decided which polygon survived and dropping the big one takes the zone with it. The mirror case is a proper name 30 m from ONE stand of a row running 686 m (KMEM cargo), 1,016 m (KLNK GA) or 1,296 m (KSNA GA) — inherited whole, it reports itself 0 m from the far end. THE ZONE is where the aircraft IS, in four rungs (`SurroundingsReport.Zone`): a NAMED `Apron`/`DeicePad` footprint containing it, else the ramp whose STANDS it is among (`ZoneMemberMetres`, 40 m — about one stand spacing; measured fs2024 GA nearest-neighbour p90: KTIW 39.2 m, KSNA 39.3 m, KLNK 42.4 m, and it stays under Apron's 50 m merge radius), else ANY containing footprint, else the nearest Concourse/Terminal within `ZoneNearMetres`. Rung two exists because a navdata ramp has NO outline — it IS its stands — so without it the ramp a pilot is parked on could only ever be a nearby thing, and at KTIW the anonymous polygon underneath took the zone line instead. Nothing the aircraft is STANDING ON (`IsStandingOn`) is also offered as nearby, and UNDER A GROUND ZONE two kinds of ground add nothing and are left unsaid (`AddsNothingBesideGroundZone`): an `Apron` with NO name at all (`HasName`), which speaks as the bare kind word — "Apron, ahead, 12 metres" beside the ramp the aircraft is parked on IS that ramp's pavement and names nothing a pilot can act on — and anything carrying the zone's OWN spoken name, KTIW's second "GA ramp" 590 m away being the one-name-two-places confusion. Both exclusions are deliberately NARROW. NOT `HasProperName`, which is one notch too wide: `NavdataFeatureSource` marks "North ramp"/"South ramp" and "GA ramp" `NameIsGeneric`, yet each names ONE ramp rather than all of them and is what a controller calls that pavement. NOT the KIND either, in either direction: an unnamed `DeicePad` speaks as "De-ice pad", where the kind word IS the information, while spending the zone's whole kind silenced a real "North Apron" 300 m from an anonymous polygon the aircraft sat in. With no ground zone — out on a taxiway, or under a concourse/terminal zone — nothing has been said about the pavement, so even an unnamed "Apron, ahead, 200 metres" is real information and still speaks. NOTHING AT ZERO RANGE GETS A DIRECTION: at or below `ZeroRangeMetres` a feature reads "{name}, here." in BOTH surfaces, because the bearing to something the aircraft is standing on is degenerate and the side it yields is arbitrary; the floor is 12.5 ft (3.81 m), the larger of `DistanceFormatter`'s two round-to-zero thresholds, so neither unit can ever print a zero with a side beside it. → [taxi-guidance.md](../taxi-guidance.md)

## SUR-4

- "Which airport am I at" is `CurrentAirport.Resolve` → `CurrentAirportResolver.Pick`, four passes each taking the nearest by TRUE distance: an airport WITH TAXI PATHS whose navdata box (grown `BoxMarginMetres`, 300 m) contains the aircraft; then an airport of ANY kind whose grown box contains it; then the nearest with taxi paths within 3 NM; then the nearest of any kind within 5 NM — idents of any length. The any-kind box pass must stay BELOW the taxi-path box pass (above it, 41 of KSNA's stands — inside heliport 10CL's grown box and nearer its reference point — go to the heliport) and ABOVE the 3 NM pass (without it, 1,552 strips with runways but no taxi paths that the old rule named at their own reference point went to a neighbour, mostly a taxi-path field up to 3 NM away: 8TX2 → KECU 4.4 km off, "Not on a known taxiway or ramp at KECU."; with it 1,353 of them name their own strip, and the answer at none of the 302,142 stands changes). EVERY caller asks it — Alt+Y, Alt+L, Ctrl+Shift+L, the passing-callout monitor, the Taxi Assist form Shift+Y opens (and so its Place list), takeoff assist's under-aircraft runway detection, the Settings taxiway-name refresh (from a position asked of the simulator at the press, `GetFreshAircraftPositionAsync` — the cached `LastKnownPosition`, a by-product of other features' requests that goes stale in quiet cruise, is only its 1.5 s fallback) and the SayIntentions import's position fallback (`MainForm.ResolveImportAirport`); the last four used the legacy rule until the PR #230 review and disagreed with Alt+Y at 19,700 of 302,142 stands (at KSNA 111 stands opened heliport 10CL, and takeoff assist on runway 02L found no runway because 10CL has no taxi data). Never `GetNearbyAirportICAOs(…)` for "which airport am I at" — its only remaining callers are `GateResolver`'s TCAS list (every nearby code, for OTHER aircraft) and `CurrentAirport.Resolve`'s own no-candidates fallback; it is ordered by unscaled |Δlat|+|Δlon| to the reference point, sent 111 of KSNA's 201 stands to a heliport and can never resolve the 2,454 fields with a 3-character ident (replayed on fs2024: 301,865 of 302,142 stands, 99.91 %, resolve to their own airport against the old rule's 93.4 %, and 270 of the remaining 277 are duplicate airport records for ONE physical field; no constant was tuned). The legacy rule runs ONLY when the provider supplied NO candidates at all — never as a second opinion on candidates `Pick` considered and DECLINED: it has no true-distance filter and would hand back exactly the corner-of-the-box airport 5-7 NM out that `Pick` had just refused, chosen by the metric this exists to retire. The catalog is NEVER built on the UI thread: `SurroundingsCatalogCache.GetAsync` is the only builder (thread-pool, single-flight per ICAO, written back only while the build is still that airport's IN-FLIGHT build — `Invalidate` and `Clear` both drop that entry, so an invalidation landing mid-build is not undone, and ONE identity test decides it: never a second per-ICAO generation counter beside `_inFlight`, which kept the same fact twice and was never pruned — and that check guards the FAILURE too, or a build that threw BECAUSE a database switch pulled its provider out would blank the airport on the NEW database for `FailureMemory`, 60 s); a UI-thread caller takes the non-building `TryGetCached` instead. The one line a build writes says `stored` / `discarded (invalidated mid-build)` / `discarded (cache cleared mid-build)` — a discarded build must never read as though it had been cached, because that line is how "the OSM buildings never appear" gets diagnosed. A surroundings lookup's SPOKEN line — the Alt+L answer, or either chord's error/empty line — interrupts only within `SurroundingsLookupNotice.Delay` (1.5 s) of the PRESS and is QUEUED after it (`SurroundingsLookupNotice.Delivery`, the one pure rule; it still interrupts while the announcer is `Suppressed`, which drops a queued line): an answer arriving 3-10 s late as `AnnounceImmediate` cut off whatever taxi instruction had been spoken since. The catalog build STARTS before the Where-Am-I line and the two run side by side, and "Looking around." watches the WHOLE answer from the PRESS (`SurroundingsLookupNotice.NoticeWait`) — never re-time either from the position callback or from one build's start. → [taxi-guidance.md](../taxi-guidance.md)

## SUR-5

- An airport's online taxiway names and surroundings catalog are readied BEFORE the pilot asks (`Services/AirportWarmUp`): the airport the aircraft is at, ON THE GROUND only, on connect and 10 s after every `AircraftLoaded`; the Shift+D destination on the ground or in the air. Names are claimed in the one `_augmentPrefetched` set every name prefetch shares, and only while online taxi data is ON — `AugmentingAirportDataProvider.PrefetchAsync` now returns at once when that switch is off (it once fetched regardless, from every prefetch site: Shift+D, ILS and visual guidance, the taxi form, the landing-exit planner, the flight plan), and Settings' Refresh Taxiway Names SAYS the switch is off rather than reporting "No new names found"; the surroundings build is asked every time, the catalog cache deciding whether it is owed. → [taxi-guidance.md](../taxi-guidance.md)

## SUR-6

- The scenery tier: a model name reaches speech ONLY through `SceneryModelNameClassifier` (raw `KTIW_*` / `concourse_a_02` strings never do), and ground equipment is caught by TWO nets that are BOTH required — the LEXICAL one in that classifier (a `StopWords` token, a `StopList` phrase, or no kind word at all condemns the model; `VendorTokens` is NOT a rejection rule, it only strips a leading vendor token in `Tokenize`; every rule pinned to a measured package name, so extend the test table FIRST; every regex `static readonly` + `CultureInvariant`, none built per call) and the STRUCTURAL one in `SceneryPackageIndexer` (a name scattered over many separate clusters is clutter; a real building becomes one feature PER CLUSTER, never a package-wide average, which put MK Studios BIKF's seven "DS Hangar" buildings 2.3 km apart at one phantom point between them). `Tokenize` strips the vendor prefix up to and INCLUDING the airport's ICAO token (`mk_bikf_…`, `iniscene-egss-…`), or failing that the PACKAGE's own ICAO from its `<vendor>-airport-<icao>-…` folder name (`PackageIcao`); where the ICAO instead ENDS the name (`DHL_YSSY`, `TankOil_KPHX`, `Hangar_KTIW_02`) — the words after it holding no kind word and the words BEFORE it holding one ON THEIR OWN — only the ICAO token goes. The kind test there is `HasKindWord`, the prefilter's own test over `KindWordPatterns` (positive patterns only, never the FBO veto). "On their own" is load-bearing: `MightBeFeature` knows no ICAO and sees the whole name, so a kind phrase completed ACROSS the removed token (`Jet_KXYZ_Centre`) would be accepted by `Classify` and already rejected by the prefilter. Measured over all 26,098 model names in 35 installed airport packages, the rule affects five models the old strip threw away whole and NAMES four: YSSY "DHL" and "Security DHL" (single placements ~100 m from its cargo stands), YSSY "Cargo Rwy" (`cargo_rwy25_yssy` — the author's own words, a RECORDED residual beside EIDW's pre-existing "Rwy 28 Poi Bud 2 Cargo": runway designators inside a model name are a separate lexical question) and KPHX "Tank Oil"; the fifth, `Fuel-truck_KPHX`, stays clutter. What the rule owes those models is that they are no longer DROPPED: their names follow the classifier's existing rules ("Terminal", "Hangar 2", "Boeing Hangar"), never a hand-picked "Main Terminal" or "Hangar 02" (review SI-3). A concourse or terminal is named from the keyword that DECIDED its kind (`Terminal_1_pier_2` is Concourse "Pier 2", never a second "Terminal 1"). The 2026-09-24 audit of all 360 installed-scenery airports pinned stop words for ground equipment (`gse` is a STOP word, not a vendor token — a Signature-branded GPU became an FBO), masts named "… tower" (`radar`/`ils`/`radio`), city landmark packs and `poi` (MK/iniBuilds' landside-landmark tag); a second pass on 2026-09-25, reading every kept name by eye, pinned brand-carrying props (KATL's `…_signature` benches, bins and people were FBOs), taxi guidance signs (`tgs`, `taxisign`), fire-training wrecks and planes (routable "fire stations"), masts (`lamps`, `dme`, `comm`, "steel tower"), landside fuel (`costco`, `propane`) and cargo-area dressing, and widened the freighter test to a separated `B777_F` — never `canopy` (part of KATL's Concourse T) or a bare `box` (`KLAX_TheBoxTerminal`), only "cargo box"; residual: an unmarked skyscraper at a city heliport still reads as a tower. `FeatureKind.Terminal` and `FeatureKind.Concourse` are EXEMPT from the PLACEMENT cap (`PlacementCapApplies`) and exempt BY KIND, never by a cluster count: a 46-part terminal and a 41-container blob are the same single-cluster shape, so no cluster rule can tell them apart. Measured across 34 installed packages, NO Terminal/Concourse group was clutter while the cap had dropped EDDB Terminal A/B/C (46/49/49 parts) and its generic Terminal (175), KPHX Terminal L (21 parts at one coordinate) and KATL Terminal E; 308,833 placements → 837 features before the clutter rule → 533 after.
