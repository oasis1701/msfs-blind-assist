# TFDi Design MD-11

Aircraft code `TFDI_MD11`. Definition: `MSFSBlindAssist/Aircraft/TFDiMD11Definition*.cs`
(+ `Aircraft/MD11/`). Control map generator: `tools/md11-gen/generate_md11_map.py`.

The MD-11 does not resemble any other aircraft MSFSBA supports. Read this before touching it —
most of what you know from the FBW/PMDG/HS787 work is wrong here.

---

## 1. It is event-driven. There is no L:var to set.

TFDi's Integration Guide (`md11.tfdidesign.com/md11/integration-guide`) is explicit:

> The TFDi Design MD-11 is primarily event-driven. This means that variables and systems are
> driven by an event, not by reading the state of an L:VAR or similar. **Writing directly to any
> of the variables will bypass our integrity checks and allow potentially incorrect or conflicting
> states.** To trigger a custom event, you can write the value of the event ID to the L:VAR named
> `CEVENT` and our code will translate it. Please note that **the aircraft itself also uses this
> event, so do not overuse it.**

So every switch, knob and button is actuated by writing ONE integer — the event id — to
`L:CEVENT`. There is no per-control L:var to write, and writing one anyway is explicitly
unsupported. `Md11EventBus` owns this channel and is the ONLY way to actuate the aircraft.

The sanctioned exception is `MD11_EXTCTL_*`, which TFDi document as "designed for external
control of the aircraft" — those *are* direct writes by design (fuel, FCP values, baro, minimums,
outflow, ZFWCG, flap/spoiler handle).

**Three constraints fall out of that paragraph. All three are load-bearing:**

1. **Anti-coalesce.** MobiFlight's command channel silently drops a calc string identical to the
   previous one (already bit this repo twice: the A380 RMP repeated-digit drop, the DCDU
   WILCO→SEND two-step). Here it is worse than cosmetic — the string for a given event id is
   *always* the same, so pressing a button twice, or stepping a knob N times, would land exactly
   once. Every write carries a `{seq} 0 *` prefix, which computes a discarded zero purely to make
   the string textually unique. **Never route a CEVENT write through `SetLVar`** — it emits the
   bare `"86018 (>L:CEVENT)"` and the repeats vanish.
2. **Pacing.** "Do not overuse it" is real: `CEVENT` is a single shared slot the aircraft's own
   code also writes. Writes are serialized through one queue with a minimum gap so ours cannot
   race or clobber theirs.
3. **Press *and* release.** Buttons carry a DOWN id and an UP id. Sending only DOWN leaves the
   button held for the session — the Fenix stuck-button bug, which on that aircraft re-fired the
   takeoff-config test after touchdown. Always send both.

`TDMD11.TRIGGER_EVENT` also exists in the wasm (the only dotted custom event) and is a plausible
native-SimConnect alternative to the CEVENT L:var — no MobiFlight dependency, no coalescing, no
shared-slot race. It is **undocumented and untested**; if CEVENT proves racy in the sim, this is
the first thing to try.

## 2. The displays have NO DOM — but the MCDU IS fully exported over a Client Data Area

Two separate facts. Do not collapse them (an earlier pass did, and wrongly concluded the CDU was
unreadable — see "A correction" below).

### 2a. There is no DOM. Coherent scraping cannot work here.

`PANEL.CFG` declares every screen as a WASM-rendered gauge:

```
htmlgauge01=WasmInstrument/WasmInstrument.html?wasm_module=md11host.wasm&wasm_gauge=DU1
…DU2 … DU6, LMCDU, RMCDU, CMCDU, ISFD, AFS, FUEL, RADIOS_XPNDR
```

They are drawn from inside `md11host.wasm` via NanoVG. **There is no HTML DOM behind them**, so
the Coherent-debugger scrape that reads the PMDG / FBW / HS787 CDUs has nothing to read.
**Do not sink time into DOM-scraping the MD-11's displays.**

### 2b. The MCDU is exported as TEXT over SimConnect. Use this.

Documented at <https://docs.tfdidesign.com/md11/integration-guide/data-export> (note the host —
`docs.tfdidesign.com`, NOT `md11.tfdidesign.com`, which 500s). Every name below is corroborated
directly in `md11host.wasm`.

The MD-11 publishes all three MCDUs as **plain text** in a SimConnect **ClientDataArea** — the
same mechanism PMDG uses, which this codebase already has infrastructure for
(`PMDG777DataManager` / `PMDGNG3DataManager` are the reference).

**Registration name: `MD11MCDU`.** Read with `SimConnect_RequestClientData`.

```c
struct MCDUCHAR
{
    char16_t value;
    bool large = false;
};

struct MCDUEXPORTDATA
{
    bool dspy = false;
    bool fail = false;
    bool msg = false;
    bool ofst = false;

    MCDUCHAR text[MCDU_ROWS][MCDU_COLS];
};

#define MCDU_ROWS  14
#define MCDU_COLS  24
#define MCDU_CHARS MCDU_ROWS * MCDU_COLS

size_t MCDU_DATA_SIZE = sizeof(MCDUCHAR) * MCDU_CHARS + (sizeof(bool) * 4);

enum CLIENT_DATA_DEFINE_ID
{
    CLIENT_DATA_DEFINE_ID_LMCDU,   // offset 0
    CLIENT_DATA_DEFINE_ID_CMCDU,   // offset MCDU_DATA_SIZE
    CLIENT_DATA_DEFINE_ID_RMCDU,   // offset MCDU_DATA_SIZE * 2
};
```

**Resolved layout — `MCDU_DATA_SIZE` = 1012 bytes.** The structs are **PACKED**
(`#pragma pack(1)`), so `MCDUCHAR` is **3** bytes (`char16_t` 2 + `bool` 1, NO tail pad):
`3 × 336 + 4 = 1012`. Offsets: L = 0, C = 1012, R = 2024; whole area = 3036 bytes.

⚠ **This number has been wrong twice, and both wrong answers read garbage without throwing.**

| Answer | Where it came from | Why it's wrong |
|---|---|---|
| 8068 | a doc-summarising fetch | back-computed a 24-byte `MCDUCHAR`; pure fabrication |
| 1348 | assuming natural alignment | a 4-byte `MCDUCHAR` (2 + 1 + 1 pad). Plausible C++ — and the trap: the arithmetic is self-consistent, so a size assert written against it **passes** while every cell is misaligned |
| **1012** | **the binary** | **correct** |

Do NOT re-derive this from prose, or from `sizeof` reasoning about the struct source — the C++
declaration alone does not tell you whether TFDi packed it. **The binary settles it**: DWARF gives
`MCDUEXPORTDATA byte_size = 1012` and `MCDUCHAR byte_size = 3` (`char16_t`@0, `bool`@2), and
`SetupExportData` contains a literal `i32.const 1012` (code offset 969964) feeding the one
`CreateClientData`. Independently corroborated by scanning the whole 103 MB wasm: `i32.const 1012`
occurs **9 times**, `i32.const 1348` occurs **zero** times — nothing in the aircraft ever computes
1348. If the CDU ever reads as noise, suspect this constant first.

Per-MCDU field offsets (stride **3**, not 4):

| Offset | Field |
|---|---|
| 0 | `dspy` (bool) |
| 1 | `fail` (bool) |
| 2 | `msg` (bool) — scratchpad message flag |
| 3 | `ofst` (bool) |
| 4 + (row*24 + col)*3 | `text[row][col].value` (`char16_t`, UTF-16 LE) |
| 6 + (row*24 + col)*3 | `text[row][col].large` (bool) — large vs small font |

`large` is the MD-11's title/label distinction — it is what tells a screen reader a line is a page
title or a big-font value rather than a small label, so keep it.

Writes go back the other way: **"Send commands back through SimConnect using custom key events"**
— i.e. `TDMD11.TRIGGER_EVENT` (the only dotted custom event in the wasm) and/or the `CEVENT`
L:var, with the MCDU key ids from the control map.

Corroborating symbols in the wasm: `MCDU::ExportText`, `MCDU::StoreText`, `MCDU::ResetText`,
`MCDU::MCDUEXPORTDATA`, `MCDU::PressButton`, `MCDU::SetPage`, `MCDU::SetKeyboardInput`,
`MCDU::LMCDU`/`CMCDU`/`RMCDU`, the whole `MCDU::SCRATCHPAD` API
(`add`/`clr`/`pushTypeIMessage`/`pushTypeIIMessage`/`clearTypeIMessage`/
`clearFirstTypeIIMessage`/`reset`), and `MCDU::Draw_*`/`Handle_*` for every page.

### 2c. The PFD / ND / EAD / SD / ISFD are NOT exported — proven, three independent ways

This one was inherited as an assertion for a while. It is now settled, and the evidence is worth
keeping so nobody spends another pass re-opening it:

1. **The binary.** Exactly ONE `SimConnect_MapClientDataNameToID` and ONE `CreateClientData` exist
   in the entire 18.5 MB code section — both for `MD11MCDU` — followed by three
   `AddToClientDataDefinition`/`SetClientData` (L/C/R). There is no `RequestClientData`/
   `GetClientData` import at all: the aircraft is a writer only.
2. **DWARF.** `CLIENT_DATA_ID` has a single member (`_MCDU`); `CLIENT_DATA_DEFINE_ID` has three
   (`_LMCDU`/`_CMCDU`/`_RMCDU`); there is one area-name constant and one `*EXPORTDATA` struct.
3. **The live aircraft.** Scraping the `VCockpit01/02/03 - WasmInstrument` views returns
   `textLen=0`, `canvases=0` — the DUs are GDI+ draws over internal `DEU::DRAWING_DATA`.

**The FMA follows from this.** The engaged autoflight modes (PROF, NAV, ALT HOLD, FMS SPD…) exist
only as UTF-32 string literals drawn onto the PFD — rendered, never exported. Across all ~2600
variables the aircraft defines there is no mode/FMA var. `MD11_CGS_PROF_BT` and friends are the
BUTTONS: they report what the pilot pressed, **not what engaged**, and a pressed mode can fail to
arm — so never present them as engagement. `MD11_AP_STATE`/`MD11_ATS_STATE` encode ENGAGEMENT only
(`FCC::GetAPState()`/`GetATSState()` → `AFSState{Off,Warn,On}`; the docs' 0=Off/1=AP1/2=AP2/3=AP1+2
for AP_STATE is presumably composed from FCC1+FCC2 — the `ATS_STATE` enum is undocumented).

That is why the exported L:vars matter: TFDi publish the numbers a sighted pilot reads off the
glass — V-speeds, minimums, altimeters, FCP windows, AP/ATS/APU state, fuel. For everything except
the MCDU, those exports **are** the instruments.

**Undocumented exports exist.** `MD11_ENG1_N1`/`ENG2_N1`/`ENG3_N1` are real registered L:vars that
TFDi's Variables page does not list (found in DWARF, confirmed live reading ~25.4% at idle with
per-engine variation). On an aircraft whose EAD cannot be read, that is the only engine N1 a blind
pilot gets. `MD11_ENG1_N2`/`_EGT`/`_FF` do NOT exist — they read a flat 0, exactly as an invented
name does, which is also the warning here: **a 0 read proves nothing** on this aircraft.

TFDi's `Interop` layer (`Interop.cpp`, the platform-abstraction seam) is where this all hangs
off: `SETFN_REGISTER_SHARED_VARIABLE` (L:vars), `SETFN_TRIGGER_SHARED_EVENT` (CEVENT), and
`SETFN_SET_EXPORT_DATA(void(*)(int, const char*, size_t))` — a keyed **string** export, which is
what the MCDU rides.

### 2d. The EFB is real HTML

`[VCockpit04] htmlgauge00=aircraft_efb/TFDi_MD11_efb/efb.html` — scrapeable exactly like the PMDG
EFB (`CoherentPmdgEfbClient` is the model).

### A correction, so nobody repeats it

An earlier pass concluded "the displays cannot be read" from the `wasm_gauge` finding alone. That
was wrong. "No DOM" ⇒ "Coherent scraping won't work"; it does **not** ⇒ "no readable channel".
The evidence pointing the other way was already in hand and got waved past: the wasm calls
`SimConnect_CreateClientData`/`MapClientDataNameToID`, TFDi's docs have a page literally titled
*Data Export*, and aviaCDU ships MD-11 CDU support commercially (so it is demonstrably readable).
A single 500 on a **mistyped host** was treated as evidence of absence. Check the primary source
before declaring a capability impossible — the [Troubleshooting Playbook](troubleshooting-playbook.md)
rule ("most 'broken' verdicts turn out wrong") applies to *whole features*, not just to controls.

## 3. Everything is relative. Nothing accepts "go to position 3".

Knobs expose `WHEEL_UP`/`WHEEL_DOWN`; rotary switches expose `LEFT_BUTTON_DOWN`/
`RIGHT_BUTTON_DOWN` (click the left/right half). MSFSBA's panels are combo boxes, so
`Md11SelectorWalker` closes the loop: read state → step once → re-read → repeat, bounded.

**Step polarity is documented nowhere** — the ModelBehaviorDefs give event ids and nothing about
their sign. Rather than guess across ~200 controls, the walker treats polarity as unknown,
assumes the conventional mapping, watches what the state var actually does, and flips + remembers
(keyed on node id) if it moved away from the target. Costs at most one wasted step per control,
once per session. The log line `step polarity calibrated to …` should appear **at most once per
control** — more than that means the walk is oscillating.

The Dial-A-Flap thumbwheel is continuous, not detented, and `WalkAnalogAsync` handles it by
*measuring* rather than assuming: one probe click yields a signed delta that carries both the step
size and the polarity, after which the remaining distance is arithmetic. Stepping it one click at
a time would need up to 100 clicks (raw 0–100) on a channel we are asked not to overuse.

## 4. The data-definition budget

SimConnect caps a client at ~1000 data definitions. There are 1404 controls. The split is
deliberate:

| Class | Count | UpdateFrequency | Individual defs |
|---|---|---|---|
| Buttons | 666 | `Never` (write-only) | **0** |
| Annunciators | 532 | `Continuous` + `IsAnnounced` → batch-covered | **0** |
| Switches / knobs / guards / levers / handles | ~206 | `OnRequest` | ~206 (cap is 900) |

Only `OnRequest` and `Continuous`-without-`IsAnnounced` consume individual defs. Flipping
annunciators to non-announced would add **532 individual defs** and blow past the cap — don't.
Watch `registration.log`'s `approxTotalDefs` after any change here.

## 5. The flap system

**The MD-11 has ONE handle for flaps and slats together**, plus a separate Dial-A-Flap thumbwheel
for the take-off angle. Clean → fully extended:

| Detent | `MD11_FLAP_RNG` | Notes |
|---|---|---|
| Flap Up / Slat Retracted | 0 | clean flight |
| Flap 0 / Slat Extended | 20 | slats out, flaps zero — low-speed margin without flap drag |
| **Dial-A-Flap** | **38–65 (range)** | take-off detent; angle comes from the thumbwheel |
| Flap 28 | 70 | mainly the go-around setting |
| Flap 35 | 82 | normal landing — less drag than 50 |
| Flap 50 | 100 | max landing flaps; not required every landing |

From clean, successive extend steps give: `0/EXT → DIAL-A-FLAP → 28 → 35 → 50`.

There is a **physical gate at 28** so the handle cannot slip straight between the take-off range
and the landing range. That is why 28 is a detent in its own right and not a waypoint: a go-around
from 35 or 50 retracts to **28 first**.

**Dial-A-Flap** selects any take-off flap angle from 10° to 25°. TFDi's own tooltip formula:

```
degrees = 10 + MD11_DIALAFLAP_IND_RNG / 6.6667     (raw 0…100 spans 10°…25°)
```

Exposed as a combo of whole degrees, 10–25 — that is how the setting is briefed and read
("dial a flap 15"); the var is continuous but fractional entries would be a combo with hundreds
of meaningless rows to arrow through.

### Invariants

- **The detents are CURATED, not parsed — six positions, not five.** TFDi's tooltip encodes five
  positions as an RPN `%{case}` map and the Dial-A-Flap detent as a **range test**
  (`38 65 (L:MD11_FLAP_RNG) rng`) *outside* the case block. A generic parser sees the cases and
  misses the range, so the lever reads as five positions with the take-off detent — the one the
  thumbwheel exists to serve — missing entirely. They are pinned in the generator's `CURATED`
  table. Regenerating must not lose them.
- **Never resolve the flap detent by nearest value.** Dial-A-Flap spans 38–65 but is represented
  by 50, so nearest-value hands everything from 60 up (the midpoint of 50 and 70) to "Flap 28":
  a handle in the take-off detent with the wheel toward 25° would read out, and be walked from,
  as 28. Use `Md11Detent.Matches` / `Md11SelectorWalker.PositionIndex`, which test the range
  first. Pinned by `Md11SelectorWalkerTests.PositionIndex_DivergesFromNearestValue_InsideTheDialBand`.
- **Every Dial-A-Flap read-out carries its angle.** Handle position and selected angle are two
  independent facts; "Dial-A-Flap" alone does not tell a pilot what they are rotating on.
- **A failed walk must SPEAK.** Success is silent (the screen reader already announced the combo
  selection — the global `_uiSetEcho` rule), but a walk that does not reach its target says so.
  On an aircraft with no readable gauge, a silently-failed selection is indistinguishable from a
  successful one.

## 6. The control map

The 1404 controls are **generated, not hand-written**:

```bash
python tools/md11-gen/generate_md11_map.py          # finds the install itself → md11_control_map.json
cp tools/md11-gen/md11_control_map.json MSFSBlindAssist/Resources/
```

The generator finds the MD-11 itself — FS2020 and FS2024, Microsoft Store and Steam,
and custom/external package folders (including a packages root whose add-on folder is
not literally named `Community`; the owner's FS2024 install keeps it in `Community2024`).
It identifies the package by looking for `ModelBehaviorDefs/TFDi_Design/MD11` inside a
folder rather than by the folder's name, so a TFDi package rename does not break it.

- Installed in two sims? It lists both and asks which to use (pass `--pkg` to skip the
  question, or when running unattended).
- Can't find the aircraft, or finds it without `md11host.wasm`? It **stops and writes
  nothing**. It must never emit a map with no wasm-derived L:vars — those are the PFD
  speed-tape and V-speed read-outs, which have no other source.
- `--pkg` / `--wasm` still override discovery entirely.

The `md11host.wasm` location differs between installs (`common/panel/` on FS2024,
`panel/` on FS2020), so it is searched for, never assumed.

It reads the aircraft's own `ModelBehaviorDefs` + `md11host.wasm`. Every label, detent name and
switch position is **TFDi's own tooltip wording**, so the screen reader says what the real cockpit
says. After a TFDi update, regenerate — don't patch C#.

The JSON is an **`EmbeddedResource`**, deliberately not the repo's usual `None Update` +
CopyToOutputDirectory: the MD-11 has *zero* controls without it, so a file that can go missing
from the output folder is not an acceptable failure mode (unlike `Resources\*.js`, where a missing
agent degrades to one broken feature).

Panels come from the node id's structure, `MD11_<AREA>_<SUBSYSTEM>_…`: **section = area**,
**panel = subsystem**. The subsystem split is what makes the aircraft navigable — the Overhead
alone has 429 controls, which as one flat panel is unusable with a screen reader; split it becomes
Electrical (74), Pneumatic (74), Fuel (69), Lights (58), Hydraulics (37), Flight Controls (28)…

Annunciators are **excluded from panels** and announced on change instead (the A380 rule: a panel
is for operating controls, not scanning 532 lamp rows). A blind pilot cannot see a lamp light up,
so announcing them is the highest-value thing this aircraft does — but 532 of them may be a
torrent on startup. If so the answer is Ctrl+M, or trimming `IsAnnounced` to a safety subset.

### Generator gotcha: the export scan is prefix-based

`EXPORT_PREFIXES` missed 11 documented exports on the first pass — `MD11_V1`/`VR`/`V2`/`VSR`/`VFR`
are single tokens with no shared prefix (and a bare `MD11_V` prefix would drag in every
`MD11_VLV_*`/`MD11_VOR_*` control), and `MD11_ATS_`/`MD11_CAP_`/`MD11_FO_` simply weren't listed.
Those are exactly the blind-pilot read-outs — the V-speeds have **no other source**, there is no
speed tape to read. `EXPORT_EXACT` now carries the no-prefix ones. Cross-check any new export
against the docs' Variables page, not just the wasm scan.

## 7. Aircraft variants

Installed as five packages (FS2020 Community): a base package plus GE/PW × pax/cargo, and separate
"Flagship" variants. Identity:

- `atc_model` = `MD11` (pax) or `MD11F` (freighter); `icao_type_designator` matches.
- Every `title` starts with `TFDi Design MD-11`.

**There is no aircraft auto-detection in this app** — selection is a manual menu choice persisted
to `UserSettings.LastAircraft`. Nothing maps an ATC model to a definition, so there is no match
pattern to register. (`AircraftIcaoTypeDetected` exists but only feeds GSX door-side lookup.)

## 8. Status

### Verified against a live aircraft (2026-07-17)

Probed on a running MD-11 via the Coherent debugger, so these are facts rather than intentions:

- **The EFB works end-to-end.** Its own Coherent view (`VCockpit04 - TFDi_MD11_efb`); the agent
  injects, scrapes and CLICKS — a tab click re-rendered React and the page changed. Every page
  reads: Dispatch, Payload (live fuel 33069 lb, editable), Perf (ICAO/Runway/Wind/Temp/Pressure),
  Charts, Services (door buttons), State, Options (incl. a range slider).
- **The FCP takes typed values.** `MD11_EXTCTL_FCP_HDG = 123` → `MD11_AFS_HDG` = 123, inbox reset
  to -1. `SPD_U=1` + `SPD=0.82` → `AP_IAS_MACH`=1, `AFS_SPD`=0.81999999 (float32).
- **Engine N1 exists** (`MD11_ENG1/2/3_N1`, ~25.4% at idle) though undocumented.
- **The displays do not export.** See §2c — three independent proofs.
- **Flap detents match the aircraft's own XML**, corroborated by TFDi's shipped ReadyToFly state
  (handle 46.91 in the Dial-A-Flap band, `commandedFlapsDeg` 14.95 = the band geometry exactly).

### Switch actuation flood — root-caused from the user's logs (2026-07-17)

The first in-sim switch test failed: detented controls (autobrake the worst) reported *"did not
move. It may be guarded, unpowered, or inhibited."* `debug.log` showed the cause — NOT the CEVENT
channel, but a **SimConnect send-queue flood**. Arrowing through a combo fires a SET for every
intermediate entry, and the generic detented-walk path ran ONE `WalkAsync` per intermediate value.
Several walks then ran at once on the SAME control, each `RequestVariable(forceUpdate:true)` every
~150 ms, until SimConnect choked and threw `0xC00000B0` on **both** reads and the MobiFlight write.
Reads returned null → the walk logged `state var … unreadable — aborting walk` → "did not move."
Autobrake (5-position) spawned the most concurrent walks (176 `0xC00000B0` reads) and never once
read successfully; GPWS (36×) was intermittent and only ever moved via the direct-L:var-write
fallback.

Fix: the generic detented path now debounces + single-flights per control and cancels superseded
walks, exactly as the Dial-A-Flap path already did (`DebouncedWalk` in `TFDiMD11Definition.Interaction.cs`;
`WalkAsync`/`ReadAsync` take a `CancellationToken`). One walk to the final selection, no flood.
**Still needs the in-sim retest** to confirm reads stop erroring and the switch reaches the detent.

### Still unflown

Builds clean; the characterization suite passes. These need a real flight:

- **CEVENT actuation end-to-end** — does a panel button actually move the switch? Confounded by the
  flood above until now: in the logs, CEVENT clicks showed *some* movement on GPWS ("value went
  1 -> 0/2" during polarity calibration) but the only thing that reliably moved a switch was the
  direct-write fallback. With the flood fixed, retest whether clicks actuate; if not, the direct
  write now has a clean shot, and `TDMD11.TRIGGER_EVENT` remains the untried fallback.
- **Walker convergence** — does a combo selection land? Does `step polarity calibrated to …`
  appear at most once per control?
- **The MCDU on screen** — the transport is wired and the struct size is now proven from the
  binary (§2b), but no one has yet watched a page render. If it reads as noise, re-read §2b.
- **Flap handle** — all six detents; the 28 gate on a go-around from 35/50.
- **Dial-A-Flap** — 10–25° lands on whole degrees; the analog walk converges in a few rounds.
- **Annunciator chattiness** — 532 announcing lamps on startup. Partly addressed: a per-lamp
  anti-flap guard (`SuppressAnnunciatorFlap`, `TFDiMD11Definition.Interaction.cs`) now drops a lamp
  that blinks 3+ times in 5 s — the pneumatic avionics fan flow light pulsing with bleed flow on a
  throttle advance was the reported case. First one or two transitions still speak (a one-shot
  caption is never delayed); Ctrl+M still fully mutes any lamp. Retest for the right aggressiveness.
- **`MD11_EXTCTL_FLAP_HANDLE`** — documented as "set the current flap handle position", but the
  *encoding is unknown* (detent index? RNG value?). Now that the other EXTCTL vars are proven to be
  one-shot command inboxes, this very likely replaces the whole lever walk with one write. Probe it.
- **Def budget** — check `registration.log` `approxTotalDefs` on first load.

### Not started

- **V1/VR/V2 hotkey** — no `HotkeyAction` exists for take-off V-speeds; they are reachable in the
  Read-outs → V-Speeds panel. `ReadSpeedS`/`ReadSpeedF` are claimed for VSR/VFR, which are exact
  concept matches (slat/flap retraction speed).
- **A dedicated "read the selected FCP value" hotkey.** The FCP window (Ctrl+P) speaks all four
  values with their modes, but there is no output-mode key for them; adding one means adding new
  `HotkeyAction`s to the shared enum, which touches every aircraft.

### V/S engage (2026-07-18) — needs in-sim confirmation

The reporter found V/S "doesn't engage" and noted there was no button to activate V/S mode. There
isn't one on the aircraft either: the MD-11's ONLY V/S controls are the **V/S / FPA wheel**
(`MD11_CGS_VS_KB`, WHEEL_UP/DOWN — no push/pull) and the VS/FPA display toggle. Rotating that wheel
is what engages the pitch mode; a bare `MD11_EXTCTL_FCP_VR` write only fills the window, and a value
can sit in a window the FCC is not flying. Fix:

- The wheel is now exposed directly — as an "Up/Down" row in the Ctrl+P **FCP window**
  ("Vertical speed wheel") and as "Wheel up/down" actions in the **Ctrl+V dialog**. One CEVENT step
  per click (`TFDiMD11Definition.FireControlEvent` fires a SINGLE event, unlike the DOWN/UP-pair
  `PressControlEvents`).
- The Ctrl+V **typed value now auto-engages**: `SetVerticalSpeedEngaged` nudges the wheel once to
  engage, then writes the exact value AFTER the nudge lands (the wheel rides the paced CEVENT queue,
  the EXTCTL write is immediate — writing the value first would let the later click drag it off
  target).

UNVERIFIED: whether one wheel step reliably engages V/S from PROF/ALT HOLD, and whether the EXTCTL
value then holds once engaged. If the auto-engage falls short in sim, the manual wheel controls are
