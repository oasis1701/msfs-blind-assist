# TFDi Design MD-11

Aircraft code `TFDI_MD11`. Definition: `MSFSBlindAssist/Aircraft/TFDiMD11Definition*.cs`
(+ `Aircraft/MD11/`). Control map generator: `tools/md11-gen/generate_md11_map.py`.

The MD-11 does not resemble any other aircraft MSFSBA supports. Read this before touching it —
most of what you know from the FBW/PMDG/HS787 work is wrong here.

---

## 1. It is event-driven. There is no L:var to set.

TFDi's Integration Guide (`md11.tfdidesign.com/md11/integration-guide`) is explicit:

> The TFDi Design MD-11 is primarily event-driven. This means that variables and systems are
> driven by an event, not by reading the state of an L:VAR or similar. **Writing directly to any
> of the variables will bypass our integrity checks and allow potentially incorrect or conflicting
> states.** To trigger a custom event, you can write the value of the event ID to the L:VAR named
> `CEVENT` and our code will translate it. Please note that **the aircraft itself also uses this
> event, so do not overuse it.**

So every switch, knob and button is actuated by writing ONE integer — the event id — to
`L:CEVENT`. There is no per-control L:var to write, and writing one anyway is explicitly
unsupported. `Md11EventBus` owns this channel and is the ONLY way to actuate the aircraft.

Three writes bypass CEVENT, all through `Md11EventBus.WriteExternal` (seq-prefixed, calc path),
and the set is closed:

- **`MD11_EXTCTL_*`**, the sanctioned exception, which TFDi document as "designed for external
  control of the aircraft" — those *are* direct writes by design (fuel, FCP values, baro, minimums,
  outflow, ZFWCG, flap/spoiler handle).
- **The Dial-A-Flap thumbwheel's own backing var** `MD11_DIALAFLAP_WHEEL_RNG`
  (`Md11FlapSystem.SetDialRawAsync`, the only setter the panel uses): the wheel spans ~90 raw units
  at one unit per WHEEL CEVENT, and bursting that many clicks jams it at an end stop (proven live).
- **The walk's direct-write fallback** (`TryDirectSetAsync`), reached only after a closed-loop walk
  failed to move a control. It writes the control's L:var and confirms by re-reading the control's
  own registered definition — so `Md11DirectSet.Refuse` lets it write ONLY the var that definition
  reads back, and never a control in `Md11DirectSet.FallbackNeverWrites`: the speedbrake lever (its
  row reads `MD11_SPDBRK_RNG`; the map's state var is `MD11_SPDBRK_HANDLE`, the 0/1/2 ground-spoiler
  pull — a dropped wheel click once wrote 17.5 there and blanked the Ground spoilers row), the flap
  lever (`MD11_FLAP_RNG` is ASSUMED to be the handle's animation — unmeasured; §8 carries the probe
  that would settle it) and the gear switch (`MD11_MIP_GEAR_SW` is the lever's 0–25 travel). A
  refused control logs
  `direct write of N refused — …` and speaks the same "did not move" as a failed write. This
  fallback is what moved the fuel switches, the IRS selectors and GPWS in the early logs, before
  `ToggleCoreAsync` existed; today it remains the hand-over for a click that changes nothing.

The name half of that gate has an exact scope, and it is narrower than it looks: it catches a
definition RE-POINTED off the map's state var (the speedbrake shape). A state var that is the wrong
QUANTITY under its own name is invisible to it — the EFIS minimums caps read `MD11_CAP/FO_MINIMUMS`,
the minimums VALUE, under exactly that name, so this gate alone would let a 0/1 be written there.
They are kept off the fallback one level up instead: `Md11ExportBacked` refuses an export-backed row
at the top of `SetControl`, so the walk never starts. A future control of that shape must be kept
off the walk the same way, or added to `FallbackNeverWrites`; nothing in the gate can infer it.

**Three constraints fall out of that paragraph. All three are load-bearing:**

1. **Anti-coalesce.** MobiFlight's command channel silently drops a calc string identical to the
   previous one (already bit this repo twice: the A380 RMP repeated-digit drop, the DCDU
   WILCO→SEND two-step). Here it is worse than cosmetic — the string for a given event id is
   *always* the same, so pressing a button twice, or stepping a knob N times, would land exactly
   once. Every write carries a `{seq} 0 *` prefix, which computes a discarded zero purely to make
   the string textually unique. **Never route a CEVENT write through `SetLVar`** — it emits the
   bare `"86018 (>L:CEVENT)"` and the repeats vanish.
2. **Pacing.** "Do not overuse it" is real: `CEVENT` is a single shared slot the aircraft's own
   code also writes. Writes are serialized through one queue with a minimum gap so ours cannot
   race or clobber theirs.
3. **Press *and* release.** Buttons carry a DOWN id and an UP id. Sending only DOWN leaves the
   button held for the session — the Fenix stuck-button bug, which on that aircraft re-fired the
   takeoff-config test after touchdown. Always send both.

`TDMD11.TRIGGER_EVENT` also exists in the wasm (the only dotted custom event) and is a plausible
native-SimConnect alternative to the CEVENT L:var — no MobiFlight dependency, no coalescing, no
shared-slot race. It is **undocumented and untested**; if CEVENT proves racy in the sim, this is
the first thing to try.

**And a fourth: the module itself is a hard dependency, and only the probe can say so.** Every
write above lands in MobiFlight's command client-data area, and `MobiFlightWasmModule.IsConnected`
is true whether or not a WASM module is installed to read it (`Initialize` is purely local
client-data setup). With no module every press is dropped, the bus writes `quiet`, and the
feedback sentence reads the unchanged state back as the result. The one signal that works is
MainForm's end-to-end calc-path probe: a nonce written through the calculator to
`L:MSFSBA_BRIDGE_PROBE` and read back over a data definition (`SimConnect/BridgeProbe.cs`). An
aircraft opts in by REGISTERING that var, and the MD-11 does (`BuildVariables`, one extra
OnRequest def, §4). A working install logs `calc path VERIFIED after N attempt(s)` within a few
seconds of detection; a missing module logs `calc path NOT available after 40 attempt(s)` after
~60 s and speaks, once and queued, "MobiFlight calculator path unavailable. Some cockpit controls
may not respond." Until 2026-09-09 the MD-11 was outside the probe altogether — the timer gated
on an FBW type list — so a missing module was never spoken, and every MD-11 load logged
`calc path NOT available after 0 attempt(s)`, a false alarm on a healthy install that the opt-in
retires. The probe var is ours, not the aircraft's: it is not in `SeededScalarKeys`, so its nonce
is never evidence for the context-reset seed gate (§8), and it is in no panel and no Ctrl+M row.

## 2. The displays have NO DOM — but the MCDU IS fully exported over a Client Data Area

Two separate facts. Do not collapse them (an earlier pass did, and wrongly concluded the CDU was
unreadable — see "A correction" below).

### 2a. There is no DOM. Coherent scraping cannot work here.

`PANEL.CFG` declares every screen as a WASM-rendered gauge:

```
htmlgauge01=WasmInstrument/WasmInstrument.html?wasm_module=md11host.wasm&wasm_gauge=DU1
…DU2 … DU6, LMCDU, RMCDU, CMCDU, ISFD, AFS, FUEL, RADIOS_XPNDR
```

They are drawn from inside `md11host.wasm` via NanoVG. **There is no HTML DOM behind them**, so
the Coherent-debugger scrape that reads the PMDG / FBW / HS787 CDUs has nothing to read.
**Do not sink time into DOM-scraping the MD-11's displays.**

### 2b. The MCDU is exported as TEXT over SimConnect. Use this.

Documented at <https://docs.tfdidesign.com/md11/integration-guide/data-export> (note the host —
`docs.tfdidesign.com`, NOT `md11.tfdidesign.com`, which 500s). Every name below is corroborated
directly in `md11host.wasm`.

The MD-11 publishes all three MCDUs as **plain text** in a SimConnect **ClientDataArea** — the
same mechanism PMDG uses, which this codebase already has infrastructure for
(`PMDG777DataManager` / `PMDGNG3DataManager` are the reference).

**Registration name: `MD11MCDU`.** Read with `SimConnect_RequestClientData` — an ON_SET+CHANGED
subscription PLUS a start-up `PERIOD.ONCE` snapshot on a distinct request id per unit, because
the subscription alone never delivers the current page (the full measurement is under §9's
transport facts).

```c
struct MCDUCHAR
{
    char16_t value;
    bool large = false;
};

struct MCDUEXPORTDATA
{
    bool dspy = false;
    bool fail = false;
    bool msg = false;
    bool ofst = false;

    MCDUCHAR text[MCDU_ROWS][MCDU_COLS];
};

#define MCDU_ROWS  14
#define MCDU_COLS  24
#define MCDU_CHARS MCDU_ROWS * MCDU_COLS

size_t MCDU_DATA_SIZE = sizeof(MCDUCHAR) * MCDU_CHARS + (sizeof(bool) * 4);

enum CLIENT_DATA_DEFINE_ID
{
    CLIENT_DATA_DEFINE_ID_LMCDU,   // offset 0
    CLIENT_DATA_DEFINE_ID_CMCDU,   // offset MCDU_DATA_SIZE
    CLIENT_DATA_DEFINE_ID_RMCDU,   // offset MCDU_DATA_SIZE * 2
};
```

**Resolved layout — `MCDU_DATA_SIZE` = 1012 bytes.** The structs are **PACKED**
(`#pragma pack(1)`), so `MCDUCHAR` is **3** bytes (`char16_t` 2 + `bool` 1, NO tail pad):
`3 × 336 + 4 = 1012`. Offsets: L = 0, C = 1012, R = 2024; whole area = 3036 bytes.

⚠ **This number has been wrong twice, and both wrong answers read garbage without throwing.**

| Answer | Where it came from | Why it's wrong |
|---|---|---|
| 8068 | a doc-summarising fetch | back-computed a 24-byte `MCDUCHAR`; pure fabrication |
| 1348 | assuming natural alignment | a 4-byte `MCDUCHAR` (2 + 1 + 1 pad). Plausible C++ — and the trap: the arithmetic is self-consistent, so a size assert written against it **passes** while every cell is misaligned |
| **1012** | **the binary** | **correct** |

Do NOT re-derive this from prose, or from `sizeof` reasoning about the struct source — the C++
declaration alone does not tell you whether TFDi packed it. **The binary settles it**: DWARF gives
`MCDUEXPORTDATA byte_size = 1012` and `MCDUCHAR byte_size = 3` (`char16_t`@0, `bool`@2), and
`SetupExportData` contains a literal `i32.const 1012` (code offset 969964) feeding the one
`CreateClientData`. Independently corroborated by scanning the whole 103 MB wasm: `i32.const 1012`
occurs **9 times**, `i32.const 1348` occurs **zero** times — nothing in the aircraft ever computes
1348. If the CDU ever reads as noise, suspect this constant first.

Per-MCDU field offsets (stride **3**, not 4):

| Offset | Field |
|---|---|
| 0 | `dspy` (bool) |
| 1 | `fail` (bool) |
| 2 | `msg` (bool) — scratchpad message flag |
| 3 | `ofst` (bool) |
| 4 + (row*24 + col)*3 | `text[row][col].value` (`char16_t`, UTF-16 LE) |
| 6 + (row*24 + col)*3 | `text[row][col].large` (bool) — large vs small font |

`large` is the MD-11's title/label distinction — it is what tells a screen reader a line is a page
title or a big-font value rather than a small label, so keep it.

Writes go back the other way: **"Send commands back through SimConnect using custom key events"**
— i.e. `TDMD11.TRIGGER_EVENT` (the only dotted custom event in the wasm) and/or the `CEVENT`
L:var, with the MCDU key ids from the control map.

Corroborating symbols in the wasm: `MCDU::ExportText`, `MCDU::StoreText`, `MCDU::ResetText`,
`MCDU::MCDUEXPORTDATA`, `MCDU::PressButton`, `MCDU::SetPage`, `MCDU::SetKeyboardInput`,
`MCDU::LMCDU`/`CMCDU`/`RMCDU`, the whole `MCDU::SCRATCHPAD` API
(`add`/`clr`/`pushTypeIMessage`/`pushTypeIIMessage`/`clearTypeIMessage`/
`clearFirstTypeIIMessage`/`reset`), and `MCDU::Draw_*`/`Handle_*` for every page.

### 2c. The PFD / ND / EAD / SD / ISFD are NOT exported — proven, three independent ways (read by AI vision instead, §11)

This one was inherited as an assertion for a while. It is now settled, and the evidence is worth
keeping so nobody spends another pass re-opening it:

1. **The binary.** Exactly ONE `SimConnect_MapClientDataNameToID` and ONE `CreateClientData` exist
   in the entire 18.5 MB code section — both for `MD11MCDU` — followed by three
   `AddToClientDataDefinition`/`SetClientData` (L/C/R). There is no `RequestClientData`/
   `GetClientData` import at all: the aircraft is a writer only.
2. **DWARF.** `CLIENT_DATA_ID` has a single member (`_MCDU`); `CLIENT_DATA_DEFINE_ID` has three
   (`_LMCDU`/`_CMCDU`/`_RMCDU`); there is one area-name constant and one `*EXPORTDATA` struct.
3. **The live aircraft.** Scraping the `VCockpit01/02/03 - WasmInstrument` views returns
   `textLen=0`, `canvases=0` — the DUs are GDI+ draws over internal `DEU::DRAWING_DATA`.

**The FMA follows from this.** The engaged autoflight modes (PROF, NAV, ALT HOLD, FMS SPD…) exist
only as UTF-32 string literals drawn onto the PFD — rendered, never exported. Across all ~2600
variables the aircraft defines there is no mode/FMA var. `MD11_CGS_PROF_BT` and friends are the
BUTTONS: they report what the pilot pressed, **not what engaged**, and a pressed mode can fail to
arm — so never present them as engagement. `MD11_AP_STATE`/`MD11_ATS_STATE` encode ENGAGEMENT only
(`FCC::GetAPState()`/`GetATSState()` → `AFSState{Off,Warn,On}`; the docs' 0=Off/1=AP1/2=AP2/3=AP1+2
for AP_STATE is presumably composed from FCC1+FCC2 — the `ATS_STATE` enum is undocumented).

**What IS readable: the FCP's own windows.** TFDi's Systems Guide (Forward Panel page) documents
the FCP's engagement cues, and the exported window values carry them: the IAS/MACH window "shows
dashes when the AFS is controlling to the FMS flight plan speed" (`MD11_AFS_SPD` = -999 ⇔ FMS SPD
engaged), the HDG/TRK window "is blank when the AFS is controlling to the FMS flight plan"
(`MD11_AFS_HDG` = -999 ⇔ NAV engaged), and the V/S-FPA window "is blank if V/S or FPA are not
engaged" (`MD11_AFS_VS` = -9999 ⇔ neither is — PROF or ALT HOLD, indistinguishable). Measured
2026-09-06 at FL360 with NAV, PROF and FMS SPD engaged: all three dashed, every `MD11_CGS_*_BT`
button var 0. Each window's dash is its OWN sentinel — `Md11Fcp.IsDashedSpeedHeading` (-999) and
`Md11Fcp.IsDashedVerticalSpeed` (-9999), every caller naming its window — because a selected
-999 fpm is a real V/S that a shared test read as "dashed, not engaged". A Mach target reads to
three decimals, as the FCP window renders it (`%0.3f`): "Mach 0.825", "Mach 0.820".
`Md11AutoflightState` composes every autoflight string from these plus
`MD11_AP_STATE` and `MD11_ATS_STATE` (1 measured with the ATS engaged; 0 off; 2 never seen), and
it is the ONLY place the words live — the FCP window, the Shift+H/S/A/V read-outs, the
Ctrl+H/S/A/V dialogs and the Autoflight Status rows all call it. PROF and APPR/LAND stay
unclaimed: their engagement exists only on the FMA.

That is why the exported L:vars matter: TFDi publish the numbers a sighted pilot reads off the
glass — V-speeds, minimums, altimeters, FCP windows, AP/ATS/APU state, fuel. For everything except
the MCDU, those exports **are** the instruments.

**Undocumented exports exist.** `MD11_ENG1_N1`/`ENG2_N1`/`ENG3_N1` are real registered L:vars that
TFDi's Variables page does not list (found in DWARF, confirmed live reading ~25.4% at idle with
per-engine variation). On an aircraft whose EAD cannot be read, that is the only engine N1 a blind
pilot gets. `MD11_ENG1_N2`/`_EGT`/`_FF` do NOT exist — they read a flat 0, exactly as an invented
name does, which is also the warning here: **a 0 read proves nothing** on this aircraft.

TFDi's `Interop` layer (`Interop.cpp`, the platform-abstraction seam) is where this all hangs
off: `SETFN_REGISTER_SHARED_VARIABLE` (L:vars), `SETFN_TRIGGER_SHARED_EVENT` (CEVENT), and
`SETFN_SET_EXPORT_DATA(void(*)(int, const char*, size_t))` — a keyed **string** export, which is
what the MCDU rides.

### 2d. The EFB is real HTML — and how it is read

`[VCockpit04] htmlgauge00=aircraft_efb/TFDi_MD11_efb/efb.html` — an ordinary Coherent view (a React
app at `#MSFS_REACT_MOUNT`), scraped and driven exactly like the PMDG tablet: `CoherentPmdgEfbClient.ForMd11()`
installs `Resources\coherent-md11-efb-agent.js`, the shared `FbwEfbForm` shows the result (Shift+T).
The bundle `efb.js` under `Community2024\tfdidesign-aircraft-efb\html_ui\...\TFDi_MD11_efb\` is
**unminified** — read the component source before guessing at a DOM shape.

**The reader recognises the EFB's building blocks by STRUCTURE** (`A.BLOCKS`, tried before the generic
walk; first match owns the subtree; colour is only ever the selected-state cue):

| Block | Cue | Reads as |
|---|---|---|
| section strip | `ul[role=tablist] > li > button`, active = `underline` | "General (selected)" |
| choice group | `div[role=group]` of buttons, chosen = `bg-green-700`/`-600`, caption = the span before it | one dropdown "Weight Units: Imperial"; a lone disabled button = "…: N/A on Pax Model" |
| stepper | `div > input[disabled] + ChevronUp + ChevronDown` (the EFB's `Select`) | one dropdown with the FULL list, read from the FIRST fiber carrying an `options` array (`input[__reactFiber$…].return.return.memoizedProps.options`) — an EMPTY array is the component before its list exists and counts as no list, never a reason to keep walking up into an ancestor's `options`; without it: the static "Runway: RW06L" ("Runway: (empty)" when the field is blank), then "Runway previous (now RW06L)" / "Runway next (now RW06L)" (each arrow repeats the field and the current value; the arrows carry a stable `key`, which keeps the node across a press, and `announceChange: true`, which makes the shared shell speak its new label) |
| unit box | short text-only `div` right after an input, holding a letter, `°` or `%` — so a numeric value ("507.9") is never taken for a unit | "Temperature (°C)" |
| span row | `div` of plain spans | "Headwind 0 KT", "Slope 0.1%" |
| read-out row | `h3/p/span` + short `p`/`span`, or a label + DISABLED input | "Block Fuel: 77347 lbs", "V1: 155", "Load: 35%" — each with a stable `key`, so a new value patches the node in place; a disabled input is never an edit box, and a disabled checkbox/radio/range is never a read-out (it stays its own control) |
| tile | `p` + `button`; or `button(p)` + `button` | "GPU: Connect"; "Cold and Dark" / "Cold and Dark: Set as default" / "Cold and Dark is the default". The tile button and the State tile's action button each carry a stable `key` (`tile:<name>`, `tile-action:<name>`); the load button ("Ready to Fly") needs none, its label never changing, so it and "Ready to Fly: Set as default" never share a reconcile key. When the EFB swaps that action button for its check mark, the reader keeps a BUTTON under the same key, labelled "Ready to Fly is the default" (`announceChange`), so the node survives the press and the outcome is spoken; a press on it is refused (the shell says "Activating Ready to Fly is the default" and nothing reaches the EFB). The tile button and the state tile's ACTION button carry `announceChange: true` (their label holds their own state); the load button beside it does not, its label never changing on a press |
| pre | `<pre>` (the OFP) | `controlType 'pre'`, line breaks kept |
| toast | `div.absolute.bottom-0.right-0.z-10 > div(msg + X)` | `kind 'alert'` (spoken at once) + "Close" |
| locked page | any `pointer-events-none` subtree with children (GroundPage in flight) | content read, every control `disabled` — and never pressed or written (see Presses) |
| charts strip | button row: one `bg-*-500`, rest `bg-navigraph-background` | "STAR (selected)" |
| Dispatch header | Dispatch page only, exact row shapes | "Flight …", "From …", "To …", "Departure …", "Arrival …", "Alternate …", "Route …" |

The page tab bar is found by `A.findTabBar`: it skips a hidden bar, tolerates non-button children in
the nav row (and still reads them), prefers the bar carrying the current-page marker, and never takes
a choice group or the Charts strip (exactly five buttons) for the nav bar.

Casing: a Tailwind `uppercase` element is read from `textContent` ("Save", "General"), because
Chromium's `innerText` applies the transform and a screen reader spells "SAVE" — and only from its
RENDERED descendants, so text hidden inside it is never read.

**Presses.** `A.click` fires pointerdown/mousedown/pointerup/mouseup and then `el.click()` — a real
click event with activation behaviour, which bubbles and which React's `onClick` handles **exactly
once**. Until 2026-09-06 a synthetic bubbling `click` MouseEvent was dispatched as well, so every
press ran the handler TWICE; it went unnoticed only because this EFB's handlers close over state
captured at render (a door tile toggles to the state it captured, so twice lands where once does),
and a handler reading live state or counting presses would have stepped twice per press. The
"one call = one step on the Autobrake stepper" measurement dated 2026-09-05 was taken WITH the
double dispatch and does not carry over — **re-measured 2026-09-06 on the ground at UCFM
instead:** the Thrust Setting stepper walked FLEX → TO1 (two presses) and back with `el.click()`
alone, a Weight Units dropdown set applied both ways, Save produced the spoken toast, and after
one full scrape the next scrapes answered `unchanged:true` on the live page. React applies the
press on the NEXT tick, so the stepper walk (`A.stepTo`) presses, waits
`STEP_DELAY_MS`, re-reads, repeats — never inline. A choice-group pick presses that option's own
button. A text field commits with input + change + blur/focusout (the EFB's `Input` reformats in
`onBlur`).

**The reader never acts inside the EFB's in-flight lock.** `clickElement` and `setValue` return
`false` without dispatching anything when the target sits inside a `pointer-events-none` wrapper
(`A.isInert`, the same `A.isInertRoot` test the walk uses to dim what it reads, so the two cannot
drift). `pointer-events: none` blocks REAL hit-testing only — a dispatched event or `el.click()`
reaches the handler regardless — and the EFB's door, GPU and state handlers carry no ground check
of their own, so without this the reader would open a cargo door in the cruise. The shell's
native-list fallback (the WebView2-failed list mode, `FbwEfbForm.CreateControlFor`) is reached by
exactly that path, and honours `Disabled` the way the browser shell does: the control stays
focusable, its label gains ", dimmed", and activating it announces "Unavailable" without posting — a
WinForms `Enabled = false` would drop it from the tab order — and a flip of `Disabled` alone rebuilds
the control (`StructureSignature`). `A.setValue` returns `A.clickElement`'s real result for a checkbox
and refuses a disabled element on its native-setter path, and `A.controlFor` builds on `A.el`, so the
`_inert` → disabled rule holds there too.

**The dirty gate pauses while the reader works.** `collect()` mutates the DOM itself — it clears
stale `data-md11-efb-idx` stamps, stamps fresh ones, and sets/clears the `data-md11-efb-label`
claims — so the MutationObserver, armed with `attributes:true` over the same subtree, queued the
reader's OWN bookkeeping and re-armed `_dirty` as a microtask after every scrape. `unchanged:true`
could therefore never fire on the live page and the window paid a full traversal every ~400-600 ms
poll (the OFP page streams ~100 KB of it). `scrape()` now disconnects `A._obs` for exactly the
duration of `collect()` and re-observes in a `finally` — safe because JS is single-threaded and
`collect()` never yields, so nothing else can mutate the DOM meanwhile — with a forced full scrape
every `FORCE_FULL_EVERY` (10th) poll as the safety net for a change the observer cannot see. The
PMDG reader carries the same pattern and the same note. The harness had missed this because its
"unchanged" test called `scrape()` twice synchronously, so no MutationRecord was ever delivered;
it now awaits a tick between the two.

**The shell's reconcile key is explicit where a label carries state.** This reader puts a control's
state IN its label — "Passenger 1L: Closed" → "Open", "GPU: Connect" → "Disconnect", "Runway next
(now 06R)", "Load: 35%" — and the shared shell (`FbwEfbForm`, mirrored by `flypad-shell.html`) keys
each node by its rendered type plus its label, so every flip was a NEW key: the node the pilot had
just pressed was destroyed and rebuilt under their screen-reader focus, and its new label was never
spoken. So every element whose label carries changing state carries an explicit, stable `key` —
`tile:<name>`, `tile-action:<name>`, `step-prev:` / `step-next:` / `step-value:<field>`,
`readout:<caption>` — which the shell's `keyOf` prefers over the text key (`rk(it) + '|k:' + key`). The
key rides agent → `EFBElement` → page JSON and is part of `CoherentPmdgEfbClient.ElementsSignature`,
the push hash, as a dropdown's options now are too. #189 first solved this with two text heuristics in
the SHARED `baseLabel` — strip a `(now …)` suffix, strip any after-colon tail — and both are gone, the
text key back to exactly its pre-#189 rules (the parenthesised state suffixes and `: placed` /
`: not placed`): the colon rule collapsed the flyPad ATC page's "UNICOM 122.800: Set Active" and
"…: Set Standby" onto one key held apart only by DOM position, and this EFB's own "Ready to Fly" and
"Ready to Fly: Set as default" likewise. Never add a text heuristic to the shared shell for one
reader; stamp a `key` in the reader. Pinned in `tools/flypad-shell-test` (no key → the full-text key,
so the ATC pair stays two keys; an explicit key wins — against both the shipping shell and
`flypad-shell.html`) and in `tools/md11-efb-test` (keys stamped on tiles, arrows and read-outs;
"Set as default" keeps its kind and key).

**The shell's post-press announce.** Keeping the node is only half of it: the new label is SPOKEN because
the agent flags that element `announceChange: true`, and `FbwEfbForm`'s `patchEl` requires the flag
beside its last-pressed / still-focused / within-5-s conditions. It is set on exactly the controls
whose label carries their own NEW STATE — the two stepper arrows ("Runway next (now 06R)"), the tile
button ("Passenger 1L: Open"), the state tile's action button and the "…is the default" button the
reader emits in its place — and on nothing else, not even the
load button beside that action. The flag was briefly missing and the gate spoke EVERY post-press
label change on EVERY EFB the shell serves: the PMDG tablet's "Performance (current page)" and the
flyPad's "Baggage (called)", a second reading of a press the screen reader had already spoken. The

### A correction, so nobody repeats it

An earlier pass concluded "the displays cannot be read" from the `wasm_gauge` finding alone. That
was wrong. "No DOM" ⇒ "Coherent scraping won't work"; it does **not** ⇒ "no readable channel".
The evidence pointing the other way was already in hand and got waved past: the wasm calls

A single 500 on a **mistyped host** was treated as evidence of absence. Check the primary source
before declaring a capability impossible — the [Troubleshooting Playbook](troubleshooting-playbook.md)
rule ("most 'broken' verdicts turn out wrong") applies to *whole features*, not just to controls.

## 3. Everything is relative. Nothing accepts "go to position 3".

Knobs expose `WHEEL_UP`/`WHEEL_DOWN`; rotary switches expose `LEFT_BUTTON_DOWN`/
`RIGHT_BUTTON_DOWN` (click the left/right half). MSFSBA's panels are combo boxes, so
`Md11SelectorWalker` closes the loop: read state → step once → re-read → repeat, bounded.

**Step polarity is documented nowhere** — the ModelBehaviorDefs give event ids and nothing about
their sign. Rather than guess across ~200 controls, the walker treats polarity as unknown, assumes
the conventional mapping (left click / wheel up = increase), and judges the first step by the
DIRECTION the state var moved (never by distance: a click that lands twice can overshoot to a spot
no nearer the target). A wrong-way step flips the sign and persists it in
`UserSettings.Md11InvertedStepControls` (`Md11PolarityStore`, wired to the walker's
`LoadPolarity`/`SavePolarity` hooks by the definition), so a control pays for its calibration once,
ever. Measured so far: the seat-belt switch is inverted (RIGHT increases), the autobrake is
conventional. The log line `step polarity calibrated to …` should appear **at most once per control
per install** — more than that means reads were stale, which is the next paragraph.

**A step is read back on delivery, not on a timer (2026-09-06).** A var with its own data
definition is read through `SimConnectManager.ReadFreshAsync`, which completes when SimConnect
delivers it: fire, poll every 80 ms until the position index has changed and the value is settled
(exactly on a point detent, or two consecutive reads agree — ANIM_LAG vars travel for up to a
second), cap 1200 ms, which is the only way to conclude "no movement". Each read's PERIOD.ONCE goes
out under its OWN request id (`FreshReadWaiters`, a range above every data-definition id), and only
that request's answer completes it — or, for a var on its own periodic subscription or in the
continuous batch, the next sample, which is taken after the read registered. A read that timed out or
was cancelled is abandoned: its late answer updates the cache and wakes nobody (`debug.log`:
`Dropped late fresh-read answer for …`), so the next read is never handed a value SimConnect sampled
before it asked. The first version issued the ONCE under the definition id — no identity on the
wire — and left the timed-out waiter registered for the next read to inherit; only
`ReadSettledAsync`'s two-consecutive-reads rule bounded the harm, and not on a point detent, where
one delivery is accepted. One detent lands in about
half a second, two in under a second. The previous protocol slept 150 ms and read the cache until
two reads agreed — 300 ms per read, a second per detent, and stale enough to call real movement
"no movement" and mis-learn polarity (the autobrake flipped twice in one session). A walk also waits
out a 1000 ms settle window after the last click recorded on its node, because a walk cancelled by
fast arrowing can have a click still landing. A first no-movement AT AN END STOP is ambiguous
(inhibited, or the wrong guess with the asked direction being the stop itself), so there the walker
clicks the other event once: toward the target flips the polarity, nothing either way is inhibited.
A HANDLE never gets that probe, at any index (`Md11Kinds.Handle` gives up on its first stall): on a
two-position control every index is an end stop, and a fire handle's walked axis is the agent
discharge.
A stall at mid-range can only be a dropped or refused click — a wrong guess would have moved the
control — and the walker gives up at once rather than probe, because on the engine fire handles the
walked axis is the agent discharge (since round 2 the walker never probes ANY handle, at any index,
and the engine handles are not walked at all — see the fire-handle note in §8). Every walked MD-11
control has its own data definition, so this
protocol covers all of them. The flap lever and
speedbrake stream on their own SIM_FRAME + CHANGED subscription (`ExcludeFromBatch` +
`HighFrequency`, so a stationary lever delivers nothing): for those a fresh read IS the cache, at
most a frame old, which `SimConnectManager.ReadFreshAsync` hands back at once instead of waiting for
a delivery an unchanged value never sends (`FreshReadPolicy`). The old cache-poll protocol and its
single-no-movement give-up survive only for a var that answers with the next 1 Hz delivery at best —
batch-covered, or on its own PERIOD.SECOND subscription; no walked MD-11 control is of that kind
today.

**A walked control owns its var until the walk lands.** `TFDiMD11Definition.ProcessSimVarUpdate`
consumes every delivery of a var whose `DebouncedWalk` is registered, so MainForm's control refresh
cannot re-set the focused combo to each position the walk passes through (NVDA spoke every one of
them: "Takeoff", "Off", "Minimum" after the pilot picked "Minimum"). When the walk ends the
definition force-reads the var once with the gate down — a landed walk re-syncs silently (WinForms
ignores a same-index set), a failed one snaps the combo to the real position beside the
"did not move" message. Same shape as the PMDG 737's transponder walk gate.

**Single-click switches toggle (2026-09-07).** TFDi builds the IRS selectors, the fuel switches and
starters, the parking brake, the gear lever, QNH/QFE, the minimums mode and the transponder mode
switches on `TFDi_Design_MD11_Switch_SingleEvent_Template`: one `LEFT_BUTTON_DOWN` that TOGGLES the
state. Those cannot be stepped, and until now every one of them failed the walk ("no step events")
and reached its position only through the direct-write fallback, about 1.2 s later — your own logs
showed `direct set to 0 → read 0, held=True` for the fuel switches and IRS 1/2. The walker now reads
such a control fresh, clicks once when the position differs, and confirms on delivery
(`ToggleCoreAsync`); a click that changes nothing still hands over to the fallback. The gear lever's
var is the lever's 0–25 travel against a map that says {0 Up, 1 Down}: the nearest-position rule
reads 25 as Down and the read-back settles on two agreeing reads, so the toggle works there too —
the fallback's direct write of 1 into that travel var never could, which is why the gear was driven
through the sim until now, and why `Md11DirectSet.FallbackNeverWrites` now refuses the gear switch
outright (a value written there moves the picture, not the gear). The panel COMBO is keyed on that same {0, 1} map, and MainForm's combo lookup is an
exact key match, so with the gear down (25) the combo opened with no selection and the walk's
gate-down re-sync could never land: `Md11GearLever` classifies the travel onto the map's keys by
TFDi's threshold (Down at >= 20 — the one rule the gear hotkey read-out also uses) through
`SimVarDefinition.ValueToDescriptionKey`, which the combo renderer consults at build and refresh.
A pick still writes the key, so nothing the walker reads changed.
The gear HOTKEY read-out reads the lever fresh every time (`ReadFreshAsync` on `Md11GearLever.Key`
with the walker's `FreshReadTimeoutMs`, spoken on the UI thread): the var is OnRequest, filled only
when the Landing Gear panel opens, so a cache read said "Gear position unavailable" until that panel
had been opened and went stale once the gear was moved with the sim's own key. `Md11GearLever.Describe`
now says "unavailable" only when nothing was delivered.
The click is decided only on a delivered read — if the fresh read times out the walker refuses and
leaves the fallback's absolute write to it — and the click and its no-movement deadline are stamped
at the time the CEVENT bus will actually write it (its queue is paced 60 ms per event, and an
MCDU scratchpad send can queue dozens). Twenty-five controls ride this path today, including the AFS
overrides, the cargo vents, the EVAC horn shutoff, the cargo-door arm switch and the ADG lever,
whose double tap a single click cannot satisfy (it falls to the direct write as before).

The Dial-A-Flap thumbwheel is continuous, not detented, and is NOT walked at all: the wheel spans
~90 raw units at one unit per WHEEL CEVENT, and bursting that many clicks on a channel we are asked
not to overuse jams it at an end stop (proven live). `Md11FlapSystem.SetDialRawAsync` writes the
wheel's own backing L:var (`MD11_DIALAFLAP_WHEEL_RNG`, the OVERRIDE_ANIM_CODE source) once through
`WriteExternal` and the animation follows — one of the three non-CEVENT writes listed at the top of
this document. The analog CEVENT walk that preceded it (`WalkAnalogAsync`, reached only through the
uncalled `SetDialDegreesAsync`) was deleted in review round 2 (2026-09-11), together with the equally
uncalled `SetLeverAsync` (a wrapper of the detented walk for the flap lever): neither had a caller,
and the analog walk's correction burst chose the wrong direction whenever its probe had fired the
decrement event.

## 4. The data-definition budget

SimConnect caps a client at ~1000 data definitions. There are 1361 controls. The split is
deliberate:

| Class | Count | UpdateFrequency | Individual defs |
|---|---|---|---|
| Buttons (momentary) | 497 | `Never` (write-only) | **0** |
| Buttons that latch (own L:var is the position: tooltip-proven, plus the battery measured live) | 163 | `OnRequest` | **163** |
| Annunciators | 488 | `Continuous` + `IsAnnounced` → batch-covered | **0** |
| Switches / knobs / guards / levers / handles | 206 | `OnRequest` | 206 (cap is 900) |

(Plus 7 `MD11_OPT_*` configuration flags, which are not controls and are never registered.)

Only `OnRequest` and `Continuous`-without-`IsAnnounced` consume individual defs — **379** measured
on the shipped map, base and export variables included, plus the calc-path probe target
`MSFSBA_BRIDGE_PROBE` (§1) (cap 900). Flipping annunciators to
non-announced would add **488 individual defs** and blow past the cap — don't. Watch
`registration.log`'s `approxTotalDefs` after any change here.

## 5. The flap system

**The MD-11 has ONE handle for flaps and slats together**, plus a separate Dial-A-Flap thumbwheel
for the take-off angle. Clean → fully extended:

| Detent | `MD11_FLAP_RNG` | Notes |
|---|---|---|
| Flap Up / Slat Retracted | 0 | clean flight |
| Flap 0 / Slat Extended | 20 | slats out, flaps zero — low-speed margin without flap drag |
| **Dial-A-Flap** | **38–65 (range)** | take-off detent; angle comes from the thumbwheel |
| Flap 28 | 70 | mainly the go-around setting |
| Flap 35 | 82 | normal landing — less drag than 50 |
| Flap 50 | 100 | max landing flaps; not required every landing |

From clean, successive extend steps give: `0/EXT → DIAL-A-FLAP → 28 → 35 → 50`.

There is a **physical gate at 28** so the handle cannot slip straight between the take-off range
and the landing range. That is why 28 is a detent in its own right and not a waypoint: a go-around
from 35 or 50 retracts to **28 first**.

**Dial-A-Flap** selects any take-off flap angle from 10° to 25°. TFDi's own tooltip formula:

```
degrees = 10 + MD11_DIALAFLAP_IND_RNG / 6.6667     (raw 0…100 spans 10°…25°)
```

Exposed as a combo of whole degrees, 10–25 — that is how the setting is briefed and read
("dial a flap 15"); the var is continuous but fractional entries would be a combo with hundreds
of meaningless rows to arrow through.

### Invariants

- **The detents are CURATED, not parsed — six positions, not five.** TFDi's tooltip encodes five
  positions as an RPN `%{case}` map and the Dial-A-Flap detent as a **range test**
  (`38 65 (L:MD11_FLAP_RNG) rng`) *outside* the case block. A generic parser sees the cases and
  misses the range, so the lever reads as five positions with the take-off detent — the one the
  thumbwheel exists to serve — missing entirely. They are pinned in the generator's `CURATED`
  table. Regenerating must not lose them.
- **Never resolve the flap detent by nearest value.** Dial-A-Flap spans 38–65 but is represented
  by 50, so nearest-value hands everything from 60 up (the midpoint of 50 and 70) to "Flap 28":
  a handle in the take-off detent with the wheel toward 25° would read out, and be walked from,
  as 28. Use `Md11Detent.Matches` / `Md11SelectorWalker.PositionIndex`, which test the range
  first. Pinned by `Md11SelectorWalkerTests.PositionIndex_DivergesFromNearestValue_InsideTheDialBand`.
- **Every Dial-A-Flap read-out carries its angle — and never an invented one.** Handle position and
  selected angle are two independent facts; "Dial-A-Flap" alone does not tell a pilot what they are
  rotating on. `Md11FlapSystem.DescribePosition` takes the wheel as a `double?`: an unsampled wheel in
  the Dial detent reads "Dial-A-Flap, angle not yet read", because raw 0 is a real 10° and all three
  callers used to pass 0 for a wheel not yet delivered — a phantom "10 degrees" right after connecting.
- **The streamed flap read-out is baseline-first** (`Md11FlapSystem.ReadoutDecision`). Its first
  COMPLETE composed text seeds silently, as the spoiler read-out's does, so switching to the MD-11
  mid-flight no longer announces "Flap 35". A text still waiting for the wheel's first sample
  ("Dial-A-Flap, angle not yet read" — the lever's sample can land first) is neither spoken nor
  recorded as that baseline, or the wheel's sample would then speak the angle on connect: connecting
  with the handle in the Dial detent says nothing. After the baseline every change is spoken — "angle
  not yet read" included, which is then news — and a repeat is not; the context reset deliberately
  leaves it alone.
- **Neither flap combo may be seeded by an exact key — the definition owns the mapping.** Both
  are combos of discrete positions over a var that is not discrete: the thumbwheel's value is
  CONTINUOUS (raw 33.0 for TFDi's shipped 14.95°) against rows keyed by whole degrees, and the
  handle's Dial-A-Flap detent is a BAND (FLAP_RNG 38–65, parked at 46.91) against rows keyed by
  the detent points. MainForm's combo lookup is an exact key match, so both opened with NO
  selection — and in a DropDownList the first Down-arrow selects row 0 and COMMITS it: 10° on the
  wheel, and on the handle "Flap Up / Slat Retracted", a walk that RETRACTS the flaps
  (review F9, 2026-09-09). Which key a delivered value describes is a property of the VARIABLE,
  so both definitions carry a classifier on the `SimVarDefinition.ValueToDescriptionKey` seam
  (§3, the gear lever's): the wheel's is `Md11FlapSystem.NearestDialChoice` (nearest listed
  degree, half away from zero — the rule `ToString("0")` applies in the display row and the flap
  read-out, so the three can never disagree; clamped to 10–25°), the handle's is
  `Md11FlapSystem.LeverDetentKey`, the same `DetentFor` range test the read-out already uses (a
  value in no detent is the handle in transit and stays unclassified, so the combo shows nothing
  rather than a position the handle is not in). That seed is the ONLY seed either combo gets —
  `ProcessSimVarUpdate` consumes both keys (returns true), so `OnSimVarUpdated` returns before its
  Step 4 refresh — and `PanelLoadTimer_Tick` rebuilds the panel on every show, so returning to the
  panel re-snaps it. The Ctrl+P window's copy of the wheel is seeded the same way, from
  `NearestDialAFlapChoice`, under `_populating` and AFTER `Show()` so the assignment lands on a
  live handle with nothing deferred to handle creation — and after focus has been put on the
  Autoflight button, because a screen reader DOES speak a programmatic selection change on the
  control it is sitting on. Pinned by `Md11FlapSystemTests.NearestSelectableDegrees_*`,
  `NearestDialChoice_IsAListedKeyWhoseLabelMatchesTheDisplayRow`,
  `BothFlapCombos_ClassifyTheirValueOntoAListedKey` and
  `Md11ReadoutTests.OnlyMismatchedKeySpaces_ClassifyTheirValue`.
- **A failed walk must SPEAK.** Success is silent (the screen reader already announced the combo
  selection — the global `_uiSetEcho` rule), but a walk that does not reach its target says so.
  On an aircraft with no readable gauge, a silently-failed selection is indistinguishable from a
  successful one. A walk that THROWS speaks the same failure sentence (`SafeWalk`, through
  `OnUiThread`) unless the definition has been disposed or the walk was cancelled — it used to log
  and say nothing. The Dial-A-Flap set follows the same rule: a set that LANDED is silent (the
  combo already spoke it) and anything else speaks both numbers — "Dial-A-Flap 17 degrees, could not
  reach 20" — through `OnUiThread`. Landing means EXACTLY, not "within a degree": the set is one
  direct write that round-trips, so the ±1° band the CEVENT walk needed could only hide a real
  1° miss — the combo showing 25 over a wheel on 24, with the display row reading 24 and nothing
  said. It used to announce success as well, from a pool thread after four
  `ConfigureAwait(false)` awaits, where `ScreenReaderAnnouncer` can drop speech without a trace.

## 6. The control map

The 1361 controls are **generated, not hand-written**:

```bash
python tools/md11-gen/generate_md11_map.py          # finds the install itself → md11_control_map.json
cp tools/md11-gen/md11_control_map.json MSFSBlindAssist/Resources/
```

The generator finds the MD-11 itself — FS2020 and FS2024, Microsoft Store and Steam,
and custom/external package folders (including a packages root whose add-on folder is
not literally named `Community`; the owner's FS2024 install keeps it in `Community2024`).
It identifies the package by looking for `ModelBehaviorDefs/TFDi_Design/MD11` inside a
folder rather than by the folder's name, so a TFDi package rename does not break it.

- Installed in two sims? It lists both and asks which to use (pass `--pkg` to skip the
  question, or when running unattended).
- Can't find the aircraft, or finds it without `md11host.wasm`? It **stops and writes
  nothing**. It must never emit a map with no wasm-derived L:vars — those are the PFD
  speed-tape and V-speed read-outs, which have no other source.
- `--pkg` / `--wasm` still override discovery entirely — but a `--wasm` path that does not
  exist is rejected the same way, rather than silently producing that same incomplete map.

The `md11host.wasm` location differs between installs (`common/panel/` on FS2024,
`panel/` on FS2020), so it is searched for, never assumed.

It reads the aircraft's own `ModelBehaviorDefs` + `md11host.wasm`. Every label, detent name and
switch position is **TFDi's own tooltip wording**, so the screen reader says what the real cockpit
says. After a TFDi update, regenerate — don't patch C#. A guard cover's `state_var` is always its
own node id, whatever its tooltip reads (`finalize_controls`; see "A guard reads its own cover,
never the control under it" below).

**Review every regeneration by node id before the copy above.** The map is ~31,000 lines and a
reorder moves whole controls, so a text diff cannot be reviewed. `tools/md11-gen/diff_maps.py <old
map.json> <new map.json>` (stdlib, tested beside the generator) prints what the review needs: every
node added or removed, every changed field of a node both maps carry, order-only differences on
lines of their own, and the top-level keys entry by entry; it exits 1 when anything was added,
removed or changed. Every line it prints must be explained by a generator rule the change set out to
make. A position lost or gained on an OPERABLE control, a changed `state_var`, a node added or
removed, or a line no rule explains STOPS the regeneration: nothing is copied or committed until the
owner has seen it (a changed TFDi package shows up exactly there). The JSON itself is never
hand-edited.

The JSON is an **`EmbeddedResource`**, deliberately not the repo's usual `None Update` +
CopyToOutputDirectory: the MD-11 has *zero* controls without it, so a file that can go missing
from the output folder is not an acceptable failure mode (unlike `Resources\*.js`, where a missing
agent degrades to one broken feature).

Panels come from a CURATED layout table, `Aircraft/MD11/Md11PanelLayout.cs` (sections in the
order a preparation flows, panels named as TFDi's Systems Guide names them, controls in the
physical order the guide numbers, a guard cover immediately before the control it covers, a
panel's standalone lamps as its Status Display rows). It is the only source of panel order; a
control it does not name is appended to a "{Area} (other)" panel, never dropped, and
`Md11PanelLayoutTests` pins that the shipped map needs no such panel. The earlier alphabetical
grouping by node-id token is gone.

Lamps are never tab stops: `Md11Placement.Displays` carries each panel's lamps in table order and
the definition publishes them through `GetPanelDisplayVariables()`, so MainForm renders one
read-only list per panel (Ctrl+3, F5, live refresh) — the Airbus pattern, and on this aircraft the
lights ARE the instrument panel. The five Read-outs panels, the COM read-backs and the squawk
code are rows of the same kind; `Md11StatusRow` decides every row's words (a lamp's composed
state, "not set" for an unentered V-speed, both units for an altimeter). The MCDU keys and
brightness knobs are not rows anywhere: the MCDU window presses them (`Md11PanelLayout.IsMcduControl`).

Lamps that belong to a button are folded into that button's spoken state (§9); standalone lights
(the 13 bus OFF lights, hydraulic SYS PRESS, cargo HEAT/SMOKE, gear lights…) are Status Display
rows of their panel (never tab stops) AND announce on change under the same name.

### Generator gotcha: the export scan is prefix-based

`EXPORT_PREFIXES` missed 11 documented exports on the first pass — `MD11_V1`/`VR`/`V2`/`VSR`/`VFR`
are single tokens with no shared prefix (and a bare `MD11_V` prefix would drag in every
`MD11_VLV_*`/`MD11_VOR_*` control), and `MD11_ATS_`/`MD11_CAP_`/`MD11_FO_` simply weren't listed.
Those are exactly the blind-pilot read-outs — the V-speeds have **no other source**, there is no
speed tape to read. `EXPORT_EXACT` now carries the no-prefix ones. Cross-check any new export
against the docs' Variables page, not just the wasm scan.

### Generator rules added in review round 2 (2026-09-11)

- **A composite (D10).** A tooltip whose outer `%{case}` reads ANOTHER var and hands one of its
  positions to a nested `%{case}` on the control's OWN var — the three engine fire handles: the pull
  (`…FIRE_SW`), then the rotation — is emitted with a `composite` block (`outer_var`, `outer_words`,
  `delegate`, `inner_var`, `inner_words`) and an EMPTY `value_map`, so nothing can walk it. The
  definition registers the inner var under `<node>__INNER`, composes the row's words from both vars
  (`Md11CompositeState`) and keeps the row read-only. The block appears on a composite only: the APU
  handle, whose tooltip reads its own rotation var, stays a plain combo, and a nested case on a THIRD
  var stops the generator (the next rule).
- **An outer `%{if}` composite (D13), and the refusal.** The same rule behind an if/else: an outer
  `%{if}` on ANOTHER var whose TRUE branch is, whole, a `%{case}` on the control's OWN var and whose
  ELSE is a plain word is a composite with two outer positions — 0 the else word, 1 (the
  `delegate`) handing over to the case. The Elevator Feel knob (`MD11_OVHD_FLTCTL_ELEVFEEL_KB`) is
  the only such tooltip in TFDi's package: "Auto" while its MANUAL latch (`…_ELEVFEEL_BT`) is off,
  the knob's own five reference-speed words once it is on. It had shipped with the latch as its state
  var and the KNOB's words as its positions, so an aircraft in Auto read "Decrease Reference Speed
  Fast", a walk turned the knob's wheel while it read the latch and could never land, and the
  direct-write fallback then wrote the latch. Both rules read an inline if/else inside the block by
  its resting word first — its own `%{end}` once cut the nested case short — and a single-var outer
  `%{case}` or `%{if}` that nests a case on another var the rules cannot split (a third var, a true
  branch holding more than the case, an else that is not a plain word) stops the generator with the
  file and the node named, instead of emitting a flat map that puts one var's words on another; a
  variant flag still yields nothing, and the Spoilers and Flaps levers, whose case sits under a
  computed condition, are read as before.
- **`%%` in if/else words used as a latch (D11).** The two oxygen flow regulators
  (`MD11_LSIDE_OXY_FLOW_SW`, `MD11_RSIDE_OXY_FLOW_SW`) write their state as
  `%{if}100%%%{else}Normal%{end}`, a trailing if/else. The `%%` → `%` rule covered case labels only,
  so those words never came out and the regulators shipped with no latch and no spoken state. The rule
  now covers if/else words used as latch words, and a press confirms the regulator's state in its own
  tooltip's words ("100%" / "Normal").
- **`<UseTemplate Name = "…">` with spaces around `=` (D12).** Lighting.xml writes 58 blocks that way,
  and the parser matched none of them. All 58 are skipped templates (48 `MD11_IntegralLighting_Template`,
  10 `MD11_PA_Lights_Template`), so no control changed — but a CONTROL written that way would have
  vanished without a word. The parser tolerates the whitespace now.
- **XML comments are stripped before the parse (D14).** `read_xml` now removes every `<!-- … -->`,
  so only LIVE blocks are read. The package holds **444** `<UseTemplate>` blocks inside comments;
  48 are skipped templates and 388 have a live twin — but in **236** of those the commented copy
  sorts earlier in the walk (`FlightDeck/Lighting.xml` before `Overhead.xml` /
  `RObserverAudio.xml` / `MiscOptions.xml`) and was therefore the copy `seen` kept, the live block
  being counted as a duplicate. The map read correctly only because the two copies were identical.
  A TFDi update that edits one of those live blocks and leaves the old copy commented out would
  have been read from the comment and `diff_maps` would have printed **nothing** — the STOP rule
  blind for 17 % of the map, which is the entire safeguard for every future regeneration. The
  strip also settles the D6 nesting check by construction: a `<UseTemplate` inside a comment inside

  on the map is ~230 corrected `source` fields (the field a human reads when a regeneration line
  needs explaining) and the legend order of 9 buttons' stem-matched lamps, which had been decided

- **The eight gear lights are curated back, by decision (D15).** `MD11_MIP_{NOSE,LEFT,CTR,RIGHT}_{RED,GREEN}_LT`

### Switch actuation flood — root-caused from the user's logs (2026-07-17)

The first in-sim switch test failed: detented controls (autobrake the worst) reported *"did not
move. It may be guarded, unpowered, or inhibited."* `debug.log` showed the cause — NOT the CEVENT
channel, but a **SimConnect send-queue flood**. Arrowing through a combo fires a SET for every
intermediate entry, and the generic detented-walk path ran ONE `WalkAsync` per intermediate value.
Several walks then ran at once on the SAME control, each `RequestVariable(forceUpdate:true)` every
~150 ms, until SimConnect choked and threw `0xC00000B0` on **both** reads and the MobiFlight write.
Reads returned null → the walk logged `state var … unreadable — aborting walk` → "did not move."
Autobrake (5-position) spawned the most concurrent walks (176 `0xC00000B0` reads) and never once
read successfully; GPWS (36×) was intermittent and only ever moved via the direct-L:var-write
fallback.

Fix: the generic detented path now debounces + single-flights per control and cancels superseded
walks, exactly as the Dial-A-Flap path already did (`DebouncedWalk` in `TFDiMD11Definition.Interaction.cs`;
`WalkAsync`/`ReadAsync` take a `CancellationToken`). One walk to the final selection, no flood.
**Still needs the in-sim retest** to confirm reads stop erroring and the switch reaches the detent.

### V/S engage (2026-07-18) — needs in-sim confirmation

The reporter found V/S "doesn't engage" and noted there was no button to activate V/S mode. There
isn't one on the aircraft either: the MD-11's ONLY V/S controls are the **V/S / FPA wheel**
(`MD11_CGS_VS_KB`, WHEEL_UP/DOWN — no push/pull) and the VS/FPA display toggle. Rotating that wheel
is what engages the pitch mode; a bare `MD11_EXTCTL_FCP_VR` write only fills the window, and a value
can sit in a window the FCC is not flying. Fix:

- The wheel is now exposed directly — as an "Up/Down" row in the Ctrl+P **FCP window**
  ("Vertical speed wheel") and as "Wheel up/down" actions in the **Ctrl+V dialog**. One CEVENT step
  per click (`TFDiMD11Definition.FireControlEvent` fires a SINGLE event, unlike the DOWN/UP-pair
  `PressControlEvents`).
- **A knob or wheel action that cannot be DELIVERED is spoken, in one sentence, from every surface**
  (2026-09-12). Both methods now answer false when the transport cannot send
  (`SimConnectManager.CalcWriteCanLand`, the MCDU keys' gate), and every caller says so
  through `Md11Fcp.Unavailable` over the knob names on `Md11Fcp` — "Heading push unavailable",
  "Vertical speed wheel up unavailable". The Ctrl+P window and the panel's STD rows already

  and the eight Ctrl+H/S/A/V dialog toggles discarded it and spoke nothing at all. A typed Ctrl+V

  would otherwise sit in a window the FCC is not flying. `Connected()` does not cover this: it

  bridge probe to see it — `CanExecuteCalculatorCode` is TRUE there, because `mobiFlightWasm` is

| Dial-A-Flap wheel write | **no** — the write always "succeeds"; the read-back returns silently | "Dial-A-Flap unavailable" |
| Panel combos/buttons, walks, direct-set fallback, held test buttons (`SetControl`) | partly — a walk said "did not move. It may be guarded, unpowered, or inhibited" (wrong cause, after ~1.5 s); a plain press and a held test button said nothing | refused by label, before the walk starts |
| Typed minimums | **worse than silent** — spoke "… baro minimums set to N feet, the display did not report back", claiming a set that never left | refused by side name |
| Typed squawk | **worse than silent** — spoke "Squawk 1200 entered, …" | refused; no digits pressed |
| COM standby tune / transfer | **no** — `VerifyComAsync` speaks only a delivered mismatch | refused ("COM 1 standby unavailable") |

Two predicates, and each caller asks the one matching its own transport: `CalcWriteCanLand` for the
CEVENT/calc bus, `CanSendEvent` for a stock SimConnect event (COM tuning needs no MobiFlight module
— conflating them would refuse tuning that would have worked). **Never the bare
`CanExecuteCalculatorCode`**: that is what `ExecuteCalculatorCode` guards itself with, and it is
TRUE with no WASM module installed, which is exactly when calc writes vanish. `CalcWriteCanLand`
adds the bridge probe — the only end-to-end evidence — refusing once the probe has CONCLUDED
unverified and staying permissive while it is pending, so nothing is refused that would have
worked. The probe term must never move into `ExecuteCalculatorCode` itself: the FBW catch-alls
write through the calculator unconditionally by design.

Every refusal happens BEFORE the write, so nothing schedules a read-back for a write that never
happened. `SetControl`'s gate is deliberately the LAST of its refusals, so a read-only export or a
composite still gives its own, more useful reason — and it is judged per BRANCH, not per commit:
the one-shot kinds per press, the walked kinds after their debounce, so arrowing a combo during an
outage speaks one refusal rather than one per row passed. The dialog toggles suppress
`ValueInputForm`'s own post-press announce when the press refused (`SuppressStateAnnounce`): that
announce interrupts 1.2 s later and was truncating the refusal.
- The Ctrl+V **typed value now auto-engages**: `SetVerticalSpeedEngaged` nudges the wheel once to
  engage, then writes the exact value AFTER the nudge lands (the wheel rides the paced CEVENT queue,

## 9. Control state, layout and names (2026-09-05)

### The state channel is heterogeneous — measured, not assumed

Every button used to be write-only, so "Battery" never became "Battery: On". Probed live on a
cold-and-dark MD-11F (`{seq} 0 * {id} (>L:CEVENT)` writes, exactly what `Md11EventBus` sends):

| Control | What holds its state |
|---|---|
| Battery (`90150`/`90151`) | its own L:var latches (0→1, stays 1) AND `BATT_OFF_LT` |
| External power (`90142`/`90143`) | `EXT_PWR_AVAIL_LT` / `EXT_PWR_ON_LT` only — the button var stays 0 |
| Engine anti-ice, APU bleed, the system-mode selectors, source selects, breakers | the own L:var — TFDi's own tooltips read it (`%((L:MD11_OVHD_AICE_ENG1_BT))%{if}On%{else}Off`) |
| Navigation lights | `LTS_NAV_LT` (the OFF legend); the button var went to 1 on the first press and never moved again |

So `Md11ControlState.Compose` speaks, in order: lit legends → the proven latch → "unpowered" →
the dark meaning. **Dark is not normal.** Cold and dark every lamp reads 0, `BATT_OFF_LT` and
`GEN1_OFF_LT` included; only `EXT_PWR_AVAIL_LT` (cart-powered) read 1.

#### The power gate is two vars, not the voltage

The stock `ELECTRICAL MAIN BUS VOLTAGE` (registered as `MD11_DC_BUS_VOLTAGE`, silent) says only
that *something* is on, and on its own it is not enough. Measured on the same aircraft, battery
only:

| Var | Cold | Battery only | External power |
|---|---|---|---|
| `ELECTRICAL MAIN BUS VOLTAGE` | 0 V | 24 V | 24 V |
| `MD11_OVHD_ELEC_DC1_BUS_OFF_LT` | 0 | **1 (lit)** | 0 |
| `MD11_OVHD_ELEC_AC1_OFF_LT` | 0 | 1 (lit) | — |
| `MD11_OVHD_FUEL_TANK_1_PUMP_OFF_LT` | 0 | **0** | **1 (lit)** |
| `MD11_OVHD_HYD_EDP_1_L_OFF_LT`, `MD11_OVHD_ELEC_GEN1_OFF_LT` | 0 | 0 | — |

On the battery alone the DC busses that feed the systems annunciators are dead, so the pump, EDP
and generator OFF lamps read 0 *because nothing is lighting them* — not because those systems are
on. A volts-only gate composed **"Tank 1 Fuel Pumps: On" for a pump that was off**, and the same
for packs, bleeds, ties and every other OFF-legend button on DC busses 1–3. External power on
inverts it (DC1 OFF dark, pump lamp lit); external power off with the battery still on puts it
back (bus still 24 V, DC1 OFF lit again, pump lamp dark).

No stock var separates the two states — `ELECTRICAL GENALT BUS VOLTAGE:1` reads 0 on external
power too — so the gate uses the lamp the aircraft itself lights:

> **powered ⇔ `MD11_DC_BUS_VOLTAGE` ≥ 20 V AND `MD11_OVHD_ELEC_DC1_BUS_OFF_LT` dark.**

Cold: 0 V, unpowered. Battery only: DC1 OFF lit, unpowered — lamp-only rows say "unpowered", while
the battery row still says "On" from its latch, external power still says "Available" from its lit
lamp, and the bus OFF lights still say "Off". External, APU or generator power: DC1 OFF dark,
powered. A DC1 value that has not been delivered yet counts as unpowered. (A recorded deviation
from the design spec's §3.4, which fixed the gate at the voltage alone.) Both keys are in every
state-bearing row's `StateVariables`, so a change in either relabels the visible panel. The voltage
counts as changed only past its definition's 0.5 V `ChangeTolerance` (the gate needs only the 20 V
line; with the shared 0.001, every ripple of the bus re-composed every stateful row of the open
panel, ~32 on Electrical, once a second), and MainForm composes a state only for a control that can
show one — a Button or a read-only TextBox (`MainForm.ShowsDescribedState`).

The map's `state` block (generated: `apply_state` in the generator) carries per control the
lamps (var, printed legend, spoken word when lit), the latch (var, on/off words — polarity is
TFDi's: windshield defog `1` = "Off") and the dark meaning. Latching buttons are `OnRequest`
(read on panel open and force-read after a press); every other button stays `Never`.

### Announcements

A lamp change speaks its OWNER's composed state ("External Power: On"), deduplicated on text,
baseline-first, blink-guarded; a standalone light speaks "AC Bus 1: Off" and is a Status Display
row of its panel reading the same words.

**A lamp going DARK never speaks on the spot.** If the aircraft is already unpowered it is silent
outright — that is the panel losing power, not a system changing. Otherwise it is deferred
`DarkSettleMs` (1500 ms) and re-decided from what is true *then*
(`Md11AnnouncementGate.SpeakDarkTransition`): unpowered by then drops it, else the state is
re-composed and goes through the normal text dedup. Both halves are needed because the 528
batch-covered variables (488 of them lamps) ride two SimConnect batches sorted by name — `MD11_OVHD_ELEC_DC1_BUS_OFF_LT`, the
lamp the gate reads, is in batch 1 while the `MD11_OVHD_HYD_*` and `MD11_OVHD_PNEU_*` lamps are in
batch 2 — so in the normal shutdown order (external power off, battery still on) a batch-2 lamp
can go dark a beat before the gate learns the DC busses died, and the immediate guard alone would
still have announced "Tank 1 Fuel Pumps: On", "Pack 1: On", … one sentence per control. Re-composing
also means a control with several legends reports what it reads now rather than which lamp moved.
LIT transitions are untouched and speak at once: a light coming on is news. A deferral scheduled
before an aircraft switch or a reconnect is dropped (`ResetAnnouncementBaselines` bumps a
generation counter).

After a press the definition waits ~1.2 s for the lamps and latch, then speaks the resulting state once — always,
so an inert press (generator with engines off, tank pumps under automatic fuel control) reads
back the unchanged state. The lamps that press lights are swallowed until that feedback speaks,
and at most 2.5 s (`Md11AnnouncementGate`) — the feedback IS the confirmation, so once it has been
heard a lamp carrying a DIFFERENT text is the correction and must be spoken. (A guarded press
spends 550 ms lifting its cover before the button is written, so its lamp routinely lands after
the feedback has already read the stale state; with the window still open that correction was
swallowed and never spoken again.) Every lamp update is consumed in `ProcessSimVarUpdate`; Ctrl+M mutes
through MainForm's `Suppressed` wrap, rows named "External Power AVAIL light" / "AC Bus 1" — and
the deferred dark tail (`DeferDarkTransitionAsync`) re-checks the mute by the lamp's key itself,
because it speaks from a timer 1.5 s later, outside that wrap (it did not until 2026-09-07, so a
muted lamp still spoke its dark edge). The
Ctrl+M dialog itself is `MonitorManagerFormBase` like every other aircraft's (`Md11MonitorManagerForm`
supplies only the title, `MonitorRowBuilder.Build` rows and the `Md11DisabledMonitorVariables`
list), so it has the search box and the Show filter — it began as a hand-rolled form without either,
which over ~530 rows meant a lamp could not be found at all; the MD-11 is in
`ComboLabelCollapseTests.AllAircraft`, so `MonitorRowLabelUniquenessTests` now pins its rows too. The
form is disposed and nulled on an aircraft switch, as its five siblings are, and at app exit too,
beside the MD-11's other windows (the siblings are not disposed at exit; they close with the
application) — it was neither — so the next Ctrl+M builds it from the live definition. Press
feedback is composed and spoken on the UI thread (the definition posts it to the captured
`SynchronizationContext`), because the gate's dictionaries and the announcer are UI-thread objects.

### Radios (2026-09-06)

TFDi's radio panel drives the simulator's OWN COM radios: `(A:COM ACTIVE FREQUENCY:1, MHz)` read
135.500 through the calculator path on a live aircraft, all three COMs carrying real airband
frequencies and `COM AVAILABLE:1..2`/`NAV AVAILABLE:1` all true. So the stock `COM ACTIVE
FREQUENCY:n` / `COM STANDBY FREQUENCY:n` variables are the frequency here — the RCP display
itself is a WASM gauge like everything else, and no `MD11_*` variable carries a frequency.
`Md11Radios` registers the six as batch-covered stock SimVars (kHz), `Md11ComAnnouncer` speaks a
change baseline-first and airband-gated ("COM 1 active 135.500"; standby too, so a tuner click
and an XFER both read back — and an out-of-band value, a power loss's 0, is neither spoken nor
stored as the baseline, on the live path and on the flight-load seed path alike, so the power's
return is not announced as six tunes), and they sit in the Read-outs → Radios panel and in Ctrl+M.

**Tuning.** The aircraft honours the stock tuning EVENTS as well (probed live 2026-09-06 on
COM3: `COM3_STBY_RADIO_SET_HZ` 124900000 set the standby and it held for 40 s; `COM3_RADIO_SWAP`
swapped it into the active slot; both reversed afterwards). So the Radios panel — moved from the
read-outs to the head of the Pedestal, because it is now operable — carries per radio a typed
standby (`COM_STANDBY_FREQUENCY_SET:n`, MainForm's `_SET` text box, MHz in, validated 118.000 to
136.975, sent as exact Hz through `COM_STBY_RADIO_SET_HZ` / `COMn_STBY_RADIO_SET_HZ`) and a
Transfer button (`COMn_RADIO_SWAP`). Those six rows go at the HEAD of the panel, AHEAD of the 24
hardware rows `Md11PanelLayout` places there (the captain's, first officer's and observer's radio
control panels: VHF 1-3, HF 1-2, the two tuners and the transfer) — they once REPLACED that list, so
none of the 24 appeared on any panel. `HandleUIVariableSet` claims both keys so the generic
MainForm handler never double-announces; the COM announcer speaks the frequency that then
changes, and `VerifyComAsync` speaks only a MISMATCH after 1.5 s ("COM 1 standby did not change,
still 121.500"). What is NOT verifiable from outside: whether TFDi's own RCP display follows a
stock event — the sim's radio state is what the ATC clients read, and a later knob turn on the
aircraft's own panel would re-assert the RCP's idea through the announcements.

**Squawk.** `TRANSPONDER CODE:1` (BCO16, 0x5473 = 5473 read live) is driven too, so the
Transponder panel carries a typed field (`Md11Squawk.SetKey`, MainForm's `_SET` text-box
convention) in place of the eight keypad buttons: `SetSquawkAsync` presses the aircraft's own
digit keys in order over the paced CEVENT bus, waits a second for the fourth digit to commit,
force-reads the stock code and speaks what the transponder actually shows ("Squawk 1200." /
"Squawk entry did not take, the transponder reads 5473."). An empty box arrives as 0 and is
refused rather than sent as 0000. The keypad buttons stay registered (the entry presses them);
`Md11PanelLayout.SupersededByEntryField` keeps them out of the safety net that would otherwise
append every unlisted control. Whether TFDi's keypad commits on the fourth digit without a CLR
first is the one thing not yet confirmed on the ground — the read-back is what makes a wrong
guess audible rather than silent. The code is ALSO announced on change, whichever way it was set
(`Md11SquawkAnnouncer`: baseline-first, unchanged redeliveries silent, and every delivery during a
typed entry tracked but not spoken — the entry's own confirmation is the sentence, and the
transponder may show intermediate codes as the digits land). `MD11_SQUAWK` therefore rides the
continuous batch like the A380's `XPNDR_CODE` and has a Ctrl+M row, "Squawk code"; the entry's
read-back goes through `ReadFreshAsync` (completes on the next 1 Hz delivery, 2.5 s ceiling)
because a fixed sleep read a successful entry back as "did not take" whenever the batch landed
late. Entries are counted and run one after another (`_squawkEntries`), so two Sets inside one
window keep the silence until the last ends and each gets its own read-back, never interleaved
digits. Enter in any `_SET` field presses its Set button (the shared builder in
`MainForm.PanelBuilder.cs`, since 2026-09-07 — the guides had promised it while a bare TextBox
swallowed Enter).
W in output mode reads the gross weight in pounds (`ReadWaypointInfo` is the key's registered
action and every definition repurposes it so; the MD-11 had no case and W said nothing).

⚠ A trap recorded so nobody re-derives "the MD-11 has no radios": the probing tool's plain
data-definition read (`msfs_get_simvar`) returned **0** for every `COM …:n` and `NAV …:1` variable
on this aircraft while the calculator read (`(A:COM ACTIVE FREQUENCY:1, MHz)`) returned the real
value in the same minute. On this aircraft a zero from a tool proves nothing — the calculator path
is the second opinion.

### Speedbrake (2026-09-06)

TFDi's lever tooltip composes THREE variables — `MD11_SPDBRK_RNG` (travel: 0 / 17.5 / 25 / 32.5),
`MD11_SPDBRK_HANDLE` (the pull: 0 down, 1 = ground spoilers ARMED with the lever retracted, 2 =
auto-extended on landing) and a latch animation — and the lever template gates the wheel events
on the pull being down while the single click toggles the pull. The generated map had hung the
travel detents on the HANDLE var, so the Spoilers combo could neither read a detent nor reach one
(the walk read a var that never moved) and knew nothing of "armed". `Md11SpeedbrakeSystem` owns
the model now: the Spoilers row reads the TRAVEL var, streamed like the flap lever, and a second
row of the app's own, Ground spoilers, reads the pull; arming fires the lever's click after the
refusals the aircraft would otherwise enforce silently (lever not retracted, "Extended" chosen).
The Spoilers combo classifies the streamed travel onto the detent the read-out names
(`Md11SpeedbrakeSystem.TravelDescriptionKey`, the same tolerance) through `ValueToDescriptionKey`,
so it opens on the lever's detent — 26.4 reads "2/3 extended" — where it used to open unselected
on every value and let the first Down-arrow commit "Retracted". Between detents it still classifies
to nothing, and unlike the flap handle (between detents only in transit) the speedbrake lever can
REST there: the panel then opens the combo with no selection and its first Down-arrow still commits
"Retracted" — an accepted residual. Whenever the pull is up a Spoilers pick is refused, in words naming the state — armed (1):
every extension; auto-extended on landing (2): every position but Retracted, "The ground spoilers
are extended; select Retracted to stow them." — where it used to fall through to a generic "did not
move". The pick is judged ONCE, on the final selection after the debounce, so arrowing through the
rows says it once (a pause of more than 300 ms on a row counts as a selection). The combo keeps a
refused pick: like the flap handle's and the thumbwheel's, it never follows the lever once the panel
is built (`ProcessSimVarUpdate` consumes the travel before MainForm's combo re-sync), so the Spoilers
read-out row is what tells the truth — at pull 2 the combo can still show Retracted, and stowing then
means arrowing off it and back. Retracted stays allowed at
2 because it is the stow; whether the wheel really stows the lever there is unmeasured — the lever
template gates the wheel on the pull being down (above) — so land with the spoilers armed, then
pick Retracted: a "did not move" means the stow is the lever's click.
Probed live: the click took the pull 0 → 1 → 0 with the lever retracted; the stock `SPOILERS
ARMED` / `SPOILERS HANDLE POSITION` stay 0 throughout (not driven).

### Read-backs complete on delivery (2026-09-09)

Every spoken read-back verdict — the ground spoiler pull after the lever's click, the COM
standby-set and transfer, the typed minimums, the direct-write "held" check, the press feedback's
latch, the guard's open/closed decision and Ctrl+B's three altimeters — reads through
`SimConnectManager.ReadFreshAsync` (which completes on the DELIVERY: the `PERIOD.ONCE` of an
individual-def var, the next 1 Hz batch of a batch-covered one, the cache for the SIM_FRAME-streamed
flap wheel) instead of sleeping a fixed time and then reading the cache. That sleep was the defect:
a forced read of a batch-covered key is honoured only by the NEXT 1 Hz delivery, so whenever the
last delivery before the sleep expired had been sampled before the aircraft applied the click, the
cache still held the pre-click value — and "Ground spoilers did not arm." was spoken over a click
the aircraft had taken. Because MainForm's combo-echo wrap suppresses the pull var's own
announcement for 3 s after the pick, that false failure was normally the ONLY thing the pilot heard.

A read-back that follows a click QUEUED on the CEVENT bus also waits from the click's expected
WRITE — `Md11EventBus.ReadBackDelayMs` = settle + `Pending × MinGapMs`, the stamp the walker and
`PressAndHoldAsync` already carry. That is the general rule rather than the fix: on today's paths
the backlog is at most a couple of events (the walker queues one click per step; the MCDU
scratchpad send is the one real burst), so with an idle queue it costs the pilot nothing.

A verdict is spoken only on a DELIVERED value (`Md11SpeedbrakeSystem.ArmReadBack`,
`Md11Radios.TuneReadBack`; the minimums and altimeter sentences already treat an undelivered
export as "did not report back" / no evidence): nothing delivered inside the ceiling means nothing
spoken and a `debug.log` line. Ceilings are per var class — 2500 ms for a batch-covered key
(`BatchReadBackTimeoutMs`), the walker's 1200 for an individual-def key, and 300
(`GuardReadTimeoutMs`) for the guard's two reads and the press feedback's latch, because those sit
on an actuation's path AND the guarded press's whole chain has to speak inside
`Md11AnnouncementGate.EchoWindowMs` (2500 ms) or the press's own lamp echo is spoken as well
(idle queue: 300 + 250 + 1200 + 300 = 2050 ms; pinned by `Md11AnnouncementGateTests`). A guard read
that times out actuates UNGATED — the same outcome an unreadable state always had — so a covered
fire handle may then report "did not move"; retry the pick.

That chain absorbs the bus backlog TWICE — once in `EnsureGuardOpenAsync`'s cover settle, again in
the feedback's own lamp settle — and each term is `Pending × MinGapMs`, bounded only by the queue
(256 ids ⇒ 15 s), so no fixed sum can budget for it: a guarded press queued behind an MCDU
scratchpad send (~24 CEVENTs, 1.4 s) would speak 4930 ms after the press with the window long
closed, and the pilot would hear the sentence twice — something the pre-2026-09-09 fixed 1700 ms
wait could not produce. The constraint is a DEADLINE, so the feedback's own wait is what gives:
`TFDiMD11Definition.FeedbackDelayMs` takes the smaller of the settle-from-the-write and whatever
the window has left (`Md11AnnouncementGate.RemainingFeedbackBudgetMs`, minus a
`FeedbackReserveMs` = 400 ms allowance for the latch read that follows). With an idle queue nothing
is truncated and the full 1200 ms settle is honoured; behind a burst the feedback reads early, which
is the SAFE direction — it may then compose the pre-press state, and a lamp landing later with a
different text is the correction, which is exactly what `Feedback` closing the window allows. The
guard's own settle is never clamped: that one paces two writes at the AIRCRAFT, and shortening it is
how a covered control fails to actuate at all.

The settles that remain are the AIRCRAFT's apply/animation time and were kept, not cut, where
unmeasured: `ArmSettleMs` 700, `ComTuneSettleMs` 1500, the direct set's 600 ms ANIM_LAG,
`GuardOpenSettleMs` 250 (now measured from the click's write), and ONE EXTCTL-inbox allowance,
`Md11Fcp.VerifyAfterMs` = 1200, shared by the minimums and the altimeters (the altimeters' old 2500
was batch-phase padding). The `Minimums read-back:` / `Altimeter read-back:` / `Ground spoiler
read-back:` lines in `debug.log` carry the elapsed time, so the FCC cycle can finally be measured
before anything is cut. The guard's log-only re-read is fire-and-forget (`LogGuardAfterAsync`) — the
fire-handle walk and the guarded press never wait on it — and the press feedback's clock starts
when the press is actually QUEUED (`GuardedPressAsync` returns the backlog at its `Press`); only the
hold-to-test path still estimates its guard chain (`GuardedPressExtraMs`), because its feedback must
speak at the settle rather than after the 3 s hold.

**Fresh reads from pool threads (2026-09-11).** Every walk and read-back above reaches
`ReadFreshAsync` from a thread-pool thread (`ConfigureAwait(false)` chains), while the core
`RequestVariable` reads `continuousVariableIndexMap` and issues `RequestDataOnSimObject` — UI-thread
work. `SimConnectManager` captures the UI thread's WinForms `SynchronizationContext` and thread id at
construction (`UiThreadGate`; the manager is built with `MainForm` on the UI thread), and
`RequestVariable` called from any other thread posts itself there and re-checks the connection when
it runs; a post refused at shutdown is dropped, never run inline. `FreshReadWaiters.WaitAsync`
registers the waiter before the request is issued, so a posted request loses nothing, and
`continuousVariableIndexMap` is a `ConcurrentDictionary`. A pool thread's fresh read now spends that one
UI-thread hop inside its own ceiling — normally one message-loop turn, but it counts against the
tightest of them, the guard's 300 ms `GuardReadTimeoutMs`, and a guard read that times out actuates
ungated, exactly as an unreadable state always did. **Not fixed, recorded:** the CEVENT pump's
calculator writes stay on the pump thread. `SendMFCommand` is a pure send with no shared state (a
local struct into `SetClientData`) — the same shape as the A380's `Task.Run` calc write — so it is
carried to the cross-aircraft follow-up rather than moved here.

### The altimeter read-out (2026-09-06)

`MD11_CAP_ALTIMETER` carries whichever unit the PFD shows (29.92 or ~1013 — TFDi's tooltip
switches on `> 500`), the stock `KOHLSMAN SETTING HG/MB:1` follow it on both sides, and the STD
flag is on the WASM PFD: `KOHLSMAN SETTING STD:1` read 0 at FL360. So B speaks both units in the
PMDG order — "Altimeter: 1013, 29.92" — and "Altimeter standard" by the PMDG heuristic
(`Md11Fcp.IsStandard`: 29.92 within 0.005 inHg, or 1013.25 within 0.75 hPa, which admits TFDi's
"1013.2 Hp" QNE). The three altimeter rows use the same body, and a row whose altimeter has not
been delivered (0 or below) reads "not available", never "0, 0.00". The B key applies the same rule
(`Md11AltimeterAnnouncer.HotkeySentence`): a reading that is null, or 0 or below, says "Altimeter
unavailable". And the captain's altimeter announcer treats 0 or below as no reading at all — never
its baseline, never a change — because an export reads a flat 0 until the aircraft publishes it,
and a baseline of 0 announced the first real setting on connect.

### Transport facts worth keeping

- Three rapid CEVENT clicks on the autobrake selector all registered (1→4). Bursts do not
  overwrite each other; the `{seq}` prefix is what matters.
- `TDMD11.TRIGGER_EVENT` works as a channel but coalesces identical consecutive commands like any
  MobiFlight command (three identical clicks → one). No advantage; not adopted.
- A guard click sent immediately after its button's press pair was ignored twice; a lone press
  closed it. Keep guard writes spaced from their button's (`GuardOpenSettleMs`, measured from the
  guard click's WRITE — both ride the same FIFO, so the backlog ahead of the guard click is added
  to the settle).
- Some presses legitimately do nothing: GEN with engines off, tank pumps in AUTO. The feedback
  sentence is how the pilot learns that.
- A lamp shared by two buttons' stems is resolved curated-first, then longest stem first
  (`pair_lamps`); the fuel-dump STOP lamp belongs to the Emergency Stop button, per the guide.
- **The `MD11MCDU` subscription never delivers the current page.** `Md11McduDataManager`
  subscribes ON_SET+CHANGED, and SimConnect hands such a subscription only the writes that
  FOLLOW it — while the aircraft writes the area only when a screen changes. Measured with a
  read-only probe against the live aircraft (2026-09-07 16:56): the subscription alone
  delivered nothing in 8 s and nothing in a further 10 s; a `PERIOD.ONCE` read on the same
  definitions returned all three current pages within 22 ms. The app's own logs show the same
  gap on two starts (registered 16:23:19 → first delivery 16:23:40; 10:38:13 → 10:39:11, all
  three units at once, no key pressed). So `RequestAll` reads each unit ONCE alongside its
  subscription — on a DIFFERENT request id, because a request re-issued under an existing id
  REPLACES it and a ONCE on the subscription's id would freeze the window on its first page
  (pinned by `Md11McduInitialReadTests`). Before this, a pilot who started the app in flight
  saw an empty window until their first key press — and it was literally empty: `Poll`
  returned before `Render` on a never-delivered unit, so even the "no data received yet"
  advisory `Md11McduPresence` had always carried was unreachable.
- **One `Md11McduDataManager` per SimConnect CONNECTION, never per aircraft load.** Its
  `Register()` latch was written "once per connection", but `SimConnectManager.InitializePMDG`
  constructed a NEW manager on every switch into the MD-11 (and on a re-click of its Aircraft
  menu item — there is no same-aircraft early return), so the latch was per-instance and the
  second load re-issued `MapClientDataNameToID` + three `AddToClientDataDefinition` against ids
  still defined and still carrying the first load's live ON_SET subscriptions (nothing in the
  tree ever clears a client-data definition or cancels one with `PERIOD.NEVER`). Now
  `InitializePMDG` reuses the manager bound to the live handle (`IsBoundTo`), `DisposePMDG`
  leaves it alone, and only the END of the connection disposes it — `Disconnect`, or the
  `COMException` path in `Connect`, which disposes and nulls it exactly as `Disconnect` does (no path
  reaches that catch with a live manager today; the MCDU window keeps its last page and only its
  status line changes). A simulator crash reaches neither: `ReceiveMessage` swallows its
  `COMException`, so `IsConnected` stays true — a pre-existing gap. On reuse it calls
  `Reset()` — forget the previous load's pages —
  before `RequestAll` re-issues the subscriptions (same ids = a replacement) and the ONCE
  snapshot. That reset buys two things: a later-opened window cannot read the previous load's
  page as current if the snapshot never answers, and the snapshot that does answer lands as a
  FIRST delivery again — the fresh `first delivery` log line that is the evidence of a healthy
  reuse — instead of being dropped as an identical repeat (pinned by
  `Md11McduManagerReuseTests`). In practice no window is reading across the reuse: the MCDU form
  is disposed on every aircraft switch and the snapshot lands in ~22 ms. Log evidence of a
  healthy switch: one `registered` line per connection, a `MD-11 MCDU manager reused` line and a
  fresh `first delivery` line per MD-11 load, no `DUPLICATE_ID` exception. `Register()` records
  each completed step — the name mapped, then each unit's definition, then each unit's struct, seven
  steps (`Md11McduRegistrationSteps`) — and a retry resumes after the last one. After a partial
  failure it used to re-issue every step that had already succeeded, adding definitions again to ids
  already defined; SimConnect reports that later, as an exception message (`DUPLICATE_ID`), never at
  the call. The test seam
  (`internal Md11McduDataManager()`) must leave `_simConnect` untouched — even `= null!` makes
  the JIT resolve the field's type and load the mixed-mode SimConnect wrapper, which cannot load
  in the test process (no native SimConnect DLL beside it).
- **MD-11 page titles carry their page counter** — the live Left unit reads
  `      ACT F-PLN     1/2` (name large, counter small). A slew across a page boundary changes
  the title TEXT without changing the page, so the MCDU window announces a changed title but
  moves the cursor to line 1's VALUE row — found by row kind and line (`Md11McduRows`), never raw
  index 1, which is a bare label row on most pages; the same row is the fallback when nothing is
  selected — only when the page NAME changed (`Md11McduTitle.SamePage`, which
  also folds a pending-modification prefix away: ACT F-PLN and MOD F-PLN are one page with one
  set of lines, SEC F-PLN is not). The last adopted title and the last cursor row are kept PER
  UNIT (`Md11McduUnitMemory`, three slots): one slot for all three compared a unit's title
  against whichever unit was shown before it, so Left → Center → Left read as a page change and
  threw the cursor to line 1 on the way back. A blank-and-return to the same page, and a switch
  to another unit and back, both put the cursor on the row that unit was last on; a unit that was
  blank at the switch and then shows the page it last showed is silent too — the switch was
  already spoken. The advisory row itself is selected the moment it appears so the screen reader
  reads it rather than an empty list. On a unit switch or a first open the list is replaced AT
  ONCE — by the new unit's page, or by a waiting row naming the unit until that page, or its
  settled blank state, arrives — so it never shows one unit's rows under another unit's name (the
  blank clock ticks only while the window is visible, so a switch soon after opening used to hold
  the previous unit's rows, and opening onto a blank unit showed an empty list for up to the blank
  settle). A re-show CLEARS all three blank clocks before it re-syncs, because a clock stopped
  while the window was hidden cannot say how long a unit has been blank: a unit caught mid-erase at
  the last pre-hide tick and mid-erase again at re-show read as a SETTLED blank, which put "… MCDU
  is blank - nothing on this screen." under the cursor the window then focuses — so the screen
  reader, not the app, read a false sentence aloud on activation and the real page overwrote it
  0.2-0.4 s later. The window follows the feed ONLY while it is visible: the
  250 ms poll is started by `ShowForm` and stopped in `OnVisibleChanged` on hide (the scratchpad
  announcer rides that poll) — as every other CDU window in the app does — because a poll that
  ran on after Escape spoke every page title, MSG lamp and scratchpad change over the cockpit
  for as long as the window stayed closed. A re-show goes through the same silent re-sync as a
  unit switch (`ResyncToSelectedUnit`: drop the followed page, re-seed the scratchpad announcer
  silently and re-baseline the flags,
  draw the current page with the title adopted silently), so what changed while hidden is read
  from the list under the cursor, never replayed. Because that re-sync says nothing, a FIRST
  open — and a re-show onto a page the FMS moved to while the window was hidden
  (`!Md11McduTitle.SamePage` against that unit's own last title) — puts the cursor on the TITLE
  row, so the screen reader's own read of the focused row names the page with no app
  announcement; a same-page re-show keeps the row-identity restore and the line the pilot left.
  A Shift+M on an already-open window re-syncs nothing: it is following the feed already. MSG
  lighting while the window is closed still reaches the pilot through the
  `MD11_{L,C,R}MCDU_MSG_LT` lamp announcement — unless that Ctrl+M row has been muted, which is
  inviting while the window is open, because an open window speaks its own "MSG" beside the
  lamp's (a pre-existing double, worth removing separately). The cursor itself is put
  back by ROW IDENTITY (`Md11McduRows.Restore`: title / label n / line n / scratchpad), never by
  index — blank label rows are dropped, so "6:" is item 12 on the F-PLN page and item 7 on the
  MENU page, and the index restore every other CDU form uses handed a pilot reading line 6 the
  scratchpad after a few slews (pinned by `Md11McduCursorTests`).
- **Backspace (one CLR) and Delete (clear the whole scratchpad) are bound on the DISPLAY list,
  never form-wide.** The window has `KeyPreview`, and a form-level Delete consumed the key before
  the MCDU Input box saw it: a forward-delete while editing typed text ran the CLR loop
  (`ClearScratchpadAsync`, one CLR per 150 ms until the exported pad reads blank) against the
  aircraft's scratchpad and announced "Scratchpad cleared" over the edit. Same scoping as the
  iFly CDU window (`IFly737CDUForm`, `case Keys.Delete when ActiveControl == _display`). The loop
  is a Task with an `OnlyOnFaulted` continuation into `debug.log`, never `async void`. Not
  unit-tested — the decision is which control's `KeyDown` the handler is subscribed to, WinForms
  wiring with no separable predicate. The clear itself says nothing when it works: the scratchpad
  is read by the shared `CduScratchpadAnnouncer` (moved from the iFly window to `Forms/`), built here
  by `Md11McduScratchpad.CreateReadBack()` — "Scratchpad cleared" where the iFly keeps "Cleared", and
  TWO stable polls where the iFly keeps one: a change is spoken only once it has read the same on two
  polls in a row, so a one-poll redraw flicker (a blank frame between two identical ones, which the
  old 300 ms debounce also absorbed) is never read. Typing and CLR bursts set its
  `SuppressUntil` from the queued key count × the bus pacing, so the settled pad is read ONCE and no
  intermediate text ("KJF") leaks. It used to say "Scratchpad cleared" even when its presses ran out
  with the pad still full, and its own debounce said it a second time; now presses exhausted without
  an empty pad say "Could not clear the scratchpad", and a second Delete while a clear runs is ignored.
- The export's per-cell `large` flag carries meaning the window does not yet render: on the
  F-PLN page the FROM line is all large and every later waypoint's time/speed/altitude
  predictions are small (measured 2026-09-07 17:04) — the Honeywell "large = entered or
  actual, small = FMS-predicted" convention. `Decode` keeps no size at all: the per-line majority
  it once kept (`LineIsLarge`) had no reader but the content comparison, so a font-only change
  re-rendered the page and re-restored the cursor for nothing. `Md11McduChar.Large` stays — it is
  part of the 3-byte binary layout. Per-cell sizes would be needed for a Fenix-style
  selected-option marker or a predicted-value cue. No page with a mixed-size option group has been
  captured yet, so
  whether the "large among small" selection convention exists here is unmeasured.

### Labels

Repairs live in the generator (`finalize_controls`): balanced-parenthesis strip (four tooltips
had lost their closing parenthesis), HTML entities, `<->` → "to", breakers "C24 Tank 1 Transfer
Pump Power", guards "{control} guard", curated names for the derived garbage, MCDU keycaps.

**One row per physical control**, judged on the EVENTS map rather than the name
(`_second_clickspots`): an event id IS the action here, so two nodes of the same kind firing
byte-identical events are one control reached from two 3D clickspots, and a second row asserts a
distinction the aircraft does not make. That covers the `001` / `_F` twins (`ECON_BT001`), the
throttle-grip and glareshield go-around buttons (`GA_BT_ALT`, event 77851), the EFB toggle from
either seat (`MD11_EFB_TOGGLE_FO`, event 94465) and the door 1L/1R slide levers reachable at the
door and from the cabin — 1365 controls down to 1361. The survivor is decided deterministically,
never by file-traversal order: MD11_-prefixed first (the aircraft's own naming over a raw 3D
name), then shortest, then ordinal. The labels that named the lost half went with it: "EFB Toggle",
not "(Captain)"/"(First Officer)"; "Door 1L Slides", not "(cabin lever)". Lamps dedupe separately,
on their L:var (the `MD11_CPT_*`/`MD11_FO_*` audio families were second nodes on one var — two
batch entries with one Name, the VarNameCollision trap).
`MD11_OPT_*` are configuration flags, kind `option`, never registered. `GSL`/`GSR` are the
glareshield (master warning/caution), not ground service.

**No two lamps share a spoken name.** Every lamp is a Ctrl+M row as well as a status row, and a
screen reader cannot tell two rows with one name apart, so `LAMP_NAME_OVERRIDES` (generator)
curates the label — only the label; legend and lit word are untouched — where the generated name
collided: the Captain's and First Officer's glareshield lights ("Captain Master Caution CAUT
light"), the centre-panel aux-pump light, and the LTS panel's bare `_LT` vars, which TFDi's
`MD11_PA_Lights_Template` binds to the BUTTON's own emissive (so "Passenger Addressing light",
distinct from the "Passenger Addressing ON light" annunciator beside it). `apply_state` refuses to
generate a collision, and `Md11LabelTests.NoTwoLamps_ShareASpokenName` pins the shipped map.

**Four label rules from review round 2 (2026-09-11)**, all but the first latent in TFDi's package
(they change nothing in today's map), each pinned in `test_generate_md11_map.py`:

- **An airframe variant flag never shapes a label or a position.** A tooltip label that reads one
  (`LABEL_ONLY_VARS`) has one wording per variant, so `parse_tooltip` refuses it until `LABEL_FIXES`
  names the control, and no expression that reads a variant flag yields positions — the two cabin
  temperature knobs, §10.
- **Guard labels are composed last.** "{control} guard" is built in a second pass once every other
  label is final, so a repair `finalize_controls` makes to the covered control reaches its guard's
  name too; and the guard test runs before the breaker and MCDU ones, so a guard whose id starts
  with `MD11_BKR_` or an MCDU area is still named as a guard.
- **The surviving lamp is chosen by rule.** When two lamp nodes light one L:var, `_second_lamps`
  keeps the node NAMED AFTER THE VAR, then `_second_clickspots`' rule (MD11_-prefixed, shortest,
  ordinal) — never file-traversal order, and `collect()` walks folders in name order. That keeps
  all 37 shipped pairs as they were; shortest-first alone would have renamed 34 lamps. A lamp under
  two knob/switch stems belongs to the LONGER stem (`_owner_by_stem`).
- **A nested `<UseTemplate>` stops the generator.** The parse is flat — a block's body runs to the
  first `</UseTemplate>` — so a nested block would be merged silently; `collect()` raises a
  `ValueError` naming the file, the parent's node and the nested node, skipped templates included.

### Where the layout deviates from the design spec, and why

Three departures from spec §3.8's panel list, all deliberate and now pinned by
`Md11PanelLayoutTests` so a future edit has to mean them:

- **Glareshield gained "Warnings Captain" / "Warnings First Officer"** and lost the spec's "Ground
  Service": `GSL`/`GSR` are the glareshield master warning and caution, so there was no
  ground-service panel to build.
- **Circuit Breakers are four panels, Upper first** (spec: "Lower Panel, Upper Panel") — the
  aircraft has four banks, and Upper leads because that is where they sit.
- **EXT PWR's lit order reads "On, Available"**, not the spec example's "Available, On": lit
  legends are joined in lamp order, and that is the order the state block lists them in.

### Three guards the aircraft does not link

`MD11_AOVHD_EVAC_GRD`, `MD11_AOVHD_GPWS_GRD` and `MD11_EXT_DOOR_CRG_MAIN_ARM_GRD` cover controls
that carry no `guard_id`, so `EnsureGuardOpenAsync` never lifts them automatically. The layout
places each immediately before its switch and every guard is an operable button, so the pilot
opens them by hand — the same manual fallback that exists for every guard. (An earlier version of
this paragraph recorded a "quirk to expect": `MD11_EXT_DOOR_CRG_MAIN_ARM_GRD` reading `..._ARM_SW`
so its spoken Open/Closed mirrored the arm switch. That was not a quirk but the guard-state defect
below, and it is gone.)

### A guard reads its own cover, never the control under it

A guard cover's position is its OWN L:var — TFDi animates the cover on its node id, and the
aircraft's state files carry it (`Data/State/ReadyToFly.json`: `Aircraft::vars->MD11_OVHD_FUEL_DUMP_GRD`).
Four covers' TOOLTIPIDs read the control UNDER them for their Open/Closed wording —
`Fuel Dump (%((L:MD11_OVHD_FUEL_DUMP_BT))%{if}Open%{else}Closed%{end})`, likewise
`MD11_OVHD_FUEL_DUMP_STOP_GRD` (`..._STOP_BT`), `MD11_MIP_CTR_GEAR_GRD` (`..._GEAR_BT`) and
`MD11_EXT_DOOR_CRG_MAIN_ARM_GRD` (`..._ARM_SW`) — and `parse_tooltip`'s "first L:var in the
tooltip" rule handed each guard the covered control's var as its `state_var` while `latch_for`
(correctly) keyed the latch on the guard's own id. The C# Guard case registers the guard's
definition with `Name = state_var`, so the key `EnsureGuardOpenAsync` force-reads was the BUTTON's
latch: Fuel Dump on → off → on again read latch 0 with the cover still open, decided "closed", fired
the guard click — which LOWERED the open cover — and the press landed under it; the composed
"Fuel Dump guard: Open/Closed" label followed the valve for the same reason. `finalize_controls`
now pins every `kind == "guard"` to `state_var = node_id` with an empty `value_map` (a cover has no
positions; the other 28 guards always shipped that shape), and the rule is pinned three ways:
`test_a_guard_whose_tooltip_reads_the_covered_button_still_reads_its_own_cover` (generator),
`Md11ControlMapTests.EveryGuard_ReadsItsOwnCover_NotTheControlItCovers` (shipped map) and
`Md11DefinitionStateTests.EveryGuard_RegistersItsOwnCoverVar_NotTheCoveredControls` (registration).
Never "fix" a guard's var in C# or with a per-guard curation — the generator owns it.
`MD11_EXT_DOOR_CRG_MAIN_ARM_GRD` appears in the wasm only as one bare string and its
`_LEFT_BUTTON_DOWN` event — unlike the other 31 guards it has no `Aircraft::vars->` accessor and no
entry in the state files (measured 2026-09-09); its arm switch `..._ARM_SW` is in the same position,
so HEAD's read of it was no better founded. The cover var should still be live once clicked, and if
it ever reads a constant 0 the only cost is a "Closed" label — the arm switch under it carries no
`guard_id`, so no auto-open ever acts on it.

## 10. Panel gaps pass (2026-09-06)

Measured on a live MD-11F on the ground at UCFM (cold and dark, ground power available; battery
and external power switched on for the powered probes, everything restored afterwards). Design:
`docs/superpowers/specs/2026-09-06-md11-panel-gaps-design.md` (local).

### The third IRS was there all along

TFDi's tooltip for `MD11_OVHD_IRS_3_KB` is `Auxiliary IRS (%((L:…))%{if}%Nav%{else}Off%{end})` —
a stray `%` before `Nav`. `parse_tooltip`'s if/else extraction needs a `%`-free branch, so the
switch shipped with no positions; a position control with no value map is `RenderAsReadOnlyStatus`,
which MainForm renders as a read-only numeric field (`Units` defaults to `"number"`, so it takes the
read-only TextBox branch, not a button — an earlier telling here said "plain BUTTON"), and a pilot
counted two IRS switches.
The generator now drops a `%` glued to a letter (only `%{`, `%(`, `%!` and `%%` are meaningful),
which changed exactly one control. Live: event 90116 toggles the switch 0→1→0 like IRS 1/2.

### The same defect class, and the knobs that came out of it

Every position-type control with an empty value map renders as that read-only number — about 110 of
them: audio volumes (one raw unit per wheel click, 0–10), lighting and brightness knobs, the
temperature knobs, the pressurization controls, trims, tuners. Two temperature knobs were worse:
`FWD_CAB_TEMP`/`MID_CAB_TEMP` carried the freighter/pax WORDING ("Courier Cabin"/"Forward Cabin")
as positions, an inline-if leak, and their LABELS spoke both variants at once ("Forward Cabin/Courier
Cabin Temperature"). Since round 2 the generator refuses an airframe-variant word in a label unless
the node has a curated name, and these two are "Forward Zone Temperature" and "Middle Zone
Temperature" — true on the freighter and the passenger jet ("Aft Cabin Temperature" is TFDi's own
wording on both). The six temperature knobs now carry curated positions
(`temperature_positions(n)` in the generator: "1 (full cold)" … "n (full hot)", per TFDi's Systems
Guide, which describes the selectors' ends as full COLD/HOT, 65–85 °F, 75 °F centre); a curated
`value_map` wins in `finalize_controls`. Whether position 1 is the guide's OFF detent is unverified.

**Left as they are, deliberately:** the outflow valve switch (`MD11_OVHD_PNEU_OUTFLOW_VALVE_POS_SW`,
5 unnamed states) did not move on either click with the cabin system in automatic; the manual
landing elevation knob (`MLDG_ALT_KB`) is a 72-step counter (the guide: "knob must be turned 120°
to operate") with no readable feet-per-step; cabin climb/descend (`CLBDES_KB`) is a spring-loaded
hold switch (right-down 1→2, right-up back to 1) the app has no control type for. Volumes,
lighting and trims are the same class, not done.

### Knobs that read an export are rows, not combos

Nine controls carry one of TFDi's read-only **exports** as their `state_var` — the three FCP mode
knobs (`MD11_CGS_HDG_KB` → `MD11_AP_HDG_TRK`, `SPD_KB` → `MD11_AP_IAS_MACH`, `VS_KB` →
`MD11_AP_VS_FPA`), the two EFIS minimums caps (`MD11_LECP/RECP_MINIMUMS_CAP` → `MD11_CAP/FO_MINIMUMS`)
and four baro/ISFD knobs with no positions. Their WHEEL events turn the heading, speed, V/S,
minimums or altimeter VALUE, never the var the row names, so a combo on such a row can only stall
its walk — and `SafeWalk`'s direct-write fallback then raw-wrote the export (`MD11_CAP_MINIMUMS` ← 0
zeroed the captain's minimums, silently, before "did not move"). Two fixes, each at its own depth:

- The generator no longer lifts a trailing `%{if}A%{else}B%{end}` as positions unless the trailing
  expression reads exactly ONE L:var. The minimums caps' tooltips read their own value and then the
  mode SWITCH's var for the Baro/Radio word, which had given a 0–15000 ft value knob a
  `{0 Radio, 1 Baro}` map; the switch (`MD11_LECP/RECP_MINIMUMS_KB`) keeps those words.

### Tests: what the aircraft has

Fourteen test controls, all in panels. **No overspeed, stall or per-loop engine fire test exists**
— the words appear only on breaker labels; stall and overspeed are warnings in the wasm
(`StallAOA`, `SND_CAWS_OVERSPEED`). The one fire test, `MD11_AOVHD_FIRETEST_BT`, tests EVERYTHING:
held live it lit ENG 1/2/3 FIRE, APU FIRE and the master warning, all dark on release. TFDi's
tooltip says "APU Fire Test"; their Systems Guide names it ENG/APU FIRE TEST, so the app says
"Engine and APU Fire Test" (`LABEL_FIXES`). The buttons are hold-to-test: the lights are on while
the button is down, so the bus's 60 ms press ended before the 1 Hz lamp batch could see them.
`Md11TestButtons` holds **eleven** of them for 3 s (`Md11EventBus.PressAndHoldAsync`); the weather
radar TEST mode is a selection and is not held. The three "test running" lamps (cargo smoke,
hydraulic, cargo door) are Status Display rows of their panels.

**The annunciator light test (`MD11_OVHD_ANNUNLT_TEST_BT`) is excluded and must not be added
back.** It is the one test whose job is to light EVERYTHING: a hold turns on all ~488 of the
aircraft's annunciators at once, every one of those is a lamp update, and `HandleLampUpdate`
composes and speaks a sentence per lamp on the lit edge — then again, 1.5 s later, on the deferred
dark edge when the button releases. That is close to a thousand sentences, which buries the very
thing the pilot pressed it to hear along with everything else in the queue; a pilot cannot even
skip it. It stays a tap, exactly as it behaved before this pass, and the tap is still useful — the
lamps are visible to a sighted observer and the aural warnings still fire. The follow-up, if it is
ever wanted, is a hold made under a lamp-speech mute that ends in ONE summary sentence
("Annunciator test: 488 lights on"), not a hold that speaks each lamp.

Three of the eleven held buttons — `MD11_AOVHD_CRGSMK_TEST_BT`, `MD11_OVHD_HYD_HYD_TEST_BT` and
`MD11_OVHD_CRG_DOOR_TEST_BT` — carry a lamp state block with no latch, so the press feedback can
speak the dark word before the lit lamp lands and is then corrected once the lamp does. (The other
eight are stateless: their press is silent and their lights are the whole read-out.) Overlapping
presses on one button shorten the visible hold but always end released.

**Disposal releases the hold.** `Md11EventBus.PressAndHoldAsync` registers the UP it owes AS it
queues the DOWN (only when both a DOWN and an UP exist — a button with no DOWN was never pressed)
and takes it back as it queues the UP, both under the held table's own lock; the pump records,
under that same lock, when it WRITES a DOWN a registered hold owns. `Md11EventBus.Dispose` stops
accepting and stops the pump FIRST: it cancels the pump, takes off it, in order, everything it had
not yet taken — under `_takeLock`, which the pump holds around its own take, so no id is stranded
between the two or written out of order (the pump holds that lock through its wait, so this take
MUST follow the cancel, or it hangs the UI thread) — and waits up to `PumpStopTimeoutMs` (500 ms) for
the one write it may have in hand.
A pump still stuck in a write past that gets NOTHING written beside it (a second writer would
interleave on the one CEVENT slot): its queued ids and owed UPs are logged as discarded — the
residual a hung channel always had. Otherwise, on the calling thread, it writes the UP of every hold
whose DOWN was written — still held, or already ended with its release queued (a release is queued
carrying its hold), once per button — the first thing written, so a 3 s test button is released at
once however long the backlog; drops every held DOWN still queued (never written, so nothing is owed)
together with its UP; and drains the rest IN ORDER, paced, within `DrainTimeoutMs` (1000 ms). It sits
on the UI thread, so disposal is bounded at 500 + 1000 ms in all. An UP never precedes its own DOWN.
One case stays open: a hold that ENDED with its DOWN still unwritten keeps both halves in order behind
the backlog, and the drain bound can cut between them — reachable only after a pump stall of about
3 s, because the hold's wait already includes the backlog ahead of it. The
version before fired each owed UP onto the
TAIL of the paced FIFO and allowed `DrainTimeoutMs` (about 16 ids) for the drain, so behind an MCDU
scratchpad send (48 ids) the UP was dropped and the test button stayed held; the one before that
cancelled immediately after `CompleteAdding`, which discarded every queued id — a held button's UP
and a walk's last click among them — so a MANUAL re-select of the MD-11 from the Aircraft menu
inside the 3 s hold (which disposes the definition with the MD-11 still loaded) left that test's
lights on until the app was restarted and the button pressed again. Releasing from `Dispose` is safe because `L:CEVENT` is TFDi's private
channel: no airframe this app supports reads it (checked against the FBW A320/A380, PMDG 737/777,
HS787 and iFly definitions, 2026-09), so on the auto-detect path — where the MD-11 is no longer
loaded — an inert write lands on an aircraft that ignores it. Whoever takes the entry back fires the
UP, so a hold that outlives the bus writes nothing more; a hold that starts after the release sweep
is refused outright and writes neither half; a hold RACING the sweep cannot be caught in between,
because the register and the DOWN happen under the held table's own lock as one step (and the
release mirrors it) — the guarded hydraulic test lifts its cover on a pool thread first, so as two
steps its DOWN could be queued just after a sweep that did not yet owe its UP, and the mirror case
let `CompleteAdding` drop an UP the sweep had already declined to fire, each leaving the button
held; a control with NO DOWN writes nothing at all, since a button never pressed cannot be
released; and `Fire` after disposal is dropped with a debug line, never thrown — as is a read of
`Pending`, so a walk on its way out cannot surface a benign shutdown race as an Error-level
"set threw" line.

The definition's `Dispose` also cancels every walk in flight (`CancelWalks`: the `_walkCts` entries
and the Dial-A-Flap source, through `Md11WalkCancellation.CancelAll`, which tolerates a source the
walk's own finally disposed a moment earlier; `_dialSetGen` is bumped, and `SetDialAndAnnounce`
re-checks the generation after its settle delay, so a dial set past its debounce returns before it
could speak a shortfall read from the next aircraft's cache) so none finishes
against the next aircraft's registrations and speaks "… did not move" for it. `Dispose` also nulls
`_sim` — every reader null-checks — so a late callback cannot read the next aircraft's cache; a
reader of the mutable `_bus` takes it into a local ONCE and checks that (`TryDirectSetAsync` read
the field twice, with `Dispose` able to null it in between). The
debug.log lines are `CEVENT bus disposing with N held button(s) — releasing UP …` and
`Definition disposed with N walk(s) in flight — cancelled.`

**Accepted residual, narrowed:** a SimConnect drop inside the hold still loses the UP — there is no
channel to send one over, and the definition is not disposed on a drop. App exit is covered exactly
when `MainForm.OnFormClosing` disposes the definition before `Disconnect()` (the exit-time disposal
parity with the PMDG EFB clients): the same drain-and-release runs there, which is why the wait must
stay bounded.

### Altimeters and minimums

`MD11_EXTCTL_FO_BARO` and `STBY_BARO` are inboxes of the captain's contract (29.85 → 29.85, 29.80
→ 29.8, both reset to -1), so Ctrl+B sets all three from one entry, each in its own display's
unit, and "Standard" writes standard pressure as a VALUE to all three (`Md11Fcp.StandardFor`),
the PMDG dialogs' way, instead of the knob-push toggle. The captain's setting is announced once it
settles (`Md11AltimeterAnnouncer`, 1.5 s, baseline-first; the mute is checked in the timer callback
because it speaks outside `ProcessSimVarUpdate`). An unchanged redelivery — the status-display
auto-refresh force-reads the var about once a second while the Minimums and Altimeters panel is
open — does not re-arm the settle: the first implementation did, and the setting was never spoken
while that panel stayed open. That announcer speaks only on a CHANGE, and the other two sides
have no announcer at all, so Ctrl+B reads all three back on their next DELIVERY, `Md11Fcp.VerifyAfterMs`
(1200 ms, the EXTCTL inbox allowance) after the writes — see "Read-backs complete on delivery"
(`VerifyAltimetersAsync`, `Md11Fcp.AltimeterAgrees` — one display step of the coarser unit, 1 hPa
or 0.01 inHg, because the export's own resolution is unmeasured) and speaks ONLY a disagreement
("Standby altimeter not set, reads 1012, 29.88"); agreement stays silent, a read-back of 0 is no
evidence, and a newer entry supersedes an older one's read-back (the dialog stays open for more
input, so Standard followed by the ATIS QNH within the window must not cite the QNH as a failure
of the Standard). A typed standard pressure snaps to the exact standard value of the display's unit
(`BaroToDisplayUnit`): 1013 on an inches display writes 29.92, not the converted 29.91 that
the read-back would have spoken as a QNH.

**The STD rows (2026-09-11).** The EFIS panels' baro knobs push for STD, and so does the standby

## 11. AI display reading (2026-09-08)

The five display reads every AI-vision aircraft has — Alt+P / Alt+N / Alt+E / Alt+S / Alt+I in
output mode — with two things the other aircraft do not have yet: the app moves the simulator
camera to the instrument view that frames the display (and leaves it there — see "No restore"
below), and the capture is taken with `PrintWindow` so a window on top of the sim does not land
in the picture. Wiring:
`Aircraft/MD11/Md11DisplayReads.cs` (five rows: key → prompt → spoken name → view index) called
from `HandleHotkeyAction` ahead of its switch; `BaseAircraftDefinition.ReadDisplay` with an
`InstrumentViewRequest`; `Services/InstrumentViewPlan` (pure) + `InstrumentViewSwitcher`;
`SimConnectManager.Camera.cs` (fixed def 341). Prompts: `GeminiService.DisplayType.*Md11`.

### The instrument camera views — measured, not read off cameras.cfg

`cameras.cfg` ships ten `SubCategory="Instrument"` cameras; `CAMERA VIEW TYPE AND INDEX MAX:2`
reads 10. The sim selects them with Ctrl+1…Ctrl+0 (MSFS 2020) or Shift+1…Shift+0 (MSFS 2024);
the SimVar index is 0-based. Captured one by one on MSFS 2024 at 3840×2160:

| View | Index | Frames | Used for |
|---|---|---|---|
| 1 | 0 | Captain's PFD, captain's ND, EAD — all legible | Alt+P, Alt+N, Alt+E |
| 2 | 1 | Whole glareshield with the tops of all six DUs; SD cut off | — |
| 3 | 2 | Captain's ND, EAD, gear handle, SD | Alt+S |

### The camera over SimConnect

`CAMERA STATE` (2 = cockpit), `CAMERA VIEW TYPE AND INDEX:0` (1 pilot, 2 instrument, 3
quickview) and `:1` (index) are readable AND settable. Verified live: index alone switches within
a type; type-then-index switches from a pilot view; the cut is instantaneous (a capture 0 ms
after the write already showed the new view), so the switcher's read-back poll normally matches
on its first read and the whole entry costs one 250 ms settle. Rules, all pinned by
`InstrumentViewPlanTests` / `InstrumentViewSwitcherTests`:

- A non-cockpit camera (state ≠ 2) is REFUSED — "Switch to a cockpit view first." — with nothing
  written. Forcing the cockpit from an external view is out of scope.
- Already on the wanted view: no writes.
- Otherwise write type 2 then the index, verify by read-back (100 ms steps, 1 s cap), settle
  250 ms, capture. The camera STAYS on the instrument view — see "No restore".
- A write that never verifies (paused sim, menu open) is announced — "Could not confirm the
  cockpit view switch; reading what is on screen." — and the read continues. It never says "could
  not switch": Switch and Unknown both write, so the camera may well have moved.
- A camera read that misses still attempts the switch. Every read takes its OWN request id from a
  rotating range of eight starting at `REQUEST_CAMERA_VIEW` (341-348, below
  `INDIVIDUAL_VARIABLE_BASE`; `CameraReadWaiters`), and a delivery completes only the waiter
  registered under ITS id, so an abandoned read's late reply completes nothing. Every read used to
  share one request id, and releasing an abandoned waiter protected only the case where nobody was
  waiting — a late reply could complete the NEXT read: a false "could not switch", or a stale
  "already there" that skipped the write and read the wrong display. The verify cap is elapsed time
  (read timeouts included), and one display read runs at a time: a second key press while one is in
  flight is refused with "A display read is already in progress."

### No restore — measured, and removed on 2026-09-09

The first version wrote the previous `(type, index)` back after the capture, and it worked for
the built-in pilot and instrument views in the 2026-09-08 probe. It did NOT work for the views
blind pilots actually sit in: Robin and a friend both fly from user-saved custom cameras (a cabin
view, wing views — chosen for what they SOUND like), stored per variant under
`%LOCALAPPDATA%\Packages\Microsoft.Limitless_8wekyb3d8bbwe\LocalCache\SimObjects\Airplanes\
TFDi_Design_MD-11\presets\…\cameras.cfg` as `Category="Cockpit"`, `SubCategory="Custom"`
(slots 0, 8, 1, 6, 9; slot 6 sits 11.6 m aft of the cockpit datum facing 135°, the cabin view).
The sim REPORTS such a camera as `CAMERA VIEW TYPE AND INDEX` type 1 (pilot view) with an index
the write path does not accept: Robin's own debug.log for 2026-09-09 01:15:46 shows the restore
writing type 1 / index 7 while `CAMERA VIEW TYPE AND INDEX MAX:1` advertises 6 pilot views, and
the pilot stayed in the instrument view. Neither the SimVar (types 0–5, "View" being the external
showcase/drone family) nor any SimConnect key event (`VIEW_*` are FSX leftovers; nothing loads a
saved camera by slot) offers a way to select a custom cockpit camera, so a restore can only ever
cover the built-in views — and a restore that works for some views and silently fails for the
ones a pilot chose is worse than none. Robin's call: keep the switch, drop the restore; the pilot
returns with their own view key. Do NOT re-add a restore that writes the read-back pair, and do
NOT add one keyed to this preset file — custom view sets vary per pilot.

### The capture

`ScreenshotService` tries `PrintWindow(PW_RENDERFULLCONTENT)` first (verified 2026-09-08 with the
sim fully hidden behind another app: 536 of 576 sampled pixels non-black) and falls back to the
old BitBlt screen copy when `ScreenshotFrame.LooksBlank` says the frame is blank: every sample dark
(R+G+B ≤ 30) AND uniform (the spread of R+G+B across the samples ≤ 6). A failed PrintWindow frame
is flat black; a night cockpit is dark but not flat, and under the old dark-only rule every night
read fell through to the screen copy, which captures whatever window sits on top of the sim. The
scene description shares the path.

`PrintWindow` is a synchronous cross-process render request with no timeout of its own, so
`CaptureAsync` bounds its own work at 10 s and returns null on a timeout: a hung simulator used to
block the capture's pool thread forever and hold `BaseAircraftDefinition._displayReadInFlight` for
the session, refusing every later display read. An abandoned capture's pool thread is left to
finish (or not) on its own; each timed-out press strands at most one. The frame is 24-bit RGB
(`Format24bppRgb`), so there is no alpha channel to leave transparent in the PNG — the 32-bit ARGB
frame it replaced was probed on 2026-09-09 and came back fully opaque on three live windows, so no
transparent frame was ever seen; GDI simply leaves that byte undefined, which is a guarantee
nobody has. The capture
thread runs per-monitor DPI-aware (`SetThreadDpiAwarenessContext(PER_MONITOR_AWARE_V2)`, restored
afterwards, tolerated where the call is absent) so `GetWindowRect`, `PrintWindow` and the
screen-copy fallback agree in physical pixels.
