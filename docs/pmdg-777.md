# PMDG 777

> **Read this when:** working on the PMDG 777 (switch/CDA patterns, CDU, radios, System Display).

### PMDG 777 Specific Patterns

**Switch control:** Use CDA (SetClientData) with direct position values for most switches.
- Two-position toggles: `SendPMDGEvent(eventName, eventId, targetPosition)` where targetPosition is 0 or 1
- Multi-position selectors: same, with the target position index
- Momentary buttons: `SendPMDGEvent(eventName, eventId, 1)` — parameter 1 = pressed, 0 = no-op
- Continuous knobs (brightness, temperature, EFIS baro/mins): **cannot be controlled via the SDK event with a position param** — do not add to panels via that path. **EXCEPTION (2026-06): knobs whose cockpit-model L:var IS the pilot input are fully settable by writing that named L:var** — e.g. the shoulder heaters (`L:LEFT/RIGHT_SHOULDER_HEATER`, 0–100; the SDK struct field `AIR_ShoulderHeaterKnob` follows the write, live-verified). Find the L:var in `77W_Cockpit_Behavior.xml`; see the Cockpit furniture section below.
- **Temperature controls (Air Conditioning panel, 2026-07, live-verified on BOTH variants):** flight deck + cabin temp selectors are continuous knobs on that L:var exception — stepped combos writing `L:FLTDeckTempKnob` / `L:CABINTempKnob`, and the two knobs have **DIFFERENT scales**: the FLIGHT DECK knob is 0–75 mapping ×0.8 onto SDK `AIR_TempSelector[0]` 0–60 Cold→Warm (write 60 → SDK 48, verified; MAN detent: write 87 → SDK 70, verified), but the CABIN knob is **0–60 mapping 1:1** onto `AIR_TempSelector[1]` (its cockpit XML clamps at 60; live-verified 15→15, 60→60 — and an out-of-range external write passes through UNCLAMPED, 75→SDK 75, so never reuse the flt-deck 0–75 steps on the cabin knob). The **AFT + BULK 3-position cargo selectors** (`AIR_CargoTemp_Selector[2]`, 0=Off/1=Low/2=High — the SDK header says aft/bulk, NOT fwd/aft) work on BOTH variants via the normal CDA event path. The **four continuous cargo knobs** (`L:MAINDECK{FWD,AFT}TempKnob` / `L:LOWERDECK{FWD,AFT}TempKnob` → SDK `AIR_CargoTemp_MainDeck*/Lower*_Sel`) are functional on the **77F freighter only**, with a DIFFERENT scale from the flight deck knob: **1:1 onto SDK 0–60** (55→55 verified), and the lower-aft knob takes the bulk-heat detent values DIRECTLY: **67 = HEAT HIGH, 70 = HEAT OFF, 73 = HEAT LOW** (all live-verified on the 77F). **Variant gating** (`HandleUIVariableSet`, keyed on the CDA **`AircraftModel`** field — SDK: 1 -200, 2 -200ER, 3 -300, 4 -200LR, 5 777F, 6 -300ER): the cargo knobs announce "freighter only" on any known passenger model, and the CABIN knob announces "not functional on the freighter" on model 5 (dead both ways — the L:var moves the visual but PMDG's systems never sample it; live-verified on 77W + 77F; every variant's cockpit behavior XML carries all six knobs, so the write always "sticks" even where dead). **Never gate 777 variants on `CurrentAircraftIcaoType`**: the 777F and the pax 777-200LR both declare `icao_type_designator B77L` (verified in the installed `pmdg-aircraft-77f` and `pmdg-aircraft-77l` packages), and livery TITLEs are freeform — the CDA `AircraftModel` field is the only reliable variant id. Unknown model (CDA not ready) falls through to the normal write; a refused set also re-requests the var so the combo snaps back to the real value. The wrong-variant knobs are additionally **hidden from the Air Conditioning panel entirely** (`IsPanelControlVisible` override — the generic hook lives on `BaseAircraftDefinition` and is re-evaluated on every panel build, so late variant detection self-corrects on the next panel open); the set-time guards remain as the backstop for a panel built before the first CDA snapshot. **No actual °C temperature values exist anywhere in the SDK** (only selector positions) — cabin/cargo temps on the EICAS AIR synoptic are pixel-only, same class as the MD-11 FMA. The 77W and 77F SDK headers are byte-identical (one shared 777X SDK).
- **Fuel control levers:** Exception — use CDA with **inverted** parameter (1=Cutoff, 0=Run). See special case in HandleUIVariableSet.
- **Ground power switches (ELEC_ExtPwr):** Momentary push buttons — send parameter 1 regardless of target. See special case in HandleUIVariableSet.

**Autobrake selector — EIGHT detents, and the 777 has a DISARM the 737 does not (fixed 2026-08-01, live-verified).** `BRAKES_AutobrakeSelector` runs `0 RTO / 1 OFF / 2 DISARM / 3 "1" / 4 "2" / 5 "3" / 6 "4" / 7 MAX AUTO` (SDK `PMDG_777X_SDK.h` line 272; the SDK comment abbreviates after index 3, but **index 7 exists and is the top detent** — every position was walked against the hardware through a MobiFlight profile). The label table had been **missing DISARM**, so every entry from index 2 up sat one step ahead of reality: picking "4" in MSFSBA wrote 5, which is really autobrake **3**. The symptom was quiet and mis-attributed for a long time — the ACARS/EICAS reported one setting *lower* than MSFSBA claimed, and landing rollouts consistently ran further than the calculated setting predicted, which had been put down to the aircraft's autobrake modelling rather than to a label bug. The old 7-entry table also left a switch physically at MAX AUTO with **no label at all**. **Never harmonize this table with the 737's `MAIN_AutobrakeSelector`** — the NG selector is RTO/OFF/1/2/3/MAX (six positions, no DISARM; that detent is a 777 thing) and already matches the NG3 SDK. `PMDG737Definition` carries a comment recording the same boundary from the other side: TFM's 737 dict exposes a spurious "disarm" that was most likely cross-pollinated *from* the 777.

**Speed-brake lever — read from `L:switch_498_a`, NEVER the SDK's `FCTL_Speedbrake_Lever` byte (measured live 2026-09-30, MSFS 2024, 777F, hydraulics pressurised).** The L-var runs 0-400 and the combo's Down / Armed / 50 percent / Up picks land exactly on **0 / 200 / 300 / 400**; the SDK byte is a quarter of it, TRUNCATED (0 / 50 / 75 / 100). ARM is EXACT: at 201, 202 and 203 the spoilers are already **34 percent up** while the byte still reads exactly 50, so the byte cannot tell armed from extended and a lever a fraction past ARM was announced "Speed brake armed". The ARM detent carries its own exact tolerance (`PmdgLeverDetent.Tolerance`, 0.25); a lever past it speaks its travel as a percentage of ARM to UP, never below 1 percent. A hardware axis (`AXIS_SPOILER_SET`) parks the lever at 22 for Down and snaps it straight from Down to ARM, so it never rests between them; above ARM it rests anywhere (225, 282, …, with the spoilers 37 / 60 / 72 / 100 percent at 225 / 300 / 340 / 400). The lever is slow: about ten seconds end to end. The SDK header's "25: ARMED" is WRONG. The L-var sweeps through every value in between while the lever moves. The one detent table for both PMDG jets is `Aircraft/PmdgSpeedBrakeLever.cs` (the 737 has five detents on `L:switch_679_73X`, since the NG3 SDK has no lever field; the 777 SDK has no flight-detent click, so it has four). `FCTL_Speedbrake` (the key keeps its old name so the Ctrl+M mute setting survives) is BOTH the announced var and the Control Stand combo — one key, so MainForm's UI-echo suppression matches the pick. Its classifier seeds the combo with the lever's POSITION (`PmdgSpeedBrakeLever.PositionIndex`: the detent within the settle tolerance, DOWN for anything short of ARMED — such a lever is not armed, and the old nearest-detent rule called a 777 lever short of ARM "Armed" — else, past ARM, the nearest DEPLOYED detent, never Armed: the combo is read aloud, and a lever past the exact ARM detent is deployed — live-verified 2026-09-30, a hardware lever resting just past Armed opened the combo on "50 percent"), never an exact-key miss (a blank DropDownList commits row 0, "Down", on the first arrow press). Picks go to the per-detent click events with `MOUSE_FLAG_LEFTSINGLE` (`PmdgMouseFlags.LeftSingle`); the base `EVT_CONTROL_STAND_SPEED_BRAKE_LEVER` is a drag event. A pick made before the PMDG data manager is ready says "Switch not ready", as the flap lever does. The callout on BOTH jets is `PmdgSpeedBrakeCallout`, a trailing-edge SETTLE announcer that reads the same table: every sample restarts a timer (1500 ms on both, because each L-var rides the 1 Hz batch while the lever is still travelling — the 737 was 300 ms until it too began speaking between detents) and only the resting position is spoken ("Speed brake armed"; a lever resting above ARMED between detents reads as a percentage of ARMED to UP, and one resting short of ARMED says "Speed brake down", on both jets). ARM is EXACT on the 737 too (0.25 on `L:switch_679_73X`, measured 2026-09-30 with hydraulics pressurised: spoilers down at 100, 34 / 34 / 37 percent up at 101 / 105 / 137), where its old ±10 band had called 101-110 "armed". Its timer speaks outside MainForm's `announcer.Suppressed` wrap, so it applies both suppressions itself: the Ctrl+M row mutes it, and a SENT pick is remembered for 15 s (`PmdgSpeedBrakeCallout.PickMemoryMs`: the 777's full ten-second travel, one batch and the settle, rounded up — at 10 s a Down-to-Up pick expired before its arrival settled and was read back; live-verified 2026-09-30, a 777 Down-to-Up pick is silent on arrival) so the lever arriving at the picked detent is silent (MainForm's echo window is used up by the first sample of a sweep, so without this a 777 pick spanning two polls was spoken twice). A lever that stops elsewhere, or reaches the picked detent only after those 15 s, is announced. A rest at a detent answers the LATEST pick of it and every pick before it, so overshooting and coming back (Armed, 50 percent, Armed) leaves nothing pending. Only a lever resting AT a detent answers a pick: a 1 Hz batch can deliver a travelling lever as its last sample, so a settle can fall mid-sweep, and a mid-travel sample short of ARM (it reads as Down) must not use up a pick of ARM. Neither jet resets the callout on a context reset, and on both the first sample is the lever's position at load, recorded silently: both levers are L-vars now, and a flight load re-delivers only changed L-vars, so a reset would make the first real move afterwards a silent baseline. (The 777 used to reset, while it read the CDA, whose initial snapshot never reached the callout.) Both jets stop the callout when the pilot switches aircraft (`OnSwitchedAway`, called by `MainForm.SwitchAircraft` on every outgoing definition), so a lever moved just before the switch is never announced over the next aircraft (live-verified 2026-09-30: a lever moved a second before switching aircraft said nothing). Known gap: an open combo does not follow a lever moved by anything else (neither jet sets `SimVarDefinition.RefreshControlWhenDefHandled`, the per-value predicate the iFly lever uses to follow at resting positions only); it re-reads on the next panel build.

**Speed-brake SDK byte `FCTL_Speedbrake_Lever` — an ANALOG 0–100 position, and ⚠️ the SDK header states the wrong value for ARMED (measured 2026-08-29; the First Officer has since moved off the byte, see below).** `PMDG_777X_SDK.h:454` — byte-identical in the 77W, 77ER and 77F packages — says `// Position 0...100  0: DOWN, 25: ARMED, 26...100: DEPLOYED`. The lever never rests at 25. Every detent was clicked on a live 777 at the gate through the stock `K:ROTOR_BRAKE` transport and the field read back, with the owner also moving the lever by hand first to prove the field was live (it tracked them, so it was not stuck):

| Detent | Event | Measured `FCTL_Speedbrake_Lever` |
| --- | --- | --- |
| DOWN | `EVT_CONTROL_STAND_SPEED_BRAKE_LEVER_DOWN` | **0** |
| ARM | `..._ARM` | **50** |
| half deployed | `..._50` | **75** |
| UP (full) | `..._UP` | **100** |

The 75 reading is what SETTLES the scale rather than merely asserting it: PMDG's own event for that detent is named `_50`, and (75 − 50) / 50 = 50 %, which only holds if deployment is measured from an ARM detent at **50**. Do not "correct" the constants back toward the header comment. That 0 / 50 / 75 / 100 table is what the SDK BYTE reads, kept as history: it is the measurement that showed the header is wrong and that the byte is a quarter of the L-var, truncated. The First Officer now reads the lever the same way as the panel — main's `L:switch_498_a` through `Aircraft/PmdgSpeedBrakeLever.B777` (PR #254, via `FirstOfficer/SpeedbrakeLeverState`; the settle announcer and its 0 / 200 / 300 / 400 table are described in the first paragraph above), never the byte — so there is ONE table. `FirstOfficer/Pmdg777SpeedbrakeLever` only wraps it (`DownValue` 0, `ArmedValue` 200, `HalfDeployedValue` 300, `UpValue` 400), pinned by `Pmdg777FlowOrderingTests`.

Two separate traps around this field, both paid for:
- **The First Officer profile read it as a detent INDEX** — every 777 speedbrake condition tested `v > 0.5 && v < 1.5`, which the lever cannot satisfy on ANY reading of the scale. The Landing flow armed the lever and then announced *"Skipping: Speedbrake: ARM"* (leaving the checklist item unfinished for the whole approach); a hand-tick of "Speedbrake: ARMED" reverted and spoke *"Unable to complete"*. (Since 2026-10-09 the line a hand-tick arms is the new Landing section's "Speedbrake: ARM", `LDA_SPEEDBRAKE`; the Landing Checklist's "Speedbrake: ARMED", `LDG_SPEEDBRAKE`, only reads the lever, and both judge it with `Pmdg777SpeedbrakeLever.IsArmed`.) The wrong scale existed only as a comment on `AircraftStateEvaluator.SpeeedbrakeLeverPos` ("0=Down, 1=Armed, 2–7 = deployed positions").
- **The PANEL call-out** is now main's settle announcer (`PmdgSpeedBrakeCallout`, PR #254, described above), reading the same measured scale from `Aircraft/PmdgSpeedBrakeLever`; the old `<=0` / `<=50` / `(v−50)/50` thresholds it replaced were already right against this scale, and a 25-based "fix" must never be applied to either.
- **The First Officer later moved off the byte too (2026-09-30).** After the profile's detent-index test was fixed it still read the byte on the 0 / 50 / 75 / 100 scale, which read a lever at 201-203 (spoilers already 34 percent up) as exactly 50, "armed", and a hardware axis's DOWN at 22 as 5, "not down". It now judges the L-var, as above.

The ARM detent is an ABSOLUTE click position, so re-arming an already-armed lever is a harmless no-op — but clicking ARM over a lever the pilot has RAISED retracts it. So armed is "Already set", and a deployed lever (anything past ARM) is left alone with *"Speedbrake extended, not armed. Left as it is."* — by a flow step through `FlowStep.LeaveAloneWhen`, by a hand-tick through `ChecklistItem.LeaveAloneWhen` — and the executor's `DispatchCoreAsync` never clicks ARM over a lever not known to be DOWN (deployed or unread). The Landing step arms through the verified `SPEEDBRAKE_ARM` pseudo-key (`ArmSpeedbrakeAsync`), which waits up to 8 s for the lever to reach ARM: the lever takes about five seconds from DOWN to ARM, and a flow step's own verify gives a write only 2.6 s (`FlowManager`'s verify window, 2026-10-18: a first read at 600 ms, then one every 200 ms, so it always spans a 1 Hz CDA snapshot; until then it read once at 600 ms, and about half the 777's verified writes that worked were announced "Skipping"). The 737 has the same guard (`PMDG737.SpeedbrakeArmLadder`, through `ExtendedField`).

**Ground power — the event NAMES are reversed against the annunciator array (live-confirmed 2026-08-29).** With both receptacles showing AVAIL (which is what rules out the "pressing an unavailable side is a silent no-op" mis-test), firing `EVT_OH_ELEC_GRD_PWR_**PRIM**_SWITCH` lit `ELEC_annunExtPowr_ON[**1**]` and `..._**SEC**_SWITCH` lit `ELEC_annunExtPowr_ON[**0**]`. This confirms what the panel's `_simpleEventMap` had assumed since e051748d. `FirstOfficer/GroundPowerGate.EventForAnnunciatorIndex` is now the single source of truth and BOTH the panel and the First Officer route through it — the FO profile previously paired each index with the SAME-NAMED event, so all six of its flow steps and three checklist actions gated on one receptacle and pressed the other. ⚠️ Do NOT re-derive the direction from event-id order (SEC = MIN+7 < PRIM = MIN+8); see the "Do NOT re-derive that from event-id order" note below. Same session also killed the "a momentary CDA button only fires once per session" theory: PRIM connected on one press and disconnected on a later one.

**Stabiliser trim is announced in UNITS, not degrees (PR #194).** The 777 SDK publishes no stabiliser-trim position, so the shared base `MON_ElevatorTrim` (stock `ELEVATOR TRIM POSITION`, degrees) is converted by `Aircraft/Pmdg777StabTrim.cs` and spoken through the `PMDG777Definition.DescribeElevatorTrim` override: **units = degrees + 3.75**, snapped to the indicator's quarter-unit graduations, no up/down word, clamped at 0.00 at the bottom and deliberately left raw past 14.50 at the top. The offset is MEASURED (SimVar read at both stops, −3.75° / +10.75° → 0.00–14.50) and checked against the indicator at 3.75, 4.00, 4.50 and 6.00 units; PMDG's `elevator_trim_limit = 11.0 // 4/11 Code controlled` fixes only the travel and cannot tell 3.75 from 4.0 — never "correct" the offset from that comment. The debounce keys on the quantised units, and a new quarter unit is spoken once the degrees are the shared `TrimHysteresis` (0.03°) past its boundary (PR #260) — so a trim resting on a boundary no longer flickers between two units. The 737 keeps its own `ElevTrimTT` path and phrase ("Trim 5.3": one decimal, no unit word) — the two PMDG types currently differ in wording. The SD F-CTL "Elevator Trim" row shows the same units.

**Emergency exit lights (`LTS_EmerLights`) — the guard is real and must be driven (2026-08-01, verified against the real switch via MobiFlight).** `EVT_OH_EMER_EXIT_LIGHT_GUARD` takes 0 = closed, 1 = open. **ARMED is the guard-closed position**; OFF and ON sit outside it, so the guard has to be lifted *before* the switch will move there, and it closes again on the way back to ARMED. An earlier build deliberately never touched the guard, believing that opening it left the switch unusable afterwards — that was wrong, and driving the guard is what makes OFF/ON reachable at all. The **switch** keeps its absolute-target `TransmitClientEvent` (`"#<id>"`) rather than the CDA selector, which only ever steps one detent upward — that is why Armed → Off was unreachable through it.

⚠️ **The two writes travel on DIFFERENT transports** — the guard is a CDA write (`SendPMDGEvent`), the switch a `TransmitClientEvent` — so issued back-to-back they are **not guaranteed to arrive in order**. The switch could reach PMDG before the guard had opened, the write was refused, and the pilot had to pick the position TWICE. An **80 ms settle gap** orders them reliably while still feeling immediate (the generic `SendGuardedSet` uses 150 ms). **Do NOT drop it to zero.** A MobiFlight profile never shows this because both of its writes take the same path.

Two consequences of that gap, both load-bearing:
- **The sequence must be serialized** (`_emerLightsGate`). A screen-reader user arrowing through the combo commits one set *per arrow key*, so a second sequence starts while the first is still mid-gap. Interleaved, the Armed sequence's guard-CLOSE lands between the Off sequence's guard-OPEN and its switch write, PMDG refuses the switch, and the combo ends up displaying a position the aircraft never reached — reproducing the very "pick it twice" symptom the gap exists to prevent. This is cooperative interleaving across `await`s on ONE thread, not a data race: the gate is needed even though every write stays on the UI thread. A burst also collapses to its LAST selection (`_emerLightsRequest`) — superseded picks are skipped **whole**, never half-applied, so the guard can never be left open over a closed position. Since 2026-10-18 the First Officer's own sequence (`AircraftActionExecutor.SetEmerExitLightsAsync`: the Power Up and Secure flows and their lines) takes the same gate through `EmerLightsSequenceGate`, inside its own dispatch gate, and reads the switch position only once inside, so a combo pick never lands between its guard and switch writes, nor the reverse. It takes no part in the latest-selection collapse: the gate serves waiters first come, first served, so the later of the two finishes last.
- **Fire the sequence as a plain `async` local function, never `Task.Run`.** `HandleUIVariableSet` is only ever called on the UI thread and there is no `ConfigureAwait(false)`, so the awaits resume there and every SimConnect call stays on the UI thread, matching the generic `SendPMDGGuardedSet` path. `Task.Run` would push `SimConnectManager.SendEvent` onto a pool thread, where its lazy `"#<id>"` registration races the UI thread on an **unlocked** `eventIds` dictionary ([SIM-20]).

**The Landing flow's last step confirms "Landing Gear: DOWN" from the physical gear, not the lever alone (lever-only until 2026-09-25).** `LANDING_CL`'s `LDG_GEAR` ("Landing Gear: DOWN") had no step behind it, so running the Landing flow before lowering the gear latched the line complete over gear still up. `LD_GEAR_DOWN_CHECK` closes that: a read-only `WaitForCondition` (it never writes the lever) that is the LAST step of the flow, waiting up to 20 s and — on a timeout — announcing skipped and FailurePolicy.Skip rather than stopping the flow, which is what keeps `LDG_GEAR` out of `MarkGroupComplete`'s latch so the checklist line keeps mirroring the real gear instead of reading complete over gear that never came down. **The 777 SDK exposes no gear-indication light fields at all** — `GEAR_Lever` is the only gear signal the CDA struct carries — so the 777's "three green" is composed instead from the lever AND the stock `GEAR LEFT/CENTER/RIGHT POSITION` SimVars (percent, the same ones the System Display's Gear page reads): `Pmdg777GearConfirmation` publishes synthetic `FO_GEAR_DOWN` = lever DOWN and all three legs ≥ 99 %, and `FO_GEAR_UP` = lever UP and all three legs ≤ 1 % — the Gear page's own `GearPos` thresholds, so the checklist never calls gear "down" that the Gear page calls "in transit". Both are NaN while the lever (no CDA snapshot yet) or any leg (no push yet) is unknown, so an unread value can never read "confirmed". Both the checks (`LD_GEAR_DOWN_CHECK`, `ATKOF_GEAR_UP_CHECK`) and the checklist lines (`LDG_GEAR`, `ATKOF_GEAR`) read these fields; the action group's "Gear: UP" (`ATKO_GEAR_UP`) stays on the LEVER its write moves. **The feed:** `FirstOfficerForm`'s 1 Hz timer calls `SimConnectManager.RequestFOGearPositions()` — for the 777 profile only (`_stateEval is FirstOfficer.AircraftStateEvaluator`), so no other aircraft's SimConnect traffic changes — which re-registers ONE temporary data definition (`DEF_FO_GEAR_POSITIONS` = 385, three FLOAT64s in a `DoubleValueTriple`) and issues a `PERIOD.ONCE` under `REQUEST_FO_GEAR_POSITIONS` = 385, exactly like the FO engine-N2 and center-fuel requests beside it. The dispatcher raises `SimVarUpdated` as `FO_GEAR_LEFT_POS`/`FO_GEAR_CENTER_POS`/`FO_GEAR_RIGHT_POS` (never announced), and `OnSimVarUpdated` pushes each into `AircraftStateEvaluator.SetGearPosition`. It costs one data definition, and it is not the System Display's own `GEAR x POSITION` variable defs (those are OnRequest vars registered by `PMDG777Definition`, requested only while the Gear page is shown) — a separate FO-private definition, as the N2 feed already is. **Since 2026-10-09 the gear check is the last of four Landing steps:** `LD_SPEEDBRAKE_ARM` (completes the new Landing section's "Speedbrake: ARM", `LDA_SPEEDBRAKE`, and links the Landing Checklist's `LDG_SPEEDBRAKE`), `LD_MISSED` (the Captain's "Set the missed approach altitude" reminder, which delivers the section's `LDA_MISSED`), `LD_FLAPS_CHECK` (the landing flap-lever check, completing `LDG_FLAPS`) and then this one. The flow's related groups are `LANDING` (the section) and `LANDING_CL`, so it latches both.

**Cockpit Prep opens with a read-only power-up check, on a third synthetic (2026-10-09).** The five Preflight lines the Electrical Power Up flow sets — "Battery switch: ON" (`PF_BATTERY`), "ADIRU switch: ON" (`PF_ADIRU`), "Demand pump selectors: OFF" (`PF_DEMAND_PUMPS_OFF`), "Navigation light: ON" (`PF_NAV_LIGHTS`) and "Landing gear lever: DOWN" (`PF_GEAR_DOWN`) — had no step in the Cockpit Prep flow, so a finished run latched them over whatever the switches read (FO-7). `CP_POWER_UP_CHECK`, the flow's FIRST step (PMDG's preflight opens with the battery, and the Preflight group lists the battery and ADIRU lines first), is a read-only `WaitForCondition`: it never writes, waits up to 20 s and, on a timeout, is heard skipped (`FailurePolicy.Skip`). It waits on the synthetic `FO_POWER_UP_OK`, which the pure helper `Pmdg777PowerUpCheck` computes for the evaluator (the seam `Pmdg777GearConfirmation` uses): 1 when all five lines' own conditions hold, 0 when one does not, NaN while any input is unread, so an unread switch keeps the check waiting. Its inputs are exactly the five lines' own fields and conditions — `ELEC_Battery_Sw_ON`, `ADIRU_Sw_On`, the four demand-pump selectors (`HYD_DemandElecPump_Selector_0/1` and `HYD_DemandAirPump_Selector_0/1`, all OFF), `LTS_NAV_Sw_ON` and `GEAR_Lever` (DOWN) — which `Pmdg777PowerUpCheckTests` pins. The one step completes `PF_BATTERY` and names the other four in `FlowStep.AlsoCompletesChecklistItemIds`, so a timeout keeps all five out of the latch and each line then follows its own switch; `IsPowerUpConfirmed()` reads "Already set" when the state is already confirmed, never over unread data. No checklist line reads `FO_POWER_UP_OK`: only the check and `IsPowerUpConfirmed()` do. Cockpit Prep's other new step is `CP_FUEL_PUMPS_OFF`: PMDG's Preflight runs "CROSSFEED switches OFF" and then "FUEL PUMP switches OFF", so the flow writes the six pumps OFF right after `CP_XFEED_OFF` (Shutdown's write, wing pumps before centre pumps, FOB-12) and completes `PF_FUEL_PUMPS_OFF`, reading the last pump written (the right centre pump, `FUEL_PumpCtr_Sw_1`) back after the write, so a write that did not take is heard skipped and keeps the line out of the latch (the other five pumps are not read back); it says "Already set" only when `AreAllFuelPumpsOff()` reads all six OFF (NaN-safe, `IsPosition`).

**The After Takeoff flow's "Gear: UP" and "Landing Gear: UP" lines are now backed by two DIFFERENT steps, matching the Landing flow's shape above.** `ATKOF_GEAR_UP` — the step that WRITES `EVT_GEAR_LEVER` — used to complete the CHECKLIST item `ATKOF_GEAR` directly off its own 600 ms verify; that meant a failed write was excluded from the checklist line (via `FlowManager`'s `_unfinishedChecklistItemIds`) but NOT from the flow's own `AFTER_TAKEOFF` action group, whose `ATKO_GEAR_UP` item was still ticked complete by `MarkGroupComplete`'s blanket sweep at flow completion — a lever that never moved could still read "Gear: UP" complete. `ATKOF_GEAR_UP` now completes its OWN group's `ATKO_GEAR_UP` instead, so a failed write is excluded there too. A new read-only step, `ATKOF_GEAR_UP_CHECK` — the same shape as `LD_GEAR_DOWN_CHECK`, a 20 s `WaitForCondition` on `GEAR_Lever` under `FailurePolicy.Skip` — is appended as the LAST step of the flow and completes the checklist's `ATKOF_GEAR` on a genuine confirmed read rather than the write's own quick verify — since 2026-09-25 the gear physically up (`FO_GEAR_UP`: lever UP and all three legs retracted, see the Landing paragraph above), not just the lever. Two accepted side effects, each a narrow, documented exception in `Pmdg777FlowOrderingTests`: `AFTER_TKOF_CL` lists `ATKOF_GEAR` before `ATKOF_FLAPS`, but the flow now ticks `ATKOF_FLAPS` first (the flaps check settles well before the gear's confirmation, which stays the LAST step); and, since 2026-10-09, `LANDING_CL` lists `LDG_GEAR` before `LDG_FLAPS`, but the Landing flow ticks `LDG_FLAPS` first, because its flap-lever check `LD_FLAPS_CHECK` sits before the gear check, which stays the LAST step (FO-13).

**The After Takeoff flaps lines have the same two-step shape as the gear (2026-09-25).** `ATKOF_FLAPS_UP` — the step that WRITES `EVT_CONTROL_STAND_FLAPS_LEVER_0` — used to complete the checklist's `ATKOF_FLAPS`, which left the action group's own "Flaps: UP" (`ATKO_FLAPS_UP`) with no step behind it, so `MarkGroupComplete` latched it complete even when the write was skipped over a lever that never moved. The write now completes `ATKO_FLAPS_UP`, and a new read-only `ATKOF_FLAPS_UP_CHECK` (20 s `WaitForCondition`, Skip, never writes) completes `ATKOF_FLAPS`, placed after the flaps write and before the gear check. It reads the flap LEVER at UP — the checklist line's own condition — not the physical flap angle, because a retraction from takeoff flap outlasts any sensible wait and the check would routinely time out. After a good write it passes at once; after a failed one the pilot has 20 s to move the lever before it is skipped aloud and both lines stay live. `AreFlapsUp()` is now NaN-safe (`IsPosition`): the old `(int)Math.Round(v) == 0` read "flaps up" before the first CDA snapshot, because .NET's saturating float-to-int conversion turns NaN into 0. The read-only check is labelled "Flap lever: UP" (what it reads, in the gear checks' "Noun: STATE" form), not "Flaps: UP" — sharing the write's label made a failed write followed by a timed-out check say "Skipping: Flaps: UP" twice.

**Every First Officer write step names the checklist line it sets (2026-09-25).** A finished flow latches every line of its groups except those a SKIPPED step links, and only about a quarter of the 777's write steps linked anything — the Electrical Power Up flow's verified nav-lights (`EPU_NAV_LIGHTS`) and ADIRU (`EPU_ADIRU`) writes, the unverified storm-lights (`EPU_STORM_OFF`) and seat-belt (`CP_SEAT_BELTS`, verified since 2026-10-09) writes and 90-odd others were latched complete over a failed write. The audit also found — and the same pass FIXED — the Before Taxi takeoff-flaps steps naming 737-style detent INDICES: flaps 5 / 15 / 20 wrote `EVT_CONTROL_STAND_FLAPS_LEVER_2/3/4`, which the 777 event table does not have (it is keyed by DEGREES: `_0/_1/_5/_15/_20/_25/_30`), so the lever never moved and the step was announced skipped, and "Flaps: 25" wrote `_5` (flaps 5). They now write the degree events, as `SetFlapsPosition` always did; and the Before Takeoff Checklist's "Flaps: Set for takeoff" accepts lever 2–4, flaps 5, 15 or 20 (it stopped at 3 and never ticked for a flaps 20 takeoff; it accepted lever 1 until 2026-10-18, though flaps 1 is no 777 takeoff setting). Pinned by `Pmdg777TakeoffFlapsTests` and `Every_written_event_is_in_the_777_event_table`.

**The four flap-lever checks, in detail (2026-10-09).** The flaps lines four flows latch — Before Taxi "Flap lever: Set for takeoff" (`BT_FLAPS`), Before Takeoff "Flaps: Set for takeoff" (`BTKOF_FLAPS`), Landing "Flaps: Set for landing" (`LDG_FLAPS`) and Shutdown "Flaps: UP" (`SDCL_FLAPS_UP`) — had no step behind them, so a finished flow latched them over whatever the lever read (FO-7). The takeoff and landing checks, their "Already set" (`AreFlapsForTakeoff()`, `AreFlapsForLanding()`) and the read-back lines share one pair of static range predicates, `AircraftStateEvaluator.IsTakeoffFlapLever` and `IsLandingFlapLever`, so those three cannot disagree; `AreFlapsForTakeoff()` used to stop at lever 3, as the line once did. UP shares nothing: `SD_FLAPS_UP_CHECK` and `SDCL_FLAPS_UP` each spell out `v < 0.5`, and the check's "Already set", `AreFlapsUp()`, uses `IsPosition(…, 0)`; `Pmdg777FlapLeverCheckTests` pins each check to its line at every detent, and an unread lever is "not up" in all three. `BT_FLAPS_CHECK` accepts any takeoff detent, 2-4, not necessarily the planned one, and the Before Taxi line itself has no state, so that check borrows the Before Takeoff line's range. The five Before Taxi flap WRITES (`BT_FLAPS_1`, `BT_FLAPS_5`, `BT_FLAPS_15`, `BT_FLAPS_20`, `BT_FLAPS_25`) stay unlinked on purpose: they are gated on the SimBrief plan, so the four not planned skip as "Already set" and would tick `BT_FLAPS` whatever the planned one did (FO-6), and `BT_FLAPS_CHECK` completes the line instead. A flaps-25 takeoff plan never meets the 2-4 range (the owner kept it, 2026-10-09), nor does a flaps-1 plan (`BT_FLAPS_1`), so on such a plan both takeoff checks time out and both takeoff-flap lines ("Flap lever: Set for takeoff" and "Flaps: Set for takeoff") stay open. Pinned by `Pmdg777FlapLeverCheckTests` and `Pmdg777FlowOrderingTests`.

**CDU array index convention:** The PMDG SDK uses `0=Captain(L), 1=F/O(R), 2=Observer(C)` for ALL crew-position arrays — including CDU data areas (`PMDG_777X_CDU_0/1/2`), `CDU_BrtKnob[3]`, and all `CDU_annun*[3]` fields. The CDU form dropdown is ordered Left/Center/Right (0/1/2), which does NOT match the SDK ordering. `PMDG777CDUForm` uses a `DataCDUIndex` computed property to remap dropdown index to SDK index (`1→2, 2→1`). The event prefix switch (`EVT_CDU_L_/C_/R_`) uses the raw dropdown index and is correct as-is.

**Hydraulic pump array index — an index is a SLOT, never a side NUMBER.** The same `0=Left, 1=Right, 2=Center` ordering the CDU convention above records (sides first, center last) is what decides what a hydraulic pump array slot means. On the 777's two-element pump arrays `[0]`/`[1]` is Left/Right **only where the pair is a pair of sides** — the engine primaries (`HYD_PrimaryEngPump_Sw_ON`) and the electric demands (`HYD_DemandElecPump_Selector`). The other two pairs are not sides at all: the **Center** system carries BOTH electric primaries (`HYD_PrimaryElecPump_Sw_ON`) and BOTH air demand pumps (`HYD_DemandAirPump_Selector`), so those are spoken "Center 1"/"Center 2". Labels that read "1"/"2" named four center pumps after sides they are not on — a blind pilot has no placard to correct the impression.

**Where the convention comes from (checked against `PMDG_777X_SDK.h`, 2026-08).** The four `HYD_*Pump*` arrays are declared with **no index comment** — only the selector value meanings — so the slot meaning is read off the convention the header states everywhere it *does* annotate a pair: `FCTL_WingHydValve_Sw_SHUT_OFF[3]` / `FCTL_TailHydValve_Sw_SHUT_OFF[3]` `// left/right/center`, `LTS_LandingLights_Sw_ON[3]` `// Left/Right/Nose`, `COMM_SelectedMic[3]` `// 0=capt, 1=F/O, 2=observer`, and every annotated two-element pair (`AIR_Pack_Sw_AUTO`, `AIR_TrimAir_Sw_On`, `ENG_EECMode_Sw_NORM`, `ENG_Start_Selector`, `FUEL_PumpFwd_Sw`, `FUEL_JettisonNozle_Sw`, `AIR_IsolationValve_Sw`, `AIR_EngBleedAir_Sw_AUTO`) reading `// left / right`. Sides first, centre last, without exception in the header. Two related renames are directly SDK-annotated rather than inferred: `FUEL_PumpCtr_Sw[2]` / `FUEL_annunLOWPRESS_Ctr[2]` are `// ctr left / ctr right` (so those are Center Left/Center Right, **not** Center 1/2), and `ICE_WindowHeat_Sw_ON[4]` / `ICE_annunWindowHeatINOP[4]` are `// L-Side/L-Fwd/R-Fwd/R-Side`. Note `ELEC_ExtPwrSw[2]` is `// primary/secondary` — an unannotated two-element array is not *automatically* a side pair, so check the header before assuming.

**Do NOT re-derive that from event-id order.** Event ids order *events*, not array slots, and the SDK header itself disproves the equivalence: `FCTL_WingHydValve_Sw_SHUT_OFF[3]` is annotated `left/right/center` while its ids run `WING_L +60 < WING_C +63 < WING_R +66`. `ELEC_ExtPwr*` has the event **names** swapped against the array outright (`_simpleEventMap` says so in place). The eight pump ids do happen to trace the panel rows (`DEMAND_ELEC1 +35, AIR1 +36, AIR2 +37, DEMAND_ELEC2 +38`, then `ENG1 +39, ELEC1 +40, ELEC2 +41, ENG2 +42`; `THIRD_PARTY_EVENT_ID_MIN` 69632), but that is corroboration, not the rule — and it is 8 of the 22 `EVT_OH_HYD_*` events, the excluded `RAM_AIR`/`VLV_PWR` ones being exactly those that break it. Pinned by `tests/MSFSBlindAssist.Tests/Pmdg777HydraulicPumpLabelTests.cs`; the dictionary keys keep their `_1`/`_2` suffixes because Ctrl+M persists a mute under the key and there is no rename migration.

**⚠️ Still to confirm in-sim:** the C1/C2 **order within each center pair** is the one part inferred rather than corroborated — the header annotates neither array, and the NG3 SDK inverts exactly this array on the 737 (`HYD_PumpSw_elec`: `[0]`=pump 2, forcing a compensating display swap). What the 737 inversion was *spotted by* is absent here, which is mild reassurance rather than proof: there `ELEC2` carries the lower id, while on the 777 `ELEC1 +40 < ELEC2 +41` runs in order. Confirm that `HYD_PrimElecPump_1` moves the **C1** electric primary (not C2), and likewise `HYD_DemandAirPump_1` and C1 AIR. **CDU interaction:** CDU buttons must send parameter 1 (pressed) via CDA; parameter 0 also registers as a press (not a release). The exception is FMCCOMM and HOLD (`PMDG777CDUForm.SendCDUKey`), which go through `TransmitClientEvent` with `MOUSE_FLAG_LEFTSINGLE`: the CDA path never releases, and the SDK will not re-trigger the same page key without a release edge, so a second press after navigating away was silently dead (issue #46, regressed once by commit f55d157). Text entry sends one character at a time with 350ms delay; repeated characters need an extra 400ms for the CDU to distinguish separate presses. CDU display uses color and font-size data to detect toggle selections (non-white color or non-small font = selected, marked with `X`). Toggle detection only applies to rows with adjacent `<>` (mapped from 0xA1/0xA2 arrow symbols). Scratchpad announcements are suppressed during text entry and clearing (`_typingInProgress`/`_clearingInProgress` flags); `_previousScratchpad` is only updated when the announcement actually fires. CLR uses `_clearingInProgress` to suppress intermediate states and only announces "Cleared" once the scratchpad is empty.

**Autopilot window (Ctrl+P):** Input-mode Ctrl+P opens the engage-cluster window: AP L/R, both flight directors, A/T Arm L/R, A/T, Approach, LOC, the disengage bar, the bank limit selector, and the A/P and A/T disconnects. Suppress button push state (_Sw_Pushed) announcements via RenderAsButton check. Annunciator lights announce both on and off states. For variables needing cache but no auto-announcement, set `IsAnnounced = true` and return `true` from ProcessSimVarUpdate to suppress.

**System Display synoptic read-outs (`PMDG777Definition.SystemDisplay.cs`, partial class).** A read-only status box in the **Displays → System Display** panel, organized like the real Display Select Panel synoptic pages. A single combo (`PMDG777_SD_PAGE`, `SdPageKey`) selects one of 9 pages (0 Engine, 1 Status, 2 Electrical, 3 Hydraulics, 4 Fuel, 5 Air, 6 Doors, 7 Gear, 8 Flight Controls); selecting a page writes a private L:var (`PMDG777_MSFSBA_SD_PAGE`), and `RefreshSystemDisplayAsync` repaints the box. **HYBRID data sourcing** — each row is `(label, var, fmt)`: most values are **stock SimVars** read from the SimConnect cache (`GetCachedVariableValue` — oil temp/press/qty, EGT, N1/N2, fuel flow, hydraulic pressure/reservoir, electrical voltages, cabin alt/rate/diff, CG%MAC, gear, control surfaces/trim), while a small set of PMDG-SDK-broadcast fields (`_sdPmdgVars`: feed-tank fuel quantities, duct pressures, brake accumulator, IRS aligned, APU running, door states) are read **live** via `simConnect.PMDGDataManager.GetFieldValue(name)` (with `_N` array-index suffix), because OnRequest PMDGVars never land in the SimConnect cache. The box rides the GENERIC MainForm `_DISPLAY_` status-box infra (a navigable ListBox with a 1 s live auto-refresh, F5 for an immediate one, + coalesced in-place row reconcile — see "Status-display boxes refresh live") — `OnDisplayPanelShown` triggers a refresh when the panel is shown; `TryGetDisplayOverride(SdPageKey, …)` renders the page name + content. **Documented gaps not in the SDK** (so NOT covered): oxygen, water, brake temp, tire pressure, APU N/EGT/load, generator load amps, EICAS alert message TEXT (WASM-only), wear/cycles, chrono elapsed time. **Formatting (2026-06-21):** the shared `Lbs`/`Pph` formatters show weight/fuel in BOTH units — "`<lb>` pounds (`<kg>` kg)" / "… pounds per hour (… kg per hour)" (1 lb = 0.45359237 kg) — covering every pounds field on every page (Fuel Flow, Fuel Used, Gross Weight, Total Fuel, per-tank). The continuous readouts carry ONE decimal place (`{v:0.0}` on percent / volts / psi / degrees-C) so sub-unit changes are visible — integer rounding had made live values look frozen (a reservoir at 96.9% read a static "97"). Weight/fuel stay whole (sub-unit is noise on a 6-digit number); N1/N2, vibration, flaps, diff-pressure already carried a decimal. The row formatters are `private static` methods (not per-call local funcs) so the compiler caches the method-group delegates — the auto-refresh tick and the 9-page registration loop don't re-allocate them; `TryGetDisplayOverride` renders the page name from `_sdPage` (the same source `_sdContent` was composed from), NOT the cached L:var `value`, which lags the calc-write/read-back and would briefly show the wrong header over fresh content. **PMDG-broadcast reads are gated on `IPMDGDataManager.IsReady`** — until the first CDA snapshot arrives `GetFieldValue` returns `0.0` for EVERY field (interface contract), which `DoorState(0)="open"` would render as "every door open" / "0 lb"; not-ready now renders `--` (matching the stock-SimVar cache-miss path). **MainForm's PMDG panel-populate loop only force-reads `Type == PMDGVar` controls** (`MainForm.cs` ~6598) — reading a non-PMDG control (the SD page combo is an `LVar`) via `GetFieldValue` returns the `0.0` "unknown field" sentinel, which used to force-reset the combo to page 0 on every panel re-show; non-PMDG controls populate via combo-creation + continuous monitoring instead.

## Options.ini requirement

Each installed variant keeps its own `777_Options.ini` in its package's `work` folder, in the same four
storage trees as the 737 (see docs/pmdg-737.md, "Options.ini requirement"; on the owner's FS2024
Store install, `...\LocalState\WASM\MSFS2024\pmdg-aircraft-77x\work\777_Options.ini`, all four
variants). The package folders are `pmdg-aircraft-77er` (777-200ER), `-77l` (777-200LR), `-77f`
(777F) and `-77w` (777-300ER). The 777 needs the center CDU line as well, because
`PMDG777DataManager` maps all three CDU areas:

```ini
[SDK]
EnableDataBroadcast=1
EnableCDUBroadcast.0=1
EnableCDUBroadcast.1=1
EnableCDUBroadcast.2=1
```

On the owner's install PMDG keeps this block as the file's last lines, with no blank line after it,
and the broadcast works. The pilot adds it; MSFSBA never edits the file ([PSDK-1]). Picking the PMDG
777 from the Aircraft menu, or starting MSFSBA with it as the selected profile, opens the PMDG 777 SDK
setup dialog while any installed variant's file lacks the lines or none exists yet ([PSDK-2]).


## AI display reads (Alt+P / Alt+N / Alt+E / Alt+S / Alt+I)

Five reads, a table of `Aircraft/AiDisplayRead.cs` in `Aircraft/Pmdg777DisplayReads.cs`,
dispatched by `BaseAircraftDefinition.HandleHotkeyAction` from the definition's `DisplayReads`
override. The app moves the simulator camera to the view that frames the display, captures with
`PrintWindow`, puts the camera back, and only then makes the AI call.

| Key | Display | Instrument view |
|---|---|---|
| Alt+P | PFD | view 8 (index 7) |
| Alt+N | ND | view 8 (index 7) |
| Alt+E | Upper EICAS | view 2 (index 1) |
| Alt+S | Lower display | view 2 (index 1) |
| Alt+I | ISFD (standby) | view 2 (index 1) |

**Measured on the live aircraft** (2026-09-22, MSFS 2024 1.8.16.0, PMDG 777F) by writing each
index and capturing the frame. View 8 frames the captain's PFD and ND large; view 2 frames the
whole forward panel — the ISFD, the upper EICAS, the lower display, both CDUs and the first
officer's displays.

The titles happen to be honest on this airframe. That is **not** a reason to trust them next
time: on the PMDG 737 the camera titled "PFD" frames the ND as well, and on the Fenix A320 v2 the
live index was not even the camera's position in the file (v3 restored the missing camera, so it is again). Measure, then write the number down.

⚠️ **The camera list is in `common/config/cameras.cfg`** and the per-livery preset is a 48-byte
`[MODULAR_MERGE] auto = true` stub — the same layout as the PMDG 737-900 and the OPPOSITE of the
737-600/-700/-800, where `common` is the stub. Read whichever of the two is not a stub.
`CAMERA VIEW TYPE AND INDEX MAX:2` reads 10 for 10 instrument views, 0..9 — a COUNT, not a top
index, the same as the Fenix.

**Why the standby does not use the captain-panel view.** The ISFD is in that frame, but hard
against the right edge, so a narrower window would clip it. In the forward-panel view it sits well
inside and crops the same size. Same reasoning as the PMDG 737 and the iFly.

**Alt+S reads the lower display**, added 2026-09-22 after the camera work, closing the gap this
doc previously recorded as needing its own measurement. It shares the forward-panel view with the
upper EICAS and the ISFD, so those three prompts exclude each other by name. The display is
SELECTABLE — secondary engine indications, one of the synoptics (STATUS, ELEC, HYD, FUEL, AIR,
DOOR, GEAR, FCTL), or a navigation display — so `DisplayType.LowerDisplay777` identifies which
page is present before reporting it, the way the 737's lower-DU and the MD-11's SD prompts do.
It is a genuinely different surface from the 737's lower DU, which is why it got its own prompt
rather than a copy of that one.

⚠️ **What the stock SimVars do and do not give you here.** Measured live on the 777F with the
engines at idle, against the lower display showing its secondary engine page: `TURB ENG N2` reads
71.16 % against a displayed 71.1, `TURB ENG N1` 22.32 against 22.3, and
`GENERAL ENG OIL TEMPERATURE` 70.5 °C against a displayed 69 — all real. But
`GENERAL ENG OIL PRESSURE` reads 58.1 psi against a displayed 32/33, `ENG OIL QUANTITY` a flat
100 % against 22/21, and `ENG VIBRATION` 2.12 against 0.6/0.5 — those three are the stock engine
model's, not PMDG's. The 777's CDA struct carries none of them. So oil pressure, oil quantity and
vibration are reachable ONLY through this read; N2 and oil temperature could also be ordinary
panel rows, which is a separate capability with its own in-sim test plan and deliberately not part
of this change.
