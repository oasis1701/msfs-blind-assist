# PMDG 777

> **Read this when:** working on the PMDG 777 (switch/CDA patterns, CDU, radios, System Display).

### PMDG 777 Specific Patterns

**Switch control:** Use CDA (SetClientData) with direct position values for most switches.
- Two-position toggles: `SendPMDGEvent(eventName, eventId, targetPosition)` where targetPosition is 0 or 1
- Multi-position selectors: same, with the target position index
- Momentary buttons: `SendPMDGEvent(eventName, eventId, 1)` — parameter 1 = pressed, 0 = no-op
- Continuous knobs (brightness, temperature, EFIS baro/mins): **cannot be controlled via the SDK event with a position param** — do not add to panels via that path. **EXCEPTION (2026-06): knobs whose cockpit-model L:var IS the pilot input are fully settable by writing that named L:var** — e.g. the shoulder heaters (`L:LEFT/RIGHT_SHOULDER_HEATER`, 0–100; the SDK struct field `AIR_ShoulderHeaterKnob` follows the write, live-verified). Find the L:var in `77W_Cockpit_Behavior.xml`; see the Cockpit furniture section below.
- **Temperature controls (Air Conditioning panel, 2026-07, live-verified on BOTH variants):** flight deck + cabin temp selectors are continuous knobs on that L:var exception — stepped combos writing `L:FLTDeckTempKnob` / `L:CABINTempKnob`, and the two knobs have **DIFFERENT scales**: the FLIGHT DECK knob is 0–75 mapping ×0.8 onto SDK `AIR_TempSelector[0]` 0–60 Cold→Warm (write 60 → SDK 48, verified; MAN detent: write 87 → SDK 70, verified), but the CABIN knob is **0–60 mapping 1:1** onto `AIR_TempSelector[1]` (its cockpit XML clamps at 60; live-verified 15→15, 60→60 — and an out-of-range external write passes through UNCLAMPED, 75→SDK 75, so never reuse the flt-deck 0–75 steps on the cabin knob). The **AFT + BULK 3-position cargo selectors** (`AIR_CargoTemp_Selector[2]`, 0=Off/1=Low/2=High — the SDK header says aft/bulk, NOT fwd/aft) work on BOTH variants via the normal CDA event path. The **four continuous cargo knobs** (`L:MAINDECK{FWD,AFT}TempKnob` / `L:LOWERDECK{FWD,AFT}TempKnob` → SDK `AIR_CargoTemp_MainDeck*/Lower*_Sel`) are functional on the **77F freighter only**, with a DIFFERENT scale from the flight deck knob: **1:1 onto SDK 0–60** (55→55 verified), and the lower-aft knob takes the bulk-heat detent values DIRECTLY: **67 = HEAT HIGH, 70 = HEAT OFF, 73 = HEAT LOW** (all live-verified on the 77F). **Variant gating** (`HandleUIVariableSet`, keyed on the CDA **`AircraftModel`** field — SDK: 1 -200, 2 -200ER, 3 -300, 4 -200LR, 5 777F, 6 -300ER): the cargo knobs announce "freighter only" on any known passenger model, and the CABIN knob announces "not functional on the freighter" on model 5 (dead both ways — the L:var moves the visual but PMDG's systems never sample it; live-verified on 77W + 77F; every variant's cockpit behavior XML carries all six knobs, so the write always "sticks" even where dead). **Never gate 777 variants on `CurrentAircraftIcaoType`**: the 777F and the pax 777-200LR both declare `icao_type_designator B77L` (verified in the installed `pmdg-aircraft-77f` and `pmdg-aircraft-77l` packages), and livery TITLEs are freeform — the CDA `AircraftModel` field is the only reliable variant id. Unknown model (CDA not ready) falls through to the normal write; a refused set also re-requests the var so the combo snaps back to the real value. The wrong-variant knobs are additionally **hidden from the Air Conditioning panel entirely** (`IsPanelControlVisible` override — the generic hook lives on `BaseAircraftDefinition` and is re-evaluated on every panel build, so late variant detection self-corrects on the next panel open); the set-time guards remain as the backstop for a panel built before the first CDA snapshot. **No actual °C temperature values exist anywhere in the SDK** (only selector positions) — cabin/cargo temps on the EICAS AIR synoptic are pixel-only, same class as the MD-11 FMA. The 77W and 77F SDK headers are byte-identical (one shared 777X SDK).
- **Fuel control levers:** Exception — use CDA with **inverted** parameter (1=Cutoff, 0=Run). See special case in HandleUIVariableSet.
- **Ground power switches (ELEC_ExtPwr):** Momentary push buttons — send parameter 1 regardless of target. See special case in HandleUIVariableSet.

**Autobrake selector — EIGHT detents, and the 777 has a DISARM the 737 does not (fixed 2026-08-01, live-verified).** `BRAKES_AutobrakeSelector` runs `0 RTO / 1 OFF / 2 DISARM / 3 "1" / 4 "2" / 5 "3" / 6 "4" / 7 MAX AUTO` (SDK `PMDG_777X_SDK.h` line 272; the SDK comment abbreviates after index 3, but **index 7 exists and is the top detent** — every position was walked against the hardware through a MobiFlight profile). The label table had been **missing DISARM**, so every entry from index 2 up sat one step ahead of reality: picking "4" in MSFSBA wrote 5, which is really autobrake **3**. The symptom was quiet and mis-attributed for a long time — the ACARS/EICAS reported one setting *lower* than MSFSBA claimed, and landing rollouts consistently ran further than the calculated setting predicted, which had been put down to the aircraft's autobrake modelling rather than to a label bug. The old 7-entry table also left a switch physically at MAX AUTO with **no label at all**. **Never harmonize this table with the 737's `MAIN_AutobrakeSelector`** — the NG selector is RTO/OFF/1/2/3/MAX (six positions, no DISARM; that detent is a 777 thing) and already matches the NG3 SDK. `PMDG737Definition` carries a comment recording the same boundary from the other side: TFM's 737 dict exposes a spurious "disarm" that was most likely cross-pollinated *from* the 777.

**Stabiliser trim is announced in UNITS, not degrees (PR #194).** The 777 SDK publishes no stabiliser-trim position, so the shared base `MON_ElevatorTrim` (stock `ELEVATOR TRIM POSITION`, degrees) is converted by `Aircraft/Pmdg777StabTrim.cs` and spoken through the `PMDG777Definition.DescribeElevatorTrim` override: **units = degrees + 3.75**, snapped to the indicator's quarter-unit graduations, no up/down word, clamped at 0.00 at the bottom and deliberately left raw past 14.50 at the top. The offset is MEASURED (SimVar read at both stops, −3.75° / +10.75° → 0.00–14.50) and checked against the indicator at 3.75, 4.00, 4.50 and 6.00 units; PMDG's `elevator_trim_limit = 11.0 // 4/11 Code controlled` fixes only the travel and cannot tell 3.75 from 4.0 — never "correct" the offset from that comment. The debounce keys on the quantised units, so ANY degree change that crosses a quarter-unit boundary is a new callout (there is no deadband). The 737 keeps its own `ElevTrimTT` path and phrase ("Trim 5.3": one decimal, no unit word) — the two PMDG types currently differ in wording. The SD F-CTL "Elevator Trim" row shows the same units.

**Emergency exit lights (`LTS_EmerLights`) — the guard is real and must be driven (2026-08-01, verified against the real switch via MobiFlight).** `EVT_OH_EMER_EXIT_LIGHT_GUARD` takes 0 = closed, 1 = open. **ARMED is the guard-closed position**; OFF and ON sit outside it, so the guard has to be lifted *before* the switch will move there, and it closes again on the way back to ARMED. An earlier build deliberately never touched the guard, believing that opening it left the switch unusable afterwards — that was wrong, and driving the guard is what makes OFF/ON reachable at all. The **switch** keeps its absolute-target `TransmitClientEvent` (`"#<id>"`) rather than the CDA selector, which only ever steps one detent upward — that is why Armed → Off was unreachable through it.

⚠️ **The two writes travel on DIFFERENT transports** — the guard is a CDA write (`SendPMDGEvent`), the switch a `TransmitClientEvent` — so issued back-to-back they are **not guaranteed to arrive in order**. The switch could reach PMDG before the guard had opened, the write was refused, and the pilot had to pick the position TWICE. An **80 ms settle gap** orders them reliably while still feeling immediate (the generic `SendGuardedSet` uses 150 ms). **Do NOT drop it to zero.** A MobiFlight profile never shows this because both of its writes take the same path.

Two consequences of that gap, both load-bearing:
- **The sequence must be serialized** (`_emerLightsGate`). A screen-reader user arrowing through the combo commits one set *per arrow key*, so a second sequence starts while the first is still mid-gap. Interleaved, the Armed sequence's guard-CLOSE lands between the Off sequence's guard-OPEN and its switch write, PMDG refuses the switch, and the combo ends up displaying a position the aircraft never reached — reproducing the very "pick it twice" symptom the gap exists to prevent. This is cooperative interleaving across `await`s on ONE thread, not a data race: the gate is needed even though every write stays on the UI thread. A burst also collapses to its LAST selection (`_emerLightsRequest`) — superseded picks are skipped **whole**, never half-applied, so the guard can never be left open over a closed position.
- **Fire the sequence as a plain `async` local function, never `Task.Run`.** `HandleUIVariableSet` is only ever called on the UI thread and there is no `ConfigureAwait(false)`, so the awaits resume there and every SimConnect call stays on the UI thread, matching the generic `SendPMDGGuardedSet` path. `Task.Run` would push `SimConnectManager.SendEvent` onto a pool thread, where its lazy `"#<id>"` registration races the UI thread on an **unlocked** `eventIds` dictionary.

Note that `RequestVariable(key, forceUpdate: true)` — the combo snap-back used by the temp-knob variant guards — is a **no-op for any `PMDGVar`**: it only serves individual data-def or continuous-batch vars, and PMDG fields are CDA-broadcast into neither. Don't reach for it to resync a PMDG combo.

**Cockpit furniture (777 "Cockpit" panel section — Captain/FO Seat, Windows and Shades, Doors and Tables; all live-verified 2026-06-11):** Two mechanism families, both discovered by reading the cockpit behavior XML (`...\pmdg-aircraft-77w\SimObjects\Airplanes\PMDG 777-300ER\attachments\pmdg\Function_Interior_77W\model\77W_Cockpit_Behavior.xml` — the complete map of every interactive cockpit part and its L:vars):
- **SDK-event furniture** — armrests (`EVT_CA/FO_ARMREST_LEFT/RIGHT_SWITCH`, CDA param 1=up/0=down). **Foot heaters were REMOVED (2026-06):** the xBAW "Boris Audio Works" soundpack repurposes the CAPTAIN FOOT HEATER knob (SDK switch 319) as its hydraulic-pump-model gate, so the foot-heater combo (`EVT_FWD_LEFT/RIGHT_FOOT_HEATER` / `AIR_FootHeaterSelector`) and the Boris "Hydraulic Pump Model" combo (`switch_319_a`) drove the SAME physical knob — selecting a Vickers model moved the foot heater and vice versa. They are one control, so only the Boris hydraulic-pump combo is exposed; the FO foot heater was dropped for symmetry. The armrest anim L:vars `switch_1006_a`–`switch_1009_a` are **PMDG-SDK-owned read-backs** (rewritten from the real switch state every frame, same family as the xBAW switches) — a raw SetLVar reverts; the event is the actuator and the L:var follows for the combo display. Generic rule: `switch_<eventOffset>_a` anim L:vars give read-back for SDK events with no struct field.
- **L:var-input furniture** — visors (`visor_{L,R}_{front,side}_stow_unstow` + `_drag`, 0–100), worktables (`worktable_{ca,fo,obs_l,obs_r}`), shoulder heaters, window handle/clipboard (`WindowHandle{CA,FO}` / `WindowClipboard{CA,FO}`), cockpit door (`door_cockpit` — flips the SDK `DOOR_CockpitDoorOpen` read-back), crew rest doors (`door_crew_area_{left,right}`), cockpit curtain (`curtain_cockpit`), window shades (`7X7X_shade_{LF,LR,RF,RR}`, bool). These L:vars ARE the pilot input: writes hold and the model/system follows, so plain combos via MainForm's generic `SetLVar` fall-through drive them — no event mapping.
- **Sliding windows are the special case** — NO PMDG event exists for the window itself; the cockpit click runs RPN that toggles `L:Window_OpenClose_{CA,FO}` and fires stock `TOGGLE_AIRCRAFT_EXIT_FAST` on **exit 17 (captain) / 18 (FO)**, gated on handle unlocked AND clipboard moved aside. The `WINDOW_CA/FO` combos replicate that callback verbatim via `ExecuteCalculatorCode`; **Open auto-performs the unlock sequence** (handle + clipboard to 100 first), Close only closes (the model blocks the handle while the window travels — re-lock via its combo afterwards).
- **Crew seats are NOT adjustable on the PMDG 777** — no event, no struct field, no L:var, no model animation (verified across SDK, behavior XML, and the gltf: seat meshes are static). The armrests are the entire movable-seat surface; don't go hunting for seat-motion vars.

**Radio frequencies and transponder:** Use standard SimConnect events (not PMDG SDK):
- `COM_STBY_RADIO_SET_HZ` / `COM2_STBY_RADIO_SET_HZ` for setting standby freqs
- `COM_STBY_RADIO_SWAP` / `COM2_RADIO_SWAP` for swapping active/standby
- `XPNDR_SET` for squawk code (BCD16 encoded)

**CDU array index convention:** The PMDG SDK uses `0=Captain(L), 1=F/O(R), 2=Observer(C)` for ALL crew-position arrays — including CDU data areas (`PMDG_777X_CDU_0/1/2`), `CDU_BrtKnob[3]`, and all `CDU_annun*[3]` fields. The CDU form dropdown is ordered Left/Center/Right (0/1/2), which does NOT match the SDK ordering. `PMDG777CDUForm` uses a `DataCDUIndex` computed property to remap dropdown index to SDK index (`1→2, 2→1`). The event prefix switch (`EVT_CDU_L_/C_/R_`) uses the raw dropdown index and is correct as-is.

**Hydraulic pump array index — an index is a SLOT, never a side NUMBER.** The same `0=Left, 1=Right, 2=Center` ordering the CDU convention above records (sides first, center last) is what decides what a hydraulic pump array slot means. On the 777's two-element pump arrays `[0]`/`[1]` is Left/Right **only where the pair is a pair of sides** — the engine primaries (`HYD_PrimaryEngPump_Sw_ON`) and the electric demands (`HYD_DemandElecPump_Selector`). The other two pairs are not sides at all: the **Center** system carries BOTH electric primaries (`HYD_PrimaryElecPump_Sw_ON`) and BOTH air demand pumps (`HYD_DemandAirPump_Selector`), so those are spoken "Center 1"/"Center 2". Labels that read "1"/"2" named four center pumps after sides they are not on — a blind pilot has no placard to correct the impression.

**Do NOT re-derive that from event-id order.** Event ids order *events*, not array slots, and the two disagree inside `PMDG777Definition.cs`: the three-element `FCTL_*HydValve` arrays are `[0]=Left [1]=Right [2]=Center` while their ids run `WING_L 69692 < WING_C 69695 < WING_R 69698`, and `ELEC_ExtPwr*` has the event **names** swapped against the array outright (`_simpleEventMap` says so in place). The eight pump ids do happen to ascend with the labels (`DEMAND_ELEC1 69667 … ENG2 69674`, `event_base 69632`), but that is corroboration, not the rule — and it is 8 of the 22 `EVT_OH_HYD_*` events, the excluded `RAM_AIR`/`VLV_PWR` ones being exactly those that break it. Pinned by `tests/MSFSBlindAssist.Tests/Pmdg777HydraulicPumpLabelTests.cs`; the dictionary keys keep their `_1`/`_2` suffixes because Ctrl+M persists a mute under the key and there is no rename migration.

**⚠️ Still to confirm in-sim:** the C1/C2 **order within each center pair** is inferred from the array convention, not corroborated — and the NG3 SDK inverts exactly this array on the 737 (`HYD_PumpSw_elec`: `[0]`=pump 2, forcing a compensating display swap). Confirm that `HYD_PrimElecPump_1` moves the **C1** electric primary (not C2), and likewise for `HYD_DemandAirPump_1` and C1 AIR. The Left/Right pairs are the safer half but deserve the same check: `Primary Engine Pump Left` must move the **L** ENG pump.

**CDU interaction:** CDU buttons must send parameter 1 (pressed) via CDA; parameter 0 also registers as a press (not a release). Text entry sends one character at a time with 350ms delay; repeated characters need an extra 400ms for the CDU to distinguish separate presses. CDU display uses color and font-size data to detect toggle selections (non-white color or non-small font = selected, marked with `X`). Toggle detection only applies to rows with adjacent `<>` (mapped from 0xA1/0xA2 arrow symbols). Scratchpad announcements are suppressed during text entry and clearing (`_typingInProgress`/`_clearingInProgress` flags); `_previousScratchpad` is only updated when the announcement actually fires. CLR uses `_clearingInProgress` to suppress intermediate states and only announces "Cleared" once the scratchpad is empty.

**MCP dialogs:** Use `ValueInputForm` with `ToggleButtonDef` for mode toggles. Opened non-modal (`Show()`, not `ShowDialog()`) with `ShowCancelButton = false` so other windows remain accessible. Dialogs stay open after value entry (callback pattern). `MCP_IASBlank` indicates FMC-controlled speed. VS/FPA dialog uses `inputEnabledCheck` to gate input on mode engagement (`MCP_annunVS_FPA`). `EVT_MCP_VS_SET` requires VS mode to be engaged first ("VS window open").

**VS/FPA event naming (SDK names are misleading):** `EVT_MCP_VS_SWITCH` (69855) is the **engage/disengage** button. `EVT_MCP_VS_FPA_SWITCH` (69852) is the **VS↔FPA display mode toggle**. Confirmed by live sim testing — do not trust the SDK naming alone.

**Autopilot window (Ctrl+P):** Input-mode Ctrl+P opens the engage-cluster window: AP L/R, both flight directors, A/T Arm L/R, A/T, Approach, LOC, the disengage bar, the bank limit selector, and the A/P and A/T disconnects. Rows are declared as data in `Aircraft/PMDGAutopilotRows.cs` and bound to live UI by `Forms/PMDG/PMDGAutopilotRowBinder.cs`; the window itself (`Forms/PMDG/PMDGAutopilotWindow.cs`) is shared with the 737. The per-axis mode buttons (LNAV, VNAV, LVL CHG, HDG HOLD, ALT HOLD, VS/FPA) are NOT here by design — they live in the Ctrl+H/S/A/V value dialogs, and duplicating them would put one control in two places. Approach and LOC ARE here, and are not an exception to that rule: no value dialog carries them, so before this window they were reachable only from the MCP panel. The test is "is it already in a dialog", not "is it a mode button". Invariants: Every row actuates through `HandleUIVariableSet`, never a direct `SendPMDGEvent`. The 777's F/D and A/T Arm switches ignore position values and need `MOUSE_FLAG_LEFTSINGLE` simulation, which only that path applies. Reads gate on `IPMDGDataManager.IsReady` and render `--` before the first CDA snapshot; a 0.0 read there is a sentinel, not a real position — stateful toggle buttons (and the bank limit combo) are DISABLED until the snapshot arrives, because a toggle press computes its flip target from the current state; momentary buttons stay pressable, their press ignores the value. Presses call `MainForm.SuppressUiEcho` with the EXPECTED RESULTING value, not the press parameter — the echo gate is value-matched, so marking a press with 1 would let the matching disengage announce twice. Bank limit is a ComboBox, never a cycling button. Multi-position switches stay multi-position combos. Window hotkeys (native mnemonics, carried as row data and pinned by tests): AP Left **Alt+A**, AP Right **Alt+R** ("AP Right" has no B — an unannounced Alt+B was rejected in favor of an announced Alt+R), Approach **Alt+P**, LOC **Alt+O** (same letter as the 737's VOR LOC so the localizer key matches across fleets), Bank Limit **Alt+L**.

**Announcements:** Use `Announce()` (queued) in ProcessSimVarUpdate, `AnnounceImmediate()` only in HandleHotkeyAction. `IsAnnounced = true` is required for continuous monitoring registration. Suppress button push state (_Sw_Pushed) announcements via RenderAsButton check. Annunciator lights announce both on and off states. For variables needing cache but no auto-announcement, set `IsAnnounced = true` and return `true` from ProcessSimVarUpdate to suppress.

**System Display synoptic read-outs (`PMDG777Definition.SystemDisplay.cs`, partial class).** A read-only status box in the **Displays → System Display** panel, organized like the real Display Select Panel synoptic pages. A single combo (`PMDG777_SD_PAGE`, `SdPageKey`) selects one of 9 pages (0 Engine, 1 Status, 2 Electrical, 3 Hydraulics, 4 Fuel, 5 Air, 6 Doors, 7 Gear, 8 Flight Controls); selecting a page writes a private L:var (`PMDG777_MSFSBA_SD_PAGE`), and `RefreshSystemDisplayAsync` repaints the box. **HYBRID data sourcing** — each row is `(label, var, fmt)`: most values are **stock SimVars** read from the SimConnect cache (`GetCachedVariableValue` — oil temp/press/qty, EGT, N1/N2, fuel flow, hydraulic pressure/reservoir, electrical voltages, cabin alt/rate/diff, CG%MAC, gear, control surfaces/trim), while a small set of PMDG-SDK-broadcast fields (`_sdPmdgVars`: feed-tank fuel quantities, duct pressures, brake accumulator, IRS aligned, APU running, door states) are read **live** via `simConnect.PMDGDataManager.GetFieldValue(name)` (with `_N` array-index suffix), because OnRequest PMDGVars never land in the SimConnect cache. The box rides the GENERIC MainForm `_DISPLAY_`/`_REFRESH_` status-box infra (a navigable ListBox with a 1 s live auto-refresh + coalesced in-place row reconcile — see "Status-display boxes refresh live") — `OnDisplayPanelShown` triggers a refresh when the panel is shown; `TryGetDisplayOverride(SdPageKey, …)` renders the page name + content. **Documented gaps not in the SDK** (so NOT covered): oxygen, water, brake temp, tire pressure, APU N/EGT/load, generator load amps, EICAS alert message TEXT (WASM-only), wear/cycles, chrono elapsed time. **Formatting (2026-06-21):** the shared `Lbs`/`Pph` formatters show weight/fuel in BOTH units — "`<lb>` pounds (`<kg>` kg)" / "… pounds per hour (… kg per hour)" (1 lb = 0.45359237 kg) — covering every pounds field on every page (Fuel Flow, Fuel Used, Gross Weight, Total Fuel, per-tank). The continuous readouts carry ONE decimal place (`{v:0.0}` on percent / volts / psi / degrees-C) so sub-unit changes are visible — integer rounding had made live values look frozen (a reservoir at 96.9% read a static "97"). Weight/fuel stay whole (sub-unit is noise on a 6-digit number); N1/N2, vibration, flaps, diff-pressure already carried a decimal. The row formatters are `private static` methods (not per-call local funcs) so the compiler caches the method-group delegates — the auto-refresh tick and the 9-page registration loop don't re-allocate them; `TryGetDisplayOverride` renders the page name from `_sdPage` (the same source `_sdContent` was composed from), NOT the cached L:var `value`, which lags the calc-write/read-back and would briefly show the wrong header over fresh content. **PMDG-broadcast reads are gated on `IPMDGDataManager.IsReady`** — until the first CDA snapshot arrives `GetFieldValue` returns `0.0` for EVERY field (interface contract), which `DoorState(0)="open"` would render as "every door open" / "0 lb"; not-ready now renders `--` (matching the stock-SimVar cache-miss path). **MainForm's PMDG panel-populate loop only force-reads `Type == PMDGVar` controls** (`MainForm.cs` ~6598) — reading a non-PMDG control (the SD page combo is an `LVar`) via `GetFieldValue` returns the `0.0` "unknown field" sentinel, which used to force-reset the combo to page 0 on every panel re-show; non-PMDG controls populate via combo-creation + continuous monitoring instead.
