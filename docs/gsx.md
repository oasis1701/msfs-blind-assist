# Access GSX

Access GSX is the screen-reader-friendly interface for GSX Ground Services Pro. It mirrors the GSX in-sim menu and tooltip stream in standard Windows controls, so NVDA, JAWS, and other screen readers can read GSX status without relying on the simulator overlay.

## Opening And Reading GSX

- Open the Access GSX window with Input mode > `Alt+G`.
- Press `F5` inside the Access GSX window to open or reopen the GSX menu.
- Choose GSX menu options with `1` through `9` and `0` (the in-sim GSX numpad layout).
- `A`, `B`, `D` and `E` run GSX's own system commands — Customize Airport positions, Customize Airplane, Restart GSX, and Reload SimBrief. They are listed at the end of the menu options, and they work whether or not a menu is open: `D` (Restart GSX) is the standard recovery when GSX stops responding.
- Press `Esc` to hide the Access GSX window. The GSX service keeps running in the background.
- Press Output mode > `Ctrl+G` to read the latest cached GSX tooltip without opening the Access GSX window.

The Access GSX window has separate read-only fields for connection status, menu options, and the latest tooltip. When the GSX menu is hidden, the menu field shows a prompt telling the user to press `F5` again.

While a service is running, GSX keeps republishing the menu several times a second — an entry can carry a live counter such as a boarding passenger count. Access GSX re-speaks the menu only when something meaningful changes: it just opened, its title changed, the number of options changed, or an option's wording changed for a real reason (for example, boarding closing). A counter ticking by itself updates the on-screen menu list silently — arrow through the list at any time to read its current text.

If GSX's Remote API cannot be reached — a GSX older than 4.0.8, or GSX not running — the window still opens and its status field says so, and `F5` speaks the same explanation. Nothing is announced at startup; the reason is only given when you ask for GSX.

Selecting a gate for you (see "Auto-select gate on Calculate Route" in [taxi guidance](taxi-guidance.md)) needs **GSX 4.0.8 or newer**. On an older GSX everything else here still works — menus, services, settings — so nothing says GSX is unavailable; instead, the first time a route to a gate is calculated, Access GSX tells you gate selection needs 4.0.8 and that you will need to pick the stand in GSX yourself. It says that once per taxi-assist window, not on every route.

## Settings

Press `C` inside the Access GSX window while a GSX menu is available to open the accessible GSX Settings window. The settings window reads GSX's published settings page, groups controls by GSX section, and exposes toggles, choices, ranges, text fields, action buttons, and read-only information with standard Windows controls.

Setting changes are sent to GSX and persisted to the GSX configuration file. Numeric and text settings are committed as they change and again when the settings window closes, with duplicate writes suppressed. GSX echoes each change back; the window takes the echoed value into the control in place — focus stays where you are, and a control you are currently in is never written under your hands. Only a change to the settings page's SHAPE (a field added, relabelled or re-ranged) rebuilds the window.

If GSX has not published its settings page yet, open the GSX menu with `F5`, then press `C` again. The settings window opens only in answer to `C` — GSX republishing its settings on its own (every reconnect does) never opens it for you.

## Active Services

When GSX has two or more services running at the same time, the Access GSX window shows an Active services combo box above the tooltip. Selecting a service chooses which active row drives the tooltip. The selector is hidden when zero or one service is active so it does not clutter the tab order during normal use.

The automatic announcement stream is independent of this selector: every service's own transitions are announced regardless of what's selected here (see "Automatic Announcements" below and the "Tooltip selection vs. announcements" note under Implementation Notes) — a pilot who selected Boarding still hears that refuelling finished.

## Automatic Announcements

Access GSX speaks meaningful changes from the tooltip/status feed instead of every small text refresh. It handles:

- Service state changes — started, complete, available — for every service GSX publishes. "Available" names the handling company when GSX has assigned one ("Refuel available from United Ground Express.").
- Boarding and deboarding progress at milestones, not per passenger: passenger 0, passenger 1, then every tenth, plus the bag percentage every ten percent. A revised passenger total is always announced.
- Refuelling (and any other quantity GSX meters the same way) as "Refuel 820 of 13001 kg." — at most once every 30 seconds while the number moves.
- Bus arrival phases (approaching, in position, leaving).
- GSX's own on-screen message — the follow-me, marshaller and positioning banners GSX shows when no service is running — whenever its wording changes (a countdown ticking by itself stays silent).
- Metered ground connections (jetway, GPU, stairs): when one starts, a reminder every 15 minutes with the elapsed time and the amount so far, and when it stops.
- Invoices, announced once each: the handling company from GSX's receipt, and the amount from GSX's running charges. When GSX has published no amount yet, the invoice is announced without one rather than with a made-up figure. An invoice that was already sitting in GSX when the app connected is not read out again.

The Access GSX window speaks announcements while it is visible. When the window is hidden, background tooltip announcements follow the user's Announcement Settings option for GSX background monitoring. Nothing is read out for the state GSX is already in when the app connects — only what changes afterwards.

## Implementation Notes

Access GSX talks to GSX itself, not to a scrape of its UI. GSX ships a first-party **Couatl Remote API** — a WebSocket JSON protocol served on `ws://127.0.0.1:8744/` (the same origin and port as GSX's own "GSX Remote" PWA, reached via the WebSocket `Upgrade`; no pairing, no auth). Menu entries, service state, settings and billing arrive as typed, structured data — the 294 lines of tooltip regex (the old `GsxService.TextRules`) and the SimConnect-L:var / Windows-message path that used to carry menu, tooltip, status and settings are gone.

**There IS vendor documentation, and it was not available when most of this was written.** Virtuali publishes a *"Couatl Remote API v2 — Developer Guide & SDK Reference"* **embedded inside `C:\Program Files (x86)\Addon Manager\couatl\GSX\GSX_manual_MSFS.pdf`** — extract with `pdftotext -layout` and search for "Remote API"; it starts around 88 % of the way in. A local extraction is kept at `docs/superpowers/gsx-remote-api-guide.txt` for convenience. **That file is gitignored and must stay that way: it is Virtuali's copyrighted manual text. Never commit it, never paste it at length into a doc, a comment or a commit message** — cite what it says, in our own words, the way this document does. It settles what capturing traffic could not: the verb list, the error taxonomy, which surfaces are writable, and (below) that the docking stop position is genuinely unreachable rather than merely unfound.

Everything in "Protocol invariants" below was learned the harder way — by capturing live traffic against a running GSX (2026-08) — and it stays, because it is mostly what the guide does *not* say: patch coarseness, announcement rates, which `stateClass` values actually occur, how pagination behaves, what padding a search response contains. It is pinned by a dedicated xUnit suite over captured, redacted frames (`tests/MSFSBlindAssist.Tests/Fixtures/gsx-*.json`; `GsxFrameTests`, `GsxRemoteStateTests`, `GsxMenuModelTests`, `GsxSettingsSchemaTests`, and siblings).

**Minimum GSX version: 4.0.8.** The Remote API itself arrived in 4.0.1, but `gate.select` and the `handler.set` write surface arrived in 4.0.8, which is what this integration needs overall. **The code never compares versions** — it feature-detects on `hello.capabilities`, per the vendor guide's own instruction — and 4.0.8 is named in exactly two user-facing strings and nowhere else: `GsxService.ReasonNoRemoteApi` (no Remote API at all) and `GsxGateSelectAnnouncer.GateSelectUnsupportedMessage` (connected, but no `gate` capability). Naming 4.0.1 in either would be worse than naming nothing: the pilot would install a build where the Access GSX window works and gate selection silently does nothing.

**File map:**
- `Services/Gsx/Remote/GsxRemoteConnection.cs` — owns the socket: connect, subscribe, fast-start reconnect (250 ms → ×1.6 → 600 ms cap — a flat retry would make the app look dead through every routine `RESTART_COUATL`), id-correlated command/result matching (`GsxPendingRequests.cs`), frame reassembly.
- `Services/Gsx/Remote/GsxFrame.cs` — parses one wire frame (`hello`/`snapshot`/`patch`/`event`/`result`). `Parse` never throws; an unrecognised frame becomes `Unknown` so a future GSX field addition can't kill the connection.
- `Services/Gsx/Remote/GsxRemoteState.cs` — the flat state mirror (see "Protocol invariants" below).
- `Services/Gsx/Remote/GsxMenuModel.cs`, `GsxServiceState.cs`, `GsxSettingsSchema.cs`, `GsxBilling.cs` — typed models parsed on demand from state-store values.
- `Services/GsxService.cs` — the facade `AccessGSXForm`/`GsxSettingsForm`/`MainForm` actually talk to. Its public surface (`CouatlStarted`, `StatusText`, `MenuTitle`, `LastTooltip`, `IsMenuActive`, `OpenMenu()`/`Choose()`/`PickMenuEntry()`, `SetSettingNumber/Text()`, `PulseSettingAction()`, `StateChanged`/`MenuChanged`/`TooltipChanged`/`AnnouncementReady`/`SettingsChanged`) is unchanged from the pre-Remote-API version by design, so the forms needed minimal changes. **`GsxService` touches SimConnect nowhere at all.** It used to own a second, independent SimConnect client, kept for nothing but the `FSDT_GSX_SetGate_*` read-only confirmation L:vars the old menu-walking gate selector polled; `gate.select`'s own synchronous result payload replaced that polling, and the client, the `WM_USER_GSX_SIMCONNECT` window message and the `PumpSimConnectMessage` pump `MainForm.WndProc` routed to it all went with the selector. `GsxServiceFacadeTests` asserts their absence so they cannot quietly return. Two members exist for the gate work specifically: `Capabilities` (the live `hello.capabilities` token set, refreshed on every `hello`, cleared on disconnect) and `GetHandlerDataAirport()`, plus `SendCommandAsync(verb, args)` — the awaited-result escape hatch, since everything else on this facade is fire-and-forget `Send`.
- `Forms/AccessGSXForm.cs` — the accessible window. A menu pick goes through TWO independent layers of re-resolution before anything is sent (see "Protocol invariants").
- `Forms/GsxSettingsForm.cs` — renders directly from `GsxSettingsSchema` (typed tabs/subtabs/fields) instead of scraping GSX's settings HTML. Field type → control: `toggle`→CheckBox, `choice`→ComboBox, `range`→NumericUpDown, `text`→TextBox, `info`/`action`→read-only TextBox + buttons, `separator`→group heading. GSX now owns settings persistence (`settings.set`/`settings.action`) — MSFSBA no longer writes GSX's own config file (the one survivor, `StripUtf8BomIfPresent`, is a one-shot migration cleaning up `CouatlAddons.ini` files an *older* MSFSBA build poisoned with a BOM, unrelated to who owns persistence today).
- `Settings/UserSettings.cs` stores only the app-level `GsxBackgroundMonitoring` option; everything else GSX-side now lives in GSX's own settings.

**Connecting and failing.** The socket auto-reconnects silently on drop — GSX restarts its engine routinely (`RESTART_COUATL`) — and the window just shows disconnected meanwhile, with no announcement. A port that never accepts a connection at all means this GSX build predates the Remote API; that is reported on the next explicit user action (`Alt+G`, `Ctrl+G`, `F5`), never as unsolicited startup speech, matching this project's silence-on-background-failure rule.

**Lifecycle rules (2026-08 review fixes — each was a live failure).** `GsxRemoteConnection.Start()` must never REFUSE to start: `Stop()` only cancels the receive loop and must not join it, so a SimConnect disconnect→fast-reconnect (an aircraft switch, a status flap) routinely calls `Start()` while the old loop is still unwinding. It used to refuse, and its one caller `GsxService.Start()` had already latched `_remoteStarted` and never retried — the whole GSX integration stayed down until the next full disconnect/reconnect cycle while `UnavailableReason` claimed "needs GSX 4.0.8". `Start()` now CHAINS the new loop onto the old task's completion (`ContinueWith(...).Unwrap()`), keeping the no-two-loops guarantee without asking anyone to retry. `GsxService.Stop()` and `OnRemoteConnectedChanged(false)` share ONE teardown, `ResetSessionModels` — they were two hand-maintained blocks and had drifted: `Stop()` never cleared the `GsxRemoteState` store, so after a sim disconnect the facade answered `CouatlStarted`/`IsMenuActive`/`GetHandlerDataAirport()` from a dead session, and the next `Start()`'s hello (which carries NO state keys) re-derived every model from the stale store — re-announcing the previous session's invoice into a dedup set `Stop()` had just emptied and baselining the service announcer on stale rows. Both teardowns raise `MenuHidden` when a menu was showing, so `AccessGSXForm` swaps its list for the reopen prompt instead of leaving a dead, live-looking menu whose digit picks silently no-op; and `OnFrame`/`OnRemoteConnectedChanged` capture a lifecycle generation on the socket thread and drop after marshalling if `Stop()` ran in between, so a frame posted a moment before teardown cannot repopulate the models a moment after it.

There is no fallback transport, so **that message IS the entire mitigation** and three things have to hold for it to reach anyone. `GsxService.UnavailableReason` names the ACTUAL cause — no Remote API, a dropped Couatl, or no simulator connection — never "not connected to the simulator" for all three. It is seeded in `Start()`, because a connection that NEVER succeeds raises no `ConnectedChanged` at all (`GsxRemoteConnection.SetConnected` early-returns on an unchanged value, and `_connected` starts false), so nothing downstream would otherwise ever set one; and its getter can never return empty while disconnected, because a queued announcement of `""` is silently dropped. And `Alt+G` **opens the window anyway** when the Remote API is down — its status field carries the reason and `F5` speaks it. Refusing to open, which is what an `IsConnected` gate did, hid the only explanation there was.

### Protocol invariants (Couatl Remote API)

Each of these was a real defect caught while probing a protocol with no vendor documentation, not a style preference — undoing one reintroduces the bug it fixed.

- **State is FLAT — a `patch` frame replaces one top-level key outright; never deep-merge.** `GsxRemoteState.Apply` treats `{"type":"patch","path":"/services","value":…}` as `_state["services"] = value` in full (a `null`/absent value deletes the key). This mirrors GSX's own client (`store.js`) exactly, and it matters because GSX's patches are coarse: a patch resends the WHOLE array/object under that key, never a delta within it. Deep-merging would resurrect members GSX just removed — e.g. a service that stopped being offered would sit in the merged result forever instead of disappearing.
- **Only ONE `ReceiveAsync` may be outstanding on the socket at a time.** `GsxRemoteConnection.ReceiveLoopAsync` fully awaits each `ws.ReceiveAsync` before issuing the next. Starting a second concurrent receive faults the `ClientWebSocket` outright — hit twice while probing the live API, not a theoretical race. There is exactly one receive loop; sends go through the separately-locked `SendRawAsync`, so nothing else may call `ReceiveAsync` on this socket.
- **Accumulate raw BYTES across receives and decode UTF-8 once at `EndOfMessage` — never decode a chunk on its own.** `handlerData` alone is ~1.7 MB and always arrives fragmented across many `ReceiveAsync` calls. Decoding each chunk independently SILENTLY corrupts any multi-byte character split across a chunk boundary: `Encoding.UTF8.GetString`'s default fallback substitutes U+FFFD instead of throwing, so the damaged result is still syntactically valid JSON — no exception, no log line, nothing to reveal it happened. `GsxRemoteConnection.ReceiveLoopAsync` writes every chunk into a `MemoryStream` and calls `GsxFrame.Parse` only once `EndOfMessage` is true. This codebase already paid for this exact lesson once, in `SimConnect/CoherentDebuggerClient.cs` — same bug, same fix.
- **A `result` frame can carry a `payload`, not just `ok`/`id`.** `settings.get` returns `{"ok":true,"id":…,"payload":{"settings":{…}}}` — observed live at EDDF. `GsxPendingRequests`/`GsxService` neither parse nor need it today (the same schema also arrives unprompted as a `/settings` patch), but a future verb might return data ONLY in the result rather than also patching state — don't assume a `result` frame is contentless beyond `ok`/`id`.
- **Re-resolve a menu index against LIVE state at pick time, and refuse an AMBIGUOUS match, not just a missing one.** A menu navigation can land between an entry being read aloud and the key being pressed — GSX's own client re-reads the index at click time for the same reason. `GsxMenuModel.ResolveIndex(paintedIndex, expectedLabel)` first checks whether the painted index still holds the expected label; if not, it scans the current entries for that exact label and returns -1 (refuse) on either zero matches OR more than one — two entries carrying identical text is exactly the case a plain "find the label" lookup gets silently wrong by picking the first. This runs TWICE, independently: `AccessGSXForm.SelectMenuEntry` resolves against the menu it last rendered/announced (comparing the live menu to itself would never catch a real change), then `GsxService.PickMenuEntry` resolves again against the truly-live `Menu` immediately before sending `menu.pick`.
- **`menu.pick` has no "abandon" index — close the menu with `menu.close`.** `-1` was the OLD SimConnect L:var protocol's "user abandoned" value and does not exist here. GSX's own client guards `if (idx < 0) return;`, so no first-party client ever sends it — and Couatl is **Python**, where `entries[-1]` is the **LAST** entry: on the captured menu that is "Reposition Aircraft", i.e. sending -1 to abandon a menu would instead teleport the aircraft. `Send` is fire-and-forget, so a wrong pick raises nothing to notice it by — nothing fails, the aircraft simply moves. `GsxService.HideMenu()` sends `menu.close` and is the only correct way out; it is what `AccessGSXForm` uses. (This invariant predates the retirement of the menu-walking gate selector and outlived it: no code in this app walks GSX's menu any more, but `AccessGSXForm` still picks entries the pilot chooses, so the rule stands.)
- **The menu announcement must be CHANGE-GATED, never fired on every `/menu` patch.** GSX republishes the whole `/menu` object continuously while a service runs — measured live at EDDF, roughly 3 times a second — because an entry embeds a live counter (`"113/143 passengers boarded"` → `"114/143"` → `"115/143"`, otherwise byte-identical). `AccessGSXForm`'s announcer is QUEUED and non-interrupting, so speaking the full menu on every one of those doesn't just repeat, it backlogs — burying every other callout in the app behind an unbounded queue. `GsxMenuAnnounceResolver.ShouldAnnounce` (bottom of `AccessGSXForm.cs`) decides: announce on first appearance (including a reopen — `OnMenuHiddenUi` resets the snapshot to `GsxMenuModel.Empty`), a title change, an entry-count change, or any entry changing by more than a run of digits (`"Request Boarding"` → `"Boarding no longer possible"`, `"Customize this Parking position"` → `"Reset position"` — both real transitions observed live, and GSX flagged neither via `disabled`, see below). A pure digit-run change is suppressed even when the run's own LENGTH changes (`9` → `10`). **Guard: if MORE THAN HALF the entries changed at all, announce regardless of whether every change is digit-only** — **GSX paginates its own menus server-side** (confirmed live at EDDF 2026-08: once a logical list exceeds 10 items GSX splits it into pages of at most 10 and appends an ordinary-looking "Next Page ▶" entry as the tenth, index 9; a real menu page was never observed to publish an 11+-entry `entries` array), so a page turn on a long stand list can plausibly change every entry by digits alone (`Gate A11` → `Gate A21`, …); without the guard that looks exactly like a counter tick and silently swallows a page-turn keypress. An earlier note argued the opposite — that the Remote client scrolls one full unpaginated array client-side (`menu.js`) — from a single 10-entry capture that happened to land exactly on the boundary and could not distinguish the two theories. That reasoning was wrong; GSX pages. The menu LIST itself (a focusable `ListBox`) is always repopulated regardless of this verdict — only the SPOKEN announcement is gated, so a silently-ticked count stays readable on demand.
- **`GsxMenuModel.StateSuffix`'s live `stateClass` inventory — attested vs speculative.** Across the ENTIRE EDDF session exactly three values were ever observed on the wire, and all three are mapped:
  - `"gsx-state-performed"` → "In progress" — e.g. `"113/143 passengers boarded"`, "Fuel Truck is in position".
  - `"gsx-state-completed"` → "Completed" — e.g. `"Operate Jetway"`.
  - `"gsx-state-requested"` → "Requested" — e.g. `"Deboarding requested"`, captured right after requesting deboarding. This suffix does NOT recover information GSX was otherwise hiding — the entry text already says "requested" — it exists for consistency with the other two attested states, not to close a gap.

  `"gsx-state-performing"` (→ "In progress") and `"gsx-state-unavailable"` (→ "Unavailable") are SPECULATIVE — carried over from before this migration, never once observed on the wire across the whole session. Both stay mapped anyway: keeping them costs nothing, and one session not observing a value doesn't prove no GSX build ever emits it.
- **GSX does not use the `disabled` array in these flows — unavailability is conveyed in the ENTRY TEXT instead.** Zero disabled entries were observed across the entire live EDDF session, including through states that plainly should be unselectable (boarding closed, catering blocked during boarding/departure, jetways withdrawn). GSX instead rewrites the entry's own text: `"Request Boarding"` → `"Boarding no longer possible"`, `"Request Catering service"` → `"Catering not available during boarding/departure"`, `"Operate Jetway"` → `"Operate Jetways no longer available"`. `GsxMenuModel.Disabled` stays exactly as it is — defensive, and `AccessGSXForm.SelectMenuEntry` already refuses a `Disabled` pick before sending anything — but the ENTRY TEXT, not the disabled flag, is what actually informs a pilot whether an option will work; our `disabled` handling is inert in practice. (`IsSelectable` later gained a SEPARATE blank-entry check — see the parking-search bullets below — for a different kind of padding `disabled` also never flags.)
- **The `/receipt` frame carries NO money.** Its members are exactly `canPrint`, `html`, `logo`, `operator`, `printPreview`, `printer`. The charge lives in `/billing` — `builders[]`, each `{friendly, subtotal, lines:[{description, amount}]}` — alongside the still-running `timers[]`. A model that parsed `total`/`lines` off the receipt made every invoice announce **"Total 0.00"** over a real 1761.42 charge, and the test suite agreed with it because the test literal invented the same two members. `GsxService.FormatReceiptAnnouncement` takes the operator from the receipt and the figure from `GsxBilling.BuildersTotal`, and states NO figure when billing has published no builders. `html` and `logo` are deliberately never read (large blobs, no screen-reader value). Invoices are also deduped by a digest of the raw payload — `ApplyReceipt` runs on every `receipt` patch AND every reconnect snapshot, and GSX restarts its engine routinely.
- **`message` is an OBJECT — `{"text":…,"visible":…}` — not a string, and `visible` gates it.** GSX's own client renders `m.text` only when `m.visible`. This slot is the tooltip's fallback whenever no service is `performing`, i.e. parked, before departure, in the cruise, and after every service completes; reading it as a bare string left `LastTooltip` permanently empty across that entire idle case (blank Tooltip box, `Ctrl+G` answering "No GSX tooltip yet"). `GsxActiveServiceResolver.MessageText` owns the read.
- **A service row's real detail is `statusText`, not `progressText`.** On the captured deboarding, `statusText` reads `"bus in position\npax 181/186\nbags 100%"` while `progressText` reads `"181/181"` — GSX's progress bar is current-out-of-current. Rendered bare, that told a blind pilot deboarding had finished with five passengers still aboard. `GsxActiveServiceResolver.ComposeTooltip` prefers `statusText`, then the typed `detail.pax`/`detail.bagsPercent`, and falls back to `progressText` only when GSX published no typed detail at all.
- **Progress announcements MUST be milestone-gated.** GSX patches `/services` at roughly 1 Hz for the whole run of a service, so "announce every change" speaks once per passenger — ~186 utterances for one wide-body deboarding plus up to 100 more from the bag percentage. They are QUEUED and never interrupt, so they do not merely repeat: they accumulate and saturate the pilot's only output channel for minutes, with lag that grows the whole time. `GsxServiceAnnouncer` speaks passenger 0, passenger 1, then every tenth (bucket change, not exact multiple — GSX's sampling skips round numbers), and bags every ten percent; a REVISED passenger total always announces, since "150 of 190" and "150 of 186" are different facts and the count alone would never open the gate.
- **Every announcer here is BASELINE-FIRST, and the hello frame is not a baseline.** A hello carries no state keys; the snapshot that follows it is the full state of the session just joined. So `ApplyReceipt` records a receipt's digest silently until the first snapshot has been read (`_receiptsBaselined`) — before that fix, starting the app (or restarting Couatl, which clears the digests) with an hours-old invoice still in GSX's state spoke "Invoice available…" as if it had just arrived; the "message"-slot announcer (`GsxMessageAnnounceGate` + `_messageBaselined`) records the text present at the snapshot and speaks only later NON-DIGIT changes (a countdown is a tick, not news; an empty/invisible slot says nothing and does NOT reset the last-spoken text, so a banner flickering off and on is not re-read); and `GsxBillingTimerAnnouncer` is fed ONLY from the snapshot and `billing` patches, never from the hello — an Update on the hello's empty billing would baseline it on no timers, and the real snapshot a moment later would announce every already-running jetway as having just started. The reminder cadence (started / still running every 15 min with elapsed time and amount / stopped) is the pre-Remote-API `GroundConnectionTimerAnnouncementInterval`; it rides on GSX's own `billing` republishes as the hours accrue and never runs its own clock. `GsxServiceAnnouncer`'s generic progress branch (fuel kg — any row with `progress.current/total` and no pax detail/unit) is TIME-throttled at the old 30 s `FuelingProgressAnnouncementInterval` rather than milestone-gated, because litres/kg/percent have no natural bucket. All four were spoken by the pre-Remote-API transport and had been lost in the migration.
- **`SettingsChanged` fires on EVERY hello and snapshot (every connect/reconnect) and every unprompted `/settings` patch — so the settings WINDOW may be CREATED only in answer to a recent `C` press.** `AccessGSXForm` stamps `_settingsRequestedUtc` when it sends `settings.get` and `OnSettingsChangedUi` creates+shows the window only while that stamp is fresh (10 s window, consumed on use, also cleared when an already-open window absorbs a frame). The old transport raised the event only from the pilot's own settings flow, which is why the create path never needed a gate; without one, every reconnect after Access GSX had been opened once (its subscriptions outlive the hidden window) popped the settings window uninvited and `Activate()`d it — stealing screen-reader focus mid-flight, with FormClosed → `HideMenu` as a bonus side effect on dismissal.
- **`GsxSettingsForm` rebuilds ONLY on a STRUCTURAL change; a value-only republish is applied in place, and never into a control the pilot is currently in.** GSX echoes every `settings.set` back as a `/settings` patch (vendor guide: every change round-trips and GSX pushes a patch back). The old signature included each field's live `NumericValue`/`TextValue`, so every checkbox toggle, combo pick and — because `NumericUpDown.ValueChanged` sends per arrow-tick with no debounce — EVERY arrow-step made the echo differ, disposed every control (the focused one included) and `SelectSectionList()`ed focus back to the section list; range controls were unusable. `GsxSettingsSchemaSignature.Structural` (pure, `GsxSettingsSchemaSignatureTests`) covers Key/Type/Label/Tooltip/Min/Max/Step/Unit/IsFloat/MaxLength/Placeholder/Choices/Buttons and NOTHING live; equal structure → per-field appliers (positional, one slot per `BuildPages` field — Info fields carry no key) set the new value under `_applyingRemoteValues` so nothing echoes back, skipping any control that `ContainsFocus` (a fast arrow run outruns the echoes, and applying one to the focused control sets it BACK between two presses; a TextBox additionally requires no pending edit). The pages and signature are cached when `_schema` is assigned, so `HasFields`/`RefreshSchema` no longer re-walk the schema up to five times per republish.
- **The "GSX Menu hidden. Press F5 to open it." prompt is READ, never SPOKEN, and menu-change speech is form-VISIBLE only.** `GsxMenuAnnounceResolver.ShouldAnnounce` returns false whenever the CURRENT menu is empty — `MenuChanged` fires on both the hello and the snapshot of every connect/reconnect with the menu normally closed, and treating each as a "first appearance" spoke the prompt twice back-to-back on every connect and after every 'D' Restart GSX, even with the window hidden. Menu-hide is silent by design (`OnMenuHiddenUi`). `OnMenuChangedUi` still re-renders the list and re-snapshots `_renderedMenu` while hidden (keypresses resolve against the snapshot; the re-shown window must be current) but speaks only when `Visible`, the same gate `OnAnnouncementReadyUi` applies — and there is deliberately NO re-render in `VisibleChanged`: that would re-snapshot the LIVE `GsxService.Menu`, the stale model `OnMenuHiddenUi`'s `Empty` reset exists to keep out of reach after a close (see the `_renderedMenu` field comment). Digit keys carry the same `RemoteApiAvailable` gate F5 and the letter commands do, so a digit pressed after the socket dropped announces why instead of dead air.
- **`services[].state` has a `bypassed` value, not just the states already handled.** Requesting pushback flips Deboarding, Catering, Refueling, Boarding, OperateJetways, OperateStairs, GPU and Cleaning to `bypassed` simultaneously — eight services in one `/services` patch, observed live at EDDF. It falls through `StatePhrase`'s default case and speaks GSX's own `stateText` verbatim, which read sensibly and needed no code change — but be aware requesting pushback produces an eight-announcement burst from `GsxServiceAnnouncer`, all at once, all queued.
- **"Reset position" restarts the Couatl engine — expect the same reconnect sequence as any other `RESTART_COUATL`.** Picking it emits `event topic=engine gsxRunning=false restarting=true` and the socket drops. Confirmed live at EDDF to recover cleanly with no code change (the existing fast-start reconnect in `GsxRemoteConnection` already handles it), with every service returning to `available`. "Reset position" is just one more trigger for the restart the app already tolerates, not a special case to handle separately.
- **Settings tabs publish in TWO shapes — read both, unconditionally.** Some tabs carry `subtabs[]`, each with its own `fields[]` (e.g. Simulation → Services/Pushback/Parking/UI); others carry `fields[]` directly on the tab with no subtabs at all (Timings, Audio, Network, Diagnostic). In the captured live schema that split is 42 fields under subtabs and 39 fields directly on four tabs — 81 total. Reading only `tab.Subtabs[].Fields` silently drops FOUR WHOLE TABS. `GsxSettingsSchema.AllFields()` and `GsxSettingsForm.BuildPages` both walk `tab.Fields` AND `tab.Subtabs[].Fields` for every tab, unconditionally — a tab could in principle carry both shapes at once (not observed live, but the schema doesn't forbid it), and it must still get every field either way.
- **The API does NOT publish the docking stop position, and has no method-invocation verb — docking still reads GSX's profile files.** At KJFK, the one airport captured live for this work, `stopPosition`/`objectPosition` are `null` on every one of 238 parkings the API reports, while the equivalent `.ini` key (`parkingsystem_stopposition`) is present on 227 of that airport's 231 gates — and for the one gate matched by every other identifying field (lat/lon/heading/parkingSystem/gateDistanceThreshold/maxWingspan/hasJetway), the two points sit **~11.6 m apart** (10.40 m along-track, 5.18 m across), far outside docking's 0.3 m `StopToleranceMetres`. The per-aircraft stop offset is equally unreachable, and this is now settled by the vendor's own guide rather than inferred: a parking serialises `computeStopOffsetForAircraft` as the literal string `"method"`, the guide states plainly that `gate.setStopPositionOffset(...)` is **not callable** through `handler.set` — which "writes data properties only" — and the API exposes no method-invocation verb of any kind. So `GsxProfileLocator`, `GsxProfileParser`, `GsxStopOffsetResolver`, `GsxPyProfileReader`, `GsxPyOffsetEvaluator` and `GsxAircraftId` — the whole file-parsing stack under "Developer internals" below — are UNCHANGED by this migration and must stay that way. **This is NOT a version floor and no GSX update retires it**: the protocol does not carry the data, on any build. **Do not "finish the migration" by sourcing the stop from the API's `lat`/`lon`** — those sit ~11.6 m from the real VDGS stop point against docking's 0.3 m `StopToleranceMetres`, i.e. it would park every aircraft about eleven metres out, reintroducing the exact "stop position is not the parking position" failure this document's docking section already spent many bugs fixing.
- **Never log a raw frame.** `receipt`, `billing` and `handlerData` carry operator names, cost, and (via `handlerData.simbrief`) flight/crew data — the same class of data this project already treats carefully elsewhere (see the SayIntentions `flight.json` rule). None of the `Log.Debug` calls in `GsxRemoteConnection`/`GsxService` log frame payloads today, only verb names and error messages — keep it that way. The committed fixtures (`tests/MSFSBlindAssist.Tests/Fixtures/gsx-*.json`) are already redacted (e.g. `simbrief_username` reads `"redacted"`) — redact the same fields in any future capture before committing it.
- **The stand-selection interface — reached via "Reposition Aircraft" — is a DIFFERENT paginated shape from the service menu, and `layout` tells them apart.** The service menu (the committed KJFK capture, `Fixtures/gsx-menu.json`) publishes `layout: "t9"` and pages at 10 real entries, with "Next Page ▶" as the tenth (index 9). The stand-selection menu instead publishes `layout: "list"` and pages at 8: real stand choices occupy indices 0-7, "Next Page ▶" sits at index 8, and "↑ Back" at index 9 — confirmed live at EDDF. Real stand choices never exceed index 7 in this interface. `layout` is therefore a usable discriminator for any code that needs to tell which menu family it is looking at before assuming either pagination shape. **Nothing in this app drives that stand-selection interface any more** — `gate.select` replaced it entirely (see "Selecting a gate" below) — so these three observations are kept for `AccessGSXForm`, which still renders whatever menu the pilot opens by hand, including this one.
- **Group headers in the stand-selection menu carry a TAB then `(N suitable parkings)`** — e.g. `"Terminal 1 - A Gates [SE] (A1-A40 (V143+V144)) \t(24 suitable parkings)"`, confirmed live at EDDF. The count is parenthesized and can sit anywhere in the string, with arbitrary text (and that tab) before it; any future parser of these headers must not assume it follows the name directly. Previously matched by the retired classifier's `CategoryCountRegex` (`\(\s*\d+\s+(suitable|positions?|parkings?)`), whose deliberate "search anywhere, never examine what precedes it" shape is exactly why the tab changed nothing — worth knowing if this text is ever parsed again.
- **Stand entries pack VDGS type, size class and a jetway/pushback suffix into one string, with stray leading/trailing whitespace** — e.g. `" Gate A15 with Safedock© - Heavy - 1x  /J "` (leading space, `Safedock©` VDGS type, `Heavy` size class, `/J` jetway-and-pushback suffix — `"No Push"` appears on some entries in its place — then a trailing space). Confirmed live at EDDF. A structured parser of this text must trim first and then split on the embedded `-`-delimited fields. Note this is the MENU's rendering of a stand; the identifier `gate.select` takes is a different string entirely (`handlerData`'s own `name`, via `ParkingSpot.GsxIdentifier`) and is never derived from this one.
- **Parking search is a MODE, entered explicitly, not an ambient filter capability.** Picking the `"Search parking..."` entry sets `search: {"active": true, "session": N}` and retitles the menu `"Type a gate, terminal or number"`; only THEN does `menu.search {"text": …}` filter the results. Confirmed live at EDDF. A future implementation driving search must enter that mode first — pick the entry, wait for the retitled menu — rather than calling `menu.search` cold against whatever menu happens to already be open.
- **Parking-search results pad unused slots with empty strings, and — like the `disabled` array above — GSX does not flag them as unusable.** A live EDDF search for `"A15"` returned a fixed 10-slot response: one real match at index 0 (`" Gate A15 with Safedock© - Heavy - 1x  /J "`), `"Back"` at index 9, and `""` at every slot in between, with `disabled` staying `[false x10]` across the whole response. Before this was caught, `AccessGSXForm.RepopulateMenu` rendered all eight blanks as bare numbered rows (`"2. "`, `"3. "`, …) and `GsxMenuModel.IsSelectable` reported them pickable. `GsxMenuModel.IsBlank` (null/empty/whitespace) is now a second, independent check alongside `Disabled` in both `IsSelectable` and `ResolveIndex`'s `expectedLabel` guard, and `GsxMenuEntryRenderer` (bottom of `AccessGSXForm.cs`) skips a blank entry outright rather than rendering it — WITHOUT renumbering the surviving entries compactly, since the printed shortcut must stay the entry's real GSX index (exactly what `menu.pick` receives).

**Tooltip selection vs. announcements (closed 2026-08, was a known gap through Tasks 10-12).** `GsxService.ActiveServiceNames`/`DefaultActiveServiceName`/`SelectedActiveService` are derived from the typed `Services` list by `GsxActiveServiceResolver` (bottom of `GsxService.cs`, pure and covered directly by `GsxActiveServiceResolverTests` via `InternalsVisibleTo`): `ActiveServiceNames` is every service currently `State == "performing"`; `DefaultActiveServiceName` is the first of those; `SelectedActiveService`'s setter re-resolves `LastTooltip` immediately (silently — a combo change is a direct UI interaction the screen reader already announces, so this only raises `TooltipChanged`, never `AnnouncementReady`) and is cleared automatically if the pilot's choice stops being active, so a finished service can't strand the readout. `ActiveServicesChanged` fires only when the active *set* actually changes, not on every `services` patch, so the combo doesn't rebuild (and steal screen-reader focus) on every progress tick. This selection deliberately governs `LastTooltip` ONLY — `GsxServiceAnnouncer.Update` (in `ApplyServices`) reads `Services` directly and announces every service's own transitions regardless of what's selected, unlike the old tooltip-file transport where one selector necessarily gated both because GSX only ever pushed a single message at a time.

## Developer internals

The sections above document **Access GSX** — the accessible GSX menu/tooltip/settings window (PR #84's territory: live SERVICE STATE — boarding/refuel/catering/deice/pushback status, timers). The rest of this document covers a **separate, coupled feature set** layered on taxi guidance (branch `feat/gsx-taxi-gate-integration`): GSX gate/stand **positioning** (asking GSX to assign and prepare a parking position), audio **docking guidance** to the stop position (VDGS/marshalling analog), and an app-wide metres/feet **distance unit** toggle. These notes are developer-facing implementation detail, folded in verbatim from CLAUDE.md (Task 1.3, 2026-07).

**Domain boundary with PR #84 ("Fix GSX active service") — do not cross.** The docking/positioning code owns POSITIONING only: gate/stand selection, docking geometry, deice-pad positioning. PR #84 owns live SERVICE STATE (boarding/refuel/catering/deice/pushback status, timers, `GsxSettingsForm`). Don't add service-state logic to the docking code, and don't let docking read service vars.

**Feature:** Three coupled subsystems layered on taxi guidance — (1) selecting a GSX parking position with the `gate.select` verb, (2) audio docking guidance to the stop position (VDGS/marshalling analog), and (3) an app-wide metres/feet distance toggle. Verified with console probes under `tools/` plus xUnit characterization tests (`DockingGeometryTests`, `GsxOffsetTests`) run by CI (run `dotnet run --project tools/<Name> -p:Platform=x64`): `DockingProbe`, `DistanceUnitsProbe`, `GsxProfileProbe` (`--all` sweep / `--audit` robustness), `GsxAirplaneProbe`.

**TWO file-parsing paths deliberately SURVIVED the move to the Remote API. Neither is a compatibility shim, and neither is a version floor — no GSX update makes either redundant. Do not delete them.**

1. **The `.ini`/navdata gate LIST, for a REMOTE airport.** `handlerData.airport` only ever describes the airport GSX currently has loaded, and both `TaxiAssistForm` and `GateTeleportForm` let the pilot type any ICAO. The API structurally cannot answer for an airport GSX has not loaded.
2. **The `.py`/`.ini` stop-offset chain, because the API cannot supply the docking stop.** `stopPosition`/`objectPosition` read `null` on every parking, the guide states `gate.setStopPositionOffset(...)` is not callable through `handler.set`, and the parking `lat`/`lon` sits ~11.6 m from the real VDGS stop against a 0.3 m tolerance.

Both are LOCAL FILE PARSING, not GSX interactions, so they do not contradict "talk to GSX only over the newest, most reliable interface". Full reasoning: the gate-list bullet immediately below, and the "The API does NOT publish the docking stop position" invariant above.

**Key rules when touching this code:**

- **Gate-list source selection lives in `Services/GateDataSource.cs`, and there are now THREE answers, not two** (`GateSource.GsxRemote`, `GateSource.Gsx`, `GateSource.Navdata`). The Remote API path is taken **only** when GSX advertises the `handlerData` capability **AND** `handlerData.airport.icao` equals the ICAO being asked about; otherwise the `.ini`/navdata path below runs exactly as it always has.
  - **Why the file path survives, and why this is NOT a version floor.** `handlerData.airport` only ever describes the airport **GSX currently has loaded**. Both `TaxiAssistForm` (`txtAirport`) and `GateTeleportForm` (`icaoTextBox`) accept a **typed ICAO**, so a pilot planning ahead for a different airport — the whole point of those boxes — is asking about an airport the API cannot describe. That is a data-availability fact about the protocol, not a "some users have an old GSX" fallback, and it does not go away on any future GSX version. **Do not delete the `.ini`/navdata gate-list stack.**
  - `Services/Gsx/Remote/GsxRemoteParkingReader.cs` turns `handlerData.airport.parkings` into `ParkingSpot`s: Vehicle/Fuel parkings are excluded, `Radius` is `maxWingspan/2` in **METRES** (`ParkingSpot.Radius` is FEET on a navdata spot and METRES on a GSX one — `Source` is the discriminator; getting this wrong makes every tolerance 3.28× wrong), and a headingless stand is **kept** with `Heading = double.NaN` rather than dropped. `GsxStopPositionJoiner` then joins the `.ini` stop onto that list (exact lat/lon first, a logged 1 e-6-degree tolerance fallback second; it **refuses** on more than one match rather than picking) and fills the NaN heading from `this_parking_pos`. `GateDataSource.DropUnusableHeadings` is the last NaN gate — only there does a still-headingless stand get discarded. The API result is cached per (ICAO, raw `handlerData.airport` JSON).
  - **`Name`/`Number`/`Suffix` follow the app-wide stand-identity convention, and the terminal is a SEPARATE field.** `Name` is the concourse **letter** ("B"), exactly as `GsxGateMapper.ToParkingSpot` has always set it on the `.ini` path — the split goes through `StandId.Parse`, the one canonical parse `GateAliasResolver` and `GateSearchFilter` already share, so the reader and the alias resolver agree by construction (and it reads "Gate A12A", letter *and* trailing suffix, which the two hand-written regexes it replaced both fell through). The terminal (`uiTerminalName`) rides in **`ParkingSpot.TerminalName`**, which `Describe()` renders *after the type and before the Jetway/VDGS notes*. The worked example — GSX's `"Gate 25"` @ `"Terminal 4 - Concourse B"` rendering as `"B 25 - Gate Medium, Terminal 4 - Concourse B (Jetway) [SafeDock]"` — takes **two** steps, and the second is easy to miss: the reader itself produces `Name = ""` there, because `uiGateName` says only "Gate 25". The **`B` comes from `GsxConcourseLetterFiller`** (next bullet), which `GateDataSource` runs immediately after the reader. `StandId.Parse` alone gets you the `B` only for the 9 KJFK stands that spell it in `uiGateName` ("Stand H6"). **Do not fold the terminal back into `Name`.** It was there briefly and broke three consumers that read `Name` as a stand letter — `GateAliasResolver` (`StandId.Parse` rejects terminal prose, so *every* online alias candidate was dropped), SayIntentions' assigned-gate resolution and MainForm's parked-at-the-right-stand check. The SayIntentions failure is the expensive one: `NormalizeParkingName` cuts at the first spaced dash, so `"Terminal 4 - Concourse B 25 - Gate Medium"` normalized to `"TERMINAL4"` with the stand number gone, the assigned gate could never match, and destination resolution ran its whole chain to the **arrival runway**. The terminal still has to exist *somewhere* in the label — `uiGateName` alone names five different KJFK stands, and the dropdown de-duplicates by label text, so four of the five would be unreachable — and after the first spaced dash is exactly where it is invisible to both consumers. Pinned by `ParkingSpotDescribeTests` plus a 231-stands/231-distinct-labels assertion over the KJFK capture.
  - **The concourse letter is BORROWED — name-only, position-matched — when GSX's own `uiGateName` carries none** (`Services/Gsx/Remote/GsxConcourseLetterFiller.cs`). This is the Remote API path's equivalent of the borrow `GsxNavdataMerger.Merge` has always done on the `.ini` path (`if (string.IsNullOrEmpty(spot.Name) && nav != null) spot.Name = nav.Name;`), and without it the field convention above is only *stated*, not populated: across the 231 selectable KJFK stands, **9** carry the letter in `uiGateName`, **91** carry it only in `uiTerminalName`, and **131** have none anywhere. For that middle 91 the label normalized to `"25"` while SayIntentions asks for `"B25"` (every real captured `assigned_gate` carries the letter — "Terminal 3 Gate J1", "Terminal 2 Gate C6", "South Terminal Gate A24"), so `MatchDestinationLabel` failed and destination resolution ran to the **arrival runway** — the same ending as folding the terminal into `Name`, reached from the opposite direction.
    - **Two sources, in this order, and the order is MEASURED — do not flip it back.** (1) **`uiTerminalName`'s own "Concourse X" wording**; only the literal word "Concourse" plus a **single** standalone letter is trusted, so "Pier X"/"Satellite X"/"Concourse BC"/"Concourse 4" are refused rather than guessed. (2) **Navdata, matched by POSITION**, when the terminal names no concourse — still the only source for 52 of KJFK's 222 letterless stands, so it is not decoration.
    - **Why GSX beats navdata here, against the usual precedence.** Both sources were resolved for all 222 letterless KJFK stands against the real fs2024 navdata: 32 agree, **46 DISAGREE**, 52 navdata-only, 13 terminal-only, 79 stay letterless. Every sampled disagreement has **GSX right and navdata wrong** — navdata calls "Gate 25"/"Gate 27"/"Gate 29B"/"Gate 31" at *Terminal 4 - Concourse B* concourse **A**, while the real KJFK T4 is Concourse A (A2-A7) and Concourse B (B20-B41), so gate 25 is **B25**, which is what a controller and SayIntentions say. The reason is specific: navdata's letter comes from the BGL parking-**name enum** (`GATE_A`…`GATE_Z`, which `LittleNavMapProvider.MapParkingName` reduces to a bare letter) and that field is whatever the scenery author set — at KJFK uniformly `GATE_A` across a whole concourse. So navdata stays authoritative for stand **geometry** (position/heading/radius — none of which this touches) and is demonstrably **not** authoritative for the concourse letter. **This is a measured exception to "navdata is authoritative", not a contradiction of it** — navdata-first produced the wrong letter for 46 of 222 stands, i.e. it reproduced a navdata-quality problem instead of fixing it. A disagreement is logged with both letters, so "why is this stand called B?" is answerable from the log.
    - **The residual risk of leading with GSX's prose, stated not hidden.** At an airport that letters its *concourses* but not its *gates*, this renders "B 25" while the controller says plain "Gate 25" — the same class of failure being fixed, pointed the other way, and slightly larger now that this source leads. The mitigation is the strictness of the wording filter, so do not relax it. No such airport appears in any capture held; GSX wording a terminal "Concourse X" is itself a statement about how its stands are named; and every real captured SI `assigned_gate` carries the letter.
    - **NAME-ONLY. Nothing else is imported from the matched navdata spot** — not the coordinates, not the heading, not the radius, not the stop. That is exactly why this is a small dedicated borrow and not a `GsxNavdataMerger` call: the API's own geometry is complete and authoritative. It also never overwrites a letter GSX *did* supply.
    - **The match needs position AND number to agree, and refuses ambiguity.** The radius is **10 m**, chosen against measured geometry: in the committed KJFK capture the two closest stands of any kind are **21.2 m** apart (median nearest-neighbour 53.4 m, nothing under 15 m), and the closest pair sharing a number while differing in concourse letter is **227.4 m** apart — so the guard has a ~22× margin on the failure it exists for. Erring tight is deliberate: too small costs only a stand keeping `Name = ""`, which is today's behaviour; too large hands a stand its *neighbour's* letter, a wrong stand identity that corrupts the SI match, mints a junk alias and can taxi a blind pilot to the wrong pier with everything else sounding right. Two navdata stands in range disagreeing about the concourse are **refused, never arbitrated** (the same guard `GateAliasResolver` applies, and the same refusal idiom as `GsxStopPositionJoiner`'s multi-match).
    - **A stand still letterless afterwards is a CORRECT answer.** 131 of KJFK's 231 and the whole of a live ENGM read genuinely have no concourse letter; `Name = ""` stays a fully supported shape. Do not "improve" recall by widening the radius or the wording.
    - **The navdata read is a delegate, invoked at most once and skipped entirely when no stand needs a letter** — this runs on the UI thread while the gate dropdown is built, over ~231 stands. Never a per-stand query. A navdata read that throws degrades to "no letters borrowed", never to losing the API list.
  - **A published heading is normalized to 0-360 in the reader** (`GsxProfileParser.NormalizeHeading`, the same helper the `.ini` path has always used — the same GSX data must not read differently for having arrived over a different transport). GSX publishes **signed** headings: 122 of 231 in the KJFK capture, 37 of 68 on a live ENGM read. Steering and docking geometry are wrap-safe, so this is a wrong NUMBER rather than wrong steering — but the number is **spoken** (*"Align with {stand}, heading -90"*, *"Lining up {stand}, gate heading -120"*), and a heading a pilot cannot find on their heading indicator is worse than none. `double.NaN` passes through unchanged; that is what keeps the "GSX published no heading" sentinel (`HasUsableHeading`) intact.
  - **ONE name reaches the pilot, everywhere — `Services/ParkingSpotSource.cs`, and it is corrected IN PLACE.** Before this seam, only the dialogs went through `GetGates` while everything else called `IAirportDataProvider.GetParkingSpots` directly, so a stand had **two names in one running app** — and one consumer was not cosmetic: an aircraft parked exactly at KJFK B25 was told *"Aircraft appears near A 25, not assigned gate Terminal 4 Gate B25."*, a confident, wrong claim that a blind pilot is at the wrong stand. The seam has **two shapes**, and the split is load-bearing:
    - **`GetSelectableGates`** — *"which stands can I be sent to?"* — GSX's own list plus `AugmentParking`'s online aliases. Used by the taxi dialog's destination combo and the gate-teleport list, because a caller acting on a stand needs `GsxIdentifier` (for `gate.select`), the docking stop position, the max wingspan for the fit filter, and `TerminalName` to tell identically-named stands apart. This is exactly what those two already did.
    - **`GetNamedSpots`** — *"what is this stand called?"* — **navdata's own set** (same spots, count, coordinates, order) with only the concourse letter corrected from the gate list by `Services/Gsx/GsxStandNameOverlay.cs`, then `AugmentParking` re-run so aliases resolve against the corrected identity (`GateAliasResolver` matches on the letter, so an alias resolved beforehand is resolved against the wrong stand). Used by **every `TaxiGraph.Build` call** (so Where-Am-I says *"Gate B 25"*) and by SayIntentions' parked-at-the-right-stand check.
    **Why not simply hand `Build` the GSX list:** the parking list is not only a name source — `TaxiGraph.Build`'s parking pass also writes `node.Type = TaxiNodeType.Parking`, which `NamedHoldingPointResolver` (it SKIPS parking nodes when snapping a named holding point), `HoldShortNodeResolver` and the route truncation in `TaxiGuidanceManager.Routing` all read, so a different SET could **move a hold-short**. The GSX list is also smaller — it excludes Vehicle/Fuel stands and drops headingless ones (230 of KJFK's 231 survive `GateDataSource`) — so swapping it in would strip the Where-Am-I label off stands that have one today. Naming a stand and deciding which nodes are parking are different jobs, and only the first may change. The overlay touches `Name` **only** — never the coordinates, heading, radius (FEET on navdata, METRES on GSX), type or metadata — and never `Number`/`Suffix`: the match already requires the numbers to be equal, and copying a suffix could turn navdata's "A 24A" into a claim about a different stand. The match itself (same number, within 10 m, all in-range candidates agreeing on one letter or the whole thing refused) is `Services/Gsx/GsxStandLetterMatch.cs`, **extracted** from `GsxConcourseLetterFiller` rather than copied beside it, so the two directions cannot drift from the measurement that justifies them. **When GSX is not running this changes nothing** — `GetGates` falls through to the `.ini`/navdata path whose last fallback is literally `GetParkingSpots`, so the correction compares the list against itself. Graph builds inside `TaxiGuidanceManager` reach the seam through the injectable `ParkingSpotSupplier`, which **defaults to `dataProvider.GetParkingSpots`** so every caller that does not wire it stays byte-identical. **Call it where a graph is built or a dialog opens, never on a position update**, and note it runs off the UI thread (Where-Am-I comes from a `RequestAircraftPositionAsync` callback), which is why MainForm's supplier constructs a fresh `GateDataSource` per call instead of sharing one — `GateDataSource`'s per-ICAO caches are plain `Dictionary`. See also [taxi-guidance.md](taxi-guidance.md) §"One name for a stand".
  - **`ParkingSpot.GsxIdentifier` is populated ONLY by `GsxRemoteParkingReader`.** A list served from the `.ini`/navdata fallback has none, so `gate.select` cannot be sent for those spots and auto-select degrades to `BadArgs` — i.e. to manual selection, the behaviour that existed before any of this. That is the intended degradation, not a bug, but it does mean the auto-select feature is live only where the API list is. **But a per-ICAO gate-list cache must NOTICE when the API list becomes available — it used not to.** `TaxiAssistForm._cachedGateSpots` was keyed on the ICAO alone, the form is hide-on-close and `LoadAirportDataCoreAsync` early-returns for a same-ICAO reload, so a list bound from the fallback BEFORE GSX published the airport (an arrival pre-planned during descent, or the spawn before the first `handlerData` frame) was served identifier-less all session and every gate Calculate spoke "GSX could not prepare this stand." — the intended one-time degradation became a session-long one. `GateDataSource.GetGateListVersion(icao)` is the fix: an O(1), compare-only staleness token (`api:{GsxService.HandlerDataVersion}` / `ini` / `navdata` — a capability lookup, a dictionary read and a field read; NEVER a file, a DB query or `GetGates`, because it is compared per gate-search keystroke, and NOT a substitute for `GetActiveSource`). `HandlerDataVersion` is bumped by `GsxService` on every `handlerData` patch and every snapshot. `TaxiAssistForm` keys its cache on (ICAO, token), and `RefreshDestinationsIfGateSourceChanged` re-checks it at the two moments `PopulateDestinations` does not run — on show (`OnVisibleChanged`; a selection the rebuilt list no longer carries is announced QUEUED) and at the top of Calculate (a lost selection ABORTS through `AnnounceCalculateAbort` rather than routing to whatever item 0 now is). `GateResolver` (the TCAS "at Gate …" label) keys its own per-ICAO cache on the same token, so the TCAS list follows the corrected letter the moment GSX catches up too.
  - **`GATE_EXTRA`/`RAMP_GA_EXTRA` map — to navdata's SWAPPED numbering.** GSX's enum has `RAMP_GA_EXTRA = 14` and `GATE_EXTRA = 15`; navdata's has 14 = "Gate Extra" and 15 = "Ramp GA Extra". `GsxGateMapper.MapGsxTypeToNavdataType` maps 15→14 and 14→15 and `GsxRemoteParkingReader.NameToKnownGsxTypeInt` lists both constants. They used to be omitted "because the mapper has no case for them", which made every A380-class stand on the Remote API path `Type 0` — "Spot N - Unknown", outside `IsGateType`, in the teleport dialog's "Other" bucket and out of its gate count — at exactly the airports big enough to have them. The `.ini` path was never affected (its `DeriveType` classifies from category + wingspan). Pinned by `GsxGateMapperTests` and two reader cases.
  - GSX is authoritative on the file path when GSX is available AND `GsxProfileLocator` finds a matching profile; otherwise navdata. **"Available" is EITHER signal — `GsxService.CouatlStarted` (the Remote API's own `gsxRunning`) OR `SimConnectManager.GsxCouatlStartedLVar` (GSX's `L:FSDT_GSX_COUATL_STARTED`, one fixed def on the main SimConnect connection, `SECOND` period on change) — ORed in `MainForm.Dialogs.BuildGateDataSource`.** The L:var is what EVERY GSX build publishes, Remote API or not; before the migration `CouatlStarted` WAS that L:var, and afterwards it came only from Remote-API frames, which silently switched the `.ini` overlay, the deice pads and the profile stop positions — local-file features that never needed the WebSocket — off for any GSX build older than 4.0.1, against the "neither is a version floor" rule above. `GsxService` itself still touches SimConnect nowhere; the read lives in `SimConnectManager` where every other L:var read lives. `GsxNavdataMerger` overlays GSX metadata onto the navdata skeleton (navdata supplies positions GSX omits, matched by concourse+number). **Merger safety: no cross-concourse coordinate borrowing.** When a GSX gate HAS a concourse, a navdata candidate may only donate coordinates if its normalized concourse matches — otherwise the spot is DROPPED (routing a blind pilot to "A12" at B12's coordinates on another pier is worse than omission). **Spot position priority is `this_parking_pos` → navdata → stop position (LAST resort).** The GSX stop position is a VDGS NOSE-STOP reference, not an aircraft-datum location — using it as the spot position teleports the datum metres deep into the stand (sometimes at heading 0); docking is unaffected because it reads the preserved `StopLatitude/StopLongitude/StopHeading` fields directly. **GSX Python (`.py`) profiles are NOT parsed for the gate LIST** — only `.ini`. So large airports with a `.py` profile (e.g. EDDF `eddf-Aerosoft.py`) fall back to navdata for the LIST *on the file path*; at the currently-loaded airport the Remote API path above supersedes this entirely, and `.py` airports are exactly where it helps most. Deice areas are GSX-only and excluded from the normal gate list (`GetDeiceAreas` is separate). **The DOCKING STOP, however, DOES consume `.py`** — see the per-aircraft stop-offset bullet below.
  - **Deice pads: the API HAS them, in their own collection, and nothing reads it yet.** A live 2026-08-14 ENGM read shows `handlerData.airport.deIceAreas` populated (9 entries, each with `uiName`/`lat`/`lon`/`heading`/`radius`/`uiType: "DeIce Area"`/`index`/`isParking: false`), and pads do **not** appear in `parkings` at all — the distinct `uiType` values across all 99 live parkings are Fuel, Gate Heavy, Gate Small, Ramp Cargo, Ramp GA Large, Ramp GA Medium, Ramp Mil Cargo. So `GetDeiceAreas` stays on the `.ini`'s `is_deicearea` key **because nothing has wired `deIceAreas` up yet**, not because the API cannot tell a pad from a stand (an earlier comment claimed the latter; both halves of it were false). The reassuring corollary, worth keeping in mind before anyone "adds a deice filter": `GsxRemoteParkingReader` needs **no** deice exclusion — a pad can never leak into the API-sourced gate list, because pads are never in `parkings`. If `deIceAreas` is ever wired up, note it publishes no stop position either.
- **GSX `.py` per-aircraft stop offset applies to ALL non-deice gates (incl. `.ini`).** `TaxiAssistForm.ApplyGsxStopOffset` resolves GSX's per-aircraft longitudinal/lateral stop offset (metres) and feeds it to `DockingGuidanceManager.SetStopOffset` for every non-deice gate — `.ini` gates included. It previously SKIPPED the `.py` `customOffset` whenever the gate had a `StopLatitude` (i.e. `.ini` gates), wrongly assuming the `.ini` stop was already aircraft-exact. It isn't: the `.py` `customOffset` is GSX's PER-AIRCRAFT adjustment layered ON TOP of the static `.ini`/navdata base (same gate → different offset per airframe — EDDF A66: 777 = 5.3 m, A380 = 6.3 m, base = 1.65 m). Without this the 777 parked ~5.3 m short at every `.ini` airport (EDDF etc.). **Suffix changes the resolved function:** EDDF **A66** (no suffix) → 777 = **+5.3 m**; EDDF **A66A** (suffix "A") → 777 = **0 m** (that stand's function has no 777 table entry, so it correctly falls to base 0; an A320 there gets −2.5 m — proves it evaluates rather than parse-missing). Locked by `tools/GsxOffsetProbe` resolver-level asserts. A `STOPOFFSET` diagnostic line (icao / gate# / suffix / stopLatSet / ac / acId / resolved offset) is appended to `%APPDATA%\MSFSBlindAssist\logs\docking-aircraft.log` on each route-calculate for one-glance debugging of "offset is 0" reports. `GsxStopOffsetResolver` locates the airport `.py` (`GsxProfileLocator.TryFindPyProfile`, excludes `_handler.py`), parses it (`GsxPyProfileReader`, cached by path+last-write), and evaluates the gate's `customOffset` function (`GsxPyOffsetEvaluator`) for the resolved `GsxAircraftId`. **Aircraft resolution is UNIVERSAL** (`GsxAircraftIdMap.TryResolve(icao, wingspanMetres)`): idMajor/idMinor are DERIVED from the ICAO designator pattern (Boeing `B7Xd`→707+X·10, Airbus `A3YZ` narrowbody-literal/widebody-300+Y·10, Embraer literal) and ARC from wingspan (Annex-14 A&lt;15…F≥65 m); a thin exception table holds only irregulars (B787 bare-minor, A350 idMinor 1000, neo idMinor 1, A220, **and the 737 MAX family — `B37M`/`B38M`/`B39M`/`B3XM` → 737 family with closest-gauge minor**: the `B3xM` designators break the `B7Xd` pattern and used to resolve idMajor 0, silently losing every idMajor-keyed `.py` stop offset for one of the most common airliner families; locked by probe asserts). The raw ICAO is always kept so ICAO-keyed tables hit; idMajor 0 forces the base offset. Evaluator group fallback tries `"ARC-E"`, bare `"E"`, and `"Heavy"` (authors key differently; `"ARC-X"` dominates installed profiles). In `DockingGuidanceManager.UpdatePosition` the stop point is shifted (`ShiftStop`, equirectangular) BEFORE any distance is computed — longitudinal along `StopHeading`, lateral perpendicular (right=+). **`GsxOffset.Zero` is a strict no-op** (shift skipped) so behaviour is byte-identical to today; any miss at any layer (no profile/unknown aircraft/parse error) degrades to `Zero`. Logged as `stopOffL`/`stopOffLat` in `docking.log`. Measured golden: EDDF A66 / 777-300 = +5.3 m. Verified by `tools/GsxOffsetProbe` (golden + `--sweep` over all 72 profiles + a **universal installed-aircraft scan**: `AircraftCfgCatalog.EnumerateInstalled()` enumerates THIS machine's real fleet and asserts every distinct ICAO resolves without throwing — zero hardcoded expected values, so the probe works on any user's machine).
- **TITLE→ICAO catalog fallback (`Services/AircraftCfgCatalog.cs`).** The whole GSX/docking aircraft-resolution chain keys on the ICAO from SimConnect `ATC MODEL` (`SimConnectManager.ExtractIcaoFromAtcModel`). For the rare add-on whose ATC MODEL doesn't parse to a clean ICAO, `SimConnectManager` falls back to `AircraftCfgCatalog.TryGetIcaoByTitle(currentAircraftTitle)`. The catalog is a PURE, dependency-light service (file IO only — no WinForms/SimConnect/EFBModPackageManager deps, so the probe links it) that scans installed `aircraft.cfg` files under `<InstalledPackagesPath>\{Community,Official\OneStore,Official\Steam}\…\SimObjects\Airplanes` (depth-bounded so it never crawls texture trees), parsing each cfg's package-level `icao_type_designator` and every `[FLTSIM.N] title` into a `titleLower→icaoUpper` map. It resolves the packages root itself by reading `InstalledPackagesPath` from the FS2024/FS2020 `UserCfg.opt` locations. **Background + lazy + cached + thread-safe; NEVER throws** (any missing dir / locked file / malformed cfg degrades to empty/no-hit). The fallback runs ONLY when `ExtractIcaoFromAtcModel` returns empty, NEVER blocks the SimConnect callback (the scan/lookup is on a `Task.Run`), validates the result looks like an ICAO (2–4 alphanumerics), and — mirroring the door-offset background re-fire — sets `CurrentAircraftIcaoType` + re-fires `AircraftIcaoTypeDetected` when it later resolves. The common case (ATC model present) is byte-for-byte unchanged. The catalog is warmed via `BeginBuild()` at `Connect()` time so the fallback has near-zero latency.
- **Selecting a gate is ONE verb: `gate.select {gate, revokeServices?, force?}` (`Services/Gsx/Remote/GsxRemoteGateSelector.cs`).** It replaces the entire menu walk that used to live here — a bounded backtracking page-aware DFS over GSX's live menu (`GsxGateSelector`, 1013 lines), plus 762 lines of leaf-vs-category string heuristics (`GsxMenuClassifier`) and a small automation helper (`GsxMenuAutomation`). All three are **deleted**, and with them the `FSDT_GSX_SetGate_*` SimConnect confirmation client that polled up to ~6 s for a result the verb now returns synchronously. There is no live menu state left to traverse, classify, back out of, or corrupt. The verb **assigns and prepares** the stand; it does **not** move the aircraft, and it works in flight, so it can be sent the moment a route is calculated rather than on arrival.
  - **The gate sent is GSX's OWN identifier — `ParkingSpot.GsxIdentifier`, verbatim.** Never a label rebuilt from `Describe()`, `Name`, `Number` or `Suffix`. A round-trip through our own formatting is precisely how the wrong stand gets selected, and it is the class of bug the retired classifier's `MATCH-BARENUMBER` fallback and identity-normalisation existed to paper over. `GsxIdentifier` is populated only by `GsxRemoteParkingReader` (see the gate-list bullet above) — an absent one is refused locally as `BadArgs`, never guessed at.
  - **What GSX says it selected is CHECKED against what was sent** (`GsxGateSelectResult.RequestedIdentifier`, stamped by the selector; `ResolvedGateContradictsRequest` does the comparing). `uiGateName` is the only identity field GSX publishes per parking, and its uniqueness is **airport-dependent**: 98/98 distinct on a live ENGM read, but 128 of KJFK's 231 selectable stands share one with another stand ("Gate 2" names five physically different stands across five terminals). When GSX can choose it either answers `ambiguous` (surfaced) or resolves to one of the matches — and that second case used to taxi a pilot to a stand GSX had not prepared, in silence. The check is deliberately **conservative**, because a false alarm teaches the pilot to ignore the real one: matching **either** echoed string (`gate` or `uiName`, trimmed, ordinal-ignore-case) clears it — the guide's own shape pairs a full `uiName` ("Gate A12") with a bare `gate` ("A12"), so which one equals what we sent depends on GSX's spelling, not on whether it picked the right stand — and an echo with no interpretable strings is **not** a mismatch. `gsx-gate-select.log` gains a `resolvedMismatch=true` token, appended only when true so ordinary lines keep their `target=… identifierSent=…` scan shape. **Do not "fix" this by switching the identifier to `index`**: `index` is not among the four identity fields §8.14 says `gate.select` accepts, the committed fixture does not carry it, and guessing an undocumented match field is a worse failure than a verified one. The echo check is correct whichever field GSX matches on.
    - **It CANNOT detect the identical-name collision it was added for, and no care with the comparison ever will.** When two stands share the *same* `uiGateName` — KJFK's five "Gate 2" — GSX echoes that same string back whichever one it resolved to, so the echo equals what we sent and the check reads clean, exactly as it would for a correct resolution. Nothing available to us disambiguates them: the four identity fields carry no terminal, and `bglName`/`index` are not published in `handlerData.airport.parkings` at all. This is a **structural limit of GSX's API**, not a flaw in the check. Keep the check anyway — it catches a resolution to a *differently-named* stand, the half of the same failure we can see — but never read a clean result as "GSX prepared the stand the pilot picked". It only means GSX did not name a different one.
  - **`force` is NEVER sent as `true`.** It is a hardcoded `false` literal in the request object, with no parameter, property or field anywhere able to set it — verified by an independent reviewer trace, not just by reading the call site. `force` overrides a stand GSX has assigned to AI traffic; doing that silently would put a blind pilot nose-to-nose with an aircraft they cannot see. The `assigned_to_other` outcome is **spoken** instead, and the phrase deliberately never offers to force it.
  - **`services_active` is retried EXACTLY once, with `revokeServices: true`, and the retry is announced.** GSX returns this when it is already committed at a gate; the pilot asked for a different stand, so revoking the old stand's setup is the obvious consequence (it is what the in-game menu does). Whatever the retry returns is final — success, `services_active` again, or anything else — it never loops. `GsxGateSelectResult.WasRevokedAndReprepared` marks the retry's own success, because a single result frame carries no way to tell "prepared" from "prepared after tearing down the previous stand's services", and the pilot needs the latter.
  - **The feature is gated on `hello.capabilities` containing `gate`, never on a version number** — the vendor guide's own instruction, and the reason a future GSX that moves the verb around cannot break us silently. The gate has **two** outcomes, and conflating them puts a false statement in front of a pilot: a **non-empty** capability set that lacks `gate` is positive evidence of a connected 4.0.1-4.0.7 build (`GateSelectUnsupported`, spoken once per taxi dialog — this is the only place a version number reaches the pilot on this path), while an **empty or unreadable** set means nothing is known about GSX at all, usually because the Remote API is not connected (`Unavailable`, silent — telling that pilot to install 4.0.8 could send them after a version they already have). Every live `hello` carries several tokens (the committed fixture has nine) and Access GSX works fine on 4.0.1-4.0.7, so a connected older build always lands in the first case.
  - **`SelectGateAsync` SERIALIZES concurrent calls (`SemaphoreSlim(1,1)`); it does not reject the second.** This is a deliberate reversal of the old DFS's `Interlocked` reject-latch. That latch protected a minutes-long traversal of a live shared menu from two interleaved walks pressing arbitrary wrong entries; `gate.select` has no shared traversal state, so the risk it guarded is gone. What remains is that two overlapping requests could interleave and the second `revokeServices` the first mid-flight — serialising removes that by construction, and unlike a reject it can never silently drop a **pilot's correction** (they hear a wrong gate, re-pick, and the second call is discarded behind a "busy" message easy to miss). Serialising guarantees GSX ends on the pilot's LAST request.
  - **Every outcome that ENDS the request is spoken** (`GsxGateSelectAnnouncer`, pure and stateless; `TaxiAssistForm.SelectGsxGateAsync` does the speaking, always via the QUEUED `Announce`, never `AnnounceImmediate` — this arrives from a background round trip well after the Calculate click, not from a direct UI interaction). A pilot who calculates a route to a gate has taken an explicit action, and its terminal answers must not all sound the same: they briefly did, because specifying four *new* outcomes silently dropped the two the retired menu-walking selector used to speak (*"GSX: A 6 selected."* and *"GSX: … not found in GSX menu."*), leaving "GSX prepared your stand" acoustically identical to "GSX is not running" and to "the request timed out". What is spoken:
    - **`Prepared`** — *"GSX prepared Gate A12."* The positive confirmation, naming the stand **GSX** resolved to, so a wrong resolution is audible in the same breath (see the echo-check bullet above; on a mismatch it names both).
    - **`already_parked`/`already_selected`** — *"GSX is already set up at Gate A12."* The guide's "nothing to do" is about not **retrying**; it is not about not telling the pilot. `already_selected` fires when the pilot asked for a **different** stand from the one GSX has, and `error.gate` is the only thing naming which — so silence here is the wrong-stand failure by another route. The same echo comparison applies, and the wording never claims GSX moved to the pilot's pick.
    - **`not_found`** — names the stand and says no stand was prepared. **`bad_args`** — says no stand was prepared (both ways in: GSX rejecting the request, and a spot with no `GsxIdentifier`, i.e. a list served from the `.ini`/navdata fallback).
    - a **`too_small` warning** on an otherwise-successful selection (GSX's own verdict that the stand does not fit the airframe — there is no other route to that information, and GSX prepares the stand anyway); an **`assigned_to_other`** occupied stand (never offering to force it); an **`ambiguous`** identifier (up to 3 candidate names plus a residual count, never guessed at); and a **successful revoke-and-reprepare**.

    Silent **by design**, each documented inline in the switch: `no_airport` (the request was made before GSX had an airport loaded — auto-select fires on every route calculation, including ones made hours out, and there is nothing to do but calculate again nearer the field); a double `services_active` (unreachable except when the one automatic retry is also busy); `gsx_not_running`/`auth_required`/`Unavailable`/`TransportFailure` (covered by `GsxService.UnavailableReason`'s own explicit-action surface, and not actionable in flight). The switch has **no `default:` arm**, which is what makes a new outcome member safe to add: it stays silent until someone deliberately gives it a case.
  - **`%APPDATA%\MSFSBlindAssist\logs\gsx-gate-select.log` is still the FIRST STOP when debugging "gate not found"** — it inherited that role from the retired walk-log. One line per attempt now instead of a whole traversal: target label, the identifier actually sent, `revokeServices`, outcome, the stand GSX resolved to, warnings, the raw GSX error code, **and GSX's own error message** (the most useful field for diagnosing `not_found`/`bad_args`/`no_airport`, parsed but discarded until 2026-08). The no-send cases log too, with the reason. **Never log a raw frame here** — frames can carry `handlerData`, which holds user data; this log is fed only already-parsed, already-safe fields.
  - **`gsx_not_running` and `auth_required` have their own outcome members** rather than pooling into `Unavailable`. Not because either is spoken — neither is — but because "GSX is not running", "GSX wants a password" and "GSX said something this build has never seen" demand three different next moves from whoever reads that log, and one shared word gave them no way to tell. `auth_required` should never occur (`authRequired: false` on every capture, localhost only); it is named precisely so that if it ever does, nobody has to guess. `unknown_verb`/`internal` stay pooled — nothing distinguishes what to do about them — with the raw string preserved in `RawCode` either way.
- **Docking (`Services/DockingGuidanceManager.cs` + `DockingGeometry.cs` + `ProximityBeeper.cs`)** is a standalone state machine (Idle→Armed→Docking→Stopped) fed from the SAME ~30 Hz position handler as taxi guidance but **independent of `TaxiGuidanceManager`**. It owns its OWN `TaxiSteeringTone` instance (lateral cue) + a `ProximityBeeper` (accelerating beep) + spoken metric milestones. To avoid two panning tones, `MainForm` calls `taxiGuidanceManager.SetSteeringToneSuppressed(dockingManager.IsActive)` each frame so only one sounds.
  - `DockingGeometry` is pure static + probe-tested. `alongM` = forward distance to stop, **datum-aligned**: the aircraft DATUM stops at the parking/stop position — an MSFS parking position (and a GSX stop position) is where the aircraft *reference* sits when correctly parked, and the scenery jetway is placed to reach the door for that datum location. **The per-aircraft `gsx.cfg` longitudinal door offset is NOT subtracted from the stop math, and the `SetDoorOffsetMetres` plumbing is removed end-to-end — do NOT reintroduce it.** It describes where the door is ON the airframe, not a stop offset; subtracting it parked a B777 ~26 m short (it had been telemetry-only dead plumbing since that fix). Only the door SIDE cue survives from `gsx.cfg` (see the `GsxAirplaneProfile` bullet). Per-airframe stop depth is the `.py` stop offset's job (`SetStopOffset`), which deice areas keep at `GsxOffset.Zero` (datum-aligned pad). The lateral cue is the **heading-error angle (`hdgErr`)**, NOT `CalculateCrossTrackError` (which assumes the aircraft is ahead of the reference and yields ±180° garbage when docking from behind).
  - **GSX static occupancy clamp (`DockingGeometry.ClampStopToOccupancy`, called in `UpdatePosition` right after `ShiftStop`).** GSX registers an aircraft as PARKED (offers arrival services + operates the jetway) only when its DATUM is inside a circle of radius ≈ the gate's `gatedistancethreshold` centred on `this_parking_pos` (= `_gate.Latitude/Longitude` for GSX gates) — **live-verified at KBOS E13 2026-06-13**: services at ≤25 m incl. 10 m BEHIND the point, reposition past it (so it is a RADIUS, not a forward-only segment; side / `radius{left,right}` do NOT govern static occupancy). The `.py` per-aircraft `SetStopOffset` can push the datum OUTSIDE that circle (KBOS E13 B772: offset → datum 31.5 m > 25 m circle → GSX offered "reposition" after a clean dock — the reported bug). The clamp pulls the post-offset stop back along the gate heading to `gatedistancethreshold − OccupancyClampMarginMetres (2 m)` (FLOORED AT 0 — a malformed profile with `gatedistancethreshold < 2 m` would otherwise pull the datum BEHIND `this_parking_pos`; real thresholds are 15–30 m so this never affects a legitimate gate, probe-locked by the `tiny-threshold` case) **only when** the base stop is itself inside the circle AND the shifted datum would land outside it; it is a **strict NO-OP** for deice pads, navdata-only gates (no `StopLatitude`/threshold), datums already inside the circle, and **VDGS-reliant gates whose stop sits BEYOND the threshold** (EDDF A66: stop 25.1 m, threshold 15 m — those are accepted ONLY via GSX's dynamic VDGS approach-dock, which a static placement even at the exact `.py` target does NOT trigger; clamping them would pull the datum far short of the bar and break jetway reach + the VDGS dock). `ClampBaseStopToleranceMetres (1 m)` keeps the author-set-`gatedistancethreshold == stop-distance` knife-edge (KBOS: both 25) on the CLAMP side despite float/coordinate noise. A one-shot `OCCUPANCY-CLAMP` line goes to `docking-aircraft.log` (latched by `_occupancyClampLogged`, reset per gate in `ResetLocked` — never per-frame IO). Probe-locked (`tools/DockingProbe`: KBOS fires→23 m, EDDF/KATL/inside-circle no-op); a scan of installed GSX profiles found ~850 gates in the affected band across essentially every major airport, so this was a widespread silent failure. Live-verified end-to-end: KBOS E13 (B772 → fixed), EIDW C406 (B738, base stop outside circle → fixed), EIDW C402 (B738, no-op), EDDF A66 (B77W, golden untouched). **Do NOT remove**, do not "simplify" it to clamp on `gatedistancethreshold` unconditionally (breaks EDDF-type gates), and clamp only the `.py`-shifted stop (never the navdata base point).
  - The docking lateral tone uses the **runway-lineup precision profile** (`UpdateHeadingErrorWithThresholds`, 0.5°/1.0°/15°), NOT the width-scaled `UpdateHeadingError` overload (whose `MIN_SCALE` clamp bottoms out at ~1.95°/3.9° — far too loose for parking).
  - `Services/Gsx/GsxAirplaneProfile.cs` reads each aircraft's `gsx.cfg` `[exit<preferredexit>] pos` (col1 = lateral, neg=left), matched by ICAO extracted from SimConnect `ATC MODEL` — **its ONLY consumer cue is the door SIDE** ("Jetway/Door on your left/right" at docking engage); the longitudinal column no longer feeds anything (see the datum-aligned bullet above). The ICAO map is built in the background and refreshed on aircraft change; the build is **single-flight via `Lazy`** (two concurrent multi-second scans no longer race), the `gsx.cfg` scan is **depth-bounded (6)** so texture/sound trees are never crawled, and `UserCfg.opt` parsing **excludes `InstalledPackagesPathNextBoot` lines** (which could resolve a not-yet-active packages path after a relocation). `MainForm.OnAircraftIcaoTypeDetected` locks `_refreshedIcaos` (concurrent `Task.Run` mutations of a plain HashSet) and rechecks the ICAO is still current before publishing the door side, so a late Refresh for the OLD aircraft can't clobber the NEW one.
- **Docking completion stops taxi guidance.** `DockingGuidanceManager` raises a `DockingCompleted` event once on the Docking→Stopped transition (including overshoot), fired OUTSIDE its lock. `MainForm` subscribes and calls `taxiGuidanceManager.StopGuidance()` (thread-safe + silent) so the flow ends cleanly instead of taxi sitting in LiningUp forever after parking.
- **Arrival ownership is ENGAGE-LATCHED, not gate-set.** `MainForm` feeds `taxiGuidanceManager.SetDockingActive(dockingGuidanceManager.IsActive)` — `IsActive` = the docking state machine is in Docking or Stopped, exposed as a **lock-free volatile snapshot** (one fewer docking-lock + zero SettingsManager static-lock reads per 30 Hz frame). Taxi speaks its FULL arrival sequence — parking countdown, "Stop. Hold position.", "Align with X", "Destination reached", "Parking brake." — right up until docking actually engages; once engaged, docking owns the rest of the arrival through Stopped and taxi stays quiet. **Do NOT widen this back to gate-set semantics** (the old `OwnsArrival` = gate set + docking enabled): a navdata gate where docking never engages (approach outside the 70° cone, stop beyond engage range, approximate navdata heading) then arrives in TOTAL verbal silence. The deliberate trade: a brief sequential overlap is possible (taxi's stop callout fires, then docking engages with its own countdown) — that's self-correcting and far better than silent arrivals. The same `IsActive` read also drives the steering-tone mute via `SetSteeringToneSuppressed`. **PENDING-aware wording (third state between "not engaged" and "engaged"):** `DockingGuidanceManager.IsArmedAwaitingEngage` (volatile snapshot, set per-frame in the Idle/Armed branch when detail math is available, the stop resolves >3 m ahead, and engage conditions aren't met; cleared on engage/reset/dispose) feeds `taxiGuidanceManager.SetDockingPending`. While pending, taxi's arrival wording REDIRECTS FORWARD — align announce gains "Then continue ahead for docking guidance.", aligned-enter says "Continue ahead. Docking guidance will take over." (NOT "Parking brake."), the 10 ft countdown directive and stopped-in-zone cue say continue instead of "Stop. Hold position.", and the LiningUp status readout says continue. Why: the GSX stop is routinely tens of metres past the navdata point where taxi's route ends, and a gate's GSX `gatedistancethreshold` can shrink the engage range BELOW that gap — KATL F3 2026-06-11: pilot was told "Parking brake." at the navdata point and sat 26 s at 33.7 m with docking Armed (engage range ~24 m from the gate's threshold), until they crept forward on their own. Announcements only — engage logic, tone ownership, and the engage-latch trade above are unchanged; a pending gate where docking never engages still gets the full (redirected) verbal arrival.
- **Jetway-precise lateral lineup (`DockingGuidanceManager.ComputeLineupError`).** Intercept dead-band tightened **8 ft → 1 ft** (the 8 ft band stopped correcting cross-track below 8 ft, parking up to ~2.4 m off centerline); `SaturationFt` 60 → 40 (a small residual still yields a usable correction angle). Cross-track convergence is a function of DISTANCE travelled, not time (`d(cross)/d(forward) = −sin(angle)`), so it closes the same per metre at 1 kt as at 5 kt — no slow-speed special-casing — and the continuous sqrt ramp never springs a late turn.
- **Final alignment turn completes earlier.** The intercept-fade squares the heading to pure gate heading by **2.5 m out** (`FadeStartM`/`FadeEndM` = 6/2.5, was 4/1), so an over-rotated gate entry (~5° off the taxi turn) finishes the squaring turn with room to creep straight in instead of cramming it into the final metre and stopping ~2° off.
- **Precise, unforgiving stop + persistent "docked" tone.** `StopToleranceMetres` tightened **0.5 → 0.3 m** (drives gate IsStop, the solid tone, and the "GSX docking complete." callout), so the pilot lands within ~0.3 m of the exact stop. The beep plateau is removed: `BeepNearMetres = StopToleranceMetres`, so the accelerating pulse keeps speeding up right to the stop with NO max-speed plateau — the old 2 m plateau made everything from 2 m to the stop sound identical, so pilots read "fast beep" as "stop" and parked short, mid-turn. Now: accelerating pulse = keep creeping; solid tone = stop here. The SOLID continuous tone was previously DEAD CODE — the state machine called `_beeper.Stop()` at the same 0.3 m threshold the solid tone begins, so the beep just vanished at the stop. Fixed: at IsStop the lateral pan tone stops but the beeper is held in its solid mode as a "docked" marker (for how long, see the conclusion bullet below). An OVERSHOOT stop does NOT hold the solid tone — a "docked" marker over a bad park misleads — and no longer disposes the beeper, so a back-up-and-retry dock re-engages with working audio.
- **Completion requires SQUARENESS with the gate axis, not just the stop band.** `IsStop` + the ≤ `StopMaxCrossMetres` (2 m) cross gate were never enough: at KJFK gate 20 (FBW A380, 2026-08-01) the aircraft reached the stop 1.9 m off the line but **17.4° askew** (43.4° true vs a 60.8° gate axis) and still got "GSX docking complete." — GSX refused to register the park and offered *reposition*. Worse for a blind pilot, that callout landed MID-ALIGNMENT-TURN: the one cue meaning "you are done" fired while the turn was still in progress. Completion now also requires `DockingGeometry.IsSquare` (`StopMaxHeadingErrorDeg`, **7°** — deliberately more generous than the ~2 m lateral gate; a couple of degrees off still reaches the jetway, and nagging a good park is worse than letting a marginal one through; widen only on live GSX evidence). An askew arrival is **terminal, not advisory** — it mirrors `IsLateralMiss` exactly (*"Stop. Nose 18 degrees left of the gate heading. Back up and try again."*, `SilenceLocked`, `_overshootStop = true`, `Stopped`, `DockingCompleted`) because the stop band spans along 0.3 → −1.0 m, i.e. **1.3 m of travel — about 1.9° of heading change at an A380's full-tiller radius and ~4° on a 737**. An in-place "finish the turn" instruction cannot be complied with; every askew arrival ends in a back-up regardless, and `RearmBackupMetres` (3 m) already re-arms a clean re-dock. Do NOT reintroduce a non-terminating advisory, and do NOT add an early squareness warning in the squaring zone without live data: during a normal intercept the aircraft is deliberately crabbed up to 35°, so a useful early check needs a tolerance tracking the intercept's squaring fade. Deice pads skip the square gate entirely (wide, datum-aligned) and get no squareness clause in the Y status at all.
- **Spoken steering degrees (engage callout + Y status).** The docking pan tone saturates at `DockMaxPanThresholdDeg` (15°), so a hard-panned ear cannot tell a 16° nudge from a 35° maximum-tiller swing — on a slow-yawing airframe that difference decides how much tiller to use and when to release it. `SteerPhrase` speaks the demand: bands 5-10 "Slight", 15-20 plain, ≥25 "Sharp", rounded to 5 (AwayFromZero), silent inside ±3°. **The strength word is chosen from the ROUNDED number, never the raw angle** — otherwise 12.4° speaks "Right, 10 degrees.", the plain band's word on a Slight-band number. The number fed to the voice is the same variable handed to `UpdateHeadingErrorWithThresholds` on the same frame, so the voice and the pan can never disagree. `AskewDescription` (the squareness phrase) CEILS its degrees rather than rounding, so it can never speak a number inside the 7° gate — an `F0` format turned a not-square 7.4° into "7 degrees". Heading degrees are a permitted verbal quantity; cross-track feet still are not.
- **A verified-good park CONCLUDES guidance — verbal closure + a 3 s hold tone, then silence.** Reaching the stop band on the centerline AND square (the gate above) is a *terminal* state, not a hold-forever one. `CompletionPhrase(deice, hasGsxStop)` composes the closure — *"GSX docking complete. Aligned with gate. Parking brake."* at a GSX gate with a real VDGS stop position, *"Stop. Aligned with gate. Parking brake."* at a navdata-only gate, *"Stop. Parking brake."* on a deice pad (not a gate: no alignment claim, and its square/cross gates were skipped anyway). *"Aligned with gate. Parking brake."* is the wording taxi guidance used at a gate before docking guidance existed — a familiar closure that also tells the pilot guidance is finished until a new route is set. The solid tone then holds `CompletedHoldToneSeconds` (**3 s**) as a positional reference across the moment of stopping — the audio equivalent of a VDGS holding its STOP display for a beat — and fades for good; the Y status switches to *"Parked at the stop. Guidance complete."* **Do NOT restore the old "the tone holds until the pilot presses Stop" behaviour** — concluding verbally while leaving a drone running told the pilot nothing was finished, and the pilot had to press Stop guidance to silence a correct park. The two bad endings are unchanged: an askew stop still gets *"… Back up and try again."* and does NOT conclude (`_overshootStop`, Y status keeps "At the stop. Hold position."), and an overshoot is still silent immediately with no parking-brake prompt.
- **The hold-tone fade MUST be a one-shot `Timer`, never a per-frame countdown.** (Live regression, 2026-08-04: the first attempt counted down in the per-frame `Stopped` branch and the tone never stopped at all.) Completion raises `DockingCompleted` → `MainForm` → `taxiGuidanceManager.StopGuidance()` → the `Inactive` transition → `StopTaxiGuidanceMonitoring()`, and `DockingGuidanceManager` is fed from that same `TAXI_GUIDANCE_POSITION` stream — so **the completing frame is normally the LAST frame this manager ever sees for the arrival**, and anything scheduled "a few frames later" never runs. The same applies to any future "N seconds after the park" behaviour. What must not be dropped: the timer is cancelled at BOTH reset sites (`ResetLocked`, `EngageLocked`) and on dispose, so a taxi-away, back-up retry, Stop button or **re-engaged dock** can never have its live tone killed by the previous park's timer; the callback re-checks `_disposed` + `_completedGood` + `_completedToneStopped` under `_lock` before firing; and cancellation uses the NON-blocking `Timer.Dispose()` overload, since `Dispose(WaitHandle)` would deadlock against a callback already waiting on that lock. The fade runs `EndHoldToneLocked`, which also calls `_beeper.Stop()` — releasing the WaveOut device and its 15 ms tick timer that `SilenceLocked` deliberately leaves alive (after a conclusion there is normally no later frame and no `ResetLocked` to release them). The Stopped-branch countdown that remains is defence in depth with **no live path today** (the feed's only restart is taxi's `Taxiing` transition, and every route load calls `SetDestinationGate` first, which resets `_completedGood`) — it cannot be exercised in the sim, so do not treat it as testable.
- **Concluding is not the same as releasing arrival ownership.** `IsActive` stays true through `Stopped`, so a concluded park still mutes taxi's steering tone and suppresses taxi's arrival callouts on any frame that arrives before a reset. Every live path resets first (`SetDestinationGate` from a new route or Stop guidance, the takeoff-assist / `LandingRollout` clears, or the Stopped branch's own taxi-away / back-up escape) — keep it that way, and do not "fix" the latch by clearing `_isActiveSnap` at conclusion: that would re-open the engage-latched-ownership hole the bullet above exists to close.
- **Docking state lifecycle — Stopped is escapable, every state is exitable.** (a) **Taxi-away disengage uses ABSOLUTE distance, not along-track**: along-track goes NEGATIVE once the stop is behind the aircraft, so the old `alongM > 75` check could never fire for a forward taxi-out and the state (and solid tone) latched forever — raw distance >75 m disengages in ANY direction, including a stale next-flight gate hundreds of km away. (b) **Backing up >3 m past the stop re-arms to Idle** (`RearmBackupMetres`) so a back-up-and-retry dock re-engages through the normal `ShouldEngage` path with fresh audio + milestones. (c) **Disabling docking (or losing the gate) mid-approach fully resets** (`ResetLocked`, not just silence) — leaving `_state` latched at Docking/Stopped kept `IsActive` true forever, muting taxi's steering tone with no lateral cue for the final gate turn. (d) **Stopped-short closure**: engaged + sitting still ≥4 s with 0.3–10 m to go → *"X to stop. Continue forward."* — taxi's stopped-in-zone "Stop. Hold position." cue is suppressed while docking owns the arrival, so docking must provide its own closure instead of an endless fast-but-not-solid beep. (e) **Stale-gate lifecycle**: takeoff-assist activation and `LandingRollout` entry both call `SetDestinationGate(null)` — a stale departure gate could otherwise keep `IsActive` latched on landing and mute the landing-exit rollout steering tone.
- **Gate-lineup "aligned" band is docking-aware; gate lineup NEVER pulses.** Tight (1° / 12.5 ft enter, 2° / 25 ft exit) ONLY while docking is engaged (`_dockingActive` — docking's tone + 0.3 m stop own the precision and taxi's verbal is suppressed anyway); forgiving (4° / 25 ft enter, 7° / 40 ft exit) otherwise, because the navdata parking point is routinely metres off the real stand and demanding ~12 ft to it left correctly-parked pilots permanently "not aligned" (no "Parking brake." cue). The runway-style stopped-misaligned pulse was briefly enabled for gate lineup and is REMOVED — precision parking is docking's job, and pulsing 3 Hz at a correctly-parked pilot demanding precision to a possibly-offset navdata point is a misfeature. Runway lineup keeps its pulse (its centerline reference is authoritative). Do not re-add a gate pulse.
- **One-knot ground-speed callouts (`Services/DockingSpeedCallout.cs`, setting `DockingSpeedCalloutsEnabled`, default ON).** The global `GroundSpeedAnnouncer` works in 5/10-kt buckets, so it is silent across the WHOLE 0-5 kt docking band — the band where speed decides the park. Live A380 telemetry, three consecutive dockings: the aircraft slows correctly to ~1.5 kt around 13-15 m out, then **accelerates into the gate** as the alignment turn straightens and the tyre scrub disappears with thrust still in (0.6 m to run: 4.5 kt run 1, **5.7 kt** run 3). At 1.5 kt the last 8 m take ~20 s; at 4.5 kt under 4 s — and the intercept fades near the stop into a final, *opposite* squaring turn of 7-14°, which a widebody cannot make in four seconds. Every one of those approaches ended askew or ran through the stop. A pilot with one hand on the tiller and one on the thrust levers cannot poll speed by hotkey, so the number has to come to them. Three things about the wiring are load-bearing, all learned the hard way:
  - **QUEUED `Announce`, never `AnnounceImmediate`.** Every other callout on this path is immediate, and immediate INTERRUPTS (NVDA `Speak(msg, true)`, SAPI `SpeakAsyncCancelAll`). This is the only PERIODIC cue here, and a chatty cue must never displace a one-shot instruction — the milestone the pilot is braking for is exactly what an interrupt kills, and braking is exactly what makes the speed change on that frame. Same rule, same reason, as `GroundSpeedAnnouncer`'s own queued callout.
  - **It runs LAST, after the slow-down and milestone one-shots, and is SKIPPED on a frame one of them fired.** Speaking it first does not make speed win — whatever speaks LAST wins the speaker — it only means `Update()` consumes the knot and the phrase is then cut off, so the pilot skips a number outright. Deferring costs one frame (16-33 ms) and the number lands right behind the distance it belongs with.
  - **`EngageLocked` ARMS at the current speed (`Arm`), it does not `Reset`.** The engage callout is seconds of speech (VDGS type, distance to stop, steering demand, jetway side) and the position feed is `SIM_FRAME`, so a "next sample always speaks" re-arm put a number on top of it 16-33 ms later, on **every dock**. `Reset` (speak whatever comes next) stays for the full-reset path, where nothing else is talking. The deadband is `HysteresisKts` 0.6 measured from the last ANNOUNCED integer, not from the rounding boundary: 0.6 rather than 0.5 is what makes a speed parked exactly on x.5 silent (it rounds up but is only 0.5 from the last value), leaving a residual **0.2 kt** flutter band (N+0.6 up, N+0.4 back) — a jitter-sized guard, not immunity. This does NOT replace "Slow down." and does not touch the tone, beeper, intercept profile, squareness gate or state machine; minor overlap with the global announcer at its 0 and 5 kt buckets is accepted rather than special-cased.
- **`SlowDownSpeedKts` is 3.0, lowered from 5.0 (2026-08) — and `SlowDownMetres` must NOT be widened to compensate.** The per-knot callout tells the pilot what the speed IS; "Slow down." tells them what to do about it, and at 5.0 it never got the chance: across the three live A380 approaches above it was silent at 4.0 kt with 5 m to run, 4.3 kt at 2 m and 4.7 kt at 2 m — every one of the failures — and the single time it fired was 5.7 kt at 0.6 m, too late to act on. 3.0 is where the remaining TIME crosses the boundary the failures identified rather than a round number: the 6 m gate takes 2.3 s at 5 kt, 3.9 s at 3 kt, 7.6 s at 1.5 kt, and the final squaring turn of 7-14° is not makeable by a widebody in about four seconds. A well-flown dock is ~1.5 kt at 13 m, so 3 kt inside 6 m is already abnormal and a good profile never trips it. **Widening `SlowDownMetres` is the trap**: the callout is a ONE-SHOT (`_slowDownSaid`, re-armed only at engage/reset), so a wider gate lets it fire harmlessly during the normal deceleration from taxi speed and be SPENT before the band where it matters — the speed threshold is the knob, not the distance.
- **Hot-path perf invariants (do not regress):** docking far-field telemetry + lineup math are gated to `<150 m` raw distance or engaged (`DetailRangeMetres`) — no more 2/s `docking.log` file appends on the SimConnect thread, under the docking lock, for the whole taxi; hold-short label formatting happens only in firing branches and the hold-short/parking/exit-approach/runway-end callout paths early-out once all their latches have fired (don't reintroduce per-frame milestone-table builds); `TaxiAssistForm`'s gate list is cached per ICAO as (spot, resolved node) pairs and the search box / fit filter filter IN MEMORY per keystroke (don't reintroduce per-keystroke `GetGates` + navdata query + nearest-node resolution on the UI thread — matches the `GateTeleportForm` pattern); `SettingsManager.Save` serializes under the static lock but writes the file OUTSIDE it (don't move the IO back under the lock — an options-dialog save mid-approach stalled the 30 Hz position path behind an antivirus-scanned `%APPDATA%` write).
- **`docking.log` telemetry includes absolute coords.** Lines now carry `stopLat`/`stopLon` (computed stop target) and `acLat`/`acLon` (aircraft position) alongside the relative `along`/`crossFt`, so docking's target can be compared directly against a known-correct GSX position.
- **SimConnect heading-unit gotcha (live verification).** SimConnect's `PLANE_HEADING_DEGREES_TRUE` / `_MAGNETIC` are returned in **RADIANS**, not degrees, despite the name — multiply by 57.2958 (180/π) to get degrees (a logged 5.93 = 339.7°). Latitude/Longitude ARE in degrees. Applies to any future MCP/SimConnect live-verification of docking.
- **GSX operational note: engines OFF for services.** GSX will not offer ground services (deboarding/jetway/etc.) while engines are running — it prompts "stop engines to request services." This is GSX behaviour, not an MSFSBA bug; a precise dock with engines running still won't show service options.
- **Verified live (EDDF A66 / B77W, engines off):** offset 5.30 m applied; docking target (50.04691716, 8.56034700) heading 339.9° true; a real dock stopped ~0.6 m short + 0.27 m left of centerline and GSX accepted services — confirming the target is GSX-correct.
- **Distance units (`Settings/DistanceUnit.cs`, `Services/DistanceFormatter.cs`, `Services/DistanceMilestones.cs`).** Default metres, optional feet. `DistanceFormatter` is the DISPLAY layer only — its `UnitProvider` is wired to `SettingsManager.Current.GroundDistanceUnit` at startup (`MainForm`); **never use it for guidance thresholds** (those stay unit-native internally). `DistanceMilestones` returns **unit-native** countdown tables (round numbers in the active unit, e.g. docking 30/20/10/5 m vs 100/60/30/15 ft — NOT literal conversions); triggers stay metric so guidance logic is unaffected. **`GroundTrafficUseMetres` is a SEPARATE, independent toggle** — do not fold it into `GroundDistanceUnit`. **Long taxi distances (>~6000 ft, `TaxiGuidanceManager.FormatDistance`) switch to the big unit MATCHING the setting** — kilometres in metres mode, nautical miles in feet mode; a metric user never hears NM for a ground distance.
