# Stock Cessna 172 Skyhawk (G1000)

> **Read this when:** working on the stock MSFS 2024 Cessna 172 definition (`Aircraft/Cessna172Definition*.cs`, `Aircraft/C172/`).

Design: `docs/design/2026-09-21-c172-design.md`. Scope is option A — the physical panel, COM/NAV/
transponder, background callouts and guidance numbers. No GFC 700 autopilot, no G1000 screen reading,
no V-speed callouts, no throttle.

## Transport

Stock SimVars and stock K: events only, over `SimConnectManager.SendEvent`. No MobiFlight module, no
L:vars, no calculator path — the definition registers no `MSFSBA_BRIDGE_PROBE`, so it neither waits on
the probe nor gets the calc-path warning. The HS787 is the model.

## Two design rules

**Simple switches take MainForm's generic path.** Every Off/On switch, the flaps, the fuel selector and
the parking brake are Continuous + IsAnnounced vars that `ProcessSimVarUpdate` does NOT consume. That is
what gives them the combo refresh, the combo-pick echo suppression and the Ctrl+M mute for free, and the
callout is the generic "Beacon: On". Only what must be composed (the magneto position) or edge-triggered
(the warnings, COM actives, squawk) is handled in the definition — and those are spoken with the
suppressible `Announce`, so MainForm's Step-2.5 `Suppressed` wrap (`c172Muted`) covers them. The stall
warning is the one `AnnounceImmediate`, so it checks the mute set itself.

**The magneto selector is split** (the A380 wiper / ND-filter pattern). `C172_MAGNETOS` is an ACTION
combo — `UpdateFrequency.Never`, no backing var, so it is never REGISTERED and the request MainForm
makes on every panel open is a no-op (nothing is ever delivered, so a delivered 0 can never snap it to
Off) — that writes `MAGNETO1_SET` (0 Off / 1 Right / 2 Left / 3 Both; 4 START is not selectable). The
"Magneto position" STATUS row (`C172_MAG_LEFT`) reads the position composed by `Cessna172Magnetos` from
`RECIP ENG LEFT MAGNETO:1`, `RECIP ENG RIGHT MAGNETO:1` and `GENERAL ENG STARTER:1`. A combo cannot show
a position composed from two vars (MainForm re-syncs a combo only from its own var), so the combo's
selection is the pilot's last pick and the status row beside it is the truth. The position CALLOUT is
composed once per continuous batch in `OnDeferredFlushBatchDelivered` (watch var `C172_MAG_RIGHT`),
because Off→Both flips two vars in one batch and composing per delivery spoke "Left" then "Both". That
hook runs outside the `Suppressed` wrap, so it checks Ctrl+M and the definition's own 3 s pick-echo
window (`_magnetoPickTicks`) itself.

**The "Set magnetos" combo is WRITE-ONLY, and its selection is not a reading.** It has no backing var,
so there is nothing for MainForm to sync it from: it opens on its first item, "Off", on the first open
of a session and after every aircraft switch, whatever the key is actually at. Its selection afterwards
is only ever the pilot's own last pick — and MainForm's combo cache remembers a pick the definition
DISCARDED (a pick made while an engine start is in flight, or the START position, which is not
selectable and is refused), so the combo can sit on a position that was never sent. The **"Magneto
position" status row beside it is the truth** — composed from the three sim bools, so it is what the
key is at whoever moved it, MSFSBA or the G1000. The two carry different names for exactly that reason;
do not "fix" the combo with `ReverseDisplayOrder` or by syncing it to the status row's var, which is
the two-vars-one-combo case MainForm cannot express.

## Start Engine

`Cessna172EngineStart` is a pure machine: `Begin` → `MAGNETO1_SET 4`; every combustion delivery and every
1 Hz batch tick feeds `Tick`; the first true `GENERAL ENG COMBUSTION:1` ends it as "Engine running",
10 s without one as "Engine did not start"; either sends `MAGNETO1_SET 3`. A second press while one is in
flight is ignored, and the magneto combo is ignored too. `CancelDeferredFlush` (aircraft swap, disconnect,
exit) returns the key to BOTH if a start was in flight; `OnSimContextReset` cancels without sending.

A press while the engine is already running (combustion true) is refused aloud with "Engine already
running" and sends nothing; a press with no combustion reading yet proceeds.

## Warnings

Edge-triggered, one-shot per excursion, baseline-first, wiped in `OnSimContextReset` (never in
`ResetAnnouncementBaselines`). Limits in `Cessna172Limits`. "Engine stopped" fires when combustion falls
while airborne or on the ground above 20 kt IAS — IAS, not ground speed, because MainForm swallows the
base `GROUND_VELOCITY` before the definition sees it. Low voltage and the oil warnings are gated on the
engine running.

The continuous batch is NAME-sorted, so on the batch that carries a shutdown `ELECTRICAL MAIN BUS
VOLTAGE` is fed one sample BEFORE `GENERAL ENG COMBUSTION:1` and the low-voltage tracker sees the stale
engine-running gate for that one sample. Harmless, and recorded so it is not re-derived as a bug: the
bus has not collapsed yet at that sample, so nothing fires. The two oil feeds sort after combustion
(`GENERAL ENG OIL …` > `GENERAL ENG COMBUSTION`) and see the gate already closed.

The three engine-gated trackers (low voltage, oil pressure, oil temperature) are re-baselined on every
falling combustion edge, so a second start in the same session is as silent through its normal
oil-pressure/voltage build-up as the first — `ThresholdWarning.Feed(…, enabled:false)` changes no state,
so without that reset the second start would have spoken "Oil pressure low" and "Low voltage".

## Warning feeds vs status rows

A warning FEED is a Continuous var consumed by the definition whose `DisplayName` is its Ctrl+M row label
("Low fuel warning, left tank"). The panel STATUS row for the same quantity is a separate OnRequest key
("Left fuel quantity"). Two keys may share a SimVar name as long as only one is Continuous and batched.

## Radios and transponder

COM standby boxes are keyed `COM_STANDBY_FREQUENCY_SET:n` (the `_SET` renders the entry box) and the
definition claims the write (validate 118.000–136.975, `COM_STBY_RADIO_SET_HZ` / `COM2_STBY_RADIO_SET_HZ`);
success is silent, and it is the STATUS ROW that reads the new standby back — the active-frequency
change that announces itself only happens on a Swap. Both standby keys and the squawk key are therefore
listed in `GetPanelDisplayVariables()` as well as in the controls, so each is readable at rest and not
only when it changes; all three are batch-covered, so the display force-read is a no-op.
`TRANSPONDER_CODE_SET` is claimed too
(`Cessna172Squawk.TryToBcd` → `XPNDR_SET`), so the one confirmation is the "Squawk 1200" the definition
speaks on the Bco16 change — also heard for a G1000 knob change. NAV is Ctrl+N only. The altimeter box
sends `KOHLSMAN_SET` = round(inHg × 33.8639 × 16) (millibars × 16). Transponder mode is read-only until
test-plan item 4 shows the 2024 G1000 honours a stock state-set event.

**Entry boxes render EMPTY unless the definition gives them a `CurrentValueSourceKey`, and an empty
box is not inert** — MainForm parses the text with `double.TryParse` and passes its FAILURE VALUE, 0,
so Enter on an untouched box sends whatever 0 means for that control. The three boxes answer it three
different ways, each deliberate:

- **Mixture** pre-fills (`CurrentValueSourceKey = "C172_MIXTURE_SET"`, seeded on creation and on every
  focus-in from `GENERAL ENG MIXTURE LEVER POSITION:1`). It is the spec's read-back, and it is the
  safety fix: 0 is inside the valid 0–100 range, so an empty box sent `MIXTURE1_SET 0` — idle cut-off
  on a running engine.
- **Squawk** is deliberately NOT pre-filled: the source is the raw Bco16 double (4608 for 1200), which
  the seed would render as "4608". `Cessna172Squawk.TryToBcd` refuses 0 instead, so a blank or garbled
  box is answered with "Invalid squawk code" rather than a silent `XPNDR_SET 0000`.
- **COM standby** is deliberately NOT pre-filled either, and this one is a MainForm limitation, not a
  preference: `seedFromCurrent` renders the cached value as an INTEGER, so 121.900 would seed as "122"
  — a false readout when the pilot tabs in, and a silent set of 122.000 on Enter. The box stays empty
  (Enter on it is refused aloud by the 118.000–136.975 range check) and the STATUS ROW carries the
  read-back. Fixing the seed to honour a decimal format is a fleet-wide MainForm change, not a C172 one.
- **Altimeter** likewise stays empty; its own `C172_ALTIMETER_DISPLAY` row carries the read-back, and a
  blank box is refused by the 27.00–31.50 range check.

The two entry boxes that speak a numeric confirmation (mixture, altimeter) first check
`SimConnectManager.CanSendEvent` and refuse aloud ("Mixture unavailable. Not connected to the simulator."
/ "Altimeter unavailable…") instead of confirming a write `SendEvent` silently dropped — the house rule
that a refused write leaves no false trace; the silent-success boxes (COM standby, squawk) are unchanged,
since silent failure there makes no false claim.

## Uncertain wirings (in-sim test plan item 4)

- Standby battery: `ELECTRICAL MASTER BATTERY:2` / `TOGGLE_MASTER_BATTERY` param 2.
- Fuel shutoff valve: `GENERAL ENG FUEL VALVE:1` / `TOGGLE_FUEL_VALVE_ENG1` (vs the selector's Off).
- Avionics bus set events `AVIONICS_MASTER_1_SET` / `_2_SET`.
- Fuel selector Off (`FUEL_SELECTOR_SET 0`) vs the shutoff valve: two ways to cut the fuel, and which
  one the 2024 model honours (or whether both do) is unconfirmed.
- `PITOT HEAT`: the plan substituted the shorter stock name for the spec's `PITOT HEAT SWITCH:1`;
  in-sim items 3/4 confirm which one reads back.
- Alternate air: no stock var found; not modelled.
Anything that fails ships read-only or is dropped with a note here — never a control that silently does nothing.

## Guidance numbers

Spec §6 values in `GetVisualGuidanceProfile()`; the three flare rows are starting values until measured on a
live pattern circuit (test-plan item 6). `TaxiTurnLeadSeconds` 0.5.

**Career landing lesson.** The lesson locks the throttle and spawns the aircraft about 1.5 nm out and
700 ft above a 3° glidepath (measured 2026-09-22) — a power-off glide where pitch is the only speed
control. Visual guidance's glidepath law fights that (it pitches for the path and assumes power holds
the speed); press **M** for its airspeed mode, which holds the profile's 65 kt with pitch instead. See
docs/visual-guidance.md, "Airspeed mode".
