### FlyByWire A32NX Panel Parity (Phase 3)

The A32NX panel set in `FlyByWireA320Definition.cs` is now at parity with the A380 (`FlyByWireA380Definition.cs`) — every A380 overhead/glareshield/pedestal/ground-services panel exists on the A320, with matching labels. Notes for future maintainers (all live-verified against the running A32NX via the SimConnect MCP calculator path):

- **EFIS is split Captain / First Officer.** The ND mode + range CONTROL is the FCU knob `A32NX_FCU_EFIS_{L,R}_EFIS_MODE/RANGE` — it drives the computed `A32NX_EFIS_{L,R}_ND_MODE/RANGE` DISPLAY output. The bare `A32NX_EFIS_*_ND_*`, `_OPTION` (CSTR/WPT/VORD/NDB/ARPT filter) and `_NAVAID_*_MODE` vars are computed outputs that REVERT a calc-path write (verified) → they stay read-only. The LS button: dev FBW REMOVED `A32NX_EFIS_{L,R}_LS_BUTTON_IS_ON` (the old "directly settable" verdict was the dead-var write-stick trap) — control = the registered input event `A32NX.FCU_EFIS_{L,R}_LS_PUSH`, state = `A32NX_FCU_EFIS_{L,R}_LS_LIGHT_ON`.
- **Anti-Ice:** the `XMLVAR_MOMENTARY_PUSH_OVHD_ANTIICE_*_PRESSED` vars are model press-animation flags that do NOT actuate (same as A380 #56). WING anti-ice = `A32NX_BUTTON_OVHD_ANTI_ICE_WING_POSITION` (the var the cockpit PB writes and the only input `WingAntiIcePushButton::read` takes). ⚠️ **CORRECTED** — this line used to say `A32NX_PNEU_WING_ANTI_ICE_SYSTEM_SELECTED` "holds in flight"; that was a mis-test, the var is a Rust per-frame OUTPUT and any write reverts within 2 s at any phase. `_SYSTEM_ON` is the read-only flowing status. The **A380 uses neither var** — it drives the stock `STRUCTURAL DEICE SWITCH`; never copy wing anti-ice wiring between the two airframes. ENG 1/2 anti-ice = the stock K-event `ANTI_ICE_SET_ENGn` (state from `ENG ANTI ICE:n`), routed in HandleUIVariableSet.
- **Thrust Levers (settable detents)** ported from the A380 (2 engines): synthetic `THROTTLE_ALL_DETENT` + `THROTTLE_{1,2}_DETENT` combos → `THROTTLEn_AXIS_SET_EX1` with the FBW default-calibration axis values (idle `-0.44` verified to snap to the A320 idle dead-zone). The synthetic `_DETENT` keys are EXCLUDED from the GetVariables auto-announce loop (no real L:var to monitor — the loop guard checks `!key.EndsWith("_DETENT")`); the live angle reads from `A32NX_AUTOTHRUST_TLA:n`.
- **Doors** = synthetic `A32NX_MSFSBA_DOOR_{0..5}` combos backed by `INTERACTIVE POINT OPEN:n` (the exit index maps 1:1 to the interactive point on the A32NX; 0-3 = passenger, 4-5 = cargo per `EXIT TYPE:n`), set toggles `TOGGLE_AIRCRAFT_EXIT:n`. The var is a 0..1 animation fraction → ProcessSimVarUpdate announces Open/Closed once per transition (>0.05) and TryGetDisplayOverride renders the state. **Ground Equipment** jetway/stairs are momentary Activate combos → stock `TOGGLE_JETWAY` / `TOGGLE_RAMPTRUCK` (the A320 has no clean state var like the A380's `A380X_GND_*`). The flyPad Ground page (Shift+T) stays the richer ground interface.
- **Audio Control Panel: REMOVED (2026-06 dev-source audit).** The `A32NX_RMP_{L,R}_VHF{n}_VOLUME` L:vars do NOT exist in dev FBW — the physical ACP is unmodeled (tooltip-only dummies in the cockpit XML). The old 5-step volume combos were dead writes and were deleted. If volume control is ever wanted, the only functional mechanism is the stock sim (`COM1/2/3_VOLUME_SET` / `COM VOLUME:n`).
- **Flaps-and-Brakes is intentionally NOT consolidated** on the A320 (it keeps the separate Flight Controls / Speed Brake / Parking Brake panels) — a deliberate divergence from the A380's "Flaps and Brakes".
- **COM radios (RMP panel) — stock events, auto-announced (2026-06).** The A32NX RMP drives the STOCK COM radios (its React panel writes `K:COM*_STBY_RADIO_SET_HZ` / reads the stock simvars), so — UNLIKE the A380 — the stock set + swap events work: live-verified `COM2_STBY_RADIO_SET_HZ` and `COM2_RADIO_SWAP` round-trip. The former separate "Radios" panel was MERGED into the **RMP** panel (frequency tuning IS the RMP on the A320); tab order is deliberate — per-radio **Set Standby**, **Set Active** (= set standby, 100 ms, swap — there is no direct active-set that keeps the RMP display honest), and **XFER** (swap) for COM1 + COM2 come FIRST after the panel list, the rarely-touched RMP power/mode switches last. Set logic lives in `FlyByWireA320Definition.HandleUIVariableSet` (index-aware: COM1 = un-numbered `COM_STBY_RADIO_SET_HZ`, COM2/3 = `COM{n}_STBY_RADIO_SET_HZ`), SILENT on success because **`COM_ACTIVE/STANDBY_FREQUENCY:1/2` are Continuous+IsAnnounced** and `ProcessSimVarUpdate` speaks the resulting change ("COM 1 active 121.500") — Fenix/A380 RMP parity, seeded silently on first sample, airband-gated (118–137 MHz) so unpowered junk caches silently, Ctrl+M-mutable. A swap therefore reads both the new active and new standby. `COM_TRANSMIT:1-3` are also monitored: "Transmitting on VHF n" on the rising edge only. The freq display fields render MHz via `TryGetDisplayOverride` (raw values are kHz) and refresh from the SimConnect cache fallback on panel open (the ProcessSimVarUpdate `return true` skips MainForm's displayValues sink — same idiom as the EFIS baro fields).
- **A380 Speed Brake** — a pedestal "Speed Brake" panel with a Retracted/Half/Full combo → `SPOILERS_SET` (0/8192/16383) + a Disarm/Arm combo → `SPOILERS_ARM_OFF/_ON`, and the handle auto-announced by 10% band. **The Retracted/Half/Full combo is LIVE-VERIFIED (2026-06-18):** `SPOILERS_SET` drives the FBW speed brake even though the stock `SPOILERS HANDLE POSITION` simvar stays 0 — read back the FBW L:var `A32NX_SPOILERS_HANDLE_POSITION` instead (8192→0.5, 16383→~1.0, 0→0). The Disarm/Arm combo (`SPOILERS_ARM_OFF/_ON`) is still unverified.
- **EWD on-demand read** is on BOTH jets via `ReadDisplayUpperECAM` (output mode, Alt+E), each opening the `FbwEwdWindow` pop-out. **Both are now DECODE-based — NO Coherent scrape in the A320 path.** The A320's `BuildEwdWindowTextAsync(sim)` decodes the upper E/WD from SimVars: thrust rating + the single `A32NX_AUTOTHRUST_THRUST_LIMIT` number (the A320 has NO per-engine THR% gauge, unlike the A380), per-engine N1 / N1-command / EGT / N2 / FF / state (2 engines, no N3), reversers, IDLE, and FOB (`A32NX_TOTAL_FUEL_QUANTITY` via `WeightUser`) — plus the ECAM memo/warning lines decoded from the `A32NX_Ewd_LOWER_*` SimVar codes via **`SimConnectManager.GetEcamLineRaw`** (the batch handler decodes those codes to `ecamStringData` strings and `continue`s PAST the numeric cache, so `GetCachedVariableValue` returns null for them — `GetEcamLineRaw` exposes the decoded text). The schematic engine row scraped as garbage ("XX XX"), and the Coherent scrape socket is a documented native-crash risk, so the **A320 scrape was REMOVED entirely** (the old `ReadEwdAloud` method + `_ewdScrapeClient` field are gone); a text placeholder shows when nothing decodes (displays unpowered). The SD page-0 box uses the same decode. **The A380 KEEPS its always-on `CoherentEWDClient` (`EwdMonitor`)** — but only because its newer architecture moved the sensed abnormal/failure PROCEDURES onto an in-process EventBus with NO SimVar (so they can ONLY be scraped); its normal memos decode the same way, and its SD box-scrape fallback goes THROUGH the one always-on monitor socket (never a second client). The A32NX (older FBW) publishes ALL its EWD message content — warnings + actions + memos — as the `Ewd_LOWER` codes, so it needs no scrape. The continuous EWD-line monitor still auto-announces new memos/warnings on both.
- **Autoflight (A/THR / LOC / APPR) is wired via the FBW input events** `A32NX.FCU_{ATHR,LOC,APPR}_PUSH` (A380 A/THR also via stock `AUTO_THROTTLE_ARM`). These are registered FBW **input events** (source: `fbw-a380x/.../SimConnectInterface.cpp`), reached by MSFSBA's `SendEvent` — which routes DOTTED event names through the MobiFlight calc path (`{data} (>K:NAME)`), the shipping transport for all A32NX.* events (see the "SendEvent H:/dotted calc-path gate" section; an older note here claimed the calc K: form no-ops — the FCU events are live-verified through exactly that path). They won't arm on the ground, so ground testing is inconclusive but the wiring is source-correct. Both FCU panels expose engage + disengage + LOC + APPR. The A/THR disconnect is NOT one of these events: it is the stock, undotted `AUTO_THROTTLE_DISCONNECT` (sent with `TransmitClientEvent`), never `A32NX.FCU_ATHR_DISCONNECT_PUSH`, which the FWC reads as an involuntary loss (AUTO FLT A/THR OFF); see "Cleared minimums and the A/THR disconnect" below.
- **Air-conditioning ZONE TEMP selectors** (5th-audit gap): Cockpit / Fwd Cabin / Aft Cabin are numeric °C inputs (`COND_*_TEMP_SET`) → `HandleUIVariableSet` converts to the `A32NX_OVHD_COND_{CKPT,FWD,AFT}_SELECTOR_KNOB` (0..300 ↔ 18-30 °C, live-verified). Actual zone temps `A32NX_COND_*_TEMP` read in the display. **APU AVAIL** (`A32NX_OVHD_APU_START_PB_IS_AVAILABLE`) is a read-only APU-panel field (not auto-announced — the EWD memo speaks it).
- **EFIS baro (altimeter) is per-side + silent on first detect.** Captain = `A32NX_FCU_LEFT_EIS_BARO_HPA` + `_EFIS_L_DISPLAY_BARO_VALUE_MODE`; First Officer = the `RIGHT`/`_R_` equivalents (announced with a "First Officer" prefix). BOTH the HPA and the value-MODE handlers **seed their cache silently on the first read** — otherwise each announced on first detect, which was the "altimeter spoken twice on start" bug. Brake "triple indicator" (`A32NX_HYD_BRAKE_{NORM,ALTN}_{LEFT,RIGHT}_PRESS` + `_ALTN_ACC_PRESS`) + Brakes Hot + GPWS Test were added for A380 parity.
- **Feature parity with the A380:** the A32NX now also has **rudder trim** (FCC display reads `A32NX_FAC_1_RUDDER_TRIM_POS`, an ARINC degrees word, positive = nose-Left, + a Reset combo firing `RUDDER_TRIM_RESET`) and **metric/imperial weight units** (gross-weight + fuel-info readouts follow the EFB `A32NX_EFB_USING_METRIC_UNIT` setting via `WeightUser(kg)`; the EFB "US Units" toggle, Shift+T → Settings, is the control — no separate hotkey). NOT ported (the A320 genuinely can't): **metric ALTITUDE / MTRS** (the real A320 has no MTRS button — A330+/A380 only; NOTE: dev FBW registers a metric-alt-toggle event on the A32NX, but it is INERT on the installed build — the L:var never moves and no consumer exists in any installed bundle, only the ISIS/EFB metric settings do — so it is deliberately NOT exposed, resolved 2026-06-12), and **BTV / OANS / ROW-ROP** (A380/A350 systems).
- **FCU value-entry windows ported (Ctrl+S/H/A/V/P/B).** The A32NX now has its own Fenix-style FCU windows (`Forms/FBWA320/FBWA320{Speed,Heading,Altitude,VS,Autopilot,Baro}Window` + shared `FBWA320FCUWindowBase`), mirroring the A380's — value entry + knob Push/Pull + mode toggles + spoken read-out, replacing the deleted single-field `ShowA320*InputDialog` / `ShowFBWBaroSetDialog`. Thin UI delegating to public `FlyByWireA320Definition` methods: `SetFCU{Heading,Speed,Altitude,VS}Value`, `FireFCUButton(evt)` (readback via an inline event→`RequestFCU*` switch — the A320 overrides `OnPanelButtonFiring` to arm the FCU echo before a panel button's event is sent, but `FireFCUButton` still runs its own readback switch rather than `OnPanelButtonFired`), `RequestFCU{Heading,Speed,Altitude,VS}Readout` (wrappers over the existing private `RequestFCU*WithStatus`/`RequestFCUVerticalSpeedFPA`, which read the `A32NX_FCU_AFS_DISPLAY_*` combine vars), `RequestAutopilotStates`, `SetAltIncrement`. Differences from the A380: **no MTRS/metric toggle** in the Altitude window (real A320 has none); the **Baro** window sets QNH via the proven `A32NX.FCU_EFIS_L/R_BARO_SET` (hPa×16) events (not `CAPT_QNH_SET`/`KOHLSMAN_SET`), **STD/QNH via the `A32NX.FCU_EFIS_L/R_BARO_PULL` (STD) / `_BARO_PUSH` (QNH) knob events — live-verified round-trip 2026-06; the `A32NX_FCU_{LEFT,RIGHT}_EIS_BARO_IS_STD` L:vars are DEAD on the new-FCU A32NX (hold a write but drive nothing, and stay 0 even while actually in STD — the original "STD button doesn't work" bug; dev FBW removed them on the A380 TOO — its STD is now the `A32NX.FCU_EFIS_{L,R}_BARO_{PUSH,PULL}` K-events, read back from `A32NX_FCU_EFIS_{L,R}_DISPLAY_BARO_IS_STD`. **This sentence used to name `H:A380X_EFIS_CP_BARO` + the stock `KOHLSMAN SETTING STD:n` readback; FBW #10855 deleted those H-events, and the A380 now reads the FCU's own per-frame flag instead. The stock mirror is NOT dead — it still tracks both directions — it is simply no longer what MSFSBA reads. See [a380x.md](a380x.md).** CAUTION, the two jets are OPPOSITE: A380 PUSH=STD/PULL=QNH (live-verified 2026-06-11 in the installed fcu.js onPush/onPull), A32NX PULL=STD/PUSH=QNH — never harmonise them). STD state reads `A32NX_FCU_EFIS_L_DISPLAY_BARO_VALUE_MODE == 0`** (mode 0=STD/1=hPa/2=inHg; the mode carries no unit info while in STD, so the window keeps the last known entry unit), unit via `A32NX_FCU_EFIS_{L,R}_BARO_IS_INHG` (dev FBW REMOVED `XMLVAR_Baro_Selector_HPA_*` from the A32NX — exactly inverted vs the A380, where the XMLVAR is live and IS_INHG is stuck). The Ctrl+B window is now Fenix-style (Mode/Unit combos + value box, 2026-06). **Autopilot panel (Ctrl+P)** identical to the A380 (shared `A32NX.FCU_*` events + `A32NX_*` state vars). The A380 FCU windows are Gus's; these are the A32NX mirror.

- **A32NX System Display now has 12 pages (added ENG + F/CTL).** The `A32NX_MSFSBA_SD_PAGE` combo offers E/WD(0), ELEC, HYD, PRESS, APU, COND, WHEEL, BLEED, FUEL, DOOR, **Engine(10)**, **Flight Controls(11)**. Verified live: `2 (>L:A32NX_AUTOBRAKES_ARMED_MODE_SET)` arms MED, the SET var auto-resets to -1. The FCU value-set events likewise work via the calc-K path (live-verified: HDG/SPD/ALT/VS incl. signed VS round-trip through the `A32NX_FCU_AFS_DISPLAY_*` readback vars).

- **Status-display boxes refresh live — F5 AND auto, without yanking the reader cursor (both jets).** The SD-page status box renders the aircraft def's `_sdPageContent`, an OnRequest **snapshot** that is ONLY rebuilt by `OnDisplayPanelShown → RefreshSdPageDisplayAsync` (which re-reads the underlying SimVars: FOB, engine N1/N2/N3, per-tank fuel, …). **The core bug:** the F5 / Refresh handler re-requested the panel's display vars and re-rendered, but never rebuilt `_sdPageContent` — so it re-printed the SAME stale snapshot and "FOB 13400 KG" never moved, *even on a manual F5*. Fix: the refresh (now `MainForm.RefreshDisplayNow`, run by the 1 s tick, by F5 and by Ctrl+3 onto an empty list; the Refresh button was removed once the list updated itself) calls `OnDisplayPanelShown(currentPanel)` (fire-and-forget; it pushes its own `UpdateDisplayText` ~0.6 s later when the fresh read completes). Non-SD panels no-op (each def gates on its own panel key: A380 = "ECAM Control Panel", A32NX = "System Display").
  - **The status display is a LISTBOX, not a TextBox (2026-07 rework).** The generic `_DISPLAY_` control is a read-only navigable `ListBox` (one synoptic row per item); every write goes through `MainForm.UpdateDisplayText(ListBox)` → **`Forms.DisplayList.UpdateInPlace`**, which rewrites ONLY the rows whose text changed, grows/shrinks the tail in place (never `Items.Clear()`), and restores the selection by ROW CONTENT — matching the occurrence **nearest the old index** (status lists contain duplicate/blank rows) and **clamping to the last row** when the list shrinks past the cursor (never dropping the selection to -1). A ListBox item-text update never touches a caret, so NVDA's cursor stays on the row being read; a row whose value actually changes re-announces while focused (intended live behaviour). The old TextBox path + its `SetDisplayTextPreserveCaret` wrapper were REMOVED from MainForm. All MCDU/CDU/DCDU forms, the pop-out windows (E/WD, OANS, RMP, HS787 display + EICAS, GSX menu, Weather Radar — via the shared `Forms/DisplayListBox` control), and the ECL now reconcile through `DisplayList.UpdateInPlace`; per-form selection semantics (title/page force-select, CDU positional index restore, ECL FWS cursor-follow) run caller-side after the call. `DisplayText.SetPreserveCaret` survives with a single caller (the OANS Airport tab's one-line box); the GSX status/tooltip boxes keep plain unchanged-guarded `.Text` writes.
  - **Auto-refresh** (`MainForm._sdAutoRefreshTimer`, **1 s**, started/stopped by `StartOrStopSdAutoRefresh()` per panel — only panels with a `_DISPLAY_` status list): each tick rebuilds any snapshot SD content via `OnDisplayPanelShown` AND force-reads the panel's display vars directly (`RequestVariable(…, forceUpdate: true)` — no more `PerformClick`/2 s-timeout dance), then schedules a repaint. Repaints are **coalesced by `ScheduleDisplayRepaint`**, a one-shot 120 ms timer armed by the FIRST push and NOT restarted by later ones — a bounded leading-edge coalesce. **Do NOT make it a restart-per-push trailing debounce**: hand-fly/takeoff-assist stream `PLANE_PITCH/BANK/HEADING` per SIM_FRAME (~30-60 Hz), those are PFD/ISIS display vars, and a trailing debounce starves — the "live" list froze exactly while hand-flying. **`UpdateDisplayText` always overwrites `displayValues` from `GetCachedVariableValue` first** — displayValues alone goes stale for def-handled vars (`ProcessSimVarUpdate` returns true → the Step-3 write is skipped: A32NX COM freqs, A380 EFIS baro, HS787 flight data); the old 3 s tick masked that by `displayValues.Clear()` via the old Refresh button. **Nothing clears `displayValues` any more, F5 included:** for a row the cache never holds (the iFly 737's SDK-fed `PMDGVar` rows, which `RequestVariable` cannot re-read and whose live text comes from `TryGetDisplayOverride` only while a stored value exists) a clear blanked the row to "--" until the aircraft reloaded. F5 runs the tick's own `RefreshDisplayNow` without the combo skip, ignores its key auto-repeat, and speaks "Status display refreshed" ([CORE-7]). The tick still skips while a selector combo is focused; the refresh shows "Loading..." only on the first **empty** populate. Perf invariant: the per-event "is this var in any panel display" gate in `OnSimVarUpdated` uses **`GetDisplayVarNamesCached()`** (a HashSet keyed on the aircraft instance) — never call the defs' `GetPanelDisplayVariables()` per event; it rebuilds its whole dictionary each call (the same lag class `_varCache` fixed for `GetVariables`).
- **Master Warning / Caution acknowledge — clears the aural too (live on the A380, source-correct on the A32NX).** The acknowledge PBs are momentary **buttons** (`Btn`, pulse L:var 1→0) not combos. **A380:** the FBW glareshield.xml HOLD_SIMVAR is misspelled `PUSH_AUTOPILOT_MASTER`**`A`**`WARN_L/R` (extra A) — verified live: pulsing that clears `A32NX_MASTER_WARNING` + cancels the aural, while the no-A name is a no-op; caution `PUSH_AUTOPILOT_MASTERCAUT_L/R` is spelled normally. **A32NX:** `CLEAR_MASTER_WARNING`/`CLEAR_MASTER_CAUTION` already pulse `PUSH_AUTOPILOT_MASTERWARN_L`/`MASTERCAUT_L` (no extra A — the conventional A32NX name; the typo was A380-specific) 1→0 via `HandleUIVariableSet`, rendered as buttons. **DEFERRED (verify when loaded in the A32NX):** confirm the A32NX master-warn/caut pulse actually clears `A32NX_MASTER_WARNING`/`_CAUTION` + the aural live (source XMLs aren't in this fbw-aircraft checkout to cross-check the var name); if the no-A name no-ops like the A380 did, switch to `MASTERAWARN`.

### FlyByWire A32NX Accessible MCDU

**Feature:** Screen-reader-accessible MCDU for the FlyByWire A32NX, opened with **Shift+M** (input mode) — same shared `HotkeyAction.ShowFenixMCDU` dispatch as the other CDUs, selected by `AircraftCode == "A320"` (Fenix is `FENIX_A320CEO`, so no collision). **Single MCDU (Captain) by design** — see the protocol limitation below.

**CRITICAL — the protocol cannot separate Captain and First Officer MCDUs.** FBW's `A320_Neo_CDU_MainDisplay.sendUpdate()` builds ONE `screenState` from its own display and assigns that same object to BOTH the `left` and `right` keys of every `update` message (only `annunciators`/brightness differ). (Earlier notes described one broadcaster per MCDU writing interleaved; the current FBW build runs a SINGLE MCDU instrument — see below — and the no-separation conclusion is unchanged.) So `content.left == content.right` in every message (verified live: 100% of messages) and a Left/Right selector cannot pick one MCDU — it only drives the two physical MCDUs apart, making the shared display flip last-writer-wins (this was the "adjusting one side changes the other" bug). We therefore mirror FBW's own web remote MCDU exactly: **only ever control the Captain MCDU (`event:left`) and read the single shared screen (`content.left`).** Do NOT reintroduce a side selector or `event:right` — the separation is not achievable over this transport. **The Coherent transport cannot separate them either:** FBW's `panel.cfg` declares ONE `A32NX/MCDU/mcdu.html` gauge on the shared MCDU texture, so a single instrument (a single `A32NX_MCDU` Coherent view) draws both screens — there is no second view to read.

Until the fresh frame arrives the window keeps what it showed. WHY: SimBridge is a separate process the sim never launches, it crashes or hangs on long sessions, and a hung SimBridge still reads as connected to the aircraft (`McduServerClient` reconnects only on socket close), so the MCDU was simply gone until it was restarted. ⚠️ Coherent GT allows ONE inspector socket per view: once the MCDU window has been opened the service OWNS the `A32NX_MCDU` view for the aircraft session, reconnect gaps included, so the D / Shift+D flight-info script always rides `FlyByWireMCDUService.EvalOnMcduViewAsync` (`MainForm.AnnounceA32NXFlightInfo`; "Flight management not ready." while it reconnects) and a one-shot `CoherentEvalClient` eval is used only before the window has ever been opened, or when the Coherent client could not load its agent. The old "no persistent Coherent socket on the A32NX" policy was retired by the maintainers on 2026-09-25.

**Key components:**
- **`Services/FlyByWireMCDUService.cs`** — the facade (see Transport): owns `SimConnect/CoherentA32nxMcduClient` + `Services/FlyByWireSimBridgeMcduClient`, drives `FbwMcduTransportArbiter` on the UI context (both clients post there), forwards `DisplayUpdated`/`ConnectionStatusChanged`/`PrintReceived`, routes `SendButtonPress` by what can deliver the key (Coherent whenever it holds the view, the relay otherwise — see Transport), and exposes `EvalOnMcduViewAsync` for the one-socket-per-view rule (the view itself is owned through `CoherentViewOwnership`). The class remarks document the no-separation limitation for BOTH transports.
- **`Services/FbwMcduFormat.cs`** — decodes curly-brace cell markup (`{green}`/`{small}`/`{sp}`/`{end}`/…) into accessible text and builds the shared `MCDUDisplayData` (extended with `Page`/`Arrows`/`Annunciators`). Mixed-color lines with a green segment mark the active option with `*` (same convention as Fenix) — ONE `*` per green value: FBW sends a value as touching pieces (`10.2`, `/`, `0213`), and a piece that continues a green run gets no star of its own. The star takes NO column of its own where the line has room: `PositionLine` lays the 24 columns out first, then writes each `*` into a spare blank in front of its value, or inserts it and pays the column back from the next gap, so right-hand values stay on column 24 for braille. FBW pads cells with U+00A0 as well as `{sp}`, so `ParseSegments` turns U+00A0 into a plain space as a cell is decoded (and the public `PositionLine` does the same for the DCDU's undecoded text) — nothing downstream sees one, so none can overwrite a neighbouring cell, and titles, scratchpad and cell values carry plain spaces too. FBW draws its entry boxes (`[  ]`, `/[   ]`) from the same character, so the blanks between `[` and `]` are the field's width: `PositionLine` never seats a `*` there or pays one back from them. Write U+00A0 as an escape in these sources, never the literal character (it looks exactly like a space) — `FbwMcduFormatTests.Source_spells_the_no_break_space_as_an_escape` fails on one. **This is a 1:1 mirror of `tools/fbw-mcdu-probe/mcdu-format.js` — keep both in sync.** **CRITICAL — `{`/`}` are overloaded.** They delimit `{tag}` markup AND are the MCDU's literal LSK arrow/bracket glyphs (e.g. a selectable runway renders as `{08L{small}-ILS{end}`). `parseSegments` therefore consumes ONLY *known* tags (colors / `small` / `big` / `left` / `right` / `sp` / `end`); a lone `{` or `}` is the glyph — dropped, with its content kept. Do NOT revert to greedy "`{`…`}` is always a tag" parsing — it ate the runway designators (`08L` etc.) and broke the DEP/ARR pages. **Lines are reconstructed positionally** via `PositionLine` (24 cols: left-aligned left, right-aligned right, centred centre), NOT by dropping blank columns — otherwise a right-only cell collapses onto the left of the line.
- **`Forms/FlyByWireA320/FlyByWireMCDUForm.cs`** — ListBox display + scratchpad TextBox + page buttons (no side selector — single Captain MCDU). LSK keys use the shared `MCDUUseAlternateLSKKeys` setting (Ctrl/Alt+1–6 or F1–F12). Annunciators + page number + ▲▼◄► page-arrow hints render into the display. Only background-state changes are announced per the screen-reader rule, decided by the pure `Forms/FlyByWireA320/FbwMcduReadBack` (`FbwMcduReadBackTests`): a page title once per page and only while the window is OPEN (a page reached while it was closed is spoken when it next shows); the scratchpad through the shared `CduScratchpadAnnouncer` on a 100 ms tick, spoken once it has shown for 400 ms — the tick re-samples the LAST frame, so a count of ticks is a duration, not a count of reads, and 400 ms is longer than one Coherent read with the window open (250 ms plus an eval of up to 150 ms), so there a value seen in a single read (a redraw caught mid-way, or FBW's 150 ms blank before the next queued message) is not spoken — a closed window reads once a second and speaks only FMS messages; each typed key holds the read-back 600 ms, from before it is sent and again once it is delivered, so an entry is read back once, whole; and while the window is CLOSED only an FMS message (a scratchpad that gains text, e.g. DEST EFOB BELOW MIN) — never a page title or "Scratchpad cleared". Connection changes are spoken only while the window is visible.
- **`tools/fbw-mcdu-probe/`** — standalone Node CLI (`watch`/`press`/`type`/`replay`, `--export` JSONL captures) to inspect, drive, and capture the MCDU over the websocket without the C# app. `replay` re-renders an exported capture offline (shareable for diagnosing a page without a live sim). `mcdu-format.js` is the authoritative decode reference; `node --test` covers it.


### Fenix A320 cockpit controls — new "Cockpit" panel section (2026-06)

`FenixA320Definition.GetPanelStructure` has a **"Cockpit"** section with 6 panels (five arrived in 2026-06 as previously uncovered, live-verified-settable L:var combos; Cockpit Door was added in 2026-10). Their writes route through `SetLVar` → the MobiFlight calc path unless a bullet says otherwise:
- **Cockpit Door** (the first panel; before 2026-10-23 the overhead VIDEO pushbutton sat in Overhead and the pedestal button in Cockpit Other as "Cockpit Door Video"): "Cockpit Door" Closed/Open (`S_COCKPIT_DOOR`, a model L:var, 0 closed, 1 open, and a written value holds, measured 2026-10-23), "Overhead Video" (`S_OH_COCKPIT_DOOR_VIDEO`, the overhead VIDEO pushbutton as an Off/On combo) and "Pedestal Video" (`S_PED_COCKPIT_DOOR_VIDEO`, a press button with no light of its own, so it says "Pedestal Video pressed"). The door is the one the First Officer closes before start and opens at shutdown (`FenixActionExecutor.SetCockpitDoor`, the same write). It is `Continuous` + `IsAnnounced`, so it says itself when it moves, whoever moved it; a panel set is the combo's own echo ([CORE-8]). The pedestal OPEN light (`I_PED_COCKPIT_DOOR_U`) and the overhead CTL upper light (`I_OH_DOOR_CTL_U`) are lit while the door is open (measured 2026-10-23) and mirror it, so they are silent; the pedestal FAULT light reads "Cockpit Door Fault". The Fenix's own cockpit hides the door's clickspot while the jumpseat is deployed and the jumpseat's while the door is open (`FNX32X_Interact_Cockpit_Door_Template` and `_Jumpseat_Template`, 3.0.0.7426), and an L:var write skips that, so the panel refuses the same two moves (`FenixA320CockpitDoor`): opening the door with the jumpseat out says "Stow the jumpseat first.", deploying the jumpseat with the door open says "Close the cockpit door first."; closing the door and stowing the jumpseat are never blocked, and an unread value never refuses. The overhead VIDEO pushbutton's light `I_OH_COCKPIT_DOOR_VIDEO` is an OFF legend (VIDEO set to 0 lights it, measured 2026-10-22), and the pedestal press leaves it unchanged, which is why the pedestal button has no light. Left out, measured 2026-10-23: the pedestal UNLOCK/NORM/LOCK switch (`S_PED_COCKPIT_DOOR`, 0/1/2: a written position holds until written back, and neither end moves the door or lights anything) and the cabin keypad, which the Fenix does not model (no keypad in its cockpit, cabin or galley models, EFB, FAP or documents; its help center says its keypad only beeps "on CDLS startup"), so there is no entry request for the switch to answer. The First Officer's Shutdown step and hand-tick open the door without the jumpseat check (`FenixFlowDefinitions` `SD_COCKPITDOOR`); only the panel refuses.
- **Captain Seat / First Officer Seat** — Seat Height (`S_SEAT_HEIGHT_*`), Seat Distance (`S_SEAT_DISTANCE_*`), Armrest L/R (`S_ARMREST_{LEFT,RIGHT}_*`). Seats are **3-position direction switches** (Height: Down/Stop/Up; Distance: Aft/Stop/Forward) that HOLD the written value — the seat moves while at Down/Up (0/2) and the model **auto-centers the switch to Stop (1) at the travel limit** (no per-frame motor-tick needed, unlike the A380's `SEAT_*_MOVE_*` 0-100 position vars). The Height/Distance combos are `Continuous+IsAnnounced` so they track that spring-to-Stop silently (see the monitor section); armrests are `OnRequest` (2-position, no Stop).
- **Windows and Shades** — sunshades + window blinds (`S_SUNSHADE_*`, `S_WINDOW_BLINDS_*`).
- **Standby Instruments** — `S_STANDBY_COMPASS`, and `S_STANDBY_ATTITUDE_CAGE` only on a livery with the round standby gauges (hidden when the variant has an ISIS, see "Fenix v3: variants").
- **Cockpit Other** — Headset first (Off/On; see "Fenix v3: variants"), jumpseat (Stowed/Deployed, interlocked with the door as above) + headrest, oxygen-mask covers, gravity gear extension (one control, below), F/O DCDU brightness (a spring-loaded switch; see "Fenix v3 panel-control fixes"). The cockpit-door video button left this panel for Cockpit Door. (NOTE: the overhead emergency-call guard `S_OH_CALLS_EMER_Cover` is NOT here — it was already defined+paneled in the overhead Calls panel; an early duplicate was removed.)

**Gravity gear extension (v3, 2026-10).** v2 had two controls, "Gravity Gear Extension" and "Gravity Gear Crank", and neither extended the gear on v3. The v3 crank is `S_HYD_GRAVITY_GEAR_EXTEND`, 0 to 3 turns in 0.05 steps, plus a stow handle `S_HYD_GRAVITY_GEAR_HANDLE` (cockpit template `FNX32X_Interact_Emergency_Gear_Lever_Template`: the handle is raised, the crank then turns at 10 Hz, and the model lets the handle go back down only at crank 0). `S_HYD_GRAVITY_GEAR_EXTEND_ROTATION` is gone. It is now ONE combo, Stowed/Extended, and a pick runs `FenixA320GravityGearWalker` (`MoveGravityGearAsync`): extending raises the handle, waits 300 ms, then writes the crank 0.05 at a time every 100 ms up to 3 (60 writes, about 6 to 7 s; the owner measured the crank 0 to 3 in 6.4 s, 2026-10-22); stowing writes it back down in reverse and lowers the handle LAST. A second pick before it finishes is refused aloud ("Gravity gear: crank already turning."), and a crank the walker cannot read moves nothing ("Gravity gear: no read-back, nothing moved."). The result is spoken once, about 6 s after the pick, from a fresh read of the crank: "Gravity gear: cranked 3 turns." or "Gravity gear: crank stowed." (never write 1: that is a third of a turn). Two measured facts shape it. (1) The data service reads the crank as whole numbers (1, 0, 1 on the way up, 0 at the end) and never 3, and reads the handle as `""` (model only), so the check is the L:var read-back over SimConnect (`ReadFreshAsync`), never the data service. (2) The same trap as the MD-11's walked controls ([MD11-8]/[MD11-27]): while a move runs, the crank's own deliveries are consumed silently in `ProcessSimVarUpdate` (otherwise MainForm's combo refresh snaps the pick back to Stowed mid-walk, found in the owner's check), and one forced read re-syncs the combo to where the crank really is when the move ends (a refusal does not force one: the move still running does its own). Pinned by `FenixV3FixGravityGearTests`. Checked on the ground on 2026-10-22 (Extended stays Extended, "cranked 3 turns", Stowed, "crank stowed"); the real gear drop in flight is unproven.

**Fenix cockpit controls not built** (each needs different handling than a plain `SetLVar` combo — implement as `RenderAsButton` pulses / increment events): the **momentary buttons** `S_PED_DFDR_EVENT` and `S_PED_AIDS_PRINT`, and the DCDU2 keypad (LSK/MSG/PG/PRINT — it would be control-only since the DCDU2 display isn't readable; only the F/O DCDU brightness switch is built); the **encoders** `E_STANDBY_ALT_IMPERIAL_BARO` and `E_STANDBY_ALT_METRIC_BARO` (the analog standby altimeter's baro knobs) and `E_MIP_CLOCK_SET` (the clock's SET knob, see "Fenix v3: variants"); and **controls left out on purpose**: `S_AUDIO_SWITCHING` (accepts 1/2, not 0), `S_CHART_LIGHT_TEMP_CAPT/FO` (uncertain semantics), and the pedestal cockpit-door UNLOCK/NORM/LOCK switch `S_PED_COCKPIT_DOOR` (measured 2026-10-23 and left out, above). The clock buttons and switches (`S_MIP_CLOCK_CHR/ET/RST/SET/UTC`), the ISIS baro push (`S_MIP_ISFD_BARO_BUTTON`) and the recorder's ground control `S_OH_RCRD_GND_CTL` (a button in the overhead Voice Recorder panel) ARE built.


### Fenix monitor manager (Ctrl+M) — now DYNAMIC + clock counters default-off (2026-06)

`FenixMonitorManagerForm` previously listed a **hardcoded 10 keys** (master warnings/cautions + ECAM CLR) — the "weird version". It now enumerates **every `UpdateFrequency.Continuous + IsAnnounced` var** from the aircraft def (mirroring `FBWA380MonitorManagerForm` / `FlyByWireA320MonitorManagerForm`), sorted by display name. Unchecked keys persist to `UserSettings.FenixDisabledMonitorVariables`; `MainForm.OnSimVarUpdated` (~683) already gates on it. Most Fenix cockpit controls (comfort/standby/gravity-gear etc.) are `OnRequest` panel combos — not monitor entries — EXCEPT the 4 seat height/distance switches, which are `Continuous+IsAnnounced` (so the combo can track the spring-to-Stop) but seeded default-silent (see below).

### Fenix momentary buttons are a full PRESS-RELEASE, not press-only (2026-07 — stuck-button fix)

**Every Fenix panel pushbutton routed through `FenixA320Definition.ExecuteButtonTransition` now pulses `0 → gap(200ms) → 1 → hold → 0` — it RELEASES back to 0.** The old code stopped at 1 (`0 → 200ms → 1`), leaving the button **held down for the whole session**. Fenix pushbuttons are momentary (`S_…` catalog value is literally `"0: Off, 1: Press"`): the systems logic latches the effect on the **`0→1` rising edge** and keeps it in a **separate `I_…` indicator**, so releasing to 0 afterwards is the correct real-cockpit behavior and **never loses state** — live-verified that the latched state PERSISTS after release for RMP mode selects (`I_PED_RMP1_VHF2`), EFIS filters (`I_FCU_EFIS1_CSTR`), and ECAM SD page selectors (`I_ECAM_HYD`). For pure momentary actions (ECAM CLR/RCL/EMER CANC, ADIRS keypad, master-warning cancel) the release is a no-op. So the release is **safe + correct for all ~150 buttons** — do NOT revert `ExecuteButtonTransition` to the press-only form.

**Why it mattered — the stuck `S_ECAM_TO` (TO CONFIG test) bug:** that test is **level-triggered** (active only while the button is held at 1). Held-at-1 forever, it stayed inert in flight (FWC inhibits it) but **re-fired against the landing config after touchdown** — once below 80 kt in FWC **phase 9** (on-ground, engines running, no inhibit) → a spurious red `CONFIG` + `SLATS/FLAPS NOT IN T.O. CONFIG` + master-warning aural on rollout. Live-proven: writing `1 (>L:S_ECAM_TO)` fires `I_MIP_MASTER_WARNING_CAPT`; writing `0` clears it. `S_ECAM_STATUS` had the same latent stuck-at-1 (fixed by the same release). `ExecuteButtonTransition` takes an optional `pressHoldMs` (default `ButtonPressHoldMs = 200`) and `confirmPress` (says "<name> pressed" when the press lands; only for a button with no light of its own, [CORE-7]). The 200 ms hold stands on v3: measured 2026-10-21 on 3.0.0.7426 (ECAM DOOR page button `S_ECAM_DOOR`, pulsed 0, 1, 0 on the ground with ground power), holds of 200, 100 and 50 ms each flipped `I_ECAM_DOOR`, and a 20 ms hold (about one frame) was missed. The First Officer's executor releases the same way (`LVarActionExecutor`'s held pulses), which settled the old worry that its writer had the same stuck-at-1 bug.

**TO CONFIG (the panel's ECAM TO CONFIG button and the First Officer's "Takeoff config test") says its result from a watch of fresh reads, `FenixTakeoffConfigVerdict.WatchAsync` ([FNX-4]).** The panel button (`RunTakeoffConfigTestAsync`) holds `S_ECAM_TO` for `HoldMs` (1.5 s) through `ExecuteButtonTransition` and releases it (the level-triggered test must never stay at 1, above); the First Officer pulses the same button for the same time (`FenixActionExecutor.TakeoffConfigTest`, its watch started BEFORE the pulse because the dispatch gate may delay the press). Both then speak the watch's verdict, in the same words. The watch reads three on-request `_READOUT` twins ([A320-41]: `S_ECAM_TO`, and the captain's `I_MIP_MASTER_WARNING_CAPT` and `I_MIP_MASTER_CAUTION_CAPT`) every 200 ms over SimConnect, never the data service, so the verdict does not depend on the gateway. It times from the press it observed itself (the button reads released, then pressed; a button already held needs a release first, and a press it never sees gives "no result read"; the panel waits up to 3 s for it, the First Officer up to 30 s). A lit master warning gives "Takeoff config: check configuration." at once (a late warning outranks a caution), a lit master caution "Takeoff config: caution. Check the ECAM.", an unread light "Takeoff config: no result read. Check the ECAM." and never "normal"; "Takeoff config normal." comes only when both lights read dark at or past `VerdictAfterMs` (2,100 ms) after the press. There is no pre-press baseline, so a warning lit before the press also gives "check". The sighted equivalent is `TO CONFIG NORMAL` on the E/WD.
Why a watch: the Fenix v3 changelog says the warning computer was rebuilt with deliberately delayed MASTER WARN and MASTER CAUT, and the v2-era code (hold 1.5 s, then one cached read of the 1 Hz lights, via `AnnounceTakeoffConfigResult` and `TakeoffConfigTestHoldMs`) said "Takeoff config normal." over a bad configuration in all three bad runs. Measured 2026-10-21 on 3.0.0.7426 (A320, engines running, parking brake set, flaps 0, a probe polling the data service every 150 to 200 ms, so times are detection to detection): the first lit light came 1,015, 1,009 and 809 ms after the press (MASTER WARNING, captain and first officer; a lit warning reads 2 on the data service and flashes 1/0 over SimConnect); it went out about 1 s after release (+1,017, +974, +905 ms), and MASTER CAUTION followed about 0.5 s after release and stayed lit until reset. Flaps 1 with trim and speeds set lit nothing in 27 s. `VerdictAfterMs` is the slowest press-to-light time plus 1 s, rounded up to 100; a shorter value lets a slow warning arrive after "normal" was spoken, so re-measure it after a Fenix update that touches the warning computer. Owner checks 2026-10-22: flaps 0 gave "Takeoff config: check configuration.", flaps 1 gave "Takeoff config normal.", the First Officer's Taxi "Takeoff config test" with flaps 0 gave the failure verdict, and the panel's 200 ms press gap never beat the watch's first read in five presses. Pinned by `FenixTakeoffConfigVerdictTests` and `FenixTakeoffConfigWiringTests`. Known and not built: the panel watch and the gravity-gear walker can outlive an aircraft switch by a few seconds.


### Fenix MCDU window: the data service connection (2026-10)

The Fenix MCDU window (`Forms/FenixA320/FenixMCDUForm.cs`, `Services/FenixMCDUService.cs`) reads the screens from the Fenix data service, a GraphQL server on port 8083: one `graphql-transport-ws` subscription for the screens, and one HTTP POST per key edge (`writeInt` 1, then 0 after 50 ms, on `system.switches.S_CDU{n}_KEY_<key>`). Fenix v3's own web MCDU writes only the 1; the pulse stays because the 0 is what lets the MCDU recognize a second press of the same key, and a typing check on v3 (2026-10-22: AAB1 entered with no doubled letters, Backspace clearing it) showed the 0 is not counted as a second press. v3's MCDU screens decode on the same 24-column grid as v2's (`FenixMcduV3ScreensTests` pins the MCDU MENU, ARRIVAL, PERF TAKE OFF and ATSU captures of 2026-10-21/22; MCDU MENU lists `<ATSU` where v2 had another line, and `<FMGC` is green). Known and left: the ARRIVAL title reads "ARRIVAL TO *KMCO", because the green rule marks the green destination (long-standing; the owner ruled it not worth chasing). Address it as `127.0.0.1`, never `localhost` ([A320-40]): it listens on IPv4 only, and Windows spends about 2 s refusing `::1` on every new connection. The key client's pooled connection goes after about a minute idle, so the first key press after a pause used to stall about 2 s (measured 2,005 ms against 1 ms). The receive loop answers the service's 15-second `ping` with a `pong`, and the app disposes the service on exit as well as on an aircraft switch.

**Both MCDUs live.** One subscription carries `aircraft.mcdu1.display` and `aircraft.mcdu2.display` (`FenixMcduSides`), and each `next` message names its screen. `FenixMcduScreens` keeps the latest screen of each side as raw XML; only the selected side is parsed, shown and spoken, and a side switch shows the stored screen at once, with no reconnect (it used to disconnect and resubscribe, paying the 2 s address penalty). A dropped connection clears the stored screens, so a switch never replays a stale one; a switch while disconnected retries the connection at once instead of waiting out the backoff. Key presses go to the selected side (`FenixMcduSides.KeyRef`). The connection messages name no side: "MCDU connected" / "MCDU disconnected".

**Ctrl+Shift+L / Ctrl+Shift+R** switch to the left / right MCDU from anywhere in the window, the side selector included (MD-11 precedent, `FenixMCDUForm.SideShortcut`). Off the selector the app says "Left MCDU" / "Right MCDU" before the page title; on it, only the title, because the screen reader reads the new item ([CORE-7]). Pressing the chord for the side already shown changes nothing on screen, so off the selector it says just "Left MCDU" / "Right MCDU" (a silent key would sound dropped); on the selector it stays silent. On the selector, the window's MCDU keys leave the list's own keys alone (Alt+Up/Down, F4, a letter), through the MD-11 window's `KeyRouting.ComboBoxNeedsKey`.

### Fenix FCU and altimeter readouts read on request (2026-10)

Output-mode Shift+H/S/A/V and B each force-read two values. Their continuous originals (`N_FCU_*`, `I_FCU_*_MANAGED`, `B_FCU_VERTICALSPEED_DASHED`, `N_FCU_EFIS1_BARO_*`) stream on their own once-a-second subscriptions (ExcludeFromBatch since `f500915db`), and since `c5c624a84` a forced read of such a var waits for its next delivery instead of replacing the subscription: up to a second before the readout spoke. The readouts now read on-request twins, `<name>_READOUT` (`FcuReadoutVariables`), answered within a frame ([A320-41]). The originals keep their subscriptions, Ctrl+M rows and the FCU set windows' cache reads, and a readout no longer swallows one of their deliveries. The wording is unchanged, except that the altimeter inches are written invariant (29.92 on a German or Swedish Windows too, never 29,92), in the B readout and the Ctrl+B confirmation. The Ctrl+B set's ±1 verify waits for the next delivery (`ReadFreshAsync`) instead of reading the cache after a forced read, which on these vars is a no-op: a cache older than the counter write made the correction repeat the whole delta.

**The V/S and the baro windows on v3 (2026-10-22).** Fenix v3's `N_FCU_VS` carries the LIVE vertical speed while the V/S window is dashed (`B_FCU_VERTICALSPEED_DASHED` = 1, a managed climb or descent; v2 held it still), and the app spoke it every second or two (a collaborator's v3 flight, 2026-10-21: dashed from 13:40, `N_FCU_VS` 3400, 1700, 4100, 3400 between 14:09 and 14:12). `ProcessSimVarUpdate` now only peeks the dashed flag (so "FCU VERTICAL SPEED DISPLAY: Dashed" and "Shown" still speak) and consumes `N_FCU_VS` silently while the flag reads exactly 1; an unread flag, 0 and NaN do not silence it (`FcuVsIsSilenced`). So the V/S is spoken only while its window shows a selected value, with its sign ("FCU VERTICAL SPEED: +300", a descent "-300", as the FBW A320; `SimVarDefinition.SpokenNumberFormat`, opt-in and shared). The flag is cleared only when the variable cache is cleared, not on a reconnect or flight load (a reset there wiped the seeded flag, against `IAircraftDefinition`'s reset contract). Two races are accepted: the first selected value after a V/S pull may arrive before "Shown" and stay unspoken (the next turn speaks), and after a connect one live V/S may be spoken before the dashed flag arrives. The typed V/S (`SetFCUVS`) aims its first write from the live V/S while the window is dashed (the owner left that unchanged on 2026-10-22), then, since 2026-10-24, steps from the value the window shows, read fresh with its dashes flag; a window still dashed after a write ends the set with "Vertical speed still dashed, not …" ([FNX-20]; what the Fenix shows after the first click on a dashed window is not measured). Owner check, 2026-10-22: connected with the V/S window already dashed, a managed climb stayed silent; a pull said "Shown" and the turns were spoken; the dash back said "Dashed".
The Ctrl+B window (`FenixBaroWindow`) sets both sides and confirms from a read of both: "Both altimeters set: 1015, 29.97." when the two sides read alike (both units kept, the owner's choice), else each side by name ("Captain altimeter 1015, 29.97. First officer altimeter 1014, 29.94."), with "still in STD" or "not read" for a side that did not take it (`AltimeterSetText`); it used to read the captain's side alone as "Altimeter set: …". A typed QNH leaves STD with a push step, so it always ends in QNH whatever the knob's count after cockpit pulls and pushes, and the window's QNH/STD pick pulls or pushes the STD counters instead of writing a fixed value ([FNX-5]). ### Fenix MCDU selected-option marker — colour ALONE is not enough (2026-08)

**Symptom:** the CONFIG > FAILURES page (Failures = LSK 2R) cycles FAILURE TYPE between NONE / MINOR / ALL, but the MCDU window rendered `1: ←NONE/MINOR/ALL  RANDOM*` — **no accessible indication of which option was active**, on any of the three settings. Same for FAILURE RATE (REALISTIC / HIGH).

**How the Fenix encodes a selection.** The `aircraft.mcduN.display` dataref carries inline single-letter codes — colours `a c g m w y`, font sizes `s` (small) / `l` (large), all lowercase and case-sensitive so uppercase display text is never mistaken for a code. A selected option is marked **TWO ways at once: cyan (`c`) AND large font**, with its siblings small + white. Live capture, failure type = ALL, then after ONE `LSK1L` press:

```
before: c£wsNONEl/sMINORl/cALLw  cRANDOM*w    → ALL  is cyan+large
after:  c£wcNONEw/sMINORl/sALLl  cRANDOM*w    → NONE is cyan+large
```

Both markers moved together, which is what establishes the convention (it is also the standard Airbus "selected option is large, the others small" idiom). There is **no failure-mode dataref** — all 481 datarefs were enumerated and only `I_CDU1_FAIL`/`I_CDU2_FAIL` match "fail" — so the display markup is the ONLY source of this state.

**Root cause:** `StripFormatCodes` discarded both signals. Size codes were skipped unconditionally, and the one marker it emitted (a leading `*`) was gated on GREEN: `hasMixedColors = distinctColors.Count > 1 && distinctColors.Contains('g')`. This page's selection is cyan, so the gate was false and nothing was marked. The green-only assumption dates to the original Fenix MCDU commit (`07ba886e`) and had never been revisited.

**Fix:** the decoding moved to `Services/FenixMcduFormat.cs` (pure + unit-tested, mirroring `FbwMcduFormat`), which keeps the per-character large/small flag and adds a **second, additive** rule: within a whitespace-delimited field holding a `/`-separated option group, mark the one option in LARGE font while every sibling is small. The original green rule is preserved byte-for-byte (colour segmentation still splits on every colour code, even a repeated one — verified by differential fuzz: 200 000 random size-code-free inputs decode identically to the pre-fix implementation). Result: `←NONE/MINOR/*ALL` and `←*REALISTIC/HIGH`.

**Rule ordering is an invariant, and the shared marker set is NOT what prevents double-marking.** The colour rule must run FIRST, and the size rule then skips any option token the colour rule already claimed. The `HashSet<int>` only collapses an *identical* index, and the two rules deliberately anchor differently — rule 1 on the green segment's first character, rule 2 on the option's first letter/digit. When a green option starts on a non-alphanumeric (`(`, `[`, `←`, `-`), those anchors differ and the set does nothing: `wsAl/g(B)` decoded to `A/*(B)` before the fix went in and would have decoded to `A/*(*B)` — "star paren star B" on a screen reader — without the per-token overlap check in `MarkFieldIfOptionGroup`. Do not "simplify" that loop away.

**The `currentLarge = true` initial value is load-bearing, not a fallback.** A line starts large and only an explicit `s` makes it small. The NONE-selected capture above carries no size code anywhere before `NONE`, so `NONE` reads as large purely from that initial value — flip it to `false` and that whole capture silently stops marking. The cost is that an unsized-but-meant-small first option would be marked (`ABC/sDEF/sGHI` → `*ABC/DEF/GHI`); the Fenix always emits `s` explicitly to go small, so that shape does not occur in practice. Both facts are pinned by tests.

**The `SpecialChars` glyph table uses `\uXXXX` escapes on purpose.** The keys are Latin-1 supplement characters (`¤ ¥ ¢ £`) matched against live dataref text; as literals in a BOM-less UTF-8 file they would mangle if the file were ever re-saved as CP1252, breaking arrow decoding at RUNTIME with no compile error. Do not "modernise" them to literals.

**Do NOT "simplify" this to a colour test.** Broadening the colour rule to "green or cyan" is the obvious-looking fix and it is wrong: cyan is used throughout the MCDU for entry fields, brackets and the leading `←` cycle arrow, so it would emit an asterisk on nearly every line — including `*←` on this very line. The size rule is deliberately conservative and bails out unless there are ≥2 options, each option's letters/digits are uniformly one size, and EXACTLY one is large; that leaves page counters (`1/1`), labels (`FROM/TO`) and same-size values (`250/.78`) untouched. A token's size is read from its **letters/digits only**, so the always-large `←` prefix can't misreport the first option as selected. The group is bounded by whitespace so the adjacent TRIGGER column (`RANDOM*`) is never pulled in as a fourth option.

`MCDUDisplayData.Lines[]` (the 24-column `SplitLine` pairs) is written but never read — the Fenix form renders `RawLines` — so the marker's column shift has no consumer. If a future feature starts reading `Lines[]`, re-check that truncation.

### The FBW A32NX MCDU does NOT have this bug — checked live, no code change (2026-08)

`FbwMcduFormat` drops `{small}`/`{big}` as "styling only" (`DropTags`, line ~27) — structurally the same assumption that caused the Fenix bug above — so the FBW A32NX was probed live to see whether it loses a selection the same way. **It does not. `FbwMcduFormat` was deliberately left unchanged; do not port the Fenix size rule to it.**

**Method:** ~350 cells across 11 pages read straight off SimBridge (`ws://localhost:8380/interfaces/v1/mcdu`), dumping RAW cell markup so the size tags stay visible: MCDU MENU, INIT A, PERF TAKE OFF RWY, RADIO NAV, INIT FUEL PRED, DATA INDEX, F-PLN, AIDS, ATSU DATALINK, AOC MENU, ATC MENU. (`tools/fbw-mcdu-probe` does the same job but needs Node, which this machine lacks — a throwaway `ClientWebSocket` console app was used instead. Note SimBridge streams updates continuously, so the first frame after a key press is usually STALE: drain to the LAST frame, and never cancel a `ReceiveAsync` to do it — that aborts the socket.)

**Result: zero instances of the Fenix idiom** (a `/`-separated group of ≥2 real options with exactly one large among small siblings). FBW *does* use the size tags meaningfully, but for the other Airbus convention — **large = pilot-entered / entry field, small = FMS-computed, default, or optional**:

```
INIT A          big:"---"   small:"36090"        CRZ FL entry     / TROPO default
PERF TAKE OFF   big:"___"   small:"    F=---"    V-speed entry    / computed F-speed
RADIO NAV       big:"[  ]"  small:"/[    ]"      VOR ident entry  / optional course
```

Those are adjacent FIELDS in one cell, not competing options. Selection/availability on the FBW MCDU is carried by **colour** instead (`{green}<FMGC (REQ)`, `{inop}NAV B/UP>`), which `DecodeCell`'s existing mixed-colour green rule already surfaces.

The RADIO NAV rows are the closest false-positive candidate — they carry both a `/` and mixed sizes — and the Fenix rule would correctly ignore them anyway: `[  ]`/`[    ]` contain no letters or digits, so the `firstAlnum < 0` guard disqualifies the group. The conservatism guards hold against FBW markup too.

**Two things this sweep could NOT reach — re-check them before calling the FBW fully clear:**
- **PERF APPR.** FBW gates PERF page selection on flight phase; on the ground in preflight `NEXTPAGE`/`PREVPAGE` do not move off TAKE OFF. PERF APPR carries `LDG CONF` (CONF 3 vs FULL), the one genuinely mutually-exclusive pair on an A320 MCDU.
- **A populated F-PLN.** No flight plan was loaded, so F-PLN was empty. On a populated F-PLN, FBW renders *entered* speed/altitude constraints large and *predicted* values small — the same number carrying different meaning with no other cue. That would be a real gap of a DIFFERENT kind (not "which option is selected" but "is this value mine or the FMS's"), and it needs a loaded flight plan to observe.

### Fenix v3 panel-control fixes (2026-10-21/22)

Fenix v3 (3.0.0.7426, released 2026-10-21) renamed a few names and showed that many panel controls never moved like the cockpit's. All 443 panel controls were checked against the v3 package model (the `FNX32X_Interact_*` cockpit templates) and the uncertain ones measured live on 2026-10-21 (A320-214 CFM on the ground, ground power, every value restored). The mechanisms are [FNX-5] (counters), [FNX-6] (press buttons and spring switches) and [FNX-7] (lamps); the long measurements are in their full texts, and the pilot-visible results are here. Fenix 2.x is no longer supported.

- **Names v3 changed.** `B_ELEC_BUS_POWER_DC_SERIVICE` (Fenix fixed its own typo) is `B_ELEC_BUS_POWER_DC_SERVICE`, and `I_OH_DOOR_VIDEO` is `I_OH_COCKPIT_DOOR_VIDEO`; both were never announced until renamed. `I_OH_ELEC_COMMERCIAL_U` is gone (only `_L` exists). `doors.entry.*` became `doors.control.*` on the data service and `system.config.Units.Weight` is gone (the weight unit is the settings API's `weight_unit`). All 16 `FNX2PLD_*` L:vars are gone from the definition: they came from FenixQuartz, a separate tool that is discontinued and that v3 does not feed, and every one read 0. The First Officer's take-off speeds and the take-off calls read the Fenix's own `N_MISC_PERF_TO_V1/VR/V2` instead (below). A pilot's Ctrl+M mute of a renamed key is carried over by `SettingsManager`'s `FenixRenamedMonitorKeys` (`FenixRenamedMonitorMuteTests`). The 13 FenixQuartz rows and the COMMERCIAL upper-legend row leave the Ctrl+M list (they never spoke). The ADR 1-3, IR 1-3 and Bus Tie lamps keep their keys under new names ("ADR 1", "IR 1", the owner's choice), so existing mutes stay.
- **Counters.** Knobs and push/pulls step from the sim's own value through `CounterStepCode`, never from an app-side count (details: [fenix-increment-decrement.md](fenix-increment-decrement.md)). Because they go through the MobiFlight calculator channel (`ExecuteCalculatorCodeUnique`), they need the MobiFlight WASM module, as the FCU push/pull always did. Baro STD is "EFIS Left Baro Pull (STD)" and "Push (QNH)" (and Right), like the FCU knobs, and its state is read from the EFIS QNH light `I_FCU_EFISn_QNH` (1 QNH, 0 STD), announced as "EFIS1 BARO STD Status"; the First Officer's baro setting works the same way.
- **Press buttons.** A control built from the model's `Button_Momentary` template is a press button, not an Off/On combo: the template is a counter (the cockpit adds 1 on press and 1 on release), so a held "On" flipped the function once whatever its state and "Off" did nothing. Turned into `RenderAsButton` presses through `ExecuteButtonTransition`: Bus Tie, Service Interphone Override, Avionics Compartment Light, the radar's GCS, ACP PA Transmit and CALLS Mech/All/Fwd/Aft; CALLS Mid and Exit (A321), the clock's Chronometer Start/Stop, Chronometer Reset and Date, ISIS Baro Push and the pedestal's Pedestal Video were added as presses. One with a light of its own stays quiet (the light speaks); one without says "<name> pressed" once ([CORE-7]): GCS, Service Interphone Override, Avionics Compartment Light, CALLS Mech/All/Fwd/Aft/Mid/Exit, the clock buttons, ISIS Baro Push and Pedestal Video. Other `ExecuteButtonTransition` buttons without a light are still silent on press (known, not changed), and a Pull when already in STD (or a Push already in QNH) is silent, since the read-back is the QNH light changing.
- **Spring-loaded switches.** The model's `Switch_3Position_Hold` springs back only when the cockpit mouse lets go, so a written end stays where it was written: Cargo Discharge 1 and 2 (the model's tooltips give 0 "Agent 2", 1 "Rest", 2 "Agent 1"; the old Off/On combo fired agent 2 on "Off" and could not choose agent 1), F/O DCDU brightness (it ramped to its limit) and the clock's Elapsed Time knob at Reset (a written 2 stayed 2). `PulseSpringSwitch` writes the end, writes the middle after `ButtonPressHoldMs`, and forces one read so the open combo shows the middle again (WinForms ignores a pick of the index already shown, so the same end could not be picked twice); DCDU brightness therefore takes one step per pick. Elapsed Time Reset shows Stop again about half a second after the pick.
- **OFF legends.** A button whose light is an OFF legend sets `SimVarDefinition.StateLitText` to "Off" and `StateDarkText` to its dark text, shared and opt-in (only the Fenix sets them). ADR 1-3 and IR 1-3 (the `_L` lights) read "On" with the light dark and "Off" lit, and so do the lamps' own announcements ("ADR 1: Off"); the Bus Tie reads "Auto" with its light dark and "Off" lit ("Electrical Bus Tie: Off"); the overhead VIDEO pushbutton's light likewise says "Off" when VIDEO is set to 0. The Bus Tie's state is heard twice after a press (NVDA reads the button's new label, then the lamp announces), against [CORE-7]'s once; the owner judged it fine (2026-10-22), and a later pass could mark the lamp in the UI-set echo gate. Two lights never answered on the ground with ground power, `I_OH_LIGHTING_AVIONICS_COMPT` and `I_OH_SVCE_INT_OVRD` (0 for every press, 2026-10-21), so they are not those buttons' state.
- **Other corrected panels.** The overhead gained a **Flight Control Computers** panel (ELAC 1 and 2, SEC 1 to 3, FAC 1 and 2); `BuildPanelControls` had assigned `["Flight Controls"]` twice and the pedestal list won, so they were never reachable. **Generator 1** switches GEN 1 (`S_OH_ELEC_GEN1`); it used to press the EMER ELEC GEN 1 LINE button (`S_OH_ELEC_GEN1_LINE`). Manual Vertical Speed Up and Down were reversed (manual pressurization: Down closes the outflow valve, Up opens it, checked 2026-10-22). The ADIRS System Display has its four positions, and the weather radar Image Selector reaches all four modes, both in the real selectors' order (not yet confirmed live: the ADIRS display needs a GNADIRS livery and the radar a ND read). The thrust levers were checked and left alone (input 0 settles at near-idle reverse, N1 22.7, not full reverse). **N1 MODE** (Engine N1 Mode 1 and 2) is registered once, as an on-request switch like every other Fenix switch (it had two registrations in one initializer and the announced copy won), so a change made outside the app is no longer announced by the switch itself and its two Ctrl+M rows are gone; the IAE lights announce the state (below). The master warning light is spoken "On" when lit: it reads 2 on the data service and flashes 1/0 over SimConnect (measured 2026-10-22), and used to be spoken "Master Warning Captain: 2".
- **Take-off calls.** The Fenix calls "V1", "Rotate" and "V2" from the speeds on the MCDU's PERF TAKE OFF page (`N_MISC_PERF_TO_V1/VR/V2`, followed live: enter or change them any time before the roll) through the shared `TakeoffVSpeedCallouts` machine (`FenixTakeoffCallouts`; mirrored rule [TKO-5]), whether or not Takeoff Assist is on, as the A32NX, the A380 and the MD-11 do (see "Take-off roll callouts" above). Each call is muted with its speed's Ctrl+M row, and a cleared speed (`NotSetBelow = 1` on the three speeds: a cleared speed reads 0) is spoken "not set". Takeoff Assist no longer calls "V1" or "rotate" on the Fenix; its 80 and 100 knot calls stay. The Fenix's own warning computer also calls "V1" aloud (`FWC_V_ONE_L/_R` in its cockpit `sound.xml`; it plays no Rotate or V2), so V1 is heard twice: the owner chose to keep all three app calls (2026-10-22), as on the A380. Flown 2026-10-22 with Takeoff Assist on: V1, Rotate and V2 each once, and the Fenix keeps the speeds after liftoff (no "not set"). A pilot cannot clear a speed to test the "not set" wording (the Fenix MCDU refuses CLR on V1, as the real FMGS): unit tests only.
- **Known and not built.** On v3 the owner heard a flood of fuel, generator and other light announcements at engine and APU power changes, and "OverheadMisc Toilet, on" at the gate. The app announced those lights before v3 too, so the likely cause (a guess, not measured) is that v3 itself moves more lights (the cabin simulation, lights cycling on a power transfer) and the app speaks each change, as it always has. Deciding which lights to quiet needs a recording of the lights through a power change, which has not been made. An ISIS baro readout from `N_MIP_ISFD_BARO_HPA` / `_INCH` is not built.

### Fenix v3: the data service (the gateway on port 8083)

The data service on port 8083 (the one the MCDU window has used since v2) is, on v3, served by the Fenix's gateway (its log is `C:\ProgramData\Fenix\FenixSim A320\logs\log-GqlGateway.log`). It serves, on `127.0.0.1` only (IPv4, [A320-40]): GraphQL over HTTP POST at `/graphql` and over a `graphql-transport-ws` WebSocket at `ws://127.0.0.1:8083/graphql`; REST paths under `/fenix/…`; and the Fenix's own web apps, the EFB (`/?target=external#/efb`) and the FAP (`/fap/index.html`). `Services/FenixDataService` is the one client of the Fenix windows list's windows and of the First Officer (the MCDU window keeps its own connection, above). `FenixA320Definition.DataService` creates it on first use; `OnSwitchedAway` disposes it after the background Stops and KEEPS the disposed instance, which is inert (reads give Unknown, writes false, queries null, `Subscribe` does nothing), so a late callback cannot bring a live service back, and a service nothing had touched is built and disposed too. `Dispose` aborts the socket without a close handshake: the gateway drops the subscriptions with the connection, and it runs on the UI thread during an aircraft switch.

- **Reads.** `ReadAsync` / `ReadManyAsync` send one query `query { dataRef { r0: dataRef(name: "…") { value } r1: … } }`; every name asked for is in the answer (`FenixDataQueries.ParseReadMany`). Values are `FenixDataValue` (kinds Number, Bool, Text, Array, Object, Null, EmptyOrUnknown). **A name the gateway does not know reads `""`**, not an error and (v3 change) not null: `FenixValueKind.EmptyOrUnknown`, "no data", never 0, false, off or closed ([FNX-1], measured 2026-10-21: `doors.entry.d1l` and `system.config.Units.Weight` read `""`; Fenix 2.4 answered null). A Fenix not loaded or a gateway down also reads Unknown. Names look like `system.numerical.N_FCU_SPEED`, `system.switches.S_CDU1_KEY_A`, `aircraft.engines.1.n2`, `aircraft.communication.cids.cabinReady`, `doors.control.d1l`, `aircraft.fuel.total.amount.kg`; `system.numerical.N_CONFIG_AIRCRAFT_TYPE`, `_ENGINETYPE` and `_ACT_COUNT` read `""`, which is why variant detection stays on the SimConnect L:vars.
- **Writes.** `WriteIntAsync` / `WriteBoolAsync` / `WriteFloatAsync` / `WriteStringAsync` send `mutation ($name: String!, $value: <Int!|Boolean!|Float!|String!>) { dataRef { write<Kind>(name: $name, value: $value) } }`; a float goes out with an invariant decimal point and NaN or infinity is never sent. `true` means the service accepted the write (HTTP 200, no errors, `write<Kind>` not false), not that the sim changed: read it back.
- **Settings API.** `GetSettingsAsync` / `GetSoftwareVersionAsync` run `query { settings { softwareVersion state { settings { key category value possibleValues source type writable } } } }` (146 options on an A320 CFM, 149 on an A321 IAE, where it measured 22.7 KB in 2 to 27 ms). A change is the EFB's own mutation, `settings { setSetting(setSetting: {key, value, persist}) { success } }` (`value` always a string: "true"/"false", the enum name), and a reset `settings { setDefault(key) { success } }`; the app builds both in `FenixOptionEdits` (the Fenix documents window's pin writes the same `setSetting`, from `FenixDocumentPins`). **The settings query lags `setSetting` by up to about 2 s** ([FNX-13]): the write answers `success` at once but the next read can still show the old value (measured 2026-10-22, 3.0.0.7438: every pin and unpin took effect, yet the read straight after showed the old list and the new one 0.4 to 1.9 s later). So a write's result is read back with `FenixSettingReadBack.AwaitAsync` (every 250 ms, up to 16 reads, 3.75 s, injectable delay, immediate stop on cancellation), which the documents pins and the options window share; the two differ only in a read that gets no answer: the documents window's `FenixDocumentPins.AwaitStateAsync` goes on through it, the options window stops at it (each such read can take the data service's 10 s time-out). Settings hold the pilot's credentials; code that shows, speaks or logs them masks `FenixOptionKeys.Secrets` by EXACT key ([FNX-19]).
- **FAP API.** The cabin window's operations are `fap { pram { state { bgmOn bgmChannels … } } announcementsVariant { … } }` and `fap { pram { <mutation> { success } } }` (`FenixCabinPram` holds the bundle's mutation texts verbatim); see the Cabin window below.
- **REST.** `GetRestAsync` / `PostRestAsync` (a 2xx body, else null; POST sends `Content-Type: application/json` as the EFB does): the documents window's GETs and the failures window's GET and POST (below).
- **Subscriptions.** `Subscribe(names, callback)` runs the `dataRefs(names:)` subscription (`subscription ($names: [String!]!) { dataRefs(names: $names) { name value } }`, the one the Fenix EFB itself uses) on one shared socket that opens on the first subscription, reconnects after 3, 6, 12, then every 30 s, and subscribes every live subscription again after each reconnect. The callback runs on a thread-pool thread, never the UI thread, so a form marshals with `BeginInvoke` inside try/catch ([FNX-2], [A380C-6]); the service itself never speaks or touches a control. A subscription the service ends (`complete` or `error`) stays registered and gets nothing until the next reconnect. **The subscription is NOT a stream of every name** ([FNX-10], measured 2026-10-22 on the IAE A321 with two ACTs, a raw subscription held through an engine start and a shutdown beside a recorder polling twice a second): it sent `aircraft.engines.{n}.n2` once, when it opened, and never again (one value through a whole shutdown, 62.3 % to 5 %), and opened cold and dark even that first value failed (`Any cannot coerce the runtime value of type System.Double`; a query answers null there); the running flags (on change), EGT (about every second while it moves) and the fuel total (every 2 s) did stream. A query answered a fresh N2 every time. So a value that must stay fresh is read with `FenixDataPoller`: one `ReadManyAsync` of its names a second, reads never overlapping, an answer arriving after `Dispose` dropped, a failing read or throwing callback logged once and swallowed. Its users today: the First Officer's two N2 values (`FenixFoLiveReadings.PolledNames`), the Engines window's 16 non-flag values (`FenixEngineNames.Polled`), and the Cabin window and the app-wide cabin monitor (`FenixCabinNames.All`, one localhost query a second each). The running flags come from the subscription only (a stale poll would speak a false "stopped"), and an older poll answer never overwrites a newer subscription value (`FenixEngineSnapshot.ApplyAllIfUnchangedSince`). Which other names stream was measured only for the few above: for another name, hold a raw subscription beside a polling recorder, or poll it.
- **Names come only from open sources** ([FNX-3]): the gateway's own EFB and FAP web bundles (the pages the service itself serves; `tools/fenix-gateway/fetch_gateway_bundles.py` downloads them read-only into a folder of your own, never committed, and writes `data-names.txt` and `gql-operations.txt` beside them), names the app already uses, and HubHop; each is then checked against the running service, which an unknown name answering `""` makes possible. Never guess a name and never ask the service for its schema (introspection, `?sdl`, the IDE page): ruled out on purpose with Fenix 2.4.0.4720 and not retried or worked around since (2026-10-21): a vendor's deliberate block is the developer's decision, the principle behind the Fenix display program's refusal of .NET inspection (measured 2026-10-11). If a value the app needs is not published under a name found this way, the route is the AI picture reads. The bundles' operations touch `dataRef`, the subscription, `settings`, `fap` and `navigraph`, plus REST under `/fenix`; the app never sends the two `navigraph` operations (`accessToken`, which returns the pilot's Navigraph token, and `disconnect`, which ends the Fenix's Navigraph connection): `FenixDataServiceClientTests.No_Fenix_code_sends_a_navigraph_operation` scans for it.
- **Background seams.** `FenixA320Definition.Hooks.cs` declares optional `partial void` seams: variants (`FenixA320Definition.Variants.cs`), and a Start/Stop pair each for the cabin and the engines. Only the cabin pair is implemented (`FenixA320Definition.Cabin.cs` starts the app-wide `FenixCabinReadyMonitor`); the engine pair (`StartEngineBackground`, `StopEngineBackground`) has NO implementation and there is no `FenixA320Definition.Engines.cs`: the Engines window reads its own values while it is open. `Start` runs once per definition instance, on the UI thread, from the first `ProcessSimVarUpdate` that gets past the take-off IAS feed (that branch returns first, so it can come up to about a second after the instance's first update); a sim reconnect keeps the instance, so Start does not run again; a late update after `OnSwitchedAway` (on quit, `Disconnect` pumps messages for 500 ms) does not start one on the disposed service (`EnsureFenixBackground` skips when `DataService.IsDisposed`). Every seam call is isolated (`RunSeam`): an exception is logged and never aborts a switch or skips the data-service dispose. Tests set `FenixA320Definition.BackgroundSeamsEnabled = false` (`FenixTestHost`'s module initializer) so they never open a socket; the shipped default `true` is pinned by `FenixBackgroundSeamsTests`.

### Fenix v3: the EFB window and its accessibility layer

`Forms/Fenix/FenixEFBForm` hosts the Fenix EFB page, `http://127.0.0.1:8083/?target=external#/efb`, in a WebView2 ([FNX-8]: the `external` target keeps Tab, PageUp/PageDown/Home/End and the physical keyboard, where a sim target such as `sim-capt` swallows them and drops the focus 2 s after a click; 127.0.0.1 because `localhost` pays the `::1` refusal, [A320-40]). It used to carry the comment "already screen-reader accessible", which was true of v2. **The v3 EFB is not accessible on its own** (tour of 2026-10-21, every app opened read-only in the same Chromium engine): the home tiles, the app switcher and the home button are not buttons and not Tab stops, and the home button and the switcher's pictures have no names (once in an app there is no way back to the home screen); Ground Services' 14 switches and every Settings on/off option read "switch, on"; the Takeoff and Landing entry boxes read their placeholders ("----") and their drop-downs nothing; Mass and Balance's boxes read only their limits ("Max 180"); selections show by color alone (Settings' picture choices, Landing's runway condition, a failure's armed or failed state); the MCDU and FAP tiles leave for pages a screen reader cannot use; loading notices are plain text. The Charts moving map is out of reach by nature.

- **The layer** (`MSFSBlindAssist/Resources/fenix-efb-accessibility.js`, [FNX-9]) is injected on document creation, before the first navigation, and gives the page roles, names, states, Tab stops and key handlers; it never makes a request, moves or removes a node, or writes text or a value, so a press does what the page does. Enter and Space on a handled element call the page's own `click()` (never when the key comes from a text box); Alt+Home goes to `#/efb` from anywhere. It runs in the top document only, starts when `<body>` exists, and a MutationObserver re-runs its rules at most once per 50 ms, each in its own try/catch, so a failing rule never stops the others or throws into the page. It marks what it handled (`data-msfsba="1"`), never overrides a page's own `aria-hidden`, `aria-label` or `role`, and takes back only what it wrote when the page moves on. It exports `{ pass, textOf }` for the tests. What it keys on (read live on 3.0.0.7426; a Fenix update that renames one of these breaks it silently): home tiles `#appContainer > div.appIcon` holding `img.app-img`, a `<br>` and `span.appTitle` (named by the title); `div#homeButtonFree.home-button` ("Home") and the top-bar `div.popup-arrow` ("App switcher"), whose pictures take the nine tile titles in home order (Fenix, Takeoff, Landing, Charts, Documents, Failures, Settings, MCDU, FAP) only when the switcher holds nine; Ground Services' `mat-slide-toggle … input[role=switch]` beside `div.text` ("GPU"); Mass and Balance's section titles and `input.planned-input[placeholder]` ("Passengers Planned, Max 180"); Panel States' `mat-dialog-container` ("Panel states"); Takeoff and Landing's `div.departure-label` beside `app-keyboard-input` or `mat-select[role=combobox]`, and the results in `div.mcdu-screen` (label rows over value rows; `small-yellow-box` spans are "not computed"; the grid takes an `aria-owns` that reads each label right before its value); Landing's `div.section-item[tabindex]` with `section-selected` (a radio group "Runway condition", one Tab stop where the arrow keys pick the code); Settings' `li.category` (`category--active`) and each option `article` (the checkbox the page hides with `display:none` becomes a switch named by the heading without its badge; `button.option` with `option--active` gets `aria-pressed`; `button.overflow-button` "⋮" opens a menu with "Set as user override" and "Reset to default", focus inside it, closed with Escape or "Close menu"); Failures' `div.manual-failure-ata-title` (chapter, `aria-expanded`, ", has failures") and `button.manual-failure-item` ("CPC 1", ", failed" or ", armed"); Documents' `div.folder-name` and `div.file`; Charts' sidebar items and map controls; Quick settings' slider and buttons ("Close quick settings"); loading notices as `aria-live="polite"` with `role=progressbar`. The choices the owner made by ear on a test page: Takeoff results read each label right before its value, the runway condition is one Tab stop with arrow keys, `role=none` on the "clickable" wrappers, an empty result is "not computed" with the role "value", and a line-break button is named by its text.
- **The window.** Escape closes it unless a CDK overlay pane with content is open (a "More options" menu, a drop-down panel, the Panel States pop-up), where the overlay closes first; Escape from inside the page never reaches `ProcessCmdKey`, so an injected capture-phase listener posts a close message. A failed load swaps the browser for a retry panel and speaks "Fenix EFB is not reachable at http://127.0.0.1:8083. Make sure the Fenix A320 is fully loaded, then press Retry.", the text in a tabbable read-only TextBox ([VAT-13]). The MCDU and FAP pages are dead ends the window catches (`FenixEfbRoutes.Classify` sorts the URL by the first path segment of its fragment, hooked on `SourceChanged`, which also fires for the single-page EFB's fragment changes): it navigates back to the EFB home and says "The EFB's MCDU can't be read with a screen reader. Use the MCDU window instead: input mode, then Shift+M." or "The EFB's FAP can't be read with a screen reader. Use the Fenix windows list instead: input mode, then Control+Shift+F.", the same route once within 1.5 s (`FenixEfbDeadEndGate`: the router changes the address twice on its way in). The EFB's MCDU is two canvases ("FenixSim MCDU"), and its FAP opens on a screensaver (`#/fap/screen-saver`, a single `<img>` of the Cabin Status page; a tap wakes `#/fap/cabin-status`; awake, the section links have no names, values are bare text not tied to their zone, and only the 9 bottom-row `FAP-BUTTON`s take focus and they have no role or name). The app's own MCDU window and Cabin window cover them.
- **Captures and how to re-take them after a Fenix update.** `tools/fenix-efb-test/` is a jsdom harness (`npm install`, then `node --test`; it is not in CI's `efb-readers` job, which runs the other EFB harnesses, so a Fenix update can break the layer unnoticed): `fixtures/*.html` are trimmed copies of the page's markup, the sweep checks that every control ends up named, `core.test.js` runs on two hand-made fixtures (the layer's text folding, observer, per-rule safety net and keys), and the other suites pin the navigation, the Fenix app's own screens (`fenix-app`), Settings, Failures, Documents, Charts and quick settings (`other-apps`) and the Takeoff and Landing calculators (`performance`), each against the live captures. `tools/fenix-efb-test/capture.md` holds the snippet (strips scripts, styles, map tiles, every `value` attribute and picture data), the 22 screens to capture one by one with the browser window on screen (some screens keep their content at `visibility: hidden` until their pictures lay out), the credential search to run on a Settings capture before committing it, and what was captured when (2026-10-22, Fenix 3.0.0.7438, A320-232 IAE). Never commit a Fenix bundle or a whole document set. **jsdom has no CSS**, so it cannot see `display:none`, `visibility:hidden` or the glyph an icon font draws; the Settings checkboxes the page hides and the icon glyphs that became button names were found in the sim, not in the tests. So after every Fenix update and every change to the layer, do capture.md's live check: open the EFB in any Chromium browser, load the layer from the built `Resources` folder into the console, and read each screen in the accessibility tree for controls with no name or a stray-glyph name, "clickable" generics, unnamed graphics and display-none controls.
- **If an update makes the layer misbehave (support step):** rename or remove `Resources\fenix-efb-accessibility.js` beside the app. `FenixEFBForm` then logs `Log.Warn("FenixEFB", "Accessibility layer not loaded …")` and the plain page loads, which a screen reader cannot use but cannot be broken by the layer.

### Circuit breakers + the 2026-08 ECAM message sync (FBW #10878 / #10717)

**Only ONE circuit breaker is actually modelled — do NOT build a CB panel.** FBW #10878 added an A32NX circuit-breaker system, and it is tempting to read the 27 `A32NX_CB_*_TRIPPED_*` L:vars as "lots of new controls". They are not. Those vars are the **SDAC's monitoring table**: each is a 32-bit mask, and `CircuitBreakerMonitors.ts` declares which bits the FWC watches — **196 monitored CB positions across 7 ECAM groups** (rear panels J-M / N-R / S-V / W-Z, overhead, L and R elec bay). But the cockpit model instantiates exactly one clickable breaker: `CircuitBreaker.xml` defines `FBW_A32NX_CB_49VU` with a single `<CB_1>E12</CB_1>`, and `A320_NEO_INTERIOR.xml` uses that one template. **49VU E12 is the ECAM Control Panel's own power supply** (`Ecp.ts`: `new CircuitMonitor(this.bus, UpstreamBus.DcEss, '49VU', 'E', 12)`) — which is the whole point of the PR. The other 195 positions have no 3-D breaker, no tooltip and no name, so exposing them would mean inventing ~195 nameless controls for objects that do not exist in the aircraft. Encoding, if a real one is ever added: var `L:1:A32NX_CB_{PANEL}_{ROW}_TRIPPED_{floor((col-1)/32)}`, bit `(col-1) % 32`, pull = `OR` the bit, reset = `AND NOT` it.

**⚠️ The CB vars are only reachable through the `L:1:` form.** The systems read `RegisteredSimVar.create('L:1:A32NX_CB_…', Enum)`. Writing the unprefixed `(>L:A32NX_CB_…)` updates a DIFFERENT variable — it sticks on read-back but the FWC never sees it (live-burned 2026-08-16: `L:…` = 2048 while `L:1:…` = 0). Since `SimConnectManager.SetLVar` always emits the unprefixed form, **MSFSBA cannot currently pull a breaker**; a control would have to write `<mask> (>L:1:VAR, enum)` explicitly through the calc path in the def, and read it back by registering the var name as `1:NAME`. See the golden rules in [troubleshooting-playbook.md](troubleshooting-playbook.md).

**The C/B TRIPPED ECAM messages ARE wired and DO get spoken — verified end to end (2026-08-16).** Gating found in `CircuitBreakerLogic.ts`: a monitored bit set **AND** FWC flight phase 1, 2 or 6 **AND** held for a **60-second** confirm node (`NXLogicConfirmNode(60, true)`) — so a trip is silent for a full minute before the caution appears; do not conclude "it doesn't work" after 15 s. Live test on the running build (`a32nx-v2024.2.0-dev.7dbada1`): setting `L:1:A32NX_CB_49VU_A_TRIPPED_0` bit 0, phase 1, produced the announcement in MSFSBA's own log — `New ECAM message detected for announcement: 'C/B TRIPPED ON OVHD PNL, Amber'`. Note the ECP breaker (49VU E12) is a poor test subject: pulling it unpowers the ECAM Control Panel itself, so pick another monitored bit in the same group.

**Stray "m" in every grouped ECAM announcement — FIXED.** The live test above first came out as *"C/B **m** TRIPPED ON OVHD PNL"*. Cause: each grouped title is stored `"\x1b<4m\x1b4mC/B\x1bm TRIPPED…"`, and the closing `\x1bm` is ESC + a literal `'m'`; `CleanANSICodes`' control-character pass turned the ESC into a space and left the letter stranded as its own word, which the screen reader spoke. This affected **every** grouped message on the A320 table (`BRAKES m HOT`, `T.O m AUTO BRK`), not just the new ones. `CleanANSICodes` is now the same ESC-anchored single regex the A380 lookup has always used (`\x1b[<)\d]*m`, which covers the bare ESC+`m` reset) plus a `ƴm` alternate for this table's compile-time mojibake — C#'s greedy `\x` escape makes `"\x1b4m"` compile to `U+01B4 'ƴ' + 'm'`, which is also why four action lines briefly stored as `"\x1b5m"` (`308118602/3`, `308128002/3`) announced a stray `Ƶm` with no colour word until they were corrected to `"\x1b<5m"`. The old non-anchored digit pass that could eat real text like "75m" is gone with the consolidation. The characterization tests that pinned the old residue were updated deliberately — if one ever fails claiming a missing `m`, the fix has been reverted, not broken.

### The armed ALT call-out names an FMS altitude constraint (2026-08-23)

Ported from the A380 fix (see [a380x.md](a380x.md) for the full derivation). The two airframes
agree on the SEMANTIC and differ only in how the aircraft carries the qualifier, so
`ArmedAltitudeMode` is shared and each def supplies its own source.

**⚠️ The A32NX is NOT a verbatim copy of the A380 here — do not port by assumption.** Three
things differ, and each was checked against the source:

| | A380 | A32NX |
| --- | --- | --- |
| armed bits come from | PRIM FG discrete word 2, bits 11/13/14/15/16/18 | FMGC A-bus discrete word 3, bits **12/22/23/24/25** |
| constraint qualifier | FG word 3 **bit 28** (`alt_cstr_applicable`) | **the SSM** of `A32NX_FMGC_{1,2}_FM_ALTITUDE_CONSTRAINT` |
| cruise-altitude flavour | FG word 3 bit 29 (`altIsCrzAlt`) | **none** — the A32NX FMA has no ALT CRZ branch |

Only the final `verticalArmed = altArmed | (clbArmed << 2) | …` expression is byte-identical
between the two WASM shims, which is exactly what makes "it's shared" a tempting and wrong
conclusion.

**The SSM *is* the flag, not a proxy for it.** `FmgcComputer.cpp:4898`:

```cpp
if (alt_cstr_applicable) fmgc_a_bus.fm_alt_constraint_ft.SSM = NormalOperation;
else                     fmgc_a_bus.fm_alt_constraint_ft.SSM = NoComputedData;
```

so the word is read for its VALIDITY and its number is never used — which is also precisely what
the A32NX PFD reads (`FMA.tsx`: `altAcqArmed && !clbArmed && altConstraint.isNormalOperation()`).
`ConstraintApplicableFromConstraintWord` gates on Normal Operation **only** — the accessor its own
PFD uses for a value word's validity, where the A380 reads a discrete bit and uses `bitValueOr`.
Each mirrors its own aircraft; neither is stricter than the other, so do not "harmonize" them.

**Both FMGCs are read, and the qualifier applies if either says so.** The armed bitmask MSFSBA
receives follows `fmgcPriorityIndex`, so an FMGC-1-only read would go quiet whenever FMGC 2 held
priority. In normal dual operation both compute the same constraint, so the OR changes nothing;
under a single failure it keeps the call-out alive instead of silently degrading.

**The PFD's extra `!clbArmed` term is deliberately NOT reproduced**, on either airframe. That
term decides which single label to draw in one text slot, not whether the armed altitude is a
constraint — the A380's own colour rule has no such term, and MSFSBA announces each newly-armed
mode separately rather than only the top-priority one.

**Bit 2 removed, bit 64 kept — and the difference is the point.** The old
`(2, "Altitude constraint")` row could never fire: the shim skips bit 1 because
`base_fmgc_armed_modes` has no constraint member at all (it carries `alt_acq_armed` /
`alt_acq_arm_possible`, same as the A380's bus). That is structural, so the row is gone. Bit 64
(TCAS) also cannot fire today — the A32NX shim hardcodes `bool tcasArmed = false;` where its
siblings read a bit — but that reads as *not yet wired* rather than *not modelled*, so the entry
stays and starts working the day FBW wires it.

**⚠️ Source-verified, not sim-verified.** There was no A320 loaded when this was written. Every
claim above is traced to the FBW tree; the live measurement behind the A380 half has no A32NX
counterpart yet. (That A380 measurement was recorded as "bit 28 TRUE at FL360 with nothing armed";
decoded as FBW decodes a discrete word it was bits 29 and 20 — the CRUISE qualifier and ALT hold —
see a380x.md, "Discrete ARINC words were read from the wrong bits". The A32NX FMGC discrete words
this file reads — the LAND 2/3 capability bits among them — were misread by the same bug until
2026-09-25.) (The dispatch-ordering measurement below
is a separate matter — it is measured against MSFSBA's own registration, not the FBW source.)

**The armed-ALT call-out is HELD until the qualifier settles, and the flush re-checks the Ctrl+M
mute ITSELF.** `A32NX_FMA_VERTICAL_ARMED` sits at continuous-batch 1 index 169 while the two FMGC
constraint words sit at 172/173 — three slots later in the SAME batch (164/167/168 before PR
#140's FCU sources sorted in ahead of them) — so naming the ALT bit
inline read the PREVIOUS sample's constraint. Only the ALT entry is held, and it is released by
the DELIVERY of the batch carrying the constraint words, not by a timer and not by those words'
own `ProcessSimVarUpdate` branches (which run only when a value CHANGED, and so cannot report an
unchanged-but-now-current qualifier). Because that batch is the same one the arming bitmask rides,
the flush lands at the tail of the same message — no delay at all on this airframe. The def names
the word to wait on through `DeferredFlushWatchVariable`, and returns **FMGC_2**, not FMGC_1: the
two are OR'd so both must be current, and `A32NX_FMGC_2_...` sorts after `A32NX_FMGC_1_...`, so
waiting on the later of the two is correct whether they share a batch (they do today) or ever
straddle the 300-var boundary. See [a380x.md](a380x.md) for the full derivation, the measured
ordering on both airframes, why a wall-clock backstop was rejected, and the disproven
`GetCachedVariableValue` approach that must not be re-attempted.

The mute re-check is the one piece that is **A32NX-specific, and it is a trap for the next
deferred announcement added to this def.** This aircraft is muted CENTRALLY: MainForm wraps
`announcer.Suppressed` around the whole `ProcessSimVarUpdate` call, because vars like the A320's
EFIS baro readouts (and the Headwind A330's stock-Kohlsman altimeter, which shares the wrap)
announce from INSIDE it and return true — exiting before the generic
`A32NXDisabledMonitorVariables` gate below, so a Ctrl+M un-tick never muted them. The
`a32nxMuted` comment in `MainForm.Announcers.cs` is the authority.
Anything delivered through a callback rather than through `ProcessSimVarUpdate` — a timer tick, or
the `OnDeferredFlushBatchDelivered` batch hook — runs OUTSIDE that wrap and must consult
`A32NXDisabledMonitorVariablesSet` for itself; this def's `OnDeferredFlushBatchDelivered` does,
via the shared `ArmedAltitudeMode.ShouldSpeakHeldAlt`. The A380 has no such trap: its armed branch
checks `A380DisabledMonitorVariablesSet` locally, so its flush inherits the same check by writing
it the same way.

### VFE and VS now read the FAC bus — FBW #10890 deleted the plain L-vars (2026-09-22)

**FBW #10890 (`c0421a9`, 11 Sep 2026, "various AFS fixes") stopped the A32NX publishing
`A32NX_SPEEDS_VFEN` and `A32NX_SPEEDS_VS` at all.** The writes were deleted from
`A32NX_Speeds.ts`; the values still exist inside `NXSpeeds` but nothing puts them on an
L-var any more. Neither was renamed, so a name-diff sweep finds nothing — the vars simply
stop being written and read a stale `0` forever. That is the failure mode to fear: the VFE
and VS readouts did not go silent, they confidently said a wrong number.

The same commit DID rename one L-var: `A32NX_SPEEDS_LANDING_CONF3`, the CONF 3 landing selection,
became `A32NX_FM_LANDING_CONF3`. The First Officer's auto-flap cap read the old name, got NaN and
took flaps FULL until 2026-10-09 (FOA-6). The Headwind A330 still writes the old name.

The readouts now take the FAC's own characteristic speeds, which is what the PFD tape uses:

| Readout | Was | Now |
| --- | --- | --- |
| VFE | `A32NX_SPEEDS_VFEN` | `A32NX_FAC_1_V_FE_NEXT`, else `A32NX_FAC_2_V_FE_NEXT` |
| VS | `A32NX_SPEEDS_VS` | `A32NX_FAC_1_V_STALL_1G`, else `A32NX_FAC_2_V_STALL_1G` |

The First Officer's automatic flap extension had the same dependency: `FbwA320FOAutoManager`
gated extension on `A32NX_SPEEDS_VFEN`, and with it reading 0 the guard held on every approach,
so the FO never extended flaps. It now reads the FAC word through the evaluator's
`FO_VFE_NEXT` synthetic field: FAC 1, else FAC 2, and no data means hold. The Headwind A330's
evaluator resolves `FO_VFE_NEXT` to the plain L-var. The A380 First Officer still reads the
plain L-var its aircraft publishes.

VS keeps its meaning: `V_STALL_1G` is the 1g stall speed, the same quantity the deleted
`A32NX_SPEEDS_VS` carried, and the call-out still says "Stall Speed". Like the PFD, FAC 1 is
read first and FAC 2 is the fallback when FAC 1 has nothing to say (failed, or switched off).

Both are **ARINC429 words**. They are NOT read through the hardcoded temp-def/dispatch path
(ids 330-337, which hands the value on as a plain number): each `SpeedRequestTable` entry
carries its encoding — `PlainSpeed` for that path, `FacSpeed` for a FAC word — and a
`FacSpeed` is read through its registered `IsArinc429` definition (`FAC_n_V_FE_NEXT`,
`FAC_n_V_STALL_1G`) with `ReadFreshAsync` and decoded by `TryDecodeArinc429`, the same decode
the panel rows use. A bad SSM is spoken as "not available" rather than as a number. Never add
ARINC decoding to dispatch cases 335/337: they still carry a plain number for the Headwind
A330 (below).

⚠️ **VFE and VS are now IN-FLIGHT ONLY.** The deleted plain L-vars were valid on the ground;
a FAC word carries a no-computed-data SSM until the FACs have air data, so both say "not
available" on stand. That is a real behaviour change — and not one worth avoiding, because the
variable it replaces reads a stale 0 on the ground too, it just says it with a number.

⚠️ **The A380 is NOT affected and must not be "fixed" to match.** The A380X still writes
both plain L-vars (`FmcAircraftInterface.ts`), and `FlyByWireA380Definition` derives from
`BaseAircraftDefinition` — not from `FlyByWireA320Definition` — so it reads them through its
own `RequestReadout` path and shares none of this.

⚠️ **The Headwind A330 inherits this table and must KEEP the plain L-vars.** Checked against
`headwindsim/aircraft` @ `41eace7` (14 Aug 2026), not assumed: it still writes both from the
pre-#10890 `A32NX_Speeds.ts` it forked (lines 22/29/69/75), and its FACs publish **six**
variables in total — `DISCRETE_WORD_2`, `HEALTHY`, `RUDDER_TRIM_POS` per side — **not one of
them a characteristic speed**. None of the FAC speed words exist on that airframe, so
`HeadwindA330Definition` overrides `SpeedRequestTable` with all-`PlainSpeed` sources, and drops
the base PFD panel's FAC rows (`PFD_VSW`, `PFD_VALPHAPROT`, `PFD_VALPHAMAX`), which would read
"not available" all flight. Revisit only if Headwind syncs #10890.

**Requires a FlyByWire A32NX Development build from 11 Sep 2026 or later** for the plain
L-vars to be gone; the FAC words predate #10890, so this migration also works on an older
build.

### The SD FUEL center transfer valves (FBW #10971, 2026-10-24)

FBW #10971 (`acbfe58df`, 23 Oct 2026; the only commit of the sweep `76db0aef1..acbfe58df`, recorded
in [a380x.md](a380x.md)) adds two triggers to the A32NX `flight_model.cfg`: when either inner tank
falls below 1,651 gallons, both AUTO center transfer valves (`FUELSYSTEM VALVE OPEN:11` / `:12`) close,

takes an inner tank below 1,651 gallons; measure the center tank over an AUTO climb before blaming
either FBW or MSFSBA for center fuel left in the tank. Nothing MSFSBA read or sent changed: the CTR TK XFR buttons
(`FUEL_PUMP_C1/C2`) are valve SWITCHES 9/10; FUEL MODE SEL's junctions 4/5 keep their options
([A320-12]); MANUAL routing bypasses valves 11/12; the First Officer presses only the buttons.

`CentreToInnerTransfer`), "Left / Right center transfer valve": the pair in series (auto valve,
button valve) reads "closed" under 1 % open, else "open", and "open, Amber" when the button is off,
or in AUTO (the MODE SEL L:var) while not fully open; a NaN input reads as unread. Only the auto
valves and junctions are force-read with the rows: the buttons and MODE SEL ride the continuous
batch. `FlyByWireCenterTransferValve` decodes it; `A32nxCenterTransferValveTests` pins it and each
side's inputs. The rows replace a "Center pump" row that read only the left jet pump
(`FUELSYSTEM PUMP ACTIVE:1`), which the SD does not draw. The page also gained "Left / Right outer
transfer valve" (`FUELSYSTEM VALVE OPEN:4` / `:5`, open or closed), the arrow both SDs draw while an
outer tank drains into its inner. The Headwind A330 inherits all four rows: its fuel system numbers
the same valves, junctions and buttons, and its `sd.js` carries the same components.

### Cleared V-speeds are spoken "not set" (2026-09-25)

FBW #10855 (`1bbd304`, 18 Aug 2026 — the A32NX half of an A380 commit, in `A32NX_FMCMainDisplay.ts`)
changed the FMS's cleared V1 and VR from 0 to -1 (V2 stays 0). The FMS clears all three itself as
the flight phase passes TAKEOFF, and on a takeoff-runway change, so every climb-out was announced as
"V1: -1 knots, VR: -1 knots, V2: 0 knots" (it was "0 knots" before, no better). `PFD_V1`/`PFD_VR`/
`PFD_V2` now carry `SimVarDefinition.NotSetBelow = 1`, so `FormatVariableValue` says "V1: not set";
a threshold rather than a `ValueDescriptions` key, because a sentinel written in knots and read back
through the sim's base unit need not come back bit-exact. The A380 and the Headwind A330 (which
inherits these definitions and still clears to 0) get the same wording. Pinned by
`FbwVSpeedNotSetTests`.

The status-box panels read "not set" too: MainForm's panel formatter and `FormatVariableValue` both
ask `SimVarDefinition.IsNotSet`, the one test (the panel showed "V1: -1" while the readout already
said "not set"). And the FMS's own post-takeoff clear is no longer SPOKEN on the A32NX (and the
Headwind A330, which inherits it): `A32NX_FMCMainDisplay.ts` clears all three once the phase is past
TAKEOFF, which made three "not set" lines on every climb-out. The definition consumes a cleared
V-speed silently once `A32NX_FMGC_FLIGHT_PHASE` is TAKEOFF or later, and still leaves to the monitor
a clear made before takeoff thrust (a runway change — the FMS's only other clear — when the pilot
must re-enter them) or with the phase unknown. ⚠️ The gate is phase ≥ TAKEOFF, NOT past it: the
phase rides continuous batch 1 and the V-speeds batch 2 (separate once-a-second requests, measured
about 405 ms apart), and the FMS clears on its own 1-second throttle, so the clear can reach MSFSBA
before the CLIMB phase does. It can never arrive with anything below TAKEOFF, which is set when
takeoff thrust is. (A first version gated on "past TAKEOFF", reasoning from the name sort within one
batch; a second review found the two ride different batches.)

### Take-off roll callouts: V1, Rotate, V2 (added 2026-10-11)

The A32NX calls "V1", "Rotate" and "V2" on the take-off roll, as the A380, the MD-11 and the iFly
do, through the same `TakeoffVSpeedCallouts` machine; `A320TakeoffCallouts` wires it. Before this,
MSFSBA called nothing at V1 or VR on the A32NX: Takeoff Assist's "V1"/"rotate" have been Fenix-only
since they were added, and the A32NX plays no V-speed callout of its own (its FWS sounds in
`sound.xml` are the radio heights, "retard", minimums and the speed and pitch warnings). A pilot who
flew the A380 or the Fenix expected them (user report, 2026-10-11: Takeoff Assist said "80 knots" and
"100 knots", then nothing).

- **Speeds** are the FMS's `L:AIRLINER_V1_SPEED`/`_VR_`/`_V2_` (knots), the `PFD_V1`/`PFD_VR`/`PFD_V2`
  rows that already announce "V1: 142 knots" as the pilot enters them. They are peeked, never
  consumed, AHEAD of the branch above that swallows the FMS's post-takeoff clear. That clear comes
  only once the phase is past TAKEOFF (`A32NX_FMCMainDisplay.ts`), so the roll keeps its speeds;
  cleared speeds (-1/-1/0 since #10855, 0/0/0 before it and on the Headwind A330) arm nothing.
- **Airspeed** is `AIRSPEED INDICATED` on its own per-frame subscription (`A320_TAKEOFF_CALLOUT_IAS`:
  `HighFrequency`, `ExcludeFromBatch`, hidden from Ctrl+M), paused once airborne with no roll armed
  and resumed at touchdown (`TakeoffCalloutFeedNeeded`), as on the A380.
- **The rule is the shared machine's**: armed on the ground below 40 kt with V1 and VR set, fired on
  upward crossings, one utterance per sample ("V1, Rotate" when V1 = VR), interrupting, so it never
  queues behind Takeoff Assist's "100 knots" or a ground-speed call.
- **Mutes**: each call rides its speed's Ctrl+M row (V1 → "V1", Rotate → "VR", V2 → "V2"); the feed is
  `IsMuteWrapExempt` and checks the rows itself.
- **Resets**: the ARM is dropped, the speeds kept, on every context reset and on a reconnect. The
  Headwind A330's `ResetAnnouncementBaselines` override calls the base, so it gets both.

The Headwind A330 inherits all of it. The Fenix did not at first (it kept Takeoff Assist's own
"V1"/"rotate", queued, only while Takeoff Assist was on); since 2026-10-22 it is on the same machine
too (`FenixTakeoffCallouts`, from the PERF TAKE OFF speeds; see "Fenix v3 panel-control fixes"). Pinned by
`A320TakeoffCalloutsTests` and `TakeoffCalloutFeedTests` (the A32NX, not yet flown) and
`FenixTakeoffCalloutsTests` (the Fenix, flown 2026-10-22).

### Discrete-word readouts were decoded from the wrong bits (fixed 2026-09-25)

The A32NX shares `Arinc429Word` with the A380, and until 2026-09-25 its `BitValueOr` tested a
discrete word's RAW float bits instead of the bitfield the float's value carries (docs/a380x.md,
"Discrete ARINC words were read from the wrong bits"). Every A32NX discrete readout read noise: the
LAND 2 / LAND 3 capability (FMGC discrete word 4, bits 23/24/25), the active-CPC choice on the PRESS
and CRUISE pages (CPC word bit 11) and the COND page's hot air valve / pushbutton and cabin fans (ACSC
word 1, bits 20/23/25/26). The bit numbers themselves were checked against the FBW writers and SD
pages and are right.

**FWC word 124 was also mislabelled.** Bits 24 and 25 are an ALTITUDE discrepancy between the sides
— one side's altitude off the other's by 250 ft for 5 s, with both sides in STD (24) or both in
QNH/QFE (25) — which drives the PFD's CHECK ALT flag and ECAM "NAV ALT DISCREPANCY"
(`PseudoFWC.ts`). MSFSBA spoke them as "Baro standard mode / reference discrepancy", a baro-setting
mismatch neither bit can signal (FBW's real BARO REF DISCREPANCY drives an ECAM alert only and is in
no word). It is now one call-out, "Altitude discrepancy between sides", on the rising edge of either
bit, and the Ctrl+M row is "Altitude Discrepancy". Pinned by `A32nxAltitudeDiscrepancyTests`.

**…and it had never fired at all.** PseudoFWC builds word 124 with
`Arinc429RegisterSubject.createEmpty()` and never sets its SSM (word 126 beside it gets
`setSsm(NormalOperation)`; 124 does not), so the L:var always carries Failure Warning and every
SSM-gated read (`BitValueOr`) returns its fallback — silent before the decoder fix and after it. The
PFD reads CHECK ALT from it with `bitValue`, which ignores the SSM, and so does MSFSBA now
(`Arinc429Word.BitValue`, which is for exactly this kind of word and no other: everywhere else a
failed word must say nothing). The call-out has therefore never been heard in the sim — it wants a
live check, for example with the two sides' QNH set 10 hPa apart (about 280 ft; `PseudoFWC` compares
each ADR's baro-corrected altitude with the other side's displayed one) for more than 5 s in flight.

### FCU hardware-dial callouts — speak only what the window SHOWS (PR #140, 2026-09)

Turning an FCU knob on hardware (MobiFlight, FSUIPC, the 3-D cockpit) speaks the new value on the
A32NX, the Headwind A330 and the A380X — the PMDG 777's MCP callouts. The definition composes a
phrase per delivery (`TryComposeFcuValuePhrase` → `FcuValuePhrases`) and `FcuValueAnnouncer`
decides whether it is spoken. Pinned by `FbwFcuDialAnnounceTests`, `FcuValuePhrasesTests` and
`FcuValueAnnouncerTests`. The A330 inherits the A32NX path unchanged and its fbw.wasm carries every
source name below, but on this alpha airframe "present in the wasm" has not always meant
"delivered" (see the baro note in `HeadwindA330Definition`) — unverified in the sim; the failure mode
is silence.

**⚠️ The sources are the whole feature.** While a window shows dashes, the A32NX FCU keeps copying
the aircraft's LIVE data into its plain display values (`FcuComputer.cpp`: the dashes branches set
the heading value from the ADIRS heading or track, the speed from CAS or Mach clamped 100-399, and
the V/S from the current vertical speed rounded to 100 fpm). The first version announced
`A32NX_FCU_AFS_DISPLAY_{HDG_TRK,SPD_MACH,VS_FPA}_VALUE`, so the heading was read out as the
aircraft turned on the ground (the report that found it), and the airspeed and vertical speed
would have been narrated through every take-off roll and managed climb. Pairing those values with
the separate `…_DASHES` flags does not fix it either: the flag and the value arrive on different
SimConnect deliveries, so the order races. Every source must say ON ITS OWN whether its window
shows a selection:

| | A32NX / A330 | A380X |
| --- | --- | --- |
| Heading | `A32NX_AUTOPILOT_HEADING_SELECTED` (shim, -1 while dashed or the FCU failed) | the same name (-1 while dashed; the A380 writer has no FCU-failed term) |
| Speed | `A32NX_AUTOPILOT_SPEED_SELECTED` (shim, -1 while dashed; Mach below 10, knots above) | the same name |
| Altitude | `A32NX_FCU_SELECTED_ALTITUDE` (FCU bus ARINC429 word; Failure Warning when the FCU has failed) | stock `AUTOPILOT ALTITUDE LOCK VAR:3` (`FCU_ALT_VALUE`), metric under MTRS |
| V/S | `A32NX_FCU_SELECTED_VERTICAL_SPEED` (FCU bus word) | `A32NX_PRIM_1_SELECTED_VERTICAL_SPEED` (PRIM FG word) |
| FPA | `A32NX_FCU_SELECTED_FPA` | `A32NX_PRIM_1_SELECTED_FPA` |

The V/S word is Normal Operation only while the V/S window shows a V/S selection — No Computed
Data while dashed or in TRK/FPA — and the FPA word the reverse (`FcuComputer.cpp` bus-output SSMs;
the A380 PRIM's `A380PrimComputerFctl.cpp` mirrors them, and its FCU shows dashes exactly when the
master PRIM's word for the active mode is not Normal Operation). So neither needs the TRK/FPA mode,
and a selected V/S of 0 (a push-to-level-off) is spoken while dashes are not. The
`A32NX_AUTOPILOT_{VS,FPA}_SELECTED` shims are NOT sources on either airframe: on the A380 they read
0 while dashed, on the A32NX they carry the LIVE vertical speed or FPA while dashed, and both read 0
in the other mode. The A32NX altitude comes from its word rather than
`A32NX_FCU_AFS_DISPLAY_ALT_VALUE` because a failed FCU zeroes the display value, which spoke
"Altitude 0 feet". The A380's PRIM 1 words carry the same single-source limitation as its PRIM 1
envelope speeds: with PRIM 1 not the master they go silent rather than follow PRIM 2/3. Batched
sources are registered with Units `"number"` — a batched L:var is read in its registered unit, and a
unit conversion would destroy a packed word (individual defs always read an L:var as `"number"`,
whatever Units says).

**FCU availability.** A callout is only released while the FCU itself is producing values —
`A32NX_FCU_HEALTHY` (A32NX/A330) or `A32NX_FCU_AFS_CP_ACTIVE` (A380, `fcu1||fcu2 afs_cp_active`).
It rides the SAME continuous batch as the heading/speed shims and (A380) `FCU_ALT_VALUE`, pinned by
`FcuHealthBatchMembershipTests` against the production layout (`ContinuousBatchLayout`). Within the
batch it sorts AFTER the shims but BEFORE the A32NX `A32NX_FCU_SELECTED_*` words, and the A380's
stock altitude sorts first of all; the A380's PRIM 1 V/S and FPA words sort so late they currently
ride the NEXT batch and are judged against the health delivered one batch earlier. Either order is
safe because nothing is spoken until the batch ends: a health drop clears whatever was staged
before it and blocks anything staged after it, and a return starts a settle. Every source
above also composes `FcuValuePhrases.Unavailable` on its own when its word reads Failure
Warning/Functional Test (self-test); on the A380 only, so do the speed shim's and `FCU_ALT_VALUE`'s
own impossible zeros (the FCU never selects 0 kt/Mach, and its selected altitude is never below
100 ft, so 0 can only mean "off"). The HEADING shim's zero is NOT one of these:
`FcuValuePhrases.Heading`/`HeadingDegrees` has no zero case — 0° is a real heading — so a dead A380
FCU's zero heading composes an ordinary "Heading 000 degrees" and is kept silent only by the
health-var gate above, never by `Unavailable`. `Unavailable` is recorded like dashes, silently, but
a delivery FROM `Unavailable` (the health var returning, or a source leaving `Unavailable`) begins
a settle: the A380 zeroes every output rather than dashing it, so without this a battery-on read as
nine knob turns at once. A power-DOWN is silent outright (staged phrases are dropped).

**Callouts are STAGED, not spoken on delivery, and released at the batch's end.** Whether a change
is a knob turn depends on the FCU health var of the same sample too, which may sort before or after
the value in its batch (above) — so `AnnounceFcuValue` only records a change; `BaseAircraftDefinition.
OnContinuousBatchDelivered` (fired from `SimConnectManager.ContinuousBatchDelivered`, after every
`SimVarUpdated` that batch message carried) speaks whatever `FcuValueAnnouncer.OnBatchDelivered`
released. That release runs OUTSIDE MainForm's `announcer.Suppressed` wrap (which only wraps
`ProcessSimVarUpdate`), so each airframe checks its own Ctrl+M mute set itself before staging
(`A32NXDisabledMonitorVariablesSet` / `A380DisabledMonitorVariablesSet`) — the same reason the
armed-ALT hold above has to.

**The speak/stay-silent rules (`FcuValueAnnouncer`).** Phrases are compared, not numbers: the
first sample of a key is a silent baseline; a dashed window (null phrase) is recorded but silent,
so pulling back out of managed speaks the value even when it equals the last selection, and a key
first seen dashed still speaks its first selection (an FMS departure). A Ctrl+M mute, and a
readout about to speak the same value, still RECORD the value — skipping the call left a stale
baseline that swallowed a later turn back to the old value. Callouts yield when the shared
announcement queue is backed up.

**Every MSFSBA-origin write arms its echo from ONE table, `FcuEchoKeys.For(evt, sources,
confirmation)`, BEFORE the send.** `FcuConfirmation` says what else already confirms the write, so
the table decides which value vars are left for the dial callout to confirm: `ModeFeedback`
(MainForm's press feedback, `GetButtonStateMapping` — the A32NX's input-mode hotkeys and its
plain-event FCU panel buttons, armed in `HandleHotkeyAction` and the A32NX's `OnPanelButtonFiring`),
`ValueReadout` (a readout is about to speak the value — `FireFCUButton(readback:true)` on either
airframe, and every A380 panel button, whose own `OnPanelButtonFiring` arms it unconditionally),
and `None` (nothing else confirms the write, so the callout must — the `SetFCU*Value` methods' own
readback, `SetTrkFpaMode`, and `FireFCUButton(readback:false)`). V/S push/pull get special
treatment: nothing announces a V/S level-off on its own (the FMA stays V/S), so `FcuEchoKeys.For`
only mutes the vertical channel for those two events under `ValueReadout` — otherwise (`None`/
`ModeFeedback`) it leaves them unmuted so the dial's own batch-released callout confirms the
level-off. `MainForm` calls `OnPanelButtonFiring` on every panel Event-type button BEFORE its event
is sent, so an echo armed there can never lose the race to the sim's answer.

**A dotted A32NX event queued behind the calc-path probe re-arms its echo when it is finally
sent.** `SendEvent` can hold a dotted/`H:` event for the probe's whole run (`CalcPathVerdict`, up
to ~60 s) — long past the 2.5 s window the call site armed. `SimConnectManager.
QueuedEventDispatched` fires from `FlushPendingCalcEvents`, and the base `OnQueuedEventDispatched`
restarts that event's echo window (`FcuValueAnnouncer.RearmEcho`) the moment it actually reaches
the sim.

**After a context reset** — a reconnect (`OnVariableCacheCleared`, called right after
`OnSimContextReset`), a flight load, or an Aircraft-menu switch made within 60 s of
`AircraftLoaded` (`MainForm.AircraftLoadSettleWindowMs`, a judgement value with no captured timing)
— changes are absorbed until an FCU value the AIRCRAFT publishes has moved and then five
first-batch deliveries pass quietly, or thirty pass regardless (the MD-11's `Md11SeedGate`
numbers). A reconnect's re-fire of every cached var IS that evidence (`refireIsEvidence`), so a
reconnect settle ends in about 5-6 batches, not thirty; a flight load still waits for a genuinely
NEW value — a stock SimVar source (the A380's `FCU_ALT_VALUE`) moving is not that evidence, since
the sim core can restore it from the flight file before the FBW WASM has run, though it still
restarts the quiet count. The baselines are kept, never wiped: a value the load leaves alone is
never re-delivered, and a wiped baseline would take the pilot's first turn as its silent seed.
Accepted residual: the settle only guarantees the FIRST burst of power-up churn is absorbed — a
LATER transient, such as the FMGC's own AP-engage self-test pulse (on the order of 25 s), can
arrive after the settle has already ended on ordinary evidence and is spoken like a real knob turn.

**The A380's readouts (Shift+H/S/V) and FCU panel buttons now say "managed"/"not available"
instead of a live value.** Reading the display values while dashed spoke a live heading/airspeed
(and, on the A380, a vertical speed of 0) as though it were selected. `FcuWindowStateOf(key)`
(`BaseAircraftDefinition`, reading `FcuValueAnnouncer`'s own recorded state) answers
Dashes/Value/Unavailable for a readout to render, and every A380 Shift+H/S/V branch and
`FireFCUButton`'s value readback go through it; each also arms `SuppressFcuValueChangeEcho` for the
var it is about to speak, so the same value arriving with the next batch is not spoken twice. On
the A32NX the readouts instead mute the matching dial source WHILE their own pending flag
(`isRequestingHeading` etc.) is set (`readoutPending` in `ProcessSimVarUpdate`) and still compose
their own words via `Compose{Heading,Speed,Altitude,Vertical}Readout` — same result (no double
speech, "managed"/"not available" instead of a live number), reached by muting the callout rather
than asking the callout's own tracker for the words.

**A32NX/A330 FCU panel number fields go through the same setters and validation as the FCU
windows.** `HandleUIVariableSet`'s `A32NX.FCU_{HDG,SPD,ALT}_SET` branches now call
`FcuValueEntry.Try{Heading,Speed,Altitude}` and the matching `SetFCU*Value` directly, and
`return true` (handled) instead of falling through to the generic panel path — which sent
`(uint)value`, truncating a typed Mach (0.78 → 0) and snapping an altitude to its 1000-ft
increment, and spoke "<name> set to <value>" for whatever was typed rather than what actually
reached the aircraft. `FcuValueEntry` (a new pure class, `FcuValueEntryTests`) is the one place
both the panel fields and `FBWA320{Heading,Speed,Altitude}Window` validate a typed value and
encode it (Mach travels ×100), so an out-of-range entry reads the same error either way.

**The heading window's TRK/FPA label reads the batch, not a poll.** `A32NX_TRK_FPA_MODE_ACTIVE`
itself stays OnRequest on the A32NX — streaming it as announced spoke every panel TRK/FPA press
twice (the press feedback plus the generic monitor) — but FBW mirrors the same value into
`A32NX_FCU_AFS_DISPLAY_TRK_FPA_MODE`, which the hardware-dial announcer already streams in the
batch and consumes silently (`ExcludeFromMonitorManager`, never spoken). `FBWA320HeadingWindow`'s
500 ms label timer now just reads that cache instead of calling `RequestVariable` on a timer
(`RequestTrkMode` is gone). The A380's Ctrl+H window never polled: `A32NX_TRK_FPA_MODE_ACTIVE`
streams there on its own per-var subscription (Continuous + `ExcludeFromBatch`), and the window's
timer only reads the cache that subscription feeds — through the definition's commanded-or-cached
view (`TrkFpaModeCommandedOrCached`), so a mode just pressed shows, and a quick second press asks
for the other mode, before the sim confirms the first.

**The five streamed A32NX value vars carry `FCU … Value` `DisplayName`s** (`FCU Heading Value`,
not `Selected Heading`) so a Ctrl+M search for "heading" does not surface a row named with the
exact words the MANAGED/SELECTED mode callout speaks — muting THAT row silenced the mode feedback
instead of the dial callout it looked like it would mute. Pinned by
`A32nx_callout_mute_rows_never_read_like_a_mode_callout`. The A380's equivalent rows still carry
their older `Selected …` names — unreviewed for the same collision.

### Fenix A320 First Officer — "Landing gear: UP" by lights out, "DOWN" by three green (2026-09-22 / 2026-09-25)

**Updated 2026-10-06 ([FOA-8](invariants/first-officer-airbus.md#foa-8)).** The Fenix First
Officer no longer has an After Takeoff checklist (Airbus deleted it in November 2021) and no
`ATC_GEAR` or `AFTER_TAKEOFF_CL`; the "gear down" read-back line is `LDC_MEMO_GEAR`, the first
line of the Landing checklist's landing memo (it was `LDC_GEAR`). What follows is the history
and the measurements, which still hold: the lights-out and three-green reads below are what
`FO_GEAR_UP` and `FO_GEAR_DOWN` still do, and the read-only After Takeoff wait still exists but
now links no checklist line. The FlyByWire A32NX and the Headwind A330 have the same two
fields, built from the gear legs instead of lights (`FbwA320GearConfirmation`, below).

The Fenix's old After Takeoff Checklist's "Landing gear: UP" (`ATC_GEAR`) used to read
`S_MIP_GEAR` directly, and `FirstOfficerForm`'s automatic `<Id>_CL` rule (`RelatedGroupIdsFor`)
latches `flow.Id + "_CL"` complete on top of every group a flow explicitly declares — so
finishing the After Takeoff flow latched `AFTER_TAKEOFF_CL` even though `ATC_GEAR` had no step of
its own behind it, and the line could read complete over gear that was still down. Fixed the
way the PMDG 737's equivalent line was fixed (see [pmdg-737.md](pmdg-737.md) — same owner
decision, same day): `FenixGearConfirmation` (`FirstOfficer/Fenix/FenixGearConfirmation.cs`,
published as the synthetic state field `FO_GEAR_UP`) reads UP only when the lever reads UP
(`S_MIP_GEAR` = 0) **and** all seven LDG GEAR indicator lights are out — `I_MIP_GEAR_1_U` /
`_1_L`, `I_MIP_GEAR_2_U` / `_2_L`, `I_MIP_GEAR_3_U` / `_3_L` (each wheel's upper/lower
legend) and `I_MIP_GEAR_RED` (the main-panel lever's own red arrow). All seven are
`Continuous`-registered L:vars, so the shared batch cache always carries a fresh sample once
the aircraft is powered; an unwritten field (any of the seven, or the lever) reads NaN via
the shared `GearLightRules.AsField`, which a flow's wait treats as "not up yet" rather than
a false positive.

**DOWN is "three green", from a MEASURED legend (2026-09-25).** The PMDG 737 composes
"three green, no red" from separate green DOWN-AND-LOCKED and red IN-TRANSIT fields. Each
Fenix wheel instead carries two legend L:vars, `_U` (Upper) and `_L` (Lower), and a Fenix
legend's meaning must never be inferred from its suffix, from the real aircraft, or from a
sibling pushbutton (the APU START `_U`/`_L` reversal is the cautionary tale — see
`FoPr160ProcedureFixTests`). So it was read in the sim: Fenix A320 CFM, parked at KDFW,
powered (main bus 28.5 V), lever `S_MIP_GEAR` = 1, gear down and locked. With the
annunciator switch `S_OH_IN_LT_ANN_LT` at Bright (1), `I_MIP_GEAR_1_L`/`_2_L`/`_3_L` all read
1 and `I_MIP_GEAR_1_U`/`_2_U`/`_3_U` and `I_MIP_GEAR_RED` all read 0; with the switch at TEST
(2) all three `_U` and `I_MIP_GEAR_RED` read 1 (proving the `_U` vars are live lights, not a
nonexistent L:var reading 0), and back to Bright returned them to 0. At DIM (0) the three `_L` still read 1 — the legends are plain
on/off, not brightness-scaled like the iFly's, so the `> 0.5` test holds at either setting. So **`_L` is the green
DOWN-AND-LOCKED legend**, and `_U` is the wheel's other legend — dark when down-locked, lit
in the light test; its colour in transit was NOT observed and nothing depends on it. The
real A320's LDG GEAR panel happens to agree (red UNLK above, green triangle below), but the
measurement is the authority, not the real jet.

`FenixGearConfirmation.DownValue`, published as the synthetic `FO_GEAR_DOWN`, reads DOWN only
when the lever reads DOWN **and** all three `_L` legends are lit **and** none of the three
`_U` legends nor `I_MIP_GEAR_RED` is lit — the shared `GearLightRules.IsDown`. Treating `_U`
and the arrow as reds means an annunciator light test (which lights everything) can never
read as "down". Any unwritten reading gives NaN, as for UP. The Landing Checklist's "Landing
memo, landing gear: DOWN" line (`LDC_MEMO_GEAR`, formerly `LDC_GEAR`) auto-ticks from
`FO_GEAR_DOWN` instead of the plain lever
— the same field the PMDG 737 and iFly lines read. It has no `CheckAction`, so a hand tick
never writes the gear. The Fenix First Officer profile has **no Landing flow**, so nothing
latches `LANDING_CL` complete: the line ticks and un-ticks from its own state alone
(`FenixGearConfirmationTests.No_Fenix_flow_latches_LANDING_CL` pins that premise — a future
Fenix Landing flow would need a read-only gear-down check completing `LDC_MEMO_GEAR` first).

**The After Takeoff flow ends with a read-only step**, `AT_GEAR_UP_CHECK` ("Landing gear:
UP"), that waits up to 20 s for `FO_GEAR_UP`. It never writes the lever — gear retraction
stays the `UniversalAutomationService`'s auto-gear-up job (the flow's own `Description` says
so) — it only confirms. It used to complete `ATC_GEAR`; with the After Takeoff checklist gone
(2026-10-06) it links no checklist line, and the wait stays. On a timeout the step is
announced as skipped ("Timed out waiting for: Landing gear: UP" / "Skipping: Landing gear:
UP", heard before the non-interrupting "After Takeoff flow complete" — see
[first-officer.md](first-officer.md)).

**The A32NX and A330 confirm from the legs, not lights (2026-10-06).** Neither FlyByWire jet
has the Fenix's gear lights, so `FbwA320GearConfirmation` (`FirstOfficer/FBWA320/`, shared by
the Headwind A330) publishes the same two fields from the handle and the three leg positions:
`FO_GEAR_UP` is the handle up AND `A32NX_GEAR_CENTER_POSITION`, `_LEFT_POSITION` and
`_RIGHT_POSITION` all under 5 %; `FO_GEAR_DOWN` is the handle down AND all three over 95 %.
Any unknown input gives NaN, so a flow's wait reads "not yet" instead of a false positive.
`AT_GEAR_UP_CHECK` on those two aircraft is the same read-only 20 s wait (FO-13), and the
Landing checklist's `LDC_MEMO_GEAR` reads `FO_GEAR_DOWN`. The A32NX gear lever itself still
cannot be written, so its power-up flow's gear-lever step reads it instead (2026-10-09): a read-only
5 s check of `GEAR_HANDLE_POSITION`, "Already set" with the lever down and skipped aloud otherwise,
that completes the detect-only "Gear lever: DOWN" line (it used to be a Captain reminder; the
Headwind A330 is the same, and the Fenix writes its lever down).

### Fenix v3: the Fenix windows (input mode, Ctrl+Shift+F)

Input mode, then Ctrl+Shift+F (`HotkeyAction.ShowAircraftWindows`, hotkey id 9254) opens "Fenix windows" (`Forms/Fenix/FenixWindowsForm`): a list whose rows read "Name. Description" (a ListBox's accessible name is its item text, so what is shown and what is spoken are one string). Enter or a double-click closes the list and opens the selected window; Escape closes it. It says nothing of its own beyond a failure to open. Any other aircraft says "This aircraft has no extra windows." (`MainForm.Hotkeys.cs`, for every aircraft that did not handle the action), and a Fenix with no registered window says "No Fenix windows yet." The list is a tracked window (`ShowTrackedWindow`): a second press brings it forward and an aircraft switch closes it. `FenixWindowRegistry` builds the rows from one optional partial file per window, in the order Engines, Cabin, Failures, Fenix documents, Fenix options (`FenixWindowRegistry.Engines.cs` … `.Options.cs`, each implementing an `Add…Windows` seam, so no window's file edits another's; names must be unique, `FenixWindowRegistryTests`). Every window opens through `FenixA320Definition.ShowFenixWindow` and the shared `FenixWindowContext` (the definition, the `FenixDataService`, SimConnect, the announcer, the main form), so none outlives the aircraft it controls. Common rules: a window says nothing on opening and never repeats what the screen reader says ([CORE-7]); its status text is a read-only TextBox ([VAT-13]); value lists are `DisplayListBox`es (one line per value, braille-friendly); data-service callbacks arrive on a pool thread and marshal with try/catch `SafeBeginInvoke` or never marshal at all ([FNX-2], [A380C-6]); reopening a minimized Fenix window leaves it minimized (shared code, not changed). Formatting is invariant and tested under de-DE and sv-SE.

**Engines** (`FenixEnginesForm`, "Fenix engines"). Both engines' running flag, N1, EGT, N2, fuel flow and oil quantity, pressure and temperature, plus TAT and OAT, from the Fenix's own data-service values, the 18 names of `FenixEngineNames` ([FNX-16]; the figures that show the stock SimVars do not match the Fenix are in its full text). Two rows say whether each engine is running ("Engine 1: running", "Engine 2: not running"), then one value per row, both engines on adjacent rows so they compare row by row, in the order of the Airbus screens (E/WD: N1, EGT, N2, fuel flow; then the SD ENGINE page: oil quantity, pressure, temperature; then TAT and OAT), worded as the PMDG 777 System Display ENG page ("Engine 1 N1", "percent", "degrees C"). Precision: N1 and N2 0.1 percent, EGT 1 degree C, fuel flow 1 per hour, oil quantity 0.1 "quarts", pressure 1 "psi", temperature 1 "degrees C". The oil units are the Fenix SD ENGINE page's QT, PSI and °C, read against the window on 2026-10-22 on a CFM A320 (oil quantity 17.5 and 14.5 QT against 17.73 and 14.51; pressure 0 and 34 PSI against 0 and 33.85; temperature 15 and 30 °C against 14.97 and 31.76; engine 2 fuel flow 300 KG/H against 289, the E/WD showing steps of 20; TAT +15 against 14.97; Output O matched the window's OAT, so O stays the stock `AMBIENT TEMPERATURE`). Fuel flow is in the Fenix's own `weight_unit` setting (Kilograms or Pounds; read when the window opens and on F5; the service publishes `ff.kg`, converted at 2.2046226218487757 pounds per kilogram; kilograms, and the status says so, when the setting cannot be read). Unknown is "--", never 0; numbers are invariant, with an ASCII minus (sv-SE's negative sign is U+2212) and never "-0". `aircraft.engines.{1,2}.vibration.n1` reads `""` on v3 (not published), so there is no vibration row. Values come from the subscription for the running flags and the poller for the rest ([FNX-10]); the callback writes only the lock-protected `FenixEngineSnapshot` and a 1 s WinForms timer reads it into the list, reconciled in place and never calling `Focus` or `Activate`, so the form never marshals per update. A value that jitters (every value moves in its third to fifth significant digit: oil temperature 116.73, 116.62, 116.55 over 0.8 s) is held by `FenixEngineDisplayHold` until the raw value moves 0.6 of a display step, because a focused row whose text changes is re-read by the screen reader; during a start the focused N2 row reads about once a second, and in cruise the rows stay still. The snapshot takes a read only when at least one value is known (a gateway that is down leaves "Waiting for engine values from the Fenix. Is the Fenix loaded?") and never lets a read that a newer subscription push overtook undo it. Speech: nothing of ours on open, arrowing or Escape; F5 reads again and says "Engines refreshed" ("No engine data from the Fenix. Is the Fenix loaded?" when no value is known); and while the window is open the running flag's edges are spoken, queued, "Engine 1 running" or "Engine 1 stopped" (baseline first, so opening it says nothing, and a data dropout does not re-speak). The owner kept those window-only (2026-10-22); an always-on watcher with its own Ctrl+M row was not built, which is why the engine background seams are empty. Measured on the CFM A320 (2026-10-22, engine 2 started with the window open): N2 left 0 at 12:25:00, fuel flow came from about 24 % N2, and the Fenix set `running` at 12:25:49 with N2 59.2 %, N1 18.1 %, EGT 410 °C (idle settled at N2 59.0, N1 17.9, EGT 409, fuel flow 290 kg/h), the moment its generator came on line: the flag means the start is complete, not light-up. Cold and dark (engines, APU and batteries off) the status read "Fenix A320, CFM engines. Fuel flow in kilograms per hour, the Fenix's weight unit. Values update every second; F5 reads them again." Known minors: rows keep their last values after the Fenix quits with no per-row marker (only the status says the values stopped); F5 pressed while the open-time read is still running starts a second read ("No engine data" can be spoken twice with the gateway down); "No engine data" is spoken when the HTTP read fails even if the subscription already delivers. Pinned by `FenixEngineWindowTests` (including that the window never marshals and cleans up), `FenixEngineFormatTests` and `FenixEngineRunningWatchTests`. Outside the First Officer only Output O and the weather window read a stock temperature on the Fenix, and no stock engine SimVar is read anywhere else (surveyed 2026-10-22).

**Cabin** (`FenixCabinForm` with `.Audio.cs` and `.Controls.cs`; `Services/FenixCabin*.cs`). The Fenix's flight attendant panel (FAP), as an accessible window, because the FAP web app cannot be hosted like the EFB (it opens on a screensaver, see "Fenix v3: the EFB window"; decision 2026-10-21). Five tabs (Ctrl+Tab moves between them; the house `AccessibleTabControl`, so NVDA says only the tab name), with a read-only status box above them that says whether the Fenix answers and whether the cabin system has started ("Cabin system ready."): *Status* (cabin ready with a checkbox, the cabin lights combo Bright, Dim 1, Dim 2, Off, boarding music, doors, slides, cargo doors, temperatures, water and waste, FAP cautions), *Audio* (boarding music on or off, channel and volume; the prerecorded announcements: play now, add to or remove from the memo, clear the memo, play next, play all, stop; the announcement set when `maxVariant` is above 0; and the FAP's loudspeaker volume, the Set-Up store's, in 5 percent steps), *Doors* (each door with its slide and pressure messages; open or close a door or cargo door), *Temperature* (the forward and aft zones: warmer, cooler, reset to the cockpit temperatures) and *Water* (water, preselect, waste, service panels, lavatories, cautions). Left out of the FAP: Smoke Detection, Seat Setting, Cabin Programming and Layout Selection (FAP-local screens with no data name and no write behind them), System Info (part numbers the FAP generates from the MSN) and FAP Set-Up's screen brightness (no use to a blind pilot).
- *Data.* `FenixCabinNames` holds the 80 names, taken from the FAP bundle's own data-name table (webpack module 3716, `cabinReady:"aircraft.communication.cids.cabinReady"` and the rest; the door control and cargo names, the cargo movement flags and the height above ground from the EFB), with the composed ones (`aircraft.communication.cids.door.d1l`, `.slidePressure.d1l`, `….lav.a.flushOperational`: the bare `door`, `slide` and `lav` names read `""`). A `FenixDataPoller` reads all of them once a second (not the subscription, [FNX-10]), the FAP's audio state (`FenixCabinPram.StateQuery`: `fap { pram { state { bgmOn bgmChannels … } } announcementsVariant { preferredVariant maxVariant } }`) every 2 s, and a 300 ms timer rebuilds the lines when something changed. Every value is applied, Unknown included, so a gateway that stops answering turns the lines to "no data" ([FNX-1]); a door-pressure caution needs a known number; "Cautions: none" needs at least one caution input known (one unrelated known name proves nothing), else "Cautions: no data".
- *Writes* ([FNX-14]) are the FAP's and the EFB's own, from the Fenix 3.0.0.7426 bundles: cabin ready (`writeBool`; the FAP grays the button unless `cabinReady.available`, so a press while it says not available speaks "Cabin ready is not available yet." and writes nothing); cabin lights (`writeString`: Bright, Dim1, Dim2, Off, the FAP's `setBrightnessLevel` values); temperature (a zone's offset in 0.5 steps between -2.5 and +2.5, grayed at a target of 30 or more or 18 or less; reset writes 0); water preselect (steps of 25 from 25 to 100); the loudspeaker (5 percent, written as a fraction; the rounding lives once in `FenixCabinWrites`); the `fap { pram { … } }` mutations for music, volume (the FAP sends ±1 with no clamp; the server's ceiling is unmeasured, the owner stopped at 10), channel and announcements, each built from the bundle's text verbatim with its `success` checked; and the EFB's ground-service doors (`doors.control.<key>` Int Armed 0, Disarmed 1, Open 2, whose toggle writes Open or Disarmed and never Armed; the cargo doors Bool, their toggles grayed while `fenix.doors.cargo.{fwd,aft}.movement`). Doors and cargo doors refuse above 100 ft above the ground and with that height unknown, as the EFB shows its toggles only at or below 100 ft (EFB chunks 856 and 964): "Doors can only be opened or closed on the ground." and "Height above ground is not known." (the owner kept the hard refusal, 2026-10-23). Every control says "The Fenix is not answering." first when nothing answers, an unknown loudspeaker volume, water preselect or door control refuses "… is not known." instead of stepping from an assumed value, and presses that would change nothing say so ("The memo is already empty.", "Nothing is playing.", "Both zones already have no offset.", "No audio data from the Fenix." when the data answers but the audio state does not). Door names are the FAP's: "Door 4 left" (data name `d4l`) where the EFB calls the same A319/A320 aft door "2 left"; the lavatory caution reads "Check lavatory power supply: LAV A".
- *Layout* ([FNX-15]). `FenixCabinLayout.Resolve` gives the loaded airframe's doors, slides, ground-service doors and lavatories from the Fenix settings `emergency_exits_type` and `aircraft_variant` first (read at start, when the Fenix starts answering and on a variant change, never by a render), then the variant's type; the FAP's own defaults are A319 SingleOverwing/HighDensity, A320 DoubleOverwing/SingleClass and A321 DoubleFullsize/TwoClass, doors 1L 1R 4L 4R on the overwing layouts, lavatories A D E (SingleClass), A D (HighDensity), A M D E (TwoClass). The data service answers for doors an airframe lacks: the IAE A321 read overwing slides it does not have as armed (2026-10-21), and the owner's A320 (settings DoubleOverwing, SingleClass) lists doors 1 left and right and 4 left and right, two overwing slides, the forward, aft and bulk cargo doors and lavatories A, D and E, with its overwing slides armed at the gate and its main doors disarmed (2026-10-23).
- *Audio lists.* The music channel list comes from the data (`bgmChannels`) and is per livery: the IAE A321 Delta livery listed one channel, "Boarding Music" (2026-10-21), where an A320 listed 15 (2026-10-21), so the list is never assumed to have a size. Announcements: "After Takeoff" and "Safety Briefing" on the A321, four on the owner's A320 (After Takeoff, and a Safety Briefing each for the A319, A320 and A321); `announcementsVariant` is 0 of 0 on both, so the "Announcement set" selector is not shown.
- *Speech.* After a press the window speaks only what the screen reader cannot: the new volume, temperature target or preselect (", unchanged" when nothing moved), a door or cargo door once it has opened or closed (the read-back waits for the part the press changes, `FenixCabinLine.State`, never an intermediate state: a cargo door "moving" is not settled), the announcement now playing, the memo. A refusal interrupts, a read-back queues. After the pilot changes a check box or combo the controls keep that choice for 3 s so a render from values read before the write landed cannot flip them back (the lists and the Doors button always follow the data). The Doors tab's button is hidden on a line with no door control (the overwing slides) and when nothing is selected. A check box whose value is unknown (Cabin ready, Boarding music) shows unchecked and no press acts on it (a code-set Indeterminate would make NVDA say "half checked"; the owner may choose).
- *The app-wide announcements* (`Services/FenixCabinReadyMonitor`, started by `FenixA320Definition.Cabin.cs` from the first sim update and disposed when the pilot switches away, so they work anywhere in the app with the Fenix loaded, the window open or not). It speaks four kinds, each with its own Ctrl+M row in the Fenix Monitor Manager (`FenixCabinAnnouncements.Rows`, appended after the variable rows by `FenixMonitorManagerForm`, as the A380 does for its ECAM memos row; keys `FENIX_CABIN_READY`, `_DOORS`, `_SLIDES`, `_CAUTIONS` in `UserSettings.FenixDisabledMonitorVariables`, read each time it is about to speak, so a mute applies at once): "Cabin ready", once per known false-to-true change of `aircraft.communication.cids.cabinReady` (in v3 the virtual purser sets it, not the cockpit cabin call; settings `cabin_ready_call_enabled` True and `cabin_ready_fwc_type` Checklist, read 2026-10-21; its owner is the monitor alone, and the window and the First Officer only show the value, [FOA-13]: `FenixCabinWindowTests.Only_the_monitor_speaks_cabin_ready` scans every Fenix file for the literal); a passenger or cargo door opening or closing ("Door 1 left open", "Forward cargo door closed"); "Slides armed" or "Slides disarmed" when the passenger doors' slides are all one or the other (the overwing slides are no part of it and a mixed state is silent); and "Cabin caution: …" once when a FAP caution appears (nothing when it clears). Every kind speaks only a known change after a silent baseline (the poller's first read; a value that is not a Bool is ignored and keeps the baseline, never read as false), so connecting to a cabin that is already ready says nothing. After the Fenix has not answered for more than 10 s (`OutageRebaseline`: every polled value unknown, a reload or a second flight in the same session) the first values that answer again are a new silent baseline, so there is no burst of changes; a shorter blip keeps the baseline (this needs every polled name to read unknown). A door the pilot pressed in the Cabin window is left to the window's read-back (`FenixCabinOwnPresses`): the background line for it is held while that read-back can still speak, plus about 2 s after it does, and released when the window closes or the read-back times out, so it is said once. Pinned by `FenixCabinReadyMonitorTests`, `FenixCabinEventsTests` and `FenixCabinWindowTests`.
- *Checks.* Owner, 2026-10-23, Fenix A320 3.0.0.7454 at the gate (DoubleOverwing, SingleClass, CFM; the bundles fetched again, every chunk cited byte-identical): the window opened silently and every read matched; door 1 left and the forward cargo door opened and closed, each read back once it settled; boarding music, its volume, the loudspeaker (95 and 100 percent, "already at maximum"), cabin lights, temperature, water preselect and the memo wrote as expected; a door opened from the EFB's "2 left" toggle was announced "Door 4 left open", the four Ctrl+M rows sat at the end of the list and muting one silenced its kind, and nothing was spoken at connect. Not yet heard: "Cabin ready" once during boarding with the virtual purser (if it never reports, note when `.available` becomes true and press the Cabin ready box once), the refusal above 100 ft, "Slides armed" before pushback and "Slides disarmed" after arrival, a "Cabin caution: …" line, no burst when a second flight loads in the same session, and pressure cautions near their limits not repeating (they are not debounced). Known and not blocking: rapid presses (volume, Remove from memo, Reset) faster than the next state read can send the same target twice; if the background poll sees a door settle up to about a second before the window's poll does and the read-back times out or the window closes in that same second, the door is not announced (never wrong, never twice; a per-door "handed back" tombstone would close it); a refused or throwing door press can release a newer in-flight press's mark for its round trip, and the 2 s grace assumes a gateway read under about 1 s.

**Failures** (`FenixFailuresForm`, "Fenix failures"). The Fenix's manual failures as a tree of ATA chapters in the Fenix's own order ("Air Conditioning, ATA 21": title first, for first-letter navigation), groups (a group with one failure shows no group node, as the EFB) and failures named by their full `title` ("CPC 1"; the EFB strips the group name to "1"). A failure's node says "failed", "armed: <condition>" or "armed: fails in N seconds"; the conditions use the EFB's own unitless labels ("above IAS 250", "above altitude 10000 AMSL"). A search box (Enter jumps to the results and says how many; the EFB's rule: a case-insensitive substring of the heading, group name or failure title, a matching heading or group keeping all its failures, debounced 300 ms), a Show filter (all, armed, failed, armed or failed), and Fail now (Alt+N), Arm (Alt+A: the dialog takes above IAS, above or below altitude AMSL, after V1, take-off or landing, and seconds) and Clear (Alt+C), each asking Yes/No first with No the default ([FNX-17]); F5 refreshes; Arm with no condition is refused ("Enter at least one condition."; the EFB saves an empty `{}` and what the Fenix does with it is unmeasured). The status box shows the variant, the totals ("549 failures in 20 chapters. 0 armed, 0 failed.") and the Fenix's automatic-failure options (`auto_failure_mode`, `failure_rate`, shown read-only; the options window owns changing them). While open it re-reads the catalog every 10 s (the EFB does not poll) and speaks failures that changed without its doing ("Failure triggered: …", at most three named, "And N more changes." / "And 1 more change."). Escape with the Show list dropped open closes only the list. Nothing speaks on opening.
- *Endpoints*, all under `/fenix` (the EFB page's origin plus `/fenix`; EFB chunk `964.*` backend service and `463.*` `ManualFailuresFeatureModule`, route `efb/manual-failures`, on 3.0.0.7426): `GET /fenix/failures/manual` (`loadManualFailures`) and `POST /fenix/failures/saveManual` (`saveManualFailure`, JSON). `loadFailureCases()` GETs `/failures`, has no caller in any chunk and answered 404; `loadArrivalFailureCases()` GETs `/failures/arrival` and feeds the arrival-procedures tree, not manual failures: neither is used.
- *Shapes.* The catalog is chapters of groups of failures (A320 CFM, 2026-10-21: 65,828 bytes, 20 chapters, 178 groups of which 29 hold one failure, 549 unique ids, none armed or failed; first failure `F_PNEUMATIC_LAV_GAL_FAN` "Lavatory/Galley fan" in group "Lavatory/Galley Ventilation"; the A321 IAE 66,393 bytes and 555, [FNX-18]; reply `application/json; charset=utf-8`, `Server: Kestrel`). A failure has `id`, `title`, `failureCondition` (null, or `{id, ias, alt, altb, time, afterEvent, afterEventSeconds}`) and `failed`; armed is a truthy `failureCondition`, and a failed failure shows failed even when armed. The EFB's Apply copies the dialog's condition and `failed` onto the catalog object, turns an emptied number field into `undefined`, and posts the object (`FenixFailureRequests.BuildSaveBody` does the same: the GET's own object, deep-cloned, only `failed` and `failureCondition` changed, numbers as JSON integers, Clear removing the condition, `time` never written); the reply is the saved failure and is what the window speaks ([FNX-17]). The EFB's condition fields: "Above IAS" `ias` 0-10000, "Above Alt AMSL" `alt` 0-50000, "Below Alt AMSL" `altb` 0-50000, "After Event" `afterEvent` (none, "V1", "Takeoff", "Landing") and "After Time" `afterEventSeconds` 0-10000 ("Seconds [from event] until failure"). The test fixture holds only the first chapter (ATA 21: 14 groups, 57 failures) of the catalog, which is Fenix's content in a public repository.
- *Measured* (owner, 2026-10-22, Fenix A320 IAE, Lavatory/Galley fan): a fail-now body without the EFB's page-only `displayTitle` was accepted and the reply was the saved object (sent `{"id":"F_PNEUMATIC_LAV_GAL_FAN","title":"Lavatory/Galley fan","failureCondition":null,"failed":true}`, reply identical); failing it raised an ECAM message and Clear (`failed:false`) repaired it and the message cleared. A timed arm sent `{"failureCondition":{"afterEventSeconds":30},…}` and the reply condition was `{"id":4,"ias":null,"alt":null,"altb":null,"time":30,"afterEvent":null,"afterEventSeconds":null}`: seconds without an event become `time`, the SECONDS REMAINING, a float counting down one per wall-clock second at sim rate 1 (30.84 to 0.78 over 30.1 s), and at zero the Fenix sets `failed:true` and removes the condition. The EFB's own code reads `time` as a clock time ("Armed at"), and the window first read 30 as Unix milliseconds ("armed at 19:00"), then showed the raw float; a numeric `time` now reads "armed: fails in N seconds" (rounded up, at least 1), an ISO text "armed at T", and the 10 s re-read ignores a countdown that only ticks (`FenixFailureText.Changes`). The "Failure triggered" call came once, the ECAM chime sometimes talking over it. **Unmeasured:** whether several condition fields combine as AND or OR (an optional flight step: arm with above IAS 100 and above altitude 30000 before take-off; a failure on the roll means OR, none before 30000 ft means AND), the units of IAS and altitude (the window keeps the EFB's unitless labels), whether the countdown pauses with the sim, what `time` holds when an event is chosen, the reply to an empty `{}`, and an EFB-side arm while the window sits on that failure's node.
- *Known minors:* the status box can show a stale summary after an outage once search or Show is used; an `afterEvent` outside V1/Takeoff/Landing pre-fills as None; a selected group node falls back to its chapter on a rebuild; Arm on an already failed failure keeps `failed:true` (as the EFB) and speaks "X failed."; "clear all" is not built (the EFB has none; it would be one POST per failure). The writes are never made in tests and need the owner's go-ahead in the sim.

**Fenix documents** (`FenixDocumentsForm`, "Fenix documents"). The EFB's documents (ECAM procedures, QRH, checklists, delay allocation codes, the Fenix user guide, and the pilot's own in My Documents) in the EFB's folders and order, the gateway's search, and a reader. Why a window of our own: the EFB's Documents app has a labeled search box and readable titles, but only four focusable elements (quick settings, search, clear, upload), so no result, folder or pinned procedure opens without a mouse; the EFB layer now makes the app usable, but it has no search on Enter and no pinned-procedure key.
- *Keys* (window only; no new hotkey): Enter opens; Ctrl+F the search box (Enter searches, at least 3 characters, 10 results, as the EFB; the EFB searches as you type, which talks over a screen reader; "Type at least 3 characters to search."); F6 moves document, tree, search box, document (Shift+F6 the reverse; the owner's order, 2026-10-22); Ctrl+P opens the documents the Fenix pinned, one after another; Ctrl+D pins or unpins; F5 reloads; Escape hides the window and keeps the open document (reopening shows it). The status text names every key. **Fenix options** (`FenixOptionsForm`, "Fenix options"). Every option of the Fenix EFB's Settings with its value in the Fenix's own words, as a tree of groups (`NativeAccessibleTreeView`, [CORE-12]; children filled on `BeforeExpand`; no `TreeView.CheckBoxes`, [CORE-18]), a read-only details box and a read-only status box. First the group "Options that affect MSFS Blind Assist" (the eleven of `FenixOptionKeys.AffectsApp`, each with a note from `FenixOptionNotes` that Enter speaks and Tab shows; an affecting option is listed there and again in its own category), then one group per Fenix category in the EFB's own order, then "Other, not in the Fenix EFB" (the options the EFB hides, `writable` false or category None, which carry the variant facts `type_code`, `engine_family` and `is_sharklet`). A row reads "Label: value": On or Off, the EFB's label for a choice, a plain number written invariant (`0.###`), or the text; the five credentials read "set, hidden" or "not set" ([FNX-19]). It reads on open, on reopen and on F5 ("Refreshed, N options changed."), with no `settingsState` subscription (`Subscribe` carries only data refs, and options change only when the pilot changes them or a SimBrief import switches `weight_unit`, which no app path reads); a read that keeps every group and option in the same order only rewrites the nodes' text, so NVDA's place holds. 146 options on the A320 CFM (Boolean 73, Enum 42, String 19, Int32 11, Single 1; sources Internal 76, UserFile 41, Livery 28, Session 1; read 2026-10-22), 149 on the A321 IAE.
- *Where the words come from.* The labels, descriptions, control hints and the per-option value labels are the Fenix EFB's own: they come from the one EFB bundle chunk that defines the `humanizeKey` pipe (3.0.0.7426, `FenixOptionLabels.SourceVersion`) and are rows of `key|value|label|description|control` in `FenixOptionLabels.Table` (an empty `value` is the option's own row; any other is a value label of the option above it; an empty value label, as acp_type's Classic and Modern which carry only a picture, means no label). Value labels are scoped to their option ("Realistic" differs between refuel rate and failure rate). A key with no EFB label reads through `FenixOptionCatalog.Humanize`, a port of the EFB's `humanizeKey` pipe (separators to spaces, a break after a run of capitals and before each capital that follows a lowercase letter or digit, each word capitalized; "IaeV2500" reads "Iae V2500"; culture-invariant, tested under tr-TR), which is what the EFB itself shows; a value with no label shows the raw value and `""` shows "(none)". Never our own wording: 25 keys had no EFB label on the loaded A320 (the hidden ones, the FAP volumes, …). Pinned by `FenixOptionLabelsTests` and `FenixOptionCatalogTests`. Raw choice names such as "ManualImport", "IfrHi" and "AviationWeather" are what the EFB shows but may read run together with a screen reader; the owner decides whether to split them.
- *Regenerating the labels after a Fenix update.* The recipe is the header of `Services/FenixOptionLabels.cs` and `tools/fenix-gateway/README.md`: (1) with the Fenix loaded, `python -I tools/fenix-gateway/fetch_gateway_bundles.py <new empty folder outside the repository>` downloads the EFB and FAP bundles read-only (HTTP GET against 127.0.0.1:8083; never commit them); (2) find the file under `<out>/efb/` that contains `name:"humanizeKey"`; (3) `python -I tools/fenix-gateway/option_labels.py <that chunk.js> <out.tsv>` reads the object literal that ends right before that pipe with a small literal parser (so a value label stays with its own option and no description is cut; an earlier regex extract dropped 18 descriptions, truncated door automation's, kept `→` escapes and lost the scoped value labels) and writes a UTF-8 tab-separated file with a header row (`key`, `value`, `label`, `description`, `control`), tabs and line breaks inside text becoming single spaces; it stops if a label or description holds a `|`; (4) paste its rows over `Table` (header dropped, tabs turned into `|`), update `SourceVersion`, and run `FenixOptionLabelsTests`. Run both scripts with `python -I` and on a bundle in its own folder.
- *Changing an option.* F2 changes an on/off or choice option for this simulator session only (`persist: false`), as the EFB's own toggle does (the Fenix's tooltip: it is overridden for the current simulator session and resets when MSFS closes or the aircraft or livery changes).
