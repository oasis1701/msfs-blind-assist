# COWS Diamond DA40 (NG and XLS)

MSFSBA's first general-aviation aircraft, and its first G1000 airframe. The two variants
share one definition (`Aircraft/DA40/CowsDA40Definition.*`, `partial` across one file per
panel) and are told apart by aircraft TITLE, never by probing an L:var — an L:var the
other variant lacks reads 0 rather than erroring, so a probe cannot distinguish "absent"
from "off".

The guiding rule is the same one every other supported aircraft follows: **a blind pilot
gets this aeroplane at the depth a sighted pilot gets it.** Nothing is simplified away,
nothing is auto-completed, and MSFSBA reports rather than decides.

## Three airframe rules that are NOT obvious

Every one of these was established by live testing, and each has already caused a control
to be wrongly declared broken.

1. **`STATE_*` L:vars are READ-ONLY MIRRORS.** A write to one sticks on read-back and
   drives nothing at all. Write the K: event or the input L:var, then read the mirror to
   confirm. (This is the DA40's instance of the general rule in
   [troubleshooting-playbook.md](troubleshooting-playbook.md): read back the DOWNSTREAM
   effect, never the var you wrote.)

2. **Momentary controls need a REPEATING write, not one write.** The airframe zeroes them
   every frame, so a single write is discarded before anything samples it. `HoldLVar`
   (in `CowsDA40Definition.Ecu.cs`) re-writes at 40 ms for a measured hold and then
   releases to 0. Used by the ECU test (26 s — the POH says the sequence takes 20-25 s,
   and 11 s reached only step 1) and the standby gyro cage (700 ms).
   The airframe plays its click sound on EVERY write, so a hold is audible as a burst of
   clicking — keep holds as short as the function allows and say what the button did, or
   a control that works sounds like one that is stuck.

3. **The fuel valve is wire-locked.** It cannot leave MAIN at all until the safety wire
   is broken — the model forces `0 (>L:FUEL_SELECTOR)` on every position while
   `FUEL_SELECTOR_WIRE_CUT` is clear, so a write to the selector looks accepted and reads
   back 0. Break the wire first (a held control, rule 2), then the valve moves. See the
   Fuel System panel below for why this is not a curiosity: OFF is the engine-fire
   procedure.

## Gauge arcs — every value carries its band

A sighted pilot does not read "87 degrees" off the oil temperature gauge; they see the
needle in the green, and that IS the reading. `DA40InstrumentBands` transcribes AFM
section 2.5 verbatim and `TryGetDisplayOverride` annotates every gauge that has published
arcs, at full resolution — the value AND the band, never a rounded band alone.

Boundaries belong to the HIGHER band, matching the AFM's own wording ("50 to 135" green
with 135-140 caution). A gauge with no published arcs renders unchanged, so the
annotation can be applied unconditionally.

Take the RPM from `PROP_RPM_SENS:1`, never `DISP_PROP_RPM` — the display var is
QUANTISED TO 10 (it read 710 against a true 705.12). The rule generalises: a `DISP_*` var
is what the G1000 draws, which is not always what the sensor measured.

`ABS_AMBIENT_TEMPERATURE` is KELVIN. The L:var's Units field is a LABEL, not a
conversion — it read 303 for a 30 degree day. OAT comes from the `AMBIENT TEMPERATURE`
SimVar instead.

## What gets a panel, and what does not

**Anything doable outside a panel does not get a panel.** The G1000's own pages — the
MFD, the electronic checklist, Aircraft Options, the softkeys — are interactive display
surfaces, so they belong in a display window reached by a hotkey (the way the A380X E/WD,
SD, ND, PFD and ISIS windows already work), not in the panel tree. The G1000 entries in
the panel structure are the SCANNABLE READOUTS only.

**No panel may be silently empty.** A panel with no controls and no status rows renders
blank, and a blank panel is indistinguishable from a broken one. That is how a "Fuel
Transfer" panel left over from the planning sketch survived being folded into Fuel System
and was reported live as empty. `EveryPanelInTheStructureIsBuiltOrKnownUnbuilt` now
requires every listed panel to be either built or on an explicit not-yet-built list, and
its mirror requires building a panel to take it off that list. The list is
variant-aware — Engine Start, Power and Levers and Fuel System are built for the NG only,
so on the XLS they are still legitimately empty.

**No control appears in two panels** (pinned by `NoControlAppearsInTwoPanels`), and **no
control is repeated in its own panel's scan** (`ScansDoNotRepeatControls`). The engine
master lives in Engine Start and nowhere else.

Panel names key a FLAT dictionary, so two panels sharing a name silently collapse into
one — which is why the circuit-breaker panels are "Bus and Power" / "Airframe Systems"
rather than repeating names the Instrument Panel and Center Console already use. The
"CB" prefix is deliberately absent: the section already says Circuit Breakers.

## Announcements

`IsAnnounced` governs BACKGROUND changes — a switch thrown in the cockpit, by hardware,
or by a failure. It has nothing to do with double-talk from MSFSBA's own combo sets,
which the global `_uiSetEcho` wrap in MainForm suppresses for every aircraft. Conflating
the two is how this aircraft first shipped with nothing auto-announcing at all, with a
test asserting `IsAnnounced == false` that encoded the bug.

So: **every settable switch is Continuous + announced**
(`EverySettableSwitchAnnouncesExternalChanges`), and **every numeric readout is silent**
(`NumericReadoutsStaySilent`). Volts, temperatures and RPM change constantly; announcing
them would bury everything else. Numbers are READ, from the panel scan or a readout
hotkey.

The one deliberate exception on the settable side is the **power lever**, which is an
analogue quantity rather than a switch: under a hardware throttle it moves continuously,
so it is read like every other number.

Numeric ENTRY still confirms out loud — that is the one case CLAUDE.md's announcement
rule explicitly asks for, because the pilot needs the exact value back.

## No help text on the panels

⚠️ **The DA40 carries NO `HelpText` at all, on either variant, and must not regain any.** It had
78 of them. They are gone.

The reasoning is the pilot's own, and it is the same rule as *do not baby the pilot*, one step
further out: a pilot is expected to know the aeroplane, exactly as a sighted pilot is, and a
control that has to explain itself is a control that is named wrong. Redundant text between the
pilot and the switch is noise, and no other aircraft in this app leans on it — the fifteen
elsewhere are one-line button captions.

Everything those lines carried lives in THIS document, which is where a pilot who wants the
background goes. `CowsDA40PohFindingsTests.NoDA40VariableCarriesHelpText` enforces the rule for
both variants.

Three things are NOT help text and are unaffected:

* a **validation error** — "Hectopascals must be between 948 and 1066";
* a **refusal's reason** — "Will not open at 34 knots. The limit is 30." A refused action must
  say why it was refused;
* a **code comment**. The facts behind these controls are still written down beside them, for the
  next developer rather than for the pilot.

## Names come from the cockpit, not from what the control does

⚠️ **A control is named as the cockpit names it: the model's own tooltip, verbatim, and never a
paraphrase.** The pilot's ruling, and the same rule as the help text above from the other side: a
pilot who knows the aeroplane recognises the placard, and an expansion is MSFSBA's wording laid
over the aeroplane's.

The source is each variant's own `*_IN.xml` (`TOOLTIPID`, `ANIMTIP_n`) and, for the breakers,
`*_CircuitBreakers.xml`. Where the two cockpits differ, the names differ with them:

| Control | NG | XLS |
|---|---|---|
| Master | **Electric Master** (the key's ELECTRIC MASTER detent) | **Battery Master** and **Alternator Master** (a split rocker) |
| Alternate air | Engine Alternate Air | Engine Alternate Air |
| Autopilot disconnect | AP DISC | AP DISC |
| Essential bus switch | ESS BUS (Off / On) | ESS BUS (Off / On) |
| Canopies and windows | Canopy, Rear Canopy, Left Window, Right Window | the same |
| Propeller lever | — | Propeller |

Where the two differ only in CASE (the NG's "ENGINE ALTERNATE AIR" against the XLS's "Engine
Alternate Air"), title case is kept: nothing is paraphrased by it, and an all-capitals ordinary
word gains nothing through a screen reader. Abbreviations — every breaker — are kept exactly as
printed, because there the letters ARE the name.

⚠️ **Still to be confirmed by eye:** the light switches, the flap lever and the NG's engine master
take their tooltips from the simulator's own language files (`@TT_Package…`, `TT:COCKPIT.…`), not
from the aircraft, and those are not readable from disk. Their names stand until someone hovers
over them in the cockpit. The same goes for the two cabin levers, whose variables belong to a
stock Asobo template.

## Scan over announcements

Each panel carries a rich `_DISPLAY_` status block (Ctrl+3, F5 to refresh in place,
`_REFRESH_` for the 1 Hz tick). The design principle is that MSFSBA announces only what
would interrupt a sighted pilot too; everything else is there to be scanned when the
pilot chooses.

## Panels

### Instrument Panel → Electrical
**NG:** Electric Master, Avionics Master, ESS BUS, Emergency Battery and its guard — the five
switches the panel physically has. **XLS:** Battery Master and **Alternator Master** (the two
halves of its split rocker), Avionics Master, ESS BUS, Emergency Battery and its guard. Plus a
scan of each airframe's own buses, ammeter and batteries — the XLS has main, essential, hot and
emergency buses and no battery or ECU bus; the NG has both of those as well. Verified against a
full power-down.

⚠️ **The XLS had no Alternator Master at all** until 2026-09-19 — only the battery half, under the
NG's name. Each XLS half now applies the rocker's interlock — switching the battery OFF takes the
alternator off, switching the alternator ON brings the battery on — decided from the state read
BEFORE any toggle. ⚠️ Not by replaying the cockpit switch's own click code: that toggles first and
re-reads the SimVar after, but a K: event does not change its SimVar within the same execution, so
its interlock branch never fires. Measured live 2026-09-19: replaying ALT_Master's code from
both-off left the alternator ON and the battery OFF, and nothing corrected it afterwards. With the
read-first form all six combinations were measured correct. Only `TOGGLE_ALTERNATOR1` moves the alternator —
`ALTERNATOR1_SET` was measured inert — and every master write goes through
`ExecuteCalculatorCodeUnique`, because the interlock can move a master without the pilot, making
the same pick the next write in a row, which MobiFlight would otherwise drop.

### Instrument Panel → Engine Start
Engine Master and its guard, Start Key, Release Start Key, plus a 13-field scan. The
start key and release key are momentary and make no sound of their own, which is why the
scan carries starter and glow state — otherwise a working key is indistinguishable from
a dead one.

**The glow plugs are NOT a control and never were.** The ECU preheats a cold engine by
itself when the engine master goes on; the checklist order is `Engine Master ON` →
`Annunciations checked` → `Glow indication OFF` → `Start key START`. The pilot WAITS, and
cranking before the glow indication goes out is exactly why a cold engine turns and turns
without catching. Glow state, the glow timer and plug temperature are all on the scan,
and the sequence is above.

### Instrument Panel → ECU
Voter and ECU Test, plus a 15-field scan.

**The voter is INVERTED** relative to the obvious reading: 0 = ECU B, 1 = AUTO,
2 = ECU A. Taken from the model's ANIMTIPs, not guessed.

**`FADEC_ECUTEST_TIMER:1` is NOT the test's elapsed time.** It is a per-stage governor
watchdog that RESETS between stages, and reaching 4 latches a fault — so it reads 0
through most of a healthy test. The scan carries a computed elapsed time beside it, and
the "finished N seconds ago" figure is measured from the press END, not the press start.

A latched `ECU A FAIL` clears through the MFD's `Reset: ECU`, not by cycling the voter —
the POH's latched/unlatched distinction is real and was confirmed live.

### Instrument Panel → Lighting Switches
Four exterior toggles, two brightness sliders (`LIGHT POTENTIOMETER:3` and `:5`), three
cabin lights, and a 10-field scan. There is no "all cabin lights" button: that is a mouse
clickspot in the 3-D cockpit, not a control the panel has.

### Instrument Panel → Ice and Pitot
Pitot Heat, Alternate Air, Alternate Static, and a 5-field scan carrying
`ENG_ALT_AIR_FACTOR` — opening alternate air moved it from 1.00 to 0.98, and without it
there is no way to tell the door did anything.

### Instrument Panel → Standby Instruments
Standby Altimeter (typed entry accepting hPa or inHg), Gyro Cage (held 700 ms), Display
Backup, and a 10-field scan.

**The standby altimeter is a TYPED ENTRY, not a slider.** MainForm's `TrackBar` is
hardcoded `Minimum=0, Maximum=100` and maps the value as a PERCENTAGE of that range —
right for a lighting knob, wrong for a subscale, which it reported as "0 to 100" instead
of 28 to 31.5 inHg. Dropping `RenderAsSlider` on a key ending `_SET` gives a typed field.
This applies to ANY non-percentage numeric control, not just this one.

The gyro is properly modelled and gets more than an on/off readout. `ATT_GYRO_REL_PITCH`
and `_BANK` are the INSTRUMENT'S OWN INDICATION and they DRIFT — measured 2.2 degrees
indicated against a true -3.0. The scan carries the true attitude beside them, which is
the comparison a sighted pilot makes against the PFD, in numbers. Spin is a percentage
and topple is a flag; a toppled gyro reads a plausible lie and there is no other way to
know.

### Instrument Panel → Annunciators
Entirely READ-ONLY — an annunciator is an output. On the G1000 variant the physical lamps
are just four: three flap lights and the essential-bus light. Everything else the AFM
calls an annunciation is drawn on the CAS window and belongs with the CAS readout.

A flap light can be dark for THREE different reasons — flaps elsewhere, bulb failed,
breaker out — which is why the lamp state, the flap travel and the two breakers are all
reported separately.

### Center Console → Power and Levers (NG)
One lever. The NG has no propeller control and no mixture; the FADEC sets both.

The lever commands **LOAD**, not RPM, and commanded RPM is **not monotonic**. Measured
live, matching the POH curve exactly:

| lever | commanded RPM | actual RPM | load |
|-------|---------------|------------|------|
| 0 %   | 2150 | 713  | 2 %  |
| 20 %  | 1800 | 1490 | 20 % |
| 40 %  | 1883 | 1815 | 40 % |
| 60 %  | 1967 | 1991 | 60 % |

Below 20 % is the POH's **disc mode** — low power at high RPM, a lot of drag, used
deliberately to bleed speed or descend. A pilot who heard only "power 15 percent" would
have no idea the propeller was being used as an airbrake, so `FADEC_TARGET_RPM:1`
(commanded) sits on the scan beside the actual.

The scan also carries **both per-ECU lever readings** (`FADEC_POWER_LEVER_A:1` and
`_B:1`). The FADEC reads the lever once per ECU and the model gives each channel its own
failure modes; two channels disagreeing is the symptom of a lever-sensor fault, and there
is no other way to see it.

The write goes through `K:THROTTLE_SET`, which takes 0-16383 rather than a percentage
(3277 gave exactly 20 %).

### Center Console → Fuel System (NG)
Fuel Valve, Break Fuel Valve Safety Wire, Fuel Pumps, Fuel Transfer Pump, and a 15-field
scan.

The system is asymmetric and that asymmetry is the panel. Fuel is drawn from the MAIN
tank (LEFT wing) only; what the engine does not burn is routed through the AUX tank
(RIGHT wing) and returned to the main, which cools the rail's hot fuel and warms the cold
tanks. Fuel therefore piles up on the left and drains on the right, and the pilot moves it
back with the transfer pump. "Left" and "right" are the wrong words for this — the AFM
says MAIN and AUX, and so does the panel.

**Breaking the wire cannot be done by holding alone** — found by a live report that the
button did nothing. The model watches for `(L:FUEL_WIRE) 1 ==` on a 1 Hz Update, and the
held-button template zeroes `FUEL_WIRE` every frame (measured: written 1, read back 0 on
the very next request). So the variable equals 1 only in the gap between our write and
the next frame, and a once-per-second sampler almost never lands in it. The hold still
runs — it is the real gesture, and it plays the animation and the sound — and when it
completes MSFSBA makes the same `FUEL_SELECTOR_WIRE_CUT` write the model's own Update
would have made. Identical assignment, identical trigger, on a path that cannot lose a
frame race. `HoldLVar` gained a completion callback for this, which fires only when a
hold reaches full duration, never when one hold pre-empts another.

**THE FUEL VALVE IS WIRE-LOCKED.** The real aeroplane has a safety latch that must be
pulled before the handle will turn; COWS models it as a breakable wire. Until it is
broken the valve CANNOT leave MAIN — verified live (writing `FUEL_SELECTOR` 1 read back
0), and the model's switch code forces `0 (>L:FUEL_SELECTOR)` on every position while
`FUEL_SELECTOR_WIRE_CUT` is clear. Two AFM procedures need the valve moved and neither is
optional: EMERGENCY feeds straight from the aux tank when the transfer pump has failed,
and OFF is the ENGINE FIRE procedure — the model really does clear `ENG ON FIRE:1` when
the selector reaches 2. Both were flown live: EMERGENCY moved the tank selector to RIGHT,
OFF cut the feed to zero and stopped the engine. So the wire gets its own control, held
like the ECU test, and breaking it is one-way exactly as on the aeroplane.

**THE GAUGE LIES ABOVE 14 GALLONS, by design.** Measured live: the left tank held 18.78
US gal while both the probe and the G1000 read exactly 14.0. AFM 2.14.4 caps the
indication there and instructs the pilot to measure the tank with the dipstick, and says
that without that measurement the flight-planning figure IS 14 US gal. A sighted pilot
reads the cap off the placard beside the gauge; a blind pilot hearing "14 gallons" would
believe the tank held 14 gallons. So the scan reports the indication as the indication,
says when it is sitting on the cap, and gives the measured quantity beside it under the
name of the AFM procedure that produces it.

The indication is also deliberately noisy: the model computes it from the true quantity
with a slosh term driven by the turn coordinator ball, so it moves in a sideslip. That is
a real capacitance probe, not a bug.

The transfer SWITCH and whether the pump is TURNING are separate rows, because they
disagree for four different reasons — main tank full, aux tank empty, breaker out, bus
volts low — and the AFM says the switch deliberately stays put when the pump stops
itself. Same reasoning as the flap annunciators.

Fuel flow is on this scan AND on Power and Levers. That is deliberate: the AFM's cruise
table quotes power and fuel flow together, so the power panel needs it, and it is the
fuel system's headline number. It is a reading, not a control — the no-duplicates rule is
about switches.

There is NO left/right tank selection on the NG, and nothing to be gained by looking for
one: the checklist item is "Fuel transfer — AS REQUIRED", repeated in cruise, against a
maximum unbalance of 9 USG. Picking the fuller tank is an **XLS** procedure — its
checklists say FULL TANK, FULLEST TANK, FULLER TANK and SWITCH TANKS — and it belongs to
the XLS fuel panel, which has a genuine LEFT/RIGHT/OFF selector.

⚠️ Physical location: the fuel VALVE is on the centre console, but the FUEL PUMPS and
FUEL TRANSFER switches are on the instrument panel (AFM 7.4 legend items 6 and 2). The
panel keeps the system together rather than splitting it across two locations.

### Center Console → Flaps (both variants)
One switch, three positions, plus a 7-field scan. The flap system is identical on the NG
and the XLS; only the limit speeds differ (110/98 against 108/91), and the panel reads
them from `DA40Speeds` rather than carrying its own copy.

The detents are **not proportional** — measured live, UP, T/O and LDG command 0 %, about
47 % and 100 % travel — so "flaps 1" and "half flap" are both the wrong words. The panel
uses the aeroplane's own three names.

**The flaps take time**, and that is what most of the scan is for. The switch selects;
the flaps then travel on their own, and the AFM's own indicator shows TWO lights lit
while they are between detents. Selecting a position is not the same as having it, and a
blind pilot has no lever feel to tell them apart, so the scan says "Travelling, 47
percent" or "At T/O, 47 percent" rather than repeating the switch back.

**Left and right are reported separately, deliberately.** AFM 4B.5 FAILURES IN FLAP
OPERATING SYSTEM opens with *"FLAPS position … check visually"* — the one instruction in
the manual a blind pilot cannot follow. A split flap is a real modelled failure and a
serious one. Two travels and a computed asymmetry are the closest thing to that look out
of the window. A healthy pair tracks exactly: measured 47.23598 against 47.23598.

The flap limit speed is keyed on where the flaps ARE, not on what is selected — the limit
that binds is the one for the setting the aeroplane is actually carrying — and selecting
a setting above its limit speaks a warning, because overspeeding the flaps is a real way
to bend the aeroplane and the white arc is not available to look at.

The motor is on the essential bus and the model scales its travel rate by bus voltage, so
on a degraded bus the flaps genuinely crawl. Motor load is on the scan so that a slow
selection reads as an electrical symptom rather than a stuck flap.

`DA40_FLAPS_POSITION` is the same key the L readout has always used. It was registered in
`Shared.cs` before this panel existed and the panel **promoted** it rather than adding a
second copy — two keys sharing one SimVar `Name` are fine in general, but not when both
are Continuous and batched, because the continuous batch sorts by name and a duplicate
shifts every later variable's struct slot.

### Center Console → Elevator Trim (both variants)
Four controls — a typed wheel setting, held nose-up and nose-down stick switches, and a
centring button — plus a 6-field scan.

**Pitch only, and rudder trim is not adjustable at all — not from MSFSBA, not from the
cockpit, not on the ground.** The real aeroplane's rudder trim is a tab a mechanic bends;
the walkaround item is *"Trim - tab … visual inspection"*. COWS does not model an
adjustment, it models the tab's **effect**: `RUDDER TRIM PCT` is written every frame by
`Logic.xml`

```
(L:AIRSPEED INDICATED, Knots) 110 / 4 pow 100 * 100 min (L:FIX_FS24) 25 * - (>A:RUDDER TRIM PCT, Percent)
```

— a speed-dependent yaw compensation, which is why it reads exactly −25 % sitting still.
A `RUDDER_TRIM_SET` write is overwritten inside one frame (verified live: the value did
not move). Exposing a control would be inventing one that visibly does nothing.

**Two genuinely different paths to the same axis.** The AFM calls the black wheel in the
centre console the trim control — mechanical, works with everything off, forward is nose
down. The electric trim on the stick is a separate path through circuit 37 and the
autopilot. Both drive `L:INPUT_TRIM_AXIS`, which spans −100 to +100 and maps 1:1 onto
`ELEVATOR TRIM PCT` (measured: writing 25 gave exactly 25 % and 1.75°, against the
airframe's 7° limit). With the circuit out the wheel still works and the stick switch does
not — which is why the circuit is on the scan, since "the switch is dead" and "the trim is
jammed" are very different problems.

The stick switch self-clears: a single write moved the trim 0.99 % and stopped, reading
back 0 on the next request. That is a safety property — an interrupted hold cannot leave
the trim running.

⚠️ The position row is the BASE's `MON_ElevatorTrim`, not a DA40 copy. MSFSBA already
reads `ELEVATOR TRIM POSITION` for every aircraft and announces it as *"Trim up 1.74"*, so
a second key on one quantity could disagree with the announcement — and did:
the status display **never consults `Format` at all** — see below — so the copy's scan row
read "1", "2", "3" beside an announcement saying 1.74.

⚠️ **CORRECTION to an earlier note here.** The cause was not `Format` defaulting to `"F0"`.
`MainForm.UpdateDisplayText`'s numeric branch is a hardcoded `switch (varDef.Units)` that
knows only `volts`, `millibars`, `inHg` and `kHz`; everything else falls to
`$"{value:F0}"` — whole numbers, **no unit**, and `def.Format` never read. That is also why
"Fuel Flow: 9" had no unit and why `Format = "F3"` on the COM frequencies did nothing.
Changing a formatter every aircraft shares would silently re-render all of them, so the
DA40 renders its own readouts: `TryGetDisplayOverride` ends with a fallback that formats
any DA40 read-only status row as `{value:Format} {unit}`, with a small spoken-unit map so
`inHg` is heard as "inches" rather than spelled out.

**The AFM publishes no number for the take-off position.** It is a *mark on the wheel*,
and the checklist item is "Electric elevator trim … CHECKED, T/O SET". No constant for it
exists in the model or the manual, so this panel does **not** invent one. It offers the
centre of travel, which is a real defined reference, and reports position precisely enough
to set the mark from. A plausible made-up number presented as the T/O setting would be
worse than admitting the aeroplane does not publish one.

The **AP DISC** button lives on this panel rather than waiting for the Autopilot one. Its
other job is the trim interrupt, and that is what the before-takeoff check exercises —
*"DISCONN press, check electric trim not working"*. The autopilot is the last thing being
built, and leaving a checklist item unreachable until then would be a gap when the control
needs nothing from it.

**Runaway trim is modelled.** `FAILURES_AFCS_TRIM_RUN` drives the axis at 10 units per
second regardless of what the pilot commands, and the AFM's remedy is the AP DISC button,
which the model honours by blocking all trim input while held. Both are on the scan,
because a trim moving on its own is otherwise completely silent. The AP DISC button itself
lives on the Autopilot panel — disconnecting the autopilot is its main job and no control
gets two homes — so the before-takeoff *"DISCONN press, check electric trim not working"*
test becomes runnable when that panel arrives; the readout for it is here already.

### Center Console → Brakes (both variants)
One control — the parking brake — and an 8-field scan. The wheel brakes are toe pedals,
a flight control flown from the pilot's own hardware, no more a panel item than the stick.

**The brakes really do fade**, and that is why the panel exists. The model integrates a
temperature from braking energy and cools it over time, then

```
if temp > 400:  fade = max(0.1, 1 - (temp - 400) / 400)
else:           fade = 1
```

so authority starts dropping at **400 °C** and bottoms out at **760 °C** having lost
**ninety percent** of it. That is the AFM's caution made real — *"prolonged permanent
braking while taxiing will overheat the brakes and may cause loss of brake capacity"* —
and the aeroplane has **no brake temperature gauge**, so a sighted pilot learns it from
smell, feel and the aircraft not slowing. A blind pilot has none of those and would find
out on the rollout. Both wheels are reported separately because they heat separately, and
the fade multiplier is rendered in words ("62 percent of normal") rather than as a number
nobody can act on.

The parking brake is simpler than the book: AFM 7.5.2 has you pull the lever and then
*pump* the toe pedals to build pressure, but COWS does not model the pumping — setting
`INPUT_PARK` took `BRAKE_PRESS` from 0 to 100 in one step, measured live, and clearing it
took it back to 0. One toggle is the whole control; a pump button would be adding a step
the simulation does not have.

### Center Console → Audio (both variants)
Three controls, four-field scan. The DA40's audio panel is the **GMA 1347 built into the
G1000 bezel**, so by the standing rule the panel itself belongs to the display window.
What this panel owns is what the audio panel *does*, reachable without it — which radio
the microphone is on, and whether the other is monitored. Both are stock and both were
verified live (`COM1_TRANSMIT_SELECT` moved `COM TRANSMIT:1` 0→1; `COM_RECEIVE_ALL_SET`
moved `COM RECEIVE ALL` and `COM RECEIVE:2` together).

Plus the **headset jack** — a real clickspot on the console and the only audio item COWS
models itself. `L:HEADSET` is referenced by exactly one file in the package, `sound.xml`:
it changes what the pilot hears and nothing else, so it is a control and it does not
pretend to be a system.

The transmit combo is bound to **COM 2's** transmit flag so the encoding reads the way the
selection does — 0 is COM 1, 1 is COM 2 — rather than the inverted reading COM 1's flag
would give. Active frequencies ride along on the scan: "transmitting on COM 1" is half an
answer without the number, and a readout is not a control. Tuning belongs with the radios,
still to come.

### There is no Cabin Heat and Vent panel
The AFM legend has movable ventilation nozzles (item 16) and the aeroplane has cabin heat,
but **COWS models neither as a control** — no component in the interaction XML, no L:var,
no simvar. The planning pass had sketched a panel; it was removed rather than left to
render blank, the same call as Fuel Transfer. "Not built yet" and "does not exist" are
different things and the not-yet-built list must only carry the first.

## Circuit Breakers — all 34, and they work

Six panels, thirty-four breakers. The list, the L:var behind each and the label are read
straight out of the model's own `CircuitBreakers.xml`, so this cannot drift from the
cockpit: each breaker's click code is `(L:CB_XXX) ! (>L:CB_XXX)`, and **0 is IN, 1 is
PULLED**.

**They really do something** — worth saying, because a breaker panel that only remembered
its own switch positions would be indistinguishable from one that works. Verified live:
pulling `CB_FLP` extinguished `FLAP_LIGHT:1`, restoring it relit the lamp, which is the
same gating the Annunciators panel reports.

Every breaker announces. A breaker is not a control a pilot operates for entertainment;
when one moves untouched, something has failed, and that is precisely the background
change the announcement model exists for.

Each panel carries one readout: **how many of its breakers are out**. The checklist says
*"Circuit breakers … CHECKED IN"* three separate times, and answering that by tabbing 34
combos is auditing rather than checking.

Groups: Engine and Fuel (7), Flight Instruments (4), Avionics (8), Bus and Power (7),
Lighting (6), Airframe Systems (2). There is **no Copilot set** — the planning sketch had
one and the aeroplane does not.

### Every breaker is named by its placard

⚠️ **The row carries the placard, verbatim — "ADC Breaker", "GPS/NAV1 Breaker", "INST. Breaker" —
never an expansion.** One table (`DA40BreakerPlacards`) names the breakers, their trip failures and
the two annunciator rows, so one breaker is never called two things, and
`CowsDA40BreakerPlacardTests` reads every placard back out of the installed package.

⚠️ **Expanding them was not merely wordy; on four XLS breakers it was WRONG.** Those names had been
taken from the real Diamond AFM, section 1.5.6. This model wires the same four L:vars to other
things, and three independent sources inside the package agree on it — the tooltip, the failure
that pops the breaker, and the circuit the breaker cuts:

| L:var | Placard | Popped by | Cuts | MSFSBA used to say |
|---|---|---|---|---|
| `CB_APT` | ALTPROT | FAILURES_CB_ALT_PROT | circuit 24, ALT PROT | "Autopilot Breaker" |
| `CB_ACN` | ALTCONT | FAILURES_CB_ALT_CONT | — | "Annunciator Panel Breaker" |
| `CB_FAN` | CDUFAN | FAILURES_CB_CDU_FAN | circuit 21, CDU FAN | "Fan and Outside Air Temperature Breaker" |
| `CB_TAS` | TAS | FAILURES_CB_TAS | circuit 35, FIS (DATA) | "Turn and Bank Indicator Breaker" |

So a pilot pulling what MSFSBA called the autopilot breaker pulled alternator protection — beside a
second "Autopilot Breaker" (`CB_AFC`, placarded AFCS) that really is the autopilot. The AFM
describes the real aeroplane; the pilot is flying this one.

### Breaker trips: named after the breaker they pop, and five removed

A trip failure's row is named after the placard of the breaker it POPS, read from each model's
Failures.xml (`(L:FAILURES_CB_x) … 1 (>L:CB_y)`). The trip is not always the obvious one —
`FAILURES_CB_NAV1` pops `CB_GP1`, "GPS/NAV1". A trip that pops nothing is an **overload**: it adds a
large draw to a bus instead (AP and FLAP on both airframes, CDU FAN and TAS on the NG), and carries
the vendor's own designation because there is no placard to name it by.

⚠️ **Five were removed because nothing in the aeroplane acts on them.** The random-failure picker
sets them, `systems.cfg` persists them, and nothing else reads them: no breaker pops, no circuit
changes, a sighted pilot sees nothing. A row would announce a failure the aeroplane does not have.

* **NG:** ALT, ESS TIE and MAIN TIE. On the XLS each of these DOES pop its breaker, so they are
  XLS-only rows.
* **XLS:** ADF (it has no ADF breaker) and AV BUS (its AVBUS breaker is not wired to that failure).

`NoBreakerTripRowIsInert` enforces it, and it is the check the package-presence test cannot make:
an inert variable EXISTS, so a presence scan passes it.

## One airframe's variables never appear on the other

⚠️ **An L:var nothing writes is not an error to SimConnect: it reads 0, for ever.** So a row bound to
one reads as a plausible zero about a system the aeroplane has not got, and a pilot scans it and is
reassured by it.

**The XLS was carrying 32 of the NG's Austro variables** — a battery bus, an ECU bus and ECU
battery, the water jacket (block, radiator, thermostat, coolant leak), the turbocharger and its
wastegates, the high-pressure fuel pumps, the FADEC's start and fault timers, the combined
propeller-control failure, five breaker trips for breakers only the NG has, the ESS BUS lamp supply
and the induction-air factor. Twelve were on panels a pilot scans. Measured live on the XLS they
summed to exactly **0** while its own main and essential buses read 23.4 and 23.7 V. Worse, the
master's power-up read-back SPOKE one of them — *"battery 0.0"* — every time the XLS was switched
on.

The cause was structural: many builders are shared, and they were written on the NG.
`CowsDA40Definition.VariantScope` is the one place that removes each airframe's foreign variables,
from the variable set and from every panel list, after all the shared builders have run — in both
directions, since the NG has its own (the three inert trips above and the XLS's alternator master,
whose SimVar is the NG's engine master).

`CowsDA40PackagePresenceTests` keeps it honest: **every L:var a variant binds must appear, as a
WHOLE name, in that variant's own package.** Whole names, because a substring scan passed
`FAILURES_FUEL_L` on the XLS only because its `FAILURES_FUEL_LEAK_L` contains it. A text scan is
complete for this package only because it ships no WASM. The two cabin levers are allowed through
by name, with the stock Asobo template that owns their variables as the evidence.

## Loading a SimBrief plan into the G1000 — the way a sighted pilot does it

There is no MSFSBA shortcut for this, on purpose: the pilot does exactly what a sighted pilot
does, and the display window reads every step. Measured live on the XLS, 2026-09-05.

The import belongs to the **Navigraph G1000 plugin** — on the XLS a copy ships inside the
COWS package (`panel/Plugins/NavigraphMods`), on the NG it comes from Navigraph Hub's
"Avionics Plugin G1000" in Community (`navigraph-avionics-g1000`, the same code under a
different client id). It replaces the MFD's **Flight Plan Catalog** page with one that lists
the pilot's SimBrief flights, fetched through the Navigraph login (Aux → Navigraph Settings,
"Sign In"; the two "Load … on Import" rows there decide whether procedures and airways come
in). The walk, in the MFD window (Alt+M):

1. **Ctrl+G → Flight Plan Catalog.** The list reads one plan per row — "1 EGNX/EGHI" — then
   "6 to 99 empty". "Loading flights…" is read while the plugin is fetching.
2. **Shift+Enter** puts the cursor on the list: "Flight Plan List, 1 EGNX/EGHI". Arrow to the
   flight; Flight Plan Info below fills with departure, destination and distance.
3. **Softkey 5, Activate** (Enter on its row). ⚠️ Activate is DISABLED until a flight is
   focused — with the cursor off the press does nothing, and CLR drops the cursor.
4. The dialog reads **"Activate SimBrief flight plan?, OK, or CANCEL"**. **Ctrl+Enter** on OK.
5. The plugin imports and jumps to the flight plan page, and the readback leads with the page:
   "FPL – Active Flight Plan, …". The plan arrived complete — RW27 SAPC1N, Y53 DTY, M605
   SILVA, CPT1S RW20, altitude constraints, a VNV profile. A failure comes back as another
   dialog, "Import Failed …", read the same way.

Three things that are NOT routes, measured: loading SimBrief's `.pln` into the sim through
SimConnect (`FlightPlanLoad`) does not touch the running G1000 — both SimBrief files loaded
and the FPL page did not change by a leg; the Catalog's softkey 10 "Import" is the stock
G1000's import of a stored plan, not SimBrief; and the sim's own EFB/world-map plan only
reaches the avionics at flight load.

⚠️ Keep the navdata cycle current. The MFD's startup screen names it ("Navigation Data
AUG06SEP02/26" is cycle 2608); the Hub's `navigraph-navdata` package is what the G1000
flies, SimBrief plans on its own AIRAC, and an import whose procedure names crossed a cycle
boundary is the usual "Import Failed". After a Hub update, rebuild MSFSBA's own navigation
database so Shift+E and taxi guidance are on the same cycle.

⚠️ The database-acknowledge screen after a reload ("Press ENT or rightmost softkey to
continue") takes ENT over SimConnect only — the window's Ctrl+Enter does that itself while
the screen shows.

## The G1000 gets a window, not panels

The `G1000 PFD` and `G1000 MFD` sections are **gone**, along with PFD Readout, CAS
Messages, Engine Indication, Fuel Calculator and the XLS's Lean Assist. Everything they
would have carried is *on the displays* and reachable there: the PFD and MFD are clickable
and driveable over the Coherent debugger, the CAS window is scrapeable, and the radios and
transponder can **only** be tuned with the bezel knobs and softkeys — there is no other
way on this aeroplane. Lean Assist is an MFD page reached with the softkeys.

So the G1000 gets a display **window** opened by a hotkey, the way the A380X E/WD, SD, ND,
PFD and ISIS windows already work. A panel would only be a worse copy of it, and an empty
one reads as broken.

### Cabin → Doors and Windows (both variants)
Four openings — front canopy, rear door, two storm windows — and one status row.

**The two indices are OFF BY ONE**, which is the trap: the `K:TOGGLE_AIRCRAFT_EXIT` index
is one higher than the `INTERACTIVE POINT OPEN` index. Verified live in both directions —
event 3 opened `:2`, event 7 opened `:6`.

| | event | reads back |
|---|---|---|
| Front canopy | 3 | `INTERACTIVE POINT OPEN:2` |
| Rear door | 4 | `:3` |
| Storm window left | 7 | `:6` |
| Storm window right | 8 | `:7` |

**The aeroplane refuses above 30 knots, twice over.** The click code is gated on
`(A:RELATIVE WIND VELOCITY BODY Z, Knots) abs 30 <=`, so a door will not open into a
slipstream — and a 1 Hz Update *slams a fully-open canopy or rear door shut* the moment
relative wind reaches 30. A blind pilot pressing the control and hearing nothing would not
know which had happened, so the refusal is spoken and the relative wind is on the scan.

Doors are a **percentage** that travels, so each has its own position row saying "Closed",
"Moving, 45 percent" or "Open" — the two-state control can only ever say one end or the
other, and a travelling door is neither. Those rows are OnRequest on purpose: two
*Continuous* variables sharing one SimVar name would collide in the continuous batch. The
doors are registered as SimVars, never L:vars — a name with a space and a colon is stock,
and force-registering one as an L:var once broke A380 detection outright.

⚠️ **The set must fire the toggle UNCONDITIONALLY.** The first version compared the
request against the door's cached position first, and that is exactly what broke closing:
every door opened and none would shut. A two-state combo only reaches the handler when the
selection CHANGED, so the pilot has by definition asked for the state the door is not in —
a comparison there can only be wrong (a cache miss makes an open door look closed, and
mid-travel matches neither branch), and both failures are silent.

The wind row reports the ABSOLUTE value with what it means. `RELATIVE WIND VELOCITY BODY Z`
is signed, so it read "-4" sitting still — alarming and useless. The model compares its
absolute value against 30, so that is what is shown: "4 knots — doors free".

### Instrument Panel → ELT (both variants)
One control. **This panel exists because the first audit got it wrong.** That audit said
the ELT had "no interactive component in the model, so there is nothing to expose" — it
does: `Component ID="SAFETY"` uses `ASOBO_SAFETY_Switch_ELT_Template` with `TYPE ARM_ON`.
The component is named after the *system* rather than the switch, so a sweep looking for a
component called ELT walked straight past it.

The shutdown checklist item is *"ELT … check not transmitting on 121.5 MHz"*, so the state
is the whole point. Driven by `TOGGLE_ELT` compared against the current state, not
`ELT_SET`: measured, `2 (>K:ELT_SET)` left `ELT ACTIVATED` at 0 while `1 (>K:TOGGLE_ELT)`
moved it to 2, so only the toggle is dependable in both directions.

### Center Console → Cabin Heat and Vent (both variants)
Two levers, 0 to 100 — and **this panel was wrongly deleted once**. An earlier sweep
concluded COWS modelled neither cabin heat nor ventilation ("no component, no L:var, no
simvar") and removed it. Both are there, inside `Component ID="PASSENGER"`:

```
ASOBO_PASSENGER_Lever_Cabin_Air_Template   on PRESSURIZATION_Switch_Bleed
ASOBO_PASSENGER_Lever_Cabin_Heat_Template  on PASSENGER_Switch_Cabin_Heat
```

The sweep missed them for two reasons worth remembering: the component is named after the
**occupants** rather than the system, and the air lever's node is called
`PRESSURIZATION_Switch_Bleed` — a name Asobo reuses across aircraft — on an aeroplane with
no pressurization at all. Searching for the system found nothing; the *templates* are what
name it. They drive `L:XMLVAR_CabinHeat` and `L:XMLVAR_CabinAir`, both verified live.

These are the one place a **slider** is right: MainForm's TrackBar maps the value as a
percentage of 0-100, which is exactly what they are. The trim and the standby subscale are
not, which is why those are typed entries.

**Nothing reads them, and the panel says so.** Grepping the whole package for
`XMLVAR_CabinHeat` and `XMLVAR_CabinAir` finds only the two templates that *write* them,
and MSFS has **no cabin-temperature SimVar at all** — the closest in the entire catalogue
are `AMBIENT TEMPERATURE` and `TOTAL AIR TEMPERATURE`, both outside air. So there is no
cabin temperature to display because the simulation does not have one, and a readout
claiming otherwise would be invented. The levers are exposed because the cockpit has them
and a pilot can click them; the simulation models no cabin temperature at all.

What the scan carries instead is **what actually decides where they go**: outside air
temperature, and coolant temperature — because cabin heat comes off the **engine heat
exchanger**, so a cold engine has no heat to give whatever the lever is doing.

**The DA40 is not pressurized.** The AFM does not contain the word. Neither lever has
anything to do with cabin altitude — heat comes off the heat exchanger and air through the
nozzles. There is **no air conditioning** modelled either: the AFM never mentions one and
the cockpit has no control for it.

### Cabin → Seating and Payload (both variants)
Seven controls, four-field scan. Five stations — the ones the aeroplane declares in
`flight_model.cfg`, not a curated subset — plus the two crew figures.

**Weight is written to the SimVar, not through an event.** Verified live: the indexed
`180 2 (>K:2:PAYLOAD_STATION_WEIGHT_SET)` left the station at 170, while
`180 (>A:PAYLOAD STATION WEIGHT:2, pounds)` moved it. SimConnect's index is one higher
than the cfg's — `station_load.0` is `PAYLOAD STATION WEIGHT:1`.

**The crew figures are TRI-STATE.** `L:FORCE_PILOT` and `L:FORCE_COPILOT` run −1 / 0 / +1
and the model's own tooltip spells them "Pilot OFF" / "Pilot Normal" / "Pilot ON" — Normal
being the aeroplane deciding for itself. A two-position control would have thrown that
middle position away.

The scan is **the loading sheet**: gross weight in both units, what is left against the
maximum (or how far over), the centre of gravity, and whether the baggage is inside the
aeroplane's own declared 66 lb / 30 kg limit. A blind pilot cannot read the AFM's loading
envelope, and this is the part of it the simulation actually computes.

The station weights do not announce. That is the same rule as the power lever and the trim,
and the criterion is not "is it numeric" — the standby subscale is numeric and *does*
announce, because it is dialled to discrete settings. These vary continuously: a payload
station runs while GSX boards passengers, and announcing it would speak a new number
several times a second.

## Simulation — failures, damage and reset

Ten panels, built from the aircraft's own `FAILURES_*` L:vars and grouped the way COWS's
`Failures.txt` groups them.

⚠️ **That document is not the whole story for this airframe, and it is wrong in one
place.** It is largely the LYCOMING's list — magnetos, mixture and propeller cables,
manifold pressure, CHT and EGT — none of which an AE300 diesel has. The NG's own failures
are in the L:var table and absent from the document entirely: the FADEC's crank, cam and
boost sensors *each duplicated per ECU*, the two power-lever channels, the wastegate and
turbocharger, the glow plugs, the coolant loop. So the panels are built from the
variables and the document supplies only the wording — which is the right way round.

⚠️ **`L:FAILURES_RESET` does nothing.** The document says *"L:FAILURES_RESET = 1 can be
set to reset all failures"*; nothing in the model reads it. The model writes
**`L:RESET_FAILURES`** — the same two words the other way round. Verified live: setting
`FAILURES_RESET` left a raised `FAILURES_LIGHT_FLAP:1` raised, and `RESET_FAILURES`
cleared it. There is also `RESET_DAMAGE`, and `RESET_ALL` which does both, so the Reset
panel offers three buttons rather than one.

The aeroplane also has its **own** emergency reset, and it is a cockpit action rather than
a menu: engine master OFF with ECU TEST held for eight ticks clears the failures, resets
the battery and pushes the PFD and MFD breakers back in.

**Three shapes of failure**, and the document is explicit about all three: a flag set to 1;
a MODE where each number is a different failure of the same part ("stuck open" and "stuck
closed" are not degrees of one thing, so they are named rather than numbered); and a factor
from 0 to 1. The factors are offered as a **percentage** and divided by 100 on the way out,
because "0.35" is not how anyone thinks about a 35 % blocked injector.

Every failure announces — a failure appearing unasked is the most important background
change this aeroplane can produce. The severities do not: nothing outside MSFSBA sets them,
so there is no background change to miss, and a percentage is a number to be read.

Magnetos, the mixture lever and the propeller lever are **not** offered on the NG. Their
L:vars exist because both variants share one model, but a diesel has no magnetos and
setting them would do nothing. The XLS drops the four NG-only panels the same way.

## The G1000 displays

The PFD is reached over the **Coherent GT debugger** (`127.0.0.1:19999`), the same
transport the A380X and HS787 displays use. Views resolve by TITLE NEEDLE, never by id —
live, the DA40's are `VCockpit08 - AS1000_PFD` at id 11 and `VCockpit07 - AS1000_MFD` at
id 12, and those ids shuffle every session. The discovery endpoint is `/pagelist.json`;
`/json` and `/json/list` return nothing on Coherent's Chromium 49.

**The scrape is deliberately narrow: only what the display alone knows** — CAS, FMA,
navigation source, softkeys. Airspeed, altitude, vertical speed, heading and the barometric
setting are NOT scraped. They are stock SimVars the readout hotkeys already answer from,
and the DOM is a far worse source: the airspeed box is a **scroller**, so its `textContent`
is the whole digit strip (`"210987654321 123456789012-2109876543210…"`) rather than the
value. Scraping a number SimConnect already answers correctly would be choosing the
fragile source on purpose.

**The CAS window pre-allocates its rows** — 32 on this aircraft — and a cleared message
leaves its slot in the DOM with `display:none` rather than being removed. A row therefore
counts only when it is BOTH visible and non-empty; reading the node list alone would
report every message the flight has ever raised. Severity comes from the **class list and
never from colour**: rows carry a `new` class while flashing, which changes the rendered
colour underneath, so the same caution samples differently depending on when you look.

No new C# client was needed. `CoherentDisplayClient` is generic — resolve by needle,
install an agent, poll `__MSFSBA_DISP.scrape()` for `{ok, rows}` — so the agent exposes
that contract and inherits every piece of connection handling that client already gets
right. `coherent-da40-g1000-agent.js` needs its own explicit `<None Update>` csproj entry;
the build does not wildcard-copy `Resources\`.

Live, first run: two CAS cautions (`ECU B FAIL`, `ECU A FAIL`), autopilot off, navigation
source GPS at DPRT sensitivity, and all twelve softkeys read correctly — CAS, Map/HSI,
TFC Map, PFD Opt, OBS, CDI, ADF/DME, XPDR, Ident, Tmr/Ref, Nearest, Caution.

### Opening them, and pressing things

**Alt+P** opens the PFD, **Alt+N** the MFD. These are DIRECT Alt keys, not output-mode
chords: the display windows are Alt keys app-wide — the A380 uses Alt+E, Alt+S, Alt+N,
Alt+P and Alt+I for exactly this — so the DA40 follows the same convention rather than
inventing a parallel gesture. The MFD borrows the ND key, which this aeroplane has no
other use for.

**Enter on a softkey row presses it.** Any other row leaves Enter alone.

**READ OVER COHERENT, WRITE OVER SIMCONNECT.** A press does not go back down the debugger
socket: `1 (>H:AS1000_PFD_SOFTKEYS_11)` through the ordinary calculator path presses it,
verified live by watching the row change. That keeps the socket read-only — one less thing
that can wedge it — and it is the same split the A380 RMP uses.

### How the softkeys actually work

**One softkey is one button.** There is no such thing as several items behind one key. A
press does one of two things:

- **cycles a value in place** — CDI steps GPS, VOR1, VOR2, and the current one shows in the
  key's own value field, so the label stays put and the value changes;
- **replaces all twelve keys with a sub-menu.** Verified live: pressing 4, "PFD Opt", turned
  the row into `SVT / blank / Wind / DME / Bearing 1 / blank / Bearing 2 / blank /
  ALT Units / STD Baro / Back / Alerts`, and pressing 11, "Back", restored it.

So the menu is a **tree**, and the way out is always a Back key somewhere in the row rather
than a separate gesture. Because a press can change every key under the pilot's fingers,
the window re-reads immediately after one and speaks the new row — but only when the labels
actually changed, so a key that cycles a value in place does not re-read twelve unchanged
keys over the pilot.

**Blank slots are real and are reported as blank.** On that sub-page keys 2, 6 and 8 do
nothing, and a pilot needs to know that rather than wonder whether a key is missing.

### There is no typing on a G1000, and the transponder is the exception that proves it

The real aeroplane has **no keyboard**. Data entry is the dual concentric **FMS knob** —
outer ring moves the cursor, inner ring picks the character — plus the softkeys. Nothing
about MSFSBA changes that.

**But the transponder genuinely IS typed, on softkeys**, exactly as on the aircraft, and it
works today. `XPDR` → `Code` turns the whole softkey row into an octal digit pad:

```
0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | Ident | BKSP | Back | Alerts
```

Octal, because a squawk has no 8 or 9. Verified end to end: pressing 2, 3, 1, 1 typed 1200
and `TRANSPONDER CODE` read 1200 back. So a blind pilot can already squawk anything, with
Back-space and Ident sitting right there on the same row.

⚠️ **The claim in this heading is half wrong, and the correction matters.** The real
aeroplane has no keyboard, but the *simulated* G1000 does: every waypoint box carries a
small **keyboard icon**, and its input component carries `activateKeyboardInput`,
`setValueFromOS` and a `setText` that the icon drives. Typing an ident is therefore a
documented capability of this display, not a workaround — see **Ctrl+T** below, which drives
the same `setText` so that the aircraft's own database search, autocomplete and facility
lookup all run untouched.

The FMS knob still spells an ident character by character and always will, for anyone who
wants it. But twenty-eight knob clicks for a four-letter ident is punishing for anybody, and
the aeroplane itself offers the faster road.

### A display client error must reach the pilot

Nothing subscribed to `CoherentDisplayClient.Error`, so a failure left the window sitting
on "Connecting to the display..." for ever with no reason given — indistinguishable from a
hung app. The window now shows the error, and a six-second watchdog replaces the first line
with the likely causes if nothing arrives at all.

⚠️ **The agent MUST return a string containing `MSFSBA_DISP_INSTALLED`.**
`CoherentDisplayClient` tests for that exact token to decide the agent is in place;
anything else leaves `_agentInstalled` false, so `EnsureConnected` returns false and the
poll loop retries for ever **without raising an error** — a window stuck on
"Connecting…" with nothing in the log. This agent returned its own version string at
first and did exactly that, and the probe harness could not have caught it because probes
do not check the token. That silent path is now closed: a missing token raises an error
naming the agent file and what it actually returned, once per socket rather than every
retry.

The other cause is worth stating because it is not guessable either: **Coherent GT allows
only ONE inspector socket per view**, so a developer probe attached to `AS1000_PFD` locks
MSFSBA out of the very same screen.

### The whole PFD softkey tree, walked

Mapped by driving it, not by reading about it. A press must be followed by a **settle
delay** before reading the row back — the first walker read the DOM in the same frame and
reported every menu as an in-place action.

**Root:** `CAS | Map/HSI | TFC Map | PFD Opt | OBS | CDI | ADF/DME | XPDR | Ident |
Tmr/Ref | Nearest | Caution`

**Three of them open sub-menus:**

| Key | Becomes |
|---|---|
| Map/HSI | Layout, Detail, Traffic, Topo, Rel Ter, NEXRAD, METAR, Lightning, Back, Alerts |
| PFD Opt | SVT, Wind, DME, Bearing 1, Bearing 2, ALT Units, STD Baro, Back, Alerts |
| XPDR | Standby, On, Alt, VFR, Code, Ident, Back, Alerts |

**The rest act in place:** CAS, TFC Map, OBS, CDI, ADF/DME, Tmr/Ref, Nearest.

⚠️ **Key 12 is not a fixed key.** Its LABEL is the alert state — it read `Caution` with two
cautions standing and became `Alerts` once acknowledged. So the twelfth softkey tells a
pilot there is an unacknowledged alert before they read anything else.

⚠️ **VFR squawks 7000 on this unit, not 1200.** Pressing it set `TRANSPONDER CODE` to 7000.

Known gap: `Tmr/Ref` and `Nearest` open PANES on the display rather than changing the
softkey row, and those panes are not scraped yet. `CDI`'s effect does show, in the
navigation-source row.

### Auto-announce

**The transponder** announces from SimVars, needing no Coherent at all — `TRANSPONDER
CODE:1` and `TRANSPONDER STATE:1`, both Continuous and announced. A squawk is not a
continuously-varying quantity: it changes when someone sets it, and ATC assigning one is
exactly the background change worth hearing, so it announces like the standby subscale and
unlike the power lever. Output mode + X reads both together.

**CAS and the FMA** need the display, so there is an always-on watcher
(`CowsDA40Definition.CasMonitor.cs`) that runs whether or not the PFD window is open. On
this aeroplane that is not a convenience: there are four annunciator lamps and every other
annunciation the AFM lists is drawn on the G1000, so without this most failures are silent
unless the pilot happens to be looking.

It is **baseline-first** — the first scrape after connecting is absorbed silently, or
reconnecting mid-flight would re-read every message already standing. A message that
CLEARS gets one word too, because a caution going away is how a pilot learns the thing
they just did worked.

⚠️ **The monitor and the PFD window cannot both hold `AS1000_PFD`** — one inspector socket
per view. The window takes the socket, but it **feeds the detector** with the rows it reads
rather than silencing it.

The first version suspended the announcements outright, reasoning that a pilot who opened
the display is already reading it. That was wrong and showed up immediately: four CAS
messages raised by cycling the engine master appeared in the window and **none of them
spoke**. Having the window open does not mean the pilot is looking at the CAS block at that
moment, and a caution arriving while they read something else is exactly the one they need
told about. One detector, two sources, and the known-message set carries across the
handover in both directions so nothing is announced twice — which is also why there is
deliberately no re-baseline on resume.

### Instrument Panel → Radios

**A deliberate exception** to "anything doable inside a G1000 display does not get a
panel". The radios *are* tuned on the G1000 — but only by turning the dual concentric knob
one character at a time, and there is no keyboard on the aeroplane. Making a blind pilot
click a knob event per digit to reach 124.80 is what that rule exists to prevent, not to
require. Same judgement as Ctrl+B for the altimeters: the aeroplane's mechanism stays, and
MSFSBA offers a faster road to the identical result.

⚠️ **TWO RADIOS, TWO DIFFERENT ENCODINGS, on the same aeroplane:**

| | Event | Takes | Verified |
|---|---|---|---|
| NAV | `NAV{n}_STBY_SET_HZ` | **raw hertz** | `110300000` → 110.30 |
| COM | `COM{n}_STBY_RADIO_SET` | **BCD16** | `9344` → 124.80 |

The obvious-looking `COM1_STBY_RADIO_SET_HZ` does **nothing** — measured, the standby sat
at 125.855 while the BCD form moved it immediately. Neither was reasoned from the name;
both were written and read back.

⚠️ **BCD16 carries four digits, so COM is 25 kHz and no finer.** 136.975 encodes as
`0x3697` and returns 136.97. That is the only event this radio accepts, so an 8.33 kHz
channel has to be dialled on the G1000's own knob.

Everything sets the STANDBY and swaps on demand, which is how a radio is actually flown.
CRS (`VOR1_SET`) and the heading bug (`HEADING_BUG_SET`) are on the same panel.

### On the knobs

Probing them settled the design rather than driving it: `AS1000_PFD_BARO_INC` moved the
altimeter, so the knob H-events work — but almost everything a knob is *for* has a direct
setter that is exact instead of incremental. Frequencies, courses, the heading bug and the
baro all now go straight to their value. What genuinely still needs knob emulation is the
**FMS cursor** for waypoint entry, which belongs with the flight plan on the MFD.

### The PFD's popout panes

Several softkeys do not change the softkey row at all — they open a **dialog over the
display**. Until these were scraped they were pressable but unreadable: the key worked and
nothing could be read back. There are **four**, not the two the softkey names suggest:
Nearest Airports, **Alerts** (the full text behind the CAS abbreviations), Timer and
References, and ADF/DME Tuning.

⚠️ **A dialog is open when its OPACITY is not zero, and by nothing else.** All four are
permanently `display:block`, `visibility:visible`, 310×220, and carry the class
`quickclosed` whether open or shut — measured. A closed one is simply transparent.
Filtering on display, visibility, size, or that class name finds four windows that are not
on screen.

Two readability rules came out of this, both generic:

- **`textContent` concatenates with no separator**, so a pane of little spans reads back as
  `Timer0:00:00UpStart?VNE172KT On`. The text NODES are collected and joined instead — but
  **not inside a number**: the G1000 renders a clock one span per character, so a blanket
  space turns `0:00:00` into `0 : 0 0 : 0 0`. Two adjacent digit-ish characters are glued;
  everything else gets a space.
- A field the pilot has not filled in renders as a **row of underscores**, which is read as
  `blank` — one word instead of five.

The nearest-airport list has named fields, so it is read as fields rather than as its own
text: `VCBI, 020°, 0.4 NM, ILS, TOWER, 118.700, 10961 FT`.

Timer/References also carries the aeroplane's own V-speed table — `VNE 172, Vg 88, Vy 90,
Vx 72, Vr 67` — which independently confirms the figures in `DA40Speeds`.

## The MFD

The MFD is the same instrument as the PFD with different pages up, so **one agent file
serves both**. `A.side()` decides which half to render — and it asks for the INSTRUMENT
ELEMENT (`wtg1000-mfd` vs `wtg1000-pfd`), not for page markup.

⚠️ **Detecting the side by content does not work.** The first version tested for `.eis` or
`.mfd-page` and read the PFD as an MFD: both views carry some of the other's markup, unused
and invisible. The whole PFD then rendered as MFD rows — no CAS, no FMA, no navigation
source, on the one display where those are the entire point. The instrument element is the
one thing that is genuinely per-view, and it is what `A.key()` already had to look up.

The screen has five regions, read in the order a sighted pilot takes them:

| Region | What it carries |
|---|---|
| Page title | `Map - Navigation Map`, `Aux - System Setup 1`, … |
| Nav data bar | four PILOT-CONFIGURABLE slots (GS, DTK, TRK, ETE by default) |
| NAV/COM box | which radio the tuning cursor is on, and which is transmitting |
| EIS strip | the engine gauges, permanently down the left |
| Page | whatever the FMS knob has selected |

The data-bar slots are read as **whatever they currently are**, never against a fixed list
— they are changed on the Aux system-setup page, and a fixed list would silently report the
wrong label for a pilot who reconfigured them.

The NAV/COM box deliberately does **not** re-read the frequencies. Those are stock SimVars
the Radios panel already answers; what is taken here is only what the display alone knows.

### The power-up screen

The MFD comes up on a confirmation screen and shows **no pages at all** until it is
acknowledged. It carries the navigation database cycle and its expiry —

> `G1000 NXi System WT2.1.18 · Navigation Data AUG06-SEP02/26 · Press ENT or rightmost
> softkey to continue`

— and **nothing else on the aeroplane says when the database runs out**, which is a real
airworthiness item for IFR. It is reported as its own rows, alone: until it is dismissed
every other selector on the page is empty, and rendering those would make a display that is
merely *waiting* read as broken.

### The engine strip, and why it is not a duplicate of the Engine panel

Three gauge shapes, and what is readable differs by shape:

| Shape | Gauges | Carries a number? |
|---|---|---|
| dial | Load %, RPM | yes |
| text | Fuel Flow | yes |
| horizontal | Oil Temp, Oil Press, Coolant Temp, Fuel Temp, Fuel Qty | **no** |

The horizontal gauges are the interesting case. The real G1000 draws them as a needle
against a coloured scale **with no digits at all**, so "what does the MFD say the oil
pressure is" has no numeric answer — the answer is *where the needle is*. That is what gets
read: the colour band it sits in, how far along the scale, and the scale's own end labels
where the gauge prints them.

```
Oil Temp: green 66 percent along
Oil Press: yellow 34 percent along, caution
Fuel Qty Gal: left green 100 percent along, right green 100 percent along, scale 0 to 14
```

**This is not the Engine panel over again.** That panel reads the aircraft's sensor L:vars
at full resolution and answers *what the engine is doing*; this answers *what the screen
shows*, which is a different question and the one a display window exists for. The rule
that forbids duplicates is about two panels offering the same control, not about a display
being unreadable.

The band is computed from geometry rather than guessed — and the two agree: the Oil Press
needle sits in yellow while the gauge's own label carries the `caution` class, measured
together.

⚠️ **Take the needle's TRANSFORM, not its bounding box.** The pointer is an `<svg>` as wide
as the whole gauge, translated along it, so the box says nothing about where the needle
points. ⚠️ And **select on the transform, not on a class name**: a single-needle gauge wraps
its svg in `.pointer`, but the two-needle fuel gauges use `.pointers > .pointer-one-div` /
`.pointer-two-div`, which a `.pointer` lookup does not match — so both fuel gauges read
"no reading" while every other gauge worked. `svg[style*='translateX']` is the one thing
every needle on every shape has.

### The page groups

Six, and **31 pages**, read from the page selector's own lists rather than counted by
walking into things:

| Group | Pages |
|---|---|
| Map | 5 — Navigation Map, IFR/VFR Charts, Traffic Map, Weather Data Link, TAWS-B |
| WPT | 6 — Airport, Intersection, NDB, VOR, VRP, User WPT Information |
| Aux | 9 — Navigraph Settings, Trip Planning, Utility, GPS Status, System Setup, XM Radio, System Status, Connext Setup, Databases |
| FPL | 2 — Active Flight Plan, Flight Plan Catalog |
| NRST | 8 — Nearest Airports, Intersections, NDB, VOR, VRP, User WPTs, Frequencies, Airspaces |
| EIS | 2 — Engine, Checklist |

⚠️ **That is the list of NAMES, not the list of pages that exist.** Seventeen of those 32
have no view behind them at all — seven of the nine in Aux — and the knob lands on them and
does nothing for a sighted pilot too. See *Why some Aux pages cannot be reached* further
down for which are real and how the reader now says so.

The Navigraph plugin injects pages of its own into several groups, so a group can show one
of those rather than its own first page.

Rather than 31 hand-written branches, the page reader handles the four SHAPES those pages
come in — dial page, grouped fields, scrollable list, and free text — each verified live.
That is also what stops a page nobody anticipated from reading as blank.

Setup, status and utility pages are built as **boxes of labelled rows**, and the generic
one-level walk rendered each COLUMN as a single paragraph — *"Date 31-AUG-26 Time 21:24:35
UTC Time Format UTC Time Offset…"* — in which no individual setting could be arrowed to.
These are the pages a pilot *changes* things on, so they are the ones that most need
reading a field at a time:

```
Date / Time:
  Date: 31 - AUG - 26
  Time: 21:27:09 UTC
Display Units:
  NAV Angle: Magnetic(°)
  DIS, SPD: Nautical(NM,KT)
MFD Data Bar Fields:
  Field 1: GS
```

### The EIS page is not the EIS strip

The MFD's own **EIS - Engine** page is the one place on the aeroplane that prints the
numbers the strip only gestures at — and it uses **different markup** from the strip beside
it (`.dial-gauge-parent` with centred label/value elements, not `.eis-gauge`). The strip's
reader finds nothing there, so the page fell through to raw text: `0100 Load % 303000 RPM
7000` — three gauges, their scale ends and their values welded into one token. Read
properly it is the full engine picture, fuel calculator included, and that calculator is
what the page's own DEC Fuel / INC Fuel / RST Fuel softkeys drive:

```
Load %: 3            Oil bar: 2.3         Fluids Coolant °C 81 Gearbox °C 82
RPM: 700             Oil °C: 87           Electrical Volts 28.0 Amps +19
Fuel Calculator Gallons Remain 0.0 Gallons Used 7.8 Endurance 0+00 Range NM 0
```

A row is up to **three** things — a left-hand toggle, a title, and the value that follows
the title inside the same container. Reading the toggle as the value put `Altitude: Off`
where the screen says the BARO transition alert is set to 18000 FT *and* is switched off:
two facts, and the wrong one won.

Every scrollable list — nearest airports, intersections, VORs, NDBs, the flight plan — is
built the same way (`.ui-control-list-content`), so **one generic selector serves all of
them** and a page nobody anticipated still reads as a list rather than a paragraph. Rows are
read FIELD BY FIELD: running them through the text joiner welds the first two together,
because the last digit of an identifier and the first of a bearing are both digits, so the
rule that keeps a clock from becoming `0 : 0 0` also turned `VCBI 020` into one token.

```
DER22, 242°, 0.6 NM
VCBI, 020°, 0.4 NM
```

⚠️ **Some pages leave the page title BLANK** — every NRST page does. A window that answers
"not shown" when the pilot has just navigated somewhere is reporting a fault it does not
have, so the page selector is the fallback, and it works while CLOSED: it keeps its active
tab and highlighted entry in the DOM long after it has faded out.

### The bezel: a measured split, not a preference

**The softkeys answer over SimConnect. The rest of the bezel does not.**

`1 (>H:AS1000_MFD_SOFTKEYS_11)` through the ordinary calculator path exits the checklist.
`1 (>H:AS1000_MFD_FMS_Lower_DEC)` down the same path changes nothing at all — and it is
**not** the MobiFlight duplicate-command trap, because the same write carrying a `901 0 *`
uniquifying prefix is equally inert. Fired in-page through the instrument's own
`onInteractionEvent` every one of them works.

So "read over Coherent, write over SimConnect" gains a documented exception: the softkeys
keep the SimConnect path, and the FMS knob, MENU, ENT, CLR, Direct-To, FPL, PROC, the range
knob and the map joystick go down the socket, because for those keys there is no other
road. It is the same shape of finding as the A380's KCCU keys, which reach its MFD only
when published on the display's own event bus.

The event names were read out of the instrument's **own event table** (`mfd.js`,
`FmsHEvent`), not guessed — so no key in the map is one the display silently discards.
There are 18 on the MFD and 13 on the PFD (which has no joystick). ⚠️ Note `AS1000_MFD_CLR`
carries **no** `_Push` suffix, unlike every other button in the family; the plausible
`AS1000_MFD_CLR_Push` is a silent no-op.

### The key map

The window is read with the arrow keys, Home, End, Page Up/Down and first-letter
type-ahead, so **none of those may be taken** — spending them would cost the pilot the
ability to move around the display in order to operate it. The bezel therefore sits on
Ctrl+arrows and the function keys.

| Key | What it does |
|---|---|
| Enter | press the selected softkey |
| **Shift+Enter** | FMS cursor (CRSR) |
| **Ctrl+Enter** | ENT — accepts the choice in an open list |
| Ctrl+Left / Ctrl+Right | **lower knob** — moves between fields with the cursor on; steps the page GROUP with it off |
| Ctrl+Up / Ctrl+Down | **upper knob** — CHANGES the field you are on (opens its list, cycles a letter); steps the PAGE with the cursor off |
| **Ctrl+G** | list every page in the G1000 and open the one you pick |
| **Ctrl+T** | type straight into the waypoint box under the cursor |
| Ctrl+D / Ctrl+F / Ctrl+P / Ctrl+E / Ctrl+L | Direct-To / Flight Plan / Procedures / Menu / Clear |
| Ctrl+PageUp / Ctrl+PageDown | map range out / in |
| Alt+arrows (PFD) | COM knob — up/down MHz, left/right kHz (over SimConnect; Alt+Enter moves the tuning box, over the socket) |
| Ctrl+Alt+arrows (PFD) | NAV knob, same shape |
| F5 / Escape | refresh / close |

⚠️ **This table has been wrong before.** It advertised F2, F3, F6, F7 and F8 after those
were removed, and called Ctrl+Enter the cursor after it became ENT — so the one place a
pilot goes to find out what the keys are was telling them the wrong answer. It is asserted
against `BezelKeys` nowhere; keep it in step by hand, and keep the window's own
`AccessibleDescription` in step with both.

There are **no function-key aliases**. Two ways to press one button is two things to learn
and two things to document, and the F-keys were never mnemonic. F5 survives as the
house-wide refresh key, which is not a bezel button.

### The FMS knob takes two turns, and that is left alone

**The first turn does not change the page.** It opens the page SELECTOR, showing where you
are; the next turn moves. That is how the real G1000 behaves, and it is deliberately not
smoothed over — a sighted pilot gets the same two-step, and quietly sending a second turn
would make the knob skip a page every time the selector had closed.

But it does mean that reading back the page TITLE after a turn reports the page the pilot is
still on, which sounds exactly like a key that did nothing. So while a window is up, what
gets spoken is **that window**:

```
at rest       FPL - Active Flight Plan
first turn    Page selector, FPL, Active Flight Plan
second turn   Page selector, NRST, Nearest Airports
page turn     Page selector, NRST, Nearest Intersections
```

The settle before reading back is 1200 ms, because the selector holds its choice for about
a second before committing; a shorter wait reads the OLD page and reports the knob as
having done nothing.

### The two windows a bezel key opens

Both are `.popout-dialog`s and both are caught by the **opacity** rule the PFD's panes
already use — no new visibility test was needed, which is the rule earning its keep.

- **Page selector** — the six groups with the current one marked, and the pages of the
  current group. The only way a blind pilot can see where the knob is about to take them,
  and genuinely transient: it closes itself a second or so after the last turn.
- **Page menu** — the MENU key's options for whatever page is up. An entry the page cannot
  offer right now is **classed disabled rather than removed**, and saying so is the point:
  a pilot who cannot see it greyed out would otherwise select it and get silence.

### The PFD's optional windows — five things that were being missed

Everything under **PFD Opt** is OFF by default, so a scrape taken at rest finds an empty
screen and concludes there is nothing there. That is exactly backwards: a pilot turns a
bearing pointer on *because they want to look at it*, and being able to press the softkey
and then not read the result is the worst of both worlds. All five are now read, and only
while visible:

| Window | Reads |
|---|---|
| Selected altitude | the preselect bug, always shown |
| Bearing pointer 1 / 2 | source, bearing, distance |
| DME | mode, source, frequency, distance |
| Wind | the mode's numbers, or "NO WIND DATA" |
| Minimums | the set minimum, once there is one |

⚠️ **Wind is itself a sub-menu**, not a toggle — pressing it replaces the row with
`Off / Option 1 / Option 2 / Option 3`, and a walk that keeps pressing the old slot numbers
is then pressing inside it. Verified live by walking every option of all four sub-menus.

DME and Wind are read FIELD-WISE for the same reason the nearest lists are: joined as text
they close up into `DME NAV1110.50 blank NM`, the source running into the frequency.

### The electronic checklist

The DA40's own AFM checklist, on the MFD — the page where "documented equals doable" is
most literally true, because it *is* the documentation. It is fully operable, and the
interaction is a three-step the softkey labels do not spell out:

```
CHECKLIST or GROUP softkey   arms the selector
FMS knob                     steps through the choices
ENT                          commits
```

⚠️ **The middle step is invisible in the DOM.** The DA40's plugin does not redraw the title
until ENT commits, so a pilot turning the knob hears nothing change until they press ENT.
That is the aircraft's own behaviour, not a scrape limitation — verified by watching the
title go from `TERMS AND CONDITIONS FOR USE` to `LEGEND` only on the ENT.

Three kinds of line, and they are not interchangeable — a note is not an action, and saying
so stops a condition being read as something to do:

```
Checklist group: NORMAL OPERATING PROCEDURES
Checklist: CHECK BEFORE ENGINE START
  Electric master ... ON (current)
  note: If External Power Unit will be used, but not yet connected:
  Check prop ... CLEAR
  Rudder pedals ... ADJUSTED
Go to Next Checklist?
```

The dotted leader that holds the action out to the right margin collapses to " ... " — read
literally, a screen reader says "dot" forty times.

### Waypoint entry fields

The control the pilot TYPES A WAYPOINT INTO — Direct-To, the flight plan, every WPT page —
so the one field on the MFD whose exact contents matter most. Read as text it comes out
`VCBI__KatunayakeBandaranaike Intl Colombo`: entry box, city and facility name with no
boundary between them. The ident lives in a scroller padded with underscores for the
characters not yet entered; those are placeholder, not content, so an ident of VCBI reads
`VCBI, Katunayake, Bandaranaike Intl Colombo`.

### Flight Controls — a panel that exists for one checklist item

`Flight controls . . . CHECKED` is in BEFORE TAKE OFF CHECK on the aeroplane's own
electronic checklist, and it means what it means on every light aeroplane: move the stick
and pedals through their full travel and confirm the surfaces follow, freely, in the right
direction. A sighted pilot does that by looking out at the ailerons. **There was no way to
do it at all** — nothing in MSFSBA reported where any control surface was.

So Center Console gains a READOUT-ONLY panel: elevator, ailerons, rudder, live on the
scan, with the direction named and a note when a surface is at its stop. There are no
controls on it, deliberately — the aeroplane is flown with a stick and pedals, and
offering buttons that drive the surfaces would be inventing a cockpit that does not exist.

⚠️ **Surface position, not input position.** The COWS model publishes `INPUT_ELEVATOR` and
`INPUT_AILERON`, which are where the pilot's *stick* is. This panel reads the stock
`ELEVATOR`/`AILERON`/`RUDDER POSITION` SimVars, which are where the *surfaces* are, because
that is the difference the check is FOR: a jammed or disconnected control moves the stick
and not the surface, so reading the input back would report the check as passing in exactly
the case it exists to catch.

The three are `Continuous` + `IsAnnounced` so they reach the batch cache, then silenced via
`SilentCachedReadouts` — a control check sweeps the stick stop to stop, and speaking every
position on the way would bury the reading the pilot is listening for. ⚠️ That set is keyed
by VARIABLE KEY, never SimVar name; the suite catches the mistake
(`NumericReadoutsStaySilent`, `EverySilentCachedReadoutActuallyExists`).

### Procedures — SIDs, STARs and approaches

The PROC key works and the whole chain reads. The menu names what is loaded and greys out
what cannot be selected yet:

```
Procedures:
  Activate Vector-to-Final, not available
  Select Approach, selected
  Select Arrival
  Select Departure
Loaded:
  Approach: blank  Arrival: blank  Departure: blank
```

and the loading page carries the whole procedure — including the ILS frequency it will tune
and the leg sequence with the final approach fix and missed approach point marked:

```
PROC - Approach Loading
  Airport: VCBI, Katunayake, Bandaranaike Intl Colombo
  Approach: ILS Y 04        Transition: VECTORS
  Primary frequency: 109.90
  Sequence:
    CI04
    FI04 faf, 39°, 2.8 NM
    RW04 map, 38°, 5.8 NM
    MANSEQ, 40°, 1.0 NM
```

⚠️ **A procedure's leg sequence is a list that is not built as one** — the legs sit in a
plain container rather than a `ui-control-list`, so the generic reader ran the whole
procedure together as `CI04 0.0 NM FI04 faf 39 2.8 NM RW04 map 38 5.8 NM`. `.proc-sequence-item`
is read per leg, field-wise. These are the legs the aeroplane is about to fly, and which one
is the FAF and which the MAP are the two facts on that page that matter most.

### Sweeping for what was still missed

The pilot cannot say what is on a screen they cannot see, so the method has to be the
reverse: enumerate every visible leaf on the display, subtract everything the agent already
reports, and group what is left by the region it sits in. Run with full parent-chain
opacity (an element inside a faded-out parent computes as opaque on its own), it named the
remaining gaps directly. Both displays are now down to labels and column headers.

Added on the PFD from that sweep:

| Row | Why it matters |
|---|---|
| Active waypoint IDENT | bearing and distance to an unnamed fix say how far without saying to what |
| Information bar | OAT, ISA deviation, TAS, ground speed — what a sighted pilot takes in at a glance |
| Time | the timer a pilot starts on a hold, and UTC for a position report |
| Altimeter setting | **STD BARO is a MODE, not a number** — no barometric readout elsewhere reports it |
| Speed bugs shown | which of Vne, Vg, Vy, Vx, Vr the tape is displaying, a choice the pilot made |

and on the MFD: the map ORIENTATION (north up, heading up, track up — it changes what every
bearing on the map means) and a page's own navigation prompt, which is the only place a
gesture like "press FPL to view the previous page" is written down.

⚠️ **The waypoint ident has no class of its own** — it is the plain `.dataField` beside the
two that are named `FixBrgValue` and `FixDistValue` — so it is found by elimination.

Some of these have SimVars MSFSBA answers elsewhere, and they are read here anyway. The
point of a display window is to say what the DISPLAY says; a pilot asking what the bottom
of the PFD shows should not have to assemble it from four other hotkeys.

### The standby altimeter read zero, and why

Reported from the cockpit: *"Altimeter 1001 hectopascals, 29.56 inches. Standby 0
hectopascals, 0.01 inches."* The standby subscale was set correctly the whole time.

TWO separate faults on one variable, and the aeroplane's own rule fixes both.

**The write was landing on a different variable.** The input is `L:KOHLSMAN SETTING HG:2`,
whose name carries a space AND a colon - normally a stock-SimVar shape, so `SetLVar`
refuses the calculator path for it and falls back to a native data-def write, which lands
on the STOCK SimVar of that name. Measured: writing the L:var through the calculator moved
it to 30.11 while `A:KOHLSMAN SETTING HG:2` stayed at 29.85. They are different variables,
and MSFSBA was writing the wrong one.

**The read asked for the wrong unit.** An L:var holds a RAW NUMBER, and the definition
asked for it in `inHg` - so SimConnect converted from its own base pressure unit and the
answer came back zero. Same trap as the A380's TCAS vertical-speed L:vars, which must be
`number` and never `feet per minute`.

WARNING: **the colon alone is not what broke the read** - `FADEC_ECUTEST_TIMER:1` and
`FADEC_ECUTEST_ACTIVE:1` are colon-indexed L:vars that read correctly through the same
path, and the ECU test's elapsed time has been right all along. The unit was the read bug;
the space-and-colon name is the WRITE bug. They are separate and both were present.

The fix is this aeroplane's own rule - **read the mirror, write the input**:

```
read   L:STATE_BARO2                 clean name, unit "number", measured 30.11
write  L:KOHLSMAN SETTING HG:2       through the calculator, uniquified
```

`STATE_BARO2` is the airframe's own read-only mirror of the same subscale, so it needs no
special case at all. The separate "Standby Subscale" row was removed with it: the setting
control now carries that value itself, and two rows for one number is the duplication these
panels exist not to have.

**Setting both altimeters is Ctrl+B**, and always was - it writes the G1000 subscale with
`KOHLSMAN_SET` and the standby with the above, then reads both back. There is no separate
control for the main altimeter because there does not need to be.

### Altimeters now announce when somebody else moves them

Both were silent on an external change - the G1000 one was in the silent-readout set
outright. On an aeroplane with TWO subscales that must agree, and where a wrong one is
worth hundreds of feet, that is the change most worth hearing.

It is **debounced**, not per-step: a subscale moves 0.01 inHg at a time and a knob sweeps
dozens of steps a second, so a change only ARMS a timer, every further change restarts it,
and the value is spoken once the knob has been still for 700 ms. What gets spoken is where
it ended up, which is the only number that was ever of interest. Both are read in one
utterance when both moved.

It defers to MSFSBA's own writes (Ctrl+B already confirms what it set) through a 3 s grace
window - deliberately longer than the settle, because one set writes both subscales and the
second change can arrive well after the first.

WARNING: **the Ctrl+M mute is checked inside the timer callback**, not left to the caller:
this speaks from a TIMER, and the generic monitor gate only wraps `ProcessSimVarUpdate`, so
a callback outside that wrap would keep talking after the pilot un-ticked the row. Same rule
the A32NX's deferred armed-altitude flush follows. The G1000 subscale is therefore no longer
excluded from the Monitor Manager - it announces now, so its row mutes something real.

### Alt+M opens the MFD

It did not, and the report was fair: a glass GA panel has a PFD and an MFD and no ND at all,
so borrowing the ND key (Alt+N) was the only thing available and never the obvious one.
Alt+M is now registered for it. Alt+N still works, because the docs have said so since the
window was built and a working key is not taken away.

### Typing a squawk: the repeated-keypress bug

Reported from the cockpit: typing 1-0-0-0 into the transponder took the first digit and
then nothing. It reproduces exactly, and the cause is this codebase's own documented trap.

**MobiFlight's command channel coalesces two consecutive byte-identical calc strings**, and
pressing the SAME softkey twice running is exactly that. Measured: four plain presses of
1-0-0-0 left the code at `0010` — the "1" landed, the first "0" landed, and the two repeat
"0" presses were silently dropped. The same four presses carrying a uniquifying prefix
commit `1000` and return to the transponder menu.

That is not an edge case on this display. A squawk of 1000 presses "0" three times running;
stepping the CDI past a navigation source means pressing CDI again. The softkey press now
goes through `ExecuteCalculatorCodeUnique`, which the invariant already required of every
valueless calc write — this call was the exception that proved it.

Two things worth knowing about the keypad itself, neither of them obvious:

- **The digit keys are offset by one.** Softkey 1 is "0", softkey 2 is "1", up to softkey 8
  for "7" — it is octal, so there is no 8 or 9. Softkey 10 is backspace.
- **The code shifts in from the right** and commits on the fourth digit, which also closes
  the keypad. A half-typed code sits right-aligned: after "1" and "0" the display reads
  `0010`, which looks like a code and is not one yet.

**A press is never silent now.** If the softkey row changed, the new row is spoken; if a
display row changed, that row is; and if nothing moved at all, the key's own label is read
back. Otherwise a key that did nothing is indistinguishable from a key that never
registered — which is the doubt that started this.

⚠️ **The changed-row diff keys on label AND occurrence.** Keyed on the label alone, the CAS
block broke it: every message reads "Caution: ...", so the map kept only the first, matched
the SECOND caution against it, and announced a standing caution after every keypress.

The transponder is read in words rather than the display's abbreviations — "code 1 0 0 0,
standby" — with the code spelt digit by digit, because a squawk is four characters and not
the number one thousand.

### Three controls reported as dead that were not

**CDI and OBS both work.** Measured: CDI steps LOC1, LOC2, GPS/TERM and round again; OBS
toggles the suspend flag. They read as dead because **the window said nothing when a key
cycles a value in place**. That silence was deliberate — re-reading twelve unchanged labels
over the pilot would be noise — and the reasoning was right while the conclusion was wrong.

When the labels do not change, the window now speaks **the first line that did**: the
navigation source for CDI and OBS, the units row for ALT Units, the barometric row for STD
Baro. In every case the thing the key was pressed to change, and never twelve labels the
pilot already knows. Rows are diffed BY LABEL rather than by position, because a press can
add or remove a row and a positional compare would then call everything after it changed.

**The wind Options 1, 2 and 3 work too**, and looked inert for a different reason. Off
hides the overlay; all three options show it — so the softkeys are doing their job. But
each mode has its OWN sub-block, all three stay hidden while the G1000 has no wind
solution, and the overlay draws its placeholder instead. With no wind there is nothing to
tell the three modes apart. The readout now says why rather than only "NO WIND DATA": the
G1000 computes wind in flight, so on the ground there is none to show.

### Flight plan constraints — what is and is not there

The altitudes ARE read, and on an approach they ARE the published constraints: the VCBI ILS
Z 04 renders BUSLI 2500, LAROD 1700, GOPRU 1500, LIKRA (FAF) 1500 — the procedure's own
step-downs, each on its own row.

⚠️ **What is NOT available is constraint-versus-manual.** There is no class, attribute or
marker distinguishing a published constraint from a hand-entered altitude: the NXi's own
`ConstraintSelector` only toggles visibility, the per-leg svg is identical on every leg, and
the only difference on screen is COLOUR — which here tracks the ACTIVE leg
(`.active-wpt > div` inherits magenta), not constraint status. Reporting a constraint flag
would be inventing one.

**There are no speed constraints to read at all.** The FPL page has three columns — DTK,
DIS, ALT — and no speed column anywhere. `.constraint-failed-box` does exist, for a
constraint the aeroplane cannot make, and is a genuine class-based signal worth wiring when
a case can be produced to test it against.

### The CAS window was reading the wrong copy

The worst bug found on this aeroplane, and it read as a clean scan rather than as an error.

**The PFD carries TWO `.cas-display` blocks of 32 rows each.** Only one is ever rendered —
the other is `display:none` with stale content — and the hidden one comes FIRST in document
order. `document.querySelector(".cas-display")` therefore returned the dead copy, every one
of its rows failed the visibility test, and `A.cas()` reported **"CAS messages: none" while
ECU A FAIL, ECU B FAIL and PITOT HT OFF were on the screen.**

On an aeroplane whose only channel for most failures IS the CAS window — there are four
annunciator lamps and nothing else — that is the worst thing this agent could get wrong,
and nothing about the output looked wrong.

⚠️ **The first match is not always the one on screen.** The G1000 keeps more than one copy
of several blocks in the DOM, full-width and half-width, for its split layouts. Anything
that can plausibly be duplicated now goes through `firstVisible(sel)`, which scans all
matches and returns the first VISIBLE one: the CAS block, the FMA, the navigation source,
the softkey row, the engine strip and the page title. `A.cas()` goes further and merges
EVERY visible copy, de-duplicating by message text, so a layout that really does show two
blocks reports each caution once.

**This is very likely the root cause of the background CAS auto-announce never working.**
The always-on monitor reads through the same `A.cas()`, so it was watching the dead copy
and had never seen a single message — which is indistinguishable from "nothing has
happened" and is exactly why that fault survived so long.

Found by re-dumping both displays after a reconnect and diffing what is ON the screen
against what the agent REPORTS, rather than by reading the agent's output and finding it
plausible.

### The active flight plan

The most important page on the aeroplane for an IFR flight, and the one the generic
readers were worst at: it is a **list of lists**, and read as one it came out as a single
300-character line carrying an entire approach. No leg could be arrowed to, and the active
waypoint was invisible.

The shape is SEGMENTS — Origin, Enroute, whatever procedure is loaded, Destination — each
with its own nested list of legs. Which leg is ACTIVE is the single most useful fact on the

  VTF - VCBI - ILS Z 04:
    BUSLI, 239°, 9.5 NM, 2500 FT (active)

    LIKRA faf, 040°, 1.5 NM, 1500 FT

⚠️ **Placeholder legs are CLASSED `hide-element` rather than removed** — the third time this

This was caught only by **re-dumping both displays after a reconnect**, with an approach

### SimBrief and the EFB

**The DA40 has no EFB.** There is no tablet in the aeroplane and nothing in the package
that resembles one — it is a 2004 light single, and the G1000 is the whole avionics suite.
Nothing needs building for it.

Flight planning therefore runs through MSFSBA's own **Electronic Flight Bag (Shift+E)**,
which is aircraft-independent and already builds departures, SIDs, STARs, arrivals and
approaches out of the navigation database, plus **SimBrief import**. The SimBrief username
lives in MSFSBA's Settings and is global — neither the EFB nor the SimBrief panel is gated
on aircraft type, so both have worked on the DA40 since the day it was added.

The aircraft's own Navigraph plugin (the "Link Navigraph Account" pages in the WPT and Aux
groups) is a separate thing again: it puts Navigraph CHARTS on the MFD, behind a device
login. Its pages read — the code to enter at navigraph.com is scraped like any other page —
but linking an account is the pilot's to do, not MSFSBA's.

## Reading the G1000 from the instrument, not from its stylesheet

Everything above this point reads the G1000 by looking at its **markup**. That is right for
gauges and text, and it was wrong about the **cursor** five separate times. Each fix was
"learn one more class name" — `cyan`, then `hidden-element` beside `hide-element`, then
`highlight-active` beside `highlight-select`, then `input-component-value`, then
`number-input-active` — and each next page used a different one. A cursor is not a colour.
It is part of the instrument's **state**, and the markup is only where that state happens
to get painted.

The G1000 is a JavaScript instrument. `wtg1000-mfd` **is** the instrument object, and it
carries a `viewService` that owns every page and dialog. Each of those owns a scroll
controller that already knows the answers:

| Question | The instrument's own answer |
|---|---|
| Is the cursor on? | `scrollController.getIsScrollEnabled()` |
| Which field is it on? | `scrollController.getFocusedUiControl()` |
| Is that field open for editing? | `scrollController.getActivatedUiControl()` |
| What are the field's choices? | `control.props.data` |
| Which page/dialog is up? | `viewService.activeViewKey` |
| What pages exist at all? | the page selector's own `pageGroups` table |

So the reader asks the aeroplane instead of guessing from CSS, and the whole class of
"page reads as dead" bugs goes with it.

### The interaction model, read out of the aircraft's own source

These are not conventions inferred from behaviour. Every rule below was read off the live
instrument with `Function.prototype.toString` and then confirmed one keystroke at a time
against the real display:

```
UPPER_PUSH .................. toggles the cursor
cursor OFF + any knob ....... opens the PAGE SELECTOR
                              (upper turns the page, lower turns the page GROUP)
cursor ON,  LOWER ........... moves BETWEEN fields
cursor ON,  UPPER ........... acts ON the focused field — opens its list of choices,
                              or cycles the character of a text box
inside a list, LOWER ........ moves the highlight; ENT accepts, CLR cancels
in a text field, UPPER ...... cycles the character, LOWER moves along the box
```

`UiControlGroup.processHEvent` is the whole rule in one function: a control that is
**activated** gets every event; a control that is merely **focused** gets everything except
the lower knob; and whatever is left over scrolls the cursor.

Two consequences a pilot had already noticed and could not explain:

- **The first turn of the upper knob on a text box changes nothing.** It ACTIVATES the box;
  the turn after that starts cycling letters. `InputComponent.onUpperKnobInc` says so
  explicitly. That is the aeroplane, not a dropped keystroke.
- **Pressing the FMS knob on a setup field does not open its list.** `UPPER_PUSH` is not in
  `UiControl.onInteractionEvent` at all, so it falls through to the page and toggles the
  cursor. **Turning** the upper knob is what opens the list.

### Two control frameworks, and why the flight plan page "would not arm"

The setup pages, the dialogs and Direct-To use the older framework: a `scrollController`
with a flat `controls` array. The **flight plan page, the checklist and every list** use
`G1000UiControl`, which keeps its children in `registeredControls` and remembers focus in
`focusedIndex`.

The flight plan page's `scrollController` is therefore **empty** — all of its controls live
in the other framework. A reader that counted controls saw zero and reported the page as
having nothing on it, which is exactly the "it doesn't even arm" that was reported from the
cockpit. It arms perfectly; `MFDFPLPage.setScrollEnabled` focuses the other framework's
root.

Both frameworks are walked now. The cursor flag stays on the scroll controller for both,
which is why that — and never the control count — is what gets asked.

### The field list: scanning a page instead of groping through it

Every page now reports its **editable fields with their values**, and which one the cursor
is on, straight from the instrument's controls:

```
Fields (14), cursor on:
  Time Format: UTC
  Time Offset: +00:00 (not available)
  NAV Angle: Magnetic(°)
  DIS, SPD: Nautical(NM,KT)
  ALT, VS: Feet(FT,FPM)
  Temperature: Celsius(°C)
  Weight: Pounds(LB)   <-- cursor
  Field 1: GS
  ...
  Minimum Length: 3000FT
```

Before this, the only way to learn what an Aux setup page held was to turn the knob onto
every field in turn and listen — so a pilot could not answer "what are my units set to"
without disturbing them. This is the **scan over announcements** rule applied to the
displays.

A field the aeroplane has **greyed out** is still listed, marked `(not available)`. Time
Offset is unavailable precisely because Time Format is UTC; dropping it silently would be
deciding on the pilot's behalf what they are allowed to know.

Three field shapes had to be handled before the list was honest:

- A **number field** is a group wrapping a digit input from the *other* framework, so its
  inner controller is empty and it was being dropped entirely. Time Offset and Minimum
  Length were both missing from a list that claimed to be complete.
- A number field **renders itself twice** — once resting, once for the digit editor, both
  left in the DOM — so taking off only the visible copy left the other welded to the label:
  `Minimum Length03000FT`. Both come off now.
- A **label is a name**. Walking up the DOM for the label ran past the row into the whole
  panel on the PFD backlight window and answered `Auto100.00%Auto100.00: PFD Display` —
  four neighbouring values welded into a name. A candidate with a percent sign or a run of
  digits is rejected.

### Ctrl+G — the page list

Reaching a page by knob means holding the cursor off, turning the small knob through five
groups, then the large knob through up to nine pages, and waiting for a timer that closes
the selector if you pause. Counted by ear, with no way to see where you are, that is how
the Aux group came to be reported as unreachable.

**Ctrl+G lists the whole tree and opens the one you pick.** It is not a shortcut past the
aeroplane: it makes the identical `viewService.open` call the page selector makes when its
own timer fires. The knob still works, unchanged. Stubs are listed and say what they are.

On the **PFD** the same key lists its **windows**, because the PFD has no pages at all —
`openPageKey` there is permanently empty. Several of those windows have no bezel button and
live behind softkeys a pilot has to find first: the timer and references, ADF/DME tuning,
the nearest-airport list, the alert list, and PFD setup and backlighting. All fifteen are
now one keystroke away. (A PFD window is a **subview** and an MFD page is not; opening one
the other way leaves it registered but never shown.)

### Ctrl+T — typing an ident, and the autocomplete

**The G1000's own text boxes take keyboard entry.** That is what the small keyboard icon
beside them is for: the input component carries `activateKeyboardInput` and `setValueFromOS`
for exactly that. Ctrl+T drives the same `setText` the icon does, so the aircraft's database
search, its autocomplete and its facility lookup all run exactly as they do for a sighted
pilot. Nothing here reimplements any of them.

Autocomplete works and is now **heard**. Typing `VCR` completes to `VCRAD`; typing `VCRI`
comes back as **`VCRI, Mattala Rajapaksa Intl, Mattala`**. Turning the knob one letter at a
time announces the facility the moment the aeroplane knows it, which is what a sighted pilot
sees appear.

The read-back is **delayed on purpose**. The aeroplane debounces its own database search, so
asking straight away returns the *previous* waypoint's name — which is exactly how `VCRI`
first read back as Bandaranaike. 900 ms, measured.

The knob route is untouched and still spells an ident character by character:

```
Waypoint: VCRI__, editing, character 4, I
Waypoint: VCRI__, editing, character 5, blank
Waypoint: VCRIA_, editing, character 5, A
```

Twenty-eight knob clicks for a four-letter ident is not "the same aircraft at the same
depth"; it is the same aircraft made unusable. Both roads end in the same input component.

### The interaction surface, enumerated — so gaps stop being found by accident

⚠️ **Every gap in this project has been found by somebody stumbling over it.** The TO/GA
button, the Hobbs meter, the barometric knob, the aeroplane's own Tips page — each one
noticed in the air by the person flying, which does not scale and is not fair on them.

**The aeroplane declares its own interaction surface.** Every clickable thing in the cockpit
is a `<Component ID="...">` in the model's interaction XML, and there are **sixty-one** of
them across the two variants. That list is finite, it is in the package, and it changes only
when COWS ship an update — so it can be enumerated and compared.

`CowsDA40InteractionSurfaceTests` holds a table naming, for all sixty-one, either the MSFSBA
control that covers it or the reason it is deliberately not exposed. Three tests keep it
honest:

- a component the aircraft declares and the table does not name **fails** — that is a control
  a sighted pilot can touch and a blind one cannot, and a future COWS update adding one shows
  up here instead of in the air;
- a table entry naming a component the aircraft no longer has **fails** — a comment that has
  quietly become fiction;
- a deliberate omission with no reason written down **fails** — the next person cannot tell a
  decision from an oversight.

It skips itself when the package is not installed, because a test that fails for being on the
wrong computer teaches people to ignore failures.

Walking all sixty-one was the sweep. It came out clean: the only components not exposed are
the two display **brightness** knobs (no operational effect for a pilot who cannot see the
screen — and the reversion switch beside them IS exposed), the cabin-light **shortcut**
clickspot on the airspeed needle (the three cabin lights have their own switches), the
glareshield **emissive** material (how it looks lit, not a control). The four **XLS**
levers and the selector are covered by the XLS's own panels (below).

### The XLS, stated plainly

⚠️ **This section used to say six XLS panels were "declared and empty". They are all built** —
Engine Start, Power and Levers, Fuel System, Mixture and Propeller, Magnetos, Priming — and
`CowsDA40PanelStructureTests.NotBuiltYetOnXls` is now an EMPTY list that the test checks in both
directions, so a panel added without content goes back on it with its reason.

**374 L:vars exist on the XLS and on no NG file**, because the two aeroplanes do not share an
engine: a FADEC-governed Austro diesel with one lever against a Lycoming IO-360 with three, a
magneto key and a left/right tank selector. No NG code was reusable for any of the six.

What is there is a great deal more than three levers. The XLS models per-cylinder combustion
(`ENG_COMP_*`: crank angle, stroke, compression, ignition, magneto, pressure), per-cylinder head
temperature with its own airflow model, EGT with cylinder spread and lean-assist peak/delta/hottest,
priming tracked in **grams per cylinder** against a required quantity, **spark plug fouling**
(`DAMAGE_MAG_FOUL`, per PLUG — eight of them), **vapour lock in the fuel line**
(`ENG_FUEL_LINE_BOIL`) and the **"red box"** — the mixture-and-power region that damages the engine
while you sit in it, recomputed from its inputs because `DAMAGE_REDBOX_ITS:n` holds its last value
once the box closes. ⚠️ **Detonation is NOT modelled in this build** — the block that computes it
sits inside a comment and nothing consumes its output, so there is no call-out and must not be one.

## Wear and tear, read out of the model rather than guessed at

The store page says "engine damage, state saving, and 130+ random failures" and leaves it there.
Reading `COWS_DA40NG_Failures.xml` and `COWS_DA40NG_Logic.xml` says what that actually means, and
it changed what MSFSBA reports.

**Damage is a counter, health is what the engine does with it.** Each damaged system carries a
`DAMAGE_*` counter that climbs by 0.1 a tick whenever the engine is turning above 400 RPM and
something is wrong, capped at 100. `HEALTH_*` is computed from it every frame, and THAT is what
the engine's own physics multiply through:

| Health | Feeds | So a damaged one... |
|---|---|---|
| `HEALTH_BLOCK` | `FADEC_SET_MAP`, and DIVIDES into `WC_FRICTION` and `WC_HEAT_FUEL_OIL` | makes less power, and runs hotter and stiffer as it gets worse |
| `HEALTH_OIL` | `OP_OIL_PRESS_IN` | makes less oil pressure |
| `HEALTH_FUEL:11`, `:12` | `FUEL_PRESS` via pump circuits 42 and 43 | makes less fuel pressure |
| `HEALTH_FUEL:1` | gates combustion below 0.01 | stops the engine outright |

⚠️ **THE BLOCK IS NOT ON THE SAME SCALE AS THE REST, AND MSFSBA READ IT AS IF IT WERE.** The
formulas are `1 - DAMAGE_BLOCK/800` for the block against `(100 - DAMAGE)/100` for everything
else, so a completely destroyed block publishes **0.875** where a destroyed oil system publishes
0.0. Announced raw that is worse than saying nothing: a pilot hearing *"engine block 88 percent"*
would think it barely marked when the model cannot damage it any further, and the 5-point
announcement step meant nothing was said until 40 of its 100 damage points were on the clock. It
is rescaled now, in both the call-out and the panel row, so one number means one thing.

⚠️ **`HEALTH_FUEL:11` and `:12` are the two FUEL PUMPS.** The old note in the code said the
package never explains them and that guessing at a label was worse than omitting them. The
package does explain them, one line down in the fuel-pressure calculation — they multiply
circuits 42 and 43, whose switches are already on the Fuel panel. They damage independently of
each other and of the fuel system, and a degraded pump is a low-pressure fault a pilot diagnoses.
Both are exposed.

**Three more things the logic says that nothing in the aeroplane tells a pilot:**

⚠️ **Past 90, damage is self-sustaining.** The accumulation condition is
`FAILURES_x OR DAMAGE_x >= 90` — so beyond ninety points a system keeps damaging itself with the
original failure long gone. There is no way back except Reset.

⚠️ **An overheating block is damaged directly, with no failure involved at all**:
`WC_TEMP_BLOCK >= 140` adds `(temp - 140)/60` per tick. Running it hot IS the damage.

⚠️ **Oil damage ignores the damage-modelling switch.** Every other accumulator is gated on
`DAMAGE_ENABLED`; the oil block is `FAILURES_OIL AND RPM >= 400` with no such gate. Whether that
is deliberate or a vendor slip, it is the behaviour: an oil failure marks the engine even with
damage modelling turned off.

**Repair is one control and it is already exposed.** `L:RESET_DAMAGE` clears the failure flags
and every damage counter, cools an overheated engine back to 70, and un-fails it — MSFSBA's
"Clear Engine Damage" button. It is the engine rebuild; there is no partial repair and no
maintenance state between the two.

### ⚠️ The audit's own worst finding was about the audit

The table above once said "Report passing WAYPOINT" could be answered on demand with Ctrl+W,
and that only the automatic call was missing. **Ctrl+W did nothing at all on this aeroplane.**

It maps to `HotkeyAction.ReadNDWaypoint`, which the DA40's `HandleHotkeyAction` never had a
case for, and the shared service behind it reads `A32NX_EFIS_L_TO_WPT_*` - FlyByWire variables
that do not exist on a Diamond. The gap was BOTH halves. A key that had never worked was
written down as working, and the lesson generalises past this aeroplane: a hotkey ACTION
existing app-wide says nothing about whether a given aircraft handles it. Read the definition's
own `case HotkeyAction.` list.

### Both halves, from the aeroplane's own navigator

Nothing had to be inferred. The Working Title G1000 carries a `GpsSynchronizer` that writes the
stock GPS SimVars from its active flight plan, and reading its source out of the running
instrument settles what each one means:

- `GPS WP NEXT ID` - the **active lateral leg's** name: the fix being flown to.
- `GPS WP PREV ID` - the leg **before** it. So once the plan sequences, this IS the waypoint
  just passed. The aeroplane answers the question; this app does not have to guess at it.
- `GPS WP DISTANCE`, `GPS WP BEARING`, `GPS WP ETE` - how far, which way, how long.

Two traps came out of the same read, both of which would have shipped as bugs:

⚠️ `GPS WP BEARING` is written in **radians**. The definition asks for degrees and lets
SimConnect convert.

⚠️ `GPS FLIGHT PLAN WP COUNT`'s write is **commented out** in the shipping build. It reads 0
with a plan loaded, so anything trusting it concludes there is no flight plan. It is
deliberately not in the struct.

### A passing is a structural test, never "the ident changed"

The fix we were flying **to** must have become the fix we are flying **from**. Nothing else
satisfies that, and the alternatives all matter: a Direct-To, a plan edit, a procedure load and
the first activation of a plan every one change the TO-waypoint, and none of them is a passing.
An "it changed" rule would announce one for all four - and a pilot acting on it would report
passing a fix they had merely re-routed to, which is worse than the silence it replaced.
The first frame after connecting is a **baseline** for the same reason every other monitor here
takes one: a passing that happened before MSFSBA was watching is not news.

The call is one sentence carrying both halves of a position report - *"Passing SOXOM. Next
VEKIN, 14 miles."* - because asking for the second half on a separate keypress wastes the moment
the report has to be made in. It interrupts rather than queues, for the same reason the settled
altimeter value does: a passing spoken behind a queue of scan chatter is a passing reported late.
Idents are spelt letter by letter, the way a pilot reads one back; a generated leg name
("HDG 071") is prose and stays prose. `Waypoint Passing Call` in Ctrl+M silences it, and Ctrl+W
keeps working when it is off.

⚠️ **MSFSBA announces the passing. It does not make the call, and it must not.** What to report,
and whether to report at all, is flying - it is the pilot's judgement and their radio. What was
missing was never the call; it was the cue the call is made from.

⚠️ Two rows are marked **not flown end to end**: altitude constraints and the radial
intercept. The fields are reachable and readable - that is measured - but a constraint typed
into an empty flight plan proves nothing, and both deserve a flight before anybody is told
they work.

## Icing, on an aeroplane not approved for it

**Airframe ice already announces**, and always did - the generic accretion tracker watches
`STRUCTURAL ICE PCT` for every aircraft and says "icing conditions" on the rising edge and
"cleared" on the falling one. Nothing DA40-specific was needed.

⚠️ **What did NOT announce is the one that is specific to this aeroplane: the induction
filter blocking with ice.** That is the entire reason the alternate air control exists, and a
blind pilot had the control with no way to know they needed it.

The model's own condition, read out of its logic rather than guessed:

```
ice accreting  AND  relative wind >= 60 kt  AND  precipitation > 5 mm/h
AND ALTERNATE AIR CLOSED     ->  FILTER_RESRTICTION builds, capped at 100
```

and it clears only once the outside air is at or above zero and the ice melts off. So it is
not a failure to be reset - it is the consequence of flying in precipitation near freezing
with the filter unprotected, and the fix is to **open alternate air before it happens**.

It is a readout on the Ice and Pitot panel now, beside the control it explains, and its onset
is announced on the same graded rule as the coolant leak: once when it starts, again if it
gets materially worse, never the value.

⚠️ `FILTER_RESRTICTION` is spelt that way in the aeroplane. It is their variable and their
typo, and correcting it here would simply read nothing.


### Three faults in one dump, and one of them was mine

**The page selector read as a run-on blob.** `A.M.dialogText()` answered for any view with no
controls, no compiled map and short text - and the page selector is exactly that *while it is
fading out*: its list has already gone, so `A.M.list()` returns null, the view key is still
`PageSelect`, and the whole selector came back as one string. It is a **whitelist** now:
`Auth` is the only view on this instrument whose content IS its text, so it is named rather
than inferred. Guessing which views qualify is what broke it.

⚠️ **The Navigraph sign-in was stuck open, and I left it there.** Probing the Sign In button
during an earlier session started a device-code flow, and that view re-asserts itself as the
open PAGE and refreshes its code every few seconds - so it kept appearing in the middle of
ordinary navigation. Cancelled with the view's own `cancelSource.cancel()`.

⚠️ Note for getting out of a stuck view: the usual `while (viewKey != pageKey)
closeActiveView()` loop **cannot** help when the stuck view IS the page, which `Auth` is.
`A.goPage("NavMapPage")` is the way out.

### A door is open or closed, and closing it silently failed

⚠️ **`ExecuteCalculatorCode`, not `Unique`.** Opening a door and then closing it sends the
same calculator string twice running - `3 (>K:TOGGLE_AIRCRAFT_EXIT)` both times - and
MobiFlight coalesces byte-identical consecutive commands, so the **close was dropped and the
door stayed open**. Doing a different door in between made it work, because that broke the
identical pair, which is exactly the shape the cockpit report described.

Measured live, both ways:

```
3 (>K:TOGGLE_AIRCRAFT_EXIT)          EXIT OPEN:2  0 -> 100
3 (>K:TOGGLE_AIRCRAFT_EXIT)  again   EXIT OPEN:2  100, unchanged   <- dropped
901 0 * 3 (>K:TOGGLE_AIRCRAFT_EXIT)  EXIT OPEN:2  100 -> 0
```

This codebase's own invariant already said every valueless calc write goes through the unique
form. This call was the exception that proved it, again - the same trap as the squawk keypad,
the softkeys and the wiper switch.

**And the percentage is gone.** `EXIT OPEN` sweeps as the canopy swings, so a pilot who opened
it heard *"Front Canopy: 15.0"*, *"Front Canopy: 65.4"* and then a state - three announcements
for one action, two of them meaningless. A door now speaks the state it comes to REST in,
once, on the same settle the barometric subscales and the radios use. The percentage stays in
the panel scan for anyone who wants to know a door is halfway.

⚠️ Off the stop is **open** - which is what the aeroplane's own DOOR OPEN warning means, and
what matters to a pilot about to take off.

### The class of gap that refuelling belonged to

Refuelling was not missed by carelessness - it was missed because **the interaction-surface
audit cannot see it.** That audit enumerates every `<Component ID>` in the cockpit, and
refuelling is not in the cockpit; the filler caps are on the wings. It is a thing a pilot
DOES, not a thing they touch.

So the same sweep was run again along a different axis: not "what can be clicked" but "what
does a pilot do to this aeroplane", and "what does the model track that has no control at
all". Two searches, both against the package rather than from memory.

**Ground equipment: nothing missing, because none is modelled.** Searching the whole package
for chocks, tie-downs, covers, tow bars, ground power, pre-heaters, oil dipsticks and water
servicing returns nothing. The only covers in the aeroplane are the engine-master and
emergency-battery guards, and both are already controls. That gap class is genuinely empty
here - worth knowing, and worth re-running on the next aeroplane, where it will not be.

**Engine health: an entire model with nothing exposed.** That one was real.

### How damaged is the engine? Nothing could say

⚠️ **This aeroplane accumulates engine damage and it survives a reload.** The COWS damage
model tracks the block, the oil system, the turbocharger and the fuel system separately -
`DAMAGE_BLOCK`, `DAMAGE_OIL`, `DAMAGE_TURBO` with its own friction and heat terms,
`DAMAGE_FUEL` with cut and oscillation terms, plus dust ingestion and overstress - and
publishes the result as `HEALTH_*` fractions from 1.0 down.

MSFSBA exposed the **switch** that turns damage modelling on and the **button** that resets
it, and nothing whatsoever about the state in between. So a pilot could mishandle the engine,
land, reload, and take off again in a damaged aeroplane with no way to find out — which is
exactly the trap the state-saving system already sprang on this project with flat batteries.

Three readings now, as percentages because the model works in fractions and a pilot does not:

```
Engine Block Health   100 percent
Oil System Health     100 percent
Fuel System Health    100 percent
```

⚠️ **A FALL is announced**, not the value. Damage happens *during* something - a cold power
application, an overspeed, running the oil hot - and the moment it starts is the moment a
pilot can still do something about it; waiting for them to open a panel is waiting for the
flight to be over. Only downwards, and only by five points or more: health climbing back means
they pressed Reset, and Reset confirms itself.

`HEALTH_FUEL` carries three indices - 1, 11 and 12 - and only `:1` is exposed. What the other
two track is not written down anywhere in the package, and inventing a label for a number a
pilot might act on is worse than leaving it out.

### Refuelling, which MSFSBA could not do at all

⚠️ **The Fuel System panel had everything for MANAGING fuel and nothing for HAVING any** -
the valve, the safety wire, the pumps, the transfer pump - so a blind pilot could not put a
drop in the aeroplane. It is the most basic thing there is, and it was missing because nobody
had said it out loud.

There is no fuel panel in the cockpit to reproduce: the filler caps are on the wings. So the
honest model is the **transaction**, which is what a GA pilot actually does - tell the pump
how many gallons you want in each wing, or say fill it up:

| Control | |
|---|---|
| **Main Tank Fuel** | 0 to 19.5 gallons |
| **Auxiliary Tank Fuel** | 0 to 19.5 gallons |
| **Fill Both Tanks** | 19.5 each, 39 total |

Typed in gallons, because that is the unit the tank is measured in and the number the AFM
quotes - but **read back in whatever the G1000 is set to**, so a pilot working in litres hears
litres.

⚠️ **Ground only, engine off, and REFUSED otherwise.** You do not fuel a running aeroplane.
This is the second control here that refuses rather than reports (the ECU reset hold is the
other), for the same reason: fuelling while running is not a degraded version of what the
pilot asked for, it is something nobody does.

⚠️ And it reads `SIM_ON_GROUND` rather than `DA40_ECU_PRE_ON_GROUND`, which carries the same
SimVar. The ECU one is OnRequest - never polled - so the cache has nothing for it and the
fallback would have let a pilot refuel in the cruise. Only one of the two may be batched
anyway, because the batch sorts by SimVar name.

The two typed fields are write-only and deliberately do not announce: what the tank actually
HOLDS is `DA40_FUEL_MAIN_ACTUAL` and `DA40_FUEL_AUX_ACTUAL`, which are Continuous and
announced - so a tank filling from GSX, or draining through a leak, still speaks. Announcing
the request as well would say the same number twice.

### GSX and this aeroplane

**COWS built it to cooperate.** The model sets `L:GSX_PARK` when the aeroplane is genuinely
parked - on the ground, parking brake set, ground speed at or below 1 knot, and both brake
pedals at 25 percent or more - which is the aircraft telling GSX it is chocked and ready for
services. That is a deliberate piece of GSX support in the aircraft, not an accident.

**MSFSBA's side is already there and is not aircraft-specific**: the accessible GSX menu
(Alt+G) drives GSX's own menu, and the refuelling service is tracked in detail - MSFSBA reads
GSX's crew prose ("Operator walking to pump", "Fuel Truck is in position") as well as its
figures, after an hour of a blind pilot's ground time was lost to those lines being swallowed.

⚠️ **What I cannot tell you from here is which services GSX will OFFER for a DA40.** There is
no aircraft profile for it in `%APPDATA%\Virtuali\Airplanes` - only nine customised profiles
live there, all airliners - so GSX falls back to what it derives from the aircraft.cfg, and
which services a light single gets is GSX's decision, not MSFSBA's. That is a question to
answer with GSX running rather than by reading code, and it is worth answering: if GSX does
refuel the DA40, that is the most realistic road of all and the panel above is the fallback.

### Six states that should have been interrupting the pilot

The rule on this aeroplane is that switches announce and numbers do not, and it is a good
rule - but it left a class of **described states** silent that no sighted pilot would have to
go looking for. Found by listing every variable that has value descriptions and never
announces (forty of them), then asking one at a time whether somebody in the left seat would
notice it without trying:

| Now announces | Why it is not noise |
|---|---|
| **Engine running / stopped** | the emergency, and nothing else said it |
| **ECU A / B fault LATCHED** | the difference between "try the voter switch" and "land as soon as practical" - and the CAS only ever says ECU FAIL |
| **ECU test result A / B** | the whole reason for running the test |
| **Transfer pump running** | it stops itself above ~14 gallons, and the aeroplane's own Tips page tells the pilot to set a timer because of it |

The other thirty-four stay silent on purpose: they are mirrors of switches that already speak
(the light `_STATE` variables, the pitot and alternate-air states), things the pilot has just
commanded (the trim interrupt, the safety wire), or continuous during normal flight (the
autopilot's own trimming).

⚠️ **A trim runaway is deliberately absent from that list and is already covered.**
`DA40_TRIM_RUNAWAY` shares its SimVar with `DA40_FAIL_AFCS_TRIM_RUN`, which is already batched
and announced - so it speaks. Promoting the second copy would have put two keys with one
SimVar name into a batch that sorts by name and corrupted every later variable's slot. That is
the trap `NoTwoBatchedVariablesShareOneSimVarName` exists for, and it was sprung and caught
while writing this list rather than in the air.

### The GFC 700's pre-flight test, which nothing could see

⚠️ On a real GFC 700 the PFT is what says whether the autopilot may be **relied on at all**.
The PFD annunciates it while it runs, and a pilot who takes off without seeing it pass has an
autopilot of unknown health. MSFSBA could not see any of it.

The state machine is the model's own, read out of its logic rather than guessed:

```
AFCS_TEST   0 idle, 1 running (10 s), 2 complete, -1 the AFCS itself failed
AFCS_PFT    0 not started, 1 running, 2 passed, 3 passed and latched,
            -1 failed, -2 failed and latched
```

⚠️ **Pressing the disconnect DURING the test fails it.** The model is explicit: while
`AFCS_PFT` is 1, `INPUT_AP_DISC` — or an elevator, aileron or trim servo failure reaching 2 —
drives it straight to −1. It wants five seconds undisturbed. That is the opposite of what the
disconnect does at every other moment, which is exactly why it is worth saying out loud, and
it is what the readout says: *"running - do not touch the disconnect"*.

All three are announced, so a failed test speaks rather than waiting to be looked up. They are
the **first read-only state the GFC 700 panel has ever had** — every other item on it is a
control, which is why that panel deliberately carried no Status Display until now.

### Take-off trim: there is no number, and that is the answer

The DA40's trim wheel carries a **T/O mark** — a physical band moulded into the wheel — and
⚠️ **the AFM gives no numeric value for it.** There is nothing to calculate: no load-and-CG
table, no take-off trim setting to look up. The checklist item is "Trim … T/O position" and a
sighted pilot matches the wheel to the mark.

MSFSBA already says everything there is to say. The trim reads as `centred` or
`2.30 degrees nose up`, and there is a **Centre of travel** control to put it back. It is
NOT the take-off mark: the AFM gives no number for that, which is why there is nothing to
compute. The video's pilot sets neutral for every take-off
and calls it "roughly at the takeoff position", which is the same thing.

**The autopilot does not trim for take-off, and cannot.** The GFC 700's pitch servo trims only
while the autopilot is engaged, and the autopilot may not be engaged below the AFM's minimum
engagement height — so on this aeroplane take-off trim is hand-set, every time, by matching a
mark.

### The aeroplane's own checklist, read out of its package

Every MSFS aircraft may ship a native checklist - plain XML under
`SimObjects/Airplanes/<model>/Checklist/` - and the DA40's carries its two dozen procedures
**and** the Tips and help page with the vendor's own operating knowledge. MSFSBA now reads it
instead of a hand-written file.

⚠️ **It also fixes a quieter fault: the checklist window was showing an AIRBUS checklist.**
`ChecklistForm` reads a bundled text file per aircraft and fell back to the A320's for
anything it had no entry for - which was the DA40. A wrong checklist that looks authoritative
is worse than an empty window, so an aeroplane with neither a native checklist nor a bundled
one now says so plainly instead of borrowing somebody else's.

The mapping is Asobo's shape, not ours: a `Page` becomes a category, a `Checkpoint` becomes
"Subject … Expectation", and a `Clue` becomes its own line underneath - because a clue is
frequently the only place a real operating detail is written down ("Forwards = go, Backwards =
stop" for the parking brake). Two traps, both real in this file: Asobo puts the literal word
**"Clue"** in the expectation column of a note row, which would render as "Warmup … Clue"; and
two pages can share a name across steps, which the category dictionary downstream would
silently swallow.

Nothing to transcribe, and it follows the aircraft through updates.

### The G1000 timer, which was already reachable

Ctrl+G on the PFD, **Timer and References**. It carries five fields, and with the field
labelling below they now read:

```
Timer, 0:00:00      Timer, Up      Timer, Start?      Timer, Off      Timer, FT: _ _ _ _ _
```

Shift+Enter for the cursor, Ctrl+left/right to `Start?`, **Ctrl+Enter** - verified live, the
button became `Stop?` and then `Reset?`. Nothing new had to be built; it needed the window to
say what its fields were.

⚠️ **That window is also where the G1000 keeps the V-speeds** - VNE 172, Vg 88, Vy 90, Vx 72,
Vr 67 - which is the aeroplane's own copy of what `DA40Speeds` holds. Two sources, and they
agree, which is how the figures in `DA40Speeds` were confirmed in the first place.

### A field's label when the page has no group boxes

The setup pages and dialogs name their sections with `groupbox` + `groupbox-title`, which is
exact. ⚠️ **The PFD's own windows do not** - the timer names its rows `timerref-timer-title`,
`timerref-mins-title` - so a groupbox-only lookup left every field in that window with no
label at all: `0:00:00` and nothing to say what it was.

The fallback looks for any title element in an ancestor, and it runs **only when no groupbox
was found anywhere in the climb**. That restriction is not tidiness: the setup page's ROWS
carry a title element too, so an unrestricted fallback answered *"Time Format, Time Format:
UTC"* - the label twice, on every row of the page.

### Do failures announce? Ninety-one of ninety-four did; three did not

| | |
|---|---|
| **85** | announced flags - the model raises one and the ordinary announcer speaks it |
| **6** | reset BUTTONS, no state to announce |
| **3** | ⚠️ **percentages, and percentages do not speak** |

The three were `FAILURES_COOLANT_LEAK`, `FAILURES_TURBO` and `FAILURES_BOOST_LEAK` - a coolant
leak, a turbocharger failure and a boost leak, graded 0-100 on this engine. The
numeric-silence rule that keeps oil temperature quiet was keeping **them** quiet too, and they
are three of the most serious things that can happen to a turbo-diesel. A pilot would have
learned about a coolant leak from the temperature climbing, eventually, if they happened to be
scanning.

Their **onset** is announced now, and a **worsening of 25 points** after it - not the value.
A leak ramping 30 to 31 is not news, and announcing every percent would bury the one that
mattered. Nothing when it returns to zero: the only thing that clears one is the pilot
resetting failures, and the Reset button confirms itself.

`EveryFailureEitherSpeaksOrIsDeliberatelyGraded` now fails on any `DA40_FAIL_*` that is
neither an announced flag, nor a graded percentage, nor a button. **A failure that cannot
speak is the worst kind of silence**, and it is no longer possible to add one by accident.

**A failure genuinely acts on the aeroplane** - measured, not assumed. `FAILURES_ALT` set to 1
drove `GENERAL ENG MASTER ALTERNATOR:1` to 0 within a second (the model's own logic is
`(A:RECIP ENG ENGINE MASTER SWITCH:1) (L:FAILURES_ALT) ! and`), and clearing it brought the
alternator straight back.

**And the CAS works.** Verified end to end by opening the canopy: `DOOR OPEN` appeared at
WARNING severity, the reader picked it up, and it cleared when the canopy shut. The watcher
that speaks those now actually starts, which it did not before.

### The 77 settings are not 77 fields on one page

⚠️ **A correction.** The **System Setup page has 14 editable fields.** The 77 is the whole
Working Title settings *store* - everything the G1000 remembers - and it is spread across the
instrument:

| Where | Roughly what |
|---|---|
| Aux, System Setup | 14 - time, the six unit settings, the four data-bar fields, channel spacing, nearest-airport criteria |
| PFD softkeys (PFD Opt, SVT, Wind, ALT Units, STD Baro) | synthetic vision, pathways, wind mode, the **barometric unit**, metric altitude |

| Nav data bar | the four fields, also settable from System Setup |

So there is no page with 77 rows on it, and there never was - the number is the store, not a

### The Engine page menu is real, and it is Ctrl+E

The video is right. **MENU on the MFD Engine page opens the COWS options** - nine rows, which
is where every simulation setting on this aeroplane lives:

```
Failures Mode, State Saving, Engine Damage, Realistic Parking Brake,
Panel Shake, Steering Mode, Trim Speed, Prop Speed, Reset
```

**Ctrl+E is the MENU key** in the display window, it is bound, and it works - verified by
driving `PANEL_SHAKE_OFF` 0 to 1 to 0 entirely through that menu and reading the variable back
over SimConnect each time. Ctrl+left/right moves between rows, **Ctrl+Enter** toggles one, and
the three that carry a value (Trim Speed, Prop Speed, Reset) take Ctrl+up/down.

Every page has its own menu and the same key opens all of them: the Nav Map's carries Map
Settings and Declutter, the Traffic page's the TAS controls, the checklist's the group and
checklist pickers.

### V-speeds, and the power lever

The V-speeds are **read on demand and never announced**, which is right - they are constants
from the AFM and do not change. Vr, Vy (both configurations), Vref, short-field Vref, best
glide, Va, Vno, Vne, and a flap-aware Vfe are all on the output-mode speed keys.

⚠️ **Max power is the one that DOES change** - with altitude and temperature - and MSFSBA
cannot compute it. The figure comes from a table in the COWS product manual, and that manual
is a scanned PDF with no text layer, so the numbers have to be read off an image and checked
by a human before anything is built on them. A wrong minimum-power figure is worse than none.

**The power lever is a real 0-100 percent** and is clamped: `Math.Clamp(value, 0, 100)`, so a
typed 11,000,000 becomes 100 rather than anything strange. It commands **load, not RPM**, and
below 20 percent the engine is in disc mode - high RPM and a lot of drag, which is what the
video's pilot means by the RPM rising as the power comes back.

### A light that is selected on and not lit

⚠️ **The first version of this compared the wrong thing and was pure noise.** It watched the
`L:STATE_LIGHT_*` variables on the assumption they were the lamps. They are not — they are
COWS's **save-state mirrors**, and the model says so in two lines:

```
(A:LIGHT LANDING, Bool) (>L:STATE_LIGHT_LGN)        saved FROM the SimVar
(L:STATE_LIGHT_LGN) (>K:LANDING_LIGHTS_SET, Bool)   restored TO it
```

A mirror can never disagree with what it mirrors except for the frame it takes to catch up,
so every word it produced was a timing artefact — reported from the cockpit as *"Landing light
lit with the switch OFF"* a moment after switching it off. That is the same `STATE_*`
read-only-mirror rule this aeroplane has already taught twice, missed a third time.

**What actually gates a light is the sim's own circuit**, and the model says that too:

```
(L:CB_LDL) 0 ==                        breaker in
(L:FAILURES_LIGHT_LDG) 1 == ! and      and the bulb not failed
(L:ELEC_BUS_ESS_VOLT) ... 19 > and     and the bus above 19 volts
if{ ... connect circuit 14 ... }
```

So `CIRCUIT ON:n` is true only when the light is switched on **and** its breaker is in **and**
its bulb has not failed **and** the bus can power it. Measured both ways: breaker in, `LIGHT
LANDING` 1 and `CIRCUIT ON:14` 1; breaker pulled, `LIGHT LANDING` **stayed 1** and `CIRCUIT
ON:14` went to 0.

| Light | Breaker | Circuit | Failure |
|---|---|---|---|
| Landing | `CB_LDL` | 14 | `FAILURES_LIGHT_LDG` |
| Anti-collision | `CB_STB` | 26 | `FAILURES_LIGHT_ACL` |
| Position | `CB_POS` | 27 | `FAILURES_LIGHT_POS` |
| Taxi | `CB_TXM` | 28 | `FAILURES_LIGHT_TAX` |

⚠️ **This is also why pulling a breaker looked like it did nothing.** `L:CB_LDL` is the
handle; the sim's circuit is what carries the current, and the light SimVar never changes —
the switch is still on, the bulb is just dark. The same split is already recorded from the
other direction: a *sim*-level pulled breaker kills its circuit while `L:CB_*` still reads IN.

It says **one short sentence and nothing else** — `Landing light not lit` — and says nothing
when the fault clears: the pilot either switched the light off, in which case the switch
already spoke, or reset the breaker, in which case they know. The first version announced both
and was, correctly, called too verbose.

The cabin lights are excluded even though they have circuits (29 and 30): their switch is a
three-position selector and the aeroplane also toggles them from a clickspot on the airspeed
needle, so "selected on" is not one clean state to compare against.

### A settled knob value must INTERRUPT, not queue

`Announce()` hands NVDA the line with interrupt off, so it waits behind everything already
speaking — and the moment a pilot turns the barometric knob is exactly the moment the queue is
busy, because they are working the PFD window and it is reading itself back. Reported as the
altimeter setting arriving "very late"; it was not late, it was **in a queue**.

Both settle announcers interrupt now. That is right for this specific case and not in general:
they fire 600–700 ms *after* the pilot stopped turning, so what they carry is the number the
pilot is sitting there waiting for.

### Both settings sets are reachable AND writable — verified by round trip

Neither is a SimVar; both live inside instruments, and both are driven the same way — through
the display window's bezel keys.

| | Where | How | Proof |
|---|---|---|---|
| **COWS options** (9) | MFD Engine page → **Ctrl+E** | Ctrl+Left/Right to the row, **Ctrl+Enter** toggles; Trim Speed, Prop Speed and Reset take the upper knob (Ctrl+Up/Down) | `PANEL_SHAKE_OFF` 0 → 1 → 0 through the menu, read back over SimConnect each time |
| **G1000 settings** (77) | Aux → System Setup, and the PFD softkeys | **Shift+Enter** for the cursor, Ctrl+Left/Right to the field, Ctrl+Up/Down opens its list, Ctrl+Enter accepts | Weight Pounds → Kilograms → Pounds, with the units row following each change |

⚠️ The read-back can lag the press by one frame — the value is read before the model updates —
which is why the window retries a read that shows nothing new rather than believing it.

### Checked against a real pilot's flight, and against the aeroplane's own Tips page

A transcript of a full flight in this aeroplane - COWS DA40-NG, flown and narrated by an
airline pilot - was read line by line against MSFSBA. Almost everything in it was already
reachable: both checklists item for item (alternate air, alternate static, the essential and
avionic buses, the voter switch, the ECU test, the fuel transfer pump), the steering-mode
option, the fuel totalizer, the CAS fuel-transfer advisory, the standby horizon caging.

Three things were not, and one of them matters more than anything else found this week.

**⚠️ THE AEROPLANE SHIPS ITS OWN TIPS AND HELP PAGE AND NOBODY HAD READ IT.** Not the G1000
checklist - the MSFS *native* checklist, `Checklist/DA40_NG_Checklist.xml` in the package,
whose postflight section carries a "Tips and help" page. It contains, in the vendor's own
words, the operating knowledge this project spent days deriving by probe:

```
Warmup                Idle for 2 min. Up to 50% load.
Starting              Toggle the Engine master to recycle the glow plugs.
                      Hold the starter until 500RPM.
Normal take-off       Flaps T/O. Rotate 67KIAS. Pitch 7.5deg.
Short field take-off  Flaps T/O. Rotate 60KIAS. Pitch 7.5deg.
Traffic Pattern       Downwind 45%. Abeam 20%, Flaps T/O, 85KIAS.
                      Final 35%, Flaps LDG, 77KIAS.
ILS Approach          Approach 60%. FAF 35%, Flaps T/O. Landing 35%, Flaps LDG.
Landing               Reduce power gradually over the threshold. Bleed speed in the
                      flare. Touchdown at ~5deg ~65KIAS.
Fuel Transfer         Stops automatically above ~14gal.
Taxiing               Use your Toggle Landing gear button to switch steering assist modes.
Cabin lighting        Toggle the cabin lights by pressing the airspeed indicator needle.
Reseting failures /   Press and hold the ECU test button for 10 seconds with the engine
  Charging battery    master turned off.
```

That last line is the aeroplane's **own documented way out of a flat aircraft** - the state
that cost this project an afternoon of probing, with the answer sitting in the package the
whole time. It is now a button on the ECU panel: the same physical button as the ECU test,
told apart by the engine master and the duration. ⚠️ With the master ON the same hold runs
the 26-second ECU test instead, which cycles the propeller, so this is the one control on the
aeroplane where a blocker is **refused** rather than merely reported - the alternative is not
a degraded version of what was asked for, it is a different function.

**The glow lamp going out is a cue to ACT, and it was silent.** The start is: master on, wait
for the glow annunciation to go out, then crank. A sighted pilot is interrupted by that lamp
extinguishing whether they were watching or not - it is the whole reason they are sitting
there. It was `OnRequest`, so it appeared only in the Engine Start panel's scan and a pilot
had to sit on that panel pressing F5 to catch it. It is Continuous and announced now; it is a
described state, not a moving number, so it does not fall foul of the numeric-silence rule.

**Still not there, and worth their own pass:** the max-power check (the video reads a minimum
load off a table in the manual - 96% at sea level and 20 C - and MSFSBA cannot compute it),
and the G1000 timer, which the video starts before take-off.

### What this DA40 has, and what can be changed

| | |
|---|---|
| Avionics | one fit: G1000 (the stock Working Title instrument, not the NXi) plus the GFC 700. There is no equipment page, no alternative autopilot, no de-ice fit to choose. |
| Airframes | `BOOM`, `HIGHTAIL`, `NOTAIL`, `BOOM2` - tail variants, picked by choosing a **livery** in the sim, not from the cockpit. All five NG liveries are `BOOM`; the XLS spreads across three. |
| Changeable in the cockpit | the nine COWS options on the MFD Engine page menu, and the seventy-seven Working Title G1000 settings. Both are reachable from MSFSBA now. |

**Doors: four exits, and no latch to model.** Front canopy, rear door and the two storm
windows, on stock `EXIT OPEN` indices - and ⚠️ the TOGGLE event index is one HIGHER than the
SimVar index (`TOGGLE_AIRCRAFT_EXIT 3` opens `EXIT OPEN:2`), which MSFSBA already encodes.
MSFSBA reads them as a PERCENTAGE, so an animating door is reported at every position rather
than as open-or-shut.

The real DA40's canopy has a two-stage latch; **this model does not have one**. The only
latch variables in the package are `INPUT_LATCH` (a control-input latch for the elevator
animation - nothing to do with doors) and the FADEC's ECU-fail latches. What the aeroplane
does instead is raise a **`DOOR OPEN` CAS message at WARNING severity**, verified live by
opening the canopy: the CAS reader picks it up, and now that the CAS watcher actually starts,
it is announced.

### What auto-announces in the background, and what does not

The rule is `Continuous && IsAnnounced` and not silenced. On this aeroplane that means:

| Speaks on an external change | Stays quiet |
|---|---|
| every switch and selector - lights, buses, pumps, valves, breakers, the voter | temperatures, voltages, RPM, brightness and every other moving number |
| CAS messages, at every severity | the light **lamp** states (`*_STATE`) |
| the flap selector, the trim, the doors | |
| **the glow annunciation** (new) | |

⚠️ **A light SWITCH speaks; the light itself does not.** `DA40_LIGHT_LANDING` and its
siblings are the switches and they announce, but `DA40_LIGHT_LGN_STATE` and the other `_STATE`
variables - the lamps, which are what the bulb is actually doing - are `OnRequest` and appear
only in the panel scan. They agree with their switches almost always, and the interesting case
is precisely when they do not: a pulled breaker or a failed bulb. That disagreement is worth
announcing and a bare state change is not, which is a piece of logic rather than a flag, and
is not written yet.

### A hotkey can only read what is in the cache

⚠️ **Alt+S and Shift+F could never have worked**, and were shipped that way. Reported from
the cockpit: the engine-at-a-glance key said *"Engine readings not available yet"* with the
engine running, and the fuel key reported a flow of **0.0** out of an engine burning 3.6
gallons an hour.

Batch membership is `Continuous` **AND** `IsAnnounced` **AND** not `ExcludeFromBatch`. An
`OnRequest` variable is never polled, so `GetCachedVariableValue` returns null and the key
answers "not available yet" for ever. All thirteen variables behind those two keys were
`OnRequest`.

⚠️ **And it could not be fixed by promoting all of them.** The continuous batch **sorts by
SimVar name**, so two batched keys on one SimVar shift every later variable's struct slot
and corrupt the whole read. The traps, all real on this aeroplane:

| Wanted | Shares its SimVar with |
|---|---|
| `DA40_POWER_LOAD` | `DA40_START_LOAD` (`DISP_LD`) |
| `DA40_POWER_RPM` | `DA40_START_RPM`, `DA40_ECU_PROP_SENSED` (`PROP_RPM_SENS:1`) |
| `DA40_START_GEARBOX_TEMP` | `DA40_ECU_PRE_GEARBOX` (`DISP_GT`) |
| `DA40_POWER_FUEL_FLOW` | `DA40_FUEL_FLOW` (`DISP_FF`) |
| `DA40_STBY_AIRSPEED` | **`DA40_AIRSPEED`, already batched** |
| `DA40_STBY_ALTITUDE` | **`INDICATED_ALTITUDE`, already batched** |

The first four keep their OnRequest twins. The last two are not promoted at all — the hotkey
reads the batched twin instead, which is the same number: the standby ASI and altimeter share
the pitot-static system with the G1000 on this aeroplane.

Everything promoted is silenced and kept out of the Monitor Manager: it carries `IsAnnounced`
only to earn the batch place, and a row a pilot can un-tick that was never going to speak is
a row that lies. **The two gyro flags are the exception and are deliberately not silenced** —
a standby gyro that has been caged, or has toppled and is showing a plausible lie, interrupts
a sighted pilot the moment they look at it.

**The old test listed the keys by hand**, which is why it passed straight through this. The
new one *scans the hotkey source* for every `ReadNow` and `Add` call and checks each against
the variable table, so a key added tomorrow is covered without anybody remembering. A second
new test fails on any two batched variables sharing a SimVar name — the trap above, which is
otherwise silent and total.

### Three general-aviation engine keys

Not DA40 keys — the question is the same on every propeller aeroplane and only the answer
changes, which is why the actions are `ReadEngineRpm`, `ReadEnginePower` and
`ReadEngineTemps` rather than anything named for a diesel.

| Key | On the DA40 | On another type |
|---|---|---|
| **P** | RPM, plus what the ECU is **targeting** when that differs — the Austro has no propeller lever, so this is how you hear the governor work | prop RPM against the pitch lever |
| **E** | load percent, fuel flow, power lever — an Austro has no manifold pressure and no mixture, one lever | manifold pressure and mixture; torque and ITT on a turboprop |
| **Shift+O** | oil, coolant and gearbox — a liquid-cooled, geared diesel has two an air-cooled Lycoming has not | CHT and EGT |

`O` stays the **outside** air temperature; `Shift+O` is the engine's own. Alt+S remains the
whole picture in one press.

P, E and Shift+O were free on every modifier across the entire registration table — checked
rather than assumed, because a lost registration is a key that does nothing with no error.

### The manual sweep: what the aeroplane offers that MSFSBA was not using

The package ships its own documentation — `DA40 LVAR bindings.txt`, `Failures.txt`, the COWS
MSFS POH, and the real Diamond AFMs and checklists for both variants. The bindings file is
the vendor's own list of every control they expose, so it is the honest test of coverage:
read it line by line against the definition rather than guessing what might be missing.

Everything in it was already exposed except three things.

**TO/GA had no way in at all.** The vendor names it `KEY_AUTO_THROTTLE_TO_GA`, which is a
misleading name on an aeroplane with no autothrottle: what it does here is command the
**flight director**. Verified live — with the director off and its pitch command at zero, one
`AUTO_THROTTLE_TO_GA` turned the director on and set the command to **10° nose up**. Wings
level, ten degrees, which is the go-around attitude. It is now a button on the GFC 700 panel.

A go-around is the one manoeuvre where a pilot has no time to work out an attitude for
themselves, so having no way to press the button was a real hole rather than a tidy one.

⚠️ It is a **button, not a state**: pressing it again does not un-press it, there is no
variable to read back, and the way out is to select another mode or disconnect. The Flight
Director panel already reads the resulting pitch command, which is the aeroplane's own answer.

**The Hobbs meter was unreadable.** `L:HOBBS` — the aeroplane has a whole VCockpit gauge for
it beside the two G1000 screens — and nothing in MSFSBA could see it. It is the number that
decides when the aeroplane is due maintenance and, on a rented aeroplane, what the flight
costs; a pilot writes it down before and after every flight. It is on the ECU panel's status
now.

⚠️ **It is not the MFD Engine page's "Total Service"**, which read 0.0 hours while `L:HOBBS`
read 45.9 on the same airframe. Both are in the aeroplane; only this one is the Hobbs.

**The barometric knob was not on the keyboard.** `AS1000_PFD_BARO_INC`/`_DEC`, on the same
bezel and the same SimConnect transport as the radio knobs — verified live, one INC moved the
G1000 from 1011.85 to 1012.19 hPa, the aeroplane's own 0.01 inHg step. It is Ctrl+Shift+Up
and Down in the PFD window. Ctrl+B still sets *both* altimeters to a typed number and still
takes either unit; the knob is how the aeroplane is actually flown down an approach.

Everything else the bindings file names was already there: the trim inputs, the brake axes,
the parking brake, the ESS bus switch, the headset, the gyro cage, the standby altimeter's
own Kohlsman variable, the autopilot disconnect, and all 34 circuit breakers.

### The XLS engine panels — built on the live XLS, one at a time

The XLS's engine is a different engine, so its six engine panels share no code with the
NG's — only the panel names and positions, which is how one pilot flies both. Each was
measured on the live aircraft before it was written; every unit, encoding and trap is in
[da40-xls-variables.md](da40-xls-variables.md), and the pure logic behind each has its own
tests. `CowsDA40PanelStructureTests.NotBuiltYetOnXls` — which once listed all six — is
empty, and the test checks it in both directions.

| Panel | What it is on the XLS | Pure logic |
|---|---|---|

| **Fuel System** | Left / Right / Off, the electric pump, refuelling by the tank (20.1 gal usable a side), the gauge's 15.25-gal flat spot named, the 10-gal difference limit, feed, pressure (bar, spoken in psi), vapour lock. | **Engine Start** | The start scan the NG's panel is: readiness that names the first blocker (master, un-generated variations, selector, tank, vapour, the jet's 0.8-bar pressure gate, priming state), COWS's own auto-start narrated step by step from its counter, the crank tach, starter, amps, combustion as an announced state. | **Mixture and Propeller** | The panel the XLS exists for: the lean assist as words (peak and how far below it, per cylinder; the first cylinder to peak is called), the eight temperatures the bars are drawn from in the pilot's unit, the red box recomputed per cylinder from heat and air/fuel, plug fouling per plug, shock cooling, cylinder health, and two things done to the levers — the aircraft's own Set Best Mixture and the run-up's propeller cycle. | `DA40RedBox`, `DA40CylinderState` |

Three things that are NOT there, deliberately: detonation (commented out of this build's
model and consumed by nothing), the levers on the Mixture panel (they live on Power and
Levers — one control, one panel), and the lean-assist TOGGLE (it is the Assist softkey on
the MFD Engine page, which the display window presses).

**Manual lean assist, end to end** — measured live on the XLS, and the row now names the
softkey by NUMBER because that row is the only place a blind pilot learns where it is:

1. MFD **EIS – Engine** page (Ctrl+G, or the FMS knob).
2. **Softkey 10, "Assist"** — toggles `L:DISP_LEAN_ASSIST`. Pressed live over SimConnect
   (the transport the softkeys use) and watched take it 1 → 0.
3. Lean with the **Mixture** control on Power and Levers, or the hardware lever.
4. As each cylinder falls `PeakedAtF` (10 °F) below its own running peak, MSFSBA CALLS it
   once: *"Cylinder 3 peaked at 1484 degrees fahrenheit"*. **The first of those calls is
   the POH's cue** — "lean until the first EGT peaks".
5. The **Lean Assist** row on Mixture and Propeller carries all four at any time: each
   cylinder at its peak, or how far below it.
6. **Set Best Mixture** on the same panel is the aeroplane's own keybind — with Automixture
   off it walks the mixture down until the four cylinders average 12.5 : 1 and stops
   itself; with Automixture on it snaps to 72 %.

⚠️ `DISP_LEAN_ASSIST` IS writable and holds (verified), so a panel switch would work — it
is deliberately not added, because a softkey belongs to the display window under this
project's own rule. The row names the key instead.

### Is the autopilot used in VFR? Yes

Nothing about VFR forbids an autopilot, and a GFC 700 is used in visual conditions all the
time — it is how a single pilot gets their head out of the cockpit to look for traffic, fold
a chart, or set up an approach. The usual pattern is heading and altitude hold on a cruise
leg, hand-flown circuits, and the autopilot off below about 500 ft (the DA40's AFM gives a
minimum engagement height, and the GFC 700 will not hold an approach below it either).

For a blind pilot the calculus is different in one way that matters: the autopilot is what
buys the time to *read*. Holding a heading and altitude by ear while also arrowing through a
setup page is two jobs; letting the GFC 700 hold them is how the same flight becomes one job.
That is not a simplification of the aeroplane — it is what the aeroplane is for.

### What MSFSBA already has that VFR work would build on

Not a plan, a survey — these exist, are tested, and are the pieces any VFR feature would be
assembled from rather than written fresh:

| Already there | What it gives VFR |
|---|---|
| `VisualGuidanceManager` | dual-tone pitch/bank guidance against a **runway**, in phases, with per-aircraft profiles — the skeleton of a circuit assistant |
| `HandFlyManager`, `AudioToneGenerator`, `PhaseContinuousOscillator`, `TaxiSteeringTone`, `ProximityBeeper` | a complete audio-guidance toolkit; a "fly this tone" feature does not need a new sound engine |
| `VISUAL_GUIDANCE_GROUND_TRACK` and `VISUAL_GUIDANCE_HEADING` (already DA40 variables) | drift and wind-correction calls are arithmetic on two values that are already registered |
| `TakeoffAssistManager`, `LandingFlareAssistManager`, `LandingGuidanceLaws`, `LandingRateAnnouncer`, `LandingExitPlanner` | both ends of the circuit already exist; the middle does not |
| `GeoNamesService`, `RouteAdvisoryLocator`, `RouteAdvisoryProximityTracker`, `DistanceMilestones` | "what is out of the window", leg timers, and turning-point calls |
| `WeatherService`, `ActiveSkyClient`, `IceAccretionTracker`, `TurbulenceCategoryTracker` | cloud base, visibility and the VMC-minima question |

### QNH in hectopascals, which is most of the world

The G1000 carries its own barometric unit — `baroHpa`, set on the PFD under **PFD Opt →
ALT Units** — and it is deliberately *not* in the Display Units box on the setup page, which
is why it was missed the first time. Outside North America every clearance comes in
hectopascals, so hearing inches first means doing the conversion in your head on every
descent.

It now rides the same units row as the other six, and **B** leads with whichever the pilot
chose. Both are still given, because this aeroplane has two altimeters and a pilot
cross-checking a controller's QNH against a chart wants whichever is in front of them:

```
pressure inches        Altimeter 29.88 inches, 1012 hectopascals
pressure hectopascals  Altimeter 1012 hectopascals, 29.88 inches
```

**Setting it already worked and always has.** Ctrl+B takes either unit and tells them apart
by magnitude — anything above 100 is read as hectopascals (948–1066) and anything below as
inches (28.00–31.50) — and it sets *both* altimeters, because the AFM descent check is
"Altimeters (2) … SET".

### The fuel keys answer two different questions

⚠️ **F and Shift+F were two labels on ONE case**, so both keys said the same sentence and
one of them was wasted. On an airliner they are pounds and kilograms; this aeroplane is
fuelled by volume, so the second key answers a different question instead:

| Key | Answers |
|---|---|
| **F** | the TANKS — total and each tank, in the pilot's chosen fuel unit (with the AFM's litres beside it while that unit is the default gallons) |
| **Shift+F** | how long that fuel LASTS — current flow, endurance at that flow, and the tank difference against the 9 gallon AFM limit |

⚠️ **Neither matches the MFD's Fuel Calculator, and neither is meant to.** The calculator is
a **totalizer**: a figure the pilot sets with the INC FUEL / DEC FUEL / RST FUEL softkeys on
the Engine page, which then counts down by fuel *used*. Measured live: tanks 37.2 gallons,
calculator 32.2 remaining. That difference is the whole point of having both — the
calculator is a flight-planning figure, the tanks are the fuel.

The tank difference is on the second key because on the NG the tanks drift apart **on their
own**: fuel is burnt from the main and returned through the aux, so a pilot who never
touches anything still ends up with an imbalance to transfer back.

### Two Airbus keys that do something else here

The DA40 has no lower ECAM and no ISIS, but it does have the things those keys are *for*:

- **Alt+S — the engine at a glance.** Load, RPM, oil pressure and temperature, coolant,
  gearbox, fuel flow, bus volts and amps, each gauge with its published arc. One press for
  the whole engine picture, which on a single-engine aeroplane is the most useful key on the
  keyboard: a sighted pilot takes the EIS strip in with one look, and a blind pilot was
  otherwise opening a panel and arrowing down it.
- **Alt+I — the standby instruments.** Airspeed, altitude, compass and the standby attitude
  gyro, plus a warning when that gyro is CAGED or has TOPPLED. This is not a stand-in: the
  DA40 really carries all four, and a reversion to standbys is the one moment a pilot needs
  them together with no G1000 to read them from.

Both go through `TryGetDisplayOverride` rather than formatting their own numbers, so a
hotkey can never answer "85 celsius" while the panel beside it says "85 degrees celsius,
green".

### Cycling the propeller is an XLS item and does not exist on the NG

On the **XLS** the Lycoming IO-360 drives a constant-speed propeller with its own blue pitch
lever, and the run-up cycles it two or three times at about 1800–2000 RPM. It does two
things: it proves the governor responds, and it pushes the cold, thick oil out of the
propeller hub so the blades will actually change pitch in the air.

The **NG has no propeller lever at all.** The Austro AE300's FADEC governs the propeller
through the single power lever, so there is nothing to cycle — the run-up item in its place
is the **ECU test**, which the Engine Start panel runs for you (about 26 seconds, cycling
the propeller once per ECU).

### One G1000, two screens, and no captain/first-officer split

The DA40 has exactly **two** G1000 displays — `AS1000_PFD` and `AS1000_MFD`, confirmed from
the sim's own view list, alongside a Hobbs meter and nothing else. The PFD sits in front of
the left seat and the MFD in the centre; the right seat looks at the same two screens. There
is no second PFD and no per-side duplication, so nothing in MSFSBA needs a captain/FO
concept for this aeroplane. (Aircraft that *do* have one — the A380's CAPT and FO PFD/ND,
the 787's five displays — carry it in their own definitions.)

⚠️ **The two screens do NOT share a viewService.** Each is its own instrument with its own
registered views, its own scroll controllers and its own page state; only the *settings* are
shared over the instrument bus, which is why the units can be read from either. And only one
inspector socket exists per screen, which is why the PFD window and the CAS watcher have to
hand it back and forth.

### The radios are tuned on the PFD, globally, and that is correct

There is no radio *page*. The G1000 tunes COM and NAV from the **PFD bezel** — the frequency
boxes across the top of the PFD, with the tuning box moving between radio 1 and radio 2 —
and those boxes are live whatever page the MFD happens to be showing. That is the real
aeroplane: a sighted pilot never navigates anywhere to change a frequency. The MFD has no
COM or NAV knob at all.

What a G1000 *does* offer instead of a radio page is frequencies attached to places: the
Nearest Airports page and the WPT Information pages carry a FREQ softkey that loads a
frequency straight into the standby box. Four of the eight Nearest pages, including Nearest
Frequencies, are stubs in this build (see the page table above).

### The CAS watcher was never started for the aircraft the app opens with

⚠️ **This is why cautions never auto-announced**, and it had nothing to do with the CAS
reader. `SwitchAircraft` starts the watcher — but `SwitchAircraft` runs **only when the
pilot picks an aircraft from the menu**. The startup path sets `currentAircraft` directly
from the saved setting in the constructor, so a session that opens with the DA40 already
selected — which is every session for a DA40 pilot — never called it.

Proved from the app's own log rather than reasoned about: the aircraft registered
(`aircraft=CowsDA40Definition`), the display window worked (`Display units now: …`), and
`"CAS monitor: started"` — which `StartCasMonitor` logs unconditionally on its first line —
was never written once.

The A380's E/WD monitor and the HS787's IRS monitor are started in **both** places, in
`MainForm_Load` and in `SwitchAircraft`. The DA40's was only in the second. The rule is
now written down where it can be seen: **a background monitor must be started in both
places, or it does not run for the aircraft the app opens with.**

### The cursor is announced when it changes, and at no other time

"Cursor on." used to prefix **every field**, so walking fourteen fields down a setup page
meant hearing it fourteen times for one bit of information the pilot already had. Both
transitions are still announced, because neither marks itself — turning it off leaves only
the page title, which is indistinguishable from a key that did nothing.

### The knob does not wrap, and now says so

At the end of a page the G1000's FMS knob simply stops. The window read the same field back
on every further turn with nothing to say why — reported from the cockpit as *"Minimum
Length"* fifteen times running. The agent's state answer carries the **focused field index**
now, so when the cursor is on, the focus did not move, and the key was a field-moving knob
turn, the read-back adds *", end of the page"* or *", start of the page"*. A value key that
leaves the focus where it was has not hit any kind of end and is not told it has.

### A field is read with the box it lives in

`Minimum Length` means very little until you know it is in the **Nearest Airport** box. A
sighted pilot never has to ask: the boxes are drawn round the fields with the heading right
there. `groupbox` + `groupbox-title` is the instrument's own pairing and is used on every
page family, so one rule serves the setup pages, Direct-To, the page menus and the procedure
pages:

```
Nearest Airport, Minimum Length: 3000FT
Display Units, NAV Angle: Magnetic(°)
```

The field list in the window is grouped the same way, which makes arrowing it read like
looking at the page:

```
Fields (14), cursor on:
  Date / Time
    Time Format: UTC
    Time Offset: +00:00 (not available)
  Display Units
    NAV Angle: Magnetic(°)
    ...
  Nearest Airport
    Runway Surface: Hard Only
    Minimum Length: 3000FT   <-- cursor
```

### The PFD's cursor does nothing until a window is open, and now says so

The PFD has **no pages** — `openPageKey` there is permanently empty — only windows. So its
FMS knob and cursor genuinely do nothing until one is open, and a key that does nothing in
silence is the fault this whole file exists to avoid. It now answers with what would make
it work: *"No window open. The PFD cursor works inside a window — press Control G, or a
softkey such as Nearest or Timer and References."*

### ⚠️ The radio knobs go back over SimConnect — the opposite exception

Moving the whole bezel onto the Coherent socket silently killed radio tuning from this
window, which is what *"how do I tune the coms and navs?"* meant. Measured both ways on
COM 2's standby, minutes apart:

```
onInteractionEvent("AS1000_PFD_COM_Small_INC")   →  124.850, unchanged
1 (>H:AS1000_PFD_COM_Small_INC) over SimConnect  →  124.855
```

Same for NAV (`NAV_Small_INC` stepped NAV 1 standby 113.90 → 113.95). So the split on this
display has **two** measured exceptions pointing opposite ways:

| Over the Coherent socket | Over SimConnect |
|---|---|
| FMS knob, MENU, ENT, CLR, Direct-To, FPL, PROC, range, joystick | the twelve softkeys |
| the COM/NAV knob **push** (moves the tuning box) | the COM/NAV knob **turns** |

The likeliest reason for the radio half is that those events are consumed by the
aeroplane's own gauge logic rather than by the JavaScript instrument — but the reason does
not matter, the measurement does.

Nothing is spoken when a radio knob is turned: every frequency is Continuous and announced,
and the settle announcer speaks the value the knob comes to rest on. Announcing the
keystroke as well would put a word in front of the only thing the pilot is waiting for.

### The list holds still while the pilot reads it

⚠️ **This is why the reader kept saying "not selected".** The window re-reads the display
about once a second, and rows legitimately appear and disappear as it does — the field list
arrives when the cursor is armed, a box heading arrives with it, a caution clears.
`DisplayList.UpdateInPlace` then has to move the selection to follow the row the pilot was
on, and a ListBox whose selection is re-set under a screen reader re-announces the item
*with its state*.

So while the pilot is actually moving through the list, the list holds still — 2.5 s of
quiet after the last arrow, Home, End or Page key. The scrape keeps running and the CAS
watcher and the units reader are fed from it **before** the hold, so no announcement is ever
delayed; only the redraw waits. F5 cancels the hold, because F5 means *now*.

### What the Aux setup page still does not let you change, and why

The page **draws** ten boxes and only five of them have controls behind them. BARO
Transition Alert, Airspace Alerts, Arrival Alert, Flight Director and GPS CDI render their
values and register nothing, so the knob walks straight past them — for a sighted pilot too.
They are readable in the window's *Page content* block and are not editable by anyone.

**Setup 2 is a stub as well, and completely so.** Softkey 7 is drawn and labelled, and
pressing it over SimConnect — the transport that does work for softkeys — changes
*nothing*: the page stays on System Setup 1, the field list is the same fourteen, and
neither Setup softkey even takes the active highlight. There is only ONE subpage element
in the markup (`mfd-system-setup-subpage-1`); there is no subpage 2 to switch to. Same
emptiness as the seven unimplemented Aux pages.

### MSFSBA answers in the units the pilot set on the G1000

A pilot who switches the Aux System Setup page to kilograms has said what they want to
hear, and every panel carried on saying pounds. Same for temperature, distance and speed,
altitude and vertical speed, and fuel. That is the aeroplane disagreeing with itself, on a
display a blind pilot cannot glance at to settle the argument.

**Where the settings live, and why they arrive the way they do.** They are not SimVars and
not L:vars. They are Working Title *user settings*, held by the instrument's own
`settingSaveManager` and persisted into the aeroplane's profile (`DA40.profile_1`):

```
unitsNavAngle = magnetic     unitsTemperature = celsius
unitsDistance = nautical     unitsWeight      = pounds
unitsAltitude = feet         unitsFuel        = gallons
```

Nothing outside the instrument can read them, so they come down the **Coherent socket as
one row on the ordinary scrape** — no extra round trip and no new connection:

```
Display units: bearings magnetic, distance nautical, altitude feet,
               temperature celsius, weight pounds, fuel gallons
```

⚠️ **Both displays carry the same six** (verified live — the settings are shared over the
instrument bus). That is what makes this work with no display window open at all: the CAS
monitor already holds an always-on socket to the PFD, and the PFD's copy is as good as the
MFD's. Whichever window *is* open feeds them too, because only one client can hold each
view.

Until a scrape arrives, the defaults are the G1000's own factory defaults, so a pilot who
has changed nothing hears exactly what they heard before.

**What follows the setting.** The dimension comes from the variable's *declared unit*,
never from its name — a variable measured in `celsius` is a temperature whatever it is
called, and a name-matching rule would need extending for every new readout and would be
wrong the first time somebody wrote `OIL_TEMP_SWITCH`:

| Native unit | Follows | Becomes |
|---|---|---|
| `celsius` (13 readouts) | Temperature | degrees fahrenheit |
| `pounds` (8) | Weight | kilograms |
| `gallons`, `gallons per hour` (8) | Fuel | litres, imperial gallons |
| `knots` (6) | DIS, SPD | kilometres per hour |
| `feet`, `feet per minute`, `feet per second` (7) | ALT, VS | metres, metres per minute |

**A gauge's band is read from the raw value and only the number changes.** An arc is a
physical fact about the engine — the green on the oil-temperature gauge is the same span of
heat in either scale — so `90 degrees celsius, green` becomes `194 degrees fahrenheit,
green`, and the AFM's "at the indication limit" warning survives a switch to litres because
it is about a quantity of fuel.

**A fuel unit that cannot be converted is left alone rather than guessed at.** The Garmin
also offers weight-based fuel; turning gallons into pounds needs the fuel's density, and
inventing one would put a wrong number in front of a pilot planning a flight on it.

**⚠️ NAV Angle is deliberately not applied**, and this is a decision rather than an
omission. Magnetic to true is not a unit conversion, it is a change of **datum** — and,
far more importantly, the heading bug and the course are *written* by MSFSBA's panels
through `AUTOPILOT HEADING LOCK DIR` and `NAV OBS`, both of which are magnetic. Showing a
true bearing in a field the pilot then types a number into would put the aeroplane several
degrees off the heading they asked for, silently. The setting is read and reported in the
scan; nothing else changes.

The payload rows and `DualUnitFuel` are untouched: they already answer in **both** units
("1900 pounds, 862 kilograms"), which is strictly more than the setting asks for.

### The CAS block ends where the CAS block ends

⚠️ **Indentation alone was never a safe test for a CAS message**, and the field list made
that fault fire constantly. The scrape indents every nested list it emits — the PFD's
popout panes, and now the fields of every page — so an indentation-only rule announced
`Weight: Pounds(LB)` as a caution the moment a pilot opened a setup page. The block now
starts at the `CAS messages:` header and ends at the first row that is not part of it, and
that boundary is a static method with its own test rather than a loop inside the monitor.

### Saying when nothing is under the cursor

The knob can run off the end of a checklist, and the cursor can arm a page whose only
control is the map pointer. Answering with the page title alone is indistinguishable from a
key that did nothing — the complaint that started all of this — so the summary now says
`..., nothing under the cursor`.


## The GFC 700 autopilot

The DA40 NG's autopilot is a Garmin GFC 700, and the single most important fact about it
is that it has **no airframe variables at all**. Nothing in the COWS package writes an
`L:AP_*`; there is no `STATE_` mirror for a mode, no vendor event for a button. Every
search of the model XML and the vendor's own `DA40 LVAR bindings.txt` comes back empty.

That is not a gap — it is how the aeroplane is built. The GFC 700 is integrated into the
G1000, and the G1000 in this package is the stock Working Title instrument, which drives
the STOCK MSFS autopilot. So the whole panel is stock events and stock SimVars, and it
would have been a mistake to go looking for anything else.

### Two panels, and why the values moved here

`GFC 700` carries the modes and the selected values. `Flight Director` carries the FD's
own commanded pitch and bank, which are a readout and nothing else.

The heading bug and the course knob USED to live on the Radios panel, because physically
they are PFD bezel knobs and they sat beside the radio tuning knobs. Functionally they are
what the autopilot flies, so they moved — MOVED, not copied. `TheAutopilotOwnsTheHeadingBugAndCourse`
pins both halves of that, because a duplicated control is worse than a misplaced one: two
panels showing one knob means a pilot can set it in one place and read a stale value in
the other.

### Never a toggle — always the explicit ON or OFF event

Every mode writes a DISTINCT event per direction: `AUTOPILOT_ON`/`AUTOPILOT_OFF`,
`AP_HDG_HOLD_ON`/`AP_HDG_HOLD_OFF`, and so on down the list. The stock API offers a
`_TOGGLE` for most of them and it is deliberately unused.

The reason is the same one behind `ExecuteCalculatorCodeUnique` everywhere else in this
codebase: a combo asks for a STATE, and a toggle can only ask for a CHANGE. If the panel
and the aeroplane ever disagree by one — a mode the pilot armed from a yoke button, a
mode the G1000 dropped on its own — a toggle sends the autopilot to the opposite of what
the pilot just selected, silently and with full confidence. Every write still goes through
`ExecuteCalculatorCodeUnique`, because ON pressed twice running is two byte-identical calc
strings and MobiFlight would drop the second.

### The selected values are clamped, and they are typed entries

`ALT_SET` rounds to the nearest hundred and clamps 0–18,000 ft; `VS_SET` clamps ±2,000
fpm; `IAS_SET` clamps 60–172 kt (the NG's flap-up envelope); `HDG_SET` and `CRS_SET` wrap
0–359. All five carry keys ending `_SET`, so MainForm renders them as typed entries and
never as sliders — the slider path is hardcoded 0–100 and would read an altitude as a
percentage.

All five are in `SilentNumericControls`. A hardware altitude-preselect knob sweeping past
9,000 ft would otherwise announce every hundred feet, and a heading bug every degree.

### `AutopilotDisplay` is EMPTY, on purpose

Every selected value is already a control on this panel, and a control shows its own
value. Listing them in the display set as well read each one twice on the same scan. The
suite catches it, which is how it was found.

## The G1000 bezel keys, and why the window felt frozen

### The readback answered the wrong question

Pressing Ctrl+arrow on the checklist page spoke **"CHKLST - Checklist"** and nothing else,
whichever way the knob turned. The knob was working perfectly - measured live,
`FMS_Lower_INC` stepped the highlight from USER AGREEMENT to NORMAL OPERATING PROCEDURES -
but `A.summary()` fell through to the page TITLE, and a page title does not change when a
highlight moves. Four identical words after every keystroke is indistinguishable from a
dead key, so the page read as one you could not leave.

`A.summary()` now answers the SELECTION POPUP first and leads with the item under the
knob: *"Currently on: CHECK BEFORE ENGINE START"*. The whole list is still in the window;
what a keystroke has to answer is "where am I now".

### It was slow because every key paid the page selector's price

A bezel press waited a flat **1200 ms**, then made a full scrape round trip, and only then
a second round trip for the summary - three waits before the pilot heard anything, on
every press of an arrow key.

The 1200 ms is real but it is not general: it exists because the page selector the FMS
knob opens holds its choice for about a second before committing, and reading sooner
reports the knob as having done nothing. A list highlight, by contrast, moves on the frame
it is asked to.

So the wait is now earned rather than assumed. The quick read happens after 180 ms; the
long wait is paid ONLY when that read came back identical to the reading taken before the
key, AND the key was one of the FMS knob events. The summary is also fetched BEFORE the
scrape now, not after - the window's own text is not what a pilot is waiting on after a
keystroke.

### The keys are named after what they do

`Ctrl+Enter` was the CURSOR push, which is the one key on the bezel a pilot reaches for
expecting "confirm", so the obvious key did the unobvious thing while ENT sat on F3.

| Key | Bezel |
|-----|-------|
| `Ctrl+Left` / `Ctrl+Right` | Page GROUP; with the cursor on, moves BETWEEN fields |
| `Ctrl+Up` / `Ctrl+Down` | Page; with the cursor on, CHANGES the field's value |
| `Ctrl+Enter` | **ENT** |
| `Shift+Enter` | Cursor push |
| `Ctrl+D` / `Ctrl+F` / `Ctrl+P` | Direct-To / Flight Plan / Procedures |
| `Ctrl+E` / `Ctrl+L` | Menu / Clear |
| `Ctrl+PageUp` / `Ctrl+PageDown` | Range out / in |
| `Enter` | Press the softkey on the selected row |
| `F5` | Refresh the window (house-wide, not a bezel key) |

There are NO function-key aliases. Two ways to press one button is two things to learn and
two things to document, and the F-keys were never mnemonic. The whole bezel sits on one
modifier.

The knob labels are RIGHT, and were checked rather than assumed: `FMS_Lower` moved the
page group FPL to NRST, `FMS_Upper` moved the page within it.

### The selection reader must be gated on the checklist PAGE

⚠️ Both checklist selection lists stay in the DOM with `offsetParent` set AND `opacity: 1`
long after the pilot has left the checklist page - measured on the live MFD sitting on
"FPL - Active Flight Plan", where both lists still reported visible at opacity 1 while the
checklist page container reported hidden. So neither the visibility test nor the opacity
test that works for a G1000 popout dialog can be trusted here.

`A.checklistSelection()` therefore returns nothing unless
`.Da40-checklist-page-container` is itself visible. Without that guard the readback
answered *"Currently on: TERMS AND CONDITIONS FOR USE"* on EVERY page of the MFD - which
is a worse fault than the welded-list one the function was added to fix, and it shipped
briefly. This is the fourth appearance of "the element is in the DOM but is not the one on
screen" on this aeroplane.

⚠️ The rightmost softkey the G1000 boot page asks for is **softkey 12**.

### The PFD shares the bezel keys, and had the same read-back fault

The display window is ONE form serving both displays - it sends
`AS1000_{side}_{event}` - so every bezel key is already shared, and so is the cursor
reader, which searches the document rather than a page.

But `A.summary()` ended at `A.pageTitle()`, and the PFD has no
`.nav-data-bar-page-title` at all: that is an MFD element. So every bezel key on the PFD
read back a page name that does not exist there - the same fault the MFD had when it
answered "CHKLST - Checklist" to everything, one display over, and it had been sitting
there the whole time.

What a PFD keystroke actually changes is which POPOUT is open - nearest airports, the
timer, the transponder - and which entry inside it is selected, so `A.pfdPopout()` answers
that first. Verified live against an open window: it now says `nearest airport` where it
used to fall through to a page title.

⚠️ A popout is open iff its OPACITY is non-zero. They all stay `display:block` and full
size whether open or shut. That is the fourth distinct place on this aeroplane where "the
element is in the DOM" has meant nothing about whether it is on screen.

### Thirty breaker trips the aeroplane models and MSFSBA never offered

COWS advertise "130+ random failures"; MSFSBA exposed 79, of which 21 were dead. Diffing
what the MODEL READS against what MSFSBA offers found 46 it had never heard of, and the
largest family is thirty `FAILURES_CB_*` — failures that POP A BREAKER.

They work: `FAILURES_CB_START` is read immediately beside the write that trips `CB_STR`.
And they are a different thing from the Breakers panel, which is where a pilot PULLS one;
this is where one goes on its own, in flight. Twenty-four map to a named breaker, read out
of the model rather than guessed.

They get no " Failure" suffix — "Starter Breaker Trip" already says what it is.

### Three failures were pointed at the wrong variable

`FAILURES_OIL`, `FAILURES_BLOCK` and `FAILURES_BYPASS` are read by the aeroplane as
`FAILURES_OIL:1`, `FAILURES_BLOCK:1` and `FAILURES_BYPASS:1`. MSFSBA wrote the UNINDEXED
name, which is a different variable nothing reads. Measured before the fix: arming the oil
pump failure with the engine running left oil pressure at 2.41 bar, then 2.40 eight seconds
later. It did nothing, exactly as reported.

⚠️ A write-stick test cannot catch this — the unindexed name accepts the write happily.
Only comparing against what the MODEL READS can, and the read must be told apart from a
WRITE: `(L:NAME` is a read, `(&gt;L:NAME` is not, and the model's own random-failure
injector writes every one of these.

Honest limit: with the name corrected, `FAILURES_OIL:1` still does not move oil pressure,
because the model reads it only in its failure ROULETTE and no system consumes it. The
name is now right; whether COWS model an effect for every failure they roll is theirs.

### Twenty-one failures that could never fail, and eleven duplicate rows

**The Monitor Manager listed eleven names twice or three times.** The cause is systematic
rather than sloppy: a breaker and a failure both carry the name of the THING THEY ACT ON,
so "Landing Light" appeared as the switch, the breaker and the failure with nothing to
tell them apart. In a panel the surrounding context supplies the difference; the Monitor
Manager is one flat list and has no context to lend. Breakers now read "Landing Light
Breaker" and failures "Landing Light Failure". Zero duplicates remain.

**Twenty-one of the seventy-nine failure switches did nothing at all** — MSFSBA wrote a
variable the aeroplane never reads. Reported as "the engine stuff and the brakes in the
failure panel don't seem to work", and for the engine ones that was exactly right.

The audit that finds them has to separate a READ from a WRITE, and two earlier attempts
got it wrong in opposite directions:

- Matching `(L:NAME)` alone missed the names read with a unit, `(L:NAME, Bool)`.
- Matching the name anywhere rescued `FAILURES_OIL` by SUBSTRING, out of
  `FAILURES_OIL_P_SENSOR` — a different variable entirely.
- Matching the name with a word boundary STILL rescued it, because the model's own random
  failure injector WRITES it. A write is not a read, and `(&gt;L:NAME` is the whole
  difference.

`FAILURES_OIL` is kept regardless: the final pass finds a genuine read of it, and deleting
something that might work is the worse error. The twenty-one removed are absent under
every reading.

⚠️ This is the playbook's own rule paying off: "the reliable existence test for an add-on
control is its own SOURCE" — a write-stick test passes happily on a variable nothing
consumes, which is precisely why these shipped.

### Turning the cursor OFF now says so

Turning it ON announces itself - the readback begins "Cursor on." - but turning it off
just produced the page title, which sounds exactly like a key that did nothing. A pilot
then presses the cursor again to check, which turns it back ON, and the two states become
impossible to tell apart by ear. The window remembers whether the last thing it SPOKE
began with "Cursor on." and prefixes "Cursor off." when that stops being true.

### Why the Radios panel KEEPS its typed entry, even though the bezel now works

A sighted pilot tunes a G1000 radio with the knobs and NOTHING ELSE - there is no keypad
on the aeroplane. So the bezel is the faithful path, and it now works: measured live, the
small knob steps 128.205 to 128.210 to 128.215 through the 8.33 kHz channel list and the
large knob steps 128.210 to 127.210. It cannot land between channels, so it is exact.

That looks like grounds for deleting the panel's typed entry under the
"anything doable on the display does not get a panel" rule. It is not, and the reason is
worth stating because the rule is otherwise right.

⚠️ THE KNOB IS EQUAL IN CAPABILITY AND WILDLY UNEQUAL IN EFFORT. A sighted pilot spins a
physical detent knob in one continuous motion and watches the number fly past - 128.210 to
122.900 is a flick of the wrist. The same move here is roughly SIXTY keypresses, each a
round trip. Parity of capability is not parity of access, and this codebase has taken that
position before: the altimeter's Ctrl+B and the NAV hotkey both describe themselves as
"the same convenience, not a replacement for the bezel".

So both stay. The bezel because it is what the aeroplane does; the typed entry because it
is what makes the bezel's RESULT reachable in one action rather than sixty.

What makes the knob path usable at all is that the radio settle announcer already
debounces: holding the key steps the frequency repeatedly and speaks ONCE, when it stops -
so a spin is one announcement rather than sixty.

### The radio boxes: which knob tunes what, and which COM transmits

Two facts a pilot needs before touching a radio knob have NO SimVar at all - they exist
only as display state:

- **which radio the knob will act on** (`select` on the frequency container)
- **which COM would actually TRANSMIT** (`transmit-selected` on the active frequency)

Nothing read either, so turning the NAV knob could retune NAV 2 while the pilot believed
they were on NAV 1 - which is exactly what happened during this work - and there was no
way whatsoever to know which COM was live. Both classes came from the class inventory, not
from a bug report.

`A.radios()` reads all four rows off the PFD:

```
NAV 1, active 110.30, standby 109.90, TUNING
NAV 2, active 110.50, standby 114.95
COM 1, active 122.900, standby 128.205, TUNING, TRANSMIT
COM 2, active 127.200, standby 124.850
```

Structure, read from the live display: `.navcom-frequencies left` holds the two NAV rows
and `right` the two COM rows; each row is a `.navcom-frequencyelement-container` carrying
`select` when the knob is on it, with `.navcom-freqstandby` and `.navcom-freqactive`
inside. There is also a `.navcom-freq-digit-input` per digit, hidden until an entry is in
progress - which is the hook for typing a frequency rather than spinning a knob.

### Find the markings BEFORE they bite: `tools/g1000-class-inventory.js`

Every reading fault on this aeroplane has had one shape: the aeroplane marks something
with a class the agent does not know, and the agent then reads a hidden copy, welds two
layouts together, or reports a live cursor as absent. Reading markup you already know
cannot find those. Enumerating what the instrument ACTUALLY uses can.

The tool lists every class token on a live display and flags the state-ish ones the agent
has never heard of:

```
node tools/g1000-class-inventory.js MFD ../MSFSBlindAssist/Resources/coherent-da40-g1000-agent.js
```

Its first run found three real problems that had NOT yet been reported:

| Class | Why it mattered |
|-------|-----------------|
| `hidden-element` | We handled `hide-element`. One letter apart, both mean not-shown, and neither uses `display:none` - so the unknown one was being read aloud |

### The read-back was racing the display, which made the window feel haunted

Three separate reports, one cause: pressing the cursor "does not say it is on until the

looked like a dead key until pressed twice.

A read showing nothing NEW - same cursor flag AND same text - is now retried rather than
believed. The flag counts on its own, because arming the cursor can leave the summary
identical for a moment, which is precisely the case that was being missed.

⚠️ Corrects TWO earlier verdicts in this file, both too broad. "Nothing edits a value" was

### `classList()` returns an ARRAY, and two call sites read it as a string

The single most productive bug of the session, because it caused two unrelated-looking
symptoms and both were reported as separate faults.

`classList(el)` returns `cn.split(/\s+/)` — an ARRAY. So `.indexOf("x")` on its result is
an EXACT-TOKEN search, which is right for a whole class name and wrong for a fragment:

- `classList(e).indexOf("row")` never matches `mfd-system-setup-row-right`, because no
  token IS "row". The cursor therefore read back with NO LABEL — "Cursor on. UTC" instead
  of "Cursor on. Time Format: UTC" — even though the climb logic above it was correct.
- `classList(d).split(" ")` in `pfdPopout` called `.split` on an array, which THROWS. That
  took `A.summary()` down with it, so it returned empty and every bezel key fell back to
  its own name: "next page group", "previous page", useless.

⚠️ Diagnosing this needed the AGENT'S OWN COPY, not the source. Reading the file proved
nothing — the logic there is right. What settled it was running the agent's `cursorField()`
and a fresh re-implementation of the same logic SIDE BY SIDE in one evaluate: the agent
said "UTC", the copy said "Time Format: UTC". Identical logic, different answers, so the
difference had to be in a shared helper.

Fragments now go through `hasClassContaining`, which is what all three sites meant. A
third latent instance was found by auditing every call: the group-box title hunt tested
`"groupbox"` against children classed `groupbox-container`, so it skipped only half of
them and could steal a group's text as a dialog title.

### Output mode + Shift is the SELECTED value, and only that

`ReadAltitude`, `ReadHeading`, `ReadSpeed` and `ReadFCUVerticalSpeedFPA` were made to

them for what they are — "Shift+A (FCU Altitude)", "Shift+H (FCU Heading)" — and the

MSL, H magnetic heading, S indicated airspeed, V vertical speed). Answering with both put
a number on a key that exists to say what the AUTOPILOT is aiming at, and buried the one
being asked for.

### Which knob does what, and why "I could not change it" was the labelling

Reported as: with the cursor on, `Ctrl+Left`/`Ctrl+Right` walked to a field like "Hard
Only" but ENT would not change it. That is correct G1000 behaviour and the wrong key.

On a G1000 the LARGE knob moves BETWEEN fields and the SMALL one CHANGES the value under

is the LARGE knob - it stepped the page GROUP FPL to NRST, and it stepped the cursor UTC →
Magnetic → Nautical between fields - while `FMS_Upper` is the SMALL one, stepping the page
within a group.

So the values are changed with `Ctrl+Up`/`Ctrl+Down`, and MSFSBA had been calling that
pair "the large knob" and `Ctrl+Left`/`Ctrl+Right` "the small knob" — exactly backwards.

The window now describes what the keys DO rather than which knob they are. A pilot who
cannot see the bezel has no use for its geometry; what they need is that one pair moves
BETWEEN things and the other CHANGES the thing you are on.

### One round trip per bezel key, not four

Still reported slow after the settle was cut, and the settle was never the problem. Each
press cost FOUR round trips to the Coherent debugger — summary before, key, wait, summary
again, then scrape — and the "before" read was added by the previous fix, making it worse.

compares it with what it last SPOKE and pays for a second look only then. In the common

### The autopilot: four reports, four different causes

**The flight director was telling a pilot to push when it meant pull.** Commanded pitch
read as a raw signed number, and MSFS reports pitch NEGATIVE for nose up. Established
rather than assumed: the aeroplane sitting on its gear reads `PLANE PITCH DEGREES` −2.90
with `ATTITUDE INDICATOR PITCH DEGREES` agreeing at −2.90, and a DA40 on its gear sits
nose UP. So the reported −3 was a command of three degrees nose UP, and the note
saying "Positive is nose up" had it exactly backwards. Both axes are now spoken as words -
"3.0 degrees nose up", "5.0 degrees right" - with the sign undone once, in
`DescribeFlightDirector`, and bank is left-positive in MSFS just as the visual-guidance
tone already has to undo.

**Commanded bank was reading floating-point dust.** Measured live at `1.43e-305`, which is
not a small angle. Anything under a twentieth of a degree now reads "wings level".

**The selected values never announced.** Moving a preselect on real hardware, or the G1000
changing one, was completely silent. They now ride the same settle timer as the radios and
the altimeter subscales, and for the same reason: an altitude knob steps 100 ft and a
heading bug one degree, so only the value the knob rests on is of interest. ⚠️ The settle
announcer formats radios to three decimals and everything else to none - an altitude read
as "9000.000" is its own kind of wrong.

**Output mode + A, H, S and V gave only the current value.** They fell through to the base
class. On an aeroplane with an autopilot that is half the question, so each now answers
with the current value AND the selected one in ONE utterance. That needed three new keyed
readouts (`DA40_ALTITUDE`, `DA40_HEADING`, `DA40_VERTICAL_SPEED`): like airspeed before
them, they are FIXED data definitions in `SimConnectManager` rather than keyed variables,
so there was nothing in `lastVariableValues` for a hotkey to look up and they would have
read "not available".

⚠️ **The GFC 700 Ctrl+3 status display is EMPTY on purpose, and that is the honest answer.**
It was emptied, restored, and emptied again - `ScansDoNotRepeatControls` objected both
times and was right: a control reads its own position when you tab to it, so repeating it
on the scan is duplication that also drags an announcing variable into a list meant to be
silent. Every meaningful item on this panel is something you OPERATE; there is no
read-only state left to sweep. The need behind the complaint is met twice instead - the
values announce themselves on settle, and the four readout hotkeys answer current and
selected together.

### The G1000 cursor was invisible, which made every setup page look dead

Reported as "the knobs don't let me go through and ENT doesn't click on anything - one
knob goes to the Navigraph stuff and back, the other to the flight plan catalogue", with
the suspicion that it was the pilot being ignorant. It was not.

On a real G1000 the FMS knobs change PAGES until you push the knob to turn the CURSOR on.
Only then do they move between fields and change values. So the Aux setup page behaved
exactly as designed - the knobs were paging, and ENT had nothing focused to act on. A
sighted pilot sees a cyan box appear; a blind one had no equivalent at all, and no
announcement ever mentioned the cursor's existence.

The cursor is the element carrying BOTH `cyan` and `highlight-select`. Requiring `cyan` is
what separates it from the page selector and the checklist lists, which use
`highlight-select` on its own.

`A.summary()` answers the cursor FIRST, ahead of everything else: when it is on, the pilot
is editing a field and the only thing a keystroke has to answer is which field and what it
now says. Verified live stepping the Display Units block:

```
Cursor on. DIS, SPD: Nautical(NM,KT)
Cursor on. ALT, VS: Feet(FT,FPM)
Cursor on. Temperature: Celsius(°C)
```

⚠️ Do NOT stop the label walk at the first ancestor whose class mentions `row`. The setup
page nests three - `row-right` inside `row-title-right` inside `row` - and the innermost
holds ONLY the value, so stopping there yields `Cursor on. UTC` with no label at all.
Climb until a row carries MORE than the value.

⚠️ The window's `AccessibleDescription` must be kept in step with `BezelKeys`. It was left

### The Engine page welded four boxes into four lines

Read from a live screen-reader dump, which is why the exact shape of the fault is known:

```
Fluids Coolant °C 82 Gearbox °C 81
Electrical Volts 28.2 Amps +17
Fuel System FFlow GPH 0.641°C 34 L R Main 14105 Gal 814
Fuel Calculator Gallons Remain 38.9 Gallons Used 0.3 Endurance 64+50 Range NM 0
```

No value on those lines can be arrowed to, and the Fuel System line is worse than
unreadable: `0.641` is a fuel flow of 0.6 beside a temperature of 41, and `14105` and
`814` are tank gauges welded to their own scale markings. Numbers that do not exist.

Every value in the lower half is an `.engine-page-gauge`, and there are FOUR shapes, not
one — which is why a single rule kept producing garbage:

| Shape | Structure | Read as |
|-------|-----------|---------|
| Vertical | `.gauge-label` + `.gauge-value` | `Coolant °C: 82` |
| Horizontal | one welded `.gauge-text` | split on the trailing number → `Volts: 28.2` |
| Text | `.ff-label` + `.ff-text` | `FFlow GPH: 0.6` |
| **Double** | `.gauge-text` holding `.left-value`, `.label`, `.right-value` | `°C: left 41, right 34` |

The DOUBLE gauge is the one that produced the invented numbers: it is one gauge with TWO
needles (left tank and right), and reading its parent runs three separate nodes together.
Same family as the two-needle EIS fuel gauges that already needed their own rule.

The horizontal split is anchored at the END of the string on purpose, so a label that
legitimately contains digits keeps them.

`Load %` is drawn TWICE — once in the EIS strip and once in the page body — and read back
to back it sounds like a stutter rather than two gauges, so adjacent duplicate lines
collapse. Adjacent only: two identical values far apart on a page are two real readings.

⚠️ This also fixes the INC/DEC/RST Fuel softkeys, which were reported as doing nothing.
They work — measured, softkey 5 stepped the totaliser 38.84 to 39.00 gal — but the press
read-back announces the first row that CHANGED, and while the whole fuel calculator was
one welded line there was no row for it to notice. `Gallons Remain` is now its own row.

## The COWS POH, read cover to cover, against what MSFSBA could say back

The package ships `Documentation/DA40 Series MSFS POH_1.1.0.pdf`. It is a SCANNED document with no
text layer, so it has to be rasterised and read off the page. It is also the only place several of
these aeroplanes' behaviours are written down at all, and every line below is a fact from it that
MSFSBA had no way to report — each one re-checked against the model's own XML before it was built,
because the manual and the model disagree in two places and the model is what the aeroplane does.

### Automixture (XLS) — a whole mixture regime the pilot cannot see

⚠️ **It is not a cockpit switch and there is nothing in the aeroplane to set.** The model DETECTS
the simulator's own mixture assistance — `(A:RECIP MIXTURE RATIO:1, ratio) × 100 == 9`, or the
package's own `AUTOMIXTURE_FORCE` — and ramps `L:AUTOMIXTURE` from 0 to 1 in fifths, dropping it to
0 in one step when the assistance goes away (XLS Logic 1805ff). Verified live: forcing it took the
variable to 1 within a tick and clearing it took it straight back to 0.

With it set, three things change and nothing on the aeroplane says so:

* **The mixture valve is bypassed.** Off, the lever drives `MIXTURE_VALVE` and the servo meters
  fuel. On, the lever picks an air/fuel TARGET — full forward 10 to 1, cut-off 100, a straight line
  between — and the model delivers it (Logic 341–437).
* **The engine cannot be flooded.** Every cylinder's outside charge is clamped at 2 g every tick,
  under the flooded line, so the entire hot-start problem the Priming panel exists for cannot
  arise. Priming is still required: the clamp is a ceiling, not a prime.
* **Set Best Mixture snaps to 72 %** instead of walking the lever down to 12.5 to 1.

It is a row on Mixture and Propeller, FIRST on that panel because it frames every row under it, and
it announces on the settled edge only — the ramp's intermediate fifths are never spoken.

### The XLS start and prime, in the POH's own numbers

1. Bottom edge of the throttle lever to the bottom of the "E"; fuel pump on.
2. Mixture full forward about five seconds. **Confirm a fuel flow above 4.5 gph.** How much is
   needed varies with engine and air temperature.
3. **Top** edge of the throttle to the bottom of the "E"; engage the starter. Push the mixture
   forward when the engine fires.
4. Not started within **10 seconds** — disengage, prime another 1–2 seconds, crank again.

⚠️ **Two of those are lever positions read off a printed label, which a blind pilot cannot use at
all**, and the two differ only by the width of the lever. What MSFSBA gives instead is the
quantities the procedure is really gating on: the fuel flow, the priming charge in grams per
cylinder against the model's own required figure, and the Start Readiness row. The POH's own tip is
worth keeping: *"there is no way of knowing which side of the mixture band you're at, so it is
easier to put yourself on the richer side"* — fuel is always removed while the engine turns, so a
rich start leans itself into firing.

The **priming assist** gauge, when the option is on, *"shows the amount of fuel in the whole
engine"*, and ⚠️ **during a hot start the engine may start BELOW the green area** — which is why
MSFSBA's own priming state is derived from the cylinders directly rather than from that percentage.

### Leaning, and the one limit the display does not draw

* Stoichiometric 14.7 to 1 is usable **only below 75 % power**.
* 12.5 to 1 gives more power than stoichiometric without damage, at the hottest cylinder heads —
  and the fuel servo is not perfect, so the delivered ratio can vary by up to 2 parts.
* Full rich is about **10 to 1**, safe at any power setting, with roughly **30 % of the fuel
  unburnt**.
* Climb full rich; lean only with the cylinder heads in range.
* ⚠️ **The POH recommends not exceeding 1350 °F EGT.** The bars carry no colour of their own, so
  the AFM publishes no EGT limit — but MSFSBA does annotate it, as an upper CAUTION with nothing red
  above it (see the AFM section below, which also corrects an earlier claim that it was left
  unannotated).
* For a faster cruise, enrich until the EGT falls **100 °F**.

### The NG's fuel system, and the one that throws fuel away

The tanks are **Main** and **Auxiliary**, not left and right. Excess fuel is drawn from the Main,
pumped through the engine and the Aux cooling loop and returned to the Main, which warms both.

* The **electric transfer pump** moves about **1 gal/min** Aux to Main and **stops itself at a
  sensor near 14 gal**.
* ⚠️ **EMERGENCY has no such sensor.** The POH: *"There is no sensor to stop the transfer of fuel.
  Fuel will be pushed overboard if the transfer isn't stopped."* The model agrees — the loop returns
  `FUEL_TEMP_ENG_FLOW:1` to the main every tick, clamped `19.5 min` (NG Logic 2048ff), and past that
  clamp the fuel is simply gone. The rate is `PROP RPM ÷ 2300 × 45 ÷ 3600` gallons per SECOND, about
  0.75 gal/min at 2300 rpm, which is the POH's "around 0.7 gal/min and depends on engine RPM".

The **Emergency Transfer** row on Fuel System reports it: nothing moving, the live rate a minute, or
the rate plus *"Main tank full, the transfer is going overboard"*. Nothing is announced — it is a
state the display can report, and the pilot scans for it.

⚠️ The POH says the break wire comes out after **clicking and holding for 3 seconds**. MSFSBA holds
for 1.5 s and that is MEASURED, not assumed: the model's own gate is a 1 Hz Update watching
`(L:FUEL_WIRE) 1 ==` against a 1-second press animation, and 1.5 s clears it every time.

### The NG's commanded RPM, and the cold morning that looks like a fault

The power lever sets the propeller speed as well as the load, on a curve the model spells out
exactly (NG Logic 176–195): **0 % → 2150**, falling to **20 % → 1800**, then climbing to
**92 % → 2100** and **100 % → 2300**, linear between. Below 20 % is "disc mode" — low power at high
RPM, a lot of drag, used deliberately to bleed speed or descend.

⚠️ **Below −10 °C the 92-to-100 % branch is skipped entirely and a flat 2100 is written**, so full
power on a cold morning reads 200 rpm low and looks like a governor failure. The POH's TEXT says
minus ten; its own chart bubble says ten. **The model settles it at minus ten** — the gate is
`(A:AMBIENT TEMPERATURE, celsius) -10 >`.

### The ECU test's six preconditions

Power levers idle, ECU voters to auto, propeller below 1100 rpm, weight on wheels, no errors, and
gearbox above 35 °C (the checklist asks for 38). MSFSBA already reports each with its live value and
names the ones not met rather than letting the button look dead. ⚠️ At a high-altitude airfield the
NG idles FASTER to avoid a flame-out, which can hold the propeller above the 1100 rpm precondition —
a real reason the test refuses that is nothing to do with MSFSBA.

The POH also gives a MANUAL run-up for when the test will not run: voter to A, confirm a smooth
engine; max power, confirm a good stable load and RPM with no ECU warnings; idle; repeat for B.

### Engine damage, and what actually inflicts it

The POH lists the causes and **they differ by airframe**:

| Both | XLS only | NG only |
|---|---|---|
| Improper warmup | Improper leaning | Sustained load above 92 % |
| Overheating | Shock cooling | Improper cooldown |
| Oil starvation | Lead fouling | |
| Overspeeding | | |
| Unfiltered dirty air | | |

The Austro is water-cooled and **immune to shock cooling**, which is why listing the Lycoming's
causes on the NG would be describing the wrong engine.

⚠️ **Resetting failures does NOT reset circuit breakers or accumulated engine damage** — a separate
Reset: Damage does that. And **Reset: Damage is also the only way to regenerate the performance
variations**, which is the documented escape from an engine whose randomly generated spread leaves
it unstartable. Both variation latches say so in their help.

### State saving, and the seven things it never carries

The aircraft restores its previous configuration on load, **except when the flight starts directly
on the RUNWAY or in the AIR**. And these are never saved at all:

canopy and window positions · parking position · alternator masters · ignition switch position ·
electric, alternator and engine masters.

None of that is guessable from the switch, which is why it is written down here.

### Engage Starter with Mixture — the option the NG's menu does not have

For pilots with no starter hardware: pulling the MIXTURE lever fully back engages the starter, and
pushing it forward once the engine fires completes the start. ⚠️ **The ignition must be at BOTH**
or the starter will not engage at all, which is the half that reads as a broken option. The model's
own gate is `INPUT_MIXTURE == 0` AND `STARTER_SWITCH == 3` (Both) or 4 AND `START_MIXTURE == 1` AND
the engine under 500 rpm.

⚠️ The POH prints the same MFD menu for both airframes and they differ by exactly two rows: this one
and Priming Assist. MSFSBA's options list was variant-blind and was offering the NG a switch its
aeroplane has not got; `BuildOptionVariables` now takes the variant.

### The aircraft ships a SECOND manual, and MSFSBA was throwing half of it away

⚠️ **The native checklist reader walked only a page's DIRECT children, so every checkpoint inside a
`<Block>` was silently dropped.** Measured against the installed package: the **XLS lost 105 of its
220 checkpoints — nearly half** — and the **NG 29 of 137**. What was missing is not filler:

* the XLS's entire **cruise power table** — four blocks, 51 rows of manifold pressure, RPM and fuel
  flow by altitude from sea level to 17,000 ft, which is the shaded "recommended band" of the POH's
  chart written out as text;
* the XLS's three **start procedures** (cold, flooded/hot, and the reprime when it will not go);
* both airframes' **weights, stall speeds, operating speeds and climb figures**;
* the NG's **Fuel System**, **ECU failures** and **High Altitude operations** notes;
* the XLS's whole **Starting tips** and **Leaning** sets.

Blocks are one level deep in both files and each carries a real heading
(`Cruise:65%, 9.5gph (Best Power)`), so the fix renders the heading and then walks the block — over
the page's children IN ORDER, because a page mixes loose checkpoints with blocks and the author's
sequence matters.

The XLS table also **confirms the POH transcription independently**: every cell the two documents
share agrees exactly (45 %/1800 at MSL 22.7 in, 55 %/2000 at 9,000 ft 21.1 in, 55 %/2400 at
13,000 ft 17.6 in, 65 %/2400 at 9,000 ft 20.7 in and 9.8 gph, 75 %/2400 at 5,000 ft 24.1 in). That
is a far stronger check on a figure read off a scan than re-reading the same image.

Among the tips it restores, the ones that answer a question this project had already asked:

* **"Use the same throttle position for priming every time"** — which is the real answer to the
  POH's unusable "bottom edge of the lever at the bottom of the E": what matters is repeating the
  position, not finding the printed one.
* **"If you need to hold the starter for long, the engine was flooded. If it does not start at all,
  it was underprimed."**
* **Hot start / vapour lock:** hot fuel boils out of the lines into the manifold, so the engine is
  *simultaneously flooded and underprimed*; prime briefly, use the flooded-start procedure, expect a
  long crank and a rough-running engine.
* **High altitude:** for every 1000 ft, about +1 % throttle and −5 % mixture, and advance the
  mixture slowly on start.
* **Warmup** 1000 RPM for 2 minutes, up to 2000. **Ground lean:** 1200 RPM, mixture back slowly
  until the RPM drops, then 1000.
* **Descent:** hold about 15 in of manifold pressure to avoid shock-cooling the Lycoming.
* **Fuel indications:** the tanks have THREE chambers and only TWO sensors, in the outer ones —
  which is the dead zone MSFSBA's XLS fuel rows already report (15.25 to 18.5 gal reads 15.25).

### The indication failures are per-airframe, and the XLS had the Austro's

⚠️ **Eleven XLS indication failures had no row anywhere, and four rows on the XLS could never
read anything but "No failure".** Grepped out of each model's own XML, the two sets overlap in
six and then diverge completely:

| Shared | NG only | XLS only |
|---|---|---|
| Oil pressure | Main tank temperature | **Tachometer** |
| Oil temperature | Aux tank temperature | **Manifold pressure** |
| Ammeter | Gearbox temperature | **Fuel flow** |
| Voltmeter | Coolant temperature | **Fuel pressure** |
| Main tank quantity | | **CHT, per cylinder ×4** |
| Aux tank quantity | | **EGT, per cylinder ×4** |

This matters more on this aeroplane than almost anywhere, because of the `DISP_` rule: a failed
indication **zeroes the variable MSFSBA reads** while the engine goes on running perfectly.
Verified live on the XLS at VCBI — `FAILURES_DISP_CHT:1 = 1` took `DISP_CHT:1` from 351 °F to
**0** while cylinder 2 still read 353 — so the Mixture panel showed a cylinder at zero and there
was nothing, anywhere, to tell that from a real reading.

The four the XLS was carrying are the phantom trap this project already knows: the Lycoming has no
gearbox, no coolant jacket and no fuel-temperature indication, and none of those variables exists
in its package, so those rows sat at "No failure" for ever about systems nothing watches. A row
like that is worse than no row, because a pilot scans it and is reassured.

⚠️ The READING side was already right — `DA40_XLS_RPM` and `DA40_XLS_MAP` deliberately bind
`DISP_*` so they fail with the gauge, and that was measured when the XLS panels were built. It was
only the failure PANEL that never gained the rows, which is a good illustration of how a gap
survives: the half that was thought about was correct, and the half nobody looked at was silent.

### The real Diamond AFM, against the arcs the add-on actually draws

The package ships the genuine Diamond manuals — `Documentation/XLS/60101e-r10-complete.pdf` (DA 40-180
AFM, revision 10) and its G1000 NXi supplement, plus the NG's. Unlike the COWS POH these have a text
layer, so `pdftotext -layout` reads them directly.

Section 2.5, ENGINE INSTRUMENT MARKINGS, against the XLS's own `panel/panel.xml` — which is what the
simulated G1000 DRAWS, and therefore what a sighted pilot in this add-on actually sees:

|---|---|---|---|
| Manifold pressure | green 15–30 inHg | green 13–30 | ~ |
| RPM | green 500–2405, caution to 2705, red above | green 500–2400, caution to 2700, red above | ~ |

figure is recorded here so a pilot operating to the book knows the two differ.

⚠️ `panel.xml`'s oil-pressure RED zone begins at **90**, overlapping its own green (55–95) and

**The EGT ceiling IS a band, not just a sentence.** `DA40_XLS_EGT_HOT` and the four per-cylinder
rows carry `BandRange(null, null, 1350, null)` — the COWS POH's recommended maximum as an upper
CAUTION with nothing red above it, because the AFM publishes no EGT limit at all. ⚠️ An earlier
version of this section said the 1350 "stays a sentence rather than becoming an invented band";
that was wrong — the band was already there, and it is the right shape, since the recommendation
is a caution and not a prohibition.

### One text-joining rule that had to be walked back

Binding a dash as glue closed `31 - AUG - 26` into a tidier date and, in the same stroke,
closed the CAS Alerts pane's `PITOT HT OFF - Pitot heat is off.` into
`PITOT HT OFF-Pitot heat is off.` — the dash there separates the abbreviation from its
meaning, and running them together is a real loss on the one pane whose whole job is
spelling an abbreviation out. **A dash is not glue.** The date reads perfectly well spaced;
the alert does not read well closed up. Brackets, commas and the degree sign do bind
(`Feet(FT,FPM)`, `Celsius(°C)`), and a run of underscores or dashes is a blank field —
`__:__` is one empty time, not `blank :blank`.

## Hotkeys

`BaseAircraftDefinition` implements **NO** readout hotkeys — it does a variable-map lookup
and nothing else, so every aircraft answers its own. Until `CowsDA40Definition.Hotkeys.cs`
existed, B and L simply did nothing on this aircraft.

The DA40 answers in its own terms, not an airliner's:

- **B** reads BOTH altimeters (G1000 and standby) in BOTH units. The AFM's descent check
  says "Altimeters (2) SET"; reading one would hide the other being wrong.
- **L** reads UP / T/O / LDG, the three positions this aeroplane has.
- **Shift+G** answers "Fixed gear" — true and useful, where "gear down" would be true and
  useless, and silence would look broken.
- **F** reads gallons AND litres, and names the NG's tanks Main and Auxiliary (the AFM is
  explicit; left/right would mislead).
- The characteristic-speed keys carry the DA40's V-speeds from `DA40Speeds`, because the
  Airbus set (green dot / S / F / VLS) does not exist here.

Readout hotkeys answer from the CACHE and must answer immediately — a key that silently
queues a request and says nothing is indistinguishable from a broken key.

⚠️ **The cache is keyed by the MSFSBA VARIABLE KEY, never by the SimVar name.**
`SimConnectManager` writes it as `lastVariableValues[varKey]`, so a lookup of
`"FUEL TANK LEFT MAIN QUANTITY"` or `"KOHLSMAN SETTING HG:1"` misses however correct the
name is. Every readout here was written that way, and the old `?? 0` fallback then turned
the miss into a reading: a full aeroplane reported *"Altimeter 0 hectopascals"* and
*"Fuel 0.0 gallons"*. `ReadNow` now takes a KEY and returns **null** rather than 0,
because a missing reading and a genuine zero are different facts and only the caller
knows how to say which it has.

⚠️ **And CONTINUOUS ALONE IS NOT ENOUGH.** Batch membership — the thing that actually
gets a variable polled and cached — is `Continuous && IsAnnounced && !ExcludeFromBatch`
(`SimConnectManager.Setup.cs`). A Continuous variable with `IsAnnounced` **false** falls to
the individual-data-def branch instead, which is only read on request, so it never reaches
the cache at all. That is why B, F and W still answered *"not available yet"* after being
pointed at the right keys: the keys were right and the variables were never being polled.

So every readout-support variable is `IsAnnounced` — and silenced instead in
`ProcessSimVarUpdate`, which returns `true` for the keys in `SilentCachedReadoutKeys` so
the generic announcer never speaks them. Announcing a tank quantity or a subscale on every
change would bury everything else. Two tests pin it: one that every cache-read variable is
batch-eligible, one that every silenced key still exists.

An OnRequest variable is polled only while its own panel is open, which is the other half
of the same rule and why the tank quantities live in `Shared.cs` rather than as OnRequest
copies owned by the Fuel System panel.

### Input mode

**Ctrl+B sets BOTH altimeters** from one prompt. This aeroplane has two and the AFM
descent check is *"Altimeters (2) … SET"*, so asking twice for the same number would be a
chore invented by the software rather than by the aircraft. Type hectopascals or inches —
the ranges cannot overlap, so magnitude says which was meant.

The two altimeters take **different transports**, which is the trap:

| | Written as | Verified |
|---|---|---|
| G1000 | `{mb × 16} (>K:KOHLSMAN_SET)`, unindexed | 29.85 → 29.92 |
| Standby | `L:KOHLSMAN SETTING HG:2` | already in use by the Standby panel |

Two spellings that do **not** work on the G1000 one: writing `L:KOHLSMAN SETTING HG:1` (a
name with a space and a colon is a stock SimVar, so that just creates a stray L:var nothing
reads) and the indexed `K:2:KOHLSMAN_SET`. The unindexed millibars×16 form is what the
aeroplane's own `Logic.xml` uses.

**Ctrl+N sets the NAV standby frequencies**, both radios in one pass, either cancellable.
The event is `NAV{n}_STBY_SET_HZ` in **raw hertz** — `NAV1_STBY_SET` with a BCD-ish 11030
left the value untouched, and `_STBY_SET_HZ` with a `MHz` unit hint set it to **zero**.
Tuning on the aeroplane is still the G1000's NAV knob; this is the same convenience Ctrl+B
is for the altimeters.

### Everything else is central

Audited action by action against `HotkeyAction`: heading, altitude, vertical speed, pitch,
bank, ground speed, IAS, Mach, AGL/MSL, OAT, squawk, NAV radio info, wind, METAR, nearest
city, checklist, track slots, taxi, GSX, SayIntentions, TCAS, teleports, hand fly and
visual guidance are all handled by MainForm or a service and are aircraft-agnostic — they
work on the DA40 without the definition doing anything.

The DA40 answers the ones that need aircraft knowledge (B, L, Shift+G, F, W, the
characteristic speeds, Ctrl+M, Ctrl+B, Ctrl+N). The remaining gaps are the deferred work:
`ReadDistanceToDest` needs an FMS destination, and the autopilot and checklist actions need
the G1000 window and the GFC 700.

### Two bugs from one Alt+Enter: the radios said everything three times, and the list said nothing at all

A single press of the radio window's swap key produced this:

```
118.590  118.590  118.590
118.575  118.575  118.575
118.555  118.555  118.555
List, nothing selected, 0 of 2
List, nothing selected, 0 of 2
...
```

Two independent faults, both in code written to fix earlier faults.

**⚠️ AN ASYNC READ-BACK THAT POLLS MUST BE SERIALISED, OR EVERY OVERLAPPING PRESS ANNOUNCES
THE SAME CHANGE.** `TurnRadioKnob` fires the knob event and then polls the display for up to
six rounds of 90 ms, because the read-back has to outlast a frame (the retry-if-unchanged fix
that stopped the window reading the frequency from *before* the keystroke). Nothing stopped
two presses overlapping. Each call took its own `before` snapshot, all of them were still
polling when the frequency finally moved, and each one independently saw its own `before`
differ from the new value — so one change was announced once per in-flight call. The pattern
is general: **a poll loop plus a per-call snapshot is a fan-out, not a race that resolves
itself.** The gate is a `SemaphoreSlim`, and it SERIALISES rather than dropping — a refused
press would be a key that silently did nothing, which is the failure the read-back retry
exists to prevent. Each press now waits its turn, reads its own change, and announces once.

**⚠️ `DisplayList.UpdateInPlace` COULD KEEP A SELECTION BUT NEVER CREATE ONE, AND AN EMPTIED
LIST REPEATS THAT FOREVER.** At `SelectedIndex == -1` the restore block cannot run (`selText`
is null and the `sel >= 0` fallback is unreachable), and the first-populate branch returned
without selecting anything at all. On its own that is a one-off. What makes it repeat is the
shrink loop: `lines` arriving empty drains the list to zero items, so the NEXT refill re-enters
first-populate — and a list that empties and refills on a poll re-announces "nothing selected"
every cycle. At -1 the reader also has no current item to speak and the first Space or Enter
does nothing, the same -1 the Monitor Manager's own rebuild had to fix.

**The floor is FIRST-POPULATE ONLY, and that scoping is deliberate.** An existing test,
`No_selection_before_the_update_means_no_selection_is_introduced`, pins the opposite for the
UPDATE path — a redraw must not create a selection the pilot never made, because that moves
focus in a list somebody may have tabbed away from on purpose. `DisplayList` is shared by every
aircraft, so that is not a stale assertion to override. A list that has never been populated has
no such position to respect; one being updated does. The two rules are pinned side by side
(`ARedrawStillDoesNotCreateASelectionThePilotNeverMade`) so a future reader meets both at once
rather than "fixing" one over the other.

### The knob PUSH said nothing, so "which COM am I about to tune" had no answer

Alt+Enter and Ctrl+Alt+Enter move the TUNING box between radio 1 and radio 2. That is how a
pilot CHOOSES which radio the next knob turn will retune — the knob acts on exactly one radio
per side, and turning it while the box is on the other one retunes a radio the pilot did not
mean to. Reported from the cockpit as Alt+Enter announcing nothing at all, with the pilot then
pressing the cursor key just to find out whether the window was still alive.

**⚠️ IT WAS A BEZEL KEY BY TRANSPORT AND THAT MADE IT A BEZEL KEY BY ANSWER.** The push does
reach the instrument the way the named bezel buttons do — through the page's own
`onInteractionEvent`, the exception to the exception that puts the four knob TURNS back on
SimConnect — so it had been sitting in `BezelKeys` since the bezel work. But what a bezel key
answers with is the PAGE TITLE, and a push does not change the page. The summary came back
byte-identical, the retry fired, the summary came back identical again, and the pilot got the
whole PFD read at them or nothing they could use. `RadioPushKeys` now carries the two pushes
with the socket transport intact and a different answer: **the radio the box landed on, and
that radio's standby**, because the standby is what the next turn will move.

**⚠️ REPORT THE ROW THAT GAINED THE MARKER, NEVER THE FIRST ONE THAT CHANGED.** A push changes
two rows — one loses `TUNING`, one gains it — and only the row that gained it is where the knob
now is. A first-changed-row scan names the radio the pilot has just left. `TUNING` and
`TRANSMIT` also ride the same row and only one of them says where the KNOB is, so the marker
test compares whole comma-separated fields rather than searching the row text.

**⚠️ AND IT NAMES A FAILED RADIO, WHICH IS NOT A BREACH OF THE SCAN-DON'T-ANNOUNCE RULING.**
That ruling governs UNPROMPTED speech — a state the display can report is scanned for, not
spoken at the pilot. This is the answer to a key the pilot just pressed, in the moment they
have selected that radio, which is exactly when a sighted pilot sees the red X appear under
the box. Silence here is what cost a session already: two pushes parked the box on a failed
COM 2, the knob then moved nothing, and the radios were reported broken.

`FirstChangedRadioField`'s rule that a cursor move must never be **dressed as a frequency**
stands unchanged and is still pinned. A cursor move is now named as ITSELF — "COM 2 tuning,
standby 118.205" — which is a different sentence from "COM 2 standby 118.205" said as though
the pilot had just tuned it.

### A typed box is a convenience, not the control — the five selected values had no knob

The pilot asked the general form of it: *are we able to do the same thing as the sighted pilots
do, the same way they do?* The course prompted it — MSFSBA could only ever **type** a course
into a box, and the cockpit has no such box; a sighted pilot turns the CRS knob and watches the
number step. Auditing the rest of the aeroplane the same way, the gap was not one control but
**all five GFC 700 selected values**: altitude, vertical speed, airspeed, heading bug and
course were every one of them typed-only.

The typed box hid the gap **precisely because it worked**. Nothing was broken, nothing was
missing from any scan, and the value ended up where the pilot wanted it — so no amount of
testing what MSFSBA *does* would have found it. Only asking what the *aeroplane* has does.

⚠️ **Both paths stay.** The Radios panel already keeps its typed entry beside a working bezel
for exactly this reason, and the reasoning transfers unchanged: typing is faster when you
already know the number, stepping is what you do when you are searching for it, matching a
clearance still being read to you, or centring a course on a radial you are intercepting.

The DA40's autopilot has no airframe variables at all, so these are stock events — and a wrong

|---|---|---|---|
| `VOR1_OBI_INC` / `_DEC` | `NAV OBS:1` | 45 → 46 → 45 | 1° |
| `HEADING_BUG_INC` / `_DEC` | `AUTOPILOT HEADING LOCK DIR` | 127 → 128 → 127 | 1° |
| `AP_ALT_VAR_INC` / `_DEC` | `AUTOPILOT ALTITUDE LOCK VAR` | 5000 → 5100 → 5000 | 100 ft |
| `AP_VS_VAR_INC` / `_DEC` | `AUTOPILOT VERTICAL HOLD VAR` | −1000 → −900 → −1000 | 100 fpm |
| `AP_SPD_VAR_INC` / `_DEC` | `AUTOPILOT AIRSPEED HOLD VAR` | 90 → 91 → 90 | 1 kt |

⚠️ **A step marks its VALUE's key, never its own.** The settle announcer watches the value, so
marking the button key would suppress nothing and every detent would be heard twice — once from
the step and once when the batch delivered the same change.

⚠️ **And a step announces NOTHING itself**, which is the opposite of what the typed setters do.
A typed set is one value the pilot already knows, so reading it back confirms it landed; a
detent is one of a burst, and announcing each would read a sweep from 5,000 to 9,000 ft as
forty separate numbers — the recital the radio read-back exists to avoid. The value's own
settle announcer already waits for the knob to stop and speaks the resting number.

**Not a gap, checked while here:** the DA40 has **no wipers and no rain repellent** — nothing
whole-word `wiper` anywhere in the package, and the only `rain` hits are the fuel `drain`s. The
real aeroplane has none either; the canopy sheds rain on airflow.

### Serialising the knob fixed the duplicate by making the aeroplane slow

The gate that stopped one frequency being announced three times held for the WHOLE operation —
read, fire, poll, announce — so each press owned it for 90 to 540 ms. Press the knob quickly
and **the radio itself fell behind the pilot's fingers**, because the write for press five was
queued behind four read-backs. That is the wrong trade: a knob is turned in bursts, and the sim
has to track every detent as it is pressed.

**⚠️ THE WRITE FIRES FIRST AND NOTHING IS QUEUED BEHIND IT.** `TurnRadioKnob` is no longer
async: it calls `ExecuteCalculatorCodeUnique` synchronously on the keystroke and returns. One
press or forty, at any rate, every detent reaches the radio the moment it is pressed.

**Only the ANSWER is coalesced.** Each press restarts a 260 ms settle; when the pilot stops, ONE
read says where they landed. A sweep from 119.660 to 118.515 is one sentence instead of
thirty-five — the same recital rule the bezel read-back and the autopilot knob steps follow.
The settle can be this short only because the frequencies are on per-var SIM_FRAME
subscriptions; a batch-fed value still has to outlast a batch period, and this one carries the
`FAST-SAMPLED` marker that records the exemption.

**⚠️ THE BASELINE IS CARRIED FROM THE PREVIOUS SETTLE, and that is what makes the press free.**
Reading "before" on each press would put a socket round trip ahead of the key and reintroduce
exactly the lag being removed. Each flush keeps its own read as the next burst's baseline, so
the diff costs nothing. It is seeded ONCE per window, on the very first press, because there is
no previous settle to carry — that single read is the only one that ever sits ahead of a
keystroke, and it must not overwrite a baseline a later press already established.

The knob PUSH keeps its gate and its poll: it is a discrete selection, not a burst, and it has
to read back which radio it landed on before it can name it.

**Both variants.** The GFC 700 and the G1000 are the same fit on the NG and the XLS — the
Lycoming changes the engine, not the avionics — so the knob path, the display windows and the
autopilot knob steps all serve both, and the tests now say so for both.

### The standby subscale had a knob in the cockpit and a typed box in MSFSBA

Same question as the GFC 700 values, same answer. `INSTRUMENT_Knob_Altimeter_1` is a real
clickable knob on the standby altimeter and MSFSBA could only ever type at it — Ctrl+B sets
both altimeters and the display window's baro keys drive the *G1000* subscale, so the standby
knob alone could not be turned.

⚠️ **The step is the model's own RPN, copied verbatim from `COWS_DA40NG_IN.xml`** — including
its clamps, which belong to the aeroplane and not to us:

```
CLOCKWISE      (L:KOHLSMAN SETTING HG:2) 0.01 + 31.5 min (>L:KOHLSMAN SETTING HG:2)
ANTICLOCKWISE  (L:KOHLSMAN SETTING HG:2) 0.01 - 28   max (>L:KOHLSMAN SETTING HG:2)
```

Verified live both directions: 29.92 → 29.93 → 29.92, with the `STATE_BARO2` mirror following
each step. Rewriting that expression — even "equivalently" — is how a step stops matching what
the knob does; the aeroplane is the only authority on where its own subscale stops. (The 28.00
to 31.50 range is also exactly what the typed setter validates, which is a good cross-check.)

⚠️ **Two write traps at once, both already known and both live here.** The input's name carries
a SPACE AND A COLON, so `SetLVar` refuses the calculator path and its data-def fallback lands on
the STOCK SimVar of that name — a different variable. And a second detent in the same direction
is a byte-identical calc string, which MobiFlight coalesces, so every other click of a sweep
would go missing without `ExecuteCalculatorCodeUnique`.

A detent announces nothing itself; the baro settle announcer already speaks the resting value in
both units.

**Not a gap, ruled by the pilot:** the power lever and the XLS's three Lycoming levers keep
their typed box and gain no steps. A lever is swept on hardware; the panel entry exists so an
exact percentage can be typed, which is a different job from stepping a detented knob.

### Two dead radio definitions removed

`DA40_RADIO_CRS1_SET` and `DA40_RADIO_HDG_BUG_SET` were defined, carried live setter cases, and
sat in **no panel, no display list and no hotkey** — a pilot could never reach either. They were
left behind when course and the heading bug moved to the GFC 700 panel, and they duplicated
`NAV OBS:1` and `AUTOPILOT HEADING LOCK DIR`, which is the batch-collision shape (harmless only
because both were `IsAnnounced = false` and so never batched). Two SimConnect definitions burning
budget to do nothing. Gone, with a test asserting they stay gone and that the GFC 700 pair remain.

### The standby altimeter had no readable consequence, and its knob was silent

Three defects on one instrument, two of them mine from an hour earlier.

**⚠️ "Backup Altitude" was the MAIN altimeter's reading.** `DA40_STBY_ALTITUDE` was bound to the
stock `INDICATED ALTITUDE`, which the sim drives from `KOHLSMAN SETTING HG:1` — the *G1000's*
subscale. So a pilot could set the standby subscale and the row labelled "Backup Altitude" would
not move: it reported the instrument they had **not** touched, under the name of the one they
had. Two altimeters disagreeing is the entire reason the aeroplane carries a standby, and the
disagreement was invisible. Measured live, ten clicks of the standby subscale on the ground:

```
L:PRESSURE_ALT_INDI    67.8 ft  ->  155.5 ft
A:INDICATED ALTITUDE   47.3 ft  ->   47.3 ft   (unchanged)
```

It now reads `L:PRESSURE_ALT_INDI`, the model's own needle position — what its altimeter strip
and 100-foot needle are both animated from — which also carries the instrument's simulated lag,
i.e. what a mechanical altimeter actually shows.

**⚠️ The new knob was completely silent, and its test asserted the silence was correct.** The
detents called `MarkBaroSetByUs()`, copied from the typed setter beside them. That mark opens a
3000 ms own-write grace inside which `FlushBaroSettle` returns early — so the one channel that
would have spoken the resting value was switched off by the very press that needed it. The mark
is *right* for the typed setter, which announces the value itself and would otherwise say it
twice; it is exactly wrong for a detent, which announces nothing and **depends** on the settle.
Shipped, then caught by re-reading rather than by hearing it.

**⚠️ The two altimeters were not separately tunable from any panel.** The standby had a typed
box; the G1000 subscale had no panel control at all — only Ctrl+B, which sets **both** together,
and the display window's knob keys. So the one thing a standby is for could not be done from the
panels a pilot browses: set them differently, or notice that they already are. Both now sit
together on Standby Instruments, main first, each with its typed box and its knob. The G1000
step is the PFD bezel's own event, verified live from *outside* the display window
(29.899 → 29.910 inHg), which is what makes a panel button possible at all.

**No keyboard shortcut was added, deliberately.** `Ctrl+Shift+Left/Right` were free and would
have paired neatly with the existing `Ctrl+Shift+Up/Down`, but those keys only exist inside the
display window — outside it Windows owns them — so a chord that works in one window and does
something unrelated everywhere else is a worse answer than a panel control that always works.

### Eleven controls took a number and rendered as a bare button

Reported from the cockpit as *"why are there buttons instead of just setters where you insert
the value you want"* — about the fuel tank loads, which were written as typed gallon
transactions and could not be typed into.

**⚠️ `MainForm.PanelBuilder` GIVES A TEXT BOX ONLY TO A KEY THAT CONTAINS `_SET`.** The widget
is chosen in this order: `RenderAsButton` → button; `RenderAsReadOnlyStatus` + units → read-only
box; two or more `ValueDescriptions` → combo; **key contains `_SET`** → text box plus a Set
button. A numeric control matching none of those falls through to a plain button, which fires
the setter with no value the pilot chose. It is a NAMING CONVENTION doing load-bearing work,
which is exactly the kind of rule that breaks silently — the code looks right, the setter reads
`value` correctly, and only the widget is wrong.

Asking the definition rather than the source found **eleven on the NG, eight on the XLS**:

| Control | What it takes |
|---|---|
| `DA40_FUEL_MAIN_LOAD` / `_AUX_LOAD` | gallons |
| `DA40_XLS_FUEL_LEFT_LOAD` / `_RIGHT_LOAD` | gallons |
| `DA40_LIGHT_INSTRUMENT` / `DA40_LIGHT_FLOOD` | brightness percent |
| `DA40_CABIN_HEAT` / `DA40_CABIN_AIR` | lever percent |
| `DA40_FAIL_COOLANT_LEAK` / `_TURBO` / `_BOOST_LEAK` | failure severity percent |
| `DA40_OPT_TIMER_EXPIRED` | option value |
| `DA40_G1000_BARO` | subscale (added an hour earlier, same trap) |

All renamed to carry `_SET`. The lighting ones are the sharpest illustration: the docs already
said *"those two are BRIGHTNESS KNOBS, not on/off toggles"*, so the knowledge was recorded and
the widget still could not carry a number.

`CowsDA40ControlRenderingTests` now asks the definition — for both variants — whether every
panel control matches a widget rule at all, so the next one is caught by the suite rather than
by a pilot tabbing onto a button that does nothing useful.

**The main altimeter gets a separate write-only `_SET` key** rather than being renamed: it
binds no SimVar of its own (so it does not duplicate `DA40_G1000_BARO`'s data definition), and
`CurrentValueSourceKey` puts the live value in the box on focus. It is exempt from the
"every settable switch announces" rule because the announcing is done by the readout it is
seeded from, which carries the baro settle announcer.

### Ctrl+B gets two fields, and the step buttons come back off the panel

**Ctrl+B was one field that wrote both altimeters.** That is the common case and it is still
one keystroke away — type the same number twice — but a single field could not express the
state the standby exists to reveal: the two set differently. A pilot could not set them apart
deliberately (a QFE standby against a QNH main) and could not correct one without silently
overwriting the other with the same value. It now has **two fields, each seeded with what that
instrument currently reads**, so opening the dialog is also how you read them side by side.

⚠️ **The announcement names both when they differ and neither when they agree.** A disagreement
is either deliberate or a mistake, and both readings have to be spoken for the pilot to tell
which — "Both altimeters set" over two different numbers would hide exactly what the standby is
for. Agreement within a hundredth of an inch (the knob's own detent) is rounding, not
disagreement, and reads as one phrase.

`ValueInputForm` gained optional extra fields to do it. **Additive by construction**: with none
declared the offset is zero and every control keeps its exact position, tab index and accessible
name, so no other aircraft's dialog changes at all. Every extra field is validated *before*
anything is written — a dialog that set one altimeter and then rejected the other would produce
the disagreement it exists to reveal, by accident.

**The four altimeter step buttons are gone, on the pilot's ruling**, and the reasoning is worth
keeping because it is not "buttons are bad": if you can type the value you can just type it, and
four extra buttons on a seven-row panel is clutter every pilot tabs past forever to reach the
two rows that do the work. The knob feel still lives where it belongs — the PFD bezel keys in
the display window.

⚠️ **Not a general repeal.** The GFC 700's ten step buttons stay, because there the panel is the
**only** way to step those five values; no bezel key reaches them. The rule that came out of it:
**a step button earns its place only where nothing else can turn that knob.**

### "1453 number" — the unit field is a data-definition unit, not a label

A read-only readout renders `{value:Format} {Units}`, and an L:var **must** be registered
`Units = "number"` or SimConnect converts from its own base unit and returns garbage — this
aeroplane's own rule, learned on the standby subscale. The two demands collide: the honest unit
for the data definition is the wrong word to say out loud. So the unit a pilot hears comes from
`TryGetStandbyDisplayOverride` and the one SimConnect sees stays `number`. It only surfaced when
Backup Altitude moved off the stock `INDICATED ALTITUDE` (feet, a real unit) onto the model's own
`PRESSURE_ALT_INDI`.

While in that chain: `TryGetXlsMixtureDisplayOverride` was listed **twice**. Harmless — the
second call can never run — but it is dead code in the one place a reader looks to find out
which override owns a key.

### FS Copilot's own definition is a coverage test, and it found nine readouts

`FsCopilot_v1.2.1/Definitions/COWS_DA40NG.yaml` is a **third-party inventory of this airframe**,
written by someone who had to enumerate the state that matters or two networked aircraft would
drift apart. Diffed against every variable this definition binds, it found **nine readouts
MSFSBA was not reading**.

⚠️ It catches a class the interaction-surface audit **structurally cannot**. That audit
enumerates `<Component ID>` entries — CLICKABLE things — and not one of these nine is a control.
They are things the aeroplane *computes and shows*, which is exactly the blind spot a
click-surface sweep leaves.

⚠️ **Every one was read live before it was defined.** A variable named in a third-party file is
a claim, not evidence — the same standard the stock autopilot events were held to. Measured on
the ground, engine off, avionics master off:

| Variable | Read | Why it matters |
|---|---|---|
| `COWS_MINIMUMS_ALTITUDE` | 0 | the PFD minimums bug; 0 genuinely means not set |
| `FUEL_TOTALISER_REM` | 37.31 gal | the MFD fuel calculator — **not** the tanks |
| `FUEL_TOTALISER_USE` | 0.09 gal | fuel counted as burned |
| `FUEL_TEMP_C:1` | 29.74 | **diesel waxes when cold** — an operating limit here |
| `PITOT_TEMP` | 29.94 | the only thing that says the element is actually warming |
| `ELEC_BATT_ECU_CAPACITY` | 145.95 | the FADEC's backup battery |
| `ELEC_BATT_SURF` | — | surface charge, recovers after a load is removed |
| `AFCS_POWER` | 0 | is the autopilot *powered* — a different question from engaged |

⚠️ **`AFCS_POWER` reading 0 is not a fault and is itself a confirmation.** The avionics master
was deliberately off, and `systems.cfg` puts the AFCS on `bus.2` (`BUS_AVN`). Agreeing with the
bus wiring is what makes it trustworthy.

⚠️ **`ELEC_BATT_ECU_CAPACITY` carries no unit, deliberately.** It measured 145.95, so it is not
a percentage, and nothing in the package names its unit. A bare number a pilot can watch fall is
honest; a guessed unit presented as fact is not.

⚠️ **The units are declared `number` and spoken through an override** — every one is an L:var,
and an L:var with a converting unit makes SimConnect convert from its own base unit and return
garbage. Same trap as "1453 number", one layer earlier.

⚠️ **The fuel and pitot rows are NG-ONLY.** They were measured on the NG; the XLS is a different
engine with a different fuel system and its own YAML. Claiming a reading exists on an airframe it
was never measured on is the exact failure this exercise exists to avoid — the XLS gets its own
pass against `COWS_DA40XLS.yaml`. Electrical and the autopilot are shared (same battery model,
same GFC 700) and appear on both.

**Also worth knowing:** the YAML's `L:FSC_*` variables are FS Copilot's OWN sync plumbing, not
the aircraft's, and must be filtered out before the diff means anything.

### Three announcements that were ours, not the aeroplane's

⚠️ **"Autopilot Pre-flight Test: running — do not touch the disconnect" was COACHING.** The tail
told the pilot what not to do, which is the one thing an announcement must never carry. That the
disconnect fails the test is documented here, not spoken at the pilot. Now just **"running"**.

⚠️ **"Hide G1000 FMA: FMA shown"** said FMA three times in one breath, and named a control after
an *action* while its value contradicted it. Now **"G1000 FMA: Shown"** / **"Hidden"** — named
for the state.

⚠️ **The bus voltages were announced twice per session, the second time interrupting.** The
avionics master armed the same read-back as the electric master and re-read *the same three
voltages* — main, essential and battery are on the battery side and do not move when the
avionics bus comes up (`bus.1 = BUS_BAT` carries the displays and the first radios;
`bus.2 = BUS_AVN` only the second set). The avionics master keeps its own switch announcement,
which is the whole of the news: there is no avionics-bus voltage to report, so a read-back could
only repeat the battery side.

### `NoteXlsMixtureChange` was dispatched twice

⚠️ Unlike the duplicated line in the display-override chain — harmless, because the first call
returns — this one is a **void call with side effects**, so every update ran the mixture logic
twice: a lean-assist peak, a red-box entry or a fouling warning could announce twice, and any
latched state advanced two steps per update.

### Sweeping the whole FS Copilot definition, and what the method got wrong twice

The first pass took nine readouts. Asked to take **everything**, the sweep found 44 more L:vars
and 10 SimVars — and, more usefully, exposed two flaws in how the diff was being done.

**⚠️ FLAW 1: "not in the package" needed a BINARY scan, not a text grep.** The first check read
only `.xml/.js/.cfg` under the NG folder. A variable used by a WASM gauge or living in another
folder would read as absent while being perfectly real. Re-run across **all 687 files, binaries
included**, the verdict held: sixteen names FS Copilot lists are genuinely not in the installed
package — `AFCS_FAIL_AIL/ELE/TRIM` (the real ones are `FAILURES_AFCS_*`, already bound), the
whole `FAILURES_SENS_*` family, `LIGHTING_PANEL_1`/`_GLARESHIELD_1` (the real inputs are
`LIGHT POTENTIOMETER`, already bound) and `ATT_CAGE_IsDown`. Binding those would have produced
sixteen rows sitting at 0 forever, quietly reporting "no failure" about systems nothing watches
— worse than absent, because a pilot would scan them and be reassured.

**⚠️ FLAW 2: A BUTTON'S `Name` IS ITS OWN KEY, so reading the Name column alone finds phantom
gaps.** The L:var a button writes lives in its *setter*, not its definition. `RESET_ALL`,
`RESET_BATT`, `RESET_ECU` and `RESET_FAILURES` all looked unbound and were duly added — as
**four duplicate buttons for resets this definition already had**, all six of them, matching the
MFD's own Reset Menu. Caught only because `ResetIsAlwaysAvailable` pins the exact list. The rule:
**a candidate must be searched for in the SOURCE, not just among Names**, before being called
missing.

**⚠️ AND THE COLLISION TEST DID NOT COVER THIS AEROPLANE.** `VarNameCollisionTests` exists
precisely to stop two batched keys sharing a SimVar name — which drifts every later struct slot —
and it names the A380 and A32NX and nothing else. So the green suite proved nothing about the DA40
during the one change most able to introduce a collision: forty-odd variables added in a sitting.
`CowsDA40VarNameCollisionTests` now covers both variants.

**Controls: there are none to add.** The YAML's settable entries are the whole control surface it
exposes, and all eight real ones are already driven by MSFSBA — TO/GA, pitot heat, avionics
master, alternate static source, fuel pump and engine master (the two lighting ones are the
names the package does not have). Everything else in the file is read-only state. That is the
evidenced answer to "are there new controls", not an impression.

**⚠️ EVERY ENGINE TEMPERATURE READS A `DISP_` VARIABLE — the value the G1000 DRAWS, not the
measurement.** This project already learned that once ("take RPM from `PROP_RPM_SENS:1`, never
`DISP_PROP_RPM`, the display var is quantised") and applied it to RPM **alone**. Oil, coolant,
gearbox, oil pressure and cabin-heat source all still come from `DISP_OT`/`DISP_WT`/`DISP_GT`/
`DISP_OP`/`DISP_CT`. Measured live: `GC_GEARBOX_TEMPERATURE:1` = 80.79 against the drawn value.

The measured and sensor values are now bound **beside** the drawn rows, never swapped in over
them — a gauge's coloured BAND is looked up from the value the gauge carries, so replacing the
source under a band lookup would silently change which arc a reading falls in, on the one thing
that says whether a temperature is safe. Three readings now exist per temperature and they answer
different questions: what the gauge draws, what the physics computed, and what the sensor
reports — and a sensor disagreeing with the physics beside it is how a failed sensor shows itself.
**Which the panels should PREFER is a decision for the pilot, not a refactor to slip in.**

### How would a sighted pilot see this? The gauge — and the gauge can fail

The question was which of three readings to trust for the engine temperatures: `DISP_OT` (87.59),
`WC_TEMP_OIL:1` (86.698) or `WC_TEMP_OIL_SENS:1` (86.698). The sensor tracks the physics exactly;
the drawn value sits ~0.9° high on a *cooling* engine, which is needle **lag**, not quantisation.

**⚠️ COWS's own `Documentation/Failures.txt` settles it, and a live injection proved it.** The
engine-indication failures are named for the drawn variables:

```
--Engine Indications--
L:FAILURES_DISP_OT,   Loss of oil temperature indication
L:FAILURES_DISP_VOLT, Loss of VOLTS indication          ... and ten more
```

Injected on the live aircraft:

| | before | after |
|---|---|---|
| `DISP_OT` with `FAILURES_DISP_OT = 1` | 87.59 | **0** |
| `WC_TEMP_OIL_SENS:1` at the same moment | 86.70 | **86.70** |
| `DISP_VOLTS` with `FAILURES_DISP_VOLT = 1` | 28.14 | **0** |

**`DISP_` IS the indication.** So reading the physics or the sensor on a panel would show a blind
pilot a perfect oil temperature off a **dead gauge** — defeating an entire failure class COWS
deliberately modelled, and handing them something the sighted pilot cannot have. The existing
`DISP_` bindings were right all along, and the "every engine temperature reads a drawn value"
finding is **retracted**; the six gauge-backed readouts added on the strength of it were removed
again the same hour.

**The line that came out of it — apply it to the XLS and the DA42:**

- a quantity **with** an indication is read from the **indication**, so that when the indication
  fails the blind pilot loses it exactly as the sighted pilot does;
- a quantity with **no** indication at all (block temperature, radiator temperature, the
  thermostat, damage, health) may be exposed from the model — there is no indication to defeat,
  which is the same judgement already made for engine damage and health.

**Can the sensors fail?** Not as sensors — `FAILURES_SENS_*` is one of the sixteen families FS
Copilot lists that this package does not contain. What fails is the **indication**, and MSFSBA
already binds ten of those. The three the doc adds (`FF`, `FP`, `RPM`) are **XLS-only**, so the
NG's set is complete.

⚠️ **The RPM rule survives only by luck of the airframe.** "Take RPM from `PROP_RPM_SENS:1`,
never `DISP_PROP_RPM`" bypasses the indication — and `FAILURES_DISP_RPM` does not exist on the
NG. On the **XLS it does**, so that rule would read straight through a failed RPM indication
there and has to be re-decided rather than inherited.

### Message audit

Every spoken literal and state label in the DA40 sources, scanned for coaching and for length:
332 strings, and after the fixes **both checks come back empty**. Two announcements were
rewritten — a refusal may name the blocking **condition**, never the remedy:

- *"Turn the engine master off first. With it on this button runs the ECU test instead."* →
  **"Engine master is on. This button runs the ECU test instead."** What the button *would* do
  stays, because that is the hazard rather than advice: the same hold runs a different function.
- *"Fuel valve is locked to Main. Break the safety wire first."* → **"Fuel valve is wired to
  Main."** The wire is a control on that same panel.

And two `ValueDescriptions` labels were shortened, because a label is read **every time the row
is scanned** — prerequisites and directions belong in this document, not in a label:
*"Off, on the Engine page menu"* → **"Off"**, and *"Idle, needs the pump on and the engine
stopped"* → **"Idle"**.

`CowsDA40MessageAuditTests` pins both rules by scanning the sources with comments stripped — the
reasoning around a message is free to say anything, the message itself is not.

### Asked "is the NG complete?" — no, and the check found one of my own

Applying the indication rule to my own additions found **fuel temperature**: `FUEL_TEMP_C:1/:2`
are the physics behind `DISP_FT:1/:2`, which this definition already reads and whose failure it
already binds (`FAILURES_DISP_FUEL_T:1/:2`). Measured:

| | before | after `FAILURES_DISP_FUEL_T:1 = 1` |
|---|---|---|
| `DISP_FT:1` (the indication) | 36.73 | **−63.26** |
| `FUEL_TEMP_C:1` (the physics) | 36.81 | **36.81** |

Removed. It was missed on the first pass because diesel waxing made fuel temperature look like
safety information rather than a duplicate of a gauge — which is exactly why it is now a test
and not a note (`CowsDA40IndicationFailureTests`).

⚠️ **THE FAILURE SIGNATURE IS NOT ALWAYS ZERO.** Oil temperature and volts both went to 0; fuel
temperature goes **off-scale negative**. Never detect a failed indication by comparing against 0.

⚠️ **ONE KNOWN EXCEPTION, older than the rule and deliberate.** `DA40_FUEL_MAIN_ACTUAL` /
`_AUX_ACTUAL` read the stock quantity SimVar while `DISP_FUEL:1/:2` is the indication and
`FAILURES_DISP_FUEL:1/:2` is bound — so a failed fuel indication **is** read around. That was a
considered decision: the NG gauge SATURATES at 14 US gal (AFM 2.14.4; measured 18.78 actual
against 14.0 indicated), so the indication cannot answer "how much fuel is aboard" even when
working perfectly. Pinned so the exception stays visible rather than becoming precedent.

- **PFD: 26 page-specific unread items across 15 pages**, plus 10 chrome items.
- **MFD: 222 page-specific unread items across 17 pages**, plus 15 chrome items.

⚠️ **That number is NOT 222 defects.** The tool reports CANDIDATES, and the ranking shows why:
the worst pages are all **list-driven** — Aux/System Setup (60), Nearest Intersections (30),
Nearest Airports (28), Active Flight Plan (16). A G1000 list is navigated with the cursor and
the agent emits the FOCUSED item, so a fifty-row list reads as fifty unread items even when
every one of them is reachable by arrowing. The two PFD entries are the same shape: the SID and
STAR pick-lists on Select Departure / Select Arrival.

⚠️ **But it is not all noise, and one part matches a gap this doc already records.** System Setup
draws ten boxes of which only five register controls — "BARO Transition Alert, Airspace Alerts,
Arrival Alert, Flight Director and GPS CDI render values and register nothing, so the knob walks
past them for a sighted pilot too". A sighted pilot can still **read** those five; a blind pilot
navigating by cursor cannot reach them, and the sweep confirms the scrape does not emit them
either. That is a genuine "visible but unreadable" hole, not a list artefact.

Other candidates worth triage rather than dismissal: the Engine page's Fuel Calculator block
(Gallons Remain / Gallons Used / Endurance / Range NM / Total Service — the underlying totaliser
values are now bound as panel readouts, but the page's own rendering is not emitted) and the
checklist's "Go to Next Checklist?" prompt.

**Reproduce with:** `node tools/coherent-coverage.js AS1000_MFD` (and `AS1000_PFD`), with the sim
running, the aeroplane loaded, MSFSBA closed so the Coherent socket is free, and the
database-acknowledge screen already dismissed — a sweep run against that screen reports every
page unread.

### The CAS set, enumerated from the aeroplane rather than assumed

29 active annunciations in `COWS_DA40NG/panel/panel.xml`: 15 Warning, 6 Caution, 8 Advisory.
The monitor is TEXT-based, so it covers all of them without a per-message binding and cannot
miss one COWS adds later; `CowsDA40CasCoverageTests` pins the extractor against the real set.

⚠️ **`PITOT HT OFF` is COMMENTED OUT in the installed package and cannot be raised** — yet it was
reported from the cockpit. Worth settling: either the build differs, or something is reading a
stale block, which is the failure mode this monitor already had once.

⚠️ **COWS shipped a corrupted annunciation and it is REACHABLE.** One Advisory's `<Text>` is the
YouTube URL fragment `qnkuBUAwfe0&t=107s`, tagged `<!--A_L_GLOW_SIM-->` (copied from the real
GLOW ON at line 463), and its condition is **airspeed above 182.88 kt for six seconds** — so it
is an overspeed advisory whose text someone pasted over. The PFD really does show that string,
and MSFSBA reads it out phonetically. Left as-is deliberately: MSFSBA reports the aeroplane, and
"fix the vendor's typo" is not its call — but it is worth reporting upstream.

### `ELEC_BATT_SURF` runs 0 to −2, and calling it a charge was wrong

The model clamps it (`-2 max 0 min`), drives it NEGATIVE while the battery is loaded, recovers it
toward 0 when the load comes off, and feeds it into the charge factor as `-SURF/6`. So **zero is
the rested state and −2 is the worst case** — the opposite reading to the obvious one, and
"Battery Surface Charge: 0.0" would have read as a flat battery. Renamed to **Battery Surface
Depletion**; the range is above.

### The System Setup gap is real, diagnosed, and NOT fixed — read this before trying again

⚠️ **`A.M.fields()` walks `view.scrollController.controls[]`, so it can only ever see REGISTERED
controls.** Aux System Setup draws ten boxes and registers five — BARO Transition Alert, Airspace
Alerts, Arrival Alert, Flight Director and GPS CDI render their values and register nothing. This
doc already recorded that the knob walks past them *for a sighted pilot too*, which is true and
was taken as the end of the matter. It is not: a sighted pilot still **reads** those five, and
the row list never carried them either, so a blind pilot could reach five of ten.

⚠️ **A FIX WAS WRITTEN AND REVERTED, and the reason is worth more than the patch.** Adding an
`A.pushReadOnlyBoxes` pass over visible `.groupbox` elements (skipping any title the field walk
already covered) **did not move the number** — System Setup stayed at 60 unread across the
change. So the mechanism above explains why the boxes are missing, but something further along
also stops a groupbox pass reaching them, and that was not established. Shipping it would have
put an unproven change into the file every display readout depends on.

⚠️ **THE SWEEP IS NOT DETERMINISTIC — measure twice before believing a delta.** Three MFD runs
gave **222, 252 and 252**, with no code change between the first two. The aeroplane is live
(temperatures drifting, clock advancing, GPS moving), so page content differs run to run. A
single before/after pair proves nothing; the 222 in the first report of this sweep was the low
end of that spread, not a baseline.

**What a real fix needs:** a live probe of `A.rows()` with the MFD actually on System Setup —
printing what the fields block emits and what a `.groupbox` walk finds under `A.M.view().el` —
rather than another patch reasoned from the source. The tool measures the result; it cannot say
why a pass found nothing.

### Whatever a sighted pilot can see, we can see — the backstop, and the softkey inventory

**The pilot's ruling, stated plainly:** if a sighted pilot has the information, a blind pilot
has it too; the choice of whether to *say* it is then ours to make. "Not clickable by anyone" is
not a defence — not being able to SELECT something is the aeroplane treating both pilots alike,
not being able to READ it is not.

⚠️ **`A.rows()` now ends with `A.pushUnreadBoxes`**, a backstop that emits every visible
`.groupbox` the view registers no control for, each marked **", dimmed"**. Measured against
`tools/coherent-coverage.js`: Aux / System Setup **60 → 38** unread.

⚠️ **THE FIRST VERSION SCORED BETTER AND WAS WRONG.** Comparing the box's text against the rows
already built scored System Setup at **3** — but it marked TEN boxes dimmed, including Date /
Time, Display Units and COM Configuration, every one of which the pilot can select perfectly
well. The field walk emits `Date: 10 - SEP - 26` while the box's own text concatenates
differently, so the match failed and a selectable box was announced as unselectable. **Telling a
pilot they cannot reach something they can is worse than the gap this pass exists to close** —
and a better coverage number was what made it look right. 38 with five correct boxes beats 3
with ten wrong ones.

The five boxes that were unreachable now read: **BARO Transition Alert** (Off, Altitude 18000 FT,
Level FL180), **Airspace Alerts** (Altitude Buffer 200 FT, CL B/TMA/AWY, CL C/CTA, CL A/D,
Restricted, MOA), **Arrival Alert** (Off, Distance 1.0 NM), **Flight Director** (Format Active,
Single Cue) and **GPS CDI** (Format Allowed Auto, System CDI 2.00 NM).

⚠️ **THE FIRST ATTEMPT AT THIS SHIPPED AS A NO-OP AND WAS REVERTED. Three things make it work
and the first version got two of them wrong:**

1. **It runs LAST**, over the rows already built, so every dedicated reader (the flight plan
   page, the WPT pages, the nearest lists, the checklist) has had its say and its content is
   there to match against. Comparing against `fieldRows()` alone re-emits whole pages a bespoke
   reader already read properly.
2. **It queries `document`, NOT `A.M.view().el`.** A view is a view-service object, not a DOM
   subtree — `querySelectorAll` on it finds nothing, and the pass silently does nothing. That is
   exactly how the first version passed review, shipped, moved no number, and had to be pulled.
3. **It matches on TITLE AND VALUES**, because a box whose title happens to appear in a row is
   not necessarily a box whose content was read.

⚠️ **THE COVERAGE TOOL CANNOT DETECT DUPLICATION** — it measures only what is UNREAD, so a pass
that says everything twice scores perfectly while making the window unusable. Checked separately
across all 17 MFD pages: **zero duplicate lines on sixteen, one on Active Flight Plan** (which
predates this pass), row counts 14 to 55.

⚠️ **AND THE FIRST DUPLICATION CHECK WAS TOO WEAK TO CATCH IT.** It compared whole lines, so the
ten-dimmed-boxes bug — whose duplicates differed only in INDENTATION — passed it cleanly. The
check now normalises before comparing. A text-similarity test cannot answer a structural
question: the right test for "is this box selectable" is **does the view register a control in
it**, which `A.M.fields()` answers directly by reporting each field's groupbox title.

### `tools/g1000-page-inventory.js` — softkeys and drawn-but-unread, page by page

New, because the coverage sweep is deliberately blunt and its number drifts run to run. This
answers two exact questions with crisp answers: **which softkeys does this page have** (twelve
slots, relabelled per page, a blank slot being a real answer), and **what does it draw that the
field walk cannot see**. Two API traps it documents: `A.softkeys()` returns OBJECTS, not strings
(reading it as strings prints twelve `[object Object]`), and `A.pageList()` is a newline-joined
STRING for the pilot's jump list — the real enumeration is `A.M.pageMap()`.

The full MFD softkey inventory is reproducible with
`node tools/g1000-page-inventory.js AS1000_MFD`. Worth knowing from it: **Engine** sits on
softkey 1 of every page but the two EIS pages, **Checklist** on 12 of most, **Aux / Navigraph
Settings has no softkeys at all**, and the EIS Engine page's 4/5/6 are the fuel totaliser's
DEC / INC / RST keys.

### One word for one idea: "dimmed", app-wide

The A380 MFD, the A380 MCDU and the flyPad browser view all mark an unselectable control by
suffixing **", dimmed"** to the item. This display said **", not available"** in three places and
**" (not available)"** in a fourth, so a pilot flying both aeroplanes met three spellings of one
fact. All four are now "dimmed", and the new backstop uses the same suffix rather than a section
heading — a heading also reads as somewhere the cursor might go, which is the opposite of true.

⚠️ **One survivor, deliberately.** `A.M.goPage` still RETURNS the string `"not available"` for a
page key the display does not know. That is a different thing — a page that is absent, not a
control that is greyed — and it is read by the display window as a return code rather than spoken.
